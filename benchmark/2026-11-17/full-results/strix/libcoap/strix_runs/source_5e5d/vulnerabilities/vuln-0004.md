# Uninitialised heap memory disclosed through re-assembled Block1 body when the block size grows mid-transfer

**ID:** vuln-0004
**Severity:** MEDIUM
**Found:** 2026-11-17 11:22:31 UTC
**Target:** libcoap 4.3.5 (source snapshot), src/coap_block.c
**Endpoint:** CoAP Block1 transfer reassembly (server side), UDP/TCP port 5683
**Method:** CoAP (PUT with Block1 option)
**CWE:** CWE-457
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Low

## Description

`libcoap` re-assembles a Block1 request body into a heap buffer but never initialises the bytes the client did not send. A client can force such a gap by increasing the SZX (block size) between blocks: the write offset of the next block is computed from the new SZX (`num << (szx + 4)`), so it jumps past the data already received, while the received-block bookkeeping still treats the transfer as complete. The application is then handed a body of `total_len` bytes in which the gap holds whatever was previously in that heap memory. With the example server's echo mode the leaked bytes are returned to the client in the 2.01 response.

## Evidence

ASan build (`-fsanitize=address,undefined`), server started with `-L 3`, `-e`; response to the final block (hex, payload starts after `80ff`):

```

be00bebebebebebebebebebebebebebebebebebebebebebebebebebebebebebebebebebebebebebebebebebebebebe
```

body[0:16] = `AAAAAAAAAAAAAAAA` (client data), body[16:64] = ASan's uninitialised-malloc fill (`0xbe`, with the low byte of the neighbouring allocation at index 17), body[64:80] = `BBBB...` (client data). The gap is 48 bytes that the client never transmitted, yet they are part of the 128-byte body reported to the application and copied into the 2.01 response.

Plain `RelWithDebInfo` build (no sanitizer), heap-grooming variant, 40 iterations, `-L 3`:

```
iter 34 hole=3000000000000000434343434343434343434343434343434343434343434343 ... (41 non-zero)
iter 24 hole=100000000000000080000000000000007081d1a735560000f061d1a735560000 ... (15 non-zero)
iter 22 hole=0000000000000000a09600a8247f000000000000000000000000000000000000 ... (7 non-zero)

```

`4343...` is the payload of a previous, already completed transfer freed earlier in the same process; `a09600a8247f0000` / `7081d1a735560000` are pointer values leaked the same way. The identical gap is produced on the default `-L 1` configuration through the public `coap_block_build_body()` helper (example resource `/example_data`): 26 of 40 iterations returned non-zero gap bytes.

No sanitizer error is raised for these requests — the defect is use of uninitialised heap memory, not an out-of-bounds access, so it does not abort the process and is invisible without content inspection of the body.

## Impact

An unauthenticated client that can send UDP or TCP CoAP requests obtains heap contents it never supplied: on a non-sanitised build, 38 of 40 attempts returned previously freed request payloads and heap/library pointers inside the 2.01 response body, and the same buffer is handed to any application using `COAP_BLOCK_SINGLE_BODY` or the public `coap_block_build_body()` helper. The leaked region is attacker-sized (up to the configured maximum body size) and repeatable, so it can be used to read freed heap data such as other peers' request payloads and pointer values that help defeat ASLR. Integrity and availability are not affected by the PoC.

## Counterevidence

Checked for a control that would stop the leak before the body is handed out: (1) `coap_get_block_b()` only enforces SZX != 7 and NUM <= 0xFFFFF, no cross-request consistency; (2) the existing `lg_srcv->total_len_set` guard only rejects blocks that reach *past* the last block, and the growing-SZX block is the last block itself, so it passes; (3) `blocks_add_entry()`/`check_all_blocks_in()` track NUM values only, never byte coverage, so a gap is indistinguishable from a complete body; (4) no memset of the body buffer exists on either the allocation or the growth path, and `coap_new_binary()` clears only the header, not the data area. Tested both the `-L 3` (library re-assembly) and `-L 1` (application re-assembly through the public helper) configurations, and both a sanitised and a plain build to exclude an ASan-only artefact. The only precondition is a client that is non-compliant (RFC 7959 requires the SZX to be reduced only by the server and the NUM/offset mapping to stay consistent), which is not a mitigation because the client is the attacker. Residual limitation: the amount of disclosure depends on what the allocator hands back; on a freshly grown heap the gap may be zeros, which is why the report demonstrates it with heap reuse (38/40) rather than on the first request.

## What Would Change This Severity

Demonstrating that a long-lived secret (for example DTLS PSK material, OSCORE keys or another peer's full request body) is present in the disclosed heap region would raise this to high severity (C:H); conversely, if the delivered body is only ever consumed without being stored, echoed or acted upon, the impact reduces to uninitialised-memory use with no observable disclosure and the finding drops to low.

## Technical Analysis

Two library routines combine to produce the disclosure.

**1. Offset derived from the per-request SZX.** In `coap_handle_request_put_block()` the transfer's block size is recorded once, when the reassembly state (`lg_srcv`) is created:

```c title=src/coap_block.c startLineNumber=3693 endLineNumber=3697
    max_block_szx = COAP_BLOCK_MAX_SIZE_GET(session->block_mode);
    if (!block.bert && block.num == 0 && max_block_szx != 0 &&
        max_block_szx < block.szx) {
      lg_srcv->szx = max_block_szx;
    } else {
      lg_srcv->szx = block.szx;
    }
```

but the offset of every block is computed from the SZX carried in that individual request:

```c title=src/coap_block.c startLineNumber=3601 endLineNumber=3601
  offset = block.num << (block.szx + 4);
```

and again while marking the logical blocks as received:

```c title=src/coap_block.c startLineNumber=3787 endLineNumber=3790
    block.num++;
    offset = block.num << (block.szx + 4);
```

Nothing checks that `block.szx` still equals the established `lg_srcv->szx`, so a request sequence of `NUM=0/SZX=0` (16 bytes at offset 0) followed by `NUM=1/SZX=6` (1024 bytes at offset 1024) is accepted. `blocks_add_entry()` records NUM 0 and NUM 1, `check_all_blocks_in()` therefore reports the transfer as complete, and the body is passed to the application with `body_length = lg_srcv->total_len` (2048 in the example), although offsets 16..1023 were never written. RFC 7959 2.2/2.4 only permits the server to reduce the block size and requires the NUM/offset mapping to stay consistent, so this sequence is exactly the kind of malformed input a parser must reject.

**2. New buffer space is not initialised.** `coap_block_build_body_lkd()` allocates the body with `coap_new_binary()`, which allocates `sizeof(coap_str_bin_union_t) + size` bytes and does not clear the data area, then only `memcpy()`s the bytes of the current block into it:

```c title=src/coap_block.c startLineNumber=4594 endLineNumber=4596
  if (body_data == NULL && total) {
    body_data = coap_new_binary(total);
  }
...
    coap_binary_t *new = coap_resize_binary(body_data, offset + length);
    if (new) {
      body_data = new;
      memcpy(&body_data->s[offset], data, length);
```

The same function is public (`coap_block_build_body()`) and is the documented way for applications to re-assemble a body, so applications outside the library inherit the same uninitialised bytes. In the shipped example server the `-L 1` (default, application re-assembly) path uses this helper, and the `-L 3` (`COAP_BLOCK_SINGLE_BODY`) path receives the library's `lg_srcv->body_data` directly as `pdu->body_data`, so both configurations are affected.

The combination is confirmed by ASan, which reports the gap as its own uninitialised-malloc pattern (`0xbe`), and by a plain `RelWithDebInfo` build, which returns previously freed payloads and pointer values.

## Proof of Concept

1. Start the shipped example server with echo mode and library-side single-body re-assembly on a loopback port: `coap-server -A 127.0.0.1 -p 15689 -e -d 10 -L 3`.
2. From a single UDP socket (so both requests belong to the same session), send a Block1 PUT to `/test` with `NUM=0`, `SZX=0` (16 bytes), `M=1` and a 16-byte payload. The server answers 2.31 Continue with `Block1:0/M/16`.
3. From the same socket send the final block with `NUM=1`, `SZX=6` (1024-byte block unit), `M=0` and a 64-byte payload. The offset of this block is computed as 1 << 10 = 1024 while the first block ended at 16.
4. The server answers 2.01 Changed. Because `-e` is set, the response body is the re-assembled 128-byte body with the block option removed.
5. Observe that bytes 16..63 of the response body were never sent by the client. On an ASan build they contain the allocator's `0xbe` uninitialised pattern; on a normal build they contain stale heap data (see the grooming variant below).
6. Repeat steps 2-3 after a completed 128-byte transfer of a known pattern: previously freed payload bytes and pointer values appear in the gap in most attempts.

````python
def nib(v):
    if v < 13:
        return v, b""
    if v < 269:
        return 13, bytes([v - 13])
    return 14, b"\x00" + bytes([v - 269])

def opt(delta, value):
    dn, dext = nib(delta)
    lnb, lext = nib(len(value))
    return bytes([(dn << 4) | lnb]) + dext + lext + value

def put_block(num, szx, more, payload, tok, mid):
    hdr = bytes([0x40 | len(tok), 0x03, mid >> 8, mid & 0xff])
````

## Remediation

Reject a Block1/Q-Block1 request whose SZX differs from the block size already established for that transfer (except for the first block), because the NUM to offset mapping of an in-progress transfer is fixed and a size increase leaves a gap that is never filled. Additionally, never expose never-written bytes: zero the body buffer when it is created and zero the newly added tail whenever the body is grown, so that a gap is defined data rather than heap contents. Both changes are needed — the first enforces the RFC 7959 block-sequence rule, the second guarantees the "every byte of the delivered body was either supplied by the client or is zero" invariant for any future path that computes an offset.

## Fix Verification

**1. Security closure.** Patched copy of the tree built out-of-tree (`RelWithDebInfo`, no sanitizer, `-DENABLE_DTLS=OFF`) and exercised with the same PoC.
* `-L 3` (library re-assembly): the second request is now answered `4.08` with the diagnostic "Block size change" instead of `2.01` plus a sparse body; the re-assembly state is dropped, so the client can restart. Grooming runs: 0/40 iterations produced any leaked byte (unpatched: 38/40).
* `-L 1` (application re-assembly through the public `coap_block_build_body()`): 0/40 leaked iterations (unpatched: 26/40); the gap now contains only zero bytes.
* Re-traced the sink: with the SZX check in place the only way bytes reach the body is a block whose SZX matches the established one, and with the zero-fill any remaining unwritten byte is 0, so `pdu->body_data[0..total_len-1]` can no longer contain heap contents.

**2. Bypass review.** (a) Sibling call sites of `coap_block_build_body_lkd()`: the server Block1 path (`coap_block.c:3860`) and the client Block2 path (`coap_block.c:4971`) both inherit the zero-fill, so a Block2 response with a sparse/overlapping NUM sequence is covered as well. (b) Other offsets computed from an attacker-supplied SZX: `offset = block.num << (block.szx + 4)` at lines 3601 and 3787 — the first is the non-re-assembly path, where the library hands each block to the application and cannot know the application's buffer; that path is now bounded by the zero-filled public helper for the applications that use it, which the `-L 1` test confirms. (c) Alternate malformed inputs tried: a *decreasing* SZX mid-transfer (`NUM=0/SZX=6` then `NUM=1/SZX=2`) tiles the already-written region and stays accepted (correct); `block.num == 0` restarts and retransmissions are still accepted, because the check is scoped to `num != 0`; BERT is excluded (`block.bert`), and BERT offsets already advance in fixed 1024-byte steps. (d) Q-Block1 uses the same routine and the same offset expression, so it is covered by the same check.

**3. Preserved behaviour.** A compliant transfer (`NUM=0/SZX=2/M=1` then `NUM=1/SZX=2/M=0`, 64+64 bytes) still completes with `2.01` and the correct 128-byte body; the server-side SZX reduction path (first block larger than the configured maximum, `lg_srcv->szx` clamped, client renumbering to the returned SZX) still matches the check because it compares against the clamped value; error semantics for the existing rejects (`Missing interim block`, `Block after last block`, `Content-Format mismatch`) are unchanged.

**4. Repository checks.** `tests/testdriver` built from the patched tree and run to completion: 18 suites, 203 tests, 0 failures, 1500 assertions passing (DTLS disabled in that build, so the 19 `t_tls*` tests are absent; the same suite passes 240/240 in the DTLS-enabled sanitizer build of the unpatched tree). The patched library also compiles cleanly with the project's default warning set. Gap: the DTLS-enabled sanitizer build was not rebuilt from the patched tree, so the fix has not been exercised together with the GnuTLS backend or against the interoperability examples (`etsi_iot_01`, `coap-client`).

## Assumptions

The attacker can send CoAP requests to the server (no authentication is required at the CoAP layer) and can send two or more Block1 blocks within one session. The application re-assembles the body, either by enabling `COAP_BLOCK_SINGLE_BODY` (example server `-L 3`, library performs re-assembly) or by calling the public `coap_block_build_body()` helper (example server `-L 1`, application performs re-assembly). The echoing behaviour is only used to observe the leak; the uninitialised bytes reach the application in any embedding.
