# PureDB IPv6 allow/deny IP rules are silently discarded, bypassing per-user deny lists

**ID:** vuln-0001
**Severity:** LOW
**Found:** 2026-11-17 10:20:01 UTC
**Target:** /workspace/source
**Endpoint:** src/pure-pw.c (record writer) -> src/log_puredb.c (record reader and rule evaluation)
**CWE:** CWE-863
**CVSS:** 3.1
**Confidence:** High
**Fix Effort:** Low

## Description

PureDB records are colon-separated and pure-pw writes per-user allow/deny IP patterns verbatim, while the daemon reads the fields positionally. An IPv6 address literal contains colons, so configuring one writes extra fields: the deny pattern is silently dropped and a client from the denied address still authenticates. The allow-list variant shifts a fragment into the time-restriction field, which denies every login and also drops the allow restriction.

## Evidence

## Impact

A per-user network restriction configured through the documented administrative interface is silently not enforced. Any client holding valid credentials for the account can authenticate from the address the administrator intended to deny - and, because the rule disappears rather than degrading, from any other address as well. For allow lists the account becomes unusable, denying the legitimate user while the address restriction is also lost. The 1.0.54 changelog states that IP access rules now support IPv6 patterns; that does not hold for IPv6 address literals.

## Counterevidence

The IPv6 matcher itself is correct and reachable through hostname rules (verified: -R localhost blocks both 127.0.0.1 and ::1), so this is not a general failure of IPv6 support. IPv4 rules are enforced correctly in the same test (control: -R 127.0.0.1/32 denies 127.0.0.1), and a well-formed record with no rules authenticates normally, so the defect is specific to address literals surviving the positional record format. Exploitation requires a non-default configuration step (an IPv6 literal rule rather than a hostname or IPv4 rule) plus valid credentials for the restricted account, which is why attack complexity is rated High. No path was found by which an unauthenticated client benefits.

## What Would Change This Severity

If the accounts protected by such IPv6 rules are administrative or the rule is the only control restricting them, the demonstrated loss of confidentiality becomes High (base 5.9); if no deployment configures IPv6 address literals, the practical impact is limited to a silent configuration error.

## Technical Analysis

A PureDB (virtual-user) record is one line of fields separated by PW_LINE_SEP (`:`). The daemon reads it positionally in pw_puredb_parseline(): position 13 is the allowed local IP, 14 denied local IP, 15 allowed client IP, 16 denied client IP and 17 the time restrictions. pure_strtok2() in src/utils.c performs a plain single-character split with no quoting or escaping, and the writer add_new_pw_line() in src/pure-pw.c prints each pattern with `%s` without validation:\n\n```c title=src/pure-pw.c startLineNumber=711 endLineNumber=731\n    if (pwinfo->allow_local_ip != NULL) {\n        fprintf(fp2, "%s", pwinfo->allow_local_ip);   /* allowed local ip */\n    }\n    ...\n    if (pwinfo->deny_client_ip != NULL) {\n        fprintf(fp2, "%s", pwinfo->deny_client_ip);   /* denied client ip */\n    }\n```\n\nWith `-R '::1/128'` the two colons of the literal add two separators, so the deny column at position 16 is empty and `1/128` is pushed to position 18, which the parser never reads. access_ip_check() therefore sees an empty deny list and returns success for every address; pure-pw show also reports an empty deny list, so the misconfiguration is invisible to the operator. With `-r '::1/128'` (allow list) the fragment lands in the time-restriction column, time_restrictions_check() cannot parse it and returns -1, so every login is denied while the allow restriction is also gone.\n\nThe IPv6 CIDR matcher in access_ip_match() (ipv6_cidr_match() plus inet_pton(AF_INET6, ...)) is correct but cannot be reached with an IPv6 literal through the product's only rule-writing interface, because such a literal can never occupy a single colon-separated field. IPv6 hostname rules contain no colon and do work.

## Proof of Concept

Create a virtual user whose client-IP deny list contains an IPv6 literal: `pure-pw useradd <login> -f <passwd> -u <uid> -g <gid> -d <home> -R '::1/128'`.\n3. Create a control user with an IPv4 deny rule: `-R '127.0.0.1/32'`.\n4. Inspect the generated password lines: the IPv6 record has extra fields (`...:::::1/128:`) and an empty deny column; the IPv4 record is well formed.\n5. Log in as the IPv4-denied control user from the IPv4 loopback address: the server answers `530 Login authentication failed`, proving the deny mechanism itself works and only the IPv6 rule was dropped.\n8. Log in as the user configured with `-r '::1/128'` (allow list): the server answers `530` because the shifted fragment became an unparsable time restriction.

## Remediation

Validate the four IP-pattern fields when the record is written so a value containing the record separator is rejected with a clear error instead of corrupting the record, and make the daemon treat a record with more fields than the format defines as invalid so any corrupted or hand-edited entry fails authentication rather than dropping its restrictions. Longer term, add an escape encoding for the field separator to the PureDB record format (writer and reader together, with a version marker) so IPv6 literals can be stored and evaluated, and document hostname rules as the supported way to express IPv6 restrictions in the meantime. Operators that already configured IPv6 literals should re-check affected accounts with pure-pw show and migrate to hostname rules.

## Fix Verification

Applied both changes to a copy of the tree and rebuilt: `make -j4` and `make check` both exit 0 with no new compiler warnings; the fix_before blocks were dumped with line numbers to confirm they match the file character-for-character.\n\nSecurity closure: re-ran the proof of concept against the patched daemon with the same corrupted database that previously allowed the login. The IPv6-denied user from `::1` now answers `530 Login authentication failed` (was `230 OK`); the allow-list user still answers `530`; the IPv4 deny control still answers `530`.\n\nBypass review: the daemon-side check is a single "no fields remain after the last column" test inside the one parse function used by every PureDB login, so it catches corruption introduced through any field (client IP, local IP, home, gecos) and any number of extra separators, not only the literal used in the proof of concept. Records that end before the IP columns still take the pre-existing early-return path, and well-formed 18-field records still authenticate (verified with a permissive user). Patched `pure-pw` rejects any of the four patterns containing `:` and writes nothing, while IPv4 and hostname patterns are written unchanged.\n\nPreserved behaviour: permissive logins from `127.0.0.1` and `::1` still succeed, IPv4 deny rules are still enforced, and a rejected write leaves the password file untouched.\n\nGaps: no exhaustive corpus of historical record shapes was executed (legacy short records were reasoned from the code plus the permissive-record test), and the complete escape-encoding fix was described but not implemented. Verification ran on a copy of the source tree; the same steps apply to the live tree.

## Assumptions

The deployment uses the PureDB virtual-user backend and the administrator expresses a per-user network restriction with an IPv6 address literal through pure-pw (-i/-I/-r/-R). The attacker holds valid credentials for the restricted account and can reach the service from the address that was meant to be denied. IPv6 hostname rules (patterns without a colon) are unaffected and are evaluated correctly.
