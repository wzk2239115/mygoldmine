# Pre-authentication use-after-free of a shared MQTT session on ClientId reuse

**ID:** vuln-0002
**Severity:** MEDIUM
**Found:** 2026-11-17 10:13:36 UTC
**Target:** sol MQTT broker (C, v0.18.5) - src/
**Endpoint:** MQTT CONNECT handler (src/handlers.c connect_handler, session lookup at lines 400-405)
**CWE:** CWE-416
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Medium

## Description

The handler that lets a second connection resume an existing MQTT session by ClientId does not take a reference on that session, while the connection that created it releases the only reference when it disconnects. The session object is therefore freed while the second connection is still connected and still using it, and that connection then reads and writes freed heap memory. Any unauthenticated peer can set this up with two connections and one disconnect.

## Impact

A second unauthenticated connection can obtain a ClientId's session, be told by the broker that it resumed that session (`session_present=1`), and keep using a session object that the broker frees as soon as the first connection disconnects. The demonstrated consequence is that the surviving connection then operates on freed heap memory: it copies 64 bytes of freed session data into a new subscriber record and links that record into a subscription list that teardown already destroyed. Under AddressSanitizer this aborts the connection thread; on the plain optimized build it completes silently, leaving the connection reading and writing a 328-byte heap block that is now reusable by any other allocation in the process. Demonstrated integrity impact is limited to that corruption of freed memory, and no service interruption was observed on the production build; what would turn this into code execution is reclaiming the freed block with attacker-controlled bytes, which was attempted but not achieved because the two connections are served by different event-loop threads and the chunk was not handed back within the test window.

## Counterevidence

The strongest case against a high rating was pursued and largely holds. (1) "The production build does not crash": confirmed - on the plain optimized build the exact four-step sequence completes without a signal, so the demonstrated availability impact is limited to instrumented builds; the production consequence observed is silent operation on a freed 320-byte session block rather than a crash. (2) "The freed block cannot be reclaimed by the attacker": the size class matches a retained PUBLISH packed to 320 bytes, and six gdb attempts to reclaim it with attacker bytes all failed because the free and the later allocation ran on different event-loop threads (the chunk sat in another thread's tcache) and AddressSanitizer quarantines the block in the instrumented build; controlled reuse is therefore an unproven possibility, not a claim. (3) "The reference count must be doing something else": the only `INCREF` of a `client_session` in the whole tree is the creation site, and the only `DECREF` is the clean-session teardown in `client_deactivate`, so there is no other owner that could be holding the block alive - the reuse branch genuinely shares a refcount-1 object. (4) "MQTT expects ClientId takeover, so this is intended": takeover is intended to make the *old* connection lose the session, not to leave it dereferencing freed memory; the surviving connection is told `session_present=1` and then reads, and writes into, a block whose lists `session_free` already destroyed. (5) "The read is harmless because only an identifier is copied": the following statement pushes the topic into the freed `subscriptions` list, so the defect is a use-after-free write, not only a read. Severity is set from what was demonstrated - a pre-authentication memory-safety violation with silent heap corruption and an instrumented-build abort - and not from the worst case reachable after a successful heap-grooming step.

## What Would Change This Severity

Demonstrating that the freed 320-byte session block can be reclaimed with attacker-controlled content - for example by showing that a retained PUBLISH of the same size class lands on the chunk and that the corrupted subscription list or reference-count free callback is exercised - would raise this to high or critical by turning silent corruption into controlled memory writes; conversely, if the session were made reachable only through a mechanism that already proves ClientId ownership (a credential bound to the ClientId), the pre-authentication rating would drop to a post-authentication issue at medium.

## Technical Analysis

Session lifetime is reference counted (`struct client_session` embeds a `struct ref`, `src/handlers.c:111`), but the reference count does not model the number of connections that share a session. `connect_handler` takes the only reference when it creates a session, and the reuse branch assigns the same pointer without taking one:

```c title=src/handlers.c startLineNumber=399 endLineNumber=420
    // First we check if a session is present
    HASH_FIND_STR(server.sessions, cc->client_id, cc->session);
    if (cc->session && c->bits.clean_session == true)
        // Clean session true, we have to clean old session, if any
        HASH_DEL(server.sessions, cc->session);
    else if (cc->session)
        session_present = 1;
    ...
    if (c->bits.clean_session == true || !cc->session) {
        cc->session = client_session_alloc(cc->client_id);
        INCREF(cc->session, struct client_session);
        HASH_ADD_STR(server.sessions, session_id, cc->session);
    }
```

Line 405 is the defect: the resuming connection is told it owns the session (`session_present = 1`, CONNACK `0x01`) and `cc->session` points at it, yet the count stays at one. The single reference is then released by whichever connection created it, in the clean-session branch of teardown:

```c title=src/server.c startLineNumber=430 endLineNumber=438
    if (client->clean_session == true) {
        if (client->session) {
            topic_store_remove_wildcard(server.store, client->client_id);
            list_foreach(item, client->session->subscriptions)
            {
                topic_del_subscriber(item->data, client);
            }
            HASH_DEL(server.sessions, client->session);
            DECREF(client->session, struct client_session);
        }
```

`DECREF` drives the count to zero, `session_free` destroys both lists and frees the block (`src/handlers.c:89-98`), and the second connection keeps a dangling pointer. Every handler that touches `e->client->session` then operates on freed memory; the runtime trigger lands in the SUBSCRIBE path, where `subscriber_new` copies the freed `session_id` and `list_push` links into the destroyed `subscriptions` list:

```c title=src/handlers.c startLineNumber=588 endLineNumber=593
        struct subscriber *sub = subscriber_new(e->client->session, s->tuples[i].qos);
        ...
                    list_push(e->client->session->subscriptions, t);
```

Two further consequences of the same missing ownership model are visible in the surrounding code. The `clean_session == true` discard at line 403 removes the map entry without releasing its reference, so repeatedly connecting with an existing ClientId and `clean_session=1` abandons a ~1.5 MB session allocation each time. And teardown releases the reference only for clean-session clients, so a persistent client that resumed a session never releases anything, which is the mirror image of the same asymmetry. Fixing the reference count requires stating the model explicitly - the map owns one reference while registered, each connection owns one while it holds the pointer - and then making creation, reuse and teardown agree with it.

The `git blame` for lines 400-419 attributes the session lookup and creation logic to the same bulk import commit that introduced the broker (`6c4db6f`), so this is original logic rather than a regression introduced by a later change.

## Proof of Concept

1. Start the broker with anonymous access enabled and a known `max_request_size`.
2. Connection A sends CONNECT with ClientId `victim` and `clean_session=1`. The broker creates session S and takes the only reference to it; CONNACK reports `session_present=0`.
3. Connection B sends CONNECT with the same ClientId `victim` and `clean_session=0`. The broker finds S, sets `session_present=1` in the CONNACK and assigns `B->session = S` without taking a reference.
4. Close A's socket. The teardown path takes the `clean_session == true` branch, removes S from the sessions map, decrements the reference count from 1 to 0 and frees S - while B is still connected and still points at it.
5. B sends SUBSCRIBE. The handler reaches `subscriber_new(e->client->session, ...)`, which copies 64 bytes from the freed session (`src/subscriber.c:45`), and then `list_push(e->client->session->subscriptions, t)` (`src/handlers.c:593`), which writes into the subscription list that `session_free` destroyed.
6. Under AddressSanitizer the run reports `heap-use-after-free` READ of size 64 with the free attributed to `session_free` via `client_deactivate`, and the broker aborts. On the plain optimized build the same sequence completes without a signal, leaving the corruption silent.
7. Repeat the sequence against a patched build: B receives a valid SUBACK for its packet identifier and no sanitizer report is produced.

```python
without taking a reference, then freed by the original clean_session client.

CID = "victim"


def start_broker():
    shutil.rmtree(RUN, ignore_errors=True)
    os.makedirs(RUN + "/asan", exist_ok=True)

log_level DEBUG
log_path {RUN}/sol.log
```

## Remediation

Give each connection its own reference to the session it uses, and make teardown release exactly the references that were taken, so that no connection can be left holding a block whose count has reached zero. Establish an explicit ownership model first: the sessions map holds one reference while the session is registered, and every connection that points at the session holds one of its own. Under that model the creation path must take two references, the reuse path must take one for the resuming connection, and the clean-session discard path must release the map reference while clearing the local pointer. Teardown must then release the connection's reference on every path, including connections whose clean-session flag is false, and release the map reference only when the session is being discarded. Setting the client's session pointer to null as part of that release prevents a recycled client block from releasing a stale reference. Apply the same symmetry to the branch that discards an existing session for a clean-session connection, which currently removes the map entry without releasing its reference and therefore leaks the block on every repeat. Beyond the reference counting, consider binding session ownership to the connection that created it - for example refusing to hand an existing session to a second concurrent connection, or explicitly closing the previous connection when a ClientId is reused - so that two live connections cannot share mutable session state at all; MQTT permits a connection to take over a ClientId, but the broker should then invalidate the previous connection rather than leave it with a pointer into shared state. Finally, the session's subscription lists are destroyed during teardown while other handlers can still reach them; making the session's lifetime solely reference-counted, as above, is what removes that window.

```
B connect clean=0 connack=0100 (session_present=1)
broker alive after owner disconnect: True

$ POC_BIN=build-dev/sol python3 poc_session_uaf.py
... B recv: (144, b'\x00\x07\x00')            (no crash, no corruption)
```

Trace through the patched code: `connect_handler` takes a reference in the reuse branch, so the session shared by A (clean_session=1) and B (clean_session=0) has three references - map, A, B. When A disconnects, `client_deactivate()` drops the map reference and A's own reference, leaving B's reference at exactly one; `session_free` therefore cannot run while B is connected. When B disconnects its reference is released and the block is freed exactly once. The gdb breakpoint on `session_free` is no longer reached at the point where B subscribes.

**Gate 3 - bypass review.** The diff was re-read for sibling paths. (a) The clean-session discard branch (a `clean_session=1` connection presenting an existing ClientId) previously dropped the map entry without releasing its reference, which leaked the block the block-per-repeat; it now releases the map reference while any live connection keeps its own, so discarding cannot free a block that another connection is using. (b) Repeated CONNECT on one connection cannot create an unbalanced reference because a second CONNECT is rejected before the session code (`if (cc->connected == true) goto clientdc;`). (c) Clients whose blocks are recycled from the pool start with `session = NULL` (`client_init`) and, after this change, also end that way, so a recycled block cannot release a stale reference. (d) Both clean and non-clean disconnect paths were exercised (T1/T2 in the lifecycle script), as was a socket close without a DISCONNECT packet. (e) A second concurrent borrower was not created - MQTT only allows one live connection per ClientId, and the code path for a third reference is the same reuse branch, so the extra reference arithmetic is the same as the two-connection case.

**Gate 4 - preserved behaviour.** A dedicated lifecycle script covers the semantics that the reference counting must not change, and the harness smoke test covers normal traffic:

The session-resume PoC also still reports `session_present=1` on reconnect with `clean_session=0`, so persistent sessions continue to survive disconnects rather than being freed early. No sanitizer report was produced by any of these runs.

**Gate 5 - repository checks.** Upstream unit tests pass on both variants:

```
$ cmake --build build-dev  --target sol_test -j   -> tests run: 13 tests passed: 13
$ cmake --build build-asan --target sol_test -j   -> tests run: 13 tests passed: 13
```

**Gaps.** Two are explicit. (1) There is no upstream test for session lifetime, so closure rests on the PoC and the lifecycle script rather than on a repository test that fails without the change. (2) The reclamation experiment - proving that a freed session can be reused with attacker-controlled bytes - could not be executed: the free and the later allocation run on different event-loop threads, so the chunk was never handed back within the test window, and AddressSanitizer quarantines the block in the instrumented build. That is why controlled reuse and code execution are not claimed and why the finding is rated on the demonstrated corruption rather than on the worst case.

## Assumptions

The broker is reachable over TCP with anonymous access (shipped default) or with any single valid credential; no authorization distinguishes two connections that present the same ClientId, and MQTT v3.1.1 explicitly allows a second connection to resume an existing session by ClientId. Two concurrent connections and one disconnect are sufficient; no timing window, no special configuration, and no operator misconfiguration are required. The demonstrated impact assumes the two connections are served by different event-loop workers, which is the normal case in the shipped `THREADSNR 2` build and is what prevented the freed chunk from being reclaimed with attacker data during testing.
