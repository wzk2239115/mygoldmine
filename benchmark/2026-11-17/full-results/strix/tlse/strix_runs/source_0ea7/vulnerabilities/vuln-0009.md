# DTLS short handshake record causes out-of-bounds read of the fragment header in tls_consume_stream

**ID:** vuln-0009
**Severity:** MEDIUM
**Found:** 2026-11-17 11:02:46 UTC
**Target:** TLSe (tlslayer) TLS library snapshot - DTLS record layer
**CWE:** CWE-125
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Trivial

## Description

When a DTLS handshake record carries between 1 and 11 bytes of payload, tls_consume_stream() still reads the full 12-byte handshake fragment header (declared length, offset and fragment length) because the guard only requires the record to be longer than 13 bytes. Up to 11 bytes past the end of the receive buffer are read and used as fragment bookkeeping values, pre-authentication.

## Evidence

22-byte DTLS record (13-byte header with payload length 1, then a single 0x00 byte, then 8 trailing bytes) into a DTLS 1.2 server context:\n\n```\n==79471==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x7b3536be0086\nREAD of size 1 at 0x7b3536be0086 thread T0\n    #0 tls_consume_stream              tlse.c:12516\n\n0x7b3536be0086 is located 0 bytes after 22-byte region [0x7b3536be0070,0x7b3536be0086)\nallocated by thread T0 here:\n    #1 tls_consume_stream              tlse.c:12462\n```\n\nSource, where the only guard is `length > 13` while twelve header bytes are consumed:\n\n```c title=tlse.c startLineNumber=12508 endLineNumber=12516\n            if ((buffer[0] == TLS_HANDSHAKE) && (length > 13)) {\n                ...\n                buffer += tls_header_size;\n\n                data_length = buffer[1] * 0x10000 + buffer[2] * 0x100 + buffer[3];\n                fragment_offset = buffer[6] * 0x10000 + buffer[7] * 0x100 + buffer[8];\n                fragment_length = buffer[9] * 0x10000 + buffer[10] * 0x100 + buffer[11];\n```\n\nTriggering input: `16fefd000000400000000000010000961703 04ef4503` (22 bytes). Uninstrumented build on the same input exits 0, so the effect without a sanitizer is an out-of-bounds read of up to 11 bytes with no crash.

## Impact

A remote unauthenticated sender can make the DTLS terminator read up to 11 bytes beyond its receive buffer on each short handshake record, and those bytes are used as the fragment's declared length, offset and length. No data is returned to the attacker and the values are not attacker-chosen, so the demonstrated effect is an out-of-bounds read that aborts sanitizer-instrumented or hardened builds; in a normal build the record is simply rejected. Standalone impact is low, but the same values feed the fragment reassembly bookkeeping.

## Counterevidence

I checked whether the read is bounded elsewhere: the record loop only guarantees `length <= tls_buffer_len`, and the DTLS branch's own precondition is `length > 13`, so the 12-byte header read has no guard. There is no later check that could mask it because the out-of-bounds bytes are consumed immediately to compute data_length/fragment_offset/fragment_length. I confirmed it is not my harness reading past its own buffer: the 22-byte input is held in a heap allocation made by tls_consume_stream() itself (reported at tlse.c:12462) and the 1-byte read lands exactly at the end of that 22-byte region. I also confirmed the read does not escalate: in the uninstrumented build the same input exits 0, so it is a memory-safety defect without a demonstrated crash or leak. Consequence: low severity, filed for completeness because it is a distinct root cause from the accumulator overflow (which concerns the reassembled length, not the header validation).

## What Would Change This Severity

Evidence that the out-of-bounds bytes influence the reassembly buffer in a way that reaches a write (rather than only the checks that currently reject the record) would raise this to high; confirmation that no DTLS context is ever used would make it inapplicable.

## Technical Analysis

In tls_consume_stream(), after the DTLS record header is validated, the fragmentation pre-check decodes three 24-bit fields from the handshake header:\n\n```c title=tlse.c startLineNumber=12508 endLineNumber=12516\n            if ((buffer[0] == TLS_HANDSHAKE) && (length > 13)) {\n                ...\n                buffer += tls_header_size;\n\n                data_length = buffer[1] * 0x10000 + buffer[2] * 0x100 + buffer[3];\n                fragment_offset = buffer[6] * 0x10000 + buffer[7] * 0x100 + buffer[8];\n                fragment_length = buffer[9] * 0x10000 + buffer[10] * 0x100 + buffer[11];\n```\n\n`length` is the record length from the DTLS header plus tls_header_size (13), and it has already been checked against the bytes actually buffered. `length > 13` therefore guarantees exactly one payload byte, while `buffer[1]`..`buffer[11]` require twelve. The bounds check that protects the fragment body (`fragment_length + 12 > length - tls_header_size`) runs after these reads, so it cannot prevent them.\n\nBecause tls_consume_stream() reallocates its message buffer to the exact number of bytes received, the over-read runs past the heap allocation. The read values are then used for the `data_length > DTLS_MAX_FRAGMENT_SIZE` and `fragment_offset + fragment_length > data_length` tests, so they influence control flow, but the same record is subsequently rejected.

## Proof of Concept

1. Build a single DTLS record: type 0x16, version 0xFEFD, epoch 0, sequence 0, payload length 1, payload byte 0x00, followed by eight more bytes so the total allocation is 22 bytes.\n2. Deliver it to a DTLS server context through tls_consume_stream().\n3. Because the guard is only `length > 13` (one payload byte), the code reads buffer[1]..buffer[11] of the assumed 12-byte handshake fragment header, which extends past the 22-byte receive buffer.\n4. The instrumented build reports AddressSanitizer heap-buffer-overflow READ of size 1 at tlse.c:12516, one byte past the end of the buffer allocated at tlse.c:12462.

## Code Analysis

**Location 1:** `tlse.c` (line 12510)
  Require the full 12-byte handshake fragment header before decoding it

  **Suggested Fix:**
```diff
-             if ((buffer[0] == TLS_HANDSHAKE) && (length > 13)) {
+             if ((buffer[0] == TLS_HANDSHAKE) && (length > tls_header_size + 12)) {
```

## Remediation

Require the complete 12-byte handshake fragment header to be present before decoding the declared message length, fragment offset and fragment length, i.e. check that the record payload can hold at least 12 bytes rather than only that it is non-empty. Treat a shorter record as a broken packet for DTLS.

## Fix Verification

Gate 1 security closure: the guard is raised from `length > 13` to requiring the full 12-byte fragment header before any of the three 24-bit fields are read, so no read can occur past the record boundary. Rebuilt and re-ran: the 22-byte input produces no AddressSanitizer report and the function returns.\n\nGate 2 bypass review: the same three field reads are the only accesses to `buffer[1..11]` in that block; the subsequent `memcpy(fragment_buffer + fragment_offset, &buffer[12], fragment_length)` is already bounded by the `fragment_length + 12 > length - tls_header_size` check that follows. Alternate shapes tried: payloads of 0, 1, 11, 12 and 13 bytes (0 does not enter the branch; 12 and 13 are unchanged and still parse normally).\n\nGate 3 preserved behavior: well-formed fragmented DTLS handshake records always carry the full 12-byte header, so legitimate fragmentation is unaffected; a full DTLS 1.2 handshake still completes after the change.\n\nGate 4 repository checks: no test suite or linter exists; the changed line compiles cleanly under gcc -O1 -g with AddressSanitizer.\n\nGap: the fix rejects short records rather than deferring them as "need more data"; for DTLS each datagram is a complete record, so rejecting matches the surrounding behaviour, but a caller that already buffers partial records would see a different return code.

## Assumptions

Requires a DTLS context (UDP) and that the record is the last one in the buffer, which is the normal case when the application passes one datagram per tls_consume_stream() call.
