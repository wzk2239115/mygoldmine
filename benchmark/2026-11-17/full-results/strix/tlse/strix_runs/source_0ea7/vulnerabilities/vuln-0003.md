# TLS 1.3 client accepts Finished without CertificateVerify, enabling certificate impersonation

**ID:** vuln-0003
**Severity:** HIGH
**Found:** 2026-11-17 10:53:10 UTC
**Target:** tlse.c - TLS 1.3 client handshake state machine
**Endpoint:** tls_parse_payload case 0x14 (Finished) / case 0x0F (CertificateVerify)
**Method:** TLS 1.3 handshake
**CWE:** CWE-287
**CVSS:** 7.4
**Confidence:** High
**Fix Effort:** Low

## Description

The TLS 1.3 client state machine does not require the server's CertificateVerify message. A server that performs its own key exchange, replays any certificate that satisfies the application's validation callback, and then sends Finished is accepted as authenticated - although it never proved possession of the certificate's private key. Any active man-in-the-middle can therefore impersonate the server to a TLSe client, including for certificates that validate against the configured trust roots.

## Evidence

Attacker holding only the certificate, no CertificateVerify sent:\n\n  [server] tls_load_certificates(srv.pem) -> 1 (2 = cert+key, 1 = certificate only)\n  [server] received 234 bytes / sent 1025 bytes\n  [server] tls_established = 1\n  [server] tls_read -> 44 bytes of client application data\n  [server] client sent: GET /secret HTTP/1.1 Host: bank.example\n\n  [client] leaf validity check -> 0\n  [client] chain trusted root -> 0\n  [client] subject matches bank.example -> 0\n  [client] policy satisfied -> no_error (255)\n  [client] tls_established = 1, verify callback fired 1 time(s)\n  [client] RESULT: handshake completed and reported as authenticated\n\nControl, unmodified server that does send CertificateVerify:\n\n  [server] tls_load_certificates(srv_both.pem) -> 2 (cert+private key)\n  [server] sent 2275 bytes\n  [client] tls_established = 1, verify callback fired 1 time(s)\n\nWith the fix applied the attacker transcript is rejected (tls_consume_stream error -6, handshake rejected) while the control still completes.

## Impact

Complete loss of server authentication for TLS 1.3 clients: an on-path attacker impersonates any server whose certificate it can obtain (public information), reads and modifies all application traffic, and captures credentials and session data. The application's certificate_verify callback runs and reports success, so the embedding application has no signal that the peer was never authenticated.

## Counterevidence

Checked whether another control compensates: the certificate_verify callback is invoked and its verdict is enforced (a callback returning bad_certificate aborts the handshake), so the missing control is not the callback but the absence of any proof-of-possession requirement. tls_parse_finished verifies the peer Finished against the handshake secret, but the attacker derives that secret from its own key share, so Finished does not authenticate the certificate. Checked for PSK-based handshakes that would legitimately omit CertificateVerify: this implementation never sends or processes a pre_shared_key extension, so none exist here. Checked that the client's state machine is not gated elsewhere on CertificateVerify: hs_messages[8] is only a repeat counter and the Finished handler does not consult it. Remaining constraint: the attacker must be on-path, which is exactly the threat TLS exists to defeat.

## What Would Change This Severity

If the client also validated a pinned public key hash of the peer key and discarded the session on mismatch the severity would drop sharply; conversely, evidence that deployed clients additionally verify the peer's certificate signature over the handshake (nothing in this library does) would rule the issue out.

## Technical Analysis

In TLS 1.3 the only proof that a peer owns the private key for the certificate it presents is the CertificateVerify signature over the handshake transcript. tls_parse_payload handles case 0x0F (CertificateVerify) only if it arrives, and case 0x14 (Finished) accepts the message whenever connection_status is at least 2 (tls_parse_finished, tlse.c:9271). No state records that CertificateVerify was received: CHECK_HANDSHAKE_STATE(context, 8, 1) merely limits repeated CertificateVerify messages, it does not make one mandatory.

An attacker therefore sends ServerHello with its own key_share, EncryptedExtensions, Certificate (a replayed certificate), and Finished. It knows the ECDHE shared secret because it chose its own key share, so it can compute the handshake traffic keys and produce a valid Finished over the transcript it actually sent. The client validates the certificate through the application callback, verifies Finished, sets connection_status to 0xFF, and reports tls_established() == 1.

This implementation never negotiates PSK (the pre_shared_key and psk_key_exchange_modes extensions are only dumped, never sent or processed), so certificate authentication is always in use and CertificateVerify is always required.

## Proof of Concept

1. Create a local CA and a server certificate for CN=bank.example; give the client only the CA as a trust root, so normal chain validation applies.
2. Build a server from this library with the single change that the server flight omits tls_build_certificate_verify(), modelling an attacker that holds only the public certificate.
3. Start the server with tls_load_certificates() given the certificate PEM without its private key; it reports 1 (certificate only, no key).
4. Run an unmodified TLS 1.3 client whose certificate_verify callback performs leaf validity, chain-to-trusted-root and subject-vs-SNI checks.
5. The callback returns no_error, the client reports tls_established() == 1, and sends its request; the attacker server reads it in plaintext.
6. Control: the same client against an unmodified server that does send CertificateVerify also completes, showing the client is otherwise functional and that the only difference is the missing message.

## Code Analysis

**Location 1:** `tlse.c` (lines 10078-10079)
  Require CertificateVerify before accepting the server Finished

  **Suggested Fix:**
```diff
-             case 0x14:
-                 DEBUG_PRINT0(" => FINISHED\n");
+             case 0x14:
+                 DEBUG_PRINT0(" => FINISHED\n");
+ #ifdef WITH_TLS_13
+                 /*  TLS 1.3 authenticates the peer with CertificateVerify; it is the
+                     only proof of possession of the certificate private key, and no
+                     PSK handshake exists in this implementation to omit it. */
+                 if ((!context->is_server) && ((context->version == TLS_V13) || (context->version == DTLS_V13)) && (!context->hs_messages[8])) {
+                     DEBUG_PRINT0("* FINISHED WITHOUT CERTIFICATE VERIFY\n");
+                     payload_res = TLS_UNEXPECTED_MESSAGE;
+                     break;
+                 }
+ #endif
```

## Remediation

Require the server's CertificateVerify before accepting Finished on a TLS 1.3 client, and abort with unexpected_message when it is absent. Track a dedicated per-handshake flag rather than reusing the repeat counter if the state machine is refactored. Consider applying the same requirement in the opposite direction for deployments that mandate client authentication, so that a client cannot complete a handshake without proving possession of its certificate key.

## Fix Verification

Security closure: the check rejects a TLS 1.3 client Finished when no CertificateVerify was processed (hs_messages[8] is incremented only by the CertificateVerify case), before tls_parse_finished() is called, so the attacker flight cannot complete the handshake.

Executed: applied the patch to a copy of tlse.c, rebuilt with -fsanitize=address,undefined (exit 0), and ran the same interop test. Attacker without CertificateVerify: tls_consume_stream returns -6 (TLS_UNEXPECTED_MESSAGE), tls_established() == -1, no application data sent. Unmodified server that sends CertificateVerify: still completes, tls_established() == 1, request delivered.

Bypass review: hs_messages[8] is set by CHECK_HANDSHAKE_STATE(context, 8, 1) in the CertificateVerify case, before parsing, so an untrusted CertificateVerify that fails verification sets the counter but also aborts the handshake through the existing error path; it cannot be used to satisfy the new check and continue. The condition is restricted to clients because a server may legitimately receive no client certificate. Sibling paths checked: an empty server Certificate list is also rejected now, since it likewise leaves the counter zero.

Preserved behavior: normal TLS 1.3 clients against conforming servers continue to work (control run), and TLS 1.0-1.2 and DTLS 1.0-1.2 are untouched by the version guard.

Gaps: no test against a third-party TLS 1.3 server was run; verification used this library's own client and server plus the modified attacker server.

## Assumptions

The client offers TLS 1.3 and its application validation callback accepts the certificate the attacker presents - in practice the genuine server certificate, which is public and obtainable by connecting to the server or from certificate transparency logs. The attacker must be on-path (a normal MITM position) and no private key, credential or user interaction is required.
