# Stack buffer overflow in tls_stun_parse() key construction (WebRTC/STUN, pre-auth)

**ID:** vuln-0002
**Severity:** HIGH
**Found:** 2026-11-17 10:52:05 UTC
**Target:** TLSe (tlslayer) TLS library snapshot - STUN / WebRTC DTLS path
**CWE:** CWE-121
**CVSS:** 8.2
**Confidence:** High
**Fix Effort:** Low

## Description

tls_stun_parse() builds a "username:realm:password" string in a 1230-byte stack buffer without bounding the attribute lengths it has already accepted. A STUN binding request whose USERNAME (up to 513 bytes) and REALM (up to 763 bytes) attributes are both maximal overflows the buffer by up to 47 bytes with fully attacker-controlled data. The write happens before MESSAGE-INTEGRITY is checked, so an unauthenticated single UDP datagram triggers it.

## Evidence

1332-byte STUN binding request (USERNAME 513 bytes, REALM 763 bytes, MESSAGE-INTEGRITY) through the real entry point tls_peerconnection_iterate():\n\n```\n==27277==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7bc43f8f297e\nWRITE of size 763 at 0x7bc43f8f297e thread T0\n    #0 memcpy\n    #1 tls_stun_parse                  tlse.c:13210\n    #2 tls_peerconnection_iterate      tlse.c:14006\n\nThis frame has 7 object(s):\n    [512, 1072) 'hmac'\n    [1200, 2430) 'key'  <== Memory access at offset 2430 overflows this variable\nSUMMARY: AddressSanitizer: stack-buffer-overflow tlse.c:13210 in tls_stun_parse\n```\n\n`key` is `char key[0x4CE]` (1230 bytes) at tlse.c:13085. The overflowing copy starts at key+514 (after the 513-byte USERNAME and its separator), so 514 + 763 = 1277 bytes are written into a 1230-byte object - 47 bytes past the end, all taken from the attacker-supplied REALM attribute. With the real caller's 24-character password, further copies land inside the buffer, so the overrun is bounded at 47 bytes.\n\nCaller: `tls_stun_parse(buf, buf_len, channel->local_pwd, strlen(channel->local_pwd), ...)` at tlse.c:14006, reached from a single datagram because tlse.c:14000 only checks `tls_is_stun()`, which merely compares the 0x2112A442 magic cookie.\n\nUninstrumented build: the same input completes without crashing (`exit 0`), i.e. the 47 bytes silently overwrite adjacent stack locals rather than saved control data in this compiler layout.

## Impact

An unauthenticated attacker who can send a UDP datagram to a TLSe WebRTC/DTLS peer connection writes up to 47 bytes of fully controlled data past a 1230-byte stack buffer, corrupting the tls_stun_parse() frame. The overwritten region holds other locals of that frame, so the immediate demonstrated effect is corruption of program state in the TLS terminator plus an AddressSanitizer-detected abort; whether the overwrite reaches saved control data depends on the compiler's frame layout, and code execution was not demonstrated. Because the parser runs before any DTLS handshake or STUN authentication, no credential is required.

## Counterevidence

Reachability is narrower than a plain TLS server: the only caller of tls_stun_parse() is tls_peerconnection_iterate(), so a deployment that never uses the WebRTC DTLS-SRTP peer connection cannot reach it - that is an exposure constraint, not a control, and it does not change the code defect. Within that path there is no control: tls_is_stun() only checks the magic cookie, and the copying happens before any authentication, so the attacker needs no credentials. I checked whether the destination buffer is protected some other way: it is a plain local array and gcc emits no stack protector for this function in the build tested, so nothing catches the overrun. On the uninstrumented build the process survived the write in the tested stack layout (the overrun lands in adjacent locals rather than in saved control data), which is why availability is scored low rather than high; the out-of-bounds write itself is unconditional and reproducible.

## What Would Change This Severity

Demonstrating that the overwrite reaches the saved return address or a stack canary in a production build (giving control-flow hijack or a reliable crash) would raise this to critical; proof that the WebRTC/DTLS peer-connection feature is never compiled or deployed would lower it to informational.

## Technical Analysis

tls_stun_parse() (tlse.c:13070) declares `char key[0x4CE]` at tlse.c:13085. Attribute handlers accept USERNAME up to 513 bytes (tlse.c:13184) and REALM up to 763 bytes (tlse.c:13233); nothing checks their sum against the destination, and the caller passes the library-generated 24-character local_pwd, so the maximum concatenation is 513 + 1 + 763 + 1 + 24 + 1 = 1303 bytes against a 1230-byte buffer.\n\nThe copies happen inside the MESSAGE-INTEGRITY handler (tlse.c:13201-13210) while assembling the HMAC key, i.e. before the integrity value is computed or compared, so no authentication is required. The same block also contains a separate defect: `ptr += username_len;` after copying the REALM advances by the wrong length, so the second separator and the password are written at incorrect offsets.\n\nEntry point: tls_peerconnection_iterate() at tlse.c:14006 calls tls_stun_parse() for any datagram that tls_is_stun() accepts, and tls_is_stun() only verifies the four magic-cookie bytes 0x2112A442. The parser is therefore reachable pre-authentication from one spoofable UDP datagram in any product using the WebRTC DTLS-SRTP support.

## Remediation

Compute the total length of the concatenated key (username + realm + password + separators + terminator) and reject the message with TLS_BROKEN_PACKET when it cannot fit in the destination buffer, before performing any copy. Also correct the pointer advance for the REALM attribute, which currently uses the USERNAME length and therefore writes the separator and password at the wrong offsets. Alternatively, build the key with a length-tracking helper that cannot overrun, and lower the per-attribute limits so their sum is provably within the buffer.

## Fix Verification

Gate 1 security closure: the bounds check rejects any attribute combination whose concatenation cannot fit in key (username + realm + password + two separators + terminator), before any byte is copied; the only write path into key is guarded by it. Any request that would previously have overflowed now returns TLS_BROKEN_PACKET, so tls_stun_parse() and tls_peerconnection_iterate() return an error instead of corrupting the stack. Rebuilt and re-ran the 1332-byte PoC: no AddressSanitizer report, and the function returns an error.\n\nGate 2 bypass review: the second copy site (the password copy further down) is inside the same guarded block, so it cannot be reached with an unchecked length. Alternate input classes considered: repeated MESSAGE-INTEGRITY attributes (the first one fails the HMAC comparison and returns, so only one attempt per datagram), zero-length USERNAME/REALM (rejected by the same check), and non-4-byte-aligned attributes (the padding loop only advances the cursor; it does not affect the accepted lengths).\n\nGate 3 preserved behavior: legitimate 20-40 byte binding requests behave exactly as before; a request whose username+realm+password fits the buffer takes the same path and the same HMAC key derivation, with the ptr += realm_len correction making the derived key match the documented "username:realm:password" form instead of the previous wrong offset.\n\nGate 4 repository checks: no test suite or linter exists for this repository; the changed code was compiled cleanly with gcc -O1 -g under AddressSanitizer and the PoC was re-run.\n\nNote on line endings: this repository stores tlse.c with CRLF line terminators, so the suggestion block above uses CRLF to match the file byte for byte.\n\nGap: the password copy is bounded by the same new check rather than by a dedicated oversized-password test (the caller controls password length, not the attacker).

## Assumptions

The attacker must be able to send one UDP datagram to a TLSe WebRTC/DTLS peer connection (the documented DTLS-SRTP path). No knowledge of the local STUN password is required because the overflow happens while building the key material, before the MESSAGE-INTEGRITY comparison.
