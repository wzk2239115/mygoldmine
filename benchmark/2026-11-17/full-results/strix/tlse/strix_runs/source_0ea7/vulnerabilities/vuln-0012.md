# No DTLS anti-replay window: captured application-data records are re-delivered to the application indefinitely

**ID:** vuln-0012
**Severity:** MEDIUM
**Found:** 2026-11-17 11:13:39 UTC
**Target:** /workspace/source
**Endpoint:** tlse.c — DTLS record layer (tls_parse_message / tls_consume_stream)
**Method:** DTLS 1.2 record replay
**CWE:** CWE-294
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Low

## Description

The DTLS record layer keeps no anti-replay state, so an encrypted application-data record captured off the wire can be re-delivered to the server at any later time and is accepted again: `tls_read()` returns the same plaintext and the application acts on it a second time. The monotonic `tls_write` stream of a TLS connection does not apply to DTLS, and nothing in `tls_consume_stream()`/`tls_read()` tells the application that the record was a duplicate.

## Evidence

**Unpatched library — a DTLS 1.2 handshake, 12 commands sent, the first command record captured and replayed after the peer's sequence advanced to 12:**\n\n```text\nhandshake: srv established=1 cli established=1 cipher=ECDHE-RSA-AES128GCM-SHA256\n  original command record (captured by peer/attacker): len=53 type=17 epoch=1 seq=1 reclen=40\n  [app] executed command #1: 'CMD:TRANSFER-100' (consume=53)\n  latest record: len=45 type=17 epoch=1 seq=2 reclen=32\n  [app] 12 commands executed so far; peer sequence is now 12, captured record is sequence 1\n-- replaying the captured command record verbatim --\n  [app] executed command #13 AGAIN: 'CMD:TRANSFER-100' (consume=53)\n  [app] executed command #14 once more: 'CMD:TRANSFER-100'\nRESULT handshake=ok commands_sent=12 commands_executed=14 replayed_deliveries=2 console_effects=2\n```\n\nThe replayed datagram is byte-identical to the original (same DTLS header: epoch 1, sequence 1, same AEAD nonce and tag), and it is still accepted eleven records later, then accepted again immediately. `tls_consume_stream()` reports full consumption (53 bytes) and `tls_read()` returns 18 plaintext bytes each time.\n\n**No anti-replay state exists anywhere in the library:**\n\n```text\n$ grep -n \"replay\\|window\\|highest\" tlse.c tlse.h\n(no matches related to record sequencing)\n$ grep -n remote_sequence_number tlse.c\n10789:        context->remote_sequence_number = dtls_sequence_number & (((uint64_t)0xFFFFUL << 32) | 0xFFFFFFFFUL);\n10791:        context->remote_sequence_number ++;\n```\n\nThe value is overwritten from the received header on every datagram; it is never compared against a previously seen value, and the AEAD nonce/AAD are derived from the record's own epoch and sequence (`tlse.c:10554-10557`), so any captured record remains cryptographically valid forever.\n\n**Patched library, same binary rebuilt:**\n\n```text\n  [app] 12 commands executed so far; peer sequence is now 12, captured record is sequence 1\n-- replaying the captured command record verbatim --\n  replay rejected: consume=53 read=0\nRESULT handshake=ok commands_sent=12 commands_executed=12 replayed_deliveries=0 console_effects=0\n```\n\n**Reordering and duplicate behaviour after the patch (separate run):**\n\n```text\n-- out-of-order delivery 3,2,1 --\n  got 'C'\n  got 'B'\n  got 'A'\n-- duplicates 2,1,3 delivered again --\n  dup 2 dropped\n  dup 1 dropped\n  dup 3 dropped\nRESULT in_order_preserved=3/3\n```

## Impact

A previously valid DTLS record can be re-injected arbitrarily often and arbitrarily late in the connection, and the receiving application processes it as a fresh message each time. In the demonstrated case one command record was executed three times (once originally, twice by replay) after the peer's sequence had advanced eleven records past it, so no time or sequence proximity is required. Any DTLS-protected operation with side effects is exposed: duplicate transfers or provisioning commands, re-executed alarms or control actions, replayed chat/media-control messages on the library's WebRTC data channels, and double counting in metered or billable flows. Integrity impact scales with what the duplicated message does; confidentiality is unaffected because the replayed ciphertext is unmodified.

## Counterevidence

The strongest argument against this being exploitable is that DTLS is often used only for media or for request/response traffic where a duplicated record is harmless, and that a replayed record cannot be modified (the AEAD tag still binds the ciphertext), so confidentiality is untouched. That does not remove the issue: RFC 6347 section 4.1.2.6 makes an anti-replay window mandatory, precisely because duplicated records are indistinguishable from fresh ones for the application. I looked for an existing control and found none — no highest-seen counter, no bitmap, no duplicate cache; `context->remote_sequence_number` is overwritten from the record header on every datagram (`tlse.c:10787-10789`) and the AEAD nonce/AAD are built from the record's own epoch and sequence (`tlse.c:10554-10557`), so a captured record stays valid forever and can be re-delivered at any time, in any position in the stream. I also confirmed that the library does not reject the replay anywhere downstream: `tls_parse_message` dispatches the record to `_private_tls_write_app_data()` and `tls_read()` returns it, exactly like the first delivery. A deployment-level idempotency key would mitigate a specific application but is not a protocol-level control and is not provided by the library.

## Confidence Rationale

The exchange, the replay, and the fix are all exercised end to end in-process against an unmodified build of this source and against the rebuilt patched tree. The only deployment-specific unknown is how much of a given application's DTLS traffic is side-effecting.

## What Would Change This Severity

If a deployment uses DTLS for media or idempotent request/response traffic only, the integrity impact disappears and this drops to low; if the DTLS channel carries privileged control commands or money-moving operations, or if an off-path attacker can capture a datagram from any vantage point (making privileges-required none), the score rises to high because the replay is then unauthenticated and directly changes protected state.

## Technical Analysis

**The DTLS record layer has no anti-replay state.** `tls_parse_message()` reads the epoch and sequence number straight out of each received record:\n\n```c title=tlse.c startLineNumber=10456 endLineNumber=10462\n    if (context->dtls) {\n        CHECK_SIZE(buf_pos + 8, buf_len, TLS_NEED_MORE_DATA)\n        dtls_epoch = ntohs(*(unsigned short *)&buf[buf_pos]);\n        dtls_sequence_number = ntohll(*(uint64_t *)&buf[buf_pos]);\n\n        buf_pos += 8;\n    }\n```\n\nThose same attacker-supplied values become the AEAD additional data and nonce, so decryption is self-consistent for any record that was ever valid:\n\n```c title=tlse.c startLineNumber=10554 endLineNumber=10557\n                if (context->dtls)\n                    *((uint64_t *)aad) = htonll(dtls_sequence_number);\n                else\n                    *((uint64_t *)aad) = htonll(context->remote_sequence_number);\n```\n\nThe value is then stored with no comparison against any previous value:\n\n```c title=tlse.c startLineNumber=10787 endLineNumber=10791\n    if (context->dtls) {\n        context->dtls_epoch_remote = dtls_epoch;\n        context->remote_sequence_number = dtls_sequence_number & (((uint64_t)0xFFFFUL << 32) | 0xFFFFFFFFUL);\n    } else\n        context->remote_sequence_number ++;\n```\n\nThere is no highest-seen counter, no bitmap or cache of accepted sequence numbers, and no epoch comparison (`grep` for replay/window/highest over `tlse.c` and `tlse.h` returns nothing relevant; `remote_sequence_number` is only used as a nonce input for stream TLS). Once the tag verifies, the record goes to `_private_tls_write_app_data()` (`tlse.c:10823`) and out of `tls_read()`, so the application processes the duplicated message exactly like the original. RFC 6347 section 4.1.2.6 requires the record layer to implement a replay detection window; the README's own warning about the DTLS state machine covers DoS, not replay.\n\nBecause the check is absent rather than weak, the attack needs no cryptography: any party that can observe one datagram (an on-path attacker, a shared wireless segment, or the peer itself) can re-inject it at any later point in the connection, and the library reports nothing to the application that would distinguish the copy from a fresh record. The same code path serves the WebRTC/DTLS peer connection shim (`tls_peerconnection_iterate()` feeds datagrams to `tls_consume_stream()`), so data-channel messages are equally replayable.

## Remediation

Implement the anti-replay window that RFC 6347 section 4.1.2.6 requires for every DTLS context: retain the highest authenticated record sequence number together with a bitmap covering the preceding records (512 records is the usual size), drop any record that is older than the window or whose bit is already set, and advance the window only after the record's AEAD tag has verified so that forged datagrams cannot move it. Sequence numbers must be compared per direction and per epoch, and the window must reset when the epoch advances. Records rejected as duplicates should be discarded silently rather than answered with an alert, so that a replayed datagram does not produce an error response an attacker can use as an oracle. If contexts are exported and imported between processes in the middle of a DTLS association, serialize the window state as well, or document that the receiving process starts with an empty window.

## Fix Verification

**Gate 1 — security closure.** The four edits were applied to a copy of the snapshot and the PoC was rebuilt against it. The captured record (epoch 1, sequence 1) is now rejected on both replay attempts while the original delivery still works: `consume=53 read=0`, and the application executes exactly the 12 commands the peer sent (`commands_executed=12 console_effects=0`) instead of 14. The record is dropped before decryption, i.e. before any AEAD work and before `_private_tls_write_app_data()`, so no plaintext reaches the application on a replay.\n\n**Gate 2 — bypass review.** (a) A replay positioned before the window is covered by the `highest - sequence_number >= TLS_DTLS_REPLAY_WINDOW` branch (tested with a record eleven sequence numbers old); (b) a duplicate of the newest record is covered by the bitmap bit already being set — verified in the separate reordering run (`dup 3 dropped`); (c) a duplicate inside the window that was never delivered is still accepted, so legitimate reordering is not broken (records 3, 2, 1 out of order were all delivered); (d) the window is advanced only after the tag check, so an attacker cannot poison it with forged records carrying huge sequence numbers — with the update placed after authentication, a bogus record returns early on `TLS_BROKEN_PACKET`/`TLS_INTEGRITY_FAILED` and never reaches the update; (e) an epoch change (CCS, which increments `dtls_epoch_remote`) produces a combined sequence jump larger than the window, which clears the bitmap and moves the window forward, so old-epoch records become too old instead of being accepted; (f) the same applies to DTLS 1.0 and DTLS 1.3 records, which share `tls_parse_message` and are gated on `context->cipher_spec_set` rather than a version. The clearing loop is bounded by the window size (it memsets instead of looping when the jump is larger than the window), so a peer cannot cause unbounded work with a large sequence jump. Remaining gap: handshake retransmissions from the peer are now dropped as duplicates, which is the intended RFC 6347 behaviour, but no test exercises a lossy network or the library's DTLS retransmission path.\n\n**Gate 3 — preserved behavior.** The full DTLS 1.2 handshake still completes (`established=1` on both sides) and application data flows in both directions; out-of-order delivery inside the window is accepted in the order received; TLS (non-DTLS) record handling is untouched because every new condition is guarded by `context->dtls`. The mTLS gate matrix from the independent client-authentication fix was re-run on the combined patched tree and behaves identically (unauthenticated peers rejected, CA-signed peer accepted), confirming the two changes do not interact.\n\n**Gate 4 — repository checks.** `gcc -DTLS_AMALGAMATION -O2 -Wall -Wextra -c tlse.c` compiles with no diagnostics in the changed regions; the harness binaries for the replay PoC, the reordering test and the mTLS matrix all build and run. The repository ships no test suite, so there is no project test target. Narrowest-complete-change judgement: a bitmap window is the smallest construct that both satisfies RFC 6347 and preserves DTLS reordering; a plain high-water mark would reject legitimate out-of-order records and was rejected for that reason. Window state is intentionally not serialized by `tls_export_context()`, which is noted as a limitation rather than silently half-implemented.

## Assumptions

The DTLS peer (or any party able to observe one datagram, including an on-path attacker, a shared wireless segment, or a UDP-spoofing attacker who has captured traffic) can re-deliver a recorded datagram to the server. The application acts on each plaintext record that `tls_read()` returns and has no way to distinguish a replay, because the library reports nothing about it. Flows that depend on message freshness, exactly-once semantics, or idempotency keys are affected; stateless request/response traffic with no side effects is not.
