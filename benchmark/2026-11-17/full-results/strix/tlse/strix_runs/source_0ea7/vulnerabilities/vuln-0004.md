# DTLS cookie is not bound to the client source address, allowing replay to spoofed peers and amplification

**ID:** vuln-0004
**Severity:** MEDIUM
**Found:** 2026-11-17 10:53:30 UTC
**Target:** tlse.c - DTLS HelloVerifyRequest cookie (_private_dtls_build_cookie, tls_parse_hello)
**Endpoint:** tls_parse_hello / _private_dtls_build_cookie
**CWE:** CWE-350
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Medium

## Description

The DTLS HelloVerifyRequest cookie is computed as HMAC-SHA256(per-process secret, client_random) and carries no information about the client's source address. A cookie obtained once from the attacker's own address is therefore accepted from any other (spoofed) source address as long as the same client_random is replayed, defeating the address-validation purpose of the cookie exchange and enabling a reflected amplification and state-exhaustion primitive.

## Evidence

Harness output, one cookie obtained for a ClientHello with client_random starting 0x10,0x11,...:\n\n  peer A: hello (no cookie): reply=60 bytes\n  cookie (len 32): 81f234675c1c74c58285d7caf4179601b033ab1f025bd9ea13f384cfb5102006\n  peer B: hello (peer A's cookie, same random): reply=2257 bytes for a 99 byte datagram\n  fresh contexts (spoofed peers) accepting the replayed cookie: 5/5\n\nEach of the five fresh server contexts represents a different source address; all accepted the same cookie and each produced a 2257-byte response to a 99-byte datagram (about 22x amplification). The cookie is byte-identical across contexts because it depends only on the client_random, which the attacker chooses.

## Impact

An attacker with one legitimately obtained cookie can make the server perform a full handshake - ephemeral key generation plus certificate and ServerKeyExchange transmission - toward arbitrary spoofed source addresses. This gives about 22x traffic amplification toward third-party victims and unbounded per-address state creation from a small number of packets, with no ability to receive the replies. The address-binding property that the DTLS cookie exchange exists to provide is absent.

## Counterevidence

The cookie is secret-keyed with a per-process random dtls_secret (dtls_reset_cookie_secret), so an attacker cannot forge a cookie for a random it has not had certified - that is the one property that does hold. It is not sufficient: the value is a deterministic function of the client-chosen random, so one legitimately obtained cookie is valid everywhere. Checked whether the address is bound elsewhere (context fields, caller passing an address): tls_stun_parse and tls_parse_hello receive no peer address, and no TCPContext field holds one, so nothing else binds it. Checked whether the full flight is gated on more than the cookie: tls_parse_payload builds the server flight whenever dtls_cookie_verified is 1, with no further address or state check. A truly stateless server would limit the state impact, but the reply size is unaffected.

## What Would Change This Severity

Demonstrating that the reflected traffic can reach a magnitude that meaningfully degrades a victim (many more spoofed sources, larger certificate chains) would raise the availability impact; adding proof that each replayed cookie also allocates unbounded server-side state would raise it further.

## Technical Analysis

_private_dtls_build_cookie (tlse.c:7775) computes the cookie as HMAC-SHA256 keyed with the per-process dtls_secret over context->remote_random only. tls_parse_hello then compares the cookie carried in the second ClientHello with the value it rebuilds for that context (tlse.c:8218-8228) and accepts the handshake when they match.\n\nBecause remote_random is chosen by the client, the cookie is a deterministic function of attacker-chosen input. An attacker obtains one cookie for a random R from its own address, then replays (R, cookie) from any spoofed address: a fresh per-address context has no stored cookie, rebuilds HMAC(secret, R), matches, and proceeds. The value proves only that the client once received a HelloVerifyRequest for R - not that it can receive traffic at the claimed address.\n\nOn acceptance tls_parse_payload sets dtls_cookie_verified and builds the complete server flight (ServerHello, Certificate, ServerKeyExchange, ServerHelloDone), including ephemeral key generation, toward the claimed address.

## Proof of Concept

1. Send a DTLS 1.2 ClientHello with cookie_len 0 and a chosen client_random to a fresh server context; the server replies with HelloVerifyRequest containing a 32-byte cookie.
2. Extract the cookie from the HelloVerifyRequest.
3. Send the identical ClientHello again, this time carrying that cookie, to five brand-new server contexts that stand for five different source addresses.
4. All five accept the cookie and each answers with the full server flight (ServerHello, Certificate, ServerKeyExchange, ServerHelloDone): 2257 bytes for a 99-byte request.
5. Because the cookie is HMAC(secret, client_random) with no address input, the same cookie is valid for every address, so the exchange does not validate reachability of the claimed source.

## Remediation

Bind the cookie to the peer transport address: derive it as HMAC-SHA256(secret, client_random || source address || source port) and verify it against the address the datagram actually arrived from before accepting the ClientHello. Because the library currently has no notion of a peer address, this requires exposing the address to the DTLS layer - for example a tls_set_peer_address(context, addr, addrlen) call that the datagram server invokes before tls_consume_stream, or a callback the library uses when building and verifying the cookie. Additionally, rate-limit cookie issuance per source and avoid generating a full server flight until the cookie has been validated against the address, so a replayed cookie cannot trigger certificate transmission to a third party.

## Assumptions

A datagram server built on this library handles DTLS through tls_parse_hello with one context per peer address (the normal pattern, since the library itself has no address handling). The attacker can send from its own address to obtain a cookie and can spoof source addresses toward the server.
