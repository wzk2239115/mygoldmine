# Zero-length CBC record triggers 1-byte heap out-of-bounds read (pt[-1]) in tls_parse_message

**ID:** vuln-0005
**Severity:** MEDIUM
**Found:** 2026-11-17 10:53:43 UTC
**Target:** TLSe (tlslayer) TLS library snapshot - record layer
**CWE:** CWE-125
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Low

## Description

When a zero-length record is processed after a CBC cipher suite has been installed, tls_parse_message() allocates a zero-length plaintext buffer and then reads pt[length - 1], i.e. one byte before the allocation. The attacker controls when this happens (any CBC suite plus ChangeCipherSpec), so a single malformed record reaches an out-of-bounds heap read on an unauthenticated connection.

## Evidence

176-byte input: ClientHello (TLS_RSA/ECDHE CBC suite) + ClientKeyExchange + ChangeCipherSpec + a record of length 0, into a TLS 1.2 server context:\n\n```\n==92537==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x7beb68fe040f\nREAD of size 1 at 0x7beb68fe040f thread T0\n    #0 tls_parse_message                tlse.c:10715\n    #1 tls_consume_stream               tlse.c:12560\n\n0x7beb68fe040f is located 1 bytes before 1-byte region\nallocated by thread T0 here:\n    #0 malloc\n    #1 tls_parse_message                tlse.c:10505\n```\n\nSource at tlse.c:10505 and 10715:\n\n```c\n        pt = (unsigned char *)TLS_MALLOC(length);      /* length == 0 -> malloc(0) */\n        ...\n            padding_byte = pt[length - 1];             /* pt[-1] */\n```\n\nRemoving the final empty record (171-byte prefix) does not crash, confirming the zero-length record is the trigger. The uninstrumented build exits 0 on the same input.

## Impact

An unauthenticated remote peer can make the TLS terminator read one byte outside a heap allocation on every such connection attempt. The byte is not returned to the attacker and the record is rejected immediately afterwards, so no data is disclosed; the demonstrated effect is a sanitizer-detected out-of-bounds read that aborts hardened builds, and a small information-free side effect in normal builds. It is a memory-safety defect on a pre-authentication path but its standalone impact is limited.

## Counterevidence

I checked whether the read is reachable without the CBC/CCS precondition: with an AEAD cipher tlse.c:10495 rejects records shorter than 8 bytes first, and without ChangeCipherSpec the whole decryption block is skipped - so the CBC + CCS precondition is real and is why the crafted ClientHello/ClientKeyExchange/ChangeCipherSpec prefix is required. Both are attacker-chosen, so this constrains the attack shape, not the attacker. I verified it is not the fuzzer reading its own buffer: the 1-byte read lands immediately before the allocation made by tls_consume_stream() and disappears when the final empty record is removed (171-byte prefix does not crash while the 176-byte version does). The impact assessment is deliberately conservative - after the read, the length-vs-mac_size check returns TLS_BROKEN_PACKET, so no attacker-visible data is disclosed and the uninstrumented build does not crash.

## What Would Change This Severity

Evidence that the byte read before the allocation is reflected back to the peer, or that a zero-length record causes a write rather than a read further down the CBC path, would raise this; confirmation that no shipped build compiles with a sanitizer or hardened allocator would lower it to informational.

## Technical Analysis

In tls_parse_message(), the non-AEAD branch allocates the plaintext buffer with the record payload length and immediately reads the last byte of the plaintext as the CBC padding byte:\n\n```c title=tlse.c startLineNumber=10503 endLineNumber=10505\n        pt = (unsigned char *)TLS_MALLOC(length);\n```\n\n```c title=tlse.c startLineNumber=10713 endLineNumber=10716\n            padding_byte = pt[length - 1];\n            padding = padding_byte + 1;\n```\n\nWhen length is zero, TLS_MALLOC(0) returns a minimal heap chunk and pt[length - 1] reads the byte immediately before it. The AEAD branch guards against short records (tlse.c:10495) but the CBC branch does not, and the only earlier precondition is context->cipher_spec_set, which the attacker establishes by sending ChangeCipherSpec after offering a CBC suite in the ClientHello.\n\nAfter the read, padding_index is negative so the padding check is skipped, decrypted_length stays zero, and the length < mac_size test at tlse.c:10755 returns TLS_BROKEN_PACKET. The defect is therefore a pure out-of-bounds read with no further propagation.

## Remediation

Validate the record payload length against the minimum ciphertext size for the negotiated cipher suite (at least one padding byte plus the MAC length, plus the implicit IV where applicable) before decrypting, and reject shorter records with a bad_record_mac-style error. Additionally, guard the padding-byte read so it is only evaluated when the decrypted length is non-zero, so no code path can index pt[-1] even if the earlier validation changes.

## Fix Verification

Gate 1 security closure: the new precondition rejects any record whose CBC plaintext cannot hold the padding byte plus the MAC before the first read of pt, so pt[length - 1] is only evaluated when length >= 1. The PoC input no longer produces an ASAN report.\n\nGate 2 bypass review: the same expression is the only read of pt before the mac_size check; the AEAD branch above already has its own length guard and was not touched. Alternate shapes tried: length 1 and length 2 records (in-bounds, unchanged behaviour), an AEAD cipher (rejected earlier by the existing length < 8 check), and a non-empty record after ChangeCipherSpec (unchanged).\n\nGate 3 preserved behavior: normal CBC records carry padding and a MAC and are far longer than the new minimum, so the accepted path is unchanged; the full TLS 1.0/1.2 CBC handshake (ECDHE-RSA-AES128CBC-SHA) still completes after the change.\n\nGate 4 repository checks: no test suite or linter exists; the changed code compiles cleanly under gcc -O1 -g with AddressSanitizer and the handshake regression above was re-run.\n\nGap: the check is placed at the point of use rather than by rejecting zero-length CBC records at the record layer; both are correct, and the local placement was chosen to keep the diff minimal.

## Assumptions

Requires the attacker to complete enough of the handshake to install a CBC cipher suite and send ChangeCipherSpec (both attacker-chosen, no credentials needed). The empty record must be the last record in a connection whose buffer is freshly reallocated to its exact size, which is the normal case for a read() per packet.
