# Client-certificate authentication is not enforced: handshake completes without a client certificate and tls_client_verified() returns true for an untrusted self-signed certificate

**ID:** vuln-0011
**Severity:** HIGH
**Found:** 2026-11-17 11:08:47 UTC
**Target:** /workspace/source
**Endpoint:** tlse.c — TLS server handshake, Certificate handler (tls_parse_payload case 0x0B)
**Method:** TLS handshake
**CWE:** CWE-287
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Low

## Description

A TLSe server that calls `tls_request_client_certificate()` still completes the handshake with a peer that presents **no certificate at all** — no verification callback runs, `tls_established()` returns 1, and application data is exchanged — and no library API can make that handshake fail. Additionally, when the application does not install a verification callback (an explicitly optional parameter), a peer presenting **any self-signed certificate it just generated** is accepted and `tls_client_verified()` returns **1**, because the client certificate is never validated against a trust anchor. A server protecting resources with mutual TLS through the library's documented client-certificate API is therefore reachable by an attacker holding no credentials.

## Evidence

**Scenario A — peer presents no certificate; server gates on handshake completion (the shipped example's pattern); unpatched library:**

```text

**Scenario B — peer presents a freshly minted self-signed certificate; server gates on `tls_client_verified()`; no callback installed:**

**Gate matrix, unpatched library (AddressSanitizer + UBSan build, no memory errors):**

In every no-certificate case the server-side `certificate_verify` callback (including `tls_default_verify` with a trust store loaded) is never invoked; the only callback invocations observed belong to the client validating the server certificate.

```

## Impact

Mutual-TLS protected resources are served to unauthenticated peers. Demonstrated against an unmodified library server that requests a client certificate and exposes a protected resource: (1) a client sending an empty certificate list completes the handshake (`established=1`, `client_verified=0`, zero certificates) and receives the protected data; (2) a client presenting a freshly minted self-signed certificate obtains `tls_client_verified()==1` and receives the protected data even when the server gates on that accessor. Both TLS 1.2 and TLS 1.3 are affected. Any server-side authorisation that trusts client-certificate authentication (identity-bound access, service-to-service mTLS, device provisioning) is bypassed, and because requests from the unauthenticated peer are accepted as authenticated, modification on such endpoints follows the same path.

## Counterevidence

The strongest case against this finding is that client-certificate trust is conventionally application-supplied: the library exposes `tls_certificate_chain_is_valid*` and accepts a `certificate_verify` callback, and an application that installs `tls_default_verify` with loaded roots does reject an untrusted client certificate — verified directly, the same PoC with `tls_default_verify` installed aborts the handshake for the self-signed peer. That control, however, does not cover the more important path: it is invoked only when `client_certificates_count > 0`, so a peer that sends an empty certificate list is never subjected to it and the handshake completes no matter which callback is installed — tested with `tls_default_verify` and with a permissive callback, both with an empty list. Nothing in the library or README states that `tls_client_verified()` means proof of possession rather than validated identity, and the accessor returns 1 in the default callback-less configuration, which is a fail-open default rather than a documented policy. The shipped server example gates on `tls_established()` while requesting a client certificate, demonstrating the bypassable pattern in first-party code. What lowers severity is that deployments not relying on client certificates are unaffected, and that scenario B is neutralised by an application-supplied verification callback.

## Confidence Rationale

Reproduced end to end against an unmodified build of this source on TLS 1.2 and TLS 1.3, with a working PoC, a gate matrix, a positive control for the legitimate client path, and a rebuilt patched binary that closes both scenarios. The only untested variation is DTLS, which shares the same Certificate handler but was not exercised end to end.

## What Would Change This Severity

If the deployment only gates non-sensitive resources on client certificates, the confidentiality metric drops to L and the finding becomes medium; conversely, confirmation that a production server combines `tls_request_client_certificate()` with a `tls_established()`-based gate for administrative or tenant-isolated endpoints keeps this at high and could raise integrity impact, since the same unauthenticated peer can submit arbitrary requests the server treats as authenticated.

## Technical Analysis

**1. An empty certificate list is accepted as a successful handshake.** `tls_parse_certificate()` treats an empty list as a successful parse and returns a positive length:

```c title=tlse.c startLineNumber=8643 endLineNumber=8648
    CHECK_SIZE(3, buf_len, TLS_NEED_MORE_DATA)
    size_of_all_certificates = buf[0] * 0x10000 + buf[1] * 0x100 + buf[2];

    if (size_of_all_certificates <= 4)
        return 3 + size_of_all_certificates;
```

The server branch of the Certificate handler invokes the application callback only when a certificate arrived (`&& context->client_certificates_count`), and explicitly permits the empty list:

```c title=tlse.c startLineNumber=9988 endLineNumber=9993
                        if (context->is_server) {
                            if ((certificate_verify) && (context->client_certificates_count))
                                certificate_verify_alert = certificate_verify(context, context->client_certificates, context->client_certificates_count);
                            /*  empty certificates are permitted for client */
                            if (payload_res == 0)
                                payload_res = 1;
```

The TLS 1.0-1.2 branch has the same shape at `tlse.c:10003-10010`. The handshake therefore runs to completion, `tls_established()` becomes 1, the callback never fires, and the server delivers application data and accepts requests from a peer that presented no identity. There is no API to require a certificate — no equivalent of OpenSSL's `SSL_VERIFY_FAIL_IF_NO_PEER_CERT`; `tls_request_client_certificate()` only sets `context->request_client_certificate = 1` (`tlse.c:12972-12978`), used solely to emit the CertificateRequest. RFC 8446 §4.4.2 requires a server that demands client authentication to abort with a fatal alert. The library's own server example shows the bypassable pattern: `examples/tlshelloworld.c:156` requests a client certificate and `:179` gates only on `tls_established(context) == 1`.

**2. `tls_client_verified()` reports success for a certificate that was never validated.** The accessor is:

```c title=tlse.c startLineNumber=12980 endLineNumber=12984
int tls_client_verified(struct TLSContext *context) {
    if ((!context) || (context->critical_error))
        return 0;

    return (context->client_verified == 1);
}
```

`client_verified` is set to 1 only by `tls_parse_verify_tls13()` (`tlse.c:9450-9451`) and `tls_parse_verify()` (`tlse.c:9525-9527`), after the CertificateVerify signature checks out against the certificate the peer itself supplied. Nothing on the handshake path validates that certificate against a trust anchor: `tls_parse_certificate()` parses the DER and stores the chain (`tlse.c:8749-8753`) with no issuer or chain check, and the internal chain validators are never called from the handshake — they run only if the application installs `tls_default_verify` as its callback. A NULL callback is explicitly supported ("If the other side just presented a certificate and certificate_verify is not NULL, it will be called", `tlse.h:337-340`), so the default posture is fail-open and `tls_client_verified()` returns 1 for a certificate the attacker minted seconds earlier. Both defects reproduce on TLS 1.2 and TLS 1.3 (and DTLS shares the same handler). The snapshot has one squashed commit ("Fix for #164"), so no line history is available.

## Proof of Concept

1. Generate an RSA server certificate/key pair and an attacker certificate/key pair with `openssl` (`server_cert.pem`, `server_key.pem`, `attacker_cert.pem`, `attacker_key.pem`).
2. Build the PoC against the library: `gcc -DTLS_AMALGAMATION -g -O0 -o poc poc_compact.c`.
3. Scenario A — TLS 1.3 server calls `tls_request_client_certificate()`, installs no verification callback, and gates the protected resource on handshake completion; the client loads no certificate: `./poc server_cert.pem server_key.pem - - established`. The empty certificate list is accepted (`client_certificates=0`), no server-side callback runs, and the client reads `TOP-SECRET-DATA` (`granted=1`).
4. Scenario B — same server, additionally gating on `tls_client_verified() == 1`, still without a callback; the client presents its own self-signed certificate: `./poc server_cert.pem server_key.pem attacker_cert.pem attacker_key.pem verified`. The handshake completes with `client_verified=1` and the resource is granted to a peer whose certificate chains to nothing.
5. Repeat with a TLS 1.2 server (`tls_create_context(1, TLS_V12)`); both outcomes reproduce.
6. Apply the remediation, rebuild, and re-run: both scenarios end with `established=0` and no data, while a legitimate CA-signed client certificate with `tls_default_verify` installed still completes with `client_verified=1`.

## Remediation

Enforce client authentication instead of requesting it. In the server branch of the Certificate handler, when the application asked for a client certificate, abort the handshake with a fatal alert if the peer presented an empty certificate list, in both the TLS 1.3 and TLS 1.0-1.2 paths, as RFC 8446 section 4.4.2 requires. Make the default fail closed when a client certificate was requested but no verification callback was supplied, so a peer cannot be reported as verified against a certificate the library never validated; applications that intentionally accept arbitrary certificates can still supply an explicit callback. Document that `tls_client_verified()` reflects proof of possession of the presented key rather than validation against a trust anchor, and correct `examples/tlshelloworld.c` so it gates on both `tls_established()` and `tls_client_verified()` and performs real chain validation in its `verify_signature` callback instead of returning `no_error` unconditionally.

## Fix Verification

**Gate 1 — security closure.** Both edits were applied to a copy of the snapshot and the PoC rebuilt against the patched tree. The certificate-less peer now ends with `RESULT ... established=0 ... granted=0`, and so does the self-signed peer (exit status 1 in both cases), versus `established=1 ... granted=1` before the patch. The whole matrix (TLS 1.3 and 1.2, gates `established` and `verified`, peers: none, self-signed, CA-signed) was re-run: every unauthenticated combination ends with `established=0`. The alert path executes as designed — the peer receives a fatal `handshake_failure` alert and `context->critical_error` is set, so `tls_established()` returns -1 and `tls_client_verified()` returns 0.

**Gate 2 — bypass review.** Checked the sibling and alternate inputs: (a) empty certificate list with `tls_default_verify` installed — previously skipped the callback entirely, now rejected; (b) self-signed certificate with no callback — previously `client_verified=1`, now rejected; (c) the same peers over TLS 1.2 — the second location covers them identically, verified empirically; (d) DTLS uses the same Certificate handler and the new branch is not gated on `!context->dtls`, so it applies there too, though DTLS was not driven end to end (gap); (e) a peer that presents a certificate but omits CertificateVerify leaves `client_verified` at 0, which the accessor already reports correctly and the patch does not change. One case is deliberately not closed: an application that installs a callback returning `no_error` without validating still accepts arbitrary certificates — an explicit application decision, documented in remediation rather than blocked by the library.

**Gate 3 — preserved behavior.** A legitimate client certificate signed by a CA in the loaded trust store, with `tls_default_verify` installed, still completes with `client_verified=1` and receives the resource in TLS 1.3 and TLS 1.2, before and after the patch. Applications that never call `tls_request_client_certificate()` are untouched (all new conditions are guarded by `context->request_client_certificate`), and client-side branches are unchanged.

**Gate 4 — repository checks.** The patched `tlse.c` compiles cleanly with `gcc -DTLS_AMALGAMATION -O2 -Wall -Wextra -c` (no diagnostics in the changed region; remaining warnings are pre-existing in the vendored `libtomcrypt.c`), and the AddressSanitizer/UBSan harness build runs both scenarios without memory errors. The repository ships no test suite, so there is no project test target to run. Narrowest-complete-change judgement: the presence check enforces the invariant on every server path; the `!certificate_verify` clause covers the same invariant (a "verified" verdict must follow a real validation decision) which the application cannot enforce after the fact.

## Assumptions

The server requests a client certificate with `tls_request_client_certificate()` and derives its authorisation decision from library state: either handshake completion (`tls_established()`, as `examples/tlshelloworld.c` does) or `tls_client_verified()`. The peer is any network client able to reach the TLS listener and needs no certificate, key, or knowledge of the server's trust store. If an application additionally performs its own checks on `context->client_certificates` (chain validation against its own store, subject pinning) it would stop scenario B, but scenario A still bypasses any gate based on handshake completion.
