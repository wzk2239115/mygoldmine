# Zero-length BIT STRING in X.509 DER causes memcpy with size -1 (remote crash) in TLSe

**ID:** vuln-0001
**Severity:** HIGH
**Found:** 2026-11-17 10:51:30 UTC
**Target:** TLSe (tlslayer) TLS library snapshot
**CWE:** CWE-1284
**CVSS:** 7.5
**Confidence:** High
**Fix Effort:** Low

## Description

A zero-length BIT STRING in an X.509 DER structure makes the ASN.1 parser pass a length of -1 into tls_certificate_set_copy(), which calls memcpy() with SIZE_MAX. A TLS peer presenting such a certificate - or any application calling the public tls_certificate_parse() on attacker-supplied DER - crashes the process. The trigger is an 11-byte DER blob.

## Evidence

Minimal 11-byte DER, instrumented build:\n\n```\n==74110==ERROR: AddressSanitizer: negative-size-param: (size=-1)\n    #0 memcpy\n    #1 tls_certificate_set_copy        tlse.c:4553\n    #2 tls_certificate_set_sign_key    tlse.c:4602\n    #3 _private_asn1_parse             tlse.c:11590\n    #4 _private_asn1_parse             tlse.c:11517\n    #5 asn1_parse                      tlse.c:11780\n```\n\nSame input, uninstrumented build:\n\n```\nmalloc(): corrupted top size\nAborted (core dumped)   exit status 134\n```\n\n105-byte ServerHello + Certificate flight into a TLS 1.3 client context:\n\n```\n==78812==ERROR: AddressSanitizer: negative-size-param: (size=-1)\n    #1 tls_certificate_set_copy        tlse.c:4553\n    #2 tls_certificate_set_sign_key    tlse.c:4602\n    #3 _private_asn1_parse             tlse.c:11590\n    #6 tls_parse_certificate           tlse.c:8702\n    #7 tls_parse_payload               tlse.c:10012\n    #8 _private_tls_consume_handshake  tlse.c:10413\n    #9 tls_parse_message               tlse.c:10832\n    #10 tls_consume_stream             tlse.c:12560\n```\n\nSame flight, uninstrumented build: `Segmentation fault (core dumped) exit status 139`.\n\nA 620-byte DER carved out of a legitimate certificate by mutation reproduced the same defect on both builds.

## Impact

A remote unauthenticated peer can terminate the TLS-hosting process. A malicious or MITM server crashes any TLSe client by appending one malformed Certificate message to its ServerHello; a TLSe server crashes when parsing a client certificate in a mutual-TLS deployment. Because the memcpy size is SIZE_MAX the copy always faults at the first unmapped page, so the effect is a reliable per-connection crash rather than a controlled heap write. Applications that load or inspect certificates from files, configuration or an API via tls_certificate_parse() crash on a single crafted blob.

## Counterevidence

A bare Certificate record without a preceding ServerHello does not crash (tested on TLS 1.2/1.3 client and server contexts) because tls_parse_payload() rejects it on handshake state - the attacker supplies the ServerHello trivially as the peer. Not an instrumentation artefact: the uninstrumented glibc build aborts with a malloc assertion on the 11-byte DER and SIGSEGVs on the 620-byte DER and the handshake flight. The parser does not simply reject malformed input - 154 legitimate certificates parse cleanly on the same build, and the trigger satisfies every length check before the vulnerable branch. No downstream control stops the negative length reaching memcpy.

## What Would Change This Severity

Demonstrating the huge memcpy can be steered into attacker-controlled mapped memory (turning the crash into a controlled write) would raise this to critical; conversely, proving no deployed TLSe build reaches tls_parse_certificate() or tls_certificate_parse() with peer-supplied DER would lower it.

## Technical Analysis

_private_asn1_parse() recurses through the DER tree tracking fields[] (the child index at each level). A primitive BIT STRING that is the third child (idx == 3) of the second nesting level, whose parent is the first child of the outer SEQUENCE (fields[0] == 1), is handed to tls_certificate_set_sign_key() at tlse.c:11590. That helper (tlse.c:4597-4605) strips a leading zero byte without checking that content remains, so a zero-length BIT STRING makes len become -1. tls_certificate_set_copy() (tlse.c:4546-4558) only rejects len == 0, so TLS_MALLOC(len + 1) becomes malloc(0) and memcpy(dst, src, (size_t)-1) is executed, which always faults.\n\nReachability: tls_consume_stream() -> tls_parse_message() -> _private_tls_consume_handshake() -> tls_parse_payload() -> tls_parse_certificate() -> asn1_parse() -> _private_asn1_parse(), i.e. the certificate comes straight from the wire. The same expression is reachable with no handshake at all through the exported tls_certificate_parse() API.\n\nThe 0x00 byte checked by val[0] is the tag byte of the TLV that follows the zero-length BIT STRING, so the trigger is fully attacker-controlled.

## Proof of Concept

1. Write the 11-byte DER blob 3008050005000300000000 to a file; it is a SEQUENCE whose first element is a SEQUENCE containing three elements, the third a zero-length BIT STRING followed by a 0x00 byte.\n2. Feed it to tls_certificate_parse() for the minimal local reproduction.\n3. For the remote reproduction, wrap the DER in a Certificate handshake message: certificate_list length 0x00000e, certificate length 0x00000b, then the DER, wrapped in handshake type 0x0b inside a TLS record of type 0x16.\n4. Prepend a ServerHello record so the handshake state machine accepts the Certificate, then feed the 105-byte stream to a TLS client context through tls_consume_stream().\n5. Both cases abort: the instrumented build reports AddressSanitizer negative-size-param (size=-1) in memcpy; the uninstrumented build aborts in glibc malloc or dies with SIGSEGV.

## Code Analysis

**Location 1:** `tlse.c` (lines 4597-4601)
  Root cause: leading zero stripped without checking that content remains

  **Suggested Fix:**
```diff
- void tls_certificate_set_sign_key(struct TLSCertificate *cert, const unsigned char *val, int len) {
-     if (!val[0]) {
-         val++;
-         len--;
-     }
+ void tls_certificate_set_sign_key(struct TLSCertificate *cert, const unsigned char *val, int len) {
+     if ((len > 0) && (!val[0])) {
+         val++;
+         len--;
+     }
```

**Location 2:** `tlse.c` (lines 4549-4557)
  Defence in depth: reject non-positive lengths and never leave a freed pointer behind

  **Suggested Fix:**
```diff
-     TLS_FREE(*member);
-     if (len) {
-         *member = (unsigned char *)TLS_MALLOC(len + 1);
-         if (*member) {
-             memcpy(*member, val, len);
-             (*member)[len] = 0;
-         }
-     } else
-         *member = NULL;

+     TLS_FREE(*member);
+     *member = NULL;
+     if (len > 0) {
+         *member = (unsigned char *)TLS_MALLOC(len + 1);
+         if (*member) {
+             memcpy(*member, val, len);
+             (*member)[len] = 0;
+         }
+     }
```

## Remediation

Perform the leading-zero strip in tls_certificate_set_sign_key() only when the element actually has content, and make tls_certificate_set_copy() treat every non-positive length as "no value" while clearing the destination pointer. Note that fixing only the copy helper is insufficient: the pointer is already advanced past the value, so the length guard in the caller is required as well. Add DER fuzz coverage for zero-length primitive elements to prevent regressions.

## Fix Verification

Gate 1 security closure: patched source rebuilt (ASAN and uninstrumented). tls_certificate_set_sign_key() now strips a leading zero only when len > 0, so a zero-length BIT STRING keeps len == 0; tls_certificate_set_copy() treats any len <= 0 as no value. Results on the patched build: 11-byte DER exit 0 (was 134), 620-byte DER exit 0 (was 139), 105-byte handshake flight exit 0 (was 139); no ASAN error for any of the three. An unrelated unfixed defect (the DTLS fragment overflow) still aborts on the same binary, so detection is not silently disabled.\n\nGate 2 bypass review: sibling call sites sharing the helper checked - tls_certificate_set_key() guards the decrement with len % 2, tls_certificate_set_priv() never decrements, tls_certificate_set_copy_date() requires len > 4. Alternate inputs tried: the 620-byte mutated DER, an ECDSA certificate with the same zero-length BIT STRING shape, and the same DER inside a handshake flight. All clean. The *member = NULL change also removes a latent use-after-free (a negative length previously skipped both branches and left a freed pointer in *member).\n\nGate 3 preserved behavior: the 154-certificate corpus parses without error on the patched build, identical to unpatched, and full handshakes still complete for TLS 1.0/1.2/1.3 with RSA and ECDSA certificates and for DTLS 1.2 (ECDHE-RSA-AES128GCM-SHA256, TLS-AES-128-GCM-SHA256, ECDHE-RSA-AES128CBC-SHA, ECDHE-ECDSA-AES128GCM-SHA256). Private-key loading still works - the handshake cannot complete otherwise.\n\nGate 4 repository checks: the library has no test suite or linter; the equivalent check is a clean gcc -O1 -g -fsanitize=address compile of tlse.c with no warnings from the changed lines, plus the corpus regression above.\n\nNote on line endings: this repository stores tlse.c with CRLF line terminators, so the suggestion blocks above use CRLF to match the file byte for byte.\n\nGap: no automated unit test exists to lock this in, so the regression was executed manually.

## Assumptions

The remote variant requires the attacker to be the TLS peer (malicious/MITM server for a TLSe client, or a client presenting a certificate to a server doing client-cert auth) and a ServerHello must precede the Certificate message. The local variant needs only attacker-supplied DER reaching tls_certificate_parse().
