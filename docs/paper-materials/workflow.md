# Workflow：八阶段协作与产物传递

## 1. 为什么需要显式工作流

自主漏洞审计的输出不应只是最终回答。后续验证需要知道候选来自哪份源码、基于什么假设、有哪些证据，以及前序阶段实际具备哪些能力。多智能体协作还需要区分“模型认为任务完成”与“后续阶段已获得可用产物”。

本系统采用显式输入、输出和交付记录组织八阶段协作。智能体负责分析、探索和具体任务决策；工作流负责阶段依赖、身份绑定、产物完整性及失败恢复。二者相互配合：阶段执行结构可以固定，阶段内部的分析路径保留自主性。

## 2. 节点及其主要输入输出

| 节点 | 主要输入 | 主要输出及后续用途 |
|---|---|---|
| I 环境构建 | 项目源码、源码版本及环境需求 | 可用环境、能力与限制记录，为后续分析及验证提供条件 |
| II 安全审计编排 | 源码、环境能力、已有知识与探索建议、固定的方法版本 | 候选报告、覆盖与假设记录、读取观测，交给解释设计和动态验证 |
| III 攻击场景设计 | 候选报告及漏洞机制描述 | 技术解释图和说明产物；辅助表达，不充当漏洞证据 |
| IV 蓝队验证 | 候选及其证据、源码、环境 | 验证脚本、实际输出、证据或反证、结论与限制，支持后续候选选择 |
| V 红队场景构建 | 符合条件的蓝队确认结果、相关证据及环境信息 | 受控场景、执行约束、就绪或受阻记录，交给红队执行 |
| VI 红队执行 | 就绪场景及固定的输入条件 | 工具执行轨迹、捕获结果与证据来源记录，交给独立审核 |
| VII 独立审核 | 红队轨迹、候选、场景与证据 | 审核结论及理由，支持判断是否形成合格成果 |
| VIII 经验学习 | 前序反馈摘要及相关证据、覆盖与读取记录、技能版本 | 方法候选、探索反馈和项目限定试用安排，影响后续轮次 |

这里的“主要输入”描述节点职责，不表示每个智能体会读取所有可用文件。系统保存依赖关系，智能体根据任务需要读取相关材料。

## 3. 四条相互联系的数据流

### 3.1 候选与假设流

阶段二提出的是待核实候选，不是最终漏洞结论。后续阶段分别补充验证、场景、执行与审核状态。符合进入条件的候选继续推进；未进入、被排除、待定和受阻的候选保留对应状态。

因此，后续阶段处理数量少于阶段二候选数量，并不必然意味着漏传。需要区分两类情况：明确记录的选择或不适用，以及没有来源和原因的遗漏。前者属于流程语义，后者属于交付缺陷。

### 3.2 能力与限制流

环境阶段输出的能力和限制应影响后续任务选择。例如，缺少编译器或目标运行时，应作为验证可行性的条件，而不是等价为候选不存在。

后续阶段继续保存限制及受阻原因，供经验学习区分环境缺口、方法不足和程序故障。环境部分可用时可以支持有限任务，但不能将局部验证扩大解释为完整目标环境中的验证。

### 3.3 证据与审核流

蓝队验证提供脚本、运行输出和证据；红队执行进一步提供符合场景约束的轨迹；独立审核检查结论是否由这些证据支持。

经过验证审核的报告可用于后续探索反馈，但系统内部资格与外部 CVE 分配不同。解释性图片也不提高证据等级。

### 3.4 方法反馈流

阶段八读取前序阶段的反馈摘要和必要证据，分析哪些方法有效、哪些方向重复、哪些受阻来自环境或程序，并提出针对性的技能补充。

下一轮重新执行 I—VIII 时，阶段二可以使用更新后的探索建议和符合条件的项目试用版本。再次进入阶段一不意味着必须无条件重建所有环境；是否复用及其检查由环境执行机制决定。

## 4. 节点间如何传递产物

阶段之间通过持久化产物及交付记录建立联系，不依赖模型在对话中记住所有信息。交付记录主要回答：

1. 产物属于哪个项目、哪次审计及哪个阶段？
2. 本阶段基于哪些已交付输入执行？
3. 实际产生了哪些文件或结构化结果？
4. 内容是否完整且仍与交付时一致？
5. 阶段的完成、部分可用、跳过或失败应如何解释？

依赖记录可以包含此前多个阶段的产物，不局限于直接前驱。例如，场景构建既依赖原始候选，也依赖蓝队确认和环境信息。下游仍需按自己的语义条件选择相关输入。

这种组织方式提供可追溯性和完整性检查，并不自动证明模型已经理解了全部输入，或每个文件的语义都正确。

## 5. 身份、版本与交付边界

**身份绑定。** 项目标识与展示名称分开，候选和报告保持所属项目及审计上下文。消费方核对明确身份，冲突不能通过品牌别名或目录猜测消除。

**版本绑定。** 工作流记录源码和报告版本，并在任务启动时固定技能版本。后续阶段不应把旧报告的验证结果套用到已改变的候选上。

**完整性交付。** 对普通产物保存内容摘要，消费前检查是否缺失或改变；报告明确引用的必要附件需要可用。原始执行输出、验证脚本和证据不能仅凭模型文字说明替代。

**运行环境与证据分开。** 容器解释器、虚拟环境等运行材料不是可移植的漏洞证据。当前交付机制可对识别出的 Python 虚拟环境记录配置、文件摘要和链接文本快照，而正式脚本与证据继续接受原有检查。这避免把宿主机无法解析的容器路径错误地当作证据损坏，也不意味着可以忽略缺失的必要附件。

## 6. 失败、跳过和恢复

流程需要区分：

- **分析或执行失败**：任务未产生可接受结果。
- **条件不满足**：没有符合下游要求的候选或场景，节点可按规则跳过。
- **部分可用或受阻**：已有局部结果，同时明确记录能力缺口与限制。
- **交付失败**：计算可能已经结束，但结果缺少附件、身份不符或完整性校验未通过。

交付失败不应默认触发整轮重跑。若项目、工作流、输入版本及已完成批次仍满足复用条件，修复交付问题后可以重新校验已有结果，再从未交付节点继续。若上游内容改变或复用条件不满足，则不能直接沿用旧结果。

重复调用已完成节点时，工作流核对已有交付记录，而不是无条件重新调用模型。这为长时间、多阶段审计提供了恢复基础，但不应表述为系统能够自动修复任意失败。

## 7. 为什么这对 RSI 必要

经验学习需要知道“发生了什么”和“结果基于什么”，而不仅是最后是否生成了报告。显式产物传递使阶段八可以：

- 将验证反证关联到原审计假设；
- 将场景受阻关联到环境能力或构造方式；
- 将报告成果关联到采用的任务和方法版本；
- 避免将缺失记录推断为成功；
- 在方法试用后继续观察收益与退化。

因此，Workflow 是反馈可信度和协作可恢复性的基础；它本身不等同于自改进算法。只有后续探索或方法确实因反馈发生变化，才涉及 RSI 的方法层行为。

## 8. 可直接用于系统概述的文字

系统以八阶段工作流组织环境准备、候选发现、机制解释、动态验证、场景构建、红队执行、独立审核与经验学习。每个阶段通过具有项目与版本身份的持久化产物进行协作，并以交付记录显式描述输入依赖、输出内容及阶段状态。后续节点根据候选资格和实际能力选择任务，在消费前检查上游产物的一致性；失败恢复则优先复用仍满足条件的已完成结果。该组织方式将智能体的自主分析与执行框架的身份、完整性和恢复职责分离，为跨阶段反馈和技能级改进提供可追溯依据。
