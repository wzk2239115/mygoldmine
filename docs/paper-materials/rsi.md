# RSI：反馈引导的探索与技能改进

## 1. 动机与总体思路

持续漏洞审计面临两个问题：反复执行相同策略容易重复检查已有区域，而仅凭模型总结生成的新规则又缺少实际收益依据。我们将审计任务探索与方法改进分成两个相互联系的层次：前者决定下一步检查什么，后者根据真实反馈改变可复用的检查方法。

系统借鉴覆盖引导模糊测试的设计：保留产生新信息的探索方向，并为值得追踪的任务分配更多投入。在此基础上，将代码读取、审计意图、证据变化与后续验证成果关联，由经验学习阶段提炼小范围的 Markdown 方法补充，供后续自然审计任务试用。

这里的自改进对象是智能体使用的技能指导与探索策略，不是语言模型参数。系统继续保留原有的漏洞验证、隔离和独立审核标准。

## 2. 以任务意图组织代码探索

一个审计任务可以表示为：

> 源码版本、代码区域或入口、检查视角、待验证假设、已有证据。

智能体在派发任务前明确其意图，例如检查“请求入口到敏感操作之间是否存在权限校验”。工具观测随后记录实际读取位置，并与任务声明关联。同一代码可以接受多种有实质差异的检查：鉴权、输入传播、资源消耗等视角不应因为文件已经读过而被排除。

当前任务去重以源码版本、区域和检查视角为主要依据，假设和证据作为任务属性保存，避免仅通过改写意图名称获得新的探索奖励。

读取观测区分直接读取、搜索命中、未知范围和未关联意图。它提供智能体接触代码的可观测记录，并不证明其理解程度，也不等同于安全审计完成度。当前的意图是任务级显式声明，不能表述为对模型内部思维的直接观测。

## 3. 分层反馈与 interesting

系统使用不同强度的信号，而不是将所有新增输出视为同等收益。

| 反馈层次 | 典型信号 | 作用 |
|---|---|---|
| 探索接触 | 首次读取某个文件内容版本 | 提供较弱的新颖性信号 |
| 证据推进 | 覆盖条目的证据发生变化 | 提示值得继续检查的方向 |
| 经核验成果 | 新的独立问题满足既有验证、红队证据与独立审核要求，并形成合格报告 | 提供较强的后续反馈 |

当前实现将这些信号组合为启发式奖励，并对过程信号封顶，使重复读取和大量生成中间文本不能取代最终成果。报告按问题语义标识去重；不能确认身份时，不以报告标题猜测新漏洞。反馈不可用时保留缺失状态，不补造成功信号。

需要强调，证据摘要变化本身不证明证据质量提高，读取新文件也可能只是无效探索。因此过程信号主要服务于任务选择，经过核验的成果则提供更强的判断依据。当前奖励权重属于工程启发式，尚未证明其最优性。

## 4. energy 与自主探索

energy 表示一个任务值得获得的探索投入建议。出现证据推进、且风险较高的任务可以获得更深入的追踪；连续停滞的任务降低优先级；执行受阻的任务暂缓，等待条件变化后复查。

系统同时建议保留一部分投入用于冷门区域和新假设，避免历史成功方向占用全部注意力。智能体可以根据项目情况调整任务顺序、提出新任务、改变检查视角，并说明偏离建议的原因。

当前 energy 是离散建议档位，不是严格的 token 配额或最优资源分配算法。程序继续管理总体运行限制，Markdown 方法指导负责如何利用探索建议。这使执行边界与分析自主性可以分别维护。

## 5. 按需检索与方法扩展

当当前方向缺少新信息时，智能体可以自行选择扩展调用方、寻找反证、换视角复查，或检索同类项目的漏洞披露和修复材料。

检索优先关注官方公告、维护者分析及修复提交，提炼受影响条件、信任边界、缺失检查和修复机制。随后必须回到当前项目源码，核实对应条件是否存在。其他项目中的已知漏洞只提供假设来源，不能直接作为当前项目存在漏洞的依据。

探索中形成的新方法可以先作为本轮 Markdown 补充上下文使用，再交由经验学习阶段判断是否值得长期保留。项目专有入口、路径和版本条件保留项目适用范围；具有可复用依据的方法才提出通用技能候选。

这一过程不是固定的“没有报告就必须上网搜索”，也不把外部网页内容直接转化为生效指令。

## 6. 以 Markdown 为主要优化对象

经验学习阶段综合前序阶段的反馈，先区分问题类型：

- **方法缺口**：现有技能没有表达必要的阅读、任务分派、假设追踪或反证要求。
- **项目知识**：问题主要涉及特定仓库的入口、版本或环境条件。
- **程序故障**：现有要求已经正确，但执行器崩溃、记录丢失或交接失败。
- **证据不足**：尚不能确定应修改什么。

只有明确的方法缺口进入技能方法优化。程序故障形成带证据的修复需求，不通过追加提示词假装解决。已有正确规则未被执行时，应先调查原因，避免技能文档不断积累同义约束。

候选以实际使用的 agent／skill 文档为依据，优先生成小范围补充，记录来源、适用范围、预期动作和可能退化。当前默认直接生成 Markdown 候选；SkillOpt 保留为可选的文本改写工具，不再作为方法的必要环节。

## 7. 项目限定试用、保留与撤回

为了避免所有改动都被完整 benchmark 阻塞，阶段二的方法候选允许在后续自然任务中进行项目限定试用。即使候选面向通用方法，也先在来源项目使用，不立即传播到全部仓库。

试用版本与稳定规则分开记录。新工作流固定要使用的版本；加载时核对项目、目标阶段与文档基线，防止旧候选被应用到已经变化的上下文。

系统观察试用版本是否关联新的探索信息和正式报告。持续无增益或运行失败时收回试用，有持续过程收益时可保留为项目限定规则。因运行失败而收回是一种保守措施，并不证明该技能导致了失败。

当前实现主要支持阶段二的项目限定方法试用；其他阶段及跨项目稳定发布仍沿用既有评估机制。当前每个项目只有一个在用试用候选，尚未实现多个技能组合的搜索与贡献分解。

## 8. 反馈归因与证据边界

“采用候选后出现了新报告”是有价值的正向关联，但源码、模型、环境、投入和随机性都可能影响结果。系统记录这种关联，用于继续探索和方法选择，不直接解释为因果提升。

因此，日常运行与论文评估承担不同职责：日常运行允许可回退的小范围试用，论文实验则需要在可比较条件下分析收益。建议采用固定技能重复审计作为基线，逐步加入读取覆盖、意图关联、energy、方法试用和外部漏洞知识检索，分别评估各部分的贡献。

主要结果应关注相同预算下的独立经核验问题数、首份报告成本、误报与重复情况，以及试用规则的实际采用与退化；不以候选文件数量、读取量或模型自评分代替效果。

## 9. 与覆盖引导模糊测试的关系

本方法借鉴 AFL 的输入保留和 AFLFast 的 energy 分配思想，但两者的反馈并不等价：模糊测试通常利用程序执行覆盖，当前系统观测的是代码读取和审计证据状态。

对应关系可以概括为：

| 模糊测试概念 | 本系统中的对应对象 |
|---|---|
| 种子 | 带代码范围、检查视角和假设的审计任务 |
| 新覆盖行为 | 新读取对象、证据推进及后续核验成果 |
| energy | 后续探索投入建议 |
| 变异 | 由智能体选择新的输入链、调用方、视角或方法 |
| 语料保留 | 探索记录及可继续追踪的任务 |

方法层的技能修改进一步改变后续探索行为，这是需要通过实验单独分析的部分；不能仅因使用了覆盖反馈，就声称已经证明自改进。
