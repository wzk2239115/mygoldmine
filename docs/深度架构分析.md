## Agent 架构视角

### ✅ 架构设计优点

#### 1. 渐进式上下文管理策略（⭐⭐⭐⭐⭐）

**设计理念**：
- 将大型代码库的分析任务分解为串行的技能链
- 每个技能只关注特定维度，避免上下文爆炸

**实现位置**：
```
project-profiler (上下文: 项目结构扫描)
    ↓ 产物: project-profile.md (10KB)
web-auth-analyzer (上下文: 认证相关代码)
    ↓ 产物: web-auth-analyzer.md (50KB)
route-scanner (上下文: 路由定义代码)
    ↓ 产物: route-scanner.md (30KB)
```

**优势**：
- **上下文窗口利用率高**：每个技能专注于特定代码区域，避免一次性加载整个代码库
- **线性复杂度**：O(n) 而非 O(n²)，n 为代码库大小
- **可扩展性强**：新增技能不影响现有技能的上下文预算

**代码证据**（web-auth-analyzer SKILL.md:62-69）：
```markdown
**脚本覆盖范围**：
- ✅ **认证机制识别**：自动识别 JWT、Session、OAuth、API Key 等认证方式
- ✅ **认证豁免配置**：自动识别白名单、条件豁免、环境变量控制等
- ❌ **深度安全分析**：认证绕过验证、权限提升路径分析需要结合脚本结果进行手动分析
- ❌ **修复建议**：修复建议需要结合具体代码上下文进行手动分析
```

**设计亮点**：
- 明确区分了"自动化扫描"（quick-scan.py）和"深度分析"（LLM）的边界
- 自动化脚本负责数据收集，LLM 负责上下文理解和推理

#### 2. 混合执行模式：确定性 + 概率性（⭐⭐⭐⭐⭐）

**架构分层**：
```
┌─────────────────────────────────────┐
│  LLM 层 (Claude Agent)              │
│  - 上下文理解                        │
│  - 关联分析                          │
│  - 修复建议生成                      │
└─────────────────────────────────────┘
           ↑ 结构化数据
┌─────────────────────────────────────┐
│  确定性规则层 (quick-scan.py)        │
│  - Tree-sitter AST 解析              │
│  - 正则模式匹配                      │
│  - 优先级判定                        │
└─────────────────────────────────────┘
           ↑ 源代码
┌─────────────────────────────────────┐
│  代码库                              │
└─────────────────────────────────────┘
```

**优势**：
- **精确性 + 灵活性**：Tree-sitter 提供精确的语法分析，LLM 提供语义理解
- **成本优化**：大量的模式匹配工作由 Python 脚本完成（成本 ~$0），LLM 只处理高价值的分析（成本 ~$1-10/项目）
- **可复现性**：确定性规则保证了基础扫描结果的一致性

**实现证据**（sensitive-info-scanner quick-scan.py:63-90）：
```python
class TreeSitterParserManager:
    """Tree-sitter 解析器管理器，使用 tree-sitter-language-pack。"""

    def get_parser(self, language: str) -> Optional[Parser]:
        """获取指定语言的解析器。"""
        if language in self.parsers:
            return self.parsers[language]

        parser = get_parser(language)
        if parser:
            self.parsers[language] = parser
            return parser
        return None
```

**设计权衡**：
- ✅ **准确性优先**：使用 AST 解析而非简单的正则匹配，避免误报
- ⚠️ **性能开销**：Tree-sitter 解析需要额外的计算，但相比全代码库上下文加载仍然高效

**代码证据**（web-auth-analyzer SKILL.md:154-162）：
```markdown
#### 认证机制安全风险

| 风险类型 | 描述 | 检测要点 |
|---------|------|---------|
| JWT 密钥泄露 | 硬编码密钥、弱密钥、密钥存储不当 | 搜索 `secret`、`key`、`jwt` 相关配置 |
| JWT 算法混淆 | 允许 `none` 算法或 RS256/HS256 混用 | 检查 JWT 验证配置 |
```

**设计洞察**：
- 表格形式是**高密度知识编码**：紧凑、结构化、易于 LLM 解析
- 每个风险都包含：类型 + 描述 + 检测方法，形成完整的知识闭环

**优势**：

- **容错性**：某个技能失败不会影响其他技能，可以从断点恢复

**产物格式设计**（web-auth-analyzer SKILL.md:404-572）：

- **关键决策前置**："认证可绕过"、"多角色体系"等布尔字段控制下游分支逻辑
- **可解释性**："结论依据"字段提供了决策的推理路径

#### 5. 模块化与职责单一原则（⭐⭐⭐⭐）

**技能边界设计**（web-auth-analyzer SKILL.md:22-27）：
```markdown
### 明确不做

- ❌ **漏洞利用执行**：仅输出 PoC 说明，不实际执行攻击
- ❌ **授权逻辑深度分析**：具体的权限检查逻辑由 `idor-analyzer` 处理
- ❌ **业务逻辑漏洞**：业务流程中的逻辑缺陷不在范围内
- ❌ **密码学算法审计**：不深入分析加密算法的安全性
- ❌ **配置文件全面审计**：仅关注认证相关配置，其他配置由 `sensitive-info-scanner` 处理
```

**优势**：
- **认知负载低**：每个技能的 SKILL.md 都明确说明了"做什么"和"不做什么"
- **避免重复**：不同技能之间职责清晰，没有功能重叠
- **易于扩展**：新增技能不会影响现有技能的逻辑

**技能协作机制**（web-auth-analyzer SKILL.md:29-45）：
```markdown
### 与其他技能的协作

#### 前置技能
- **`vtr-scanner`**（路由扫描）：提供路由表信息，帮助识别需要保护的端点
- **`project-profiler`**（项目画像）：提供技术栈信息，指导框架特定的认证机制识别

#### 后置技能（下游任务）
- **`unauth-route-scanner`**：提取无需认证的路由，进行进一步安全分析
- **`normal-route-scanner`**：提取普通用户可访问的路由，检测 IDOR 等授权问题

#### 平行技能（配合使用）
- **`sensitive-info-scanner`**：检测配置文件中的密钥泄露（JWT secret 等）
```

**设计模式识别**：
- **责任链模式**：project-profiler → web-auth-analyzer → route-scanner
- **发布-订阅模式**：web-auth-analyzer 发布产物，多个下游技能订阅
- **策略模式**：根据上游产物的决策字段（如"多角色体系"），选择不同的下游技能组合

### ❌ 架构设计缺陷

#### 1. 串行执行的性能瓶颈（⭐⭐⭐⭐⭐）

**问题描述**：
- 所有技能串行执行，总耗时 = Σ(技能耗时)
- 对于大型项目，可能需要 10-30 分钟

**代码证据**：
```mermaid
graph LR
    A[project-profiler<br/>2min] --> B[web-auth-analyzer<br/>5min]
    A --> C[sensitive-info-scanner<br/>3min]
    B --> D[unauth-route-scanner<br/>2min]
    B --> E[normal-route-scanner<br/>3min]

    总耗时: 2 + max(5, 3) + max(2, 3) = 2 + 5 + 3 = 10min
```

**当前设计**：
- web-auth-analyzer 和 sensitive-info-scanner 都依赖 project-profiler，但它们之间是独立的，**可以并行执行**
- 但现有架构是串行的

**改进方案**：
```json
{
  "tasks": [
    {
      "artifact": ".workspace/tasks/{TASK_ID}/project-profile.md",
      "skill": "web-auth-analyzer",
      "run_in_parallel": true          // 新增并行标志
    },
    {
      "artifact": ".workspace/tasks/{TASK_ID}/project-profile.md",
      "skill": "sensitive-info-scanner",
      "run_in_parallel": true
    }
  ]
}
```

**理论加速比**：
- 当前：O(n) 串行
- 并行后：O(log n) 树形结构
- 实际加速：2-3倍（受限于 LLM API 的并发限制）

#### 2. 上下文碎片化问题（⭐⭐⭐⭐⭐）

**问题描述**：
- 每个技能只能看到自己的上下文窗口，无法全局关联分析
- 跨技能的复杂漏洞可能被遗漏

**具体场景**：
```python
# 文件1: src/routes/payment.py
@app.route('/api/payment', methods=['POST'])
@login_required                           # ← web-auth-analyzer 看到这里
def process_payment():
    user_id = request.json.get('user_id')  # ← 用户可控参数
    amount = request.json.get('amount')
    payment_service.charge(user_id, amount)  # ← 未验证 user_id 是否属于当前用户

# 文件2: src/services/payment.py
def charge(user_id, amount):
    # ← normal-route-scanner 看到这里
    user = User.query.get(user_id)
    user.balance -= amount
    db.session.commit()
```

**漏洞分析**：
- **IDOR 漏洞**：用户可以通过修改 `user_id` 扣除他人余额
- **问题**：这需要同时理解：
  1. `/api/payment` 需要认证但允许普通用户访问（web-auth-analyzer）
  2. `user_id` 参数未验证归属权（需要跨文件的数据流分析）

**当前架构的局限**：
- web-auth-analyzer 只关注认证，不分析参数
- normal-route-scanner 提取路由，但不分析业务逻辑
- 没有专门的 IDOR 分析技能来关联这两部分

**现有设计的部分缓解**（web-auth-analyzer SKILL.md:24）：
```markdown
- ❌ **授权逻辑深度分析**：具体的权限检查逻辑由 `idor-analyzer` 处理
```

**改进方案**：
1. 增加 `idor-analyzer` 技能，整合 web-auth-analyzer 和 route-scanner 的产物
2. 使用数据流分析引擎（如 CodeQL）追踪污点数据
3. 引入"回溯机制"：下游技能发现可疑模式时，触发上游技能的重新分析

#### 3. 产物格式的脆弱性（⭐⭐⭐⭐）

**问题描述**：
- 下游技能强依赖上游产物的 Markdown 格式
- 格式变化会导致解析失败

**代码证据**（normal-route-scanner SKILL.md:97-108）：
```markdown
### 1. 读取上游产物

**必需输入**：
- 认证分析结果：`.workspace/tasks/{AUTH_TASK_ID}/web-auth-analyzer.md`

从上游产物中获取：
- 认证机制是否可绕过
- 角色体系定义
- 管理员专属路由前缀
- 权限控制实现方式
```

**潜在问题**：
```markdown
# 上游产物格式变化示例

## 旧格式
- **认证可绕过**：是

## 新格式（更详细）
- **认证可绕过**：是（环境变量 DISABLE_AUTH=true）
                     ↑ 新增的说明文本可能破坏正则解析
```

**脆弱性分析**：
- **正则解析不稳定**：Markdown 格式的自由度高，很难用正则精确解析
- **缺乏 Schema 验证**：没有强制的产物格式规范
- **版本兼容性差**：SKILL.md 更新后，产物格式可能变化，影响下游技能

**改进方案**：
1. **引入结构化产物**：使用 JSON Schema 定义产物格式
   ```json
   {
     "auth_bypassable": true,
     "bypass_method": "环境变量 DISABLE_AUTH=true",
     "role_system": {
       "multi_role": true,
       "roles": ["admin", "user", "guest"]
     }
   }
   ```

2. **双格式输出**：
   - Markdown：人类可读，用于报告生成
   - JSON：机器可读，用于技能间数据传递

3. **版本控制**：
   ```json
   {
     "schema_version": "1.0.0",
     "data": { ... }
   }
   ```

#### 4. 缺乏反馈循环和迭代优化（⭐⭐⭐⭐）

**问题描述**：
- 单向数据流，下游技能无法影响上游技能的分析
- 没有"假阳性反馈"机制来优化规则

**场景示例**：
```
1. project-profiler 识别项目为 "Express 项目"
2. web-auth-analyzer 使用 Express 的认证模式进行扫描
3. 实际上项目同时使用了 Express + NestJS (微服务架构)
4. NestJS 部分的认证机制被遗漏
```

**当前架构的局限**：
- project-profiler 一旦判定项目类型，后续技能无法修正
- 没有"置信度"概念，所有决策都是二元的（是/否）

**改进方案**：

1. **引入置信度系统**：
   ```json
   {
     "project_type": "backend_http_service",
     "confidence": 0.95,
     "frameworks": [
       { "name": "Express", "confidence": 0.90, "files": [...] },
       { "name": "NestJS", "confidence": 0.30, "files": [...] }
     ]
   }
   ```

2. **反馈循环机制**：
   ```
   web-auth-analyzer 发现 NestJS 特定的装饰器 (@UseGuards)
       ↓
   向 project-profiler 发送反馈："发现 NestJS 证据"
       ↓
   project-profiler 更新框架列表
       ↓
   重新触发 web-auth-analyzer（仅针对 NestJS 部分）
   ```

3. **人工反馈集成**：
   ```json
   {
     "feedback": {
       "false_positive": [
         {
           "finding_id": "auth-001",
           "reason": "测试代码，非生产环境",
           "action": "add_to_whitelist"
         }
       ]
     }
   }
   ```

#### 5. LLM 调用成本累加问题（⭐⭐⭐）

**成本分析**：

假设一个中型项目（10,000 行代码）：
```
project-profiler:
  - quick-scan.py 输出: 5KB
  - LLM 分析: 5K tokens input + 2K tokens output
  - 成本: ~$0.02 (Sonnet 4.5)

web-auth-analyzer:
  - quick-scan.py 输出: 50KB
  - LLM 分析: 50K tokens input + 10K tokens output
  - 成本: ~$0.20

sensitive-info-scanner:
  - quick-scan.py 输出: 30KB
  - LLM 分析: 30K tokens input + 5K tokens output
  - 成本: ~$0.12

unauth-route-scanner:
  - quick-scan.py 输出: 20KB
  - LLM 分析: 20K tokens input + 5K tokens output
  - 成本: ~$0.08

normal-route-scanner:
  - quick-scan.py 输出: 30KB
  - LLM 分析: 30K tokens input + 8K tokens output
  - 成本: ~$0.12

总成本: ~$0.54/项目
```

**问题**：
- 对于大型项目（100,000+ 行），成本可能达到 $5-10/项目
- 如果需要多次迭代或反馈循环，成本会进一步增加

**优化方案**：

1. **缓存机制**：
   ```python
   # 对于未修改的文件，复用上次的分析结果
   ```

2. **增量分析**：
   ```python
   # 只分析 git diff 中变更的文件
   changed_files = git diff --name-only HEAD~1
   # 合并旧的分析结果和新的分析结果
   ```

   ```python
       "分析文件1的认证机制",
   ```

#### 2. 缺乏数据流分析（⭐⭐⭐⭐⭐）

**问题描述**：
- 无法追踪污点数据（用户输入）从入口点到危险函数的完整流向
- 导致大量的 IDOR、SQL 注入等漏洞被遗漏

**具体示例**：

##### IDOR 漏洞检测的局限

```python
# 文件1: routes.py
@app.route('/api/user/<user_id>/profile', methods=['GET'])
@login_required
def get_user_profile(user_id):
    # ← normal-route-scanner 检测到这里
    profile = get_profile_from_db(user_id)  # ← 参数传递
    return jsonify(profile)

# 文件2: services.py
def get_profile_from_db(user_id):
    # ← 这里没有检查 user_id 是否属于当前用户
    return db.query("SELECT * FROM users WHERE id = ?", user_id)
```

**当前工具的检测结果**：
- ✅ 检测到路由：`GET /api/user/<user_id>/profile`
- ✅ 检测到需要认证：`@login_required`
- ❌ **无法检测到 IDOR**：因为没有追踪 `user_id` 从路由参数到数据库查询的流向
- ❌ **无法检测到缺失的权限检查**：`get_profile_from_db` 应该验证 `user_id == current_user.id`

**需要的数据流分析**：
```
污点源: user_id (路由参数)
    ↓
传播路径: get_user_profile() → get_profile_from_db()
    ↓
危险沉淀点: db.query() (未验证归属权)
    ↓
漏洞: IDOR
```

##### SQL 注入检测的局限

```python
# 文件1: routes.py
@app.route('/api/search', methods=['GET'])
def search_users():
    query = request.args.get('q')  # ← 污点源
    results = search_service.search(query)  # ← 污点传播
    return jsonify(results)

# 文件2: services.py
def search(query):
    # 污点数据经过了转换
    sanitized = query.replace("'", "''")  # ← 不安全的转义
    # 仍然被拼接到 SQL 中
    sql = f"SELECT * FROM users WHERE name LIKE '%{sanitized}%'"  # ← 危险沉淀点
    return db.execute(sql)
```

**当前工具的检测结果**：
- ✅ 检测到路由：`GET /api/search`
- ❌ **无法检测到 SQL 注入**：因为没有追踪 `query` 从请求参数到 SQL 拼接的完整流向
- ❌ **无法判断转义是否有效**：`replace("'", "''")` 在某些 SQL 方言中不够安全

**专业工具的对比**：

| 工具 | 数据流分析能力 | 实现方式 |
|------|-------------|---------|
| **Vul-AI-V2** | ⭐ (无) | 模式匹配 |
| **CodeQL** | ⭐⭐⭐⭐⭐ | Datalog 查询语言，全程序数据流分析 |
| **Semgrep** | ⭐⭐⭐ | 跨函数污点追踪（有限） |
| **Checkmarx** | ⭐⭐⭐⭐ | 跨文件数据流分析 |
| **Fortify** | ⭐⭐⭐⭐⭐ | 全程序数据流 + 控制流分析 |

**改进方案**：

1. **集成现有数据流分析引擎**：
   ```python
   # 使用 CodeQL 作为后端
   codeql_results = run_codeql_query("""
       from DataFlow::PathNode source, DataFlow::PathNode sink
       where
         source = userControlledSource() and
         sink = sqlInjectionSink() and
         DataFlow::flow(source, sink)
       select sink, source, sink, "SQL injection vulnerability"
   """)

   # LLM 分析 CodeQL 结果，生成报告
   report = llm_analyze(codeql_results)
   ```

2. **轻量级污点追踪**：
   ```python
   # 基于符号执行的简化污点追踪
   def trace_taint(entry_point, taint_source):
       visited = set()
       taints = {taint_source: []}

       def visit(node, taint_value):
           if node in visited:
               return
           visited.add(node)

           # 模拟符号执行
           if isinstance(node, ast.Call):
               if is_dangerous_function(node.func):
                   # 发现危险沉淀点
                   report_vulnerability(taint_value, node)
               else:
                   # 继续追踪
                   for arg in node.args:
                       visit(arg, taint_value)

       visit(entry_point, taint_source)
   ```

#### 3. 业务逻辑漏洞检测能力弱（⭐⭐⭐⭐）

**问题描述**：
- 业务逻辑漏洞通常涉及多个步骤、复杂的状态转换
- 当前工具主要关注代码级别的安全问题，难以理解业务语义

**具体示例**：

##### 场景 1：支付逻辑漏洞

```python
# 步骤1: 创建订单
@app.route('/api/order/create', methods=['POST'])
@login_required
def create_order():
    items = request.json.get('items')
    total = calculate_total(items)  # ← 这里计算总价

    order = Order(user=current_user, items=items, total=total)
    db.session.add(order)
    db.session.commit()

    return jsonify({'order_id': order.id, 'total': total})

# 步骤2: 支付订单
@app.route('/api/order/<order_id>/pay', methods=['POST'])
@login_required
def pay_order(order_id):
    order = Order.query.get(order_id)

    # ⚠️ 漏洞: 没有重新验证订单总价
    # 用户可以在步骤1和步骤2之间修改数据库中的 order.total
    # 或者通过重放步骤1的响应来获取旧的总价

    payment_service.charge(current_user, order.total)  # ← 使用可能被篡改的总价
    order.status = 'paid'
    db.session.commit()

    return jsonify({'success': True})
```

**漏洞分析**：
- **竞态条件**：订单创建和支付之间存在时间窗口
- **业务逻辑缺陷**：支付时应该重新计算总价，而非信任数据库中的值
- **攻击向量**：
  1. 用户创建订单，获得 `order_id` 和 `total = 100`
  2. 用户修改商品价格配置（如果有权限）或直接修改数据库（如果存在 SQL 注入）
  3. 用户调用支付接口，使用篡改后的低价支付

**当前工具的检测结果**：
- ✅ 检测到两个路由：`POST /api/order/create`, `POST /api/order/<order_id>/pay`
- ✅ 检测到都需要认证
- ❌ **无法检测到业务逻辑漏洞**：因为需要理解：
  - 两个路由之间的业务关系
  - 状态机转换的完整性
  - 金额校验的缺失

##### 场景 2：优惠券重复使用

```python

    order_id = request.json.get('order_id')

    coupon = Coupon.query.filter_by(code=coupon_code).first()

        order.total -= coupon.amount
```

## 核心设计哲学

通过深度分析，我们可以提炼出这个项目的核心设计哲学：

### 1. "混合智能"架构

```
确定性层 (Tree-sitter + 规则引擎)
    ↓ 结构化数据
概率性层 (LLM 推理)
    ↓ 报告和建议
人类层 (最终决策)
```

**哲学**：
- **机器负责规模化**：处理大量代码的模式匹配
- **AI 负责理解**：语义分析和上下文关联
- **人类负责判断**：最终的安全决策

**优势**：
- 充分发挥各层的优势
- 避免完全依赖 LLM（成本高、不稳定）
- 保持人类在循环中的控制力

### 2. "知识蒸馏"范式

**传统工具**：
```
专家 → 编写规则代码 → 编译成工具 → 运行分析
       ↑ 技术门槛高
```

**Vul-AI-V2**：
```
专家 → 编写 Markdown 文档 (SKILL.md) → LLM 理解 → 运行分析
       ↑ 技术门槛低、迭代快
```

**哲学**：
- **知识民主化**：安全专家无需懂编程，也能贡献规则
- **快速迭代**：修改 SKILL.md 即可更新检测逻辑
- **自然语言编程**：用描述性语言定义安全规则

### 3. "渐进式分析"策略

**传统工具**：
```
加载全部代码 → 一次性分析 → 输出结果
↑ O(n²) 复杂度，上下文爆炸
```

**Vul-AI-V2**：
```
阶段1: 项目画像 → 阶段2: 认证分析 → 阶段3: 路由分析 → ...
↑ O(n) 复杂度，线性扩展
```

**哲学**：
- **分而治之**：将大问题分解为小问题
- **上下文局部性**：每个阶段只关注相关代码
- **可扩展性**：新增检测维度不影响现有分析

### 4. "人在环中"设计

**完全自动化工具的问题**：
- 误报率高，需要人工审查
- 无法处理业务逻辑
- 缺乏上下文，建议不切实际

**Vul-AI-V2 的设计**：
- ✅ 产出人类可读的 Markdown 报告
- ✅ 提供修复建议和 PoC，而非直接修改代码
- ✅ 优先级系统帮助人类聚焦关键问题
- ✅ 可追溯的中间产物，便于审查和调试

**哲学**：
- **增强而非替代**：工具增强人类的分析能力，而非取代
- **透明性**：所有分析过程可见、可审计
- **协作式工作流**：工具生成发现，人类做最终判断

```python
def llm_guided_taint_analysis(source, sink):
    # 1. 使用传统方法找到可能的路径
    candidate_paths = static_taint_analysis(source, sink)

    feasible_paths = []

        判断以下数据流路径是否在真实执行中可行：
        {path}

        考虑：
        1. 条件分支的可满足性
        2. 类型转换的正确性
        3. 异常处理的影响
        """)

        if is_feasible:
            feasible_paths.append(path)

    return feasible_paths
```

```python
class VulnerabilityKnowledgeBase:
    def __init__(self):

    def learn_from_project(self, project, vulnerabilities):

    def apply_to_new_project(self, new_project):
        # 使用已知模式快速扫描
        matches = []
        for signature, pattern in self.known_patterns.items():
            if pattern.matches(new_project):
                matches.append(pattern)

        return matches
```

**优势**：

## 总结

### 🏆 核心优势

1. **创新的混合架构**：Tree-sitter (确定性) + LLM (概率性) 的完美结合
2. **知识蒸馏范式**：将专家知识编码为 Markdown，降低贡献门槛
3. **渐进式分析策略**：解决了大型代码库的上下文爆炸问题
4. **全面的安全覆盖**：涵盖 OWASP Top 10 的 80% 漏洞类型
5. **多语言支持**：支持 8+ 主流语言和 30+ 框架

### ⚠️ 核心局限

1. **静态分析的根本限制**：无法处理动态路由、运行时代码生成
2. **缺乏数据流分析**：遗漏大量 IDOR、SQL 注入等漏洞
3. **串行执行性能**：总耗时较长，不适合 CI/CD 快速反馈
4. **上下文碎片化**：跨技能的复杂漏洞可能被遗漏
5. **无法自动验证**：高误报率，需要大量人工审查

### 🎯 定位和适用场景

**最适合**：
- ✅ 中小型项目（<100K 行）的全面安全审计
- ✅ 特定框架（Express、Spring Boot、Django 等）的深度分析
- ✅ 传统安全漏洞（认证、注入、XSS 等）的快速发现
- ✅ 安全意识培训和教学（清晰的报告和 PoC）

**不适合**：
- ❌ 大型项目（>1M 行）的快速扫描（太慢）
- ❌ CI/CD 流水线（耗时长，成本高）
- ❌ 复杂业务逻辑漏洞的深度分析
- ❌ 需要高精确度的生产环境扫描（误报率较高）

### 💡 关键洞察

这个项目代表了**安全工具的新范式**：
- 从"硬编码规则"到"自然语言知识"
- 从"完全自动化"到"人机协作"
- 从"单一模型"到"混合智能"

它不是要取代 CodeQL、Semgrep 等成熟工具，而是探索了一种**更灵活、更易扩展**的安全分析方法。

**最大的贡献**：证明了 LLM 可以有效地用于代码安全分析，且通过合理的架构设计，可以在成本、准确性、覆盖面之间取得平衡。
