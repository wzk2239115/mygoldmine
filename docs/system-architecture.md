# 系统架构说明

面向开发人员。目标是把“静态审计 → 自动分类 → 动态验收 → 人工展示”做成一条可运行、可审计、可回放的流水线。

## 1. 设计目标

- 候选问题（finding）不直接推给人；先自动评分、去重和路由。
- 只有进入待验收状态的条目才需要人工阅读。
- 待验收必须同时满足：红队实际捕获随机标记（flag）、独立审核（judge）通过、图文报告已生成。
- 每条自动决策和每次验证都留下执行轨迹，供 RSI 回放和策略优化。
- 所有攻击只在隔离环境内进行，随机标记每轮重新生成，攻击者容器不能直接接触标记文件。

非目标：

- 不把“自动归档”当成“确认安全”。
- 不把 AI 插图当漏洞证据。
- 不对公网或未授权目标运行红队。

### 批量审计过程设计

批量审计阶段负责产生**可追溯的静态候选**，不直接把模型结论当作已验证漏洞。执行链如下：

| 阶段 | 设计与职责 | 关键产物/边界 |
|---|---|---|
| 选择项目并批量审计 | 看板通过 `POST /api/targets/github-branches` 读取公开仓库的分支引用，只下载当前页分支的提交对象并在页内按提交时间排序，分别标记默认分支和本页最新分支，接口每页最多返回 50 条、默认返回 10 条，分支列表与页面结果使用短时缓存；通过 `GET /api/targets/browse` 为本地目录选择器列出服务器可见子目录，再通过 `POST /api/targets/import` 导入公开 GitHub 仓库或服务器本地目录，登记 `ui/data/projects.json` 与 `targets/manifest.json` 后调用 `run.sh` 完整流程；项目清单记录项目名称、源码位置和版本。批量模式由 `parallel_mine.sh` 控制并发和失败重试，`overnight.sh` 提供后台启动、状态查看、停止和恢复；每个项目使用独立审计目录 | GitHub 仅接受公开 HTTPS 地址，分支查询通过 `tree:0` 过滤只读取提交对象，不下载目录树和源码，临时目录在结束后删除；目录浏览不读取文件内容；已有目录不强制更新，已有实时审计的项目不能重复启动。已有完整成功报告的项目默认跳过；批量运行状态与项目产物分离 |
| 持久项目沙箱 | `sandbox.sh` 为每次审计运行启动独立容器，源码只读挂载到 `/target`，批量审计和交互命令行复用 `/workspace/repo`；主流程 `verify-agent` 默认用独立断网容器 | 不挂载 Docker 套接字，启用 `cap-drop ALL` 和 `no-new-privileges`；密钥不写入沙箱状态 |
| 整理审计线索并拆分任务 | Jev 为代码块生成 0 到 1 的优先检查分数（priority）、达到阈值的风险信号（flags）和已有防护措施（mitigations）；`security-orchestrator` 再结合项目结构与攻击面拆分检查任务 | 这些信息只用于安排检查顺序，不直接生成候选问题；除模型 API 和指定初筛服务外不访问公网 |
| 增量报告 | 审计开始即创建报告骨架，每个子任务完成后增量更新；候选问题必须带文件与行号、根因、影响、复现思路和修复建议 | `raw.jsonl` 保留真实动作流，`claude.rendered.log` 供人阅读，`audit-report.md/json` 保存结论 |
| 质量与运行状态 | `check_report.py` 检查固定结构、必填字段和系统语言；`run-meta.json` 记录尝试次数、退出码、超时、中断和 `reports_complete` | 模型正常退出但报告不合格仍算失败；草稿和质量不合格报告不发布到发现记录表 |
| 总时限与恢复 | 所有尝试和重试共享总时间预算；`progress_guard.py` 按环境准备、模型调用和工具执行的真实事件判断进展；`durable_recovery.py` 校验并复用分支成果，隔离失败任务 | 已完成且校验匹配的产物不重新执行；恢复源证据不可变，恢复后继续未完成工作和第 4 阶段 |
| 发布到下游 | 完整有效报告进入发现记录表；`run.sh` 默认继续执行图文报告、第 4 阶段 `verify-agent`、第 5 阶段红队批量执行与独立审核，再编译状态和自动分类 | 静态候选问题仍需验证和红队证据才能进入下一阶段，不能跳过验证通过条件 |
| 经验与挖掘修复候选 | 第 6 阶段重建红蓝经验并生成共享或仓库专属修复候选；候选经独立前后运行评估后才发布，下一轮挖掘加载已发布规则 | 候选目录、真实评估、活动规则与版本回滚记录分离；生成候选本身不改变生产挖掘 |

`run.sh` 在单项目批量审计前执行第 0 阶段环境构建：`phase0_env.sh` 默认直接启动 `environment-builder` 智能体，由智能体检查源码、选择构建方式、调用确定性构建工具、阅读日志、修复并验收环境；智能体没有产出可用环境时才执行确定性备用方案，明确关闭智能体时只执行备用方案。报告完整性检查会拒绝明确标为运行中、草稿、部分完成或失败的报告；为兼容历史报告，缺少状态字段的报告仍按现有结构和字段检查。检查通过后依次执行 `visual_report.sh`（图文报告和场景图）、`phase4_verify_agent.sh`（真实 `verify-agent` 和隔离执行器）、`phase5_redteam.sh`（红队批量执行和独立审核）以及 `post_validation.sh`（红蓝经验和挖掘修复候选），最后重算待人工验收条件。环境构建失败、报告不完整、验证结论为 `blocked` 或红队未通过时都保留明确状态，不伪装成 `ready` 或 `confirmed`。批量审计负责找候选并保留证据，候选验证负责核实候选，隔离环境验证负责证明可利用性，三者不能互相替代。

### 正式八节点执行链与运行状态

看板首页、系统架构页和运行详情共用 `GET /api/runs/:project/:runId/pipeline`，固定展示八个节点：`environment-builder` 环境构建、`security-orchestrator` 安全审计编排、`attack-scene-director` 攻击场景设计、`verify-agent` 蓝队验证、`redteam-lab-builder` 红队场景构建、`scripts/redteam/agent.py` 红队执行、`exploit-judge` 独立审核、`mining-repair-learner` 与 `stage-skill-learner` 经验学习。接口分别读取 `<run>.meta/env-phase.json`、审计报告、`visual-summary.json`、蓝队汇总、红队汇总、挖掘修复产物和阶段技能学习产物，不把整次运行的一个总状态复制到所有节点。状态分为已完成、降级、受阻、失败、运行中、未开始和已跳过；智能体失败但最终使用备用方案得到产物时标记降级，下游未实际启动时保持未开始，不伪装成智能体完成。首页默认显示最新项目，项目筛选可切换目标；实时运行时按 5 秒轮询。六个候选处理状态的计数与这条执行链分开，不混用两种“节点”含义。

每个节点都可以打开自己的只读执行轨迹。环境、场景、蓝队和独立审核启动器统一保留 Claude Code 原生 `stream-json`；安全编排读取 `raw.jsonl`，经验学习读取 `rsi/learner.jsonl`、`rsi/stage-learning-attempts/` 和 `rsi/skillopt/`。`ui/server/agentic-traces.mjs` 按节点和具体调用索引日志，同一节点存在多次调用时要求选择具体轮次、候选或红队运行，不能混成一条会话。`scripts/ccui/import_trace.py` 复用 `import_runs.py` 的转换逻辑，把选中的流式日志导入第三方 Claude Code 会话界面；`GET /api/runs/:project/:runId/ccui?node=<节点>&trace=<调用>` 只返回只读回放，不启动新智能体。旧文本日志保留文本查看；红队执行是独立模型循环，展示 `agent.jsonl` 结构化执行轨迹，不标记为 Claude Code 会话。

### 持久沙箱生命周期

`Claude Code` 的镜像默认版本为 `2.1.318`，构建时配套 `Node.js 22`。宿主机已升级至同版，并通过现有 `DeepSeek` 兼容接口完成两个并行智能体的原生工作流（`Workflow`）调用验证。已有镜像和持久容器不会随宿主机升级；只有重建后才采用新版本。页面导入、重新审计和连续循环使用 `.claude/workflows/goldmine-pipeline.js` 控制每轮01—08；`ui/server/claude-workflows.mjs` 将每步适配到原有执行器。页面04—07重跑以同样方式接续后续节点；08独立重跑不会启动01，03仍只重跑自身。普通命令行入口保留原有调度。

第 0 阶段生成的镜像以 `mygoldmine:dev` 为基础，同时包含 Claude Code 和目标依赖。`run.sh` 默认通过 `scripts/env/sandbox.sh` 为每次审计运行创建独立持久容器；`PERSIST_SANDBOX=0` 可退回一次性容器。沙箱名称和元数据保存在 `<run>.meta/sandbox.json`，不保存模型密钥。

```bash
# 创建/查看（run.sh 默认自动创建）
bash scripts/env/sandbox.sh start --project <project> --run-dir <run> --source <source>
bash scripts/env/sandbox.sh status --project <project> --run-dir <run>

# 在同一 /workspace/repo 中继续探索
bash scripts/env/sandbox.sh exec --project <project> --run-dir <run> -- <command>
bash scripts/env/sandbox.sh shell --project <project> --run-dir <run>

# 离线验证；run.sh 在第 4 阶段前自动断开持久沙箱网络
bash scripts/env/sandbox.sh isolate --project <project> --run-dir <run>
bash run.sh --verify-only <run>

# stop 保留容器与工作副本；remove 才删除容器
bash scripts/env/sandbox.sh stop --project <project> --run-dir <run>
bash scripts/env/sandbox.sh remove --project <project> --run-dir <run>
```

批量审计使用 `/target` 的只读源码生成 `/workspace/repo`，人工命令行可继续进入这个工作副本。主流程 `phase4_verify_agent.sh` 默认让每条验证程序（harness）在独立断网容器运行；`run_verify.sh` 仍支持显式 `--sandbox` 复用已断网沙箱，但要求同一工作副本串行执行。恢复审计运行时若不能共享原运行的产物挂载，自动回退到独立执行路径；沙箱创建失败也不阻断批量审计。

### 审计运行镜像与目标环境

`docker/Dockerfile` 构建审计运行镜像，Python 依赖集中在 `runner/requirements.txt`；`runner/allowed-packages.txt` 限定自动修复可以使用的包。目标项目依赖仍由第 0 阶段 `environment-builder` 构建，不能写入运行镜像。`.claude/agents/runner-builder.md` 和 `.claude/skills/runner-image-builder/SKILL.md` 负责读取结构化失败证据，判断是否属于运行镜像；只允许在该清单范围内修改依赖并调用确定性构建脚本。

`scripts/runner/build_runner.sh` 先用临时标签构建镜像，再在断网、无特权容器中运行 `scripts/runner/smoke_runner.py`；冒烟通过后才更新正式标签。`scripts/runner/validate_requirements.py` 拒绝不在允许清单中的包、远程来源、本地路径和安装选项。06 当前在宿主机执行；批处理预检缺少执行依赖时，调用统一修复入口，先让运行修复智能体读取故障，再建立独立虚拟环境并冒烟，成功后继续本次执行。修复失败记录 `blocked_harness_dependency`、`error_scope=harness_dependency`、`retry_owner=runner-environment`、解释器和缺失模块，不启动场景构建，不把故障记为漏洞不可利用。镜像构建入口仍独立保留，不承担宿主机修复；当前自动调度不刷新目标镜像。

## 3. 核心组件

| 路径 | 职责 |
|---|---|
| `scripts/env/sandbox.sh` | 管理每次审计运行的持久沙箱生命周期、交互命令行、网络隔离与工作副本复用 |
| `scripts/runner/build_runner.sh` | 用临时标签构建审计运行镜像，执行依赖清单校验和镜像内冒烟，通过后才发布正式标签 |
| `scripts/runner/smoke_runner.py` | 检查运行镜像中的 Python 模块和命令，不执行目标项目代码 |
| `scripts/runner/validate_requirements.py` | 校验运行依赖只来自允许清单，拒绝远程源和安装选项 |
| `scripts/mine/mine_one_docker.sh` | 进入持久沙箱或启动一次性审计容器，生成原始报告并触发视觉报告与自动分类 |
| `scripts/mine/progress_guard.py` | 根据共享总时限和真实进展区分环境准备、模型调用与工具执行的停滞，并统一处理超时 |
| `scripts/mine/durable_recovery.py` | 持久化分支成果、隔离失败并恢复未完成工作，恢复后继续第 4 阶段 |
| `scripts/workflow/finding_ledger.py` | 扫描全部有效审计报告，为每次发现的候选问题保留单独编号，归并多轮审计中的同一问题，并生成历史发现记录表 |
| `scripts/workflow/build_state.py` | 基于发现记录表合并验证结果、CVE 和人工状态，重算红队证据来源链并生成待人工验收条件 |
| `scripts/workflow/refine_worker.py` | 按来源哈希重算路由，归档低价值条目，让高分条目进入下一阶段 |
| `scripts/workflow/flow_worker.py` | 处理 `triage` 和 `reproduce`：调用候选验证、补充图文报告、触发红队并写回自动流转状态 |
| `scripts/verify/run_verify.sh` | 在独立容器或已断网的持久沙箱中验证单条候选问题 |
| `scripts/verify/auto_verify.sh` | 手工静态预筛，只输出 `inconclusive` 或 `blocked`；不是主流程验证器 |
| `scripts/verify/phase4_verify_agent.sh` | 主流程第 4 阶段：调用真实 `verify-agent` 编写验证程序，再交给 `run_verify.sh` |
| `scripts/redteam/lab.py` | 创建受限的目标端与攻击端容器、内部网络、`/input` 快照和随机标记，提供 HTTP、固定命令和库调用三种执行原语 |
| `scripts/redteam/agent.py` | 通过兼容 OpenAI 接口的模型进行红队多轮交互；HTTP 模式发请求，命令行和库调用模式写 `/input` 后触发固定入口，只从真实工具输出捕获随机标记 |
| `scripts/redteam/judge.py` | 校验确定性证据来源链并独立审核；候选运行可用 `RSI_VALIDATION_TRAJECTORY` 隔离轨迹输出 |
| `scripts/redteam/batch.py` | 按候选问题构建并预检隔离环境，运行攻击端，调用独立审核；启动前检查运行镜像依赖并记录 `blocked_harness_dependency` |
| `ui/server/redteam-agent-retry.mjs` | 红队执行节点单独重跑：解析候选和场景、按候选有界并行运行 `agent.py`、隔离输出并写汇总 |
| `scripts/redteam/phase5_redteam.sh` | 主流程第 5 阶段：从当前审计运行选择候选问题，调用批量执行与独立审核，刷新待人工验收条件 |
| `scripts/rsi/post_validation.sh` | 主流程第 6 阶段：重建红蓝经验并调用 `Claude Code` 学习节点，不直接发布 |
| `.claude/agents/mining-repair-learner.md` | 组合多个技能归纳红蓝经验，输出共享或仓库专属修复 Markdown |
| `.claude/skills/verification-experience-analyzer/`、`repair-scope-analyzer/`、`mining-repair-learning/` | 分析验证证据、判断修复作用域并组织已有知识与漏洞分析技能 |
| `audit_rsi/mining_driver.py` | 让候选实际参与隔离挖掘、蓝队验证和红队审核，按真实结果发布或拒绝；批量模式自动选择留出项目 |
| `scripts/mine/repair_context.py` | 把已发布共享规则与当前项目规则注入下一次挖掘，隔离其他项目规则 |

## 4. 身份、状态与优先级

每条候选问题有两层身份：`occurrence_id=project/run_id/local_id` 精确定位一次观测，`semantic_id` 由项目、规范化证据路径、根因和 CWE 汇聚多轮审计语义。每次挖掘运行另外记录 `branch` 和 `commit`；持续监控按“项目 → 分支/commit → 运行”绑定身份，派发器使用独立工作副本固定目标提交，不移动用户当前分支。历史报告独有的候选问题不会因新审计运行而消失；运行中或质量不合格的草稿不会替代最新完整报告。旧 `project:id` 状态仅在语义唯一时兼容，存在歧义时不猜测继承。

状态优先级：

```text
state.json（人工） > curated.json（人工种子） > flow-state.json（自动流转） > refine-state.json（自动分类） > auto-state.json（自动状态编译） > inbox
```

| 状态 | 含义 | 是否给人看 |
|---|---|---|
| `inbox` | 未处理候选，尚未进入下一阶段 | 默认隐藏 |
| `triage` | 自动分类进入分诊；自动流转后台任务会调用 `verify-agent` | 流程视图 |
| `reproduce` | CVE 分级候选或验证结论为 `confirmed`；等待或已进入红队验证（尚未证明可利用） | 流程视图 |
| `cve` | CVE 去重与跟踪 | 流程视图 |
| `archived` | 可重算的低优先级归档，不是安全结论 | 默认隐藏 |
| `closed` | 人工关闭、误报、重复或已知问题 | 流程视图 |
| `review` | 可信红队、独立审核和图文检查全部通过 | 人工验收 |

## 5. 自动分类后台任务（`refine`）

输入：第 2 版固定结构的发现记录表和现有自动与人工状态。输出 `refine-state.json`、`refine-queue.json` 和 `rsi/trajectories/refine.jsonl`。

规则：

- 每条决策保存 `source_hash`；原始报告、验证结果、CVE 或人工证据变化时重新计算。
- 已归档项获得 `confirmed` 验证结论后重新进入队列并转为 `reproduce`。
- 弱指纹只标记 `duplicate_candidate`；高危和严重问题不凭弱指纹直接归档。
- CVE 分级候选或 `confirmed` 验证结论进入 `reproduce`；严重和高危问题进入 `triage`；其他低分项进入 `archived`。
- 所有决策可回放；`archived` 不删除原始报告。
- `--loop` 在空队列时等待并继续扫描，不会因暂时 `pending=0` 退出；新审计运行和新证据能持续进入经验链。

## 6. 自动流转后台任务（`flow`）

输入：最新发现记录表、`refine-state.json`、`auto-state.json` 和人工状态。输出 `flow-state.json`、`flow-queue.json` 和 `rsi/trajectories/flow.jsonl`。

规则：

- 只处理 `triage` 和 `reproduce`；人工状态高于自动流转，自动流转高于自动分类。
- `triage` 调用 `phase4_verify_agent.sh --finding-id`；`confirmed` 转为 `reproduce`，`rejected` 转为 `closed`，`blocked` 和 `inconclusive` 保持 `triage` 并记录尝试次数。
- `reproduce` 先补图文报告，再调用 `phase5_redteam.sh --finding-id`；独立审核结论为 `approved` 后调用 `build_state.py` 重算待人工验收条件。
- 每次尝试记录 `flowAttempts`、`flowOutcome`、产物路径和 `flowNextAt`；默认最多一次，避免对同一失败候选无限重试。
- 环境清单缺失、镜像不存在或 Docker 不可用时只记录 `blocked`，不伪造验证结果；设置 `FLOW_BUILD_ENV=1` 时会对已知目标调用第 0 阶段构建环境后重试。`FLOW_WORKER=1` 时随看板启动，默认关闭以避免意外消耗模型。
- CVE 跟踪仍由人工或 `docs/cve-*.json` 产物推进，自动流转不会自动创建 CVE 编号。

## 7. 动态验收隔离环境契约

每个候选问题使用独立的验证环境，由 `redteam-lab-builder` 生成到 `labs/<project>/<finding-id>/`。验证场景绑定候选问题内容哈希和源码版本；构建与结构化校验都通过后才可执行。执行器提供三种原语：

- `http`：受害端是常驻服务，攻击端通过内部网络访问目标地址。
- `cli`：受害端执行场景固定的参数数组命令，攻击者只能通过 `/input` 快照提供文件或参数。
- `library`：受害端执行场景固定的驱动程序，驱动只导入并调用目标项目的真实入口，攻击者只能通过 `/input` 快照控制输入数据。

`stdio`、`ipc`、`model` 等攻击面优先映射到 `cli` 或 `library`；不能用 HTTP 包装冒充。无法用现有原语表达时提交结构化 `blocked.json`，保留真实原因和重试条件。

不变量：

- `http` 使用 Docker 内部网络，目标端不发布宿主机端口；`cli` 和 `library` 的受害端不依赖网络
- 目标端和攻击端均启用 `cap-drop`、`no-new-privileges`，并限制进程数、内存和 CPU
- 随机标记只由验证程序以只读方式挂载到目标端的 `/flag`
- 攻击端不挂载随机标记或 Docker 套接字，场景不声明 `mounts` 或 `volumes`
- 命令和库调用场景的固定命令、驱动和真实入口由场景声明，攻击者不能向受害端直接传命令
- 攻击者输入先进入 `/input`，攻击者容器按宿主机 uid/gid 运行；执行前复制为快照并拒绝符号链接、设备文件和越界路径，符号链接只拒绝本次输入并提示智能体清理，不判场景无效
- `cli` 和 `library` 在执行攻击者输入前先运行空输入或良性输入负向对照，出现标记就中止
- 随机标记只能从真实工具输出捕获；最终回答本身不是证据
- 轨迹记录工具事件、输出 SHA-256、随机标记 SHA-256 和捕获事件
- 轨迹与智能体日志都是不可信数据，独立审核不能被其中的指令带偏

## 8. 独立审核契约

`judge.json` 使用完整固定结构，包含 `verdict`、`intended_vulnerability`、`flag_provenance`、`no_cheat`、`environment_plausible`、`reproducible`、`minimal`、`confidence`、`reason`、`concerns` 和 `recommended_status`。审核结论为 `approved` 时，全部必要布尔字段必须为 JSON `true`，且 `recommended_status` 为 `runtime-validated`。

程序在调用独立审核和接收结果时都会重算确定性证据来源链；审核同时读取场景模式、固定入口和负向对照事件，核对执行路径是否与候选一致。缺字段、字符串布尔、旧审核文件或哈希不一致均拒绝。待人工验收条件的构建还会再次验证结果中记录的证据来源链，旧“仅独立审核通过”结果不能绕过。安全验证通过后，人工验收队列仍要求图文报告和场景图；视觉素材本身不是漏洞证据。

## 9. 图文报告

`project-cartographer` 生成：

- `visual-model.json`：结构、覆盖、攻击树和攻击者与受害者场景
- 结构和覆盖信息：文字、表格及结构化数据，不绘制 SVG
- 双方步骤：文字和表格，模型插图仅用于解释
- `scene-*.webp`：image2 叙事插图
- `report-illustrated.md`：供人工验收的图文报告

插图必须标注“AI 插图，非漏洞证据”。视觉素材不能替代轨迹和独立审核。

## 10. RSI 学习流程

系统现有三条相互独立的学习支路：验证资源学习、红队验证程序改进和挖掘修复。验证资源学习仍是**只读建议模式**（`shadow`），不会改变生产状态；挖掘修复则可以经过真实前后运行评估后发布到共享技能或当前项目规则，并由下一轮挖掘实际加载。三条支路不能互相冒充：只读验证策略不会因为挖掘修复发布功能存在就自动上线，验证程序候选也仍不直接修改执行器。

真实运行会留下动作前上下文、动作、结果、成本和证据来源链；策略学习验证动作的收益，独立留出验证集与非回归检查决定候选能否进入发布复核。系统不会让模型直接改写自己，也不会把最终报告回放包装成在线发现能力。

当前验证资源的只读建议模式已跑通，但训练支持 91 条全部为静态证据（`static`），可用于动作训练的可信样本（`trusted`）为 0；回放状态为 `insufficient`，没有前后结果变化（`flips`）产物。因此验证动作策略仍停留在只读建议，不发布为生产策略。

架构页按以下六步展示经验与挖掘修复的关系：

```text
01 真实轨迹（verification / redteam 经验）
  → 02 标签与证据等级（runtime / judge / manual；static 不冒充 trusted）
  → 03 成本与收益评估（固定五动作词表做 ridge utility regression；当前仅 deep_read 25 条、defer 66 条有样本）
  → 04 跨项目验证与前后结果对比（留出验证、同动作回放、真实挖掘结果对照）
  → 05 只读建议（recommendation_only=true，state_change=none）
  → 06 挖掘修复发布（独立支路：共享或仓库专属规则，经真实前后运行评估后发布）
  └──────────────── 发布后的新真实结果回到 01
```

第 06 步不是只读验证策略的自动升级，而是 `audit_rsi/mining_repair.py` 提供的独立挖掘修复链路。`trusted_support=0` 时验证动作仍以 `static-only / no_trusted_utility_targets` 继续生成只读建议；挖掘修复若只有静态证据，也只能保持候选状态。回放只描述同动作的实际收益，真实前后运行对照只描述观测变化，两者都不宣称因果评估。

红队验证程序形成第二条学习支路，与验证动作成本与收益评估分开：

```text
红队真实运行与步骤轨迹
  → 按固定规则找出反复出现的执行失败（按失败原因等分组，统计出现次数、成本和候选修改位置）
  → 白名单内的验证程序提案（稳定 candidate_id，mutation=none）
  → 独立比较配对项的前后结果变化，再进行候选与发布复核
  → 受控变更后的新红队轨迹
```

这条支路只生成候选证据与提案，不自动修改验证程序；`validated` 也不等于已经发布。

`audit_rsi/adapters/raw_trace.py` 另行把真实 Claude `stream-json` 转为动作轨迹，保留 `Task` 和 `Agent` 父子拓扑、实际结果和成本；历史动作被选中的概率（propensity）未知时保持 `null`。最终报告重建树只用于旧回放，不能证明未探索分支的发现效果。

常用命令：

```bash
python3 -m audit_rsi experience-build --runs runs --output rsi/verification-experience.jsonl
python3 -m audit_rsi label-sample --pool rsi/verification-experience.jsonl --output rsi/verification-label-sample.jsonl --limit 100
python3 -m audit_rsi label-plan --pool rsi/verification-experience.jsonl --output rsi/verification-label-plan.jsonl --report rsi/verification-label-plan.json --limit 100
# 人工填写 verdict/evidence_class 后合并，再训练和生成只读建议
python3 -m audit_rsi label-merge --pool rsi/verification-experience.jsonl --labels rsi/verification-label-sample.jsonl --output rsi/verification-experience-labeled.jsonl
python3 -m audit_rsi verify-train --pool rsi/verification-experience-labeled.jsonl --output rsi/verification-policy.json --holdout-project <project>
python3 -m audit_rsi verify-shadow --pool rsi/verification-experience-labeled.jsonl --train rsi/verification-policy.json --output ui/data/verification-shadow.json
python3 -m audit_rsi verify-replay --pool rsi/verification-experience-labeled.jsonl --train rsi/verification-policy.json --holdout-project <project> --output rsi/verification-replay.json
python3 -m audit_rsi verify-flips --baseline <baseline.jsonl> --candidate <candidate.jsonl> --holdout-project <project> --output rsi/verification-flips.json
python3 -m audit_rsi redteam-experience --runs runs/redteam --output rsi/redteam-experience.jsonl --steps-output rsi/redteam-steps.jsonl
python3 -m audit_rsi redteam-weakness --runs runs/redteam --output rsi/redteam-weakness.json
python3 -m audit_rsi harness-propose --weakness rsi/redteam-weakness.json --output rsi/harness-candidates.json --limit 3
python3 -m audit_rsi harness-validate --candidate <candidate.json> --flips rsi/verification-flips.json --output rsi/harness-validated.json
```

未知结论不等于误报；缺少合法标注倾向、留出验证集、标签覆盖或支持度时，只输出 `insufficient` 或只读建议，不发布为生产策略。回放只报告相同动作实际获得的收益，不宣称因果提升。`verify-flips` 按同一问题编号（semantic）比较两个真实经验池的 F→P 和 P→F、稳定项、配对覆盖与未知结论转移，用于观测非回归，不把不同审计运行的结果解释成反事实或因果效果。候选进入下一阶段的默认通过条件为 `paired_coverage>=0.8`、至少一个 F→P 且零 P→F；覆盖不足时为 `insufficient`，有修复但出现回归时为 `rejected`，满足条件才为 `accepted`。`mutation=none`，`accepted` 仍需候选复核和既有发布检查。版本发布复核统计各项检查结果，失败候选仍可查询和回滚。

`redteam-experience` 将审计运行级结果与攻击端步骤级工具事件分开：记录角色、动作、成本、返回码、输出哈希、失败分类和证据等级，不复制原始攻击命令、输出正文或随机标记。只有确定性证据来源链可重算的捕获才自动成为运行时标签；独立审核结论为 `approved` 时还要求审核状态与重算结果一致。`not_captured`、篡改轨迹和未复核结果保持未知，不成为误报或可信奖励。

`redteam-weakness` 按固定规则归类这些轨迹中的重复失败：以项目类型、攻击模型、失败原因、严重度和候选修改位置作为分组条件，分别输出包含该类失败的运行次数（`support`）、失败事件次数（`event_support`）、平均模型调用次数和平均耗时。模型超时（`model_timeout`）、隔离环境异常（`lab_unhealthy`）、未捕获（`not_captured`）、工具失败和结构化输出失败对应不同的执行器修改位置。该产物只供后续评估（`candidate_only`），不修改执行器（`mutation=none`）；任何候选修改仍须通过独立回放与回归检查。

`harness-propose` 只允许修改白名单允许的范围，为每个提案生成稳定 `candidate_id`、目标失败、证据哈希、保留行为和验证要求；不会直接修改验证程序。`harness-validate` 重算提案身份并检查前后结果变化，只有 `accepted` 才标记为 `validated`，身份篡改、回归或证据不足均不能通过。候选提案和验证结果都可审计、可回放，仍需后续发布复核。

经验构建同时读取 `verdict.json`、`verify-report.json` 和 `auto-state.json`：自动路由提供 `deterministic-auto-state` 动作及倾向，候选验证提供静态或运行时结果，不能把有结果但无动作的样本静默丢弃。运行时验证与人工整理记录可自动获得确定标签来源；静态验证只进入只读建议的学习；独立审核仍需独立标签复核，不自动获得标签选择概率。

`label-plan` 在普通分层抽样之外优先补齐完全缺少可信样本的项目和动作，再考虑补充覆盖；无动作记录不进入人工标注队列。每个任务保留单次观测与同一问题编号、抽样原因、分层配额和标签选择概率，并过滤敏感上下文。该计划只提高标注效率，不把未知结论自动变成可信样本。

智能体可以辅助做源码级静态标注，但必须使用 `evidence_class=static` 和 `adjudication.method=agent-static`，不能冒充人工、运行时或独立审核证据。只有静态标签时只读建议明确为 `static-only / no_trusted_utility_targets`，即使训练产生了不同建议，也不得视为已验证提升或生产候选。

### 挖掘修复学习（已接入，候选默认不发布）

`run.sh` 在第 4 阶段蓝队验证和第 5 阶段红队审核后执行第 6 阶段 `scripts/rsi/post_validation.sh`，先重建红蓝经验并形成带证据的种子，再由 `Claude Code` 启动 `mining-repair-learner`。学习节点使用 `verification-experience-analyzer`、`repair-scope-analyzer`、`mining-repair-learning`，并按候选根因调用证据优先、可达性、误报模式、项目知识和现有漏洞分析技能，将修复写到 `rsi/mining-repairs/agentic/*.md`。随后主流程自动调用 `mining-repair-drive`：把候选 `Markdown` 写入独立上下文，在 `rsi/mining-repairs/attempt-runs/` 重新执行挖掘、报告完整性检查、蓝队验证和红队审核，再用这次真实候选运行评估发布或拒绝。`--skip-mining-repair` 可跳过整个学习阶段；`--mine-only` 也会跳过。候选重跑不进入正式 `runs/`，候选红队轨迹通过 `RSI_VALIDATION_TRAJECTORY` 写入独立评估目录，不污染正式经验。批量 `parallel_mine.sh` 在项目结束后执行同一智能体学习阶段，并自动从未参与来源训练的项目中选择留出项目重跑共享候选；`--skip-mining-repair` 可关闭。无需人工执行离线命令才能完成学习。

修复分两种作用域：

- 共享修复写入 `.claude/skills/rsi-shared-experience/rules/`，至少需要两个具有可信证据的来源项目，并必须在与来源项目隔离的留出项目上通过真实前后运行评估。
- 仓库专属修复写入 `knowledge/project-rules/<project>/`，只评估并加载对应项目，不能进入其他项目的提示词或智能体加载清单。
- 可信证据只包括实际运行、独立审核和人工结论；静态证据可以生成候选，但发布检查会以 `no_trusted_source_evidence` 拒绝。

`mining-repair-drive` 使用正式运行作为修复前基线，并把候选实际参与的新运行作为修复后结果。误报修复必须至少抑制一个既有误报、降低误报率、保留全部基线正确结论且没有新增误报；已确认调查模式必须带来至少一个新的正确结论，同时满足相同的非回归条件。未知结论不当作误报，候选消失只对既有误报计为抑制，对既有正确结论计为丢失。`mining-repair-cycle` 仍可比较外部提供的经验集合，但只是离线调试入口，不是主流程的替代品，也不单独证明候选规则导致了结果变化。

发布时重算候选身份、内容哈希和评估身份，在 `rsi/mining-repairs/versions/` 保存本次内容、前一内容和清单元数据。已发布共享规则由 `scripts/mine/repair_context.py` 与项目规则一起注入下一次挖掘；超过提示词预算时保留索引并要求智能体按需读取。容器通过只读挂载获得 `audit_rsi`、共享技能和项目知识。回滚只允许针对当前最新活动版本，防止覆盖后续修复。

## 14. 架构说明维护

根目录 `AGENTS.md` 定义了同步契约。模块、数据流、候选问题身份、状态通过条件、API、恢复机制、安全边界或 RSI 发布关系变化时，同一轮修改必须核对本文和 `ui/src/components/ArchitectureView.jsx`；用户入口变化还要核对 README。局部且不改变行为的修复不需要机械更新，但不能保留已知过时描述。

架构页是面向使用者的三级实现摘要：第一级用整体漫画地图展示批量审计、自动分类与验证、红队与验收、核心组件、RSI 学习流程五个区域；第二级展示中层阶段和组件，其中 RSI 区域区分验证资源只读建议、红队验证程序候选和可发布的挖掘修复，展示共享与仓库专属作用域、真实前后运行评估、下一轮加载和回滚；第三级才展示输入输出、执行规则、对应脚本与输出文件、失败时如何处理和优化检查点。漫画由 360 平台的 `bytedance/doubao-seedream-5.0-pro` 生成，仅用于叙事，不代替准确的节点关系或安全证据。本文是面向开发人员的完整契约，两者都不能把计划、静态标签、只读建议或未评估候选描述成已验证、已发布的生产能力。修改模块职责或契约时，也要同步对应中层节点和实现详情，不能只改视觉或标题。

### 项目导入进度

导入弹窗通过 `POST /api/targets/import-stream` 接收逐行 JSON 状态事件，在提交按钮下方显示排队、源码准备、版本登记、审计启动和命令输出，以及等待时间。失败信息保留在弹窗内。原有 `POST /api/targets/import` 接口保持可用；点击取消或关闭导入连接会停止排队、下载或启动过程；本次新建源码目录会清理，已有目录和本地源码保留。已登记的项目恢复导入前记录，已启动的审计调用停止命令，运行产物保留供排查。取消后可重试，新请求会等待清理完成。此状态仅表示导入与启动过程，不表示完整审计已完成。

### 按提交版本导入

公开仓库导入使用 `POST /api/targets/github-commits` 直接读取提交历史，每页 10 条，显示短提交编号、时间与说明，默认选最新提交，支持加载更多。读取列表不下载源码，相同页短暂缓存并合并并发请求。导入按完整提交编号浅下载、检出并核对版本。

已有有效提交只有与所选版本相同才复用；不同版本须换项目标识。仅含 `.git`、来源匹配且没有有效提交的未完成目录，以及空目录，会移动到 `backups/incomplete-imports` 后重试。其他已有内容不会自动移动。下载失败、超时或取消会清理本次新建且尚未登记的目录。

下载耗时显示为实际已用时间，不是倒计时。仓库下载不设固定总时长上限；每次收到下载命令标准输出或错误输出都重置空闲计时，连续 3 分钟无输出才停止并允许重试。列表请求和启动审计仍保留各自超时。

看板扫描同时识别主运行目录和带有 `status.json` 的相邻 `.meta` 状态目录。启动早期只有状态目录时，项目也会显示在侧栏；两种目录同时存在时只统计一次，不把 `.meta` 当作独立运行。

节点轨迹转换为 Claude 会话后，使用 `scripts/ccui/index_trace.mjs` 同步登记到会话数据库，再返回对应会话地址。转换缓存与数据库登记分开处理，登记失败显示错误，不进入项目选择空页。环境构建的交付状态与能力范围分开展示：智能体正常交付可用沙箱时显示已完成；部分可用环境同时注明能力受限，轨迹面板可展开具体限制。使用备用方案、必要验收未通过或交付未确认时仍显示降级，无可用环境时显示受阻。底层环境状态与下游能力约束保留。轨迹面板提供消息数量、同步和新窗口入口。

### 沙箱源码准备与复用

沙箱创建操作按运行目录加锁，容器启动后同步复制源码，复制成功才写入工作副本就绪标记并返回。持久沙箱中的审计入口检查就绪标记后直接复用工作副本，不再清空或二次复制；停止后再次启动保留已有修改。复制失败不发布就绪状态，并停止新建容器。旧版或未准备完成的沙箱缺少标记时拒绝启动审计，需用新的运行目录重建，原工作副本保留。独立临时容器仍由入口准备源码，清理失败会直接报错。

安全审计节点在没有主会话或主会话为空时，展示本次运行的启动日志（相邻状态目录中的 wrapper.log）。复制源码失败会标明审计智能体未启动；生成主会话后优先展示真实会话。历史运行日志保持原始结果，不因代码修复改成成功。

### 删除项目

侧栏项目右侧提供删除按钮。确认后删除项目登记、发现记录与对应运行目录，不提供撤销或恢复接口；源码目录保留。项目仍在运行时禁止删除。删除使用 `DELETE /api/targets/:project`，后续重新导入是新建审计，不恢复旧记录。

### 串行阶段状态

监督脚本按实际调用顺序记录 `pipeline-stage.json`：环境准备、安全审计、攻击场景、蓝队验证、红队处理、经验学习。红队批处理在调用场景构建、执行、独立审核前更新当前节点与候选编号；不同候选会依次重复这些步骤。看板只将当前节点显示为运行中，尚未到达的节点显示等待，不使用整次任务存活状态推断每个节点运行，也不将初始占位值当成已跳过。旧运行缺少阶段文件时按已有阶段日志和产物兼容推断。完成、降级等最终结果仍以真实产物为准。

中断记录按最后执行阶段展示：该阶段保留已有结果，未完成时标注已中断；后续没有执行记录的阶段标注未执行。旧记录结合环境日志识别中断位置，不把启动前中断误报为安全审计失败。

项目侧边栏提供“重新审计”：通过 `POST /api/targets/:project/restart` 读取已登记的源码目录，调用完整审计主流程并创建新的运行目录，保留历史记录。源码不重新下载，项目正在运行时拒绝重复启动；重新审计与导入共用串行启动队列。启动后自动选择该项目并刷新看板。

项目没有显式图标配置时，优先使用本地同名项目图片 `ui/public/logos/<项目标识>.png`；没有图片时才显示默认图标。删除后重新导入也会恢复已有图片。

打开执行轨迹时，看板先检查轨迹服务；默认本机回环服务未运行时自动启动，并合并并发启动请求。启动日志写入 `runs/ccui-home/service.log`，只恢复查看服务，不重新启动审计智能体。自定义远程服务不由看板启动。

“设置 → 配置模型”可分别设置安全审计、蓝队验证、红队验证、环境构建、攻击场景设计与独立审核模型。配置经校验后保存至 `config/stage-models.json`；可选阶段留空时跟随审计模型。候选列表只读取已有模型名称，不返回服务密钥。新导入和重新审计在启动时将配置传入主脚本并固定为本次任务的模型参数；已有任务不受影响。运行状态通过 `stage_models` 保存本次各阶段模型。命令行的场景与审核模型在参数解析完成后计算，避免选项未生效。模型名称必须在对应的既有服务中可用，此入口不配置服务地址或密钥。

新启动任务的默认安全审计时限为 24 小时（86400 秒），各启动入口保持一致；看板从本次运行记录读取实际时限，不使用固定的显示值。已启动任务保留启动时传入的时限，配置修改不伪装为已延长历史任务。环境构建和验证阶段仍使用各自时限。

红队模型默认跟随安全审计模型，设置中留空即可跟随；不再默认使用 flint。红队按模型的服务前缀读取已有服务地址与鉴权配置，并去除服务前缀后发送请求；缺少配置时明确失败，不回退到旧模型服务。密钥不会写入看板配置或运行结果。


### 环境构建指令约束

环境构建技能与智能体定义以本次验收目标决定依赖范围，默认先满足轻量审计需要；导入、CPU 测试与 GPU 训练分别验收，不默认安装全部开发或训练依赖。指令要求先做平台和下载源预检、按实际日志检查进展、修正原因后重试，并保留失败方案及真实限制。

这轮调整仅更新 Markdown 指令，不改变现有智能体超时、Docker 构建超时、备用流程、缓存实现或页面进度展示。已有 Dockerfile 仍可能被备用流程复用；指令要求智能体在预算内明确处理并如实报告，不表示脚本已经提供自动降级或独立构建管理。新启动的环境构建智能体加载新指令，正在执行的会话不会自动重新加载。

环境构建指令进一步区分预检与安装：预检只读取必要元数据，安装验证必须进入正式 Docker 构建；禁止在临时容器内安装依赖。先验证最小方案，再按指定验收路径补齐依赖；持续版本回溯须先诊断约束。检查保留原命令退出码，避免管道筛选掩盖超时。这些是智能体指令要求，未新增脚本级强制检查。

环境构建指令默认优先交付满足当前审计需要的沙箱，达到明确的最小要求后停止扩建；允许带真实限制的部分可用结果，不以完整部署、全部测试通过或就绪标签作为默认目标。必要能力及既有隔离边界仍须验证，不因追求快速交付而放宽。该要求属于技能指令，不改变脚本的状态判定。

环境构建技能选择性参考 Docker 的构建分层与缓存指导、Repo2Run 的具体验收标准和 SetupX 的有证据修复经验。指令要求按平台与版本核对历史经验，在本次输出目录保留构建说明，并保留已验证方案；未接入外部框架、数据库或自动快照回退，仍以够用的审计沙箱为默认目标。来源链接记录在技能文件中。

执行轨迹的会话索引缓存统一写入相邻的 `<运行目录>.meta/ccui-session.json` 或 `.meta/ccui-sessions/`，包括批量导入入口；查看环境轨迹不会创建或占用尚未启动的审计输出目录。旧缓存可由原始轨迹重新生成，历史审计结果不改写。输出目录非空时拒绝覆盖的检查保持不变。

环境构建指令要求优先核对已有镜像的源码对应关系、平台与实际镜像编号，通过必要断网验收后直接复用。仅修正清单、补充验收记录或修复辅助脚本不触发重建；保留原始构建时间并另记本次验收时间。只有构建输入不匹配、镜像不可用或指定验收被具体缺失项阻塞时才构建。此项属于智能体指令，未新增脚本级自动复用机制，新启动的环境构建会话生效。

攻击场景设计仍由智能体按技能执行。启动器在调用 Claude 命令行前去除模型的服务前缀，配置兼容服务地址、鉴权和子智能体模型；显式连接配置优先，未设置时沿用环境构建阶段的 360 服务及已有凭据。启动时仅加载项目及本地项目设置，排除用户级设置中的其他模型服务。凭据只传入子进程环境，不写入任务或轨迹。

审计编排退出前对实际运行目录的报告执行既有质量检查，反馈缺失字段供智能体修正；原有退出检查次数上限和最终报告质量门槛保留。恢复报告标记为 `coverage.analysis_mode=assembly-only` 时，轨迹入口明确显示恢复汇总；约定的同项目 `-recovery` 运行还关联原始完整审计，两个会话分别缓存。恢复成功只代表汇总流程完成，不代表重新扫描或漏洞验证通过。

节点轨迹抽屉提供“重新运行此节点”。当前支持攻击场景设计、蓝队验证、红队场景构建、红队执行、独立审核和经验学习：复用选定运行的报告，使用设置中的当前阶段模型，将报告快照、新日志与产物保存到 `<run>.meta/node-retries/<node>/<id>/`。前置产物缺失或项目仍在运行时拒绝启动；同项目节点重跑互斥，项目重跑也检查该锁。界面显示最新节点状态及历史轨迹；仅更新该节点展示，不自动执行后续阶段，也不覆盖原始报告、验证结论或历史成功状态。其他节点尚不支持独立重跑，显示不可用说明与项目重新审计入口提示，不显示看似可用的重跑按钮。


### 结构化阶段交付

新增 `scripts/stages/submission.py`，通过 MCP 函数 `submit_stage_result` 接收实际产物路径、简短说明和限制。审计、环境构建、场景设计、蓝队验证、红队场景构建、独立审核及经验学习的 Claude 启动入口加载此工具；红队独立模型循环提供同名结构化动作。工作流在节点结束时会重新核对回执、产物路径和内容摘要；回执缺失或验收后产物改变时停止下游交接。交付格式通过与节点业务成功状态分开记录，回执通过不替代漏洞验证结论。智能体可多次提交，返回 `needs_revision` 和具体缺失项，修正后再次提交；通过后返回 `accepted`、产物 SHA-256 和检查范围，每次记录独立保存于指定输出目录的 `.stage-submissions/<stage>/`。红队场景构建阶段接受场景 JSON，也接受结构化的 `blocked.json`；受阻交付只校验原因和证据结构，不代表动态验证通过。

当前检查范围明确为 `artifact_contract`：复用报告质量检查、场景格式检查、审核结论格式检查；环境额外核对实际 Docker 镜像编号和已声明验收记录，场景设计检查设计文件与同名图片。其余交付检查文件结构及状态。提交成功不等于漏洞验证通过，不以模型自述替代执行证据；原有动态验收、来源绑定、随机标记核验、阶段脚本检查和人工验收仍须通过。这一轮不把收据自动升级为整条流程成功，历史任务没有收据时也不伪造补写。工具使用受限输出目录，拒绝越界路径和符号链接越界。已接入输出位置的交付记录可在节点轨迹选择器查看。

恢复汇总中没有重新执行环境构建时，环境节点关联同项目原始运行中的环境构建会话，并标为“原始运行”，不再误报暂无轨迹；若恢复运行确实启动过新构建，则展示本次记录。


阶段技能改进现支持八阶段分别提炼通用与仓库专属规则，按版本加载并记录本轮快照；候选经独立前后对照评估后才发布，支持回退。第 08 阶段先综合前面阶段的反馈和产物选择目标，需要重写时通过 `request_skillopt_optimization` 提交请求，由 `scripts/stages/learn_round.py` 调用本地 SkillOpt 核心入口 `skillopt.optimizer.rewrite.rewrite_skill_from_suggestions`，再由 `scripts/stages/skillopt_adapter.py` 转换为 `SkillBank` 候选。SkillOpt 版本和提交记录在 `third_party/SkillOpt.pin.json`；未启用 SkillOpt-Sleep、WebUI、插件或自动采用。终态与单节点重跑采集各阶段反馈，保留缺失、受阻和不确定状态。连续迭代使用有轮数和无改善停止条件的命令行控制器，默认不自动启动；没有可信评估套件时只积累候选。详见 [阶段技能改进说明](stage-skill-evolution.md)。


### 验证阶段的模型连接与报告传递

蓝队、攻击场景、红队场景构建和独立审核共用 `scripts/stages/claude_connection.py`，统一模型前缀、服务地址和鉴权；Claude 命令只读取项目及本地项目设置，避免个人设置将模型切换到其他服务。红队批处理通过 `--report` 校验本轮报告、绑定项目与运行编号并记录内容摘要，不依赖仅包含已结束运行的发现记录表；未指定报告的离线入口仍按指定历史发现解析。蓝队与红队的全部受阻、部分受阻分别记录为 `blocked`、`partial`，主流程汇总为降级，看板依据实际结果展示，不能仅凭汇总文件存在就显示完成。历史运行产物保持原样。


环境构建阶段将平台、验收记录和能力限制保存到本次 `env-phase.json` 的 `final.capabilities`，历史展示优先读取该快照。旧记录仅在共享清单仍绑定同一项目、源码路径和镜像，且验收时间不晚于本次阶段结束时读取其说明；条件不符时只显示已有阶段记录的能力范围，不套用后来的环境说明。


轨迹面板按项目、运行、节点及具体调用缓存最近会话信息（最多 24 条、30 秒），鼠标移入或键盘聚焦节点时提前准备，并合并同一次准备请求。源日志版本变化、缓存过期或点击“同步会话”时重新读取；运行中的会话仍按原周期检查更新，更新日志时保留已有会话页面。首次准备期间可直接选择“查看原始记录”，并可返回会话视图。后台并行进行轨迹导入与服务准备，复用短期健康检查；新转换结果按源文件路径、大小和纳秒修改时间判断缓存是否有效，不依赖导入时间与源日志时间比较。


蓝队验证在阶段内部按候选并行执行，默认并发上限为 10；命令行 `phase4_verify_agent.sh --jobs N` 可设置 1–10，`--max` 仍控制选取总数。主流程等待全部候选结束后再进入红队阶段。每条候选使用独立进程组、隔离执行目录、报告和日志；调度器原子写入 `verify/agent/tasks/<候选编号>.json`，各任务分别写 `verify/agent/<候选编号>/result.json`，父进程按原报告顺序生成总汇，多个任务不同时追加同一结果文件。取消时终止活动任务进程组，未启动任务记录已中断。

蓝队轨迹面板显示各候选的排队、运行、确认、排除或受阻状态，点击候选只打开其对应轨迹，“查看报告”读取该候选的独立报告。节点重跑使用稳定的候选编号关联轨迹，不因新增其他日志改变编号；报告接口校验运行、候选与重跑批次，不读取模型提供的任意路径。旧串行批次单独标注，不把正在执行的旧任务强行改为并发。

蓝队包装器启动后执行脚本快照，后续发布不改变运行中批次的汇总代码。汇总异常的历史批次可在校验逐候选报告后恢复汇总；保留原退出码与恢复凭据，界面明确标注仅恢复汇总，候选没有重新执行。

蓝队节点显示本批次候选数量和确认、排除、待定、受阻计数，部分候选受阻时显示“部分受阻”，保留底层降级状态。执行记录数量单独放在“日志与历史记录”中，包含智能体会话、执行器日志和批次日志，不作为候选数量。抽屉显示本批次选中数、原审计报告候选总数及逐条受阻原因；单节点重跑的结果统计读取最新重跑产物，不混用原流程旧汇总。

红队场景构建的独立重跑由 `ui/server/node-retries.mjs` 和 `ui/server/redteam-lab-retry.mjs` 调度，读取本轮审计报告快照与原红队候选清单；清单缺失时从严重和高危中选择蓝队已确认且产物完整的候选，最多 5 条。候选必须属于当前项目和运行，源码目录必须可用；调用现有场景构建智能体及其技能，使用当前红队模型。每条候选的输入、场景、构建日志和交付检查写入本次重跑的 `output/redteam/inputs/` 与 `output/redteam/labs/<id>/`，实时汇总写入 `output/redteam/summary.json`。不覆盖共享场景目录；场景构建完成后由无人值守调度另建06任务，按证据继续审核和学习；场景仍按原有源码与候选哈希、支持的攻击面和隔离条件校验，受阻不会冒充可用。关闭轨迹后刷新节点状态，独立重跑期间继续自动轮询，完成后采集对应阶段技能反馈。

红队执行的独立重跑由 `ui/server/redteam-agent-retry.mjs` 调度，从最新场景构建重跑、主流程红队汇总或共享场景目录解析候选，只执行同时具备候选文件和可用场景的条目。每个候选使用当前红队模型和独立运行根目录，输出写入本次重跑的 `output/redteam/agent-runs/`，逐候选状态与汇总写入 `output/redteam/tasks/` 和 `output/redteam/summary.json`；默认最多 10 条并行。节点重跑不自动启动独立审核，也不覆盖原始红队结果。

完整项目流程与红队构建重跑共用 `scripts/redteam/blue_handoff.py`：只接收同一项目、同一轮报告的最新已结束蓝队批次，最新批次运行中或失败时不回退旧结果。候选须有真实运行确认、匹配当前镜像编号的报告、与本轮候选内容一致的输入、验证脚本和全部引用证据。未确认、静态确认、产物缺失或版本不符的候选不启动构建，原因写入 `redteam/selection.json` 的 `excluded` 并在队员列表展示；全部不满足时记录受阻，不标为已完成。

每次构建将通过检查的文件及内容摘要保存到本批次 `redteam/blue-handoff/<id>/`；构建者再复制到自身场景目录 `blue-verification/`，通过 `lab-task.json` 的 `blue_handoff` 读取。交付快照绑定报告、候选和源码版本，构建前复核摘要，防止误用其他批次或改动后的文件。蓝队材料仅供场景构建者核对真实入口与对照，不传给红队攻击执行者；后者仍只读取原始候选与必要场景信息，独立获取新随机标记。未指定 `--report` 的离线历史发现入口保留原行为，不表示已通过本轮蓝队检查。

红队场景构建在候选之间并发，独立重跑和完整项目流程均默认最多 10 条同时构建；并发上限与候选选取总数分开，继续使用本轮选定候选。完整流程的 `batch.py --build-jobs 1..10` 可调整构建并发，全部构建结束后按候选并行执行红队；`--agent-jobs 1..10` 和 `--judge-jobs 1..10` 分别控制红队执行与独立审核并发，默认均为 10。新场景和日志写入本批次的 `redteam/batch/construction/labs/<project>/<id>/`，任务进度原子保存到 `construction/tasks/`，不会并发覆盖共享场景；已有场景仍按原规则校验后复用。独立重跑使用各自的 `output/redteam/labs/<id>/` 和 `output/redteam/tasks/`。界面显示每条候选的排队、构建中、可用、受阻和独立轨迹入口，交付接口绑定当前运行与重跑批次，只读取约定目录下的场景、报告和受阻说明。旧串行批次保持原执行方式并单独标注，新批次使用并发。

蓝队验证与红队场景构建采用“队员列表 → 个人轨迹”两层界面。打开节点时只显示队员卡片及运行中、待运行、已结束计数，不默认选择队员、不加载个人会话。点击队员卡片或“查看轨迹”进入该队员的完整执行轨迹，固定显示编号、标题和状态；“返回队员列表”关闭个人会话。查看交付或验证报告是独立操作，不打开个人轨迹。待运行或尚无日志时只显示该队员自己的等待状态；自动刷新保留已选队员，切换新批次返回列表。历史执行记录通过单独入口选择并明确标注。

蓝队验证智能体启动后读取 `.claude/skills/blue-team-verifier/SKILL.md`，按单条候选最小真实入口、先写指定目录脚本、正负对照与运行证据收敛；verl 的版本相关定位放在技能引用中。仅有源码语义不得写动态确认。红队构建智能体直接读取自身技能，先检查任务支持的真实攻击面；不支持时交付受阻说明并停止，不搜索其他批次或伪造 HTTP 包装。两阶段均区分可修复的交付错误与重复的工具契约错误，经验候选只引用本任务输出证据。

红队执行器已支持 `http`、`cli` 和 `library` 三种原语。场景构建器把库调用、命令行和模型文件加载映射到固定命令或固定驱动入口，攻击者只能写 `/input` 快照；受阻时提交结构化 `blocked.json`，阶段验收读取真实原因并传到批次汇总。场景是否动态可用仍以实际负向对照、红队标记捕获和独立审核为准，技能或受阻交付通过不表示漏洞已复现。

红队执行节点按本批次候选展示队员列表，点击队员查看其个人结构化执行轨迹，并可返回列表。待运行或尚无轨迹的候选显示自身等待状态，不借用其他候选或历史批次的轨迹；批次日志和历史记录仍可单独选择。

安全审计编排在项目画像后增加覆盖与假设驱动流程：`audit-coverage-planner` 写入 `.workspace/findings/coverage-ledger.json`，记录入口、危险操作、信任边界、检查视角、待验证假设、已有证据、缺失证据、历史尝试、下一步动作、技能版本、结论和限制；状态分为尚未检查、已分析但未确认、待补证据、执行受阻、已有反证和运行确认。高风险或待补证据条目交给 `audit-hypothesis-tracer`，合并与严重度校准仍由 `hypothesis-critic` 完成。首轮完成后由 `audit-review-planner` 根据新源码、调用方、视角、假设、技能版本或验证条件安排复审；没有新条件时只允许预算内随机复查。覆盖记录、复审计划和假设文件随 `.workspace/findings/` 复制到运行的 `task-artifacts/`，并作为 `orchestrator` 阶段反馈证据进入既有技能候选和独立评估。`.claude/hooks/coverage-ledger-guard.py` 在写入覆盖记录时校验必要字段，在会话结束时有界提示并保存 `coverage-progress.md`，在压缩前保存同一份恢复摘要；它不是漏洞语义判断，也不会无限阻止结束。

### 原生节点工作流的交付检查

协调会话仅获准调用已登记的节点命令，由保存的脚本控制顺序。每次调度在 `<运行目录>.meta/workflows/<编号>/state.json` 保存节点回执、输入产物引用、完整输出清单和文件摘要，原生会话写入同目录 `raw.jsonl`。产物清单递归登记全部普通文件，不使用界面展示条数限制；符号链接、缺失、摘要改变、乱序与并发调用均拒绝继续。节点重复调用读取已提交回执，不重复审计。每个阶段的已有启动器、候选筛选条件、环境修复和独立隔离检查保持有效。

协调脚本读取的结构化状态受枚举约束；宿主机最终还要检查全部磁盘回执和真实原生工具调用，不能接受模型的完成声明。每次协调调用登记当前节点后可以返回等待；宿主机确认该任务交付完成后，才协调剩余节点。只有未登记任何任务的协调调用异常时，才最多重试一次；已登记任务不因此重启。执行器异常停止后续节点，保留错误及已有产物；仍有未确认结束的节点时保留项目锁，避免另起相同任务。当前不自动重启未确认结束的进程。

没有合格蓝队结论、没有可用场景或没有来源完整的红队证据时，相应后续节点写入明确的跳过回执，08仍综合已有反馈；跳过不能标记为验证通过。连续循环仍有轮数、无发布改善和当前轮完成后停止条件，每轮08之后由控制器决定是否进入下一轮01。候选继续使用已有评估与发布机制；没有可信评估套件时不能用模型自评分发布。

每次原生工作流开始时冻结当前技能版本索引，并将同一 `STAGE_SKILL_BASELINE` 传给01—08的执行器；其他项目同时发布新版本不会改变本轮加载的规则。下一轮01重新冻结当时已发布的索引。

原生工作流调度会话由执行链标题区的“工作流调度”按钮单独打开，继续使用只读会话界面。01—08仅统计各节点实际执行日志及交付检查；未开始且无本节点日志时显示“尚未开始”，不因调度会话已创建而显示轨迹。

### 长节点与构建任务的持久等待

原生工作流中的节点调用只登记或查询任务；任务文件保存进程身份、心跳、截止时间、输出和退出码。节点返回运行中后，当前协调会话可以结束，宿主机继续持有项目锁并等待磁盘任务终态，再通过保存的原生工作流协调剩余节点。相同计划重复请求只接管原任务，不在十分钟后重新启动01。模型文字与会话退出码不能代替任务交付回执。

01的正式构建同样使用持久任务；模型会话结束不会终止构建。环境启动器先等待已登记构建实际结束，再在需要时启动仅做验收的有界会话；验收会话不能扩装依赖或重建。只有本次清单对应的有效交付回执才能算智能体验收完成，否则保留失败并交由既有备用流程处理。环境智能体具备 Monitor 和 TaskStop，读取任务状态和输出，不使用 Task 充当后台输出查询；专用钩子拒绝直接依附于模型会话的 Docker 构建命令。默认01只验收源码可读、Python可运行及隔离边界，额外导入、训练、GPU和服务能力未经验证时明确保留限制；后续验证仍需各自的真实证据。

节点不可变回执保存在 `<运行目录>.meta/workflows/<编号>/receipts/`，学习反馈直接引用这些回执。01不得预先向审计输出目录写入学习文件，02仍严格拒绝覆盖非空目录；正式启动前不能用放宽覆盖检查规避冲突。


### 02—08 长任务与失败验收

02—08的外层节点统一使用持久任务。03必须正常退出且产物齐全才成功，异常退出的残留文件不能作为缓存；04异常退出后只允许既有确定性验证程序重新产生结论，不采纳未完成会话留下的确认报告。05通过受限工具登记独立镜像构建，启动器等待真实终态，再开启仅验收会话；可用场景还要求受害者和攻击者镜像实际存在。06超时清理本次进程及后代；07继续要求正常退出和通过结构检查的审核结果；08的学习会话失败时不启动技能优化，成功候选仍须经过原有评估与发布条件。03、05、07、08的有界会话在超时后清理本次后代，包括另建进程组的后代。停止原生工作流时同时停止归属于本轮的01和05构建，不停止其他任务。

### 中断项目的恢复与报告兼容

工作流接受 `findings` 或 `vulnerabilities` 候选数组，两个数组同时存在时必须一致，条目必须为对象。蓝队交付检查对报告项目标识仅忽略大小写，仍拒绝其他项目；运行标识、报告哈希和证据来源检查保持有效。

使用 `node ui/server/claude-workflows.mjs --resume <state.json>` 可恢复已失败或已停止且没有活动任务的工作流。恢复前重新校验所有已成功交付的产物，取得项目锁，并将原状态与失败任务存入 `recovery-history`；从首个未交付节点继续，不清除失败证据。若上游产物改变，拒绝恢复。环境安装模式 `none` 不再安装 Rust、Go、Java 或原生编译工具链；缺少项目依赖仍须记录为能力限制。

产物阅读模式将文件列表收为方块，悬浮显示路径与来源；顶部运行信息暂时收起，正文占据剩余高度。抽屉左边缘支持拖拽和方向键调整宽度，并记住本机选择；返回节点概览后恢复运行信息。

文件选择区采用图标方格网格，每格仅显示一个类型图标，顶部显示文件总数，悬浮保留完整路径。网格按可用高度调整列数，让当前清单完整展开而不单独滚动。

所有新报告图片必须由文生图模型生成。场景智能体和技能禁止自行编写 SVG、Canvas 或其他代码绘图；兼容入口 render_diagrams.py 仅整理文字、表格和已有模型图片。image2 写同名 .generation.json，记录模型、提示词哈希和图片 SHA-256；场景交付要求真实位图及匹配记录，改后缀或只有 SVG 不能通过。模型失败保留缺图和失败原因，不绘制占位图。历史报告与运行记录保持原样。

经验学习的项目归属以运行目录的项目标识为准，不从报告品牌显示名称推断。SkillOpt 对历史请求仅允许大小写兼容并统一为当前项目标识，其他项目的专属请求仍拒绝；错误请求保留原因并阻止发布。

原生工作流的候选报告以 02 安全审计编排的成功交付回执及报告文件哈希为录入依据；后续阶段仍在运行、降级或失败，不会隐藏已验收报告。没有对应回执、报告哈希变化或草稿仍拒绝录入。02、04、06、07、08 交付后重新汇总候选，更新失败保留日志并停止后续调度，不静默显示旧统计。旧流程保留原有完整报告检查。

候选汇总按运行编号读取最近蓝队、红队与独立审核批次，验证批次项目、冻结报告内容和上游摘要；最新批次未结束或输入过期时不回退旧结论。红队捕获须重算工具输出来源链，独立审核通过须与当前红队证据匹配。每条候选通过 stageResults 分别保留三阶段状态、原因和结果路径，并在候选详情显示；未进入、待定、受阻与尚未执行不等同失败或通过。人工处置优先级不变，审核通过也不自动视为满足图文验收条件。


### 持续循环与验证报告
执行链用 I—VIII 标示固定阶段；已完成轮数按同一项目原生工作流的完整八阶段交付计算，包括有明确降级或跳过结论的轮次，不代表八阶段全部成功，也不等于技能发布次数。节点重跑、失败及只执行后半段的流程不计完整轮数。
网页“启动连续循环”显式请求持续模式：每轮由原生工作流工具执行，结束后间隔五分钟进入下一轮；没有发布改善时保持当前技能，不绕过评估。调度失败停止并显示原因，停止按钮等待当前轮结束。原有命令行和未指定持续模式的接口仍保留最多三轮、连续两轮无发布改善停止的默认值。普通重新审计只运行一轮，返回箭头不代表已经启动持续任务。
左侧邮件图标进入“验证报告”；接口 `/api/verified-reports` 按候选单独整理影响、根因、触发条件、验证方法、审核结论、修复和证据路径。只有当前批次蓝队动态确认、红队证据核验、独立审核通过，并有匹配文生图插图和图文总报告才展示。新插图核验生成记录和内容哈希，历史插图仅兼容具有同路径模型响应缓存且文件未晚于缓存修改的记录；程序绘制的结构图不能满足条件。读取后续重跑尚未完成时不展示旧批次结果。


执行链标题下显示实际运行编号。候选问题来自最近有效报告，而最新任务可能是失败且没有正式报告的恢复尝试，两者不互相覆盖。编号不一致时明确提示来源差异，并提供“查看候选对应执行链”和“返回最新运行”切换；轨迹、产物和重跑始终绑定当前展示的运行。历史失败保留可见，不用候选数量推断最新任务已成功。

验证报告页默认展示全部项目，项目筛选由报告页独立管理，不继承看板的左侧筛选；标题显示当前数量与全部数量，选择器标明每个项目的报告数。


漏洞插图统一采用 technical-explainer-v1，模板位于 .claude/skills/project-cartographer/references/technical-explainer-prompt.md。场景设计智能体与备用文生图脚本都应用该模板：默认请求 1536×864，浅色背景、3–5 个真实技术实体、深灰组件、蓝色正常数据流、连续红色利用路径和具体检查缺口；允许必要的短技术标签，禁止故事人物、纸纹、安全或工业隐喻。矢量仅指视觉风格，仍完全由文生图模型生成位图。新任务不将旧故事插画缓存当成本样式完成项；历史产物保留。这里只验证提示词、请求与缓存选择，新风格的实际模型输出仍需生成后检查，不能把风格约束当作生成质量保证。

顶部实时审计任务卡片区已移除。左侧看板图标使用数字角标展示正在运行的项目数，按项目去重，不受当前筛选影响；无项目运行时隐藏角标，悬浮说明提供运行数量。既有实时状态轮询继续更新角标，具体运行状态和轨迹通过项目执行链查看。

项目缺少本地图标时，界面服务后台下载 GitHub 或 GitLab 仓库所有者头像，不阻塞审计和页面；并发请求合并，失败后十分钟内不重复请求。仅接受受限大小的位图，完成后原子写入 ui/public/logos；图标从该目录直接提供，无需重新构建页面。下载失败时继续使用默认图标，不影响项目运行。


报告下载统一提供 ZIP 包，原始模型 Markdown 保持不变。通用导出器解析 Markdown 的图片、附件链接和引用式链接，递归收集同一产物范围内的资源与被链接章节，并在包内报告副本中重写相对路径；外部网页链接保留，外部图片、缺失附件、越界或符号链接明确报错。节点产物页的 Markdown 下载复用该导出器，不依赖模型措辞、固定文件名或某个项目。
邮箱报告包另按该候选的阶段结果收集 AI 插图、蓝队验证报告与落盘证据、验证程序、红队场景和工具轨迹、独立审核结果，生成来源及 SHA-256 清单，不包含整个运行目录或其他候选的文件。每文件上限 10 MiB，总文件内容上限 32 MiB；必需证据缺失则停止导出。下载前重新检查当前报告是否满足展示条件，客户端不能指定服务器文件路径。


交付清单按文件类型校验：普通文件记录 SHA-256；同一交付目录内的相对文件符号链接记录链接文本、解析目标和目标内容哈希，下游继续使用前重新核对。绝对路径、越界、悬空、循环和目录链接均阻断，不使用仓库名称或库名例外，也不跟随未知链接。所有文件仍进入清单，没有静默跳过依赖文件。
交付检查失败按 artifact_contract 分类，责任为 workflow-delivery；阶段执行失败另行分类。已完成批次的指针在交付成功前保留。恢复流程只在项目、运行、工作流所有者、阶段、输入总报告哈希及全部上游产物快照完全匹配时复用最新完成批次；已有成功回执再次校验，失败任务归档。条件不符则不复用旧结果，不通过反复调用模型掩盖交付问题。

左侧验证报告邮件图标使用数字角标展示实际可阅读报告总数，与报告列表共享同一接口数据，每三十秒更新，也可在报告页手动刷新。数量不使用待人工验收候选数，不受看板或报告页项目筛选影响；读取失败时保留上次成功数据并在报告页提示错误。

技能优化期间的递归保护环境标记仅在当前调用内生效，无论返回成功、失败或异常都恢复调用前状态，避免同一进程后续经验学习被错误跳过。

报告项目身份采用交付前与消费前双重校验：统一报告检查器从受控运行目录确定项目编号，也支持启动器显式传入；模型显示名称只能写入 project_name。旧版 metadata.project_id 由统一解析器兼容，顶层与旧版编号冲突时拒绝。原生工作流在 II 阶段冻结报告前及后续节点读取报告时核对启动任务的项目编号，两种编号均缺失、字段冲突、品牌名或其他项目均拒绝，错误分类为 artifact_project_identity。校验不使用人工别名表，也不自动改写已冻结报告及哈希；生产者收到修改意见后应重新提交正确产物。

导入已有 GitHub 仓库时，按主机、所有者和仓库名称比较身份，兼容 HTTPS、SSH 及 Git 地址重写；仍拒绝不同主机、所有者或仓库，保留已有源码和提交版本。

阶段二使用固定版本 agentcov 解析工具实际返回的读取范围；派发前登记审计意图、覆盖编号、假设与范围，并关联各子会话。每波可刷新读取汇总用于后续规划，退出时汇总到 task-artifacts/read-coverage/summary.json 与 summary.md，随现有阶段二交付清单冻结，经验学习沿用现有证据入口读取。仅阶段二启动器启用采集；其他阶段不增加采集。搜索命中、未知范围、未关联意图与采集异常分开保留，不改变验证状态，不计算全仓库覆盖率。历史运行不回填，工作副本遗留读取记录不会计入新一轮。


交付契约更新：报告身份由 scripts/workflow/delivery_contract.py 统一解析，兼容顶层 project 和旧版 metadata.project_id；两者同时存在必须一致，并与任务编号精确匹配，不使用品牌别名，也不改写已冻结报告。新报告模板写顶层 project 与 project_name。工作流所有阶段共用版本化交付清单：普通文件与安全的相对文件链接继续校验内容摘要；带有效 pyvenv.cfg 的 Python 虚拟环境形成 runtime_only 快照，记录配置、每个文件摘要及链接文本，不跟随容器解释器链接，不作为可移植证据。蓝队交付额外校验报告明确引用的脚本、候选和证据附件，缺失、越界或仅存在于临时环境的引用仍阻止交付；红队交接与报告下载复用相同分类，环境只导出配置和快照。此分类不按 venv 等目录名跳过，也不放宽普通产物的链接校验。计算已完成而交付失败时，沿用同一工作流、项目、上游摘要和完成批次重新校验，不重复调用模型。

验证报告的有效性检查与阶段交付工具统一校验附件，不能仅凭 verdict 接受报告。附件不完整但有验证脚本时，由执行器在干净输出目录重跑受控验证，保留原始暂存产物及脚本依赖；不让模型手动复制部分结果。旧运行可使用交付恢复命令从报告 SHA-256 完全相同且附件完整的执行目录补齐缺失文件，拒绝内容冲突，不生成或伪造日志。环境生成器对 Java 使用无图形界面的 JDK，并使用 BuildKit 的软件包缓存和有界下载重试；仍保留构建总时限，网络持续不可用时如实受阻。

阶段八优先修订方法规则，使用真实执行文档并绑定摘要；基线变化后拒绝发布旧候选。项目知识与程序故障单独归因，缺少真实评估时不声称有效进化。详见 [Markdown 优化边界](rsi-markdown-optimization.md)。

全局项目并发上限由 config/system.json 的 projectConcurrency 配置，当前为 15。完整原生工作流及独立节点重跑在调用模型前统一申请项目名额，其内部节点沿用同一名额，不重复占用。超出上限的任务持久化排队，按排队顺序取得名额，完成、失败或停止后释放；连续循环每轮重新排队。部署前已有活动工作流计入占用，不强制终止。项目内成员并发保持原配置，此上限不是 API 请求数限制。


反馈引导探索已接入阶段二与阶段八。阶段二读取 task-artifacts/exploration-plan.json，以区域、视角、假设和证据组织任务，energy 为 0—3 建议档位，并保留探索份额；智能体可基于新证据调整，不改变总时限或验收条件。读取新区域提供弱信号，证据变化提供封顶过程信号；强奖励只复用 /api/verified-reports 的严格验收并按独立根因去重，接口不可用时不产生强奖励。报告奖励仅记录关联，不能证明 skill 的因果收益。

阶段八默认直接提出 Markdown 补充，SkillOpt 改为 RSI_SKILLOPT_ENABLED=1 时可选。新生成、provenance.change_kind=method 的阶段二候选可进入项目限定短期试用；通用候选也只在来源项目试用。试用记录位于 rsi/exploration/<project>/，不修改稳定 active.json。工作流启动时固定试用版本；执行文档摘要变化则不加载。试用观察三轮后，有持续过程收益可保留为项目限定规则；连续两轮无收益或循环运行失败会收回，保留历史记录。保留不等于全局稳定发布。其他阶段仍使用原评估发布机制。

阶段二允许使用文档检索工具按项目需要查询同类 CVE、维护者公告和修复提交；检索不可用时保留限制。外部资料仅作为假设来源，必须回到当前源码核实。临时方法笔记位于 .workspace/findings/skill-experiments/，通过补充上下文读取，不冒称动态注册原生 Skill；长期方法通过现有候选机制试用。

蓝队正式报告只按批次 summary.json 中候选编号选择，诊断与历史报告保留归档但不作为当前候选验收。红队正常执行但未捕获标记记为 degraded，不提升证据等级；真实执行错误仍 failed，并单独记录目标触发次数与未触发原因。操作日志存放于独立会话目录，正式交付冻结其只读快照；旧日志恢复必须核对原长度及原 SHA-256，仅保存匹配前缀，归档迁移记录，不修改原证据。环境构建智能体在下载前检查发行版、架构和候选包；缺索引明确为 unknown，不猜测可用。

词元用量现已提供增量采集与汇总：scripts/workflow/token_usage.py 解析会话结果、消息用量、Jev 批次统计及红队 model-usage.jsonl，以会话/请求身份去重；最终会话总量替代逐消息记录，不叠加镜像日志。输入、输出、缓存写入和缓存读取分别展示，缺失字段计入 missing_fields，不推断成零。GET /api/token-usage 支持 project、run 筛选。服务启动独立采集进程，每 60 秒增量刷新 SQLite 与汇总文件；首次扫描可能较慢。原始来源与用量记录保留在本地数据库。红队新请求在解析回答前保存用量，失败且无 usage 的请求标为未知；历史未记录的调用无法补回。不代表全量账单，也不直接跨提供方相加缓存字段。尚未绘制登山图及关联成果事件。

节点交付回执按同一产物的最新提交判定，保留旧提交以供追溯；校验失败也必须返回结构化修改意见。红队执行结束时由执行器通过同一个交付工具提交实际结果，避免自动结束路径遗漏提交。


## 两项 RSI 奖励与逐轮观测

每轮阶段八收集前序结果时计算 `R = alpha * delta_risk_coverage + beta * new_verified`。当前公式版本为 `rsi-two-signal-v1`，默认 `alpha=0.01`、`beta=10`。覆盖单位是风险加权代码行：每行权重为 `1 + max(JEV priority)`，没有优先分数时权重为 1。只计实际读取的已知行范围，搜索命中和未知范围不推断为完整读取；按项目、源码版本、文件路径和内容摘要维护历史区间并计算差集。首次采用新公式时读取已登记历史建立基线，不生成旧轮次奖励。意图归属、证据文本变化和资源消耗不独立加分；没有新漏洞但新增覆盖为正也有正奖励。当前暂不增加大范围读取的额外限制。

新验证漏洞复用既有报告资格与同一问题编号去重。相同轮次重复采集只累计新出现的覆盖或成果；补算时保留原来的两项贡献。公式版本、系数、各项输入、总分、新增代码范围、问题编号、源码版本和缺失说明保存于 `rsi/reward.json` 与 `rsi/exploration-feedback.json`，跨轮历史位于 `rsi/exploration/<project>/state.json`。阶段八评分工具通过 `objective` 返回这份持久化结果；看板执行链的“RSI 奖励”展开后展示每轮计算与依据，最近二十条记录由原有执行链接口返回。数据未齐时标为暂计，不将缺失观测解释成完整零收益；不完整观测不增加连续无收益计数。没有源码版本时覆盖暂不计分。源码版本变化会建立新的覆盖基线，跨版本分数不可直接用于技能优劣判断。

奖励只表示观测收益与技能版本的关联，不替代漏洞验收和技能独立评估。任务投入建议仍独立保留；新公式未增加令牌配额调度。新增覆盖和验证成果为零时不再因证据文字变化获得奖励。


RSI 循环默认执行八轮完整 I—VIII，界面启动固定八轮。没有新奖励或新发布也继续；完成八轮自动结束，人工停止请求在当前轮结束后生效，工作流失败仍保留错误并停止。连续模式只控制轮间等待五分钟，不再表示无限轮次。


执行链展示阶段二累计词元与 AgentCov 覆盖曲线：按源码版本分组，每轮一个点，支持去重读取行数和风险加权覆盖。历史读取汇总与已去重的词元分类按项目、轮次对齐；输入输出与缓存按提供方口径计入，未知用量不伪造，累计缺口显示虚线和空心点，明细表保留未知状态。这是已记录用量的曲线，不代表完整账单或读取理解程度；数据缓存三十秒。

蓝队批次收尾逐候选复核交付回执与文件摘要。单个候选缺少回执、附件不完整或内容改变时，原始目录归档到同次节点输出的 verify/delivery-failures，正式批次仅保留由执行器提交的结构化受阻报告；不补造验证证据，不保留该候选的确认结论。其他候选的有效交付不变，按现有阶段策略继续调度。阶段交接只读取 summary.json 登记的当前候选回执，重试历史不参与当前验收；公共批次清单损坏、受阻记录无法保存或取消任务仍可停止阶段。

审计编排结束后若主报告仍与已验收版本一致，但附件在收尾过程中改变，调度器通过同一提交工具重新验收一次全部已声明附件，并保留原回执；覆盖记录同时执行现有结构校验。附件缺失、符号链接、越界、主报告改变或重新验收失败仍拒绝交接，不删除依赖文件或直接刷新旧回执摘要。此收尾处理不重新调用模型，不放宽漏洞确认条件。

第三阶段图片交付为可选增强：没有绘图任务、图片生成失败或图片回执无效时，节点保留退出码及缺图原因并标记降级，继续后续验证；不要求至少一份图片回执。图片交付失败时，正式工作流仅冻结缺图状态记录，不将未验收图片作为有效交付。正常图片仍按原有文生图来源与摘要检查；本规则不放宽蓝队、红队和独立审核的证据条件。

第五阶段按成员汇总实际有效交付，不再要求交付回执数等于全部选中候选数。缺少或无效回执的成员在批次及成员界面标记“缺少有效交付”，已有有效场景继续第六阶段；未验收场景不进入红队执行。原始受阻原因、产物和回执保留，不为满足数量补造回执。公共批次清单损坏仍拒绝交接。
