# 通用授权缺陷模式（所有项目必审）

拿到任何实现了基于角色或权限访问控制的项目，无论使用何种编程语言，以下授权缺陷模式都必须进行审计。这些问题源于业务逻辑设计和访问控制实现缺陷，与具体语言实现无关。

## 仅验证身份未验证权限

### 粗粒度身份认证
系统仅验证用户是否登录（身份认证），但未检查用户是否有权执行具体操作（权限授权）：
- 接口仅验证 token 有效性或登录态，未校验角色和操作权限（只验证身份，不验证权限）
- 中间件或拦截器进行通用身份验证，但未针对具体操作细化权限检查（中间件缺少细粒度权限验证）
- 敏感操作入口缺少权限注解、装饰器或守卫等授权检查机制（缺少授权检查机制）

## 依赖路径隐藏或前端控制

### 安全性依赖隐蔽性
将管理功能或敏感操作通过复杂路径、前端隐藏或文档不公开等方式"保护"，但未实施后端权限校验：
- 管理员接口使用随机路径、UUID 路径或混淆命名，未进行权限检查（依赖路径隐蔽性而非权限检查）
- 敏感操作依赖前端按钮隐藏或页面访问限制，后端接口未验证权限（依赖前端隐藏而非后端校验）
- 内部接口或调试接口未公开文档但可被访问，且未实施授权检查（依赖文档隐蔽性而非权限检查）

## 共享服务未区分调用上下文

### 多角色共享业务逻辑
同一个服务方法、处理函数或业务逻辑被多个不同权限级别的调用方使用，但未根据调用上下文区分权限：
- 共享服务方法被多个控制器或处理器调用，但方法内未检查调用者权限（共享方法未验证调用者身份）
- 共用处理函数处理多种角色的请求，但未区分不同角色的权限上下文（未进行角色上下文隔离）
- 批量操作或聚合接口未针对不同权限级别的资源进行过滤（缺少权限范围过滤）

## 动态函数调用绕过授权检查

### 通过参数控制执行路径
允许通过用户输入的参数（如 action、method、function 名称）动态调用内部函数或方法，绕过正常的路由和授权检查流程：
- 通过 URL 参数或请求体指定方法名，直接调用内部函数（参数控制函数调用绕过权限检查）
- 通过事件名、命令名或 action 字段进行路由分发，但未对操作授权（基于参数的路由分发缺少权限验证）
- 使用回调注册、函数映射表等机制，但注册时未添加授权检查包装（回调机制缺少权限包装）

## 权限检查覆盖不完整

### 授权机制部分失效
系统实施了权限控制机制，但部分入口点漏掉授权检查，导致防护覆盖不完整：
- 装饰器、注解或中间件链覆盖不完整，部分端点漏掉权限检查（授权机制覆盖不完整）
- 旧版本接口或兼容性接口未应��新的权限策略（遗留接口未更新权限策略）
- 异常处理、错误页面或回退路由绕过了正常的授权流程（错误处理绕过授权检查）

## 补充：对象级授权缺陷（BOLA/IDOR）与功能级授权的区别

### BOLA 定义
**BOLA（Broken Object Level Authorization，对象级授权缺陷）**，又称 **IDOR（Insecure Direct Object Reference，不安全的直接对象引用）**，指用户可通过修改资源标识符（ID）直接访问或修改其他用户的资源，而系统未验证该用户是否拥有或有权访问该资源。

### 功能级授权 vs 对象级授权

| 维度 | 功能级授权（Function-Level） | 对象级授权（Object-Level） |
|------|--------------------------|------------------------|
| **保护对象** | 函数、接口、操作权限 | 数据资源、对象实例 |
| **核心问题** | 普通用户可执行管理员函数 | 用户可访问其他用户的资源 |
| **典型例子** | `/api/admin/delete_user` 无权限检查 | `/api/user/123/documents` 改ID访问他人文档 |
| **审计重点** | 是否存在权限检查 | 是否验证资源所有权 |
| **绕过方式** | 直接访问隐藏的管理接口 | 修改资源ID进行枚举 |

### BOLA 在本审计指南中的位置

本指南主要关注**功能级授权**（函数级权限），但对象级授权（BOLA）在以下场景中有所涉及：

1. **bypassTricks.md - "用户ID和所有权检查"部分**
   - 跨用户资源访问：`GET /api/user/123/documents` 到 `GET /api/user/456/documents`
   - 所有权验证不当：未检查当前用户是否是资源的 owner

2. **bypassTricks.md - "团队和组织级别权限"部分**
   - 组织切换：修改ID访问其他组织
   - 团队成员权限：权限检查缺失

### BOLA 审计建议

若项目需要进行 BOLA 深入审计，建议：
- 关注所有资源访问端点（`/api/{resource}/{id}`）
- 验证每个资源访问前是否进行所有权校验
- 检查多租户场景下的隔离机制
- 测试参数化资源ID（123, 124, 125...）的访问权限

## 补充：CWE-288（认证绕过）与功能级授权的关系

### CWE-288 定义
**CWE-288（Authentication Bypass by Spoofing）**：通过伪造身份信息（如IP、证书、HTTP头部、Token）来绕过认证机制。

### CWE-288 与本指南的关系

| 维度 | 功能级授权 | CWE-288认证绕过 |
|------|----------|----------------|
| **保护层次** | 后端业务逻辑层 | 认证/网络层 |
| **核心问题** | 权限检查缺失或不完整 | 认证本身被绕过 |
| **典型例子** | 已认证用户越权执行管理员操作 | 伪造Authorization头部绕过认证 |
| **前置条件** | 需要通过认证 | 绕过认证本身 |

### CWE-288 在本审计指南中的位置

本指南在 **bypassTricks.md - "HTTP头部认证绕过"部分** 专门涉及 CWE-288 相关内容：

1. **代理头部伪造**
   - X-Forwarded-For、X-Real-IP 等头部伪造源IP
   - 绕过基于IP白名单的认证

2. **Authorization头部操作**
   - 多个Authorization头部选择性使用
   - 空Authorization头部或大小写变化
   - 伪造或篡改身份令牌

3. **CORS预检绕过**
   - OPTIONS请求跳过认证检查

4. **JWT头部攻击**
   - JWT算法混淆（alg: none）
   - 签名验证绕过
   - Token篡改

5. **自定义头部注入**
   - 直接注入身份信息的自定义头部

### CWE-288 vs 功能级授权漏洞的利用链

```
认证绕过 (CWE-288) → 冒充用户 → 越权执行函数 (功能级授权缺陷)
                           ↓
                    访问他人资源 (BOLA)
```

完整的攻击链可能需要同时存在多个漏洞：
- CWE-288：伪造/绕过认证
- 功能级授权缺陷：越权执行敏感操作
- BOLA：访问他人资源

### 审计建议

在审计功能级授权时，建议同步考虑：
- HTTP头部认证是否可被绕过（CWE-288）
- 是否存在CORS、OPTIONS等特殊请求处理的认证漏洞
- JWT或Token的验证是否充分
- 认证失败后是否正确拒绝授权
