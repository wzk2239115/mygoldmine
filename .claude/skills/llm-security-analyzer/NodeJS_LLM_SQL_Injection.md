# **NodeJS LLM SQL Injection**

当 Node.js 应用将 LLM 生成的输出用于构造 SQL 查询，且未使用参数化查询，攻击者可以通过提示注入使模型生成恶意 SQL，实现数据库的任意查询或修改。

## Details

**代码示例位置识别技巧（L1: 关键词扫描）**
- 搜索 SQL 构造：`"SELECT ... " + llmOutput`、`query = \`SELECT ... \${value}\``
- 查找数据库查询：`db.query()`、`connection.query()`、`client.query()`
- 搜索参数化检查：缺失的 `?` 占位符或参数数组
- 查找 ORM 使用：`sequelize`、`typeorm`、`knex` 等
- 定位动态 SQL：`raw query`、`rawQuery`、`execute()`

**核心操作保护机制（L2: 跳读）**
- 检查是否使用了参数化查询（预编译语句）
- 验证是否使用了 ORM 框架的安全接口
- 查看是否有 SQL 注入检测或防护库
- 检查是否对输入进行了验证
- 查看是否有查询白名单

**快速定位到具体漏洞（L3: 逐行读）**
- 追踪 SQL 查询的构造方式
- 检查是否使用了 `?` 占位符或命名参数
- 审查参数数组的使用
- 查看是否有字符串拼接
- 检查 ORM 查询是否安全

**数据流追踪（L4: 跨模块追踪）**
- 追踪从 LLM 输出到数据库查询的完整路径
- 检查是否有中间处理步骤
- 验证所有查询点是否都使用了参数化

## Classify

**确认为漏洞的特征：**
1. SQL 查询使用字符串拼接，包含 LLM 输出
2. 未使用参数化查询或预编译语句
3. 使用原始 SQL 查询而非 ORM 框架
4. 可以构造有效的 SQL 语句注入
5. 数据库错误信息暴露于用户

**误报场景：**
1. 使用参数化查询或预编译语句
2. 使用 ORM 框架的安全接口
3. LLM 输出仅用于参数值，不涉及 SQL 结构
4. 有严格的输入验证
5. 数据库用户权限最小化

**代码异味（需要深入审查）**
1. 混合使用参数化和字符串拼接
2. 条件性地使用参数化
3. 动态 SQL 构造
4. ORM 使用 `.raw()` 或等价方法

## Low risk

**评级为低风险的场景：**
1. 所有查询都使用参数化查询或预编译语句
2. 使用成熟的 ORM 框架（Sequelize、TypeORM）
3. LLM 输出仅作为数据值，不涉及 SQL 语句结构
4. 数据库用户权限严格限制（无 DROP、TRUNCATE 权限）
5. 有代码审查机制检查所有数据库查询
