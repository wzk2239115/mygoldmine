# **Rust LLM Output Unescaped**

当项目中集成了大语言模型（LLM）功能，并将模型生成的输出未经转义直接渲染或传递时，存在严重的安全风险。特别是在 Rust Web 框架（如 Actix-web、Rocket）中，如果将 LLM 输出直接返回给客户端或在 HTML 上下文中渲染，可能导致 XSS 攻击、代码注入或其他输出相关漏洞。

## Details

**代码示例位置识别技巧（L1: 关键词扫描）**
- 搜索 `resp.text()`、`Html()`、`render!`、`template!`、`format!()`、`String::from()` 等涉及输出的函数
- 查找 LLM API 调用后的数据处理流，特别是 `openai_client.chat()`、`model.generate()`、`completion()` 等
- 定位变量在输出到客户端前的处理方式，检查是否经过 `htmlescape`、`encode` 等转义函数

**核心操作保护机制（L2: 跳读）**
- 识别输出数据类型：是否返回纯文本（JSON）、HTML 模板、Web 响应
- 检查是否使用了防 XSS 库（如 `ammonia`、`html-escape`、`sanitize-html`）
- 追踪 LLM 输出到最终渲染的完整数据流
- 验证是否有基于上下文的编码（HTML 编码 vs JSON 编码 vs URL 编码）

**快速定位到具体漏洞（L3: 逐行读）**
- 查看 `HttpResponse::Ok()`、`HttpResponse::build()` 等返回值构造
- 检查 Actix 的 `web::Json`、`web::Html` 包装方式
- 审查 Jinja2、Tera 等模板引擎的变量使用是否启用了自动转义
- 检查 Serde 序列化时是否有特殊处理

**数据流追踪（L4: 跨模块追踪）**
- 追踪 LLM 输出从 API 调用、本地存储、缓存到最终渲染的整个路径
- 检查中间件、过滤器是否对输出进行了转义
- 验证错误处理路径中是否也包含未转义的 LLM 输出

## Classify

**理论判断标准**

**确认为漏洞的特征：**
1. LLM 模型输出直接用于 HTTP 响应体或 HTML 模板变量，未经任何转义
2. 输出数据用于执行代码路径（如 `eval`、动态 SQL、系统命令），未进行验证
3. 多用户环境下，LLM 输出可能包含来自其他用户的敏感数据且未隐藏
4. Web 框架配置关闭了自动转义或使用了 `unsafe` 的渲染方式

**误报场景：**
1. LLM 输出仅用于纯文本日志记录或内部调试
2. 输出经过了完整的 HTML/URI 编码处理
3. 在 JSON 响应中返回，且前端框架自动转义（如 React、Vue）
4. 输出被用于只读展示，无法被修改或注入

**代码异味（需要深入审查）：**
1. 存在自定义的转义函数而非使用标准库
2. 有条件性的转义逻辑（如根据某个标志位决定是否转义）
3. 多次转义或部分转义的现象
4. 模板引擎配置为不安全模式

## Low risk

**评级为低风险的场景：**
1. LLM 输出仅用于返回 JSON API 响应，且前端明确使用了类似 React、Vue、Angular 等框架自动转义
2. 输出内容完全来自非用户可控的模型参数（如系统提示），不涉及用户输入
3. 应用程序仅提供内部 API，使用者是可信任的开发人员或系统
4. 输出被用于日志、审计追踪等非渲染场景，且无敏感信息泄露风险
5. Web 框架本身实现了全局自动转义且配置正确，可验证所有输出均被保护
