# **Python LLM Prompt Injection Direct Concatenation**

当 Python 应用程序将用户输入直接拼接到发送给 LLM 的提示词中，未进行任何验证或清理时，攻击者可以注入恶意提示词内容，改变模型行为、提取敏感信息或突破应用限制。

## Details

**代码示例位置识别技巧（L1: 关键词扫描）**
- 搜索字符串拼接操作：`f"{user_input}"`、`"...{}".format(user_input)`、`+ user_input`、`str.join()`
- 查找 OpenAI、Anthropic、LangChain 等 LLM 库的调用：`client.chat.completions.create()`、`chain.invoke()`
- 定位 `system_prompt`、`user_message`、`prompt` 等包含用户数据的变量
- 搜索未使用 PromptTemplate、PromptValue 等安全构造方式的地方

**核心操作保护机制（L2: 跳读）**
- 检查是否使用了参数化的提示词构造（如 PromptTemplate with variables）
- 验证是否实现了输入验证（长度限制、字符白名单、正则表达式）
- 查找是否使用了提示词注入防护库或框架（如 langchain.prompts）
- 检查是否对用户输入进行了清理或转义

**快速定位到具体漏洞（L3: 逐行读）**
- 追踪变量的赋值过程，从用户输入到 LLM 调用
- 检查 OpenAI/Claude API 调用中 messages 列表的构造方式
- 审查是否有多个拼接点或层级嵌套的字符串操作
- 查看是否在模板中使用了分隔符（如"---"、"```"）来标记用户输入边界

**数据流追踪（L4: 跨模块追踪）**
- 追踪用户输入从接收、验证、到达 LLM 调用的完整路径
- 检查中间件、数据库查询结果是否也被直接拼接
- 验证错误消息、日志中是否也包含未清理的用户输入

## Classify

**确认为漏洞的特征：**
1. 用户可控的输入通过 `+`、`f-string`、`format()` 等直接拼接到提示词
2. 未对输入进行长度、格式、内容验证
3. 提示词包含明确的指令边界标记（如"停止处理用户输入"），但用户可以通过注入突破
4. 应用预期的功能与模型实际执行的功能不一致，表明提示词被修改

**误报场景：**
1. 仅在内部日志或调试信息中使用字符串拼接，不发送给 LLM
2. 用户输入经过严格的输入验证（如只允许特定格式的数据）
3. 使用了 LangChain PromptTemplate 等安全的参数化构造
4. 提示词系统设计明确指定了用户输入的位置和格式限制

**代码异味（需要深入审查）：**
1. 存在多层嵌套的字符串拼接
2. 动态生成的提示词内容，而非配置化管理
3. 提示词中包含注释或说明用户输入位置的地方
4. 相同的提示词构造在多个地方重复出现

## Low risk

**评级为低风险的场景：**
1. 用户输入被用于完全隔离的参数（如数据库表名、查询过滤条件），不进入提示词
2. LLM 调用使用了明确的系统提示和用户消息分离机制（separate messages）
3. 模型被严格限制在特定的输出格式或 JSON schema 中，难以被注入利用
4. 应用明确使用了 LangChain、Pydantic 等框架的参数化提示词
5. 输入长度严格限制在极小范围（如 10 个字符以内）
