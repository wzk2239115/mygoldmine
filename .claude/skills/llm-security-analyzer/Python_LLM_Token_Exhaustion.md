# **Python LLM Token Exhaustion**

当 Python 应用调用 LLM API 时，未对每个用户或应用的 Token 用量进行限制，攻击者可以通过长篇幅输入、重复调用或循环生成，快速耗尽 API 配额，导致拒绝服务（DoS）或产生巨大的成本损失。

## Details

**代码示例位置识别技巧（L1: 关键词扫描）**
- 搜索 API 调用模式：`client.chat.completions.create()`、`model.generate()`、`completion()`
- 查找输入长度处理：`len(user_input)`、`tokens = `、`num_tokens_from_string()`
- 搜索重复调用：`for _ in range()`、`while True`、`recursive` 函数调用 LLM
- 查找速率限制：`RateLimiter`、`rate_limit`、`sleep()`、`quota`
- 定位成本计算：`cost = `、`api_call_count`、`token_usage`

**核心操作保护机制（L2: 跳读）**
- 检查是否实现了每个用户的 token 配额限制
- 验证是否有输入大小的限制
- 查看是否实现了速率限制（requests per minute）
- 检查是否有成本监控或告警机制
- 查看是否有会话或请求超时

**快速定位到具体漏洞（L3: 逐行读）**
- 追踪用户输入的长度检查
- 检查 API 调用前是否进行了 token 计数
- 审查是否有余额检查或配额实施
- 查看错误处理中是否捕获 token 配额超限错误
- 检查是否有累积调用计数的机制

**数据流追踪（L4: 跨模块追踪）**
- 追踪 token 使用计数的全局管理
- 检查多个 API 调用点是否都进行了计数
- 验证用户隔离是否正确

## Classify

**确认为漏洞的特征：**
1. 未实现每个用户的 token 配额限制
2. 接受任意长度的输入，无大小限制
3. 允许用户触发多个 LLM 调用，无频率限制
4. 未监控 API 使用成本，可能导致意外账单
5. 循环或递归调用 LLM，无退出条件

**误报场景：**
1. 实现了严格的每个用户 token 配额（如每天 10M tokens）
2. 输入长度严格限制（如最多 2000 字符）
3. 实现了速率限制（如每分钟最多 10 次调用）
4. 有成本监控和告警机制
5. 仅为可信用户提供 API 访问，内部使用

**代码异味（需要深入审查）**
1. 多个独立的 token 计数机制
2. 配额检查在不同的地方进行
3. 默认值非常高或未明确设置
4. 条件性地启用或禁用配额检查

## Low risk

**评级为低风险的场景：**
1. 实现了严格的每用户 token 配额，且与实际业务需求相匹配
2. 输入长度严格限制在合理范围内（如 1000-5000 字符）
3. 实现了完整的速率限制和成本监控
4. 应用仅供可信用户内部使用，有充分的审计日志
5. 使用了 LLM API 服务的官方配额管理功能
