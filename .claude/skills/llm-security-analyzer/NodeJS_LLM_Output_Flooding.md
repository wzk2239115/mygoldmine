# **NodeJS LLM Output Flooding**

当 LLM 可以生成大量输出，而应用未对输出大小进行限制时，攻击者可以使用特殊提示使模型生成海量数据，导致内存耗尽、网络带宽消耗或拒绝服务。

## Details

**代码示例位置识别技巧（L1: 关键词扫描）**
- 搜索输出处理：`response.text`、`message.content`、`model.generate()`
- 查找数据流处理：`stream: true`、`on("data")`、`response.pipe()`
- 搜索缓冲区：`Buffer`、`array.push()`、`string concatenation`
- 查找大小检查：缺失的 `response.length` 检查
- 定位内存限制：缺失的最大输出大小限制

**核心操作保护机制（L2: 跳读）**
- 检查是否设置了最大输出令牌数
- 验证是否有输出大小限制
- 查看是否监控内存消耗
- 检查是否有超时机制
- 查看是否流式传输大响应

**快速定位到具体漏洞（L3: 逐行读）**
- 追踪输出数据的处理方式
- 检查是否有缓冲区大小检查
- 审查是否有循环或递归生成输出
- 查看超时设置
- 检查错误处理中的内存泄露

**数据流追踪（L4: 跨模块追踪）**
- 追踪输出从 LLM API 到客户端的完整路径
- 检查是否有中间处理步骤进行了大小检查
- 验证监控和告警

## Classify

**确认为漏洞的特征：**
1. 未限制最大输出令牌数
2. 没有输出大小检查
3. 支持循环或递归生成输出的提示
4. 内存消耗无监控
5. 所有输出都缓冲在内存中

**误报场景：**
1. 设置了最大输出令牌数（如 2000 tokens）
2. 有输出大小限制（如 10MB）
3. 使用流式传输处理大输出
4. 有超时机制
5. 内存消耗有监控和告警

**代码异味（需要深入审查）**
1. 输出完全缓冲在内存中
2. 无大小检查但有循环生成
3. 条件性地应用大小限制
4. 缺少超时机制

## Low risk

**评级为低风险的场景：**
1. 设置了合理的最大输出令牌数（如 1000-2000 tokens）
2. 有明确的输出大小限制并在代码中强制执行
3. 使用流式传输和渐进式处理
4. 有超时机制防止无限输出
5. 内存消耗有监控，超过阈值立即终止
