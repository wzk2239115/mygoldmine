# **Python LLM Indirect Prompt Injection LangChain**

当 Python 应用使用 LangChain 框架集成 LLM，并从外部数据源（数据库、API、用户文件）检索数据作为提示词的一部分，攻击者可以通过污染这些数据源，间接注入提示词，实现间接提示注入攻击。

## Details

**代码示例位置识别技巧（L1: 关键词扫描）**
- 搜索 LangChain 检索器：`VectorStoreRetriever`、`loader`、`load_data`、`RAG`
- 查找数据加载模式：`loader = TextLoader()`、`documents = loader.load()`
- 搜索链式调用：`RetrievalQA`、`ConversationalRetrievalChain`、`create_retrieval_chain()`
- 定位外部数据源：数据库查询、API 调用、文件读取
- 查找提示模板变量：`PromptTemplate`、`context`、`retrieved_documents`

**核心操作保护机制（L2: 跳读）**
- 检查检索数据是否进行了清理或验证
- 验证是否对检索数据进行了内容审查（关键词检查、格式验证）
- 查看是否有沙箱环境隔离不同用户的数据
- 检查数据库权限控制是否正确
- 查看是否对检索到的数据量有限制

**快速定位到具体漏洞（L3: 逐行读）**
- 追踪数据从源到提示词的完整路径
- 检查 LangChain 模板如何使用检索数据
- 审查是否有用户可见的查询或检索逻辑
- 查看是否有多个检索点或数据融合
- 检查错误消息是否泄露了检索到的数据内容

**数据流追踪（L4: 跨模块追踪）**
- 追踪用户输入 → 检索查询 → 数据库/API → 检索结果 → 提示词构造
- 检查多用户环境下的数据隔离
- 验证缓存机制是否有跨用户污染

## Classify

**确认为漏洞的特征：**
1. 使用 `RAGChain` 或 `RetrievalQA` 但未验证检索的文档内容
2. 从数据库或 API 检索数据直接用于提示词，无清理
3. 用户可以通过某种方式污染检索数据源（如上传文件、编辑数据库）
4. 多用户环境中，检索数据可能包含其他用户的敏感信息
5. 向量数据库（如 Pinecone、Weaviate）的训练数据来自未验证的来源

**误报场景：**
1. 检索数据完全来自可信来源（如官方文档、配置文件）
2. 使用了明确的访问控制，用户只能检索自己的数据
3. 检索数据经过内容审查和格式验证
4. 向量存储中的数据定期审计和更新
5. 使用了内容过滤工具检查检索结果

**代码异味（需要深入审查）**
1. 数据加载逻辑复杂或多步骤
2. 条件性地包含或排除检索结果
3. 用户权限检查在检索后而非检索前
4. 缓存机制实现不清晰

## Low risk

**评级为低风险的场景：**
1. 检索数据完全来自可信内部源（如官方文档），无用户贡献
2. 使用了严格的访问控制和数据隔离
3. 检索结果经过内容审查（关键词、格式、大小）
4. 应用有充分的日志记录可以审计所有检索和注入
5. 使用了专门的内容审查 API（如 OpenAI moderation）
