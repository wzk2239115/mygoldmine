# **Go LLM Token Quota No Limit**

当 Go 应用调用 LLM API 时，未对每个用户或全局的 Token 用量进行限制，攻击者可以耗尽配额导致拒绝服务或高额费用。

## Details

**代码示例位置识别技巧（L1: 关键词扫描）**
- 搜索 API 调用：`CreateChatCompletion()`、`CreateCompletion()`
- 查找令牌计数：缺失的 `token counting`、`num_tokens`
- 搜索配额检查：缺失的 `if tokens > limit`
- 查找速率限制：`time.Sleep()`、`rate.Limiter`、`Ticker`
- 定位成本监控：缺失的 `costPerRequest`

**核心操作保护机制（L2: 跳读）**
- 检查是否计算了请求的 token 数量
- 验证是否有用户级别的配额限制
- 查看是否有全局配额
- 检查是否有速率限制
- 查看是否监控成本

**快速定位到具体漏洞（L3: 逐行读）**
- 追踪 API 调用前的配额检查
- 检查计数逻辑
- 审查限制实施
- 查看错误处理
- 检查日志记录

**数据流追踪（L4: 跨模块追踪）**
- 追踪配额的管理
- 检查所有 API 调用点

## Classify

**确认为漏洞的特征：**
1. 无配额限制
2. 无令牌计数
3. 允许任意大小的输入
4. 无速率限制
5. 无成本监控

**误报场景：**
1. 设置了配额限制
2. 有令牌计数检查
3. 有速率限制
4. 有成本监控
5. 输入大小限制

**代码异味（需要深入审查）**
1. 无限制的 API 调用
2. 多个计数点
3. 条件性限制
4. 缺少监控

## Low risk

**评级为低风险的场景：**
1. 设置了合理的配额限制
2. 有令牌计数和检查
3. 有速率限制
4. 有成本监控
5. 输入大小限制
