# **NodeJS LLM Parameter Tampering**

当 Node.js 应用接受用户对 LLM 调用参数（如 temperature、top_p、system prompt）的修改请求，而未进行适当验证时，攻者可以篡改参数控制模型行为，绕过安全约束或诱导生成恶意内容。

## Details

**代码示例位置识别技巧（L1: 关键词扫描）**
- 搜索 LLM 参数：`temperature`、`top_p`、`max_tokens`、`system_prompt`、`model_name`
- 查找参数来源：`req.body.temperature`、`req.query.model`、`params.instruction`
- 搜索参数验证：缺失的范围检查、类型检查
- 查找默认值覆盖：`user_system_prompt = req.body.system || default`
- 定位参数使用：`openai.ChatCompletion.create(params)`

**核心操作保护机制（L2: 跳读）**
- 检查是否对所有可修改的参数进行了验证
- 验证是否有参数值的白名单或范围限制
- 查看是否允许覆盖系统提示或基础指令
- 检查是否有参数修改的权限检查
- 查看是否记录了参数修改

**快速定位到具体漏洞（L3: 逐行读）**
- 追踪参数从请求到 LLM 调用的路径
- 检查每个参数的验证逻辑
- 审查是否有类型强制或转换
- 查看是否有条件分支导致验证被绕过
- 检查错误处理中是否暴露了默认参数

**数据流追踪（L4: 跨模块追踪）**
- 追踪参数的设置和验证
- 检查是否有多个参数修改点
- 验证日志记录

## Classify

**确认为漏洞的特征：**
1. 允许用户直接修改 temperature、top_p 等参数
2. 允许覆盖或修改系统提示
3. 未验证参数值的类型和范围
4. 参数可以设置到极端值（temperature = 100）
5. 可以切换到不同的模型或配置

**误报场景：**
1. 参数有严格的白名单或范围限制
2. 系统提示不能被用户修改，仅由应用定义
3. 重要参数有权限检查
4. 参数值经过验证和转义
5. 参数修改有日志记录和审计

**代码异味（需要深入审查）**
1. 直接使用用户输入作为参数
2. 多个地方修改相同的参数
3. 条件性地验证参数
4. 缺少参数的上限检查

## Low risk

**评级为低风险的场景：**
1. 重要参数有白名单限制，用户只能选择预定义的值
2. 参数值有严格的范围限制（如 0.0-2.0 for temperature）
3. 系统提示由应用定义，用户无法修改
4. 模型选择有白名单
5. 参数修改有权限检查和审计日志
