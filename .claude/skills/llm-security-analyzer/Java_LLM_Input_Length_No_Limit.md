# **Java LLM Input Length No Limit**

当 Java 应用接收 LLM 请求时，未限制输入大小，攻击者可以发送超大输入导致内存耗尽、处理超时或拒绝服务。

## Details

**代码示例位置识别技巧（L1: 关键词扫描）**
- 搜索输入接收：`request.getParameter()`、`@RequestBody String`、`readString()`
- 查找大小检查：缺失的 `length()` 检查、`MAX_LENGTH` 常量
- 搜索内存分配：`new char[size]`、`BufferedReader`、`ByteArrayOutputStream`
- 查找文件上传限制：缺失的 multipart 大小限制
- 定位流读取：`read()`、`readLine()` 无大小限制

**核心操作保护机制（L2: 跳读）**
- 检查是否设置了最大输入大小
- 验证是否在处理前进行了大小检查
- 查看是否有 multipart 上传大小限制
- 检查是否有内存使用监控
- 查看超时设置

**快速定位到具体漏洞（L3: 逐行读）**
- 追踪输入接收的所有点
- 检查大小验证逻辑
- 审查异常处理
- 查看是否有边界条件检查
- 检查错误消息

**数据流追踪（L4: 跨模块追踪）**
- 追踪输入的完整处理链
- 检查所有接收点

## Classify

**确认为漏洞的特征：**
1. 无最大输入大小限制
2. 直接读取用户输入到内存
3. 无 multipart 大小限制
4. 整个请求体加载到内存
5. 可以导致内存耗尽或超时

**误报场景：**
1. 设置了合理的最大输入大小（如 10MB）
2. 在接收前检查大小
3. multipart 上传有大小限制
4. 使用流式处理大数据
5. 有内存监控和限制

**代码异味（需要深入审查）**
1. 无大小检查的读取操作
2. 整个请求体加载到内存
3. 无 multipart 配置
4. 缺少错误处理

## Low risk

**评级为低风险的场景：**
1. 设置了合理的最大输入大小（如 1-10MB）
2. 在处理前进行大小检查
3. multipart 有大小限制配置
4. 使用流式处理避免全部加载到内存
5. 有超时和内存限制
