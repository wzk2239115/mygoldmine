# **Python LLM Logic Bypass**

当 LLM 的输出被用于控制应用流程逻辑（如条件判断、权限决策、业务规则），攻击者可以通过精心设计的提示注入或污染训练数据，使模型生成符合攻击目标的输出，绕过应用的业务逻辑和安全检查。

## Details

**代码示例位置识别技巧（L1: 关键词扫描）**
- 搜索 LLM 输出用于条件判断：`if response in ["yes", "approve"]`、`if decision == "allow"`
- 查找业务规则检查：`is_approved`、`can_access`、`should_execute`、`validate_business_logic()`
- 搜索状态机转移：`current_state = response`、`workflow.transition(decision)`
- 查找权限决策：`permission = model_output`、`role = response.split()[0]`
- 定位输出解析：`json.loads(response)`、`response.strip()`、`response.lower()`

**核心操作保护机制（L2: 跳读）**
- 检查 LLM 输出是否作为最终的授权/审批决策
- 验证是否有独立的逻辑验证层
- 查看是否对 LLM 的决策进行了二次确认
- 检查是否有审计日志记录关键的业务决策
- 查看是否存在人类审核步骤

**快速定位到具体漏洞（L3: 逐行读）**
- 追踪 LLM 输出到业务逻辑的使用方式
- 检查是否有其他因素影响最终决策
- 审查决策的可逆性和可审计性
- 查看异常情况的处理
- 检查是否有明确的拒绝/错误处理

**数据流追踪（L4: 跨模块追踪）**
- 追踪业务决策流程中的所有输入来源
- 检查 LLM 输出是否是唯一的决策来源
- 验证权限检查是否独立于 LLM 输出

## Classify

**确认为漏洞的特征：**
1. LLM 的单一输出直接用于审批、授权或高风险操作
2. 应用依赖 LLM 输出进行访问控制决策
3. 业务规则由 LLM 解释和执行，无独立验证
4. 没有人类审核步骤，完全自动化决策
5. 输出解析简单且易被欺骗（如简单的字符串匹配）

**误报场景：**
1. LLM 仅用于建议或信息提供，最终决策由用户或系统独立做出
2. 有明确的人类审核步骤，在执行前由授权人员确认
3. 业务逻辑由独立的规则引擎管理，LLM 仅提供建议
4. 高风险操作有额外的验证层（多因素认证、二次确认）
5. 访问控制基于用户身份和权限，而非 LLM 输出

**代码异味（需要深入审查）**
1. 复杂的 LLM 输出解析逻辑
2. 条件判断包含多个相关的 LLM 输出
3. 业务规则在 LLM 提示中定义而非代码中
4. 缺乏决策的审计跟踪

## Low risk

**评级为低风险的场景：**
1. LLM 仅用于信息提供或建议，最终决策由用户手动确认
2. 实现了人类审核机制，所有关键决策需要授权人员批准
3. 高风险操作有明确的验证流程（如付款需要密码或 2FA）
4. 访问控制基于用户身份和权限系统，与 LLM 输出完全分离
5. 有完整的审计日志，所有决策可追溯
