# Vyper 闪电贷回调重入漏洞

**漏洞类型：** 回调重入  
**影响范围：** 采用 Vyper 编写的 DEX、借贷协议、收益聚合器  
**核心成因：** 闪电贷回调函数中状态未锁定，允许回调期间再次进入借贷函数

## Details

**代码示例模式：**

```python
@external
def flash_loan(token: address, amount: uint256, callback_target: address):
    # 借出代币
    ERC20(token).transfer(callback_target, amount)
    
    # 危险：调用外部合约回调，此时状态未保护
    raw_call(callback_target, method_id("onFlashLoan(address,uint256)"), ...)
    
    # 检查归还
    assert ERC20(token).balanceOf(self) >= self.initial_balance + fee
```

**快速定位核心操作技巧（L3-逐行读）：**
1. 搜索 `flash_loan`、`flash_borrow`、`execute_callback` 等函数名
2. 定位 `raw_call`、`send()`、外部合约调用点
3. 检查调用前是否修改了 `self.balance`、`self.debt`、`self.locked` 等状态变量
4. 追踪状态变量在回调前后的读写顺序（先写后读=安全，先读后写=危险）
5. 关注是否存在 `self.callback_depth` 或重入计数器

**快速定位保护机制技巧（L2-跳读）：**
1. **L1-关键词扫描**：全局搜索 `@nonreentrant` 装饰器、`locked: public(bool)` 状态变量
2. **L2-跳读**：检查函数开头是否有 `assert not self.locked` 或 `self.locked = True`
3. **L3-逐行读**：验证关键状态变量（余额、债务）在外部调用**前**是否已固化到局部变量或映射
4. **L4-跨模块追踪**：若回调目标可控，需追踪该地址是否来自白名单或可信注册表
5. **关键判断**：若状态变量在 `raw_call` 后才更新，且无锁机制，则存在重入风险

## Classify

### 确认为真实漏洞的条件（审计经验总结）

**需同时满足的三个必要条件：**

1. **技术可行性**：
   - 回调期间未使用 `@nonreentrant` 或手动锁机制
   - 关键状态变量（余额、债务、借贷状态）在外部调用**后**更新，而非之前
   - 攻击者可通过回调再次进入同一或其他函数

2. **经济可行性**：
   - 单次重入能窃取的价值 > gas成本 + 链手续费
   - 协议没有滑点损耗、赎回延迟或价格防护机制限制利润

3. **可控性**：
   - 回调目标由用户指定或可被间接控制（如通过代理、委托调用）
   - 没有严格的地址白名单验证

**真实案例警示（2023-2024）：**
- **Aave V3**：原型中闪电贷回调未完全锁定，但通过状态快照在回调前固化关键数据，降低风险
- **dYdX V3**：采用账户隔离机制，每个账户独立追踪债务，跨账户重入无利可图
- **Uniswap V3**：回调中池子状态已通过 `locked` 位域完全冻结，经验证为安全

---

### 判定为误报的情况（常见场景）

**高置信度误报（不存在真实利用路径）：**

1. **完整的原子操作设计**
   - 错误识别：函数看似先转账再检查
   - 实际情况：转账前已通过 `transfer()` 的返回值验证，或使用 `safeTransfer()` 确保原子性
   - 审查方法：追踪 `ERC20.transfer()` 调用的返回值处理

   ```python
   # 误报示例（实际安全）
   success: bool = ERC20(token).transfer(user, amount)
   assert success  # 立即检查，重入无机会修改此后余额
   ```

2. **充分的状态快照保护**
   - 错误识别：看到外部调用就警报
   - 实际情况：外部调用**前**已将所有关键状态保存到局部变量
   - 审查方法：检查是否存在如下模式：

   ```python
   balance_before: uint256 = ERC20(token).balanceOf(self)
   # 外部调用
   raw_call(callback, ...)
   # 检查基于 balance_before，而非 balanceOf(self)
   assert ERC20(token).balanceOf(self) >= balance_before + fee
   ```

3. **高效的白名单保护**
   - 错误识别：看不到地址检查就认为无保护
   - 实际情况：回调目标来自可信注册表或多签白名单
   - 审查方法：向上追踪 `callback_target` 的来源，验证是否经过 `assert self.whitelist[target]` 检查

4. **跨合约状态隔离**
   - 错误识别：一个合约内存在多个借贷映射
   - 实际情况：每个用户账户独立追踪，重入同一用户会因余额不足而失败
   - 审查方法：检查是否存在 `user_debt[msg.sender]` 这类映射，重入同用户时会被余额限制卡死

---

### 中风险的代码异味（需进一步深度审查）

**常见的"不够坏，也不够好"的设计：**

- **使用手动锁但异常处理不完善**：`self.locked = True` 后若外部调用 revert，锁永不释放
  - 修复验证：是否使用 `try-except` 或确保调用不会 revert

- **跨函数重入风险**：`flash_loan()` 有保护但 `flash_loan_to()` 没有保护，且两者操作同一资金池
  - 修复验证：全局搜索涉及同一 token 余额的所有外部调用函数

- **回调深度限制过高**：`if self.callback_depth > 10` 才拒绝
  - 风险评估：在 10 层深度内是否足以构造套利链条，计算 gas 成本是否可行

- **仅锁定单个函数**：`flash_loan()` 被锁但 `emergency_withdraw()` 可在回调期间绕过
  - 审查方法：找出所有修改相同状态变量的函数，验证都被同一个锁保护

---

### 审计实战技巧总结

**"五步确认法"（从疑似漏洞到确定判断）：**

1. **第一步**：找到外部调用点（`raw_call` / `send()` / `.transfer()`）
2. **第二步**：向前追溯，确认此前是否修改了关键状态变量（如 `self.loans[id] = 0`）
3. **第三步**：向后检查，外部调用后是否还有对该变量的读取或验证
4. **第四步**：评估经济可行性，攻击收益是否超过重入所需 gas（通常 > 5 次调用需 > 200k gas）
5. **第五步**：验证入口控制，是否真的可以用户指定回调目标，还是固定为某个合约

**常见的审计误判点：**

| 现象 | 误判结论 | 正确判断 | 验证方法 |
|------|--------|--------|--------|
| `raw_call()` 在转账后 | 一定有重入 | 需检查是否有快照保护 | 查看调用后是否基于局部变量 |
| 没有 `@nonreentrant` | 不安全 | 需检查是否有手动锁 + 状态隔离 | 搜索 `self.locked` + 追踪用户隔离 |
| 回调可自定义 | 必然漏洞 | 需评估是否经济可行 | 计算最深重入 gas + 协议滑点 |
| 多年无事故 | 可能设计有隐患 | 已验证安全，但仍需文档化保护 | 代码审查 + 形式化验证 |

## Low risk

**以下情况可评为低风险：**
1. **金额受限**：单笔闪电贷上限极低（如 < $10k），且协议总锁仓量小，攻击收益不足以覆盖 gas 成本
2. **时间锁保护**：关键状态变更需等待多个区块确认，重入攻击无法在单笔交易内完成套利
3. **经济不可行**：即使重入成功，由于手续费机制、滑点损耗或价格影响，攻击者实际获利为负
4. **只读回调**：回调函数仅触发事件或查询操作，不涉及状态变更或资金转移
5. **链上环境限制**：部署在 gas 成本极高的链上，多次重入调用成本超过可窃取价值
6. **已部署合约历史**：合约已运行多年无事故，且回调目标始终为官方控制的单一合约地址

**注意：** 即使评为低风险，仍应在报告中标注该模式，建议在未来版本中修复
