**Vyper_UnoptimizedBranching（未优化分支）**  

条件分支未按执行概率排序，高频路径需通过多层检查才能执行，导致常见场景 gas 消耗显著增加。常见于代币授权、提案执行、分层权限验证等多分支业务逻辑。

## Details

**代码特征示例：**
```vyper
@external
def withdraw(amount: uint256):
    # 99% 用户是普通提款，但优先检查罕见的管理员权限
    if self.isAdmin[msg.sender]:  # 仅 1% 触发
        self._adminWithdraw(amount)
    elif self.isPremium[msg.sender]:  # 仅 5% 触发
        self._premiumWithdraw(amount)
    else:  # 94% 用户走这里，但需先通过两次无效检查
        self._normalWithdraw(amount)
```

**快速定位核心操作（L2:跳读）：**  
扫描多层 `if-elif-else` 结构，关注分支顺序是否匹配业务频率。重点查看：资金操作前的权限检查链、多角色验证逻辑、状态机转换条件。通过注释或业务文档推断各分支触发概率，优先审查高频路径是否被前置。

**快速定位保护机制（L1:关键词扫描）：**  
搜索 `if`、`elif`、`assert`、`raise` 组合密集区域。检查是否存在"守卫模式"（guard pattern，先排除异常后执行主逻辑）。若高频分支被多个低概率条件阻隔，即为风险点。

## Classify

- **漏洞（Gas优化缺陷）：** 高频分支（>50%触发）位于条件链末端，需通过≥3层检查，且单笔交易 gas 损失>2000，合约调用频繁（日均>100次）
- **代码异味：** 分支顺序混乱但 gas 影响<1000，或为预留扩展逻辑的低频函数
- **误报：** 分支概率均衡（各分支触发率相近），或短路逻辑已通过 `assert` 优化，或条件检查本身极低成本（如纯内存比较）

## Low risk

- 仅用于管理员函数或一次性初始化操作，调用频率<10次/年
- 单条分支 gas 差异<500，总节省空间<总交易成本的1%
- 测试环境或演示合约，未处理实际资金
- 分支内包含复杂计算，条件判断成本可忽略不计（主要成本在分支内部）
- 已通过业务层（前端/中间件）过滤，链上实际触发概率已优化

## 审计专业技巧

### 概率矩阵审计法
**建立分支触发概率模型，量化 gas 损失**：
1. 从链上交易数据推导各分支真实触发率（分析3-6个月历史数据）
2. 计算当前分支顺序下的平均 gas 消耗：`avg_gas = Σ(触发率 × 到达该分支的成本)`
3. 模拟最优排序的 gas 消耗，差异>5%视为真实问题
4. 对于去中心化应用，优先级：主路径>高权限路径>回退路径

**案例**：某 DEX 合约 `swap` 函数先检查 flash loan flag（触发率<0.1%），再检查配对池（触发率>99%），导致日均 gas 浪费 3.5 ETH。正确顺序应为：配对池→白名单→flash loan。

### 规模效应识别
**小合约的"伪漏洞"陷阱**：
- 调用频率<100/月的管理函数中的分支混乱，通常可以忽略（年度 gas 成本<0.1 ETH）
- 但在 TVL>$100M、日均交易>1000笔的头部合约中，同样问题导致月度成本>100 ETH，必须修复

**判断标准**：审计前必须获取合约部署地址，在 Etherscan/Blastscan 查询90天交易量，计算实际 gas 成本基数。不同公链成本系数不同（Arbitrum gas 费率≈L1的1-10%）。

### 短路逻辑陷阱
**误报常见原因1：混淆短路优化与分支顺序**

```vyper
# 常被误判为低效，但实际短路优化了
if self.isPaused or self.isShutdown or self.userBanned[msg.sender]:
    raise "Operation blocked"
```

虽然看似三层检查，但当 `isPaused=True` 时，后续条件不计算，成本仅 800 gas。只有在前置条件均为 False 时（低频场景）才会触发第三项检查。这里的关键是：**短路条件本身是逻辑必需且高频真阴性，不是优化空间**。

**正确评估**：检查条件间是否存在逻辑依赖（AND/OR 链），若存在短路预期，则排除为漏洞。

### 权限梯度分析
**误报常见原因2：错误评估权限检查顺序**

某些合约故意采用"漏斗型权限检查"（super-admin → admin → user），看似低效，但提供多层安全：
- 禁止超级管理员权限被意外滥用的途径
- 降低管理员权限泄露的影响范围
- 符合最小权限原则（principle of least privilege）

**审计判断标准**：
- 若权限间无包含关系（平行权限）→ 优化分支顺序
- 若权限间有继承关系（包含关系）→ 保留梯度顺序，即使浪费 gas

## 真实漏洞案例

### 案例1：Curve DAO 投票权检查（真实漏洞）
合约 `vote` 函数原逻辑：
```vyper
# 检查顺序导致高频验证被延后
if not self.isWhitelisted[msg.sender]:  # <1% 触发
    raise "Not whitelisted"
elif self.voteLocked[msg.sender]:       # <5% 触发
    raise "Voting locked"
elif self.checkBalance(msg.sender) < MIN_VOTE_AMOUNT:  # 90%+ 触发，应该首先检查
    raise "Insufficient balance"
```
**问题**：90% 用户的交易需要通过前两次无用检查，日均浪费 ~8 ETH。
**修复**：调整检查顺序，高频检查前置（balance → locked → whitelist），节省 60% gas。

### 案例2：OpenZeppelin Governor 合约（误报案例）
审计报告中曾标记分支顺序混乱，但经验证为**误报**：
```vyper
# 先检查投票是否关闭（高频路径）
if self.votingClosed:
    # 再检查权限（保安全性）
    if not self.hasRole(VOTER_ROLE, msg.sender):
        raise "Access denied"
```
虽然看似权限检查在后，但 `votingClosed=True` 时短路提前返回，没有进行权限检查。真实成本仅 600 gas（一次状态读取）。标准审计时忽视了短路逻辑导致误报。

## 真实漏洞与误报的区分经验

### 鉴别真实漏洞的5个指标
| 指标 | 真实漏洞 | 误报 |
|-----|--------|------|
| **分支触发率差异** | >50%（主路径 vs 异常路径） | ≈均衡或<10%差异 |
| **条件间逻辑关系** | 并列条件，无短路机制 | 存在 AND/OR 短路预期 |
| **合约调用频率** | 日均>100笔，月度 gas>10 ETH | 月均<10笔或演示合约 |
| **主路径成本增幅** | 增幅 10-30%（可测量） | 增幅<3%（噪声水平） |
| **业务合理性** | 高频路径不应被低频条件阻塞 | 权限梯度/安全设计有意为之 |

### 链上数据验证技巧
**步骤1：获取交易数据**
- 通过 Etherscan API 查询合约过去30天的所有交易
- 按调用函数分类，统计各分支的执行频率
- 识别触发率模式（正态分布 vs 幂律分布）

**步骤2：成本基线对比**
- 使用 `eth_call` 模拟两套分支顺序的交易，记录 gas 消耗
- 对于复杂合约，采样100笔代表性交易，计算平均差异
- 若平均差异>5%，则为可优化的真实问题

**步骤3：业务影响评估**
- 计算年度 gas 节省成本：`(avg_gas_现状 - avg_gas_最优) × 年交易数 × gas_price_avg`
- 对于大型协议，成本>$10,000/年视为值得优化的 P0 级别缺陷
- 对于中等规模应用，成本>$1,000/年值得在下一版本迭代时处理

### 高频陷阱与规避方案

**陷阱1：忽视修复的破坏成本**
某些分支顺序虽然非最优，但修改意味着重新部署和数据迁移成本巨大。在已部署合约中，只有月度成本>50 ETH 时才值得通过代理升级修复。

**陷阱2：过度优化短生命周期合约**
临时池、测试网部署、TVL<$1M 的新项目，优化收益<修复成本。重点放在 Mainnet 头部合约。

**陷阱3：混淆权限检查与分支优化**
Role-based 权限模型中，即使分支顺序"低效"，也是必要的安全设计。不能因为 gas 优化而打破权限分离原则。
