**Move** (e.g., Sui, Aptos)  
常出现在资源绑定型经济模型、动态费率调整、资产铸造配额等业务逻辑实现中，包括但不限于资源销毁与增发不对称、费率随外部预言机价格跳变无缓冲、权限控制缺失导致经济参数被任意修改等方式：  
- 资产铸造销毁不对称：代币铸造和销毁机制不平衡，导致供应量单向变化破坏经济模型，详见：Move_AssetMintBurnAsymmetry.md  
在区块链领域，专注于这一垂直漏洞类型研判任务，从漏洞成因触发，编写该md文件，包含一下三个小标题，【注意语言精炼，表达简洁，可以作为审计小抄，仅专注于审计，不包含攻击与修复】：

## Details

**代码示例特征：**
```move
// 典型不对称场景：铸造权限分散，销毁权限缺失
public entry fun mint_token(ctx: &mut TxContext, amount: u64) {
    // 仅校验amount > 0，无总量上限、无时间窗口、无销毁配对机制
    let coin = coin::mint(&mut treasury_cap, amount, ctx);
    transfer::public_transfer(coin, tx_context::sender(ctx));
}

// 销毁函数不存在或权限过高（仅admin可调用）
public entry fun burn_token(_: &AdminCap, coin: Coin<TOKEN>) {
    coin::burn(&mut treasury_cap, coin);
}
```

**快速定位核心操作（L2-跳读）：**  
- 搜索关键字：`coin::mint`、`coin::burn`、`TreasuryCap`、`supply::increase_supply`、`supply::decrease_supply`  
- 检查点：铸造函数是否有entry可见性、销毁函数是否存在、两者调用频率是否对称  
- 追踪资源流：从`TreasuryCap`初始化位置向下追踪所有铸造/销毁调用点  

**快速定位保护机制（L3-逐行读）：**  
- 检查铸造是否有cap限制：`assert!(total_supply + amount <= MAX_SUPPLY, E_EXCEED_CAP)`  
- 检查是否有时间锁：`assert!(clock::timestamp_ms(clock) >= last_mint_time + COOLDOWN, E_TOO_FREQUENT)`  
- 检查权限对称性：铸造和销毁的Capability持有者是否一致或互斥  
- 检查经济闭环：是否存在强制销毁场景（如质押赎回、手续费燃烧、清算惩罚）  

## Classify

**真漏洞判定标准：**  
1. 铸造无上限且entry函数可公开调用，销毁函数不存在或仅限管理员  
2. 铸造在多个业务模块分散实现（游戏奖励、质押收益、推荐分红），销毁集中在单一低频场景  
3. 铸造速率可由外部参数无限制放大（如质押倍率、推荐层级），无销毁对冲机制  

**误报识别：**  
1. 系统设计为通缩模型（如手续费销毁代币，无需铸造对等）  
2. 铸造总量在创世时固定，后续仅执行转移操作（TreasuryCap已销毁或冻结）  
3. 不对称是阶段性的（初期铸造为空投，后期仅销毁为回购）且有明确文档说明  

**代码异味（需验证设计意图）：**  
1. 铸造和销毁存在但调用不对称（10:1比例），需结合经济白皮书判断是否符合通胀目标  
2. 销毁函数存在但gas消耗极高或需跨链操作，实际执行概率低  

## Low risk

**满足以下条件可降级为低风险：**
1. **总量硬顶保护**：铸造总量有不可修改的上限（`MAX_SUPPLY`常量 + assert校验），即使不对称也无法无限增发
2. **权限严格受限**：铸造权限由多签/DAO控制，单笔操作需时间锁和社区投票，恶意增发成本极高
3. **经济模型容错**：代币仅用于治理投票或身份标识，供应量波动不影响核心业务（如NFT铸造消耗的是稳定币而非治理代币）
4. **透明度补偿**：所有铸造事件上链可查且有链下监控告警，社区可及时发现异常并通过升级合约修复
5. **有限生命周期**：项目为短期活动（如3个月测试网激励），不对称导致的经济失衡不影响主网资产

## 审计专业技巧

**真实漏洞vs误报的核心区分标准：**

**场景1：无限增发vs受控增发**
- **真漏洞**：`public entry fun mint(amount: u64)` 无任何上限检查，调用方可任意指定amount。测试：调用 `mint(u64::MAX)` 是否被拒绝？若被接受，代币供应量溢出或资金库被掏空
- **误报**：函数虽然是entry但经过多层权限过滤（如Capability模式），或虽无entry修饰符但通过Module内部调用受限。检查TreasuryCap是否仅由多签/DAO模块持有，即使entry函数也无法直接调用burn/mint

**场景2：阶段性不对称vs永久性不对称**
- **真漏洞指标**：铸造和销毁从第一个区块到最新区块的历史比例，若铸造:销毁 > 100:1且呈递增趋势，表明经济模型失衡已成现状，非阶段性
- **误报识别**：项目文档明确声明"前6个月空投期间仅铸造不销毁，第7个月开始启动销毁与回购"。若当前确实处于空投期，不对称是预期设计。需查证里程碑时间戳，确认项目是否已进入销毁阶段

**场景3：外部参数驱动的隐藏增发**
- **真漏洞案例**：质押收益铸造 `mint_reward(stake_amount * boost_factor)`，其中 `boost_factor` 可被Governance升级合约修改无上限。审计需求：验证boost_factor修改是否有上限（如≤10倍）和时间锁（≥7天冷却）。若无，质押者可通过社区治理恶意提升因子导致无限增发
- **验证方法**：检查Governance模块的 `update_boost_factor()` 函数是否存在guard语句，跟踪历史参数变动（需检查事件日志），对比白皮书承诺值

**审计工具链与高效定位方法：**

1. **静态扫描第一步**：用Grep搜索 `supply::increase_supply|coin::mint|TreasuryCap<` 定位所有增发点，统计个数。正常项目通常不超过5个，超过10个需重点审核是否存在隐藏增发
2. **权限链路追踪**：从TreasuryCap定义出发，使用反向引用搜索，梳理所有持有者。绘制权限图谱：`TreasuryCap -> AdminCap -> Governance -> MultisigWallet -> 签名者`。若链路中任何节点可被绕过（如AdminCap可被多次复制），增发权限实际上是去中心化的
3. **事件日志对账**：检查所有mint/burn事件是否都有对应的链上操作。统计过去30天的累计增发量和销毁量，计算净增长率。若净增长 > 5%/月且无对应的通胀目标文档，可判定为异常

**常见误报陷阱与避坑指南：**

- **陷阱1**：误将"销毁权限缺失"判定为漏洞。实际上许多项目（如稳定币）设计为永不销毁，销毁权限缺失反而是符合设计。需查看是否有"burn disable"注释或文档说明
- **陷阱2**：混淆"铸造权限分散"与"增发失控"。Capability模式允许多个模块各自拥有独立的TreasuryCap片段，但单笔操作的上限仍由总量cap控制。应重点审核是否存在独立的 `MAX_SUPPLY` 检查，而非权限个数
- **陷阱3**：过度信任白皮书的通胀曲线承诺。需用 `block_timestamp` 和事件计数核对历史铸造速率是否符合承诺。许多项目前期虚报通胀率，后期通过参数升级绕过承诺

**审计检查清单（5分钟快速判断）：**
1. 搜索 `public entry fun mint`，若存在且无 `assert!(total_supply...)`，直接定性为中危及以上
2. 统计mint函数数量与burn函数数量，若mint >= 3 * burn，需详细审核销毁触发机制
3. 查询TreasuryCap初始化位置，验证是否在合约部署后立即销毁（`drop` 或 `share_object(false)`）
4. 对比链上铸造事件与白皮书的通胀承诺，若月度增速相差>20%，标记为需要沟通的异常
5. 检查AdminCap或MinterCap的转移历史，若曾被转移到外部钱包，该地址成为单点风险
