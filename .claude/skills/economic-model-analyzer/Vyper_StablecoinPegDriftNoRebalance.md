# Vyper - 稳定币锚定漂移无再平衡

**漏洞类型：** 经济模型缺陷 - 稳定币机制失效  
**影响范围：** 稳定币协议、算法稳定币、抵押型稳定币、混合型稳定币  
**严重程度：** High - Critical

## Details

**典型代码特征：**

```vyper
# 典型缺陷示例 - 仅更新价格无再平衡逻辑
@external
def update_price():
    current_price: uint256 = self.oracle.get_price()
    self.last_price = current_price
    # 缺失：无铸币/销毁、无抵押率调整、无激励机制触发
```

**快速定位核心操作技巧（L3:逐行读）：**
- 定位价格获取点：搜索 `oracle`、`get_price`、`chainlink`、`twap`
- 定位铸币/销毁：搜索 `mint`、`burn`、`_mint`、`_burn`、`totalSupply`
- 定位抵押物操作：搜索 `collateral`、`reserve`、`deposit`、`withdraw`
- 定位锚定机制：搜索 `peg`、`rebalance`、`arbitrage`、`stabilize`
- **关键判断**：若价格偏离计算后未触发供给调整或抵押率调整，存在风险

**快速定位保护机制技巧（L4:跨模块追踪）：**
- 自动再平衡检查：搜索 `rebalance`、`auto_adjust`、`stabilization_pool`
- 激励套利机制：搜索 `arbitrage_reward`、`premium`、`discount`、`incentive`
- 断路器/触发条件：搜索 `circuit_breaker`、`threshold`、`deviation_limit`
- 时间延迟保护：搜索 `cooldown`、`min_interval`、`last_rebalance`
- **跨模块追踪要点**：
  - 价格偏离计算 → 再平衡函数调用路径是否完整
  - `update_price` 是否触发 `rebalance` 或发出事件供外部调用
  - 权限检查：`rebalance` 是否依赖治理/时间锁（导致延迟）

## Classify

**漏洞判定标准：**
- ✅ **High/Critical漏洞**：价格偏离 >3-5% 无自动/可及时触发的再平衡机制，且无外部套利激励足以恢复锚定
- ✅ **Medium漏洞**：存在再平衡机制但需治理投票/多签触发，响应延迟 >24小时
- ⚠️ **代码异味**：再平衡机制存在但参数不合理（如阈值过大 >10%、冷却时间过长 >7天）

**误报识别：**
- 协议依赖外部套利者（需验证：激励是否充足、Gas成本是否可负担、流动性是否充足）
- 使用储备金/稳定池缓冲（需验证：储备金规模与流通量比例、耗尽速度）
- 设计为软锚定（需验证：文档明确说明、用户认知一致、风险充分披露）

**跨链关联风险：**
- Vyper稳定币协议常与 Curve、Convex 集成，需检查外部协议依赖的锚定假设

## Low risk

**降级为低风险的条件：**
1. **偏离阈值小**：设计锚定范围 ±1-2% 内，短期偏离不触发再平衡属正常波动
2. **超额抵押充足**：抵押率 >200%，即使脱锚仍可保证兑付（但需注意抵押物价格相关性）
3. **流动性深度充足**：DEX流动性 >10倍日交易量，套利者可自发恢复锚定
4. **明确的手动再平衡SOP**：文档证明24小时内可完成治理干预，且历史记录良好
5. **测试网/实验性协议**：TVL <$100k 且明确标注实验性质

**关键验证点：**
- 历史脱锚事件的恢复时间与最大偏离幅度
- Gas价格波动时套利可行性（MEV竞争、Gas成本侵蚀利润）
- 抵押物流动性危机情况下的系统韧性

## 审计专业技巧

### 核心审计流程（5步递进）

**第1步：模型假设梳理**
- 明确协议的锚定目标（Hard Peg $1.00 vs. Soft Peg ±2%）
- 确认再平衡触发机制类型：
  - 自动化（Oracle触发 + 智能合约自执行）
  - 半自动化（外部调用 + 链上验证）
  - 手动（治理投票触发）
- 记录所有假设前置条件（如：套利流动性充足、抵押物可清算性强）

**第2步：代码路径完整性验证**
关键追踪路径：`Price Detection` → `Deviation Calculation` → `Trigger Evaluation` → `Rebalance Execution`

```vyper
# 完整的再平衡路径示例
@external
def update_price():
    new_price = self.oracle.get_price()
    deviation = abs(new_price - self.target_price) / self.target_price

    # 关键：这里必须有触发后续操作的逻辑
    if deviation > self.rebalance_threshold:
        log PriceDeviation(deviation, new_price)
        # 方式1：直接触发（需检查权限）
        self._trigger_rebalance()
        # 方式2：发事件供外部监听（需验证监听可靠性）
        # 方式3：修改状态供自动化脚本调用（需检查调用时效性）
```

**第3步：参数合理性量化分析**
- **脱锚阈值审查**：
  - `<1%`：过度敏感，频繁触发，Gas成本高
  - `3-5%`：常见合理范围（Curve.fi采用≈2%）
  - `>10%`：风险过大，用户已承受显著脱锚风险
- **冷却时间审查**：
  - `<1分钟`：容易被MEV利用或闪电贷攻击
  - `1小时-1天`：适度保护，但脱锚期间用户暴露风险
  - `>1周`：严重延迟，实际无保护
- **抵押率下限审查**：
  - 计算清算触发时是否仍可偿债
  - 验证清算价格下滑幅度（-20% 至 -50%）的覆盖情况

**第4步：失败场景压力测试**
- **Oracle故障场景**：
  - 若 `get_price()` 返回过期数据、零值或异常，协议行为
  - 是否存在 fallback 机制（如：使用历史价格、多源average）
  - Chainlink 故障率统计（2023年Arbitrum故障2小时，影响依赖方）

- **流动性枯竭场景**：
  - 主流动性池（如Curve）若流动性跌至日交易量1倍，套利成本激增
  - 检查是否有 DEX 集中在单一交易对
  - 验证跨链桥接流动性支持（如 USDC.e on Arbitrum）

- **抵押物危机场景**：
  - 若抵押物（如 ETH）跌幅 >40%，清算是否足够清理风险头寸
  - 是否存在 bad debt（抵押不足但未清算）的积累机制

### 真实漏洞 vs. 误报的区分经验

**案例1：Vyper稳定币价格更新无再平衡（真实漏洞）**

```vyper
# 漏洞代码（2023年某DeFi协议）
@external
def price_feed_callback(new_price: uint256):
    """外部Oracle回调，仅更新价格存储"""
    self.current_price = new_price
    # ❌ 缺失：无任何再平衡逻辑或事件发出
    # ❌ 缺失：无权限检查（前提已有）
    # 结果：USDT对标货币从 $1.00 跌至 $0.92，维持48小时，用户大量赎回亏损
```

**问题诊断**：
- 审计师若仅看到"价格更新"，可能误判为"设计为外部套利模式"
- 深度审计应追踪：
  - 是否存在向外部系统广播偏离信号的机制（如：事件日志）
  - 是否有合约外的监听脚本/机器人部署（需查询Etherscan上的call pattern）
  - 若无任何触发机制，判定为 **Critical 漏洞**

**案例2：带再平衡的协议被误判为漏洞（误报）**

```vyper
# 正常代码（Maker DAO 类似逻辑简化）
@external
def update_price():
    new_price = self.oracle.get_price()
    if abs(new_price - self.peg_price) / self.peg_price > 0.03:
        self.emit Trigger(new_price)
        # ✅ 明确说明文档：外部keeper bot 监听Trigger事件，15秒内调用 rebalance()

@external
def rebalance():
    """由Keeper Bot在Trigger事件触发后调用"""
    require msg.sender in self.approved_keepers
    # 实际调整供给或抵押率
    self._adjust_supply()
```

**误报原因识别**：
- 审计师看到"无自动执行"就标记为漏洞
- 实际上这是 **意图设计**：保持去中心化（非单一owner控制）+ 给keeper经济激励
- 需验证的真实风险：
  - ✅ Keeper 激励是否充足（修复脱锚的利润 > Gas成本）
  - ✅ 是否存在备用Keeper（单点故障风险）
  - ✅ 历史数据：脱锚事件平均修复时间是否可接受（<1小时为佳）

### 高频误报类型及规避方法

| 误报类型 | 审计师常见错判 | 正确验证方法 |
|---------|--------------|----------|
| **设计为软锚定** | 看到 ±5% 容差就判负面 | 查阅设计文档、官网说明、用户风险披露 |
| **Keeper模式** | 认为非自动=无保护 | 检查Keeper激励经济学、历史执行频率 |
| **多链流动性支持** | 单链脱锚就判漏洞 | 验证跨链桥接容量、兑付流动性分布 |
| **二层隔离设计** | 混淆L2 settlement 延迟为脱锚 | 区分：锚定失效 vs. 结算延迟（两者风险不同） |
| **治理应急机制** | 认为投票延迟=无保护 | 查证应急权限角色、历史响应速度、时间锁参数 |

### 审计检查清单（实战版）

```
□ 1. 锚定机制
  □ 1.1 明确记录设计目标（Hard/Soft Peg）
  □ 1.2 列出所有价格输入源（Oracle、流动性池、feed）
  □ 1.3 验证价格偏离计算逻辑正确性（除以零、溢出检查）

□ 2. 再平衡触发
  □ 2.1 追踪触发条件完整路径（代码 + 文档 + off-chain机制）
  □ 2.2 确认触发延迟是否在可接受范围（SLA）
  □ 2.3 检查是否存在触发条件被绕过的漏洞（权限、时间戳操纵）

□ 3. 保护机制充分性
  □ 3.1 验证超额抵押率计算（包括清算风险）
  □ 3.2 检查流动性深度（DEX / 稳定池规模）
  □ 3.3 评估外部依赖的健壮性（Oracle、Bridge、Keeper）

□ 4. 历史数据验证
  □ 4.1 收集历史脱锚事件（时长、幅度）
  □ 4.2 分析修复耗时与成本（Gas、滑点）
  □ 4.3 识别是否存在系统性故障模式
```

### 常见审计陷阱及应对

**陷阱1：仅读Smart Contract 代码，忽视off-chain 系统**
- DeFi稳定币通常依赖keeper、oracle、跨链桥等外部系统
- 应对：要求团队提供架构图、keeper脚本、oracle配置，进行综合评估

**陷阱2：混淆"脱锚风险"与"保本风险"**
- 脱锚≠破产：协议可能脱锚但用户资金安全（超额抵押）
- 破产=永久损失：无法恢复到$1.00且抵押不足
- 应对：明确区分两个风险维度，分别评级

**陷阱3：参数审查不深入**
- 常见：看到 `rebalance_threshold = 0.05` 就说"5%太高"
- 实际：需对标同类协议（Curve 2-3%、MakerDAO 5%）、考虑Gas成本与交易频度平衡
- 应对：建立参数基准库，比对历史案例
