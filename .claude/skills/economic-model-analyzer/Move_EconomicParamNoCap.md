# Move_EconomicParamNoCap

**漏洞类型**：经济参数无上限  
**影响范围**：Move生态（Sui、Aptos等）资源绑定型经济模型、动态费率调整、资产铸造配额  
**核心风险**：关键经济参数（通胀率、手续费、铸造上限）可被设置为任意值，缺乏合理边界验证

---

## Details

**典型代码模式**：
```move
public entry fun set_inflation_rate(admin: &signer, new_rate: u64) acquires Config {
    assert!(signer::address_of(admin) == @admin, E_NOT_ADMIN);
    let config = borrow_global_mut<Config>(@protocol);
    config.inflation_rate = new_rate;  // 直接赋值，无上限检查
}

public entry fun update_fee_rate(cap: &AdminCap, rate: u64) {
    // 缺失: assert!(rate <= MAX_FEE_RATE, E_RATE_TOO_HIGH);
    global_config.fee_rate = rate;
}
```

**快速定位核心操作** [审计等级: **L1 - L2**]：
- **L1关键词扫描**：搜索 `inflation`、`fee_rate`、`mint_cap`、`tax_rate`、`reward_multiplier`、`burn_ratio`
- **L2跳读验证**：锁定赋值语句（`=`、`set_`、`update_` 函数），检查赋值前是否有边界检查逻辑（`assert!`、`<`、`>`）

**快速定位保护机制** [审计等级: **L2 - L3**]：
- **L2跳读检查**：在参数更新函数开头寻找常量定义（`const MAX_*`、`const MIN_*`），检查是否存在 `assert!(value <= MAX_LIMIT)`
- **L3逐行审计**：验证边界值合理性（如费率不应超过100%，即10000基点），检查是否存在溢出保护（`value.checked_mul()` vs `value * multiplier`）
- **关键缺陷信号**：参数更新仅验证权限（`assert_admin`）但无数值范围检查

## Classify

**归类为漏洞**：
- 经济参数直接影响代币供应量、手续费收取、质押奖励计算，且无任何上限检查
- 参数可被设置为极端值导致经济模型崩溃（如通胀率设为u64::MAX，瞬间增发天量代币）
- 缺乏时间锁或多签机制，单一admin可即时生效任意参数

**归类为误报**：
- 参数更新需经过治理投票模块，且投票模块内置范围校验
- 参数虽无显式上限，但在使用侧（计算逻辑）有隐式约束（如计算中会溢出自动revert，但此情况仍应标记为代码异味）
- 参数更新触发事件，配合链外监控可及时干预（注：不应依赖链外措施降级风险等级）

**归类为代码异味**：
- 参数有上限检查，但上限值设置不合理（如手续费上限设为50%）
- 存在软性约束但未强制执行（如文档说明"不应超过X"但代码未校验）
- 更新函数包含TODO注释标记待添加边界检查

## Low risk

**符合以下条件可评为低风险**：
1. **权限足够去中心化**：参数更新需多签（M-of-N，且N>5、M>N/2）或DAO治理（投票周期>7天）
2. **存在冗余防护**：时间锁机制（24小时以上）+ 紧急暂停开关（由独立安全委员会控制）
3. **参数影响范围有限**：仅影响单一非核心功能模块（如推荐奖励系数），不影响主经济循环
4. **历史安全记录**：协议已上线>1年，参数调整记录公开透明，从未出现恶意设置
5. **存在经济学对冲**：其他机制可自动平衡参数影响（如AMM自动调节流动性，但需审计该平衡机制本身是否健壮）

**不应降级为低风险的情况**：
- 声称"管理员可信"作为风险缓解措施（私钥可能泄露或被攻击）
- 依赖链外监控或社区警报系统（无法阻止原子攻击）
- 参数影响核心经济指标（代币总量、质押收益率、协议收入）但未做任何限制

## Audit Techniques

### 1. **参数链路追踪法**（最高优先级）

**核心技巧**：从参数写入点逆向追溯到实际使用点，判断是否存在隐式约束。

**具体步骤**：
```
参数设置函数 → 全局存储读取 → 算术运算逻辑 → 状态更新结果
```

**真实案例分析**：
- **误报场景**：某协议有 `set_multiplier(m: u64)` 无上限检查，但使用侧代码为：
  ```move
  let reward = (base_amount * multiplier) >> 64;
  ```
  若 `multiplier > u64::MAX >> 64`，则自动uint溢出panic。看似有保护，但**这是隐式而非显式的**，应记为"代码异味"而非真实漏洞（除非该revert会导致业务中断）。

- **真实漏洞**：参数用于 `new_supply = total * inflation_rate`，若无上限检查，则可造成代币总供应量爆炸性增长。即使溢出，也可能在另一条链（Sui用dual_writing机制）或在计算完成后的存储前被利用。

**审计技巧**：
- 搜索参数所有read点（使用 `borrow_global`、`get()` 等），统计使用频次和上下文
- 对每个使用点评估：参数值是否直接影响关键状态（供应量、余额、权重）
- 如果参数仅用于日志或事件发射，威胁等级降低

### 2. **对标检查法**（高准确率）

**核心思想**：将目标协议的参数处理与标准实现（Uniswap、Lido等）对标，快速识别偏差。

**对标清单**：
| 经济参数 | 标准做法 | 高风险信号 |
|---------|--------|---------|
| 手续费率 | 常量池内预设，升级需DAO投票 | 单函数可任意修改，无上限 |
| 通胀率 | 内置衰减公式或周期性递减 | 可被设置为固定值，永久生效 |
| 铸造上限 | 累计铸造额追踪+触发上限检查 | 上限本身可被修改 |
| 质押收益 | 预先计算的年化收益表 | 实时计算，无封顶 |

**审计技巧**：参考Sui官方生态（Cetus DEX、Scallop借贷）的参数管理方式，如未实现相同保护机制，需重点关注。

### 3. **权限链路断点检查法**

**核心洞察**：即使参数本身无上限，若更新路径有多个防护，整体风险可被降级。

**检查点**：
1. 参数更新函数是否要求 `AdminCap` 或 `OwnerCap`？（权限验证）
2. `AdminCap` 本身如何铸造和销毁？（防止权限泄露）
3. 是否存在时间锁？（常见于Aptos的Governor模块）
4. 是否需要DAO投票达成共识？（投票涵盖范围检查吗？）

**真实漏洞案例**：某协议的AdminCap可被任意铸造（无supply cap），形成"二级权限漏洞"——参数本身无上限 + 权限无限制，双倍风险。

### 4. **数值边界推演法**（最容易遗漏）

**核心技巧**：不仅检查参数本身的上限，还要推演参数与其他数据的组合效应。

**常见漏洞模式**：
- 单一参数有上限，但多个参数组合无限制
  - 例：`fee_rate <= 10%` 但 `tax_rate` 无限制，两者组合可达100%+
- 参数上限设置过高
  - 例：`inflation_rate <= u64::MAX / 2`，看似有上限但仍允许极端值
- 存在绕过路径
  - 例：主参数更新函数有校验，但存在管理员权限提升函数绕过它

**审计技巧**：绘制参数依赖图，列出所有涉及算术运算的参数组合，对每个组合求极限值。

### 5. **历史版本对比法**（识别故意隐藏的漏洞）

**核心思想**：对比不同版本的源代码，找出被移除的保护机制或参数。

**具体做法**：
- 查看git历史：关键经济参数的上限检查是否被移除过？
- 检查变更日志：是否有"移除过时的参数限制"这类提交？
- 对比测试代码：测试中是否曾设置过参数上限场景？若无，说明可能被故意删除

**真实案例**：某协议早期版本有 `MAX_INFLATION = 50%` 的常量，后续版本中常量被删除，但函数签名未变，形成隐性漏洞。

## 真实漏洞 vs 误报：区分经验

### 真实漏洞的关键特征
1. **参数直接改变代币经济学指标**（供应量、价格、权益分配）
2. **缺乏任何形式的上限**（显式、隐式、时间锁、多签）
3. **可被单一账户瞬间修改且立即生效**
4. **历史上曾被恶意利用或有明确利用路径**

### 误报的常见特征
1. 参数虽无上限但仅影响非关键功能（如日志级别、事件过滤）
2. 参数更新后需等待特定区块确认，给社区反应时间
3. 存在自动触发的风险熔断机制（如余额异常增长自动暂停铸造）
4. 参数在使用侧被强类型系统自动约束（如百分比类型编译期限制）

## 常见误区

**误区1**："代码中有overflow检查，所以无上限参数是安全的"
- 反驳：溢出panic导致业务中断，等同于DoS漏洞，仍需修复

**误区2**："参数更新需要admin权限，风险已由权限管理降级"
- 反驳：admin权限本身可能被攻击（私钥泄露、合约升级漏洞），参数边界检查应作为独立防线

**误区3**："我们会通过社区治理监督参数"
- 反驳：链外治理无法阻止原子攻击；正确做法是内置技术防护 + 治理双保险
