# Vyper - 线性释放无市场缓冲

## 概述
代币线性释放未考虑市场承受能力，缺乏动态调节机制，大量释放可能导致流动性冲击和价格崩盘。常见于治理代币解锁、团队份额释放、质押奖励分配等场景。

## Details

**代码示例：**
```vyper
# 危险模式：固定速率释放
released: public(uint256)
start_time: public(uint256)
duration: public(uint256)
total_amount: public(uint256)

@external
def release() -> uint256:
    elapsed: uint256 = block.timestamp - self.start_time
    releasable: uint256 = self.total_amount * elapsed / self.duration - self.released
    self.released += releasable
    send(self.beneficiary, releasable)
    return releasable
```

**快速定位核心操作技巧（L2：跳读）：**
- 搜索关键函数：`release`、`vest`、`unlock`、`claim`
- 检查时间计算：`block.timestamp`、`elapsed`、线性公式 `amount * time / duration`
- 关注状态变更：`released`、`claimed`、`withdrawn` 累加器
- 查看转账出口：`send()`、`raw_call()` 代币转出逻辑

**快速定位保护机制技巧（L3：逐行读）：**
- 市场感知：是否读取价格预言机、TVL、流动性深度
- 速率限制：是否有 `max_per_period`、`release_cap`、动态上限
- 触发条件：是否检查 `price_threshold`、`market_cap`、波动率
- 紧急阀门：是否存在 `pause()`、`adjust_rate()`、治理干预接口
- 梯度设计：是否采用分段释放、cliff period、非线性曲线

## Classify

**归类为漏洞的条件：**
- 释放量计算仅基于时间，无市场参数校验
- 单次可释放量无上限或上限固定不可调
- 缺乏紧急暂停/速率调整机制
- 总释放量占流通量比例过大（如 >20%）且无缓冲

**归类为误报的情况：**
- 释放量极小，对市场影响可忽略（如 <0.1% 流通量）
- 已通过多签/DAO治理控制释放开关
- 释放目标为锁仓合约而非市场流通
- 存在外部市场稳定机制（如自动做市、回购销毁）

**归类为代码异味的边界：**
- 理论存在风险但实际释放速度慢（如10年线性释放）
- 有保护机制但实现简陋（如固定上限但未考虑通胀）
- 依赖链下监控而非链上自动化防护

## 审计专业技巧

### 实战漏洞识别法则

**技巧1：数据量化验证（区分真漏洞vs虚惊）**
- 计算释放占比：`(单次释放量 / 当前流通量) × 100%`
  - 若 >5% 且无市场机制对冲 → 真实漏洞
  - 若 <0.5% 且流动性充足 → 误报（影响微乎其微）
- 对标项目：检查 Uniswap/Aave 的解锁历史，同规模项目是否承受过类似冲击
- 时间维度：10年释放 vs 1年释放，体感风险差异巨大，需分别评估

**技巧2：多签延迟陷阱（假安全识别）**
- 常见误判：代码有 `onlyMultiSig()` 就认为安全
- 真相检验：
  - 多签钱包是否托管在正规机构（如 Gnosis Safe）
  - 签名者是否与项目方有利益关联（自签导演式安全）
  - 治理提案是否真的需要 DAO 投票还是核心团队暗箱操作
  - 例：YFI 曾爆出多签被私钥持有者单人控制，形成虚假安全感
- 实战：直接查询多签钱包历史交易，看决策是否真的由多人执行

**技巧3：流动性陷阱（数据误读）**
- 不能只看 Uniswap 池深度，需验证：
  - 是否存在隐藏的流动性供应者同时是大额受益人（会同步套现）
  - 交易对是否单向流动（如只有代币→USDC，无反向深度）
  - 大额释放时是否自动触发流动性补充合约
- 案例：某项目号称有 $5M 流动性，实际 80% 由财库提供，核心交易者套现时立即枯竭

**技巧4：预言机价格操纵检验**
- 即使代码写了 `check_price_oracle()`，也需验证：
  - 预言机是否采用时间加权平均价格（TWAP）而非即时价格
  - 攻击者是否能通过闪电贷在单个区块内操纵价格绕过检验
  - 多个价格源是否真的独立（常见：都依赖 Chainlink，其故障时全部失效）
- Compound 曾因信任单一预言机遭受价格操纵损失 $88M

**技巧5：时间戳篡改风险分层**
- Vyper 的 `block.timestamp` 可被矿工/验证者篡改，但风险需分类：
  - **高风险**：使用 `block.timestamp` 作为唯一时间证明，且区块间隔 <15 秒
  - **低风险**：虽用 `block.timestamp` 但时间跨度很长（如 >1天的 cliff period），篡改成本巨大
  - **安全方案**：结合 block 高度和时间戳双重验证，或使用 Uniswap Oracle

### 常见误报陷阱

**误报1：释放速度看起来快，实际很慢**
- 表象：代码逻辑 `amount * elapsed / duration`，新审计者看到"除数小"就惊慌
- 实情：若 duration = 10 年，最初 1 年才释放 10%，实际风险远低于初期通胀的 3% 年率
- 检验方式：代入实际数值计算前三个月累计释放量，不要只看公式

**误报2：缺乏 Pause 权限被夸大**
- 现象：某项目释放合约无暂停函数，被标记高危
- 反证：Uniswap V4 主合约也不需要暂停，因为释放失败自动回滚，没有必要
- 真正的风险：是否可能造成不可逆的经济伤害（暂停本身不能）

**误报3：单一受益人被错判**
- 陷阱：看到 `beneficiary` 字段，假设团队可以随意提取
- 查证：是否受益人地址本身是多签/合约/DAO 金库，解锁流程是否透明可追踪
- Curve 的团队金库虽集中，但通过社区监督和 veCRV 制约，实际风险低

### 根因分析最佳实践

**方法1：逆向 token 经济学**
```
步骤：
1. 计算总供应量、初期流通量、解锁计划表
2. 推导市场消化能力 = min(日均交易额 × 承受价格下跌%) / 单次释放量
3. 若消化能力 <1，存在机制性风险；若 >3，风险可控
4. 对标项目数据补充：同期 Avalanche/Arbitrum 代币是否承受过类似冲击
```

**方法2：审合约关键路径**
- 追踪代币从释放合约 → 交易所 → 用户的完整路径
- 检验是否存在"隐藏释放"（如：治理合约新增铸币、质押奖励外的增发）
- 例：某项目表面 500M 代币释放计划，但工作证明矿池额外增发 100M，被遗漏

**方法3：社会学信号辅助判断**
- 团队是否对释放计划进行了可查的链上治理表决
- 是否定期发布进度报告，接受社区监督
- 大额释放前是否提前 30 天公告并吸收套现压力
- Lido 的所有升级和参数调整都在 DAO 投票，这本身就是强信号

### 审计报告撰写建议

**风险表述精准化**
- 避免：*"存在线性释放漏洞，可能导致市场冲击"* ← 过于模糊
- 改为：*"12 个月内累计释放流通量的 8.3%，单次释放量最高占日均交易额的 12%，在市场波动期存在 15-20% 短期下跌风险，建议实施分级触发式暂停机制"* ← 量化且可验证

**建议方案分级**
1. **必改**：涉及资金安全、协议失效的风险（>20% 流通量单次无限制释放）
2. **强烈建议**：风险可控但缺乏最佳实践（有上限但未动态调整、缺乏透明预告）
3. **可选改进**：锦上添花（加入 TWAP 预言机、参数治理升级路径）

## Low risk

**低风险评级的适用场景：**
- **释放规模小**：单次释放量 <1% 日均交易量，对盘面冲击有限
- **市场成熟**：项目已运行 >1年，流动性深厚，释放已被市场预期
- **多重保护**：存在时间锁 + 多签控制 + 社区监督的多层防护
- **分散受益人**：释放对象为大量小额用户而非集中持有者
- **配套机制**：同时存在回购、销毁、质押激励等平衡措施
- **可调参数**：虽当前为线性，但通过治理可升级释放曲线
- **透明预警**：提前公示释放计划，市场有充分反应时间
