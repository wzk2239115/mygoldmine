# 通用反序列化漏洞模式（所有项目必审）

拿到任何使用对象反序列化机制的项目，无论使用何种编程语言，以下不安全反序列化漏洞模式都必须进行审计。这些问题源于反序列化过程缺乏安全控制，与具体语言实现无关。

## 反序列化不可信数据源

### 直接反序列化用户可控输入

将用户提供的数据直接反序列化为对象，未进行任何验证或过滤：

- **HTTP 请求参数、请求体、Cookie 中的序列化数据直接反序列化**
  - 审计时检查所有输入点，确保反序列化前验证数据格式和签名
  - 使用白名单限制可反序列化的类

- **WebSocket、消息队列接收的外部数据直接反序列化**
  - 消息队列和 WebSocket 接收的数据需要当作外部不可信数据处理
  - 添加完整性校验和类型白名单

- **文件上传内容直接反序列化为对象，未验证来源可信性**
  - 审查所有处理上传文件的反序列化逻辑
  - 确保先验证文件签名和格式后再反序列化

### 反序列化未验证的网络数据

从网络接收的数据直接反序列化，未验证数据完整性和来源：

- **RPC 调用、远程通信接收的序列化数据直接还原**
  - 即使是内网 RPC 调用也应进行验证，检查是否有 HMAC/签名
  - 审查 RPC 框架是否支持对象类型白名单

- **跨服务通信中反序列化对方服务发送的数据，未验证签名**
  - 服务间通信需实施双向认证和数据签名
  - 禁用多态反序列化；确保类白名单仅包含当前服务需要的类

- **API 网关、代理转发的序列化数据未验证直接处理**
  - 网关层应验证转发数据的完整性，不能盲目转发序列化对象
  - 如需转发，应转为安全格式（如 JSON）后重新序列化

### 反序列化缓存或持久化数据

从缓存、数据库、文件系统读取的序列化数据直接反序列化：

- **缓存系统（Redis、Memcached）中存储的序列化对象直接还原**
  - 如果缓存存储用户数据，攻击者可通过 Redis 写入恶意序列化数据
  - 验证缓存数据来源，检查缓存是否公网可达

- **数据库 BLOB 字段中存储的序列化对象未验证直接使用**
  - 虽然数据库通常内部可信，但检查数据库权限控制是否完善
  - 审查是否有数据迁移或备份还原流程中可能被篡改的场景

- **配置文件、日志文件中的序列化数据直接反序列化**
  - 配置文件应采用 JSON/YAML 等文本格式
  - 若必须存储序列化对象，需进行文件完整性校验和访问控制

## 缺乏类型白名单或类型验证

### 反序列化任意类型对象

反序列化过程允许还原任意类型的对象，未限制可反序列化的类：

- **反序列化时未指定允许的类白名单，可实例化任意类**
  - 审计反序列化代码，检查是否传入 `ObjectInputFilter`（Java）、类型注解（Python）或白名单参数
  - 默认应该拒绝所有类型

- **使用泛型反序列化机制（如 deserialize_any），未限制类型范围**
  - 某些框架提供的通用反序列化函数默认允许任意类型，需明确限制
  - 检查是否可配置类型过滤器

- **反序列化配置允许多态类型还原，未进行类型校验**
  - 在配置多态类型时（如 Jackson 的 `@JsonTypeInfo`），确保设置严格的类型标识符映射而非依赖类名

### 类型名称由外部数据控制

反序列化的目标类型由用户输入或外部数据决定：

- **通过外部数据指定反序列化目标类型（如 TypeNameHandling）**
  - 杜绝从序列化数据中读取类名进行反序列化
  - 如必须使用此特性，需严格限制白名单；检查配置如 `TypeNameHandling=All` 的使用

- **反射机制配合用户输入动态创建对象类型**
  - 审查反射代码 `Class.forName(userInput)` 的使用，确保不能由用户提供任意类名
  - 使用 switch/map 进行静态类名映射

- **插件加载时类名由配置文件或外部输入决定**
  - 插件类名应来自配置文件而非用户输入
  - 配置文件需进行签名验证和版本管理

### 类型验证不严格或可绕过

类型验证机制存在缺陷，可被绕过：

- **类型检查使用字符串匹配，可通过命名空间绕过**
  - 避免用 `contains()` 进行类型检查（如检查 "Executable" 可被 "MyExecutable" 绕过）
  - 应使用完整的类名匹配或类型对象比较

- **白名单配置过于宽泛，包含危险基类或接口**
  - 审查白名单不能包含 Object、Comparable、Serializable 等基础接口
  - 白名单应是最小化的具体类而非抽象基类

- **类型验证存在逻辑缺陷，特定条件下不执行检查**
  - 检查条件判断是否完备，如反序列化前后、不同代码路径的类型验证是否一致
  - 确保使用统一的验证入口

## 使用已知不安全的反序列化函数

### 使用危险的反序列化 API

使用已知存在安全风险的反序列化函数或库：

- **使用已标记为不安全的反序列化函数（如 ObjectInputStream、pickle、unserialize）**
  - Java 中 ObjectInputStream 本质上不安全，需配合 ObjectInputFilter 使用
  - Python pickle 和 PHP unserialize 同样危险，应优先使用 JSON
  - 审查是否有必须使用这些函数的理由

- **使用过时或存在已知漏洞的反序列化库版本**
  - 检查依赖版本是否为最新
  - 注意反序列化库的安全更新公告（如 Commons Collections 历史漏洞）
  - 对使用的库进行定期安全审查

- **使用已废弃的反序列化机制（如 BinaryFormatter）**
  - .NET 的 BinaryFormatter 已标记为危险并计划移除
  - 审查是否仍在使用；应迁移至 JSON 或其他更安全的格式

### 自定义反序列化实现存在缺陷

自行实现的反序列化逻辑存在安全问题：

- **自定义反序列化函数未进行边界检查或类型验证**
  - 审查自实现的反序列化代码，确保验证数据大小、类型、范围
  - 使用明确的数据格式规范而非依赖特定字节序或对齐

- **二进制反序列化时直接 memcpy/fread 填充对象，未验证大小**
  - 直接 memcpy 到结构体是 C/C++ 常见的漏洞
  - 需验证数据长度且使用安全的 API；避免在反序列化过程中触发缓冲区溢出

- **自定义协议解析过程缺乏输入验证和错误处理**
  - 自定义协议解析需要逐字节/字段验证长度、类型、值域
  - 添加详细的错误处理而非忽略异常；使用 fuzzing 测试协议解析的健壮性

## 缺乏数据完整性验证

### 反序列化前未验证签名或 HMAC

序列化数据在传输或存储过程中可能被篡改，反序列化前未验证：

- **反序列化前未验证数据签名，无法确认数据未被篡改**
  - 对所有在网络传输或跨信任边界的序列化数据进行签名
  - 使用 HMAC-SHA256 或类似算法而非 MD5/SHA1
  - 在反序列化前进行验证

- **未使用 HMAC 验证序列化数据完整性**
  - 简单的 CRC 或 checksum 不够，应使用基于密钥的 HMAC
  - 审查是否使用了密码学安全的哈希函数；验证密钥管理方式

- **签名验证逻辑存在缺陷，可被绕过**
  - 避免在反序列化失败时跳过签名验证
  - 不能使用时间戳进行比对而忽视签名；确保验证是强制性的而非可选的

### 未验证数据来源可信性

反序列化时未验证数据来源的身份和权限：

- **反序列化多租户数据时未验证租户隔离**
  - 在多租户系统中，序列化数据应包含租户标识
  - 反序列化后需验证当前用户是否有权访问该租户的数据；审查租户上下文是否正确传递

- **跨信任边界传递的序列化数据未验证来源身份**
  - 不同信任域间的序列化数据需进行身份验证，不能假定同网络的数据可信
  - 添加请求发起者的身份标识和权限检查

## 魔术方法或生命周期钩子被滥用

### 析构函数/终结器中存在危险操作

对象析构或终结时执行的代码可被利用：

- **对象析构函数中执行文件操作、命令执行等危险行为**
  - 审查所有对象的析构函数，避免执行 I/O 操作、系统调用等
  - 如必须进行资源清理，应在明确的生命周期方法中进行而非依赖析构函数

- **终结器（Finalizer）中的代码可被反序列化利用**
  - Java 中 finalize() 方法在反序列化后可能被触发
  - 审查其中是否有危险操作；优先使用 try-with-resources 等替代方案

### 魔术方法中存在利用链

特殊方法（如 __wakeup、__destruct、__toString）可被串联利用：

- **魔术方法串联形成 POP 链或 Gadget 链，可执行任意代码**
  - 审查项目中所有魔术方法的实现，分析是否能通过序列化数据触发链式调用
  - 识别可作为 Gadget 的对象（如包装函数指针、命令对象）
  - 使用静态分析工具查找 Gadget 链

- **自定义序列化回调（如 __reduce__）返回可执行代码**
  - Python 的 __reduce__、__reduce_ex__ 和 PHP 的 __serialize、__unserialize 需审查
  - 这些方法返回的内容不应包含可调用对象；避免在序列化时返回函数对象

- **对象唤醒方法（__wakeup、readObject）中包含危险逻辑**
  - Java 的 readObject、readResolve 和 PHP 的 __wakeup 在反序列化后被自动调用
  - 审查其中是否有文件操作、数据库查询、命令执行等；禁止执行不安全的操作

## 反序列化过程缺乏隔离和限制

### 未在沙箱环境中反序列化

反序列化过程与主应用运行在同一权限级别，无隔离：

- **反序列化过程未使用沙箱或容器隔离**
  - 对于处理不可信反序列化数据的关键场景，考虑在独立进程或容器中进行反序列化
  - 使用操作系统级别的隔离机制（seccomp、AppArmor、SELinux）限制反序列化进程的权限

- **反序列化时未限制系统调用或资源访问权限**
  - 审查反序列化进程是否可执行任意系统调用
  - 使用 seccomp 过滤器限制允许的系统调用集合；限制文件访问、网络访问等权限

### 反序列化过程缺乏资源限制

反序列化可能消耗大量资源，导致拒绝服务：

- **反序列化未限制对象深度，可构造深度嵌套导致栈溢出**
  - 为反序列化设置最大对象嵌套深度限制（如 Java ObjectInputFilter）
  - 使用迭代而非递归方式处理嵌套结构；监控栈使用情况

- **反序列化未限制对象大小或数量，可导致内存耗尽**
  - 限制反序列化的最大数据大小；限制单次反序列化的对象数量
  - 监控内存使用并设置上限；使用流式反序列化而非一次性加载

- **反序列化未设置超时时间，可被恶意数据长时间阻塞**
  - 对反序列化操作设置明确的超时时间
  - 在超时情况下及时中断反序列化进程；避免在反序列化时执行阻塞操作（如网络 I/O）
