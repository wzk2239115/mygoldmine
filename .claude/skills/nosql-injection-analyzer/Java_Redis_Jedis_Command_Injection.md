# Java Redis Jedis Command Injection

## Details

**漏洞成因**：Jedis 是 Java 的 Redis 客户端。当使用 `eval()`、`evalsha()` 等方法执行 Lua 脚本时，若脚本内容或参数由用户输入构造，攻击者可注入任意 Redis 命令或 Lua 代码。

**代码审计焦点**：
- 是否使用 `jedis.eval()`、`jedis.evalsha()` 等方法
- Lua 脚本内容是否由用户输入动态构造
- `jedis.set()`、`jedis.get()` 等命令的参数是否来自用户输入
- 是否存在脚本参数验证或白名单

**核心定位技巧**：
- **(L1: 关键词扫描)** 搜索 `jedis.eval(`、`jedis.evalsha(`、`jedis.set(` 等关键字
- **(L2: 跳读)** 检查脚本内容是否来自 `request.getParameter()` 等不可信源
- **(L3: 逐行读)** 追踪脚本和参数从接收到执行的过程，确认是否进行了验证
- **(L4: 跨模块追踪)** 检查是否通过多个函数或切面处理脚本参数

**保护机制识别**：
- **(L1: 关键词扫描)** 检查是否使用了脚本白名单
- **(L2: 跳读)** 验证脚本是否存储在服务器端而非由客户端提供
- **(L3: 逐行读)** 确认参数是否通过类型检查（Long、String 等）
- **(L4: 跨模块追踪)** 检查 Jedis 连接是否配置了密码认证和 ACL

## Classify

**漏洞研判**：
1. 若 Lua 脚本由用户输入构造 → 高危漏洞
2. 若脚本参数未进行验证 → 漏洞
3. 若允许执行任意 Redis 命令 → 漏洞

**误报风险**：
1. 脚本存储在服务器端，用户仅提供参数 → 低风险
2. 参数通过类型检查限制 → 低风险
3. Redis 连接配置了认证和 ACL → 低风险

## Low risk

- Lua 脚本存储在服务器端
- 脚本 SHA 值白名单管理
- 参数通过类型检查和白名单验证
- Jedis 连接启用密码认证和 ACL
- 禁用高危命令（FLUSHDB、CONFIG 等）
