# PHP Redis Command Injection

## Details

**漏洞成因**：PHP 的 phpredis 扩展在处理 Redis 命令时，若使用 `$redis->eval()`、`$redis->evalSha()` 等方法执行 Lua 脚本，且脚本内容或参数由用户输入构造，攻击者可注入任意 Redis 命令或 Lua 代码。此外，直接将用户输入用于构造命令参数（如 `$redis->set($key, $value)` 中 `$key` 来自 `$_GET`）也可能导致命令注入。

**代码审计焦点**：
- 是否使用 `$redis->eval()`、`$redis->evalSha()` 等方法执行动态 Lua 脚本
- Lua 脚本内容或脚本参数是否由用户输入（`$_GET`、`$_POST`、`$_REQUEST` 等）直接构造
- 命令参数（key、value 等）是否来自不可信源且未进行验证
- 是否存在参数白名单或类型验证机制

**核心定位技巧**：
- **(L1: 关键词扫描)** 搜索 `eval(`、`evalSha(`、`script(`、`raw()` 等关键字，以及 `$_GET`、`$_POST`、`$_REQUEST`、`request->input()` 等用户输入来源
- **(L2: 跳读)** 检查 eval/evalSha 的脚本参数是否直接引用来自 HTTP 请求的变量；检查 key 或 value 参数是否包含用户输入
- **(L3: 逐行读)** 追踪用户输入从接收、处理到传入 Redis 命令的完整流程，确认是否进行了验证或转义
- **(L4: 跨模块追踪)** 检查是否通过多个函数或中间件处理参数；追踪框架（Laravel、Symfony 等）的缓存层实现；检查是否存在全局的参数过滤函数

**保护机制识别**：
- **(L1: 关键词扫描)** 检查是否使用了特定的 Redis 命令方法（`set()`、`get()`、`hset()`）而非 `eval()`；检查是否使用了 `in_array()` 或正则验证白名单
- **(L2: 跳读)** 验证脚本是否存储在服务器端（配置文件、常量、数据库）而非由客户端提供；检查参数是否通过 `intval()`、`floatval()`、`trim()` 等转换函数处理
- **(L3: 逐行读)** 确认参数是否通过严格的类型检查（`is_int()`、`is_string()` 等）；检查是否对用户输入进行了格式验证（如键名只允许字母数字下划线）
- **(L4: 跨模块追踪)** 检查 Redis 连接是否配置了密码认证；检查 Redis 是否启用了 ACL（访问控制列表）限制执行权限；检查是否使用了只读的 Redis 账户

## Classify

**漏洞研判**：
1. 若 Lua 脚本由用户输入直接构造 → 高危漏洞
2. 若脚本参数（ARGV、KEYS）未经验证即来自用户输入 → 漏洞
3. 若直接将用户输入用于 key 或 value 参数，且 Redis 连接有写权限 → 漏洞
4. 若使用 `eval()` 执行动态拼接的命令字符串 → 漏洞
5. 若允许用户控制 Redis 命令的执行（如调用 `$redis->__call()` 或反射机制） → 漏洞

**误报风险**：
1. 脚本存储在服务器端（代码中或配置文件中），用户仅提供参数 → 低风险
2. 参数通过严格的白名单验证或类型转换限制 → 低风险
3. 使用特定的 Redis 命令方法（set、get、hset 等）且参数通过验证 → 低风险
4. Redis 连接使用只读账户或通过 ACL 严格限制权限 → 低风险

## Low risk

- Lua 脚本完全由开发者在源代码中定义或从配置文件加载，不依赖用户输入
- 用户仅提供脚本的参数（ARGV、KEYS），且参数通过白名单或严格格式验证
- 使用特定的 Redis 命令方法（`set()`、`get()`、`hset()`、`lpush()` 等）而非 `eval()` 或 `evalSha()`
- 参数通过 `intval()`、`floatval()` 等类型转换或格式验证（正则表达式）限制
- Redis 连接配置了强密码认证，或通过 ACL 限制执行的命令范围
- 禁用危险命令（FLUSHDB、FLUSHALL、CONFIG、SCRIPT LOAD 等）
- Redis 连接启用 TLS/SSL 加密，确保通信安全
- 在应用层实现了严格的权限控制，验证用户是否有权限访问特定的 Redis 数据
