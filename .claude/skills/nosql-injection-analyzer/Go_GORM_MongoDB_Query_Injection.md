# Go GORM MongoDB Query Injection

## Details

**漏洞成因**：GORM MongoDB 插件通过 `bson.M` 或 `bson.D` 构造查询条件。当用户输入直接用于查询对象的键或值时，攻击者可注入 MongoDB 操作符。特别是在使用 `Where()`、`Cond()` 等方法时，若条件由用户输入组合而成且未经参数化，将导致注入漏洞。GORM 对 MongoDB 的抽象虽提供了便利，但在动态构造查询条件时仍面临 NoSQL 注入风险。

**代码审计焦点**：
- 是否使用 `db.Where()`、`db.Cond()` 构造查询条件，参数是否含用户输入
- 是否通过字符串拼接或 map 直接映射构造 bson.M 查询对象
- 是否使用 `db.Where(map[string]interface{})` 传递用户控制的 map
- `FindOne()`、`Find()`、`UpdateOne()` 等操作的过滤条件来源
- 是否进行了字段白名单验证或参数化

**核心定位技巧**：
- **(L1: 关键词扫描)** 搜索 `.Where(`、`.Cond(`、`.Find(`、`bson.M{`、`bson.D{` 等关键字，特别是 `Where()` 的参数中是否包含用户输入的字符串
- **(L2: 跳读)** 检查 `.Where()` 的参数是否来自 `c.Query()`、`c.PostForm()`、`ctx.Param()` 等不可信源，若参数通过字符串拼接构造则为高风险
- **(L3: 逐行读)** 追踪查询条件从接收用户输入到执行 MongoDB 操作的完整链路，确认是否存在字段验证、操作符过滤或参数化处理
- **(L4: 跨模块追踪)** 检查查询条件是否通过多个函数（如 service 层、repository 层）传递和拼接，追踪最终生成的 bson.M 对象结构

**保护机制识别**：
- **(L1: 关键词扫描)** 检查是否使用了 GORM 的条件构造器（如 `db.Where(builder.Eq(...))`）或原生 MongoDB 驱动的 `filter` 包，是否避免了直接 map 赋值
- **(L2: 跳读)** 验证查询条件的字段名是否通过白名单验证（allowedFields map），参数值是否通过类型检查（如 `strconv.ParseInt`）
- **(L3: 逐行读)** 确认是否使用了 GORM 的条件链式调用（如 `Where("name = ?", userInput)`）而非字符串拼接，检查是否有输入验证的中间件或 hook
- **(L4: 跨模块追踪)** 检查是否在数据访问层实现了统一的查询构造函数，是否通过 DTO 和验证库对输入进行了强制验证

## Classify

**漏洞研判**：
1. 若 `.Where()` 的条件包含用户输入且未进行参数化（如字符串拼接）→ 漏洞
2. 若通过 `map[string]interface{}` 直接映射用户输入到查询条件 → 漏洞
3. 若允许用户控制查询对象的键名，且键名可以是 MongoDB 操作符（如 `$ne`、`$gt` 等）→ 漏洞
4. 若查询条件通过 JSON 反序列化直接构造，未过滤操作符字段 → 漏洞

**误报风险**：
1. 使用 `.Where("field = ?", value)` 的参数化形式，且字段名硬编码 → 低风险
2. 字段名和操作符均来自代码常量或枚举，用户只控制值 → 低风险
3. 查询条件通过白名单字段映射且值通过类型验证 → 低风险

## Low risk

- 使用 GORM 的条件参数化形式（`.Where("field = ?", userInput)`）
- 字段名使用常量、枚举或代码中硬编码的白名单
- 用户输入仅作为查询值，不能控制字段名或操作符
- 对输入值进行了严格的类型验证和范围检查
- 使用 GORM hook（如 `BeforFind`）对查询条件进行统一验证
- MongoDB 连接使用最小化权限原则，DB 用户只读或权限受限
