# PHP MongoDB Query Array Injection

## Details

**漏洞成因**：MongoDB PHP 库（`mongodb/mongodb`）通过数组构造查询条件。当用户输入直接用于构造查询数组的键（字段名）或值时，攻击者可注入 MongoDB 操作符（如 `$ne`、`$gt`、`$where` 等）。特别是在使用数组展开、`array_merge()` 或直接数组拼接时，若未对键进行过滤验证。

**代码审计焦点**：
- 是否使用 `$collection->find()`、`$collection->updateOne()` 时直接传递用户数组
- 查询条件数组是否通过 `array_merge()`、展开运算符 `...` 等方式构造
- 是否对用户输入进行了键名验证（排除 `$` 开头的操作符）
- 是否使用了服务器端脚本 `$where` 或 `mapReduce` 等高风险操作

**核心定位技巧**：
- **(L1: 关键词扫描)** 搜索 `find(`、`findOne(`、`updateOne(`、`deleteOne(`、`array_merge`、`...` 展开运算符、`$_GET`、`$_POST` 等关键字
- **(L2: 跳读)** 检查查询数组是否来自不可信源（HTTP 请求参数、外部 API 等），重点关注如何处理数组键名
- **(L3: 逐行读)** 追踪用户输入到查询执行的完整链路，确认是否存在键名验证、类型转换或白名单过滤
- **(L4: 跨模块追踪)** 检查是否通过多个函数或类方法组合查询条件，验证整个数据流中的防护措施

**保护机制识别**：
- **(L1: 关键词扫描)** 检查是否使用了 `array_filter()`、`array_keys()` 验证，或检查是否存在 `preg_match()` 过滤 `$` 符号的逻辑
- **(L2: 跳读)** 验证用户输入是否经过白名单映射（如数据库字段与用户参数的映射表）或 `in_array()` 检查
- **(L3: 逐行读)** 确认是否使用了参数化查询构造（通过 ORM 或查询构造器而非原生数组）
- **(L4: 跨模块追踪)** 检查是否在多个层级（API、业务逻辑、数据访问层）中都有防护措施，以及是否使用了 Doctrine 或其他 ORM 框架

## Classify

**漏洞研判**：
1. 若查询数组的键来自用户输入且未验证 → 漏洞（攻击者可注入 `$ne`、`$gt` 等操作符）
2. 若使用 `array_merge()`、展开运算符 `...` 合并用户数组且未过滤键名 → 漏洞
3. 若允许用户控制字段名且使用了 `$where`、`$function` 等高风险操作符 → 漏洞
4. 若查询条件由用户输入直接构造且缺少白名单验证 → 漏洞

**误报风险**：
1. 查询条件仅涉及值的注入（键名由代码固定）→ 可能是低风险，需检查值的类型强制转换
2. 使用了 `array_keys()` 验证但验证逻辑存在绕过 → 需详细审查验证规则
3. 使用白名单但白名单过于宽泛（包含了危险字段如 `$where`）→ 误报，应标记为漏洞

## Low risk

- 查询条件的所有键名由代码常量或枚举定义，用户只能控制值
- 对用户输入的数组进行了严格的白名单验证（使用 `array_intersect_key()` 或逐一检查键名）
- 使用 Doctrine MongoDB ODM 或 Laravel MongoDB 等 ORM 框架的参数化查询构造器
- 对用户输入的键名进行了正则表达式过滤，确保不包含 `$` 或其他特殊符号
- 数据库连接配置了最小权限原则（用户、密钥等限制在必要的操作范围内）
- 使用了类型强制转换（如 `(int)$userId`）且确保其有效性
