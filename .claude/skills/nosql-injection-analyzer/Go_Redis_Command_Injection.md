# Go Redis Command Injection

## Details

**漏洞成因**：Go 的 go-redis 客户端在处理 Redis 命令时，若用户输入直接用于构造命令参数，攻击者可注入任意 Redis 命令。go-redis 的 `Do()` 或 `Eval()` 方法若接受用户控制的参数，将导致命令注入。

**代码审计焦点**：
- 是否使用 `client.Do()`、`client.Eval()` 等方法执行动态命令
- 命令参数是否来自 `c.Query()`、`c.PostForm()` 等用户输入源
- Lua 脚本内容是否由用户控制
- 是否存在命令参数验证或白名单

**核心定位技巧**：
- **(L1: 关键词扫描)** 搜索 `client.Do(`、`client.Eval(`、`client.Set(` 等关键字
- **(L2: 跳读)** 检查参数是否来自 `c.Query()`、`c.PostForm()` 等来源
- **(L3: 逐行读)** 追踪参数从接收到 Redis 执行的过程，确认是否进行了验证
- **(L4: 跨模块追踪)** 检查是否通过多个函数或中间件处理参数

**保护机制识别**：
- **(L1: 关键词扫描)** 检查是否使用了特定的 Redis 命令方法（如 `client.Set()`）而非 `Do()`
- **(L2: 跳读)** 验证参数是否通过白名单验证
- **(L3: 逐行读)** 确认参数是否通过类型检查（`strconv.ParseInt()` 等）
- **(L4: 跨模块追踪)** 检查 Redis 连接是否启用了认证

## Classify

**漏洞研判**：
1. 若使用 `client.Do()` 执行用户输入构造的命令 → 漏洞
2. 若 Lua 脚本由用户输入构造 → 高危漏洞
3. 若允许执行任意 Redis 命令 → 漏洞

**误报风险**：
1. 使用特定的 Redis 命令方法且参数通过验证 → 低风险
2. 参数通过 `strconv` 等类型转换限制 → 低风险
3. Redis 连接只读且账户权限受限 → 低风险

## Low risk

- 仅使用特定的 Redis 命令方法（Set、Get 等）而非 Do()
- 参数通过白名单验证或类型转换限制
- Redis 连接使用只读账户或 ACL 限制
- 禁用 Lua 脚本执行（EVAL 命令）
- 连接使用 SSL/TLS 加密
