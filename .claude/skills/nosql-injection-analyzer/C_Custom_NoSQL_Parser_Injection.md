# C Custom NoSQL Parser Injection

## Details

**漏洞成因**：C 语言应用实现自定义 NoSQL 查询解析器时，若对输入的解析不当，攻击者可构造特殊输入触发缓冲区溢出、格式化字符串漏洞或逻辑绕过。特别是在手动字符串拼接、缺乏边界检查的情况下。

**代码审计焦点**：
- 是否使用 `strcpy()`、`sprintf()` 等不安全函数
- 查询解析逻辑是否存在缓冲区边界检查
- 是否使用了格式化字符串（`printf()` 族函数）处理用户输入
- 解析器是否验证了输入的合法性（长度、字符集等）

**核心定位技巧**：
- **(L1: 关键词扫描)** 搜索 `strcpy`、`sprintf`、`printf`、`gets` 等危险函数
- **(L2: 跳读)** 检查用户输入是否直接用于缓冲区操作或格式化字符串
- **(L3: 逐行读)** 追踪输入的长度检查和边界验证
- **(L4: 跨模块追踪)** 检查解析逻辑是否在多个函数中存在重复的风险代码

**保护机制识别**：
- **(L1: 关键词扫描)** 检查是否使用了 `strncpy()`、`snprintf()` 等带长度限制的函数
- **(L2: 跳读)** 验证是否对输入长度进行了校验
- **(L3: 逐行读)** 确认是否使用了词法分析器或 flex/bison 等工具
- **(L4: 跨模块追踪)** 检查是否使用了内存安全的语言包装

## Classify

**漏洞研判**：
1. 若使用 `strcpy()` 或 `sprintf()` 处理用户输入 → 高危漏洞
2. 若用户输入直接用于格式化字符串 → 高危漏洞
3. 若解析逻辑不检查输入长度 → 漏洞

**误报风险**：
1. 使用 `strncpy()` 或 `snprintf()` 且指定了长度限制 → 低风险
2. 输入经过严格的长度和字符集验证 → 低风险
3. 使用成熟的词法分析器库 → 低风险

## Low risk

- 使用 `strncpy()`、`snprintf()` 等带长度限制的安全函数
- 输入长度和字符集验证
- 使用 flex/bison 等成熟的解析工具
- 内存检查工具（AddressSanitizer、Valgrind）验证
- 静态分析工具检查缓冲区安全
