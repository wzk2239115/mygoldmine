# Solidity 跨合约重入（Cross-Contract Reentrancy）

## Details

**代码特征示例：**
```solidity
// 合约A：主业务合约
contract VaultA {
    mapping(address => uint) public balances;
    IHelper public helper;
    
    function withdraw() external {
        uint amount = balances[msg.sender];
        helper.validate(msg.sender, amount);  // 外部调用
        balances[msg.sender] = 0;  // 状态更新延后
        payable(msg.sender).transfer(amount);
    }
}

// 合约B：辅助合约（可被攻击者控制或替换）
contract HelperB {
    function validate(address user, uint amount) external {
        // 回调VaultA的其他函数，此时balances尚未更新
        VaultA(msg.sender).someOtherFunction();
    }
}
```

**快速定位核心操作（L3-L4）：**
- 追踪跨合约调用链：识别 `contract.call()`、接口调用、`delegatecall` 等外部交互点
- 检查调用顺序：外部调用是否在状态变更之前（CEI模式违反）
- 关注多步骤流程：跨合约交互 → 状态未锁定 → 允许重入其他函数
- 映射交互拓扑：绘制合约A↔B↔C的调用关系，识别循环调用路径
- **审计等级：L4（跨模块追踪）** - 需追踪外部合约的回调可能性，分析调用链中的状态一致性

**快速定位保护机制（L2-L3）：**
- 全局锁检查：搜索 `nonReentrant` 修饰器或手动 `locked` 状态变量
- CEI模式验证：确认状态更新在所有外部调用之前完成
- 信任边界：检查外部合约地址是否可控（immutable/onlyOwner设置）
- 函数级隔离：不同函数间是否共享可重入的状态检查
- **审计等级：L2（跳读）+ L3（逐行读）** - 快速扫描修饰器和锁变量（L2），然后逐行验证状态更新时机（L3）

## Classify

**漏洞判定标准：**
1. 存在跨合约调用且被调用合约可执行回调代码（非纯计算合约）
2. 回调路径可访问调用方的未锁定函数
3. 重入执行能利用过期状态获利（余额/权限/计数器等）

**误报识别：**
- 外部合约为已验证的标准协议（Uniswap Router等），无恶意回调逻辑
- 虽存在跨合约调用，但全局重入锁已覆盖完整调用链
- 状态变更已在外部调用前完成（严格CEI），即使重入也无法利用旧状态

**代码异味：**
- 跨合约调用存在但未造成实际风险，仅增加攻击面（建议优化顺序）
- 部分函数有保护但未全局覆盖，存在潜在组合调用风险

## Low risk

**低风险场景评判：**
1. **只读跨合约调用**：外部调用仅用于查询（view/pure函数），无状态修改能力
2. **受信任的中心化合约**：外部合约由项目方控制且已审计，合约地址不可篡改
3. **无经济激励**：即使重入成功也无法提取额外资产或获取权限提升
4. **孤立状态**：被重入函数操作的状态与跨合约调用上下文完全隔离，无共享变量
5. **有效的部分保护**：虽未全局防护，但关键资产操作函数已单独加锁，次要功能重入不影响核心安全

## 审计专业技巧与实战经验

### 一、真实漏洞与误报的区分标准

**真实高危漏洞特征：**
- **状态敏感性**：重入时访问的状态变量直接关乎资产转移或权限验证
- **调用链完整性**：从受控入口到回调函数的完整攻击路径可被鼓励者构造
- **经济可行性**：攻击者可通过重入实现的收益 ≥ Gas成本，具体可计算ROI
- **防护缺陷明显**：缺少全局锁或状态检查，代码审阅可直观识别漏洞

**常见误报来源：**
1. **过度关注接口调用**：识别到ERC20.transfer()等跨合约调用，但忽视该函数为原子操作且已保护的事实
2. **假设恶意外部合约**：未实际验证被调用合约地址可控性，假定所有外部交互均可被攻击者利用
3. **忽视CEI模式验证**：看到外部调用就报告漏洞，未检查状态更新是否已提前完成
4. **遗漏锁覆盖检查**：检查单个函数是否有nonReentrant，但未跟踪该锁是否覆盖完整调用链

### 二、审计工作流与检查清单

**第一步：构建调用图谱（5分钟）**
```solidity
// 通过grep检索所有跨合约调用点，记录：
// 调用方合约 → 被调用合约 → 回调可能性 → 被重入函数集合
// 示例：VaultA.withdraw() → ERC20.transfer() → ERC20_onTransfer回调 → withdraw()可重入
```

**第二步：状态流追踪（核心步骤）**
- 标记所有状态变量修改的代码行
- 列出每个函数的外部调用点
- 检验：外部调用前的状态修改是否充分？（非所有状态都需更新，仅关键变量）
- 识别过期状态：重入时哪些变量值未更新、被攻击者利用

**第三步：防护机制验证**
- 扫描全局锁的定义与初始化方式（Reentrancy Guard库 vs 自定义locked标志）
- 检查所有敏感函数（转账、铸币、销毁等）是否均加修饰器
- 验证锁的粒度：是否存在多个独立的重入锁导致保护不完整

**第四步：可控性与信任边界分析**
- 外部合约地址是否为hardcoded常量？是否可通过onlyOwner修改？
- 被调用的接口是否限制了返回值检查（如ERC20可能不返回bool）？
- 调用方是否验证了返回值或异常处理？

### 三、实战案例对比

**真实漏洞示例 - Tether多重签名钱包（2016）**
- 特征：转账前未扣余额，合约间可相互调用
- 危害：攻击者通过重入转账函数可一次性提取多倍资金
- 修复：添加全局重入锁，转账前更新余额

**误报案例 - Uniswap V2 flashSwap**
- 假设：识别到swap()函数存在外部调用（to.transfer）
- 实际：虽存在跨合约调用但：
  1. 转账前已更新储备量（_update()先于transfer执行）
  2. 尽管caller可重入，但重入的swap会使用已更新的储备量计价，无法套利
  3. Flash贷款本身是设计特性，收费机制保证安全性
- 结论：设计漏洞标记为误报

### 四、高效审计工具与模式匹配

**快速识别高危模式的正则表达式：**
```regex
// 查找"外部调用后状态更新"的反CEI模式
\.call\(|\.transfer\(|\.send\(|\.delegatecall\(.*?\n.*?=.*?balance\[|\.transfer\(|\[.*?\]\s*=
```

**自动化检查脚本概念：**
- 提取AST中所有StateVariable修改
- 遍历每个函数的FunctionCall节点
- 对比修改顺序：若外部调用在状态更新前，flags为HIGH
- 若存在nonReentrant修饰器，自动downgrade为LOW

### 五、沟通与报告建议

**高风险漏洞描述模板：**
- 危害场景：具体说明攻击者利用路径（需包含数值示例）
- PoC概述：伪代码展示重入时的状态利用方式
- 修复优先级：标记为CRITICAL/HIGH，建议修复前暂停合约

**低风险/误报澄清模板：**
- 初始疑虑：为何看起来存在重入风险
- 深层分析：解释CEI、锁机制或设计特性如何消除风险
- 验证方式：给出具体的代码行号和逻辑论证
