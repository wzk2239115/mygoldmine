# 通用竞态条件审计小抄

无论使用何种编程语言，涉及并发处理的应用都必须审计以下通用竞态条件漏洞模式。这些问题源于共享状态访问缺乏同步控制，与具体语言实现无关。

## 1. 共享状态访问缺乏同步机制

### 多线程/多进程/异步并发

**检查清单：**
- 共享变量、全局状态被多个执行流并发读写，未使用互斥锁保护
- 共享集合（Map、List、Set 等）被并发修改，无同步机制
- 单例初始化（含双重检查）存在竞争窗口或内存可见性问题
- 异步任务/Promise/协程并发修改同一缓存或状态，缺乏锁或原子操作

**定位技巧：**
- 搜索全局变量声明和静态字段 `static`、`global`
- 追踪共享集合的写操作：`.add()`、`.put()`、`.remove()`、直接赋值
- 查找单例模式：`getInstance()`、`instance()`、`shared_instance`
- 定位并发入口：HTTP Handler、goroutine、Promise、Thread 创建点

### 锁粒度过细或使用不当

**检查清单：**
- 锁保护范围过小，临界区外仍有未保护的共享状态访问
- 多个原子操作需要作为整体执行，但使用了多个独立的锁
- 读-修改-写操作分离（如：先读、计算、再写），未在同一锁内完成

**定位技巧：**
- 审查锁的获取与释放位置，锁保护的代码块范围
- 检查相邻的多个锁语句，判断是否应合并为一个锁
- 查找 read-modify-write 模式：先获取值、修改、再存回

## 2. 检查时间与使用时间（TOCTOU）

**检查清单：**
- 检查库存 → 扣减库存，两步间存在竞态窗口（超卖）
- 检查文件存在 → 打开文件，文件可能被删除或被符号链接攻击
- 检查账户余额 → 扣款，检查与扣款非原子（余额可为负、重复扣款）
- 双重检查锁定未使用内存屏障（`volatile`、内存屏障）导致初始化竞态

**定位技巧：**
- 查找 if 判断与后续操作间的代码间隙
- 追踪库存/余额检查与更新的位置，确认是否在同一事务/锁内
- 检查文件操作：`exists()`/`isFile()` → `open()`/`read()`，中间无同步
- 审查单例和延迟初始化的写法

## 3. 数据库操作缺乏事务隔离

**检查清单：**
- SELECT 后 UPDATE 分为两步，非原子操作，并发请求导致数据覆盖
- 未设置足够高的事务隔离级别，允许脏读或不可重复读
- UPDATE 语句未使用 FOR UPDATE 行锁或乐观锁（版本号）
- ORM 配置未启用乐观锁或未检查受影响行数
- 批量插入/更新未在事务中执行，部分失败导致数据不一致
- 跨表操作未在同一事务中完成

**定位技巧：**
- 搜索 SELECT → UPDATE 模式的代码
- 查看数据库连接配置的隔离级别设置
- 检查 UPDATE 语句是否带 WHERE 子句和版本号检查
- 查找 ORM 乐观锁配置：`@Version`、`version` 字段、版本号约束
- 审查批量操作是否显式开启事务（`beginTransaction()`、`@Transactional` 等）

## 4. 缓存更新竞态

**检查清单：**
- 缓存与数据库更新顺序不当（先 DB 再删缓存 vs 先删缓存再 DB）
- 缓存失效时多个并发请求同时查询数据库（缓存击穿、缓存雪崩）
- 缓存更新未加锁，多个进程同时写入，导致脏数据
- 缓存重建无防护机制（无 mutex 或 singleflight）

**定位技巧：**
- 追踪缓存操作和数据库操作的顺序
- 搜索缓存 key 失效/删除的代码
- 检查缓存未命中时的重建逻辑，是否存在互斥保护
- 查找缓存相关的并发防护：mutex、singleflight、分布式锁

## 5. 文件系统操作竞态

**检查清单：**
- 多线程/进程写同一文件，未使用文件锁，内容可能交错或覆盖
- 读文件 → 修改 → 写回，中间内容可能被改变
- 临时文件由多个进程同时写入，未使用排他锁或唯一文件名
- 检查文件存在 → 打开，文件可能被删除或权限被修改（符号链接攻击）

**定位技巧：**
- 搜索文件写操作：`write()`、`writeFile()`、`file_put_contents()`
- 检查是否有文件锁：`flock()`、`fcntl()`、`LockFile()`
- 追踪临时文件生成与删除，检查唯一性和锁保护
- 查找文件状态检查与后续操作的时间间隙

## 6. 原子性操作不足

**检查清单：**
- 增量操作 `i++` 非原子，并发执行导致计数丢失更新
- 先检查再设置 `if (!exists) { set(...) }`，竞态导致重复执行
- CAS（Compare-And-Swap）实现错误或未使用
- 访问计数器、统计数据并发自增，无原子操作保护

**定位技巧：**
- 搜索 `++`、`--`、`+=` 等复合赋值操作
- 查找 if-then-set 模式：判断后直接赋值，无同步
- 检查是否使用原子操作类（`AtomicInteger`、`atomic.AddInt64` 等）
- 审查计数器相关代码的同步机制

## 7. 幂等性控制缺失

**检查清单：**
- 支付/扣款接口未使用幂等 Token，重复请求导致重复扣费
- 订单创建未检查重复，并发请求创建多个订单
- 消息队列消费未实现幂等，重复消费导致重复执行
- 状态机转换未原子检查当前状态，可重复执行转换

**定位技巧：**
- 搜索关键业务操作：支付、转账、创建订单、发放优惠券
- 检查是否有幂等 Token 机制：request_id、idempotency_key
- 查看消息消费的幂等处理：消费 ID 去重、版本号校验
- 追踪状态转换逻辑，检查是否先验证当前状态

## 8. 分布式环境竞态

**检查清单：**
- 定时任务在多实例部署时同时执行，未使用分布式锁
- 多实例同时处理同一资源，缺乏分布式协调
- 跨服务调用未使用分布式事务（Saga、TCC），数据不一致
- 消息队列消费者并发处理，未保证消息顺序或幂等

**定位技巧：**
- 搜索定时任务声明：`@Scheduled`、`cron`、`timer`
- 检查分布式锁使用：Redis `SETNX`、MySQL 行锁、ZooKeeper
- 查找跨服务调用和远程 RPC 操作
- 审查消息队列消费配置：并发度设置、分区分配

## 9. 业务逻辑竞态

**检查清单：**
- 库存扣减：扣减前未加行锁或乐观锁，高并发超卖
- 优惠券/红包：领取数量校验与发放非原子，超发
- 账户余额：扣款未使用原子操作或行锁，余额可为负
- 积分充值/扣减：并发操作导致数据不准确

**定位技巧：**
- 搜索库存、余额、积分等关键资源的更新代码
- 检查 UPDATE 语句的 WHERE 条件，是否包含数量/余额约束
- 查看是否有悲观锁（FOR UPDATE）或乐观锁（版本号）
- 追踪高并发业务操作的关键路径
