# 蓝队候选问题验证

先完成一条候选问题的最小可复核验证，再考虑扩大覆盖。环境部分可用不等于本候选无法验证，已有蓝队确认也不等于红队可利用性验收通过。

## 读取与收敛

- 先读任务指定的候选问题、环境清单和相关源码。输出目录、脚本目录、镜像及超时以本任务参数为准；不要自行另建一轮审计目录。
- 用“谁控制什么输入 → 哪个真实入口 → 哪个危险操作 → 需要什么配置”描述待验证命题，区分默认行为、显式启用和操作员导入不可信工件。调用危险接口本身不足以判定漏洞。
- 只沿入口、配置和危险操作补充证据。不要全盘查找技能或遍历其他候选、历史批次；本技能位于 `.claude/skills/blue-team-verifier/SKILL.md`。
- 找到最小调用链后，立即把可执行脚本写入任务的 `harness_dir`。原型和依赖安装放入本任务的 `VERIFY_WORK_DIR`；需要交付的测试输入和诊断证据保存到本候选交付目录，不能只留在共享临时路径。容器内部可使用独立临时目录。
- 验证 verl 的 CPU 奖励函数、分词器加载或模型合并时，再读 [verl 的局部验证范围](references/verl-cpu.md)；核对源码版本后选择适用部分。

## 先获得最小证据

优先顺序：真实现有测试或函数入口 → 最小组件 → 只有组件确实依赖调度时才启动完整管理器。不要为验证一次参数透传，先启动整套 Ray、多个工作进程、GPU 或训练任务。

允许使用小型本地测试数据或替代与待验证命题无关的外部服务；不能复制危险函数冒充目标运行、替换安全开关的决策、伪造接口返回值，或直接调用危险操作后声称完整入口已验证。插桩只能观察行为；涉及目标分支时，需用未插桩的真实调用补证，否则写明覆盖不足。

脚本至少留下：

1. 实际入口、配置、源码版本和镜像编号。
2. 良性正向观察及相同输入的针对性负向对照。直接调用另一个无关函数不是同一防护条件的对照。
3. 标记机制自身可用的检查，避免“标记未写成功”造成假阴性。
4. 哪些路径已实际运行、哪些只有源码证据、哪些仍缺失。

`confirmed` 必须有真实目标执行和负向对照证据；只有源码分析、字符串匹配、模拟返回或未运行的脚本时不得确认。前置条件未核实时为 `inconclusive`；执行所需能力缺失时为 `blocked`；`rejected` 需要具体反证。运行确认只覆盖已执行的入口，不扩大为默认配置、远程攻击或整个训练流程均已验证。

## 执行器与并发约束

- 使用任务给出的 `run_verify.sh`，沿用断网、非 root、能力限制和资源限制。不要用默认 root 的临时 `docker run` 代替验收，不通过开放网络、增加权限或绕过资源限制让试验“成功”。
- `timeout_seconds` 是单次验证脚本时限，不是智能体剩余时间。命令必须有期限；读一次结果再决定下一步，不用长串 `sleep` 轮询假装进展。
- 若出现 Ray 启动、依赖缺失或资源错误，先判断该组件是否与待验证命题有关。可以在原限制内简化一次调用；没有新证据时不连续尝试多个进程数、PID 上限和完整管理器组合。
- 每个任务只修改自己的输出目录、测试数据和容器。不读写其他并发队员的结果，不修改目标源码，不更新共享环境镜像；清理只针对本任务明确创建的资源。

### 当前非空目录冲突的交接方式

当前包装脚本要求把验证脚本写到 `output_run_dir/harness/`，而 `run_verify.sh` 会拒绝非空 `--run-dir`。这属于调度契约冲突，不是目标漏洞结论。

若调用任务指定的执行命令得到退出码 6 和 `RUN_DIR 非空`：

- 保留指定位置的脚本，检查它仍存在且可执行，然后结束智能体，让 `phase4_verify_agent.sh` 现有的 `invoke_runner` 负责暂存并执行。
- 不清空或搬走整个输出目录，不删除阶段回执，不反复试同一命令，也不手写 `verify-report.json` 冒充执行器报告。
- 在本任务目录写 `handoff.json`，包含 `finding_id`、`verdict: "inconclusive"`、真实错误、脚本路径及“待包装脚本执行”的限制；可把它提交给阶段交付工具后结束。该回执只说明交接文件可读，最终结论由之后的真实执行报告决定。
- 此方式仅适用于上述包装脚本接管的任务。独立调用没有接管者时，如实报告调度受阻，不能声称随后一定会执行。

## 交付与停止

实际执行后，读回 `verify-report.json`、`verdict.json` 和证据文件，核对候选编号、版本、命令、退出码及文件存在性。副作用发生后下游程序报错时，分别记录“已观察到的行为”和“未完成的后续流程”，不要以程序非零退出直接否定先前的真实证据。

优先交付有效脚本和已知限制，而不是一直探索到外层超时。首次可行性检查若已确定缺能力，就留下诊断及 `blocked`/`inconclusive` 结论；不要为了凑满流程重建环境。

阶段提交只引用本任务真实文件。`needs_revision` 先分类：可修复的文件或字段错误，修改后再交；未改变输入的相同错误、缺执行能力或验收器契约冲突，记录回执和修复需求后停止。`accepted` 不等于动态验证或人工验收通过。

技能改进候选只引用本任务输出目录中的实际证据；源码路径可写进说明，但不要作为工具的输出证据路径。不要把一次资源不足推广成所有项目都必须放宽限制，也不要把现有工具缺陷固化成永久技能规则。


## 临时运行环境与正式交付分开

虚拟环境、安装缓存和运行中间目录放在 VERIFY_WORK_DIR（未设置时用 mktemp -d 建立的临时目录），不要建在 evidence/ 或正式验证脚本目录内。正式交付保留验证脚本、明确引用的证据、环境定义和依赖版本；报告中引用的附件必须真实存在。Python 虚拟环境本体不是证据；交付器仅保存配置、文件摘要和链接文本的运行环境快照，不把容器解释器复制到宿主机。不得用环境快照替代验证脚本或证据文件。

## 工作目录与交付目录

验证入口为每个项目、轮次和候选问题分配独立工作区，通过 `VERIFY_WORK_DIR` 提供，并将智能体的当前目录设为该工作区。临时目录通过 `TMPDIR` 提供。原型、依赖安装和缓存均写入工作区，不得在仓库根目录创建 `.verify-work-*`、`.verifyscratch` 或其他临时目录。仓库脚本和技能使用任务提供的绝对路径或工作区中的 `.claude` 配置链接访问。

验证脚本和报告引用的附件必须保存到任务指定的正式交付目录；工作区不是交付物，不得把临时文件路径当成可长期引用的证据。不要自行清理其他任务的工作区。
