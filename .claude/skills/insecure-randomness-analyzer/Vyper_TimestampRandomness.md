# Vyper - 时间戳随机性漏洞

**漏洞类型：** 不安全的随机数生成  
**适用场景：** DeFi 奖励分配、游戏抽奖、NFT 稀有度生成  
**核心问题：** 使用 `block.timestamp` 作为随机源，矿工可在 ±15 秒容差范围内操纵出块时间

---

## Details

**典型代码特征：**
```vyper
@external
def get_winner() -> address:
    # ❌ 直接使用时间戳
    random_index: uint256 = block.timestamp % self.participants_count
    return self.participants[random_index]

@external
def mint_random_nft():
    # ❌ 哈希混淆仍可预测
    seed: bytes32 = keccak256(concat(convert(block.timestamp, bytes32), convert(msg.sender, bytes32)))
    rarity: uint256 = convert(seed, uint256) % 100
```

**快速定位核心操作（L1：关键词扫描）：**
- 全局搜索 `block.timestamp` 和 `block.prevrandao`（0.3.4+ 替代 `block.difficulty`）
- 检查是否用于 `%` 取模、`keccak256()` 哈希种子、数组索引选择
- 定位涉及 `send()`、`raw_call()`、状态变量赋值的资产分配逻辑
- 关注函数名含 `random`、`lottery`、`draw`、`mint`、`reward` 等关键词

**快速定位保护机制（L3：逐行读）：**
- 检查是否调用外部随机源（Chainlink VRF 接口、Oracle 合约）
- 确认是否实现 commit-reveal 模式：先存储承诺哈希，跨区块后揭示
- 验证是否混合多个不可控变量（`block.number`、`blockhash()`、`tx.origin`、多用户输入）
- 排查是否存在冷却期检查或时间窗口限制（注意：仅缓解不能消除）
- 检查 `@view` 或 `@pure` 装饰器：可预测函数尤其危险

## Classify

**研判为高危漏洞：**
- 时间戳直接或通过简单哈希影响高价值资产分配（抽奖中奖、NFT 稀有属性、大额奖励）
- 允许用户在同一区块内多次调用或通过回滚交易重试
- 矿工可通过微调时间戳（±15 秒）产生经济套利且收益 > 作恶成本
- 无外部熵源或多方参与机制介入

**误报条件：**
- 仅用于非关键时间记录（事件日志、截止时间检查、冷却期计算）
- 随机结果不影响资产分配或权限决策（纯展示逻辑）
- 与多个独立不可控链上变量组合使用，且单一变量操纵成本超过收益 10 倍以上
- 已集成可验证随机函数（VRF）作为主要随机源

**代码异味：**
- 低价值场景使用时间戳但缺乏风险注释
- 存在成熟替代方案（如 Chainlink VRF）但为节省 Gas 使用时间戳
- 过度混合参数（10+ 个变量）试图"掩盖"时间戳弱点但未解决根本问题
- 测试环境或 PoC 代码未标注"不适用于生产"

## Low risk

**低风险评级场景：**
1. **经济不可行性**：矿工操纵成本（MEV 贿赂、算力投入）远超潜在收益（需结合当前 Gas 价格和奖池规模评估）
2. **多变量稀释**：结合至少 3 个独立不可控因素（如 `blockhash(block.number - 1)`、历史交易哈希、多用户输入），单一时间戳操纵影响权重 < 20%
3. **非金融场景**：仅影响游戏娱乐体验（无资产损失）、UI 元素排序、视觉效果随机
4. **跨区块延迟**：实现两阶段机制且揭示阶段引入未来区块哈希（虽仍有 reorg 风险但攻击窗口显著收窄）
5. **金额上限限制**：单次随机决策涉及金额 < 当前区块 priority fee × 100（攻击成本阈值）
6. **权限约束**：仅白名单地址可触发随机逻辑且成员受信任或有连带责任机制

**注意**：即使评为 Low，仍应在报告中建议迁移至 VRF 或承诺-揭示方案，避免未来业务升级时风险等级提升。

## 审计专业技巧

### 1. 真实漏洞 vs 误报的快速识别框架

**红旗指标（必然是漏洞）：**
- `block.timestamp % array_length` 直接选择中奖者或分配奖励（可直接构造攻击）
- `keccak256(block.timestamp)` 单独作为 NFT tokenID 或稀有度因子
- 函数在同一交易内可重复调用且结果不同（时间戳在单块内不变，说明有其他变量如计数器，但计数器往往可控）
- 时间戳作为 `secret_key` 参与私密承诺哈希（矿工预知后可生成碰撞提前准备）

**绿旗指标（可能是误报）：**
- 时间戳仅用于 `require(block.timestamp > deadline)` 截止时间检查
- 随机值被立即"消耗"（如单次抽签后置零），无法重放利用
- 时间戳与用户输入、交易哈希、现有状态深度混合（至少 5+ 个独立源）且每源权重均衡
- 合约显式实现了承诺-揭示两阶段机制，且揭示阶段在 N 个区块后进行

### 2. 现场审计检查清单

**第一步：功能影响力评估（5 分钟）**
1. 确定时间戳影响的资产类型和额度：
   - 高价值：主代币奖励、NFT 白名单分配、借贷利率随机浮动
   - 中价值：LP 费用分摊、积分奖励、小额 air-drop
   - 低价值：事件日志序号、UI 展示顺序、测试变量
2. 计算单次操纵的预期收益：`(potential_gain - miner_fee) / miner_bribe_cost`
3. 若收益 < 0.1，标记为误报候选项

**第二步：矿工攻击成本分析（10 分钟）**
1. 时间戳精度：检查代码是否依赖秒级 (`block.timestamp`) 还是区块高度 (`block.number`)
   - 秒级：矿工可在 ±15 秒范围调整（Ethereum PoS 实际 ±1 秒）
   - 区块高度：无法调整（关键指标）
2. 重试成本：
   ```
   若函数可重试 N 次 → 攻击成本 = miner_bribe / N
   若单次决策后不可重复 → 成本保持高位
   ```
3. 对标当前 MEV 市场：若收益 < 一次三明治攻击利润 (典型 0.1-10 ETH)，不现实

**第三步：代码深度审查（15 分钟）**
```vyper
# 真实漏洞示例：直接利用时间戳
random_winner: address = self.participants[block.timestamp % len(self.participants)]
reward_amount: uint256 = block.timestamp % MAX_REWARD  # 矿工可控制奖励额
# 攻击成本：仅需打包 1 笔交易，成本 = 标准 Gas 费
---

# 误报示例：多源混合但权重不均
index: uint256 = (
    (block.timestamp % 10) +  # 权重 10% (矿工可控)
    (blockhash(block.number - 1)[0] % 10) +  # 权重 10% (矿工不可控)
    (msg.sender[0] % 10) +  # 权重 10% (用户确定)
    (self.global_counter % 10) +  # 权重 70% (合约状态，难以操纵)
)
# 即使矿工控制时间戳，其影响力仅 10%，总体随机性仍可信
```

### 3. 常见陷阱与应对

**陷阱 1：承诺-揭示≠安全**
- 审计师误以为 commit-reveal 完全解决问题
- 实际风险：揭示在内存池可见，矿工看到后可选择性打包或忽略
- 对标做法：需要加入预言机确认或锁定期防止 reorg（>= 15 个区块）

**陷阱 2："足够复杂"论**
- 代码混合 8+ 变量就自认为随机
- 实际评估：需计算单变量操纵对全局结果的影响范围（信息熵分析）
- 示例：128 位哈希虽有 2^128 种可能，但若时间戳决定高 32 位，降低到 2^96（仍可重复找到目标）

**陷阱 3：低交易量=低风险**
- 早期项目交易少，假定攻击不划算
- 实际：DeFi 协议可能后期增长，需前瞻性评估
- 建议：标记为"当前低风险，增长后需立即修复"

**陷阱 4：VRF 集成不完全**
- 合约导入了 Chainlink VRF 但仍有 fallback 时间戳逻辑
- 检查：搜索所有随机源路径，确认无任何分支使用 `block.timestamp`

### 4. 报告撰写建议

**对于高危漏洞：**
- 提供完整 PoC：展示矿工如何通过 `--block.timestamp` 参数控制结果
- 量化风险：计算典型奖池规模下的实际经济动机
- 修复优先级：必须在上线前修复，不接受临时措施

**对于低风险误报：**
- 承认代码存在理论漏洞但说明为何实际不可利用
- 给出改进方向而非绝对否定（如"当奖池 > 100 ETH 需升级至 VRF"）
- 计算阈值临界点：明确告知在何种增长规模下需重新评估
