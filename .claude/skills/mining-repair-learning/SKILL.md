# 挖掘修复学习

## 技能组合

本技能负责组合，不替代已有分析能力。按以下顺序选择相关文件，不要一次加载全部技能：

1. `verification-experience-analyzer`：关联红蓝证据，区分误报、已确认、未知和受阻。
2. `repair-scope-analyzer`：判断共享或仓库专属作用域及跨项目失效边界。
3. `knowledge/playbooks/evidence-first.md` 与 `reachability.md`：检查证据链和可达性。
4. `knowledge/false-positives/README.md`、`knowledge/cases/`、`knowledge/project-types/` 和 `knowledge/projects/`：复用历史反例、项目类型和项目知识。
5. 按候选类别选择现有分析技能，例如 `access-control-analyzer`、`ssrf-analyzer`、`command-injection-analyzer`、`model-loading-analyzer`、`business-logic-analyzer`；只读取与根因相关的技能。
6. 最后用本技能把上述结论写成下一轮可执行的修复 Markdown。不得绕过前两类技能直接凭标题写规则。

## 输入证据

- 蓝队验证结论、红队实际运行和独立审核结果、人工整理结论。
- 候选问题的根因、入口、默认配置、可达性、反证和来源项目。
- 证据等级与来源问题实例。实际运行、独立审核和人工结论才是可信证据；静态相似与未知结论不能冒充可信证据。

## 经验归纳步骤

1. 先判断结论是误报、已确认、未知还是环境受阻。未知与受阻不能形成误报排除规则。
2. 误报经验必须抽象出“为什么不是漏洞”的反证，例如默认回环绑定、安全加载、受信输入、有效认证或不可达前提。
3. 已确认经验抽象出“下一轮先看哪里、怎样建立证据、怎样最小验证”，不要只写漏洞标题。
4. 同一根因的多个项目实例可形成共享经验；只有单项目事实时保持仓库专属，不得为了共享而扩大语义。
5. 检查反例和边界：代码、默认配置、信任边界变化后，旧经验必须重新验证。

## 修复内容要求

- 保留原始根因，写清适用前提、下轮动作和失效条件。
- 误报排除不得只按类别、文件名、危险函数或关键词忽略候选。
- 共享修复不引用单项目文件路径；项目修复可以引用项目入口和验证配方。
- 不写武器化利用代码，不写秘密信息，不把候选写成已发布。

## 输出边界

学习智能体只输出候选文档。确定性主流程负责证据校验、隔离候选重跑、红蓝验证、评估、发布和回滚。学习智能体不得跳过这些步骤。
