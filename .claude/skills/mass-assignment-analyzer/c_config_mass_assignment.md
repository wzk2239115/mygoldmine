# C/C++ 配置批量赋值漏洞

## Details

### 漏洞成因
在使用 C/C++ 编写的服务端或嵌入式系统中，常通过配置热更新、YAML/JSON/TOML 解析或远程管理接口来更新运行时参数。如果配置载荷被直接映射到全局配置结构体，且缺乏字段白名单或权限校验，攻击者可提交额外字段修改敏感参数，如启用调试模式、放大资源配额、替换证书路径，甚至开启远程命令执行接口。在多租户或集群环境中，错误的批量赋值还可能破坏隔离。

### 代码示例

**易受攻击的代码：**
```c
typedef struct {
    int log_level;
    int max_clients;
    bool enable_remote_shell;
} server_config_t;

int apply_config(const char *json) {
    server_config_t cfg;
    // 直接解析到结构体，未限制字段
    json_to_struct(json, &cfg, sizeof(cfg));
    // 攻击者可传 enable_remote_shell=true
    g_server_config = cfg;
    return 0;
}
```

**另一个不安全示例（YAML 配置覆盖）：**
```cpp
struct FeatureFlags {
    bool newUI;
    bool betaMode;
    bool allowSuperAdmin;
};

void updateFlags(const YAML::Node &node) {
    FeatureFlags flags = g_flags;
    for (auto it: node) {
        std::string key = it.first.as<std::string>();
        // 未验证 key 是否允许
        setFlag(flags, key, it.second.as<bool>());
    }
    g_flags = flags; // allowSuperAdmin 可被恶意开启
}
```

### 快速定位技巧

#### 核心操作定位（审计等级：L1-L2）
**关键词扫描：**
- 配置解析：`json_to_struct`, `yaml-cpp`, `libconfig`, `boost::property_tree`
- 热更新入口：`apply_config`, `reloadConfig`, `updateSettings`
- 字段映射表、遍历键值对的循环
- 与权限/认证相关字段（`debug`, `remoteShell`, `admin`）

**定位步骤：**
1. 搜索配置更新函数并查找解析逻辑。
2. 检查结构体中是否包含安全敏感字段。
3. 跳读（L2）确认是否存在白名单或权限校验。

#### 保护机制定位（审计等级：L2-L3）
**检查是否存在：**
- **字段白名单：** 仅允许更新部分字段。
- **敏感字段保护：** 对 `enable_remote_shell` 等字段忽略或需要额外授权。
- **签名验证：** 配置包需通过数字签名或 HMAC 校验。
- **版本控制：** 防止旧配置覆盖新安全设置。

**定位技巧：**
- 确认配置更新函数是否检查调用者身份。
- 追踪配置从解析到持久化的整个流程，避免中途绕过。
- 检查配置文件是否允许 `include`/`anchor`，避免引入新字段。

#### 审计等级标注

| 场景 | 审计等级 | 说明 |
|------|----------|------|
| 配置字段严格枚举且有签名校验 | **L0（快速跳过）** | 安全程度高 |
| 白名单限制 + 敏感字段忽略 | **L2（跳读）** | 验证覆盖范围 |
| 直接将配置映射到结构体 | **L3（逐行读）** | 高风险 |
| 集群广播/多节点同步配置 | **L4（跨模块追踪）** | 需分析全流程 |

## Classify

### 研判标准

#### 确认漏洞
判定为漏洞需满足：
1. **配置载荷可控**（外部输入或低权限用户）。
2. **自动映射/覆盖** 未过滤敏感字段。
3. **能修改安全关键参数**，导致越权或提升权限。

#### 误报
可视为误报的情形：
1. 配置更新需高权限并有多因素认证。
2. 白名单仅允许安全字段，敏感字段在代码中硬编码。
3. 配置文件只读且由签名验证，不接受客户端输入。

#### 代码异味
需关注的风险点：
1. 配置解析函数返回值未检查，导致部分字段默认为危险值。
2. 依赖黑名单过滤敏感字段，容易遗漏。
3. 配置合并逻辑使用浅拷贝，可能覆盖嵌套结构。
4. 缺乏审计日志，难以追踪异常变更。

## Low risk

### 低风险评级场景

#### 1. 只读配置热加载
- **场景：** 配置仅包含非敏感参数，如 UI 设置。
- **风险评估：** 危害有限，但仍需防止滥用。

#### 2. 内部受控更新
- **场景：** 仅允许 Ops/CI 工具通过受信通道更新。
- **风险评估：** 攻击面较小，但需防凭证泄露。

#### 3. 多重验证机制
- **场景：** 更新前需要签名 + 审批流程。
- **风险评估：** 风险较低，但仍需确保流程不可绕过。

#### 4. 沙箱/容器隔离
- **场景：** 即便参数被修改，进程权限受限，影响范围有限。
- **风险评估：** 降低危害，但不可替代修复。

### 风险降级条件总结
| 条件 | 降级理由 | 建议优先级 |
|------|----------|------------|
| 高权限 + 审批流程 | 攻击面小 | 中 |
| 白名单 + 签名保护 | 技术防护完善 | 低 |
| 只读或非敏感配置 | 危害有限 | 中 |
| 权限隔离/沙箱 | 限制影响 | 高（仍需监控）|
