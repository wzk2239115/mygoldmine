# Node.js 代码注入：setTimeout/setInterval 执行用户输入

## Details

### 漏洞成因

Node.js 中的 `setTimeout()` 和 `setInterval()` 函数第一个参数可接收函数或字符串，当传入字符串参数时会通过内部 `eval()` 机制执行代码。若字符串由用户输入构造，攻击者可通过注入恶意代码实现任意代码执行，造成系统命令执行、数据盗取等严重安全威胁。

### 代码示例

```javascript
// 危险：用户输入直接作为 setTimeout 字符串参数
const userDelay = req.query.delay;
const userCode = req.query.code;
setTimeout(userCode, parseInt(userDelay));  // code 参数被 eval 执行

// 危险：动态构造代码字符串
const userId = req.params.userId;
const code = `console.log('User: ${userId}');`;
setTimeout(code, 1000);

// 危险：setInterval 执行用户数据
const callback = req.body.callback;
setInterval(callback, 5000);  // callback 被解析为代码字符串

// 危险：模板字符串拼接
const userInput = req.query.action;
const script = `process.env.SECRET = '${userInput}'; performAction();`;
setTimeout(script, 100);
```

### 快速定位核心操作 `[L1:关键词扫描]`

- 关键函数搜索：`setTimeout`、`setInterval`、`setImmediate`
- 特征标记识别：
  - 第一个参数为字符串字面量或字符串变量（非函数对象）
  - 参数中包含用户可控变量（来自 URL、请求体、环境变量等）
  - 使用模板字符串或字符串拼接构造代码
  - 涉及 `eval()` 类函数的参数数据流
- 示例搜索模式：
  ```
  setTimeout\s*\(\s*["`].*\${|setTimeout\s*\(\s*user|setTimeout\s*\(\s*req\.
  setInterval\s*\(\s*["`]|setImmediate\s*\(\s*["`]
  ```

### 快速定位保护机制 `[L2:跳读]`

**代码语言层防护：**
- 参数传递机制：检查是否已改为仅接收函数对象（避免字符串参数）
- 代码检查：setTimeout 调用前是否存在显式的参数类型检查（`typeof code === 'function'`）
- 白名单机制：参数值是否来自固定的安全函数集合或枚举值

**输入验证层防护：**
- 字符过滤：是否禁用危险字符（`;`, `\n`, `` ` ``, `${}`, `require`, `eval`等）
- 长度限制：字符串参数长度上限约束
- 格式约束：参数是否符合固定格式（如仅数字、纯字母等）

**执行上下文隔离：**
- VM/Worker 隔离：是否使用 `vm.Script` 或 Worker 线程进行代码隔离
- 权限限制：脚本执行是否在沙箱环境或最小权限上下文
- 环境控制：是否清理全局作用域中的敏感对象（如 `require`、`process`、`global` 等）

## Classify

### 漏洞判定理论

**确定为漏洞的必要条件：**
1. `setTimeout`/`setInterval` 的第一个参数为用户可控的字符串
2. 字符串参数未经充分验证或验证机制可绕过
3. 代码在 Node.js 标准环境中执行，可访问 `require`、`process` 等全局对象

**判定流程：**
- **参数类型检查**：参数是否严格为函数对象
  - 强制函数类型（如 `if (typeof callback !== 'function') throw Error`） → 低风险
  - 接收字符串参数 → 继续分析

- **数据源追踪**：
  - 字符串来自外部输入（请求参数、文件、网络等） → 漏洞
  - 字符串来自内部常量或受控配置 → 低风险

- **验证机制评估**：
  - 完整白名单覆盖所有分支 → 低风险
  - 黑名单过滤（仅禁用部分特殊字符） → 漏洞（可绕过）
  - 无验证 → 漏洞

- **隔离机制评估**：
  - 使用 `vm.Script` 或 `vm.runInNewContext()` 沙箱执行 → 风险降低
  - 使用 Worker 线程隔离 → 风险降低
  - 直接在主线程全局作用域执行 → 高风险

**误报的典型特征：**
- setTimeout 的第一个参数是编译时常量函数或预定义的函数引用
- 虽有字符串参数但明确为延迟时间参数（第二参数），不是代码参数
- 字符串参数经过完整的白名单验证或类型强制

**代码异味的识别：**
- setTimeout 参数来源不明确，需深入追踪数据流（L4:跨模块追踪）
- 存在条件分支动态决定是否执行代码字符串
- 字符串构造涉及多个用户输入源的拼接
- 虽有某种防护但防护机制不完整或存在已知绕过方法

## Low risk

### 低风险评级场景

**场景一：严格的参数类型限制**
- setTimeout/setInterval 的第一参数经过显式类型检查，仅接受函数对象
- 类型验证在参数传入时立即执行（如 `if (typeof code !== 'function') throw new Error()`）
- 所有调用路径均受此类型检查保护
- 评级依据：字符串代码执行通道完全封闭，攻击面消除

**场景二：完整的字符串白名单验证**
- 若必须支持字符串参数，字符串值严格限定于预定义的安全脚本集合
- 白名单经过业务需求完整设计，覆盖所有代码分支
- 用户输入仅用于索引选择白名单项，不参与字符串拼接或模板构造
- 评级依据：参数空间完全受控，无代码注入空间

**场景三：沙箱隔离执行**
- 使用 Node.js `vm` 模块的 `Script`、`runInThisContext()` 或 `runInNewContext()` 进行代码隔离
- 沙箱上下文已清理危险全局对象（禁用 `require`、`process`、`global.eval` 等）
- 沙箱使用最小化权限集，仅提供业务所需的受限 API
- 评级依据：即使代码被执行，隔离环境限制了攻击能力

**场景四：Worker 线程隔离**
- 代码执行委派至独立的 Worker 线程而非主线程
- Worker 初始化时清理全局环境，禁止访问主线程敏感资源
- Worker 进程权限受限（如通过系统级进程隔离）
- 评级依据：进程级隔离限制了代码执行的系统影响范围

**场景五：严格的内容验证组合**
- 虽不采用完整白名单，但包含多层联合防护
- 例：长度严格限制（<50 字符）+ 字符集约束（仅字母数字）+ AST 解析验证 + 执行超时控制
- 各防护层独立有效，共同覆盖了主要利用向量
- 评级依据：纵深防御和内容约束大幅提升攻击难度

**场景六：仅内部使用且权限隔离**
- setTimeout 字符串参数仅在内部业务逻辑中使用，不直接接收外部用户输入
- 代码执行仅在特定权限用户（如管理员）操作下触发
- 执行环境运行于容器或虚拟机内，进程级隔离限制了系统影响
- 评级依据：受众限制和环境隔离降低了漏洞的实际风险

### 评级决策补充

- 仅有部分字符过滤（黑名单）且存在已知绕过 → 中等风险或高风险（非低风险）
- 参数类型检查存在但某些分支遗漏 → 中等风险（非低风险）
- 沙箱隔离但全局对象未清理（如 `require` 仍可访问） → 中等风险（非低风险）
- 单一防护层有效但缺乏纵深防御且传入为用户直接输入 → 中等风险（非低风险）
