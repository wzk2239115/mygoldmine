# 原生内存安全分析器

分析原生代码中“对象从哪里来、谁持有、何时释放、释放后是否还会使用”这条生命周期链。适用缺口：空指针解引用（NPD）、内存泄漏（MLK）、释放后使用（UAF），以及它们的相邻问题重复释放和越界读写。

## 概述与边界

- **聚焦**：原生内存和资源生命周期错误，包括指针、引用计数、文件描述符、CUDA 内存与流、跨语言 FFI 所有权。
- **输入**：项目源代码、构建文件、入口点、协议解析与请求处理路径、错误处理路径、并发和回调注册位置。
- **输出**：候选问题清单、每个问题的来源、危险操作、可达条件、影响、修复建议和误报排除说明。
- **不做**：不把“缺少一次释放”直接当成漏洞；不把没有外部触发条件的单次初始化泄漏写成高危；不执行漏洞利用；不把静态命中写成运行时已确认。

普通托管语言的空引用通常由 `error-boundary-analyzer` 处理。只有在涉及本地扩展、显式 `unsafe`、FFI、外部内存或手工生命周期管理时，才进入本技能范围。

**提前退出**：

- 项目只使用有完整生命周期保证的托管语言，且没有 `unsafe`、FFI、C 扩展或外部内存。
- 项目没有处理外部输入、二进制协议、文件、模型权重或并发回调，内存操作只发生在启动阶段。
- 所有原生内存都由可靠的第三方库封装，项目没有直接调用分配、释放、指针解引用或引用计数接口。

## 术语与 CWE 对应

| 类型 | 中文说明 | 常见 CWE |
|------|----------|----------|
| 空指针解引用 | 可能为空的指针或引用在未检查时被解引用 | CWE-476 |
| 内存泄漏 | 分配或获取的内存、引用计数在生命周期结束后没有释放 | CWE-401、CWE-772 |
| 释放后使用 | 对象已经释放、关闭或销毁后仍被读取或写入 | CWE-416 |
| 重复释放 | 同一对象被释放两次 | CWE-415 |
| 越界读写 | 索引或长度计算错误导致访问分配范围之外的内存 | CWE-787、CWE-125 |

## 输入来源与危险操作

| 类别 | 具体位置 |
|------|----------|
| 输入来源 | 网络报文的长度、索引、类型和数量；文件与配置字段；命令行参数；环境变量；进程间通信与共享内存；模型权重和张量形状；回调参数；异步任务与线程事件；可能失败的查找、分配和打开操作 |
| 危险操作 | 指针解引用、数组索引、`malloc` / `calloc` / `realloc` / `free`、`new` / `delete`、`fopen` / `fclose`、`open` / `close`、`strdup` / `strndup`、容器指针与迭代器、`std::move` 后继续使用、`realloc` 失败后覆盖原指针、`Py_DECREF` / `Py_XDECREF`、`cudaMalloc` / `cudaFree` / `cudaMemcpyAsync` / `cudaStreamDestroy`、Rust `unsafe` 中的 `ptr::read` / `ptr::write` / `drop_in_place` / `Box::from_raw`、Go 的 `unsafe.Pointer` 与 `C.free` |
| 安全对照 | 分配、查找或打开后立即检查空值；单一所有权；RAII 与智能指针；引用计数纪律；释放后清零指针；回调注销；CUDA 流同步；边界检查；长度溢出检查；ASan、UBSan、Valgrind 和 Miri 等动态检查 |

## 检测步骤

### 步骤 0：确认审计范围和语言

1. 记录项目主要语言、构建方式、原生代码目录和外部入口。
2. 标记需要重点检查的语言边界：C/C++、CUDA、Rust `unsafe` 与 FFI、Go 的 cgo 与 `unsafe`、Python 的 C 扩展。
3. 找出所有直接管理内存或资源的位置：分配、释放、打开、关闭、引用计数、流创建与销毁。

### 步骤 1：建立对象生命周期

对每个可疑对象记录：

- 分配或获取位置；
- 当前持有者；
- 所有权是否转移；
- 释放、关闭或销毁位置；
- 所有可能提前返回、跳转和异常路径；
- 是否存在别名、回调、缓存或跨线程共享。

没有完整生命周期记录时，只输出待核实假设，不直接给高危结论。

### 步骤 2：空指针解引用

1. 找到可能返回空值的来源：分配函数、查找函数、字符串查找、打开文件、创建套接字、加载动态库、外部回调参数、可能失败的系统调用。
2. 检查解引用前是否有有效检查。有效检查包括：返回值判断后提前返回、失败分支释放资源、断言之外的生产路径检查。
3. 重点检查：分配失败后的错误清理路径、`goto` 标签、循环内的重复分配、`realloc` 返回值直接覆盖原指针、结构体字段未初始化就被使用。
4. 只有空值能由外部输入、资源耗尽或失败路径触发，并且后续解引用可到达时，才按漏洞候选输出。

### 步骤 3：内存泄漏

1. 找到分配或获取资源的位置，列出同一函数或对象生命周期内所有退出路径。
2. 检查错误路径和提前返回：分配后检查失败、参数校验失败、循环中断、异常抛出、`goto` 跳过清理。
3. 检查指针覆盖：同一变量被第二次分配覆盖、`realloc` 失败后丢失原指针、`strdup` 结果覆盖旧值。
4. 检查引用计数：`Py_INCREF` / `Py_DECREF` 是否成对、错误分支是否漏减、容器插入失败是否回滚。
5. 检查长期容器和缓存：是否有上限、淘汰策略和清理入口；没有上限且由外部请求持续触发时，按资源耗尽风险处理。
6. 单次启动泄漏、进程即将退出前的泄漏、受上限约束的缓存不按高危报告。

### 步骤 4：释放后使用

1. 找到释放、关闭或销毁操作：`free`、`delete`、`fclose`、`close`、`Py_DECREF`、`cudaFree`、`cudaStreamDestroy`、Rust `drop` 与 `ptr::read`、Go `C.free`。
2. 在同一作用域、别名、回调、异步任务或并发线程中查找释放后的读取、写入和再次释放。
3. 重点检查：错误路径提前释放后继续使用、`realloc` 后旧指针仍被使用、容器扩容导致指针或迭代器失效、`std::move` 后继续访问、回调未注销、CUDA 流或内核未完成就释放内存、对象析构顺序错误。
4. 重复释放按释放后使用的相邻问题记录，并单独标注为重复释放。
5. 只有在释放后仍有可到达的使用路径时才报告；释放后立即退出进程且没有后续访问的路径降级。

### 步骤 5：越界读写与长度计算

1. 检查外部可控的长度、索引、数量和类型转换是否在分配、复制和索引前验证。
2. 检查乘法、加法和类型转换是否可能溢出；与 `integer-overflow-analyzer` 重叠时，本技能只报告最终导致内存访问的链路。
3. 写越界优先按高危处理；读越界按信息泄露或拒绝服务评估，除非能进一步影响控制流。

### 步骤 6：核对防护和可达性

- 是否有空值检查、边界检查、所有权转移记录、RAII、引用计数、锁、流同步和回调注销。
- 触发条件是否来自外部输入、错误路径、并发时序或资源耗尽。
- 是否有动态检查工具配置和测试用例；没有运行时证据时保持候选状态。

## 判定矩阵

| 情况 | 建议结论 |
|------|----------|
| 外部输入控制长度或索引，未检查就写入数组或缓冲区 | 高危：越界写，可能导致内存损坏或代码执行 |
| 可能返回空值的分配或查找结果未检查就解引用，且错误路径可到达 | 中危到高危：空指针解引用，通常导致拒绝服务 |
| 外部请求每轮都泄漏一块内存，且没有上限 | 中危到高危：持续内存增长，最终拒绝服务 |
| 释放后仍可通过正常请求路径读取或写入 | 高危：释放后使用，可能导致内存损坏或代码执行 |
| 释放后仍可通过并发时序读取或写入 | 高危：释放后使用，需要说明并发窗口 |
| 同一对象被释放两次，且路径可到达 | 高危：重复释放 |
| 只在启动阶段泄漏一次，或进程退出前不释放 | 低危或提示，不单独作为漏洞 |
| 有上限的缓存保留对象直到淘汰 | 不算内存泄漏，除非淘汰条件本身失效 |
| 托管语言中的普通空引用，没有本地扩展或 `unsafe` | 交给 `error-boundary-analyzer`，本技能不报告 |

## 语言特定检查

### C/C++

- 分配和打开：检查 `malloc`、`calloc`、`realloc`、`strdup`、`fopen`、`dlopen`、`opendir` 的返回值。
- 释放和关闭：检查 `free`、`delete`、`fclose`、`close` 之后的访问、重复释放和别名释放。
- 容器失效：`std::vector` 扩容后旧指针、`std::string::c_str()` 在修改后继续使用、`erase` 后迭代器继续使用、`std::string_view` 指向临时对象。
- 所有权：`std::unique_ptr::release`、`std::move` 后继续使用、裸指针与智能指针混用。
- 错误路径：`goto cleanup` 是否跳过释放、`realloc` 失败后原指针是否丢失、结构体字段是否初始化。

### CUDA

- `cudaMalloc` 返回值是否检查；分配大小是否可能溢出。
- `cudaFree`、`cudaStreamDestroy`、`cudaEventDestroy` 是否在异步操作完成前调用。
- `cudaMemcpyAsync` 的源或目标内存在传输完成前是否被释放或复用。
- 内核参数中的指针和设备内存生命周期是否覆盖异步执行窗口。

### Rust

- `unsafe` 块中的原始指针解引用、`ptr::read`、`ptr::write`、`drop_in_place`、`Vec::from_raw_parts`、`Box::from_raw`、`CString::from_raw`。
- FFI 所有权：C 侧分配由谁释放、`CString` 与 `CStr` 的生命周期、跨语言回调中的引用是否仍然有效。
- `mem::forget`、`Box::leak`、`Arc` 循环引用是否造成有意或无意的泄漏。
- 只有安全代码且没有 FFI 时，不报告编译期已经保证的内存安全问题。

### Go

- cgo 的 `C.malloc` / `C.free` 是否配对，`C.CString` 是否释放。
- `unsafe.Pointer` 转换、切片长度和容量是否越过原始分配范围。
- 长生命周期 goroutine、未关闭的 channel 和持续增长的缓冲区是否导致资源无法回收。
- 使用 `runtime.KeepAlive` 时，对象是否在外部调用完成前被回收。

### Python 的 C 扩展

- `Py_DECREF` / `Py_XDECREF` 是否在所有错误路径上成对出现。
- `PyObject_New`、`PyObject_Call` 等新建引用在失败分支是否释放。
- `PyBytes_AsString`、`PyUnicode_AsUTF8` 返回的指针是否在对象释放后继续使用。
- `ctypes`、`cffi`、`torch.utils.cpp_extension` 加载的原生库是否把 Python 对象生命周期传递给 C 侧。

## 误报排除

- 分配失败只在内存耗尽时发生，且程序立即退出：按低危或提示处理。
- 启动阶段一次性分配且不释放，但进程长期运行也不需要重复分配：不按高危泄漏报告。
- 缓存有明确上限、淘汰策略和清理入口：不算内存泄漏。
- 释放后立即返回或退出，没有任何后续访问：不算释放后使用。
- `realloc` 成功且旧指针不再使用：不算释放后使用。
- 释放后把指针置空，后续只做空值检查：不算释放后使用。
- 断言或调试构建中的检查不能保护发布构建；发布路径仍可能触发时要保留候选。
- 只有静态分析器告警、没有调用链和可达路径：标记为待核实假设，不写成已确认漏洞。
- Rust 安全代码、Go 纯 Go 代码、Java 和 JavaScript 的普通空引用：没有本地扩展或 `unsafe` 时不进入本技能。

## 输出格式

优先加载 `bug-report` 技能生成 Markdown 报告。报告文件名使用以下简写：

- 空指针解引用：`BUG-npd-...`
- 内存泄漏：`BUG-mlk-...`
- 释放后使用：`BUG-uaf-...`
- 重复释放：`BUG-doublefree-...`
- 越界读写：`BUG-oob-...`

结构化输出示例：

```json
{
  "skill": "memory-safety-analyzer",
  "findings": [
    {
      "rule": "MEM-UAF-001",
      "kind": "uaf",
      "severity": "high",
      "confidence": "high",
      "file": "src/parser.c",
      "line": 128,
      "source": "请求长度字段",
      "sink": "free(buffer) 后继续读取 buffer",
      "evidence": "L120 free(buffer); L128 parse(buffer);",
      "path": "网络入口 -> 长度校验失败 -> 提前释放 -> 错误处理继续解析",
      "trigger": "发送长度字段与声明不一致的报文",
      "impact": "释放后读取，可能造成拒绝服务或内存信息泄露",
      "fix": "释放后立即置空并跳过后续解析；统一由单一所有者释放",
      "cwe": "CWE-416"

  ]
```

Markdown 报告按严重度排序，每条必须包含：来源、危险操作、可达路径、触发条件、影响、修复建议、误报排除说明和证据文件位置。没有动态验证时，结论只写“源码级候选”，不写“已复现”。

## 修复建议

- **空指针解引用**：分配、查找和打开后立即检查返回值；失败时走统一清理路径；初始化所有指针；在接口边界使用非空约束。
- **内存泄漏**：使用单一所有权和 RAII；所有退出路径经过统一清理；覆盖指针前先释放；`realloc` 使用临时变量；引用计数在错误分支同样成对处理；长期缓存设置上限和淘汰。
- **释放后使用**：释放后立即置空；避免跨线程共享裸指针；回调注册与注销成对；容器扩容后重新获取指针和迭代器；CUDA 异步操作完成后才释放内存和流。
- **重复释放**：统一释放入口；释放后置空并在再次释放前检查；避免多个所有者分别释放同一对象。
- **越界读写**：在分配、复制和索引前校验长度、索引和类型转换；使用带边界检查的容器和接口；对乘法与加法做溢出检查。
- **验证**：在测试和隔离环境中启用 ASan、UBSan、Valgrind、Miri 或静态分析器；动态检查结果仍需保留输入、环境和运行日志，不能只用工具告警替代证据。
