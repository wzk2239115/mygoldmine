# C/C++ 不安全文件上传验证漏洞

## Details

### 漏洞成因
在 C/C++ 实现的网关、服务器或客户端程序中，常以 `fopen`、`write`、`recv`、`libcurl` 等 API 接收并保存用户上传的文件。如果仅基于文件扩展名或简单字符串比较来判断类型，未读取文件头或使用可信库进行验证，攻击者可伪装恶意脚本、动态链接库或可执行文件，从而覆盖系统文件、触发命令执行或获取敏感信息。此外，缺少文件大小限制、临时目录隔离、权限控制也会造成拒绝服务或资源耗尽。

### 代码示例

**易受攻击的代码：**
```c
int save_upload(const char *filename, const unsigned char *data, size_t len) {
    // 仅检查扩展名，攻击者可上传 .php 伪装为 .jpg
    if (!strstr(filename, ".jpg") && !strstr(filename, ".png")) {
        return -1;
    }
    FILE *fp = fopen(filename, "wb"); // 未限制存储路径
    if (!fp) return -1;
    fwrite(data, 1, len, fp);
    fclose(fp);
    return 0;
}
```

**另一个不安全示例（缺少文件头校验）：**
```cpp
bool saveImage(const std::string &path, const std::vector<uint8_t> &payload) {
    // 仅根据请求头给出的 MIME 判断
    if (payload.size() > MAX_UPLOAD_SIZE) { return false; }
    std::ofstream out(path, std::ios::binary);
    out.write(reinterpret_cast<const char*>(payload.data()), payload.size());
    // 未检查文件魔术字，未进行杀毒或内容扫描
    return out.good();
}
```

### 快速定位技巧

#### 核心操作定位（审计等级：L1-L2）
**关键词扫描：**
- 文件写入 API：`fopen`, `open`, `write`, `std::ofstream`, `FILE`, `fs::path`
- 上传函数：`save_upload`, `handle_upload`, `process_attachment`
- 类型校验函数：`strstr`, `strcmp`, `ends_with`, `CheckExtension`
- 临时目录/路径操作：`tmpnam`, `mkstemp`, `snprintf` 拼接路径

**定位步骤：**
1. 搜索上传处理函数与文件写入 API 的调用点。
2. 检查是否仅依赖扩展名判断类型或完全无校验。
3. 跳读（L2）相关代码段，确认是否验证 MIME、文件头、大小与存储路径。

#### 保护机制定位（审计等级：L2-L3）
**检查是否存在：**
- **类型验证：** 使用 libmagic、MIME 检测库、读取魔术字进行校验。
- **白名单策略：** 显式枚举允许的扩展名与 MIME，拒绝其他类型。
- **大小与数量限制：** 控制单个文件大小、总存储空间、防止压缩炸弹。
- **存储隔离：** 将上传文件保存到不可执行目录，使用随机文件名。
- **权限控制：** 上传后文件使用最小权限（chmod 600），并在访问前鉴权。

**定位技巧：**
- 关注是否使用 `realpath`/`canonicalize_file_name` 确保路径不被穿越。
- 检查上传后是否立即进行内容扫描、防病毒、图片解码等安全处理。
- 追踪文件访问流，确认是否存在直接对外暴露的下载接口。

#### 审计等级标注

| 场景 | 审计等级 | 说明 |
|------|----------|------|
| 使用专业库验证类型 + 隔离目录 | **L0（快速跳过）** | 防护充分，可快速确认 |
| 依赖扩展名 + 额外白名单检查 | **L2（跳读）** | 检查是否覆盖全部入口 |
| 完全无类型校验或允许任意扩展 | **L3（逐行读）** | 高风险，需要深入分析 |
| 上传后直接进入解析/执行流程 | **L4（跨模块追踪）** | 需跟踪处理链路与访问控制 |

## Classify

### 研判标准

#### 确认漏洞
同时满足以下条件判定为不安全文件上传漏洞：
1. **上传入口** 接受来自用户的文件且缺乏可靠的类型、内容或大小限制。
2. **存储或处理环节** 未隔离目录、未使用随机命名或未清理临时文件。
3. **攻击者可利用上传结果** 获取执行权限、覆盖敏感文件或绕过访问控制。

#### 误报
以下情况可判定为误报：
1. 上传功能仅对高可信的内部系统开放，且链路有签名/加密保障。
2. 上传文件经由白名单验证 + 内容扫描 + 隔离部署，并确认无法解析执行。
3. 上传后立即变更文件权限为不可执行、存储在非 Web 根目录、且访问需鉴权。

#### 代码异味
需记录但尚未构成漏洞的情况：
1. 仅依赖扩展名黑名单，缺少内容校验。
2. 缺少上传速率/大小限制，易被滥用为 DoS。
3. 使用临时文件但未调用 `unlink`/`remove` 清理。
4. 上传目录与应用共用，未来配置变更可能导致暴露。

## Low risk

### 低风险评级场景

#### 1. 内部灰度环境
- **场景：** 上传功能仅用于内部测试或灰度环境且有访问控制。
- **风险评估：** 攻击面有限，但仍需防范凭证泄露。

#### 2. 只读存储 + 定期清理
- **场景：** 上传后的目录对 Web 服务仅提供只读访问，并启用定期清理。
- **风险评估：** 可降低持久化风险，但仍需类型校验。

#### 3. 上传即刻转存到对象存储
- **场景：** 上传后立即存入安全对象存储，并严格控制访问 URL。
- **风险评估：** 外部可直接利用性较低，但仍需防止恶意内容传播。

#### 4. 多重扫描与人工审核
- **场景：** 上传文件需通过杀毒、内容审计及人工复核。
- **风险评估：** 可显著降低风险，但不应替代代码层防护。

### 风险降级条件总结
| 条件 | 降级理由 | 建议优先级 |
|------|----------|------------|
| 上传入口仅供可信用户 | 攻击面小 | 中 |
| 类型验证 + 隔离目录 | 技术防护到位 | 低 |
| 对象存储/只读访问 | 降低执行风险 | 中 |
| 多重扫描与审核 | 能及时发现恶意文件 | 高（仍需持续改进）|
