**Move**  
常出现在 Aptos 或 Sui 链上的资源授权、跨账户操作、模块权限控制等业务逻辑实现中，包括但不限于直接信任外部签名而未校验 message digest、未使用 Move 提供的 auth 合约原语、签名与调用参数脱钩等方式：  
- 未验证外部签名：直接信任外部传入的签名但未验证其真实性和有效性，详见：Move_UnverifiedExternalSignature.md 
## Details

**代码示例**：验证函数接收 `signature: vector<u8>` 和 `public_key: vector<u8>`，但使用任意构造的 `message` 进行 `ed25519::verify(signature, public_key, message)` 验证，而该 message 未与当前交易上下文（如 `signer::address_of()`、`timestamp::now_seconds()`、nonce）绑定，导致签名可在不同上下文复用。典型场景：授权转账函数接收外部签名，但验证时使用硬编码字符串或仅包含金额的 message，未绑定收款地址或交易序号。

**快速定位核心操作**（L2-跳读）：搜索 `ed25519::verify` / `secp256k1_ecdsa::verify` / `multi_ed25519::verify` 调用点，检查第三个参数 message 的构造逻辑。若 message 为常量、简单字符串拼接或未包含 `signer` 地址，立即标记。关注 `bcs::to_bytes()` 的序列化参数是否包含完整上下文。

**快速定位保护机制**（L3-逐行读）：检查 message 构造是否包含：①调用者地址（`signer::address_of(account)`）②时间戳/区块高度（`timestamp::now_seconds()` 或 `block::get_current_block_height()`）③nonce/counter（从 Resource 读取的递增序号）④操作目标（如转账的 to_address、amount）⑤chain_id 或合约地址。验证逻辑需在签名验证后、权限操作前。若保护机制依赖调用者自行传入完整参数（而非从链上状态读取），需额外核查参数是否可被前端篡改。

## Classify

**漏洞判定**：message 缺少任一关键绑定（调用者、时间戳、nonce、操作目标）且该签名直接授权高权限操作（资产转移、角色变更、合约升级），允许签名重放或跨上下文滥用。**误报判定**：签名仅用于只读查询、message 已通过 `aptos_framework::account::create_signer_with_capability` 等框架原语隐式绑定、或业务逻辑本身要求签名全局有效（如公钥注册）。**代码异味**：message 包含部分绑定但缺失时间戳或 nonce，导致时间窗口内可重放，需结合业务评估是否构成实际威胁。

## Low risk

①签名仅授权低价值操作（如元数据更新、非关键配置修改），重放不会造成资产损失。②合约通过外部状态（如已消费标志位 `Table<vector<u8>, bool>`）记录已使用签名的哈希，虽 message 未绑定但通过状态防重放。③操作受额外权限校验保护（如 `assert!(signer::address_of(account) == expected_admin, E_NOT_AUTHORIZED)`），即使签名可复用也无法越权。④业务场景明确要求签名永久有效（如预授权白名单），且操作频率受链上 rate limit 或金额上限约束。

## 审计专业技巧与真实案例

**关键审计视角 1：消费状态与时间窗口权衡**

真实漏洞案例：Aptos 某抵押合约设计中，提现函数接收外部签名，message 仅包含用户地址和提现金额（`bcs::to_bytes(&vec![user_addr, amount])`），未绑定 nonce。开发者自信地说"消费状态会记录"，但审计发现消费记录在 `withdraw_history` 表中，按 (user_addr, amount) 组合键去重。若用户申请提现 100 APT，审核方需 1-2 分钟才能执行提现交易。在此时间窗口内，用户可向不同收款地址（或通过中继合约）多次提交相同签名的提现请求。虽然第二次会因"已消费"被拒，但区块链上 pending 的多个提现交易可能同时被打包，造成多次扣款。这是**真实漏洞**。

区分技巧：查看消费记录生成的时机——若在 `ed25519::verify()` 验证**后**立即记录（通过 `Table::upsert()` 或 `Coin::burn()`），则保护有效；若依赖异步回调或在事件中记录，则窗口漏洞存在。

**关键审计视角 2：链上状态读取 vs 外部参数信任**

误报案例：某 Sui 游戏合约的角色升级函数接收签名和 exp 数值。初审时觉得 message 未绑定 exp（可重放升级请求），标记为漏洞。但深入理解业务后发现：①签名由游戏后端服务生成，消息为 `{user_addr, exp, timestamp, server_nonce}`；②合约验证签名后调用 `table::borrow_mut(&mut player_stats, user_addr)` 从链上状态读取当前 exp，执行 `new_exp = max(stored_exp, received_exp)`；③即使重放旧签名，exp 不会递减，重复升级也不生效。这是**误报**，但需注意后端若生成多个签名给同一用户的不同 exp 阶段，仍可通过选择旧签名降低角色数据。

区分技巧：审计时需要**追踪签名参数和链上状态的关系**。若受验证的参数（如 exp）在合约中被**正确应用**（选择更大值、检查递增、原子性操作），则风险降低。若参数可绕过状态检查或修改已确定的资产数值，则仍为漏洞。

**关键审计视角 3：跨交易 nonce 消费的完整性**

真实漏洞案例：Aptos 某权限管理合约为了支持批量操作（如一次交易中批准多个被提名者），设计消息格式为 `{operator_addr, operations: vector<Operation>}`，并使用全局 nonce 生成规则。审计发现**nonce 来自外部参数而非链上递增计数器**。开发者传入 nonce=1001，消费后链上状态为 `last_nonce = 1001`。下一次操作必须 nonce=1002。看似安全，但合约在处理向量操作时采用"尽力执行"策略：若操作 #3 失败（如被操作者不存在），后续操作中断但 nonce 仍被消费。攻击者可构造包含一个失败操作和一个资产转移操作的批量请求，若顺序调整后导致转移先执行再失败，转移难以回滚。这是**逻辑漏洞**。

区分技巧：审计涉及 nonce 的合约时，检查以下两点：① nonce 是否是原子的——单次验证和消费是否在同一交易阶段；② 向量操作的 nonce 消费时机——全量消费（所有操作成功才消费）还是逐项消费（中途失败则部分消费）。原子性不足导致双重消费或部分消费的都是漏洞。

**关键审计视角 4：时间戳绑定的精度陷阱**

误报案例：某 Aptos 订单合约要求 message 包含 `timestamp::now_seconds()`，看似完整。初审标记为安全。但深入发现时间戳粒度为"秒"，而订单有效期为 3600 秒（1 小时）。攻击者可在同一秒内提交多次签名相同的订单（因为时间戳不变），若系统按"秒+订单 ID"的复合键去重，不同订单 ID 仍可重复充分。但如果业务本身要求同一用户同一秒内只能提交一个订单，则这是受约束的场景——可能是**误报**。审计发现系统确实在签名前端加入了随机 nonce 来保证每次签单都不同，则完全无漏洞。

区分技巧：时间戳检验时需要理解**时间精度与业务频率的匹配度**。高频操作（毫秒级）需要毫秒级时间戳，低频操作（分钟级）可接受秒级。同时检查是否有其他熵源（如 nonce、操作 ID）来补充时间戳的不足。

**关键审计视角 5：签名验证点与权限操作点的间隙**

真实漏洞案例：Sui 某多签合约设计为：先用 `ed25519::verify()` 验证签名，生成签名有效的标记，再在随后的函数中使用该标记来授权操作。审计发现两个函数间存在状态修改机会——若签名验证函数读取和修改了某个共享对象（如 proposal 状态），而权限操作函数依赖该对象的后续状态，则恶意调用方可在验证后、操作前通过其他交易修改对象，造成**时间检查漏洞（TOCTOU）**。特别是在 Sui 的 shared 对象模型中，共享对象允许并发修改。

区分技巧：审计 Aptos/Sui 合约时，检查签名验证和权限操作是否在**同一函数**中完成，是否都在**同一交易块**内。若分散在多个函数或依赖外部对象状态，需进一步核查是否存在竞态窗口。Aptos 的 linear type 系统通常能保护，但 Sui 的共享对象需特别警惕。

**快速审计检查清单**

- [ ] message 是否包含 signer 地址、时间戳、nonce、操作目标的**任意四项**
- [ ] nonce 是否来自链上递增计数器而非外部参数
- [ ] 消费状态（如 Table、BitMap）是否在验证**立即后**被修改，且修改是原子的
- [ ] 对于外部参数（如金额、权限），合约是否进行了链上状态的**覆盖或最大值选择**，确保参数不能任意修改结果
- [ ] 签名验证和权限操作是否在同一函数内完成，是否存在共享对象的并发修改窗口
- [ ] 时间戳的精度是否与业务频率匹配，是否有额外熵源补充

## 深度审计技巧与攻防细节

**审计技巧 1：识别消费状态与验证之间的竞态**

在 Aptos 中，若合约使用 `Table` 或 `Vector` 存储已消费签名哈希，需要检查**写入时机**。理想情况：
```
ed25519::verify(...) -> 立即调用 table::add() 或 table::upsert()
```

常见误设计：
1. 先验证再通过事件广播消费状态（事件异步确认，区块打包期间可重放）
2. 在独立函数中验证，在另一函数中消费（两个调用间存在竞态窗口）
3. 使用 `borrow()` 读取历史记录后再修改，而非原子操作（并发调用可都通过验证）

真实案例：某 Aptos 流动性质押合约采用模式 2，验证函数返回 bool，权限函数依赖返回值。攻击者可在同一区块内构造两个交易，均通过验证但仅第一个消费，第二个因"未消费"被后续检查拒绝——看似安全，但若权限函数未严格检查返回值或通过不同路径调用，仍可绕过。

**审计技巧 2：链上状态一致性与重放窗口**

部分合约认为"只要验证了签名就安全"，忽视了签名参数与链上状态的**一致性窗口**。

场景：某交易所合约要求用户提交 `{user_addr, withdraw_amount, nonce}` 的签名。合约验证后：
```move
assert!(withdraw_amount <= user_balance, E_INSUFFICIENT);
coin::withdraw(&mut coin_store, withdraw_amount);
```

看似安全，但若 `user_balance` 在验证和 `withdraw()` 之间被修改（例如，其他合约调用或多笔快速操作），可能导致：
- 验证通过时 balance=1000，但执行时因其他操作已变为 500
- 或反之，balance 刚好足够验证但执行时不足

这是 **TOCTOU（time-of-check-time-of-use）** 问题。Aptos 的 resource 特性和 Move 的 linear type 通常缓解此问题，但需要确认逻辑正确性。

**审计技巧 3：外部参数信任度的灰色地带**

最复杂的审计场景：签名验证和状态操作之间，存在外部参数的多重处理。

例子：某 DeFi 合约支持"闪电贷"——用户签名授权 `{borrow_amount, callback_addr}`，合约向 callback_addr 发送代币，要求其在同一交易内返还。初审时认为 callback_addr 可被攻击者篡改，因此 callback_addr 应在签名的 message 中。但若后端系统要求 callback_addr 只能是**预注册白名单中的地址**，且白名单写入链上后不可修改，则 callback_addr 虽不在签名中也无法被滥用——这可能是**误报**。

真实漏洞：某合约未正确实现白名单检查，仅在事件中记录白名单，未在合约代码中强制检查。审计时需要追踪：
1. callback_addr 是否在签名 message 中 ✓
2. 若不在，是否有**链上**强制的白名单检查 ✗ 仅事件日志不算
3. 白名单何时生效，是否可被管理员临时修改

**审计技巧 4：nonce 生成与消费的熵来源**

nonce 的安全性取决于其生成方式：

- 链上递增计数器（最安全）：`counter = table::get(&counters, user_addr) + 1`
- 时间戳 + 链上计数器（较安全）：`nonce = (timestamp << 32) | counter`
- 外部参数（需验证）：用户提交，但必须检查其单调性
- 链下生成（最不安全）：若由前端或后端生成，需验证其唯一性

常见漏洞：开发者认为 nonce 来自外部参数没关系，因为"只要满足递增就行"。但如果 nonce 验证逻辑为 `assert!(nonce > last_nonce, E_INVALID_NONCE)` 而非 `assert!(nonce == last_nonce + 1, E_INVALID_NONCE)`，攻击者可跳过中间值，造成"断层"。虽然后续操作会拒绝断层 nonce，但如果这个拒绝逻辑依赖外部参数（如操作类型），则可能被绕过。

**审计技巧 5：消费状态的持久化确认**

签名消费后，需要确保消费记录**永久持久**：

- ✓ 写入 `Table<K, V>` 或 `Vector` 并通过 resource 持有
- ✓ 调用 `Coin::burn()` 等不可逆操作作为消费凭证
- ✓ 修改 resource 的字段（如 `counter` 递增）
- ✗ 仅生成事件或 emit log（事件可重放，特别是在 Aptos 的轻节点模式下）
- ✗ 依赖临时变量或函数局部状态

真实案例：某合约在验证后调用 `event::emit(SignatureConsumed { ... })`，开发者认为"事件已发出即已消费"。但审计发现合约未在链上状态存储消费记录，仅依赖索引器的事件日志。若索引器延迟或离线，重放攻击不会被检测到。正确做法是同时在链上状态和事件中记录。

**审计技巧 6：message 构造的序列化陷阱**

Move 的 `bcs::to_bytes()` 函数序列化资源时，顺序和编码方式至关重要：

陷阱 1：不同的 struct 字段顺序导致相同数据序列化不同
```move
// 错误：前端按 amount + user_addr 排列，合约按 user_addr + amount 解析
let msg = bcs::to_bytes(&(amount, user_addr)); // [100, 0x123...]
let msg = bcs::to_bytes(&(user_addr, amount)); // [0x123..., 100]
```

陷阱 2：嵌套结构的向量长度编码
```move
// vector<T> 会在序列化前加上长度前缀（varint 编码）
bcs::to_bytes(&vec![op1, op2]) // [2, op1_bytes, op2_bytes]
```

审计时需要确认前端序列化和合约反序列化的一致性。若前端使用不同库（如 js-to-move），可能存在编码差异。

**常见漏洞模式总结**

| 模式 | 真实漏洞示例 | 区分技巧 |
|------|-----------|--------|
| 消费状态延迟 | 事件日志记录，区块打包期间可重放 | 检查是否同步修改链上资源 |
| nonce 跳跃 | 外部 nonce，验证仅检查大于而非严格相等 | 追踪 nonce 消费逻辑的严格性 |
| 参数信任不匹配 | 签名中无金额，外部参数可任意修改 | 检查合约是否重新验证或读取链上值 |
| 时间窗口 | 验证后至执行前有状态修改机会 | 确认是否原子操作，是否有竞态窗口 |
| 链下生成 | 后端签名生成，客户端可重放旧签名 | 验证消费记录的链上持久性 |

**审计决策树**

1. **message 中是否包含调用者地址？**
   - 是 → 继续
   - 否 → 检查是否有隐式绑定（如 signer 参数强制指定）

2. **message 中是否包含 nonce 或时间戳？**
   - 是 → 检查 nonce 来源和时间戳精度
   - 否 → 是否有全局防重放机制（如消费表）

3. **消费状态是否**立即、原子地**写入链上？**
   - 是 → 检查消费键是否完整（不仅是地址+金额，还需 nonce）
   - 否 → 标记为高风险

4. **签名验证和权限操作是否在同一函数原子完成？**
   - 是 → 检查是否存在外部状态修改的竞态
   - 否 → 标记为中等风险，需进一步确认分离是否必要

5. **外部参数（如金额、目标地址）是否可绕过链上状态检查？**
   - 是 → 漏洞
   - 否 → 可能安全，但需验证合约逻辑的正确性
