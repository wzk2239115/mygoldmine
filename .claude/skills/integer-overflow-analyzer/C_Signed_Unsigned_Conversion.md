## Details

- **核心操作定位技巧** (L1: 关键词扫描)：扫描混合类型的赋值、函数调用参数类型不匹配、或显式类型转换 `(unsigned)signed_var`。关注 `ssize_t` 转 `size_t`、`int` 转 `unsigned int` 等常见转换。关键词：`malloc(len)`、`memcpy(buf, src, len)`、循环条件中的类型混合、缓冲区操作的大小参数。

## Classify

判断是否为漏洞的要点：
- **确定漏洞**：负数转换为无符号类型，导致巨大的正数值，参与循环/内存操作、缓冲区分配或大小检查
- **误报**：转换值已验证为非负、或仅用于日志/格式化、不参与后续的关键操作
- **代码异味**：类型转换复杂，需追踪下游用途，可能是潜在隐患

## 真实漏洞 vs 误报区分经验

### 真实漏洞特征

1. **黑暗流路（Dark Path）**：有符号值从不被验证的输入来源（网络/文件）转换，无任何符号检查就直接用于内存操作
   - 典例：`int size = read_from_network(); malloc((unsigned)size);` 当 size < 0 时造成超大分配

2. **转换与使用分离**：转换逻辑与实际使用相隔数层调用栈，易被审计者忽视
   - 查证技巧：反向追踪参数来源，确认是否跨越了安全检查的防线

3. **条件竞争窗口**：验证后到使用前存在改写机会，特别是多线程场景
   - 重点关注：全局变量、指针间接访问、TOCTOU（Time-of-Check-Time-of-Use）

### 常见误报陷阱

1. **防御代码被忽视**：审计者在扫描关键字时，错过了前序的符号检查代码
   - 示例：`if (x < 0) return -1; unsigned int y = (unsigned)x;` 实际安全
   - 审计技巧：向上追踪20-50行，确保未遗漏条件判断

2. **上下文无关的类型转换**：某些转换虽然看起来危险，实际无法造成危害
   - 日志输出：`printf("%u", (unsigned)signed_val);` 即使负数也只影响显示
   - 位操作常数：`flags = (unsigned)signed_const;` 若常数值已知为非负，无风险

3. **编译器自动转换 vs 显式转换**：隐式转换并非总是有害，需区分意图
   - 隐式：`void func(size_t s) { ... } func(signed_val);` 编译器警告但常见于兼容代码
   - 显式：`(unsigned)signed_val` 表示审计者有意图，风险更高

## 审计关键决策树

**是否为漏洞？** 逐步问：
1. 有符号值是否来自不受信的来源？ → NO：可能误报
2. 转换后是否参与缓冲区大小/循环计数/指针偏移？ → NO：可能误报
3. 转换前是否有明确的 `>= 0` 检查？ → YES：可能误报
4. 该检查与实际使用间距是否 > 100 行或跨越函数边界？ → YES：需标记为代码异味/高风险

## Low risk

- 有符号值在转换前明确验证为非负（`if (value >= 0)`），且验证与使用紧邻
- 转换值仅用于位操作、格式化、日志输出，不参与内存分配或缓冲区操作
- 使用 `uint32_t` 等明确类型定义，避免隐式转换，函数签名完全匹配
- C++ 中使用 `static_cast<unsigned>(value)` 显式转换且有上下文验证
- 常数值转换（`(unsigned)(-1)` 用于 bitmask），转换值语义明确且文档清楚

## 审计工具与自动化辅助

- 编译器警告：`gcc -Wsign-conversion -Wconversion` 快速定位所有转换点
- 静态分析：`clang-analyzer` 追踪污点流，`cppcheck --enable=all` 检测不匹配
- 手工补充：自动工具易漏掉跨函数调用链的转换，需人工验证关键路径
