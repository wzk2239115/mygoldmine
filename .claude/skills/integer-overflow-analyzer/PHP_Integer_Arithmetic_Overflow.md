# PHP_Integer_Arithmetic_Overflow

**漏洞类型**: 整数运算溢出，PHP 整数溢出在 64 位系统上较少，但 32 位系统或大整数处理需关注

## Details

**代码示例**：`$result = $a + $b`、`$size = $width * $height`、整数超过 PHP_INT_MAX 转为浮点数

- **核心操作定位技巧** (L1: 关键词扫描)：扫描算术操作符 `+`、`-`、`*`。PHP 整数溢出会自动转为浮点数（float），可能丢失精度。关注 32 位 PHP（PHP_INT_MAX = 2^31-1）和涉及位运算、数组索引的情况。检查是否对浮点数结果进行整数运算。

- **保护机制定位技巧** (L2: 跳读)：查找溢出检查（`if ($a > PHP_INT_MAX - $b)`）、使用 GMP/BCMath 扩展进行大整数运算、或检查结果类型（`is_int()` vs `is_float()`）。检查是否使用字符串存储大数值。

## Classify

判断是否为漏洞的要点：
- **确定漏洞**：整数溢出转浮点数导致精度丢失，结果参与关键业务逻辑（如金额计算、数组索引）
- **误报**：使用 GMP/BCMath 处理大整数、有溢出检查、结果不影响业务正确性
- **代码异味**：大整数运算未使用专用扩展，需评估精度影响

## Audit Techniques

### L3 级深度审计
**精确路径追踪**：
- 追踪溢出后的浮点数是否转换回整数（`(int)`、`intval()`、`floor()`），这是漏洞转化的关键点
- 检查浮点数参与的后续计算：用作数组索引、SQL 查询参数、文件偏移量、内存分配大小
- 观察是否存在显式类型强制转换（`(int)`）将浮点数转回整数，导致精度丢失

**上下文关键词扫描**：
- 金融计算场景：`$price * $quantity`、`$balance + $amount`、`$discount * $total`
- 数组/集合操作：`array_pad()`、`str_repeat()`、`array_merge()` 中的长度计算
- 位操作混淆：`1 << $shift`、`$mask & $value`（位移数超限转浮点）
- URL/文件处理：`filesize()`、`fseek()`、`substr()` 的偏移量

### 真实漏洞特征
1. **精度丢失链路可观测**：如 `$size = (int)(1.5 * 1.5e9)` → `0`（整数转换舍入）
2. **业务逻辑依赖精准值**：支付系统中 `$total = $price * $qty` 绕过金额检查
3. **跨越类型边界**：浮点数作为数组索引 `$arr[(int)$float_key]` 导致索引错误
4. **系统调用参数污染**：`fread($fp, (int)$large_calc)` 缓冲区溢出
5. **可重复触发且可控**：用户输入直接参与溢出计算无有效限制

### 常见误报陷阱
1. **数值在安全范围内**：`$a + $b` 即使转浮点也无实际溢出（都小于 PHP_INT_MAX）
2. **浮点数不转整数**：`$result = 1.5 * 2.5` 保持浮点形式用于科学计算，无精度威胁
3. **保护检查被忽视**：存在 `if (is_int($result))` 验证或 `bcadd()` 大整数函数
4. **结果无业务影响**：溢出值仅用于统计计数、日志记录或非关键显示
5. **PHP 版本差异**：64 位 PHP 的 PHP_INT_MAX 极大（2^63-1），普通计算难以溢出

### 区分关键判断点
| 特征 | 真实漏洞 | 误报 |
|------|--------|------|
| 溢出后处理 | 显式转整数 `(int)` | 保持浮点或无后续使用 |
| 上游输入约束 | 无有效范围检查 | 有 `$a < 1000` 等限制 |
| 业务敏感性 | 金融、权限、关键索引 | 统计、显示、缓存 |
| 系统调用参数 | 作为重要参数传递 | 不影响函数行为 |
| 防护机制 | 完全缺失 | 使用 GMP/BCMath 或类型检查 |

## Low risk

- 使用 GMP 或 BCMath 扩展进行大整数运算
- 有 PHP_INT_MAX 边界检查
- 使用字符串存储大数值
- 结果仅用于日志或显示
- 64 位 PHP 且值在安全范围内
