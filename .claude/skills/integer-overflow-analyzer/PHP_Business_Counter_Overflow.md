# PHP_Business_Counter_Overflow

**漏洞类型**: 业务逻辑计数器溢出，金额、积分等业务数值计算未检查溢出

**PHP**

## Details

**代码示例**：`$totalPrice += $price * $quantity`、`$balance += $amount`、`$counter++`、使用浮点数计算金额

- **核心操作定位技巧** (L2: 跳读)：重点审计涉及金额、积分、余额的累加操作。扫描 `+=`、`*=`、`++` 操作符。PHP 整数溢出转浮点数会丢失精度，金额计算尤其危险。检查是否使用浮点数进行货币计算、以及与数据库交互时的类型匹配。

- **保护机制定位技巧** (L3: 逐行读)：查找业务上限检查、使用 BCMath 扩展进行精确计算（`bcadd`、`bcmul`）、或使用整数存储金额（以分为单位）。检查数据库字段类型（DECIMAL vs FLOAT）。

## Audit Techniques

### 浮点数精度陷阱识别

**易错点**：`0.1 + 0.2 == 0.3` 在 PHP 中返回 false。审计时需检查：
- 浮点数参与的比较操作（使用 `==` 而非 `===`）
- 浮点数转换为字符串后写入数据库的场景
- 从数据库读取后直接进行浮点计算，未重新转换类型

**审计方法**：追踪金额相关变量的类型变化，从 API 入参开始到数据库存储的完整路径。特别关注：
```php
$price = (float)$_GET['price'];  // 危险
$total = $price * 100;           // 可能丢失精度
```

### 整数溢出转浮点数识别

**关键特征**：当 PHP 整数超过 `PHP_INT_MAX` 时自动转为浮点数，导致精度丢失。

**审计清单**：
1. 检查循环累加的初值和上限（如库存、计数器）
2. 评估单次增量值与累加次数的乘积是否超过 2^53
3. 关注数据库到 PHP 的类型转换（BIGINT → float）
4. 查看日志记录、统计计算中的大数值处理

**实例识别**：账户余额为 BIGINT 存储，读取后直接参与计算而未使用 bcmath，可能累积精度误差。

### 真实漏洞 vs 误报区分

**真实漏洞特征**：
- 金额计算使用原生浮点运算，且金额大于等于 100 元（1万分）时出现精度丢失
- 业务上对账发现实际余额与系统余额偏差（通常为几分到几角）
- 大额促销/充值后用户投诉金额不符
- 积分系统中存在小数点处理，使用浮点计算导致积分无法精确兑换

**误报案例**：
- 单笔金额小于 100 分（1 元）、不涉及累加的临时计算变量
- 已限制金额范围（如最大 9999.99）且使用 DECIMAL 字段存储
- 单次操作，未经过循环或多次累加
- 数值仅用于展示（UI 层），未流向数据库或后续计算

**关键区分点**：
- 是否涉及金额的多次累加？（余额累加、分账累加）
- 是否有业务上限校验？（如最大可提现额度）
- 存储介质类型？（DECIMAL 安全，FLOAT 危险）
- 浮点值是否直接与数据库交互？（类型转换会加重精度问题）

### 上下文判断要点

**需要深入审计的场景**：
1. **支付相关**：订单金额、手续费、退款计算
2. **积分系统**：积分消耗、充值、转账操作
3. **库存扣减**：虽然整数，但需检查是否有缓存导致的不一致
4. **汇率换算**：涉及浮点中间结果的多步计算

**可快速跳过的场景**：
- 前端展示数值（无数据落地）
- 已完全使用 bcmath/Decimal 库包装的计算
- 测试、演示、非生产环境代码

### 常见审计场景分析

**Case 1: 购物车合计价格**
```
漏洞迹象：循环累加商品金额，使用 += 操作符，金额类型为 float
真实漏洞判定：
  ✓ 金额未做 bcmath 处理
  ✓ 大额订单（>1000元）可能出现精度丢失
  ✓ 直接存储到数据库

不是漏洞判定：
  ✗ 金额已通过 DECIMAL 字段存储
  ✗ 计算结果仅用于前端展示，实际金额由数据库 SUM 得出
```

**Case 2: 用户积分累加**
```
漏洞迹象：签到、购物、任务等多个途径累加积分，未校验上限
真实漏洞判定：
  ✓ 使用浮点数累加整数积分（类型混乱）
  ✓ 无法准确追踪积分变化（缺乏兑换日志）
  ✓ 数据库字段为 FLOAT，多次累加后偏差明显

不是漏洞判定：
  ✗ 积分以整数存储和计算
  ✗ 积分系统设计为整数，不存在小数
```

**Case 3: 余额提现**
```
漏洞迹象：多次小额充值累加成大额，最后提现时金额不符
真实漏洞判定：
  ✓ 提现金额通过循环累加得出，未使用 bcmath
  ✓ 审计发现累加结果与 SUM(amount) 存在偏差
  ✓ 实际可提现金额小于显示金额

不是漏洞判定：
  ✗ 提现额度直接从数据库查询（SELECT SUM）
  ✗ 金额限制在 0.01~99999.99 范围内，精度损失不显著
```

## Classify

判断是否为漏洞的要点：
- **确定漏洞**：金额使用浮点数计算导致精度丢失，或整数溢出转浮点数，影响业务正确性和资金安全
- **误报**：使用 BCMath 进行精确计算、以分为单位存储、数据库使用 DECIMAL 类型
- **代码异味**：金额计算使用浮点数或普通整数运算，需评估精度影响

### 三层判断标准

**第一层：金额流向检查**
- 金额是否从用户输入开始？（输入→计算→存储 完整链路）
- 中间是否存在计算过程？（单次赋值不构成溢出）
- 最终是否需要与金额做对账？（若无法对账，风险较低）

**第二层：类型与范围检查**
- 变量是否声明为 float 或通过浮点运算得出？
- 涉及的数值范围是否可能超过安全范围？（>9007199254740991 即 2^53）
- 数据库字段类型是否为 DECIMAL/NUMERIC？

**第三层：影响面评估**
- 用户可控的参数参与计算？（可扩大精度丢失）
- 涉及多笔交易的累加？（误差会叠加）
- 有无法对账的隐性费用？（精度丢失表现为费用差异）

## Low risk

- 使用 BCMath 扩展进行金额计算
- 金额以整数存储（以分为单位）
- 数据库字段使用 DECIMAL 类型
- 有业务上限检查和异常处理
- 定期与数据库核对余额一致性
- 采用金额快照机制（交易时冻结金额，避免多次计算）
- 金额计算完成后立即转为字符串或整数，避免进一步浮点运算
- 使用 Money Pattern（金额对象封装），内部精确计算
- 中间结果通过取整后再进行下一步计算，限制精度丢失传播

### 快速审计检查清单

```
□ 扫描金额相关变量（price, amount, balance, fee, total 等）
□ 定位所有算术运算（+, -, *, /, %, ++, +=, -=）
□ 检查变量初始化时的类型（是否显式转浮点）
□ 查找变量与数据库交互的代码（入库前是否有类型转换）
□ 定位 bcadd/bcmul/bcmath 使用情况
□ 搜索 DECIMAL/NUMERIC/BIGINT 字段声明
□ 检查金额验证和上限检查逻辑
□ 查看是否有对账或日志记录机制
□ 评估累加循环的上限（循环次数 × 单次增量）
□ 验证浮点比较是否使用 == 或 !=（高危）
```
