## Details

**代码示例**：`value << userShift`、`flags |= (1 << bitPos)`、`(value >>> offset)` 的符号扩展问题

- **核心操作定位技巧** (L1: 关键词扫描)：扫描位操作符 `<<`、`>>`、`>>>`、`&`、`|`、`^`，特别关注左移操作。检查移位数量来自用户输入或循环变量的代码。关注有符号 `>>` 和无符号 `>>>` 的区别。

- **保护机制定位技巧** (L2: 跳读)：查找移位数量的范围检查（`if (shift >= 32)` 或 `if (shift >= 64)`），以及使用 `& 0x1F` 等掩码限制移位范围的防御。

## Classify

判断是否为漏洞的要点：
- **确定漏洞**：移位数量无限制，或符号扩展导致异常值参与后续计算
- **误报**：移位为常量、有明确范围检查、或仅用于标志操作
- **代码异味**：混合使用 `>>` 和 `>>>`，需理解业务意图

## Low risk

- 移位数量为编译期常量（0-30 for int, 0-62 for long）
- 使用 `& 0x1F` 等掩码（自动限制范围）
- 移位结果仅用于标志位操作或单 bit 提取
- 明确的范围检查（`if (shift < 32)`）
- 位字段操作清晰，无跨类型转换

## 审计专业技巧

### 数据流追踪关键点
- **源头分析**：移位量来自 `Scanner/BufferedReader/HTTP参数/配置文件`，需追踪解析过程中的范围限制
- **隐式转换陷阱**：`int shift = ((byte) userInput)`、`int mask = userByte << 24`，byte/short 自动转 int，可能导致移位值异常
- **循环变量风险**：循环索引用作移位量，需检查循环上界是否超过 32/64
- **位域操作链**：多个位操作连续执行，如 `(x << 16) | (y << 8) | z`，需逐个检查每个移位

### 真实漏洞特征
- **无条件移位**：`int result = value << userInput;` 无任何验证
- **间接溢出链**：移位后结果与其他数值计算：`int idx = (hash << shift) % array.length;`，溢出值可用作数组索引
- **符号问题**：负数左移导致符号位变化：`int neg = -1; neg <<= 33;` (Java 自动模 32，但意图不明确)
- **跨类型推导**：`long val = (int)(userInput << offset); if (val < 0)` 混合 int/long 导致逻辑缺陷

### 常见误报案例
1. **标志位操作**：`flags |= (1 << position);` where `position` 被正确限制在 [0, 31]
   - 误报标志：看到 `<< userInput` 立即告警，未检查位域宽度限制

2. **预定义常量**：`private static final int[] POWERS = {1, 2, 4, 8, 16, 32};` 然后 `int val = base << POWERS[idx];`
   - 审计技巧：追踪数组初始化，确认所有元素都在安全范围

3. **右移反向验证**：`int width = (value >>> shift) & 0xFF;`
   - 右移是提取数据，非溢出操作，但需确认 `shift` 也有限制

### 高危代码模式
```
// 模式1：隐式范围假设
for (int i = 0; i < someList.size(); i++) {
    result |= (1 << i);  // 如 size > 31，则漏洞
}

// 模式2：配置驱动的移位
int shiftAmount = config.getInt("bitshift", 0);  // 无上界检查
long value = source << shiftAmount;

// 模式3：转换链中的溢出
byte userByte = getUserInput();
int shift = userByte;  // -128 到 127，都合法但 127 << 8 可能超预期
int result = base << shift;
```

### 审计清单 (Fast Checklist)
- [ ] 移位量是常量还是来自输入？
- [ ] 移位量有范围检查吗？(`< 32` for int, `< 64` for long)
- [ ] 使用了 `& 0x1F` / `& 0x3F` 掩码吗？
- [ ] 左移结果后续用在数组索引、内存分配吗？
- [ ] 混合 `>>` 和 `>>>` 吗？（理解业务意图）
- [ ] 是否存在隐式 int 转换后才做移位的情况？

## 实战区分指南

### 真实漏洞 vs 误报的关键区分点

**真实漏洞的必要条件**：
1. **控制流**：移位量来自不可信输入且无有效校验
2. **影响**：溢出结果被用于关键决策（数组访问、内存计算、算术运算）
3. **可达性**：漏洞代码在正常业务流中可被触发

**常见混淆场景**：
- `value << 1`：翻倍操作，仅当结果用于关键计算时才构成漏洞
- `flags & (1 << 5)`：位提取，位置固定则安全
- `(byte) (x >> 8)`：截断操作，右移通常安全，除非 shift 来自输入

### 深层误报陷阱
1. **防御隐蔽性**：范围检查可能在上层方法中，如 `parseShift()` 方法已验证
   - 审计技巧：追踪方法调用链，查看调用者是否已做检查

2. **框架级防护**：使用 Spring Validation、Jakarta Bean Validation 的 `@Min/@Max` 注解
   - 检查点：搜索参数类定义，查看注解约束

3. **编译期常量池**：`private static final int[] SAFE_SHIFTS = {0, 8, 16, 24};`
   - 误报原因：初看是可变数组，实际内容固定不变

### 上下文依赖的判断
```
// 情景1：高危 - shift 来自网络请求
public int process(int userShift) {
    return base << userShift;  // 无检查，直接使用
}

// 情景2：中危 - shift 来自配置但有默认限制
public int process(int userShift) {
    int safe = Math.min(userShift, 31);
    return base << safe;
}

// 情景3：低危 - shift 是常量或已验证
public int process(int userId) {
    return user[userId].flags << 4;  // 移位量为常量 4
}
```

### 符号扩展的审计要点
- `>>` (算术右移) vs `>>>` (逻辑右移) 的混用是代码异味
- 负数参与位操作时，需理解是否预期有符号扩展
- 例：`int neg = -1; neg >>> 1;` 结果是 `0x7FFFFFFF`（正数），与 `neg >> 1` 的 `0xFFFFFFFF`（-1）完全不同

## 漏洞评估矩阵

| 检查项 | 高危 | 中危 | 低危 |
|--------|------|------|------|
| 移位量来源 | 用户输入 | 配置文件 | 编译期常量 |
| 范围验证 | 无 | 部分检查 | 完整检查或掩码 |
| 结果用途 | 数组索引、长度 | 位操作标志 | 纯数据提取 |
| 溢出处理 | 无异常捕获 | 有日志记录 | 使用掩码限制 |
