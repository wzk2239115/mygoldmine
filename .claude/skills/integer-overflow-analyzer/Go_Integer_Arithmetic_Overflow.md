# Go_Integer_Arithmetic_Overflow

**漏洞类型**: 整数运算溢出，Go 中整数溢出是未定义行为，需检查溢出检测机制

## Details

**代码示例**：`result := a + b`、`size := width * height`、`offset := base + userInput`、无符号整数下溢 `uint(x) - uint(y)`

- **核心操作定位技巧** (L1: 关键词扫描)：扫描算术操作符 `+`、`-`、`*`，特别是乘法和涉及 uint/int 类型的运算。Go 整数溢出是静默的（回绕行为）。关注运算结果用于内存分配（`make`）、数组索引、或关键业务逻辑的情况。

- **保护机制定位技巧** (L2: 跳读)：查找溢出检查（`if a > math.MaxInt64 - b`），使用 `math/big` 包进行大整数运算，或使用 `math.Mul64`、`math.Add64` 等带溢出检测的函数。检查是否使用 `-race` 或静态分析工具。

## Classify

判断是否为漏洞的要点：
- **确定漏洞**：无溢出检查，操作数来自不受信任的源，结果参与内存分配/数组访问/业务逻辑
- **误报**：操作数为常量或明确在类型范围内、有显式溢出检查、仅用于日志
- **代码异味**：涉及 uint 类型的减法（可能下溢），需评估是否会回绕

## Low risk

- 操作数为编译期常量或已验证的值
- 使用 `math/big` 包进行大整数运算
- 有显式溢出检查（如 `bits.Mul64` 检查溢出位）
- 运算结果仅用于非关键场景
- 使用更宽的类型（如 int64 代替 int32）

## 审计专业技巧

### 源头追踪（Source Tracking）
- **用户输入链路**：从 HTTP 参数、配置文件、数据库读取的值需要全链路验证，特别是 `QueryInt`、`FormValue` 等接收的值
- **隐性溢出风险**：多步运算链（如 `a * b + c * d`）中，每一步的中间结果都需检查，不能只看最终结果
- **类型转换边界**：`uint32(userValue)`、`int(bigValue)` 转换时容易引发溢出，需重点审视
- **JSON/Protocol Buffer 反序列化**：第三方库反序列化时可能无边界验证，导致溢出后续计算

### 危险操作识别
- **内存分配陷阱**：`make([]byte, len*width)` 中 `len*width` 溢出后变成小数值，分配小内存块，后续写入导致 buffer overflow
- **数组索引越界**：`arr[idx + offset]` 中若 `idx + offset` 溢出回绕到小值，造成越界读写
- **时间计算**：`time.Now().Add(time.Duration(userSeconds * 1e9))` 中乘法溢出导致时间戳异常，影响业务逻辑
- **循环计数器**：`for i := 0; i < maxVal; i += step` 中若 step 过大，i 溢出导致死循环

### 真实漏洞与误报区分

**真实漏洞特征**：
1. 操作数直接或间接来自不受信任源（用户输入、API 返回、文件内容）
2. 无任何形式的预检查（不论是否有效）
3. 运算结果用于以下关键操作：
   - 内存分配尺寸（`make` 的第二个参数）
   - 数组/切片索引（`slice[calculatedIdx]`）
   - 循环条件（可导致无限循环或跳过）
   - 业务决策（转账金额、权限判断）
   - 密钥生成或加密操作

**常见误报场景**：
1. **常量运算**：`const MaxSize = 1024 * 1024` 或函数参数有 `const` 修饰（Go 中需函数级常量检查）
2. **单向不等式检查**：虽然不完全，但如 `if a > 0 && b > 0 && a*b < MaxSize` 表明开发者有溢出意识
3. **保障类型足够大**：`int64` 相对 `int32` 安全得多，具体看运算数值范围
4. **库函数保障**：`strconv.ParseInt`、`encoding/json` 等标准库有内置检查
5. **仅日志用途**：`log.Printf("%d", a+b)` 即使溢出也不构成漏洞
6. **错误路径**：return error 前的计算，不会实际执行该值

**审计决策树**：
```
发现算术操作
  ├─ 是否全为常量？→ YES → 低风险
  ├─ 操作数有输入检查？
  │   ├─ YES，检查完整性 → 看下一步
  │   └─ NO → 进入漏洞评估
  ├─ 运算结果用途是什么？
  │   ├─ 内存分配 → 高风险
  │   ├─ 数组索引 → 中高风险
  │   ├─ 业务逻辑 → 中风险（需评估业务影响）
  │   └─ 日志/显示 → 低风险
```

### 审计检查清单
- [ ] 定位所有整数运算 `+、-、*`，标记可疑操作
- [ ] 追踪操作数来源，是否存在用户输入路径
- [ ] 检查是否有显式上界检查（`if a > MaxVal - b`）
- [ ] 验证溢出检查逻辑是否正确（常见：只检查加法，忽视减法下溢）
- [ ] 评估运算结果的用途，确定风险等级
- [ ] 在 int 和 uint 混用场景特别留意符号转换风险
