## Details

**代码示例**：`result = a + b`、`size_t total = width * height`、`int offset = base + user_input`、减法中的符号翻转

- **核心操作定位技巧** (L1: 关键词扫描)：扫描算术操作符 `+`、`-`、`*`，特别关注乘法（如内存分配 `malloc(width * height)`）。检查操作数类型混合（`unsigned + int`）、以及操作数来自用户输入/外部数据的情况。快速判断：若涉及 `malloc/calloc/realloc`、数组索引、循环条件则风险提升。

- **保护机制定位技巧** (L2: 跳读)：查找溢出检查（`if (a > INT_MAX - b)`、`if (__builtin_add_overflow()`）、使用较宽类型进行中间计算、或使用安全算术库（如 libsodium 的 overflow-safe 函数）。同时观察入参是否已在上游做范围限制。

- **专业审计技巧** (L3: 逐行读)：追踪赋值链路，确认操作数最终来源是否来自 `read()`、`recv()`、`getenv()` 等不受信任的入口。检查是否存在隐式类型转换（如 `int` 与 `size_t` 混用）造成的符号扩展问题。注意乘法溢出在 32 位机器上的表现与 64 位的差异。

## Classify

**核心判断流程**：

1. **识别关键操作**：定位 `+/-/*` 操作，标记操作数来源（常量/变量/函数返回值）
2. **追踪操作数**：若为变量，向上游追踪入口，判断是否来自外部输入（用户输入、网络数据、文件读取）
3. **评估溢出触发条件**：根据数据类型的取值范围，分析溢出是否可达
4. **验证防护覆盖**：检查是否存在前置验证、范围检查或编译时保证

**真实漏洞特征**（确定为CVE级别）：
- 操作数直接来自 HTTP 请求参数、网络报文或用户文件输入，无任何验证
- 溢出后的结果立即用于 `malloc/free`、数组下标或内存操作
- 存在跨越内存边界的可能性，如 `buffer[total]` 其中 `total = width * height` 未检查
- 编译器无法进行编译期检查（如函数参数传递），运行时才能触发

**高置信误报特征**：
- 操作数为局部常量或全局编译期常量（`#define MAX 100`）
- 在函数入口有明确的范围验证：`if (size > MAX_SIZE) return -1;`
- 使用 `min()`、`max()` 等宏函数进行了范围钳制
- 操作结果仅用于非关键操作（日志输出、统计计数、CRC 校验）

**需进一步深入的代码异味**：
- 类型混合场景：`unsigned int size; int count; ... total = size + count;`
- 中间结果未显式扩展：`int a, b; long result = a + b;` 应为 `(long)a + (long)b`
- 条件分支中的验证不完整：只检查单个操作数但不检查组合结果

## Low risk

- 操作数均为编译期常量或已验证的值（前置检查）
- 使用 `uint64_t` 等足够宽的类型进行中间计算，确保结果不溢出
- 明确的溢出检查（如 `if (a > INT_MAX - b) return error;`）
- 操作仅用于校验码、CRC、Hash 计算等对溢出不敏感的场景
- 使用编译器提供的 `__builtin_*_overflow()` 函数进行安全计算
- 操作结果仅用于 `printf/log` 等信息输出，不参与内存决策

## 审计陷阱与经验

**常见的虚警原因**：
- 审计工具误报：静态分析器标记所有乘法操作，但未追踪前置验证
- 上游验证遗漏：虽然函数无验证，但调用方在传入前已做范围限制
- 类型宽度假设错误：在 64 位编译环境下审计，但代码运行在 32 位环境

**真实案例经验**：
- **PNG 解析漏洞**：`width * height * 4` 未检查，导致小分配。识别关键在于追踪返回值直接进入 `malloc()`
- **文件偏移计算**：`offset + size` 在处理大文件时，需确认是否使用了 64 位类型
- **网络协议解析**：报文长度字段用 `uint16_t`，相乘后用 `int` 接收，存在隐式转换风险

**高效审计建议**：
- 优先审计与内存、数组操作直接相关的算术运算
- 在循环条件中的算术操作需特别关注（累积溢出风险）
- 对涉及用户输入的算术，需追踪完整的验证链，不能只看单点
