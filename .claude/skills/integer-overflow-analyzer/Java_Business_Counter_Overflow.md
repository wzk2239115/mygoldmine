## Details

**代码示例**：积分累加 `userPoints += earnedPoints;`、金额计算 `totalAmount += price;`、计数 `clickCount++`，均为 int 或 long 类型

- **核心操作定位技巧** (L3: 逐行读)：扫描业务计数相关的字段（points、amount、count、balance 等），检查其类型（int/long）和递增操作。追踪字段声明、累加逻辑、以及数值来源。优先关注与金钱、积分、优惠券余额相关的累加。

- **保护机制定位技巧** (L3: 逐行读)：查找业务上限限制（`if (totalPoints > MAX_POINTS)`）、使用 BigDecimal 处理金额、或前置检查（`if (userPoints > Integer.MAX_VALUE - earnedPoints)`）。观察上限是否为硬编码常量或数据库配置。

## Classify

**真实漏洞特征**（需确认）：
- **无任何上限检查**：累加字段无业务封顶，允许无限递增（关键证据）
- **金额字段用 int**：32 位存储超大金额，MAX_VALUE 为 21 亿，易触发溢出
- **溢出导致业务异常**：字段越界后转为负数或极小值，绕过金额控制
- **数据来源不可信**：积分/金额来自用户输入或第三方接口，未验证上限
- **缺少溢出检查**：无预先计算，如 `if (userPoints > Integer.MAX_VALUE - earnedPoints)`

**常见误报场景**（确认后排除）：
- **业务已有硬上限**：积分系统上限 999999，虽无代码检查但业务规则明确封顶（需查规格文档）
- **long 型但足够大**：long 最大值 9223372036854775807，金额以分计存储，实际数据范围明确不会溢出
- **BigDecimal 已使用**：金融系统规范用 BigDecimal，自动处理精度问题，无溢出风险
- **仅用于 UI 展示的计数**：页面点击次数计数溢出，但无业务影响，可记录为低危
- **数据库列有约束**：字段定义了 CHECK 约束或触发器限制，数据库层保护生效

**区分要点**（审计专业经验）：
- **追溯上限定义位置**：查业务文档、数据库 DDL、常量定义、if 判断语句，上限可能在多个位置
- **观察溢出后行为**：负数余额能否正常使用？是否有负数验证？后续是否有恢复机制？
- **检查业务交互边界**：用户充值、提现、兑换时是否有额外校验？客户端是否有输入限制？
- **跨表关联验证**：检查订单表、账户表是否有余额冲突记录，数据库日志是否有异常更新
- **版本演变分析**：旧版本是否有上限，新版本移除了吗？是否为迭代过程中遗漏

## Low risk

- 业务字段使用 BigDecimal/BigInteger（已验证类型）
- 明确的业务上限检查（`if (balance > MAX_BALANCE)`）且数值合理
- long 类型且业务规模明确不会达到 Long.MAX_VALUE（如订单 ID 自增）
- 字段初始化明确，无外部直接写入，仅内部流程生成
- 存在业务规则文档说明上限，或数据库约束已设置
- 溢出后有补偿机制（如定期重置、周期计数）

## Real-world case analysis

**案例1：积分溢出导致免费充值**（真实漏洞）
- 用户积分用 int 存储，业务无上限限制
- 通过特殊操作将积分累加到 Integer.MAX_VALUE（21 亿 4千万）
- 再获得 1 积分后溢出为负数，系统将负数识别为欠费
- 用户可利用负数兑换大额充值卡，实现零成本充值
- **审计要点**：积分字段类型、前置检查逻辑、兑换模块验证

**案例2：金额用 int 导致大额转账翻转**（真实漏洞）
- 电商系统订单金额用 int，业务上限应为 999999 元（约百万）
- 某个营销活动允许临时突破限制，但代码改动遗漏了类型检查
- 用户输入 2147483647（INT_MAX）金额时，系统存储后立即转负
- 账户显示欠费而非充值，绕过支付验证流程
- **审计要点**：营销活动代码改动、类型与业务上限的匹配性、日志中是否有异常金额

**案例3：long 类型计数但未考虑实际溢出时间**（误报 vs 真实）
- 系统用 long 存储每日请求计数，理论值需 262144 年才会溢出
- 但若业务规则改变（如增加 API 流量），实际溢出时间减短至数年
- 审计时若不了解业务演变，可能误判为无风险
- **审计要点**：需了解历史迭代、业务增长预期、压力测试数据

**案例4：负数验证缺失导致余额操纵**（审计死角）
- 系统正确限制了余额上限，但未验证下限
- 通过并发请求或数据库直接操作，可使余额成为大负数
- 后续消费时，负数余额反向计算，变成了虚假充值
- **审计要点**：不仅检查上限，还要检查下限验证、并发场景

## Common audit traps

**陷阱1：混淆业务规则与代码检查**
- 业务文档说"积分不超过 100 万"，但代码无 if 判断
- 初审可能误判为低风险，忽视了文档无法作为代码执行保障
- 必须在代码层找到对应检查，或数据库约束

**陷阱2：只看数据类型，不看数据来源**
- 见到 BigDecimal 就认为安全，但若来自用户输入无上限参数，仍可溢出
- BigDecimal 是精度工具，不是溢出防护工具

**陷阱3：忽视 API 接口的隐形上限**
- 内部函数可能有上限检查，但调用方未必知道
- 需追踪从入口（HTTP 请求、消息队列）到存储的完整链路

**陷阱4：负数场景被遗漏**
- 积分+1 时有上限，但-1 时无下限检查
- 负数可被误用为虚假充值或绕过风控

**陷阱5：数据库约束但应用层无验证**
- 数据库有 CHECK 约束，但应用层异常捕获不当
- ORM 框架可能无法正确传播约束错误

## Technical keywords for scanning

审计时应关注以下关键字组合：
- `int balance` / `int amount` / `long credit`（类型风险）
- `balance += ` / `amount += ` / `++ count`（累加操作）
- `Integer.MAX_VALUE` / `Long.MAX_VALUE` / `Integer.MIN_VALUE`（边界常量）
- `BigDecimal` 出现位置（是否覆盖所有金额操作）
- `if (xxx > MAX)` / `if (xxx < MIN)`（上下限检查）
- `@Min` / `@Max` / `@ValidRange`（注解层验证）
- CHECK 约束在 SQL 中的定义
- 并发操作如 `synchronized`、`Lock` 是否保护累加

## Audit depth guidelines

**L1 快速扫描（适合初筛）**
- 全局搜索 `int.*balance|int.*amount|int.*point`
- 查看是否有 `Integer.MAX_VALUE` 常量定义
- 快速判断：若无上限常量定义，标记为疑似漏洞

**L2 跳读分析（适合中等风险）**
- 追踪计数字段的声明、赋值、增长操作
- 查找相关业务逻辑类中的 if 判断或验证注解
- 检查数据库表定义是否有 CHECK 约束
- 判断：有多层防护则低风险，无防护则高风险

**L3 逐行审计（适合高危操作）**
- 逐行阅读涉及金额/积分的业务逻辑
- 追踪用户输入到存储的完整链路
- 检查每个累加点是否都有预检查
- 特别关注：try-catch、异常处理、并发场景

**L4 跨模块追踪（适合复杂场景）**
- 跨越 Service-DAO-DB 多层，追踪同一字段的流转
- 检查是否存在绕过中间检查的快速路径
- 查看是否有定时任务、消息队列等异步操作导致的间隙
- 关联代码变更历史，查看是否有改动遗漏

## Practical verification methods

**方法1：静态边界分析**
- 找到目标字段的最大值（如 int 限制为 21 亿）
- 找到业务上限（如积分 100 万）
- 对比：若类型能容纳的值 > 业务设定值，存在溢出风险
- 特别注意：业务上限改变但代码未同步更新的情况

**方法2：动态测试验证**
- 构造 MAX_VALUE-1、MAX_VALUE、MIN_VALUE 等边界输入
- 观察系统是否接受、如何处理
- 检查日志、数据库是否记录异常值
- 验证：溢出后的行为是否符合业务预期

**方法3：代码流追踪**
- 从 HTTP 请求入口开始，追踪参数到数据存储
- 标记每个检查点（if 语句、注解验证、数据库约束）
- 绘制流程图，识别缺口
- 评估：是否所有路径都有保护

**方法4：历史变更分析**
- 查看 Git blame，找出何时引入风险代码
- 查看关联的 Issue/PR，理解业务背景
- 对比旧版本是否有上限，新版本是否被移除
- 判断：是否为已知风险或遗漏

## False negative checklist

避免漏报的检查清单：
- [ ] 是否检查了所有 int/long 字段，而不仅是命名为 "amount" 的字段
- [ ] 是否检查了减法操作（可能导致负数）
- [ ] 是否验证了数据库层约束是否实际生效
- [ ] 是否考虑了并发场景下的竞态条件
- [ ] 是否追踪了所有调用该字段的位置（不仅是声明位置）
- [ ] 是否检查了 API 文档中的参数上限说明
- [ ] 是否注意到了定时任务、异步操作导致的延迟风险
