# Rust_Unsafe_Integer_Overflow

**漏洞类型**: unsafe 代码中的溢出，unsafe 块中直接进行指针算术或内存操作

**Rust**

---

专注于这一垂直漏洞类型研判任务，从漏洞成因触发，编写该md文件，包含一下三个小标题，【注意语言精炼，表达简洁，可以作为审计小抄，仅专注于审计，不包含攻击与修复】：

## Details

**代码示例**：`unsafe { ptr.offset(index) }`、`ptr.add(count)`、`slice::from_raw_parts(ptr, len)`、`transmute::<T, U>(value)`

- **核心操作定位技巧** (L2: 跳读)：扫描 `unsafe` 块，特别关注指针运算（`offset`、`add`、`sub`）、原始指针解引用、以及 `from_raw_parts` 等函数。检查涉及整数计算的操作，如偏移量、长度、索引等参数。

- **保护机制定位技巧** (L3: 逐行读)：查找 unsafe 块前的边界检查和验证逻辑、使用 `checked_*` 方法计算偏移量、或详细的安全性注释说明不变量。检查所有整数参数是否经过充分验证，确保不会导致内存安全问题。

### 审计专业技巧

**1. 指针算术审计要点**
- 关键检查：参数来源追溯，是否来自用户输入、外部数据或计算结果
- `offset(n)` 与 `add(n)` 的区别：offset 允许负数，add 不允许，但都应该检查边界
- 多阶段计算：如 `len * size + offset`，需逐步追踪每个运算的安全性
- 特别关注 `wrapping_*` 系列方法，这些方法在溢出时会自动折绕，可能掩盖问题

**2. 长度与容量验证模式**
- 真实安全代码：在调用 `from_raw_parts` 前进行长度验证，如 `assert!(len <= capacity)`
- 常见误报：注释说明"调用者需保证长度有效"，但未实际验证
- 审计焦点：内存分配来源与长度参数的对应关系，是否存在 UAF 或 double-free 风险
- 重点：检查长度是否可能为零、超大值或使用了带符号整数的负数

**3. 整数溢出的隐蔽形式**
- 直接溢出：`len * size` 可能溢出，应使用 `len.checked_mul(size)`
- 转换溢出：`usize as u32` 可能截断，需验证值在目标类型范围内
- 符号转换：`i32 as usize` 对负数的未定义行为，需确保参数非负
- 加法链式：`base + offset1 + offset2`，需分步验证或使用 `checked_add` 链式调用

**4. 误报与真实漏洞的区分经验**
- **误报特征**：代码上方有详细安全证明、参数来自特定受信任来源（如编译时常量）、有完整的单元测试覆盖边界
- **真实漏洞特征**：参数来自 FFI、Socket、文件、环境变量等外部来源且无验证；计算过程中存在多个 unsafe 操作；没有对应的安全 wrapper
- **关键判别**：追踪参数来源链，如果参数最终无法验证其有效性，则为漏洞；反之，如果在 unsafe 块入口有明确的检查，则可能是误报

## Classify

判断是否为漏洞的要点：
- **确定漏洞**：unsafe 块中的整数运算无验证，可能导致指针越界、内存损坏或未定义行为；或参数来自不可信来源且没有边界检查
- **误报**：有完整的安全性证明和注释、所有参数经过验证、使用安全的封装；参数来自编译时常量或已验证的安全来源
- **代码异味**：unsafe 块中涉及整数运算，需仔细审查所有不变量；多个 unsafe 操作形成的计算链条

### 实战审计案例对比

**案例 A - 真实漏洞**（高置信度）
```rust
// 漏洞：长度参数来自网络数据，无验证
unsafe {
    let len = read_u32_from_socket() as usize;
    slice::from_raw_parts(ptr, len)  // 可能超出分配范围
}
```
审计判断：参数来自 Socket（不可信），无长度验证，确定为漏洞。

**案例 B - 误报**（低置信度）
```rust
// 安全代码：长度参数经过验证
let len = read_u32_from_socket() as usize;
if len > MAX_SIZE { return Err(TooLarge); }
unsafe {
    slice::from_raw_parts(ptr, len)  // 已验证
}
```
审计判断：unsafe 块前有明确检查，参数有界，为安全代码。

**案例 C - 代码异味**（中置信度）
```rust
// 可疑：多个 unsafe 操作的计算链
unsafe {
    let offset = index * stride;  // 可能溢出
    let ptr2 = ptr.add(offset);
    let val = *ptr2;
}
```
审计判断：乘法运算 `index * stride` 未使用 checked 方法，需进一步审查 index 和 stride 的来源和取值范围。

## Low risk

- unsafe 块有详细的安全性注释说明不变量
- 所有整数参数（偏移、长度等）都经过验证
- 使用 `checked_*` 方法计算指针偏移
- unsafe 代码被安全的 API 封装
- 有充分的单元测试覆盖边界情况
- 参数来自编译时常量、配置文件中的硬编码值或已验证的内部结构
- unsafe 块内部使用了 `debug_assert!` 或 `assert!` 验证关键不变量
- 代码中明确指出了"调用者契约"并且调用处进行了契约验证
- 使用了 Rust 社区认可的安全库（如 `zerocopy`、`bytemuck`）而非手写 unsafe 代码

### 审计效率提示

**高效审计流程**
1. 快速扫描：5 分钟内定位所有 unsafe 块和关键操作（`add`、`offset`、`from_raw_parts`）
2. 参数追踪：确定每个参数的来源，区分编译时常量、函数参数、外部输入
3. 深度分析：对外部输入相关的 unsafe 操作进行逐行审查，检查边界条件
4. 上下文关联：查看调用点是否有验证逻辑，是否存在多个 unsafe 操作的链式调用

**常见审计误区**
- 仅看注释而不追踪实际代码逻辑
- 假设 `assert!` 一定会执行（不考虑优化等级 release mode 可能禁用）
- 忽视类型转换中的隐蔽溢出（如 `i64 as usize`）
- 不检查长度为 0 的特殊情况（某些操作对零长度切片可能有定义漏洞）

### 报告关键信息

确认漏洞时需记录：
- 参数来源链：用户输入 → 函数参数 → 计算结果 → unsafe 操作
- 缺失验证点：在哪个环节没有边界检查或类型验证
- 潜在后果：可能导致的内存越界范围、信息泄露或代码执行风险
- 修复建议：使用 `checked_*` 方法或在 unsafe 块前补充验证逻辑

### 特殊场景审计注意

**FFI 边界的整数溢出**
- C 代码传入的整数参数缺乏类型检查，可能包含恶意值
- 关键：验证 FFI 调用的返回值和入参，不要盲目信任 C 库的文档承诺
- 审计重点：查找所有 `extern "C"` 函数和 `#[no_mangle]` 标记的函数

**循环中的指针运算**
- `for i in 0..len { ptr.add(i * size) }` 的乘法易溢出
- 常见误报点：编译器优化可能消除掉某些溢出检查
- 审计技巧：检查循环变量的上限是否经过验证，特别是当上限来自外部输入时

**内存池和缓冲区管理**
- 自定义的内存管理代码（如竞技场分配器）中的指针算术最易出错
- 重点：验证 allocation 大小计算（通常涉及 `size * count`）
- 检查项：分配失败后的指针是否为 null、double-free 风险、用后释放风险

**泛型 unsafe 代码中的大小转换**
- `std::mem::size_of::<T>()` 对某些泛型类型可能返回零或超大值
- 问题代码：`capacity * size_of::<T>()` 未使用 checked 方法
- 审计建议：对任何涉及 `size_of` 的计算都应使用 `checked_mul`

### 快速判别检查清单

审计时可按以下优先级检查：

- [ ] unsafe 块中是否存在整数乘法运算？检查是否使用了 `checked_mul` 或有上限验证
- [ ] 指针操作的长度/偏移参数来自何处？追踪参数是否来自外部输入
- [ ] `from_raw_parts` 的长度参数是否经过验证？
- [ ] `transmute` 是否涉及大小不匹配的类型转换？
- [ ] unsafe 块是否有关键的 `assert!` 或 `debug_assert!` 验证？
- [ ] 是否存在多层 unsafe 操作形成的计算链（乘法 + 加法 + 减法）？
