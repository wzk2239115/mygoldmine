# PHP_Array_Length_Overflow

**漏洞类型**: 数组长度计算溢出，使用用户输入创建数组或字符串时长度计算不当

**PHP**

## Details

**代码示例**：`array_fill(0, $count, $value)`、`str_repeat($str, $times)`、`array_merge()` 大数组

- **核心操作定位技巧** (L1: 关键词扫描)：扫描 `array_fill()`、`array_pad()`、`str_repeat()`、`range()` 等可能创建大数组或字符串的函数。关注长度/次数参数来自用户输入或计算结果的情况。检查是否有多个数组操作叠加。

- **保护机制定位技巧** (L2: 跳读)：查找长度上限验证、内存限制设置（`memory_limit`）、或使用流式处理代替大数组。检查是否捕获内存耗尽异常。

- **审计追踪技巧** (L3: 数据流追踪)：追踪长度参数的来源。从 `$_GET`、`$_POST`、`$_REQUEST` 开始反向追踪，检查是否经过 `intval()`、`(int)` 强制转换或上限验证。注意 `php.ini` 的 `max_input_vars` 限制可能隐性控制输入。

## Classify

判断是否为漏洞的要点：
- **确定漏洞**：数组长度来自不受信任的源，无上限检查，可能导致内存耗尽（DoS）
- **误报**：长度有明确上限、有内存限制、使用流式处理
- **代码异味**：动态计算数组长度，需评估内存影响

### 审计经验：真实漏洞与误报区分

#### 真实漏洞特征

1. **直接无限长度创建**：`array_fill(0, $_GET['count'], 'x')` - 无任何验证，将直接导致内存耗尽
2. **隐性计算溢出**：`array_fill(0, $size * $_GET['multiplier'], $value)` - 乘法可能导致计算溢出，绕过验证
3. **链式数组操作**：多个 `array_merge()` 或嵌套 `array_fill()` 调用，效应叠加
4. **异常处理缺失**：未捕获 `OutOfMemoryException` 或未设置 `ini_set('memory_limit')`

#### 常见误报情况

1. **已验证参数**：`$count = intval($_GET['count']); if ($count > 100) $count = 100;` - 虽然代码看似冗余，但上限检查明确有效
2. **配置文件来源**：`array_fill(0, $config['max_items'], $default)` - 虽然动态读取，但来自可信的配置源
3. **流式处理已采用**：使用 `Iterator` 或 `Generator` 替代大数组，虽然循环次数参数来自用户，但内存占用恒定
4. **隐性上限存在**：POST 数据受 `post_max_size` 限制，实际数组大小有物理上限

#### 审计中易忽视的细节

- **多重转换陷阱**：`(int)$_GET['count']` 后未验证，但在某些上下文中可能通过其他机制限制（如 ORM 查询参数限制）
- **变量覆盖**：审计时需跟踪所有赋值，`$count = $_GET['count']`，后续代码可能修改此变量
- **框架级保护**：某些框架自动限制查询参数大小或提供内置验证方法，需了解框架特性
- **内存计算遗漏**：`array_fill()` 参数本身可能溢出，整数最大值 `PHP_INT_MAX` 也需检查

## Low risk

- 长度参数有明确上限（如 `min($count, 1000)`）
- 设置合理的 memory_limit
- 使用生成器或迭代器代替大数组
- 长度来自已验证的配置
- 有内存耗尽异常处理
- 严格的输入验证（`if ($count < 0 || $count > MAX_LIMIT) throw new Exception()`）
- 使用 `array_chunk()` 分批处理大数据集
