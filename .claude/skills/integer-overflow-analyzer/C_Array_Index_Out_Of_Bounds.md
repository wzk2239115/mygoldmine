# C_Array_Index_Out_Of_Bounds

## Details

**代码示例**：`array[user_index]`、`ptr[offset + i]`、`buffer[size - 1]`（当 size 为 0 时）

- **核心操作定位技巧** (L1: 关键词扫描)：扫描方括号 `[]` 操作符，检查索引是否来自用户输入、循环变量或计算结果。关注负数检查（无符号类型无需检查负数）和上界检查。

- **保护机制定位技巧** (L2: 跳读)：查找索引验证（`if (index >= array_size)` 或 `if (index < 0 || index >= size)`）、使用 `assert()` 进行调试期检查、或使用带边界检查的容器库（如 C++ STL）。

## Classify

**真实漏洞特征**：
- 无任何边界检查，索引直接源自用户输入/网络数据/文件内容
- 多层计算后的索引（如 `array[a * b + c]`），未在每步验证范围
- 条件判断不完整（如仅检查上界，未检查下界或整数溢出）
- 索引依赖类型转换（`uint8_t` 转 `int`），可能产生符号错误或截断

**误报特征**：
- 索引为编译期常量或 `#define` 宏定义
- 严格的边界检查且逻辑在同一代码块中（`if (i >= 0 && i < size)`）
- 索引来自受信任源（初始化值、固定配置、库内部操作）
- 编译器能静态验证的情况（如 `array[N]` 中 N 为编译期常数）

**代码异味**：
- 索引计算复杂但无验证，需跨函数/模块追踪
- 大小参数与索引无直接关联，隐含依赖关系
- 条件判断与真实使用场景不符，存在逻辑缺陷
- 防御性编程不一致，某处有检查，某处无检查

## Audit Tips

**快速判断技巧**：
1. **污点源追踪**：从 `[]` 操作反向追踪索引来源，判断是否为用户可控
2. **边界检查模式识别**：识别 `<`, `<=`, `>=`, `>` 的完整性，识别 `&&` 和 `||` 的逻辑
3. **类型转换危险区**：`int` ← `unsigned`、`long` ← `int`、位移操作后的索引
4. **时序检查**：验证是在使用前检查，还是使用后"补救"

**真实案例区分**：
- **漏洞案例**：`for(int i=0; i<=user_size; i++) arr[i]`（循环条件 `<=` 导致 i 等于 size 时越界）
- **误报案例**：`for(int i=0; i<BUFFER_SIZE; i++) arr[i]`（BUFFER_SIZE 为编译期常数）
- **异味案例**：`arr[idx_from_func()]`（无法快速确定 idx_from_func() 的返回值范围）

## Low risk

- 索引为常量或 `#define` 宏定义，编译期已知不会越界
- 有多条件防御（负数检查、上界检查、符号检查），逻辑清晰无遗漏
- 使用迭代器、范围循环或容器库提供的方法（STL `.at()`）
- 二维/多维数组严格按行列迭代，无动态灵活索引
- 明确的 `assert()` 或编译期静态检查（如模板特化）
- 索引来自内部状态机或受信任的初始化逻辑

## Common Pitfalls

**易被忽视的陷阱**：
- **Off-by-one 错误**：`for(i=0; i<=size; i++)` vs `for(i=0; i<size; i++)`，前者会多访问一个元素
- **无符号数下界检查失效**：`if (idx >= 0)` 对 `unsigned int` 恒真，应删除此检查
- **整数溢出导致的假检查**：`if (offset + len < array_size)` 当 `offset + len` 溢出时检查失效
- **条件判断的逻辑缺陷**：`if (i > 0 || i < size)` 应为 `&&`，目前条件恒真
- **动态数组大小不同步**：大小参数在函数入参，但实际数组由调用方提供，易产生不匹配

**多步计算中的隐患**：
- `array[row * col_count + col]`：需验证 row 和 col，以及 `row * col_count` 不溢出
- `buffer[base + offset]`：追踪 base 和 offset 分别的来源和边界
- 嵌套循环索引：`matrix[i][j]`，需确保 i、j 的范围都被验证

## Advanced Discrimination

**跨模块追踪策略** (L4级审计)：
- 当索引来自函数返回值时，需回溯该函数的所有返回路径
- 检查返回值的文档或注释是否明确其范围限制
- 对于 API 调用返回的大小，验证调用方是否正确使用
- 识别"守卫函数"（如 `validate_index()`），确认其实现的正确性

**符号/无符号混用检查**：
- `int index` 与 `size_t array_size`：比较时会隐式转换，需关注
- `signed index` 赋值为 `unsigned` 后，超大正数会变成负数
- 字节/整数类型的索引转换：`uint8_t data[]; uint32_t idx;` 使用时的扩展规则

**时间序列判断**：
- 检查是否在分配数组后、使用前进行验证
- 识别"延迟验证"（先使用，后检查），这类代码常被重构时遗漏
- 多次调用同一数组，是否每次都验证索引

## High Risk Indicators

**强烈怀疑的标记**：
- 使用指针算术代替数组索引（`ptr + offset` vs `array[offset]`），检查更复杂
- 循环变量未初始化或初始化值不明确
- 边界值硬编码在多个地方（单点修改易导致不一致）
- 函数注释或代码中有 `TODO: check bounds`、`FIXME: potential overflow` 等标志
- 存在已知的 CVE 影响同类代码片段

## Audit Workflow

**系统化审计流程**：
1. **快速扫描阶段**：使用 `grep "\[\|for\|while"` 定位所有数组访问和循环点
2. **初筛阶段**：分离出带明确常数索引和低风险循环（范围循环、已验证索引）
3. **深度分析阶段**：追踪剩余的每个动态索引的来源链路
4. **交叉验证阶段**：对于多次使用同一数据结构的代码，检查一致性

**关键询问清单**：
- [ ] 索引来源是否用户可控或外部可影响？
- [ ] 是否存在 `<`、`<=`、`>` 的边界检查？下界是否被检查？
- [ ] 多步计算（如乘法、加法）是否可能溢出？
- [ ] 类型转换（尤其跨符号/无符号）是否安全？
- [ ] 数组大小与索引值是否在同一作用域内已验证？

## Real World Examples

**真实漏洞案例**（CVE式思路）：
```
// 易漏检查的写法
void process_array(int *data, int user_len) {
    for (int i = 0; i <= user_len; i++)  // 越界！
        data[i] = 0;
}

// 恶意调用：process_array(arr, 99) 时会访问 arr[0..99]，超出数组界限
```

**隐蔽的漏洞**：
```
// 两步验证但存在逻辑缺陷
int idx = validate_index(user_input);  // 返回 -1 表示无效
if (idx != -1)  // 检查不完整
    arr[idx] = value;  // idx 可能为任意值
```

**虚假的保护**：
```
// 检查与使用不在同一代码路径
if (size > MAX_ARRAY) return error;
// ... 中间可能有异常、递归、线程切换
arr[size] = data;  // size 已被修改，原检查无效
```

## Distinction Matrix

| 判断维度 | 真实漏洞 | 误报 | 代码异味 |
|---------|--------|------|---------|
| 索引来源 | 用户输入/外部 | 常数/受信任 | 依赖函数返回值 |
| 边界检查 | 无检查 | 完整检查 | 部分检查/条件模糊 |
| 类型风险 | 符号/无符号混用 | 同一类型 | 涉及转换但可追踪 |
| 验证时机 | 使用后/无 | 使用前 | 可能过期/被打破 |
| 代码位置 | 暴露在外 | 隔离/受控 | 跨模块，需追踪 |
