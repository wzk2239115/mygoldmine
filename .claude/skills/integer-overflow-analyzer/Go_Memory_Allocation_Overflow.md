# Go_Memory_Allocation_Overflow

**漏洞类型**: 内存分配溢出，unsafe 包或 CGO 调用中的内存分配大小计算

**Go**

---

专注于这一垂直漏洞类型研判任务，从漏洞成因触发，编写该md文件，包含一下三个小标题，【注意语言精炼，表达简洁，可以作为审计小抄，仅专注于审计，不包含攻击与修复】：

## Details

**代码示例**：`unsafe.Sizeof()`、`C.malloc(C.size_t(size))`、`reflect.SliceHeader{Len: len, Cap: cap}`、使用 CGO 时的内存操作

- **核心操作定位技巧** (L2: 跳读)：扫描 `unsafe` 包和 CGO 调用（`C.*`）。关注涉及内存大小计算的操作，特别是 `unsafe.Pointer`、`reflect.SliceHeader`、以及 C 函数调用（malloc、calloc）。检查大小参数来自计算结果的情况。

- **保护机制定位技巧** (L3: 逐行读)：查找内存大小上限验证、使用安全的内存分配方式（避免 unsafe 和 CGO），或使用 Go 原生内存管理。检查是否对大小计算进行溢出检查、以及是否有内存泄漏风险。

## Classify

判断是否为漏洞的要点：
- **确定漏洞**：内存大小来自不受信任的源，计算可能溢出，导致内存损坏、崩溃或安全漏洞
- **误报**：使用 Go 原生内存管理、大小有明确验证、仅用于受控环境
- **代码异味**：使用 unsafe 或 CGO，需仔细审计所有内存操作

## Low risk

- 避免使用 unsafe 包和 CGO
- 内存大小为常量或有明确上限
- 使用 Go 原生的 slice/map 代替手动内存管理
- 所有大小计算都经过溢出检查
- 有完善的错误处理和资源清理

## 审计技巧与经验

### 数据流追踪技巧

1. **函数参数来源追踪**：内存大小参数从何而来
   - 直接来自用户输入（HTTP query、POST body、JSON）→ 高危
   - 经过绑定验证标签（JSON/XML tag）→ 需检查验证逻辑
   - 来自配置文件读取 → 中等风险，需检查配置读权限
   - 硬编码常量或系统参数 → 低风险

2. **计算链路分析**：追踪大小值从输入到 unsafe/CGO 的全路径
   - 单次乘法溢出（如 `count * sizeof`）
   - 多步链式计算（加减乘除混合）
   - 条件分支中的大小差异

3. **边界条件测试**：输入极值场景
   - `math.MaxInt64`、`math.MaxUint64` 相关计算
   - 0 值的处理
   - 负值（如果参数为有符号整数）

### 真实漏洞特征

**关键信号**：
- `unsafe.Pointer` + 计算大小 = 必审
- CGO 的 `C.malloc(C.size_t(计算式))` = 必审
- `reflect.SliceHeader` 手动构造 + 外部大小 = 高优先级
- 使用 `math/big` 但最终转换为 int 时未检查 → 漏洞信号

**真实案例模式**：
```go
// 漏洞：length 来自 HTTP 请求
size := getHeaderLength()  // 用户控制
buf := C.malloc(C.size_t(size * 8))  // 乘法溢出风险
```

### 常见误报场景

1. **buffer pool 预分配**
   - 固定大小 pool：`NewPool(1024*1024)` → 低风险
   - 但若 pool 大小基于配置文件 → 需检查配置权限

2. **内部使用的 unsafe**
   - 仅用于同步原语、反射优化等受控场景
   - 例：`sync.Pool` 内部的 unsafe 操作 → 误报

3. **第三方库的 CGO 封装**
   - 如 SQLite、LevelDB 的 Go binding
   - 若绑定层无直接用户输入 → 通常不是漏洞
   - 但若库允许直接传入大小参数 → 需审计库的验证

4. **类型转换中的"虚假溢出"**
   - `int32 → int64` 自动转换通常安全
   - 但 `uint64 → int64` 需特别注意符号变化

### 区分技巧检查清单

| 特征 | 真实漏洞概率 | 审计要点 |
|------|------------|--------|
| 大小参数直接来自用户输入，无验证 | 95% | 立即标记，追踪完整数据流 |
| 有长度检查，但检查在 unsafe 前 | 80% | 检查检查条件是否被绕过 |
| 使用了 `math.MaxInt` 相关常量 | 50% | 常见误报，但需确认是否用于上限 |
| CGO 调用但无对应的大小验证 | 75% | 中等优先级，检查 C 库文档 |
| 仅在单元测试中暴露内存操作 | 5% | 通常误报，但若有集成测试路径 → 升级优先级 |

### 审计工作流

1. **快速定位**（5 分钟）
   - 搜索 `unsafe.Pointer`、`unsafe.Sizeof`、`C.malloc`、`reflect.SliceHeader`

2. **数据流分析**（10-20 分钟）
   - 追踪参数来源：是否可被外部控制
   - 记录涉及的所有计算步骤

3. **验证逻辑检查**（5-10 分钟）
   - 是否存在上限验证、溢出检查、类型范围检查

4. **风险判定**
   - 无验证 + 外部输入 = 漏洞
   - 有验证但逻辑有缺陷 = 漏洞
   - 有完整验证 = 低风险或误报

### 常见陷阱

- **假设第三方库已做好验证**：某些 CGO 库文档不完整，需自己验证
- **符号混淆**：`int` vs `uint` 的边界条件常被忽略
- **并发条件**：TOCTOU（Time-of-Check-Time-of-Use）漏洞，分配大小被改变
