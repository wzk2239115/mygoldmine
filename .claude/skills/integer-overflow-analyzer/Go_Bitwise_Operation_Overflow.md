# Go_Bitwise_Operation_Overflow

**漏洞类型**: 位操作溢出，左移或位运算结果超出类型范围

**Go**

---

## Details

**代码示例**：`value << shift`、`mask := (1 << bits) - 1`、`result = a | b`、负数左移

- **核心操作定位技巧** (L1: 关键词扫描)：扫描位运算符（`<<`、`>>`、`&`、`|`、`^`）。关注移位量来自用户输入或计算结果的情况。Go 中移位操作对于有符号整数可能产生未定义行为。检查移位量是否超出类型位宽。

- **保护机制定位技巧** (L2: 跳读)：查找移位量范围检查（`if shift >= 64`、`if shift < 0`），使用 `bits` 包的安全函数（如 `bits.RotateLeft`），或限制移位量在合理范围内。检查是否对负数进行移位。

## Classify

判断是否为漏洞的要点：
- **确定漏洞**：移位量来自不受信任的源，无范围检查，可能导致未定义行为或意外结果
- **误报**：移位量为常量或有明确验证、移位量在类型位宽内、仅用于位标志操作
- **代码异味**：对有符号整数进行移位，需确认是否安全

## Low risk

- 移位量为常量或有明确范围验证（0 ≤ shift < bitWidth）
- 使用 `bits` 包的安全函数
- 移位操作仅用于无符号整数
- 移位量使用 `% bitWidth` 限制范围
- 仅用于位标志或掩码操作

## Audit Techniques

### 真实漏洞的特征

1. **移位量源自用户输入且无验证**
   - 典型场景：从 HTTP 参数、文件读取、网络报文直接获取移位量
   - 危害：`uint32(input) << userProvidedShift`，userProvidedShift > 32 导致未定义行为
   - 识别信号：跟踪数据流，确认输入端点是否存在边界验证

2. **有符号整数的左移操作**
   - Go 规范明确：对有符号整数的左移是未定义行为（若结果溢出）
   - 真实例子：`int32(value) << 30` 当 value > 3 时产生符号位污染
   - 审计要点：区分 `int` 和 `uint` 类型，有符号数左移需重点关注

3. **循环中的动态移位量**
   - 场景：`for i := 0; i < len(data); i++ { mask |= (1 << data[i]) }`
   - 风险：data[i] 未验证范围，超过 64 会导致溢出
   - 验证方法：检查循环内是否存在 `data[i] >= 64` 或类似检查

4. **位掩码计算中的隐性溢出**
   - 代码：`mask := (1 << bitCount) - 1` 当 bitCount = 64 时溢出
   - 识别：追踪 bitCount 的来源，确认上界检查
   - 误区：假设 bitCount ≤ 31，但可能接收更大的值

### 误报的常见陷阱

1. **常量位移不是漏洞**
   - 正常：`const mask = (1 << 8) - 1` 编译时常量折叠，编译器会检查
   - 陷阱：看到 `<<` 就告警，但编译器已保证安全性

2. **受信任源的受限位移**
   - 例如：`port := 80 + (rand.Intn(100) << 1)`，移位量固定在合理范围
   - 识别方法：确认随机数上界，验证 rand.Intn(n) 返回 [0, n) 的值

3. **模运算保护被忽视**
   - 代码：`shift := userInput % 64; result := value << shift`
   - 注意：`% 64` 已保证 shift 在 [0, 63]，这是有效的防护
   - 审计错误：没有识别到模运算的约束作用

4. **按位操作的类型差异**
   - `uint64(1) << 60` vs `uint32(1) << 31`，前者安全，后者溢出
   - 陷阱：混淆类型宽度导致误判，需确认具体的操作类型

### 真实案例区分

**真漏洞**：
```go
func processFlags(input []byte) uint64 {
    var flags uint64
    for _, idx := range input {  // idx 来自网络数据，无范围检查
        flags |= (1 << idx)      // idx 可能 > 63
    }
    return flags
}
```

**误报**：
```go
func processFlags(count int) uint64 {
    if count < 0 || count > 63 {
        return 0  // 范围验证
    }
    return (1 << uint(count)) - 1
}
```

### 审计清单

- [ ] 位运算操作数是否来自外部输入（网络、文件、用户参数）
- [ ] 是否存在移位量范围检查（0 ≤ shift < bitWidth）
- [ ] 有符号整数的左移操作是否会导致符号位污染
- [ ] 循环体内的位操作索引是否受限制
- [ ] 是否使用了 `bits` 包的安全函数替代原生操作
- [ ] 掩码生成公式中的上界是否经过验证
- [ ] 错误处理路径是否覆盖了越界场景

### 快速判别技巧

**关键数据流追踪**：
- 从输入源（flag、HTTP 参数、数据库、文件）出发，跟踪变量经过的转换步骤
- 确认是否存在"信任边界"：即便中间有计算，只要最后移位量无检查就是漏洞
- 注意 `int` 与 `uint` 的隐式转换，类型转换可能掩盖溢出风险

**常见的防护模式**：
- `if shift < 0 || shift >= 64 { return error }` — 显式范围检查（最可靠）
- `shift := shift & 0x3F` — 按位与掩码，等效于 `% 64`（对无符号数有效）
- `if (1 << shift) > maxValue { return error }` — 基于结果的反向检查（可能不够）

**危险的业务逻辑**：
- 从协议报文、JSON、配置文件中直接读取位宽参数，再用于移位
- 数据库查询结果用作移位量，尤其当查询结果可被用户控制时
- 文件解析过程中提取的字段直接用于位操作，未校验

**编译器优化陷阱**：
- Go 编译器对常量折叠会检查溢出，但动态值的位移错误可能被忽视
- 即使代码看起来合理，如果移位量来自用户，仍需显式验证

### 易混淆的漏洞判别场景

1. **右移 vs 左移**
   - 右移不会导致值增长，逻辑右移安全，但算术右移（有符号数）需检查符号扩展
   - 左移才是真正的危险操作，导致数值扩大和溢出

2. **按位 AND/OR/XOR 是否会溢出**
   - `a & b`、`a | b`、`a ^ b` 的结果大小不超过操作数，不会独立溢出
   - 但若这些操作后续用于左移，则需检查移位量的合法性

3. **多步位操作的累积风险**
   - 代码：`mask = (1 << bit1) | (1 << bit2)` — 需验证 bit1 和 bit2 都在范围内
   - 每一个 `1 <<` 都是独立的溢出风险点，不能只检查一个

4. **与数值类型关联的隐含范围**
   - `byte` 的索引最多 8，但如果强转后作为移位量需重新验证
   - `int32` 的范围是 -2^31 ~ 2^31-1，负数左移时行为未定义

### 审计难点与高危场景

**常被审计师忽视的场景**：
- 在库函数或中间件中的位操作，假设输入已被验证但实际未验证
- 并发代码中的原子操作涉及位操作，竞态条件使得移位量检查失效
- 代码注释中声明了范围假设（如"bitWidth ≤ 32"），但代码无强制执行

**高危的上游数据源**：
- 环境变量、启动参数：用户可控但易被遗漏验证
- 配置文件、数据库初始化值：看似"可信"但可被间接污染
- 消息队列、缓存数据：来自其他服务的数据不能盲信
