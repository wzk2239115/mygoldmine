# C_Bitwise_Shift_Overflow

**漏洞类型**: 位操作和移位溢出，左移操作导致符号位改变或超出范围

**C/C++**

---

## Details

**代码示例**：`value << userShiftAmount`、`(1 << bits)`、`flags |= (1 << position)`、带符号整数的左移

- **核心操作定位技巧** (L1: 关键词扫描)：扫描 `<<` 和 `>>` 操作符，特别是左移操作。关注移位数量来自用户输入、循环变量或网络数据的代码。同时检查左移操作数的类型（有符号 vs 无符号）。重点留意在网络数据解析、配置文件读取、API参数处理等边界处的移位操作。

- **保护机制定位技巧** (L2: 跳读)：查找移位前的范围检查（`if (shift > 31)` 或 `if (shift >= sizeof(int) * 8)`）、使用 `unsigned int` 类型、或明确的溢出检查逻辑。注意检查是否使用了安全的移位库函数或编译器内置函数（如GCC的`__builtin_clz`）。

## Classify

判断是否为漏洞的要点：
- **确定漏洞**：移位数量来自不受信任的源且无验证，移位结果参与关键计算（内存分配、数组索引、权限计算）
- **误报**：移位数量为常量或明确验证过，移位仅用于日志/格式化、或结果立即被截断
- **代码异味**：有符号左移，或移位后的值跨模块使用、或移位数量范围不确定

## 审计专业技巧

**真实漏洞特征识别**：
1. **信任链追踪** (L4: 跨模块追踪)：移位数量最终来源于用户可控的输入，需追踪整个信任链。常见误判是认为某个中间变量已被验证，但实际未检查初始输入。例如：`int shift = get_user_input(); process_data(shift)` 中，如果 `process_data` 内部未验证，则存在漏洞。

2. **类型转换陷阱** (L3: 逐行读)：注意隐式类型转换可能导致的绕过。如 `unsigned char * signed int` 的混合移位操作，或将 `size_t` 无符号移位结果用作有符号整数上下文。例如：`int result = (int)(value << bits)` 属于真实漏洞；而 `unsigned int mask = (1U << bits)` 通常无风险。

3. **控制流依赖** (L3: 逐行读)：移位结果是否直接用于关键决策或内存操作。如 `malloc(1 << user_bits)` 或 `array[1 << index]` 是真实漏洞；而 `log_value(1 << bits)` 通常无害。

**常见误报场景**：
1. **常量传播分析不足**：认为编译器优化后的常量移位存在漏洞。实际上 `#define MASK (1 << 16)` 即使在宏中也已是常量，L0快速跳过。

2. **位域操作混淆**：位域（bit field）的左移操作通常由编译器保护，如 `struct { unsigned int flag:1; } x; x.flag = (1 << 0)` 是安全的，属于编译器强制的范围限制。

3. **有符号数字常量误判**：代码中 `int x = 1 << 30` 虽然操作有符号数但常量确定，无实际风险。真实漏洞是 `int x = 1 << user_input` 的动态情况。

4. **右移操作假阳性**：右移操作 `value >> bits` 通常无溢出风险（仅影响精度），除非结果用于缓冲区大小计算。关键区别在于操作的**方向**和**后续用途**。

**审计检查清单**：
- [ ] 移位操作数是否来自外部输入（函数参数、网络数据、文件内容）？
- [ ] 移位前是否进行了范围验证？验证是否包括负数检查和上界检查？
- [ ] 操作数类型是有符号还是无符号？有符号左移在C标准中为UB。
- [ ] 移位结果的后续使用场景是否安全（日志、计算、还是内存操作）？
- [ ] 是否存在隐式类型转换，导致溢出被隐藏或被截断？
- [ ] 移位数量是否被限制在实际有效范围（0 到 sizeof(type)*8-1）？

## 真实案例与误报对比

**案例1：内存分配漏洞（真实）**
```c
// 危险：移位数量来自用户输入
void process_buffer(int bits) {
    int size = 1 << bits;  // bits=31时，导致size为负数或溢出
    char *buf = malloc(size);  // 分配极小或无效的内存
}
```
审计要点：移位后的结果直接用于 `malloc`，属于 L4 跨模块追踪，需确认 `bits` 是否验证。

**案例2：权限检查绕过（真实）**
```c
// 危险：权限掩码计算中的溢出
int permissions = (1 << user_privilege_level);  // level=31时溢出
if (permissions & ADMIN_FLAG) grant_access();  // 可能绕过权限检查
```
审计要点：移位结果用于安全决策，属于 L3 逐行读，需检查 `user_privilege_level` 的范围限制。

**案例3：常量场景（误报）**
```c
// 安全：常量编译期计算
#define FEATURE_MASK (1 << 8)  // 编译器优化，无运行时风险
#define MAX_PRIORITY (1 << 5)  // 属于L0快速跳过
```
审计要点：所有操作数均为常量，预编译期确定，L0 直接跳过。

**案例4：位域操作（误报）**
```c
// 安全：编译器强制范围限制
struct flags {
    unsigned int enabled : 1;
    unsigned int priority : 3;
};
struct flags f;
f.priority = (1 << 2);  // 编译器自动截断至3位范围
```
审计要点：位域本身限制了有效范围，属于编译器保护，L0 跳过。

## Low risk

- 移位数量为编译期常量（0-30），被移位值为常数
- 使用无符号整数进行移位操作，且结果不参与内存操作
- 移位结果仅用于标志位操作（单个 bit），无跨类型转换
- 明确限制移位范围的检查，如 `if (shift < (int)sizeof(int) * 8)` 且在关键操作前执行
- 位字段操作（struct 中的 bit field），由编译器强制范围限制
- 移位用于常量预计算，如 `const int MASK = 1 << 8`
- 移位后立即进行截断操作（如 `& 0xFF`），限制了实际影响范围

## 高危信号（必须深入审计）

- 函数参数中的移位数量来自网络解析或用户输入，且函数内无边界检查
- 移位结果用于计算缓冲区大小、数组索引或内存分配大小
- 存在隐式整数类型转换（如 `int` 转 `size_t`）后进行移位
- 移位操作在循环中动态执行，循环条件可由外部控制
- 存在条件编译或平台相关的位宽假设（如假设 `int` 为32位）
- 移位数量来自可被中间人攻击的来源（文件、网络、消息队列）

## 快速审计流程

1. **第一遍（L1）**：用关键词 `<<` 和 `>>` 定位所有移位操作
2. **第二遍（L2）**：快速筛选：常量?无符号?有检查?若都是则L0跳过
3. **第三遍（L3）**：对可疑项逐行审视：移位数量来源？结果用途？有无截断?
4. **第四遍（L4）**：跨模块追踪移位数量的完整信任链，确认每个环节的验证
5. **最终判定**：结合数据流分析、控制流分析确定真实可利用性

## 易混淆的审计陷阱

**陷阱1：负数检查的重要性**
常见误判：认为检查了 `if (bits < 32)` 就足够安全。实际漏洞：未检查负数。
```c
// 看似有检查，但仍存在漏洞
if (bits < 32) {  // 未检查bits是否为负
    int mask = 1 << bits;  // bits=-1时导致未定义行为
}
```
正确做法：必须同时检查 `if (bits >= 0 && bits < 32)`

**陷阱2：类型转换导致的绕过**
```c
// 危险的隐式转换
unsigned long size = 1UL << user_input;  // user_input为int，可能为负
if (user_input < 64) {  // 检查不足以防止有符号扩展
    size = 1UL << user_input;  // user_input=-1时，未定义行为
}
```

**陷阱3：条件检查与实际操作分离**
```c
// 漏洞：检查和操作分离，中间可能被修改
validate_shift_amount(bits);  // 验证bits在0-31
// ... 其他代码，bits可能被修改 ...
int result = 1 << bits;  // bits已改变，验证失效（TOCTTOU）
```

**陷阱4：混淆移位运算符的安全性**
```c
// 误认为右移更安全，但后续可能有问题
int compressed = large_number >> user_bits;
// 如果压缩结果用于数组索引或大小计算，仍可能产生整数溢出
if (compressed > MAX_SIZE) allocate(compressed);  // 可能溢出
```

## 审计加速技巧

**关键源追踪**：
- 直接来自函数参数的移位数量：必须 L3 检查
- 来自循环变量的移位：需检查循环边界
- 来自宏定义的移位：优先检查宏的具体值
- 来自全局变量的移位：需跨文件追踪

**关键操作追踪**：
- 移位→ malloc/calloc/realloc：关键，必须审计
- 移位→ memset/memcpy 的大小参数：关键，必须审计
- 移位→ 数组下标：关键，必须审计
- 移位→ 权限/标志检查：关键，必须审计
- 移位→ 日志输出：低危，可L0跳过
- 移位→ 纯粹的位操作处理：中等，L2处理

## 真实漏洞的模式识别

**经典模式1：缓冲区大小计算**
```c
// 高风险模式
int get_frame_size(int bits_per_sample) {
    return 1 << bits_per_sample;  // 直接用于分配
}
buf = malloc(get_frame_size(user_bits));
```
特征：返回值直接用于内存分配，bits_per_sample无法验证

**经典模式2：权限升级**
```c
// 高风险模式
int user_capability_mask = 1 << get_user_role();  // 用户可控role
if (user_capability_mask & SYSTEM_ADMIN) {  // 权限检查
    execute_privileged_operation();
}
```
特征：移位结果影响安全决策，用户角色可被操纵

**经典模式3：协议解析**
```c
// 高风险模式
struct packet {
    uint8_t flags;
} p = parse_network_packet(data);
int important_bit = (1 << p.flags) & CRITICAL_MASK;  // flags来自网络
```
特征：移位数来自协议字段，无验证即使用
