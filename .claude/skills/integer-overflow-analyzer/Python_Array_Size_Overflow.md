# Python_Array_Size_Overflow

**漏洞类型**: 数组或列表大小计算溢出，使用 NumPy 数组或其他扩展时基于用户输入创建数组

## Details

**代码示例**：`np.zeros(user_shape)`、`np.array([0] * size)`、`bytearray(length)`、`list([None] * count)`

- **核心操作定位技巧** (L1: 关键词扫描)：扫描 NumPy 数组创建函数（`np.zeros`、`np.ones`、`np.empty`）、`bytearray()`、列表乘法 `[x] * n`。关注大小参数来自用户输入、计算结果或外部数据的情况。检查 shape 参数的各维度乘积。

- **保护机制定位技巧** (L2: 跳读)：查找大小上限验证（`if size > MAX_ARRAY_SIZE`、`if np.prod(shape) > limit`），使用内存限制，或采用稀疏矩阵/流式处理。检查是否捕获 MemoryError 异常。

## Classify

判断是否为漏洞的要点：
- **确定漏洞**：数组大小来自不受信任的源，无上限检查，可能导致内存耗尽（DoS）
- **误报**：大小有明确上限、使用稀疏矩阵、有内存限制和异常处理
- **代码异味**：动态计算数组大小，需评估是否可能超出可用内存

## Low risk

- 数组大小为常量或有明确上限
- 使用 `min(size, MAX_SIZE)` 限制大小
- 使用稀疏矩阵（scipy.sparse）处理大型数据
- 有 MemoryError 异常处理
- 使用流式处理或分块加载

## Audit Tips（审计专业技巧）

### 真实漏洞特征

1. **多维数组陷阱**：`np.zeros((h, w, c))` 中，三个维度乘积才是实际分配大小。若 `h=10000, w=10000, c=3`，实际需要 300M 内存。审计时需计算维度乘积，不只看单个参数。

2. **隐含的整数溢出**：多维度乘积可能发生整数溢出（32位系统）。若 `shape=(50000, 50000)`，乘积为 2.5e9 超过 2^31，可能绕过检查。检查是否使用 64 位整数计算乘积。

3. **循环创建积累**：
   ```python
   arrays = []
   for item in user_list:
       arrays.append(np.zeros(item))  # 多次分配未释放
   ```
   即使单次分配合理，累积也可能耗尽内存。需追踪生命周期。

4. **列表乘法的隐患**：`[0] * user_size` 在 Python 中直接分配内存，若 user_size=1e9，程序立即崩溃。这是 Python 特有陷阱。

5. **shape 参数绕过**：部分代码可能只检查 shape 的某一维度，如只验证 `shape[0] < 1e6`，而忽视其他维度。需全面审查所有维度的验证。

### 常见误报陷阱

1. **内存充足的开发环境**：开发机器内存充足，即使代码存在溢出风险也能运行。生产环境内存限制可能触发漏洞。不能以开发环境行为为依据。

2. **异常捕获的假安全**：
   ```python
   try:
       data = np.zeros(size)
   except MemoryError:
       pass  # 只记录日志，未实际处理
   ```
   捕获异常但无实际处理逻辑，服务仍可被 DoS。异常处理必须有明确的降级或拒绝策略。

3. **条件检查的遗漏**：
   ```python
   if size < 1e6:
       arr = np.zeros(size)
   ```
   表面上有检查，但若 size 是负数（整数下溢），或浮点数比较精度问题，检查失效。需验证数据类型和边界条件。

4. **依赖配置的虚假防护**：代码依赖外部配置文件限制大小，但配置文件可被篡改或配置加载失败使用默认值。需审查配置的加载、验证和降级方案。

5. **库函数的假设**：假设 `scipy.sparse` 自动处理溢出，但实际取决于使用方式。`sparse.lil_matrix((n, m))` 初始化时仍需分配内存结构。

### 审计检查单

- [ ] 定位所有数组/列表创建调用点，记录大小参数来源
- [ ] 识别多维数组，计算各维度乘积的最大值
- [ ] 追踪大小参数的数据流：用户输入 → 计算 → 使用，检查流程中每一步
- [ ] 验证整数类型：32 位 int 是否可能溢出，是否存在隐含类型转换
- [ ] 确认保护机制：检查语句位置、条件逻辑、异常处理的完整性
- [ ] 评估环境约束：系统资源限制（ulimit）、容器内存上限、OOM Killer 行为
- [ ] 测试边界值：负数、零、最大值、浮点精度问题
- [ ] 审查累积场景：循环、递归、缓存中多次分配的总量

### 真实 vs 误报案例

| 场景 | 代码示例 | 判断 | 原因 |
|------|--------|------|------|
| 无检查的用户输入 | `np.zeros(request.args['size'])` | 漏洞 | 直接使用 HTTP 参数，无类型/范围验证 |
| 带上限的检查 | `size = min(int(arg), 1000); np.zeros(size)` | 低风险 | 明确上限限制，转换异常会抛出 |
| 异常捕获且记录 | `try: arr=np.zeros(size) except: log.error(...)` | 误报 | 异常被捕获，无进一步处理不代表安全 |
| 配置验证 | `size = config.MAX_SIZE; arr = np.zeros(size)` | 需评估 | 取决于 config 来源，若来自文件需验证加载过程 |
| 多维约束 | `np.zeros((h, w)) if h<1e6 and w<1e6` | 仍为漏洞 | 单维检查不足，乘积可达 1e12 超内存 |
| 稀疏矩阵 | `sparse.csr_matrix((n, m))` | 低风险 | 稀疏矩阵内存使用与非零元素数相关，分配本身不占用 |

### 审计效率建议

- **快速扫描**：使用正则定位 `np\.(zeros|ones|empty|full)` 和 `bytearray\(` 调用
- **重点审查**：优先检查没有后续检查语句的调用，即大小参数直接进入函数的情况
- **回溯数据流**：对可疑大小参数，向上回溯至输入源，判断是否受信任
- **对标业界**：参考 OWASP、CWE-190 案例，了解已知攻击场景
