# PHP_Type_Conversion_Overflow

**漏洞类型**: 类型转换溢出，字符串到整数转换、浮点数到整数转换时的溢出

**PHP**

## Details

**代码示例**：`(int)$stringValue`、`intval($userInput)`、`(float)$bigNumber`、字符串自动转整数

- **核心操作定位技巧** (L1: 关键词扫描)：扫描类型转换 `(int)`、`intval()`、`floatval()`。PHP 的类型转换可能截断或溢出。关注转换结果用于数组索引、算术运算、或业务逻辑的情况。检查字符串到数字的隐式转换。

- **保护机制定位技巧** (L2: 跳读)：查找转换前的范围验证（`is_numeric()`、`ctype_digit()`）、使用 `filter_var()` 进行安全转换、或检查转换后的类型和范围。检查是否对转换失败情况进行处理。

## Classify

判断是否为漏洞的要点：
- **确定漏洞**：类型转换无验证，可能导致数据截断或意外值（如 "123abc" 转为 123），影响业务逻辑
- **误报**：转换前有格式验证、使用 `filter_var()` 安全转换、转换失败有处理
- **代码异味**：频繁类型转换，需确认输入格式是否可信

## Low risk

- 使用 `filter_var(FILTER_VALIDATE_INT)` 验证和转换
- 转换前进行格式和范围检查
- 使用严格类型声明（`declare(strict_types=1)`）
- 转换失败有默认值或异常处理
- 转换仅用于非关键场景

## SKILL: 审计专业技巧

### 真实漏洞特征识别

**典型漏洞场景**：
1. **数组索引越界**：`$arr[(int)$id]` 未验证转换值范围，"99999999999999" 转为 PHP_INT_MAX 后作索引
2. **金额计算截断**：`(int)$price` 丢弃小数部分，"99.99" 转为 99，绕过价格验证
3. **访问控制绕过**：`intval($adminLevel)` 将 "1admin" 转为 1，与预期的 "admin" 不同但判断相等
4. **SQL 注入诱因**：未验证的转换结果直接拼接入 SQL：`"WHERE id = ".(int)$_GET['id']`，虽然转换本身安全但前提输入未验证

**关键审计点**：
- 转换结果是否用于数据库查询、文件操作、数组访问等敏感操作
- 转换是否发生在输入层（危险）vs 内部处理层（风险较低）
- 是否存在多步类型转换导致的二次绕过（如 JSON 编码后再转换）

### 误报与正报区分实战

**常见误报案例**：
```php
// 误报1：安全的配置值转换
$timeout = (int)getConfig('timeout', '30');
// 原因：配置值来自受信源，结果值 30 用于 sleep()，范围可控

// 误报2：严格验证后的转换
if (is_numeric($id) && (int)$id > 0 && (int)$id < 1000) {
    process((int)$id);
}
// 原因：转换前已验证范围，结果值 1-999 安全可用

// 误报3：错误处理完善
$converted = (int)$input;
if ((string)$converted !== $input) { // 检测转换损失
    return error("Invalid input");
}
```

**真实漏洞案例**：
```php
// 漏洞1：直接转换用户输入无验证
$user_id = (int)$_GET['user_id'];
$user = db_query("SELECT * FROM users WHERE id = $user_id");
// 问题：虽然 (int) 转换安全，但 $_GET['user_id'] = "999999999999"
// 可能超出预期的用户范围

// 漏洞2：转换结果用于权限判断
$role = (int)$_POST['role']; // "admin123" -> 0
if ($role === 1) { // 管理员
    grant_admin_access();
}
// 问题：字符串转换为 0，非管理员可能 POST "0xyz" 导致逻辑混乱

// 漏洞3：浮点转整数的精度丧失
$discount = (int)floatval($price) * 0.1;
// 99.99 -> 99 -> 9.9，vs 期望的 10.0
```

### 审计决策树

| 条件 | 判定 | 原因 |
|------|------|------|
| 转换前有 `is_numeric()` + 范围检查 | 低风险 | 已验证格式和范围 |
| 使用 `filter_var(..., FILTER_VALIDATE_INT)` | 低风险 | 原生安全过滤函数 |
| 转换用于配置/常量，输入来自可信源 | 低风险 | 输入源可控 |
| 直接 `(int)$_GET/$_POST/$_COOKIE` | 高风险 | 无验证直接使用外部输入 |
| 转换后用于数据库查询/数组索引 | 高风险 | 可触发越界或查询异常 |
| 转换结果用于金额/权限判断 | 高风险 | 可绕过业务逻辑 |
| 存在多层转换（string -> float -> int） | 中风险 | 每层都有精度丧失风险 |

### 实战审计检查清单

- [ ] 定位所有 `(int)`、`intval()`、`floatval()` 调用，检查输入源
- [ ] 验证转换前是否有范围检查（如 `$value > 0 && $value < MAX`）
- [ ] 追踪转换结果的使用场景（数据库查询、数组访问、计算）
- [ ] 检查是否存在隐式类型转换（如数组键的自动转换）
- [ ] 对于浮点转整数，确认是否有精度丧失风险
- [ ] 测试边界值：`PHP_INT_MAX`、`PHP_INT_MIN`、负数、科学计数法
- [ ] 检查是否有 `strict_types=1` 声明（明确类型要求）
