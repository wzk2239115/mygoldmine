# JavaScript_Business_Logic_Overflow

**漏洞类型**: 业务逻辑计数器溢出，金额计算、积分累计等业务逻辑未检查溢出

**JavaScript/TypeScript**

## Details

**代码示例**：`totalPrice += item.price * quantity`、`userBalance += points`、`counter++`、`score = score + bonusPoints`

- **核心操作定位技巧** (L2: 跳读)：重点审计涉及金额、积分、余额、计数器的累加操作。扫描业务逻辑中的 `+=`、`*=`、`++` 操作符，特别关注累积类变量（total、balance、count、score）。检查数值是否来自用户输入或循环累加。

- **保护机制定位技巧** (L3: 逐行读)：查找上限检查（`if (balance + amount > MAX_BALANCE)`）、使用安全的数值范围（Number.isSafeInteger）、或使用字符串/BigInt 处理金额。检查是否对累加结果进行定期校验或使用精确计算库（如 decimal.js）。

## Classify

判断是否为漏洞的要点：
- **确定漏洞**：金额/积分计算无上限检查，JavaScript Number 超出安全整数范围（2^53 - 1），影响业务正确性
- **误报**：数值范围明确在安全范围内、使用 BigInt 或精确计算库、仅用于统计展示
- **代码异味**：累加操作频繁，需评估是否会突破 MAX_SAFE_INTEGER

## Low risk

- 业务值明确在安全整数范围内（< 9007199254740991）
- 使用 BigInt 或 decimal.js 等精确计算库
- 金额以"分"为单位存储并使用整数运算
- 有明确的上限检查和异常处理
- 计算结果定期与数据库核对

## 审计专业技巧

### 数值边界追踪技术
- **源头追踪**：追溯数值来源，识别用户可控的输入端点（API 参数、URL 查询、消息队列）
- **流向分析**：跟踪数值如何流向累加操作，特别关注循环中的叠加（如 for 循环内部的 `+=`）
- **边界测试**：识别业务的实际最大值（年度订单总额、用户最大积分、并发计数），与 JavaScript 安全整数范围比较
- **溢出覆盖**：检查是否存在溢出后覆盖旧值的场景（如交易金额溢出后变为负数）

### 真实漏洞的标志特征
1. **多层递推累加**：`total = total + order.price * quantity * discount_multiplier`，特别是乘法链可能快速超出范围
2. **无上限用户输入**：前端验证能被绕过，后端未检查 `points: 9007199254740992`（已超安全整数）
3. **积分/金额与业务资产直接挂钩**：余额溢出可导致负数（实际增加资金）或变为 0（资金冻结），造成直接损失
4. **循环中的批量操作**：处理万级以上商品列表时，计算 `totalPrice += item.price` 可能累积误差甚至溢出
5. **跨交易持久化**：溢出数值存储至数据库，后续读取时已是错误值，无法恢复

### 误报常见原因及排除
| 场景 | 原因分析 | 确认方法 |
|------|--------|--------|
| 展示类计数 | 仅用于 UI 展示，不影响数据库业务 | 搜索该变量是否被用于数据库写操作或转账逻辑 |
| 有效范围内 | 业务预期最大值 < 2^53 - 1（如日均用户数） | 查看产品文档、API 限流、数据库 schema 中的 CHECK 约束 |
| BigInt 保护 | 使用 `BigInt(x)` 或库函数自动转换 | 确认整个计算链都使用 BigInt，不是混合 Number 类型 |
| 字符串金额 | 使用字符串存储金额避免精度问题 | 验证金额在库中类型为 VARCHAR/TEXT，计算时使用精确库 |
| 异常捕获恢复 | 溢出时主动抛错并回滚事务 | 查看 try-catch 块是否完全包围累加操作，且有补偿逻辑 |

### 常见陷阱与深度审计
- **Number.MAX_SAFE_INTEGER 误解**：开发者认为该值是上限，但实际业务数据可能接近此值，加法仍会溢出
- **类型强制转换**：字符串自动转 Number（如 `"999999999999999999" + 1`），溢出后无警告
- **浮点舍入**：金额使用小数点计算（`totalPrice += item.price`，其中 item.price 为 0.1），累积舍入误差可达万级偏差
- **并发修改**：多个请求同时累加同一余额变量（race condition），其中一次溢出未被检测到
- **隐藏的乘法**：`total = (base * quantity) + previous`，quantity 来自用户，可导致快速溢出
