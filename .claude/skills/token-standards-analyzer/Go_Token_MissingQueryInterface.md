# Go Token Missing Query Interface

## Details

**核心问题定位**：Cosmos SDK 代币模块要求实现标准的查询接口以获取代币信息。常见缺陷包括：
- 查询处理函数缺失（`Query()` 方法未实现或不完整）
- 查询类型不完整（缺少 Balance、Supply、Allowance 等查询）
- 返回值格式不符合标准（数据结构或字段名错误）
- 查询响应未进行适当的验证和序列化

**代码示例位置定位**（L1：关键词扫描）：
- 搜索 `func (k Keeper) Query()` 或 `func (k Keeper) Balance()` 查询函数
- 检查 `QueryMsg` 或 `Query` 类型定义中是否包含所有标准查询
- 扫描查询响应结构：是否包含 `BalanceResponse`、`SupplyResponse`、`AllowanceResponse`
- 验证是否存在查询路由逻辑（`querier.Route()` 或 switch 语句）

**保护机制识别**（L2：跳读）：
- 确认查询是否验证了输入参数（如账户地址有效性）
- 检查查询返回值是否正确反映了当前状态
- 验证是否存在查询缓存机制（避免重复计算）
- 审查查询响应是否进行了完整的序列化
- 检查是否处理了不存在的账户或授权（返回 0 而非错误）

## Classify

**理论研判标准**：

1. **确认为查询接口缺失**：
   - Query 函数完全不存在或不可调用
   - 查询类型完全不包含标准查询（无 Balance、无 Supply）
   - 返回值完全缺失或格式不符
   - 无法查询任何代币信息

2. **分别为代码异味**：
   - 查询接口存在但某些查询类型缺失（如缺少 Allowance）
   - 返回值存在但字段名不标准
   - 查询处理存在但未进行充分的输入验证
   - 某些查询性能不佳但功能正确

3. **排除误报**：
   - 项目实现了扩展的查询接口，同时保留了标准兼容的版本
   - 使用了 Cosmos SDK 标准库的查询实现
   - 查询由第三方 indexer 提供，智能合约本身不需要实现

## Low risk

**低风险评级场景**：

- 所有关键查询存在但某些可选查询缺失
- 返回值格式基本正确但某些字段缺失
- 查询性能不优化但功能完整
- 项目已通过充分集成测试，与钱包和 DEX 兼容

## 审计专业技巧

### 1. **精准定位真实漏洞的方法**

**问题识别的四层递进式审查**：
- **第一层：接口存在性检查** - 使用 AST 解析确认 Query 方法的确切签名，避免方法重载或包装层迷惑
- **第二层：路由覆盖度分析** - 追踪 querier 注册逻辑，确认每个查询路径都有对应的处理器，检查是否存在死代码路由
- **第三层：端到端调用链追踪** - 从客户端调用起始点，跟踪完整调用链至数据返回，验证中间每一层都正确传递和处理数据
- **第四层：边界条件测试** - 对边界情况进行模拟测试（零地址、最大供应量、不存在的授权记录等）

**实际案例**：某项目声称实现了 Balance 查询，但在跟踪调用链时发现查询方法返回的是缓存值，缓存在某些操作后未更新，导致用户看到过期的余额。这是真实漏洞而非接口缺失。

### 2. **常见误报场景与快速判别**

**误报陷阱一：接口版本兼容**
- 现象：看似缺失某个查询接口（如 Allowance），但实际上该项目实现了 CW20 标准的多版本兼容
- 快速判别：搜索版本标志（如 cw20_v1 vs cw20_v2），检查是否有向后兼容层；查看是否在文档或注释中明确说明了支持的接口版本
- 审计建议：确认项目文档与合约代码一致，版本号需在链上清晰可见

**误报陷阱二：继承与组合模式**
- 现象：主合约中未找到 Query 方法，误认为缺失
- 快速判别：检查是否存在 embedded struct 或 trait 继承，追踪父类/父 trait 实现
- 审计建议：对于使用模块化架构的项目，需深入检查依赖关系，不能仅看单个文件

**误报陷阱三：宏展开与代码生成**
- 现象：Go 中通过 `go:generate` 自动生成查询方法，手动搜索找不到
- 快速判别：检查文件头部是否存在 `//go:generate` 指令，确认生成目标文件
- 审计建议：运行 `go generate ./...` 后再审查，不要遗漏自动生成的代码

**误报陷阱四：第三方 SDK 集成**
- 现象：项目依赖 Cosmos SDK 提供的查询实现，而非自己实现
- 快速判别：查看 import 路径，检查 keeper 是否嵌入了标准库的 Keeper，通过 grep 搜索 "embedded" 或 "GRPC" 关键字
- 审计建议：验证依赖版本是否正确，确认 SDK 版本包含该查询实现

### 3. **区分真实漏洞与低风险的实战经验**

**真实漏洞的标志**：
- 无法通过任何途径（直接调用、继承、生成、SDK 提供）查询关键数据
- 标准 CW20 接口的强制要求缺失（Balance、TotalSupply）
- 对接钱包或 DEX 时直接报错，无法兼容
- 安全审计报告或官方文档明确指出该接口为"必需实现"

**低风险的标志**：
- 可选查询或扩展查询缺失（如 TokenInfo、Minter 等非强制接口）
- 接口存在但某些字段命名不符合约定（仍能解析，只是命名差异）
- 查询功能存在但未经过充分优化（响应时间慢但结果正确）
- 项目有明确的升级路线图，计划在下一版本中补充

**实际判别流程**：
```
缺失查询接口
    ↓
能否通过依赖库获得？ → YES → 检查依赖版本 → 记录为低风险
    ↓ NO
是 CW20 强制接口？ → YES → 真实漏洞，严重等级
    ↓ NO
项目文档中是否说明? → YES → 确认是设计选择，酌情低风险
    ↓ NO
是否影响核心功能? → YES → 真实漏洞
    ↓ NO → 代码异味，建议优化

### 4. **高效审查技巧**

**黑名单检查法**：
- 先建立一份"必须实现的查询清单"（如 CW20: Balance, TotalSupply, Allowance, Approval）
- 对每个必需项，在代码库中进行精确搜索（支持正则表达式）
- 对每个搜索结果进行代码路径追踪，确认真实可用

**对标检查法**：
- 找到项目声称兼容的标准（如 CW20），获取标准 Rust/Go 参考实现
- 使用 diff 工具对比关键方法，快速定位差异
- 重点检查差异部分是扩展功能还是真实缺陷

**集成测试溯源法**：
- 优先查看项目的测试文件（`_test.go`）
- 检查测试中是否覆盖了所有查询场景
- 如果某个查询在测试中缺失，通常表明该功能可能有问题或确实未实现

**依赖链追踪法**：
- 使用 `go mod graph` 确认所有依赖，特别是 Cosmos SDK 版本
- 检查 keeper 的初始化代码，确认是否调用了父 keeper 的初始化
- 追踪 gRPC 或 HTTP 路由注册，确认查询路由完整

**外部兼容性验证**：
- 尝试使用主流钱包（Keplr、Cosmostation）连接该链，测试余额查询
- 使用官方 CLI 工具（如 `gaiacli`）查询代币信息
- 如果外部工具能正常工作，则说明查询接口实际上是存在的

### 5. **常见漏洞利用场景**

**真实漏洞的利用方式**：
- 缺失 Allowance 查询 → 用户无法在链上验证授权额度，容易失误
- 缺失 Balance 查询 → 钱包集成失败，用户体验断裂
- 返回值格式错误 → 自动化工具解析失败，导致交互中断

**低风险漏洞的实际影响**：
- 字段名称不标准 → 生态工具可能需要特殊适配，但不影响核心功能
- 某个可选查询缺失 → 用户在高级功能上受限，但基础功能完整
- 查询性能不佳 → 在高并发时可能超时，但不导致数据错误
