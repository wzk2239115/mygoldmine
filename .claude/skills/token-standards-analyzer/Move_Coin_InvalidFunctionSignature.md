# Move Coin Invalid Function Signature

## Details

**核心问题定位**：Move Coin 标准规范要求 `transfer`、`mint`、`burn` 等关键函数的签名必须严格匹配标准定义。常见偏差包括：
- 参数类型不匹配（如使用 `u64` 代替 `u128` 的金额）
- 返回值缺失或类型错误（应返回 `bool` 或 void）
- 泛型参数定义不符（如 `<CoinType>` 的位置或约束条件）
- 访问控制修饰符错误（缺少 `public` 或 `entry` 标注）

**代码示例位置定位**（L1：关键词扫描）：
- 快速扫描文件中的 `public fun transfer` 关键字定义
- 对比函数签名的返回值类型：`fun transfer<T>(...) -> T { }` vs 标准规范
- 检查泛型参数约束：`<CoinType: key + store>` 的完整性
- 验证函数标注的完整性：`#[entry]` 是否存在，权限范围是否为 `public entry`

**保护机制识别**（L2：跳读）：
- 确认函数是否包含参数有效性检查（余额验证、零金额检查）
- 验证是否存在事件发出机制（`Emit` 事件记录转账行为）
- 检查是否实现了权限检查（只有授权地址才能调用 mint/burn）
- 审查函数是否进行状态更新（是否真正修改了 Coin balance）

## Classify

**理论研判标准**：

1. **确认为标准不符合**：
   - 函数签名与 Move Coin 标准严重偏差，无法被标准工具识别
   - 参数类型完全不同（如 `u64` vs `u128`）
   - 返回值完全缺失或类型完全错误
   - 泛型约束缺失导致类型检查失败

2. **分别为代码异味**（警惕但非严格错误）：
   - 函数存在但使用不标准的命名约定（如 `transferCoin` 代替 `transfer`）
   - 参数顺序不同但数量相同（部分钱包可能兼容）
   - 函数存在多个重载版本，其中部分符合标准

3. **排除误报**（真实实现，非问题）：
   - Move 模块可能自定义扩展签名，同时保留标准兼容的 wrapper 函数
   - 不同 Move 生态（Aptos vs Sui）可能存在签名轻微差异，但仍保持兼容性

## Low risk

**低风险评级场景**：

- 函数签名存在细微偏差，但项目明确声明为定制实现，不声称标准兼容性
- 参数类型差异仅影响精度（如 `u64` vs `u128`），但通过显式转换保证兼容性
- 缺少标准函数，但项目提供了等价的替代函数，且生态工具已针对性集成
- 函数签名变更已进行过充分的版本迁移和工具更新，社区已接受新签名标准

## 审计专业技巧

### 真实漏洞与误报的区分经验

**1. 签名偏差的实际影响评估**

审计时需要区分"技术上偏差"与"功能上破缺"：

| 偏差类型 | 实际威胁 | 判定方法 |
|--------|-------|--------|
| 返回值类型 (bool vs void) | 高 - 调用方无法确认操作成功 | 检查所有外部调用点是否处理返回值 |
| 参数顺序变更 | 中 - 依赖类型推导的包装器会失效 | 查询生态内部署数量和集成案例 |
| 泛型约束缺失 | 高 - 可能导致运行时类型错误 | 验证模块测试覆盖率和已有问题报告 |
| 函数名变更 (camelCase vs snake_case) | 低 - 符号表级别差异，不影响功能 | 检查是否存在标准别名 (alias) |

**2. 常见的真误报陷阱**

- **误报1：跨链适配判断错误**
  - 现象：Aptos 上使用 `0x1::coin::Coin<T>` 标准，Sui 上使用 `Coin<T>` 结构
  - 专业判断：逐链检查标准文档，不能混淆两个生态的规范
  - 验证方法：对比目标链的官方标准库源代码，而非第三方文档

- **误报2：包装函数混淆**
  - 现象：项目定义 `public fun custom_transfer(...)` 但内部调用标准 `transfer`
  - 专业判断：递归跟踪函数调用链，确认最终是否委托给标准实现
  - 代码示例：
    ```move
    public fun custom_transfer<T>(from: &mut Account, to: address, amount: u64) {
        // 表面签名不匹配，但实现通过adapter模式调用标准transfer
        let coin = withdraw<T>(from, amount);
        transfer(coin, to);  // 核心逻辑委托给标准函数
    }
    ```

- **误报3：版本兼容性忽视**
  - 现象：Aptos Coin 标准在 framework upgrade 中调整了泛型约束
  - 专业判断：检查代码的 Move 编译器版本、框架版本与审计时间的对应关系
  - 验证方法：在 `Move.toml` 中查看 `compiler_version` 和依赖的 `aptos-framework` 版本号

**3. 深度审计的信息收集流程**

第一步：**确认标准定义的时间点**
- 查询目标链的 framework 发布时间表（Aptos releases、Sui milestones）
- 对比项目代码的提交日期与标准定义时间
- 如果项目早于标准发布，则"不符合"本质上是时间问题，不是质量问题

第二步：**追踪函数的实际使用场景**
- 检查所有调用该函数的外部模块（通过 Grep 查询调用点）
- 统计这些调用点的成功部署数量和交互日志
- 如果实际交互量很大且无故障报告，说明功能实际可用

第三步：**分析文件变更历史**
- 查看代码仓库的 git 日志，函数签名是否曾经符合标准
- 如果存在历次尝试改正，说明开发团队意识到问题，当前非标仅是进行中的工作
- 检查相关 issue 和 PR 讨论，判断是否有明确的改进计划

**4. 特殊场景的判定要点**

**场景A：模块初始化函数签名异常**
- Move 要求 `init` 函数必须具有 `fun init(ctx: &mut TxContext)` 的确切签名
- 但 Sui vs Aptos 对 `init` 的调用机制差异导致表现不同
- 判定方法：验证模块是否能成功编译和部署，编译通过即无实质问题

**场景B：视图函数 (view) 的返回值类型**
- 某些项目用 `#[view]` 标注替代标准的 `public fun` 返回值
- 这在某些链上是新特性，旧标准检查工具可能报错
- 判定方法：确认目标链编译器版本是否支持该特性，支持则非漏洞

**场景C：权限修饰符的变体**
- `public entry fun` vs `public fun` vs `entry fun` 的选择影响可调用性
- 非 `entry` 函数无法被外部交易直接调用，但可被其他模块调用
- 判定方法：根据函数的实际用途确定权限需求，而非盲目套用标准

**5. 审计结论的质量检查清单**

在给出最终判定前，必须验证：

□ 是否查阅了目标链的最新官方标准文档（而非第三方总结）
□ 是否核对了代码所用 Move 编译器版本与标准发布版本的关联
□ 是否追踪了函数在生态中的实际使用情况和部署数据
□ 是否存在项目文档或 changelog 解释签名差异的原因
□ 是否通过编译和单元测试验证代码的功能可用性
□ 是否检查了相关的社区讨论或官方 issue 以确认该偏差是否为已知问题

只有同时满足上述多个条件的分析，才足以支撑"确认真实漏洞"的结论。
