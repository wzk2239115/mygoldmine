# Move NFT Missing Metadata

## Details

**核心问题定位**：Move NFT 标准要求 NFT 资源包含完整的元数据字段。常见缺陷包括：
- 元数据字段缺失（缺少 `name`、`description`、`uri` 等）
- 元数据存储结构不符合标准（未使用标准的 Object 或 Collection 结构）
- 元数据访问函数缺失（无法查询 name、uri 等信息）
- 元数据验证不完整（允许空值或过长的字符串）

**代码示例位置定位**（L1：关键词扫描）：
- 搜索 `struct NFT` 或 `resource NFT` 的定义
- 检查结构体字段：是否包含 `name: String`、`description: String`、`uri: Url`
- 扫描元数据访问函数：`name()`、`description()`、`uri()` 的实现
- 验证是否存在元数据存储映射（如 `table<ID, Metadata>`）

**保护机制识别**（L2：跳读）：
- 确认元数据是否为不可变（创建后无法修改）或可控修改（只有 owner 可修改）
- 检查元数据内容验证：是否验证了字符串长度、URL 格式
- 验证元数据完整性：是否强制要求所有字段都必须提供
- 审查元数据存储安全性：是否防止了元数据被意外覆写
- 检查是否实现了元数据的版本控制或升级机制

## Classify

**理论研判标准**：

1. **确认为元数据缺失**：
   - NFT 资源结构完全不包含任何元数据字段
   - 元数据访问函数完全不存在，无法查询 name/description/uri
   - 元数据存储方式完全不符合 Move 约定（如使用全局变量代替 object）
   - 无法验证元数据的真实性和完整性

2. **分别为代码异味**：
   - 元数据字段存在但部分可选字段缺失（如缺少 description）
   - 元数据访问函数存在但返回格式不标准
   - 元数据验证存在但不够严格（如未验证 URL 格式）
   - 元数据修改逻辑存在但权限控制不明确

3. **排除误报**：
   - 项目实现了扩展的元数据结构，同时保留了标准兼容的查询接口
   - 使用了标准库的 NFT 实现（如 Aptos std::token）
   - 元数据由外部 metadata service 管理，NFT 只存储指针

## Low risk

**低风险评级场景**：

- 元数据字段完全存在但某些可选字段缺失（如缺少 royalty 信息）
- 元数据访问函数正确但返回格式略微不同
- 元数据验证存在但不够全面（如未检查 emoji 字符）
- 项目已通过充分的测试，与主流 NFT 市场兼容

## 审计专业技巧

### 1. **精准定位的四层扫描法**

**第一层：结构体字段深度检查**
- 使用 grep 搜索所有 `struct` 和 `resource` 定义：`grep -n "resource\|struct" Move.lock`
- 对 NFT 相关结构体，统计必要字段出现频次
- 注意 Move 的可见性修饰符（`public`、`friend`、`private`）与元数据访问权限的关系
- 检查是否通过 `has_key()` 或 `exists()` 进行存在性校验

**第二层：访问函数溯源分析**
- 追踪元数据查询函数（如 `name()`）的完整调用链
- 验证返回值是否直接来自结构体字段或经过转换处理
- 检查是否使用了 Move 的 `borrow_global` 等底层接口，可能存在权限绕过
- 对比不同访问函数的一致性（如 `uri()` 和 `uri_mutable()` 是否逻辑矛盾）

**第三层：修改权限矩阵分析**
- 建立修改操作与权限的对应表：`update_name()` → 需要 `&mut signer` 或 `&mut NFT`
- 检查是否存在权限检查的绕过路径（如通过 event 触发外部修改）
- 分析 capability 机制的实现：是否正确隔离了不同权限级别

**第四层：版本演进兼容性审计**
- 检查元数据升级时是否保持向后兼容（旧 NFT 是否仍可查询）
- 验证迁移脚本中是否遗漏了某些 NFT 的元数据更新

### 2. **真实漏洞与误报的区分经验**

**真实漏洞的典型特征**：

| 特征 | 表现形式 | 验证方法 |
|------|--------|--------|
| **功能缺陷** | NFT 创建时部分参数被忽略或强行设为固定值 | 追踪创建函数的全部参数，确认是否全部被使用 |
| **权限漏洞** | 任何账户可修改他人的元数据，或无 signer 校验 | 构造调用路径，检查是否存在 signer 检查 |
| **数据不一致** | `name()` 返回的值与结构体存储的值不同步 | 对比多个访问函数的返回值，查看是否来自同一数据源 |
| **存储安全** | 元数据存储在不受保护的 Table 中，可被外部覆写 | 检查 Table 的权限，是否隔离在 NFT resource 内部 |
| **验证缺陷** | 允许空字符串或超长字符串作为元数据 | 搜索 `assert!` 和 `string::length()` 的使用 |

**常见误报场景与排除方法**：

| 误报类型 | 原因分析 | 排除方法 |
|--------|--------|--------|
| **扩展字段被误认为缺失** | 项目添加了非标准的元数据字段（如 `rarity_score`） | 确认标准必需字段是否存在，允许超集扩展 |
| **Lazy-loading 被误认为缺失** | 元数据通过外部服务动态加载，NFT 只存储 ID | 搜索发起 HTTP 请求或查表的代码路径 |
| **分层存储被误认为缺失** | 使用多个 Table 或 Object 分别存储元数据 | 跟踪从 NFT ID 查询元数据的完整路径 |
| **权限检查被误认为缺失** | 在 module 外部定义的权限结构，NFT 函数通过 capability 验证 | 检查函数入参中是否接收 capability 结构体 |
| **版本兼容性被误认为缺失** | 支持多个版本的元数据格式，通过版本字段识别 | 检查是否存在 `version` 字段和相应的转换逻辑 |

### 3. **高级鉴别技巧**

**对比分析法**：
- 将该项目的 NFT 结构与 Aptos 官方 `0x1::token::Token` 进行对比
- 检查是否实现了相同的必要字段和接口
- 注意 Move 版本升级带来的 API 变化（如 V1 vs V2 NFT 标准）

**权限追踪法**：
- 从公开函数入手，反向追踪所有可能修改元数据的路径
- 标记每条路径上的权限检查点
- 检查是否存在权限检查缺失的分支

**一致性验证法**：
- 对同一元数据字段的多个访问点进行取样
- 验证返回值是否始终一致
- 检查是否存在竞态条件（如修改时期间的读取返回过期数据）

### 4. **常见陷阱**

**陷阱1：混淆元数据与授权**
- 不要将用户权限信息（如 owner）与展示元数据（如 name）混淆
- 权限检查缺失是独立的安全问题，不是元数据缺失问题

**陷阱2：忽视 Move 的类型系统**
- `String` 和 `vector<u8>` 在 Move 中是不同的类型
- 某些 NFT 市场可能要求特定的元数据类型，应在 Classify 部分细化

**陷阱3：过度关注标准兼容性**
- 如果项目有充分的替代实现和文档说明，非标准的元数据结构可接受
- 关键是确保元数据可被访问和验证

**陷阱4：忽视迁移脚本的元数据更新**
- 升级合约时，旧 NFT 的元数据更新常被遗漏
- 应检查是否存在专门的迁移脚本来更新元数据
