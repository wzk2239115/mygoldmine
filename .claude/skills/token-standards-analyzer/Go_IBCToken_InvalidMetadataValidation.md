# Go IBC Token Invalid Metadata Validation

## Details

**核心问题定位**：IBC (Inter-Blockchain Communication) Token 标准要求跨链代币的元数据必须正确验证和存储。常见缺陷包括：
- 元数据验证逻辑缺失（未验证 denom、decimals、symbol 的合法性）
- 元数据与实际代币信息不匹配（存储的元数据与链上实际不一致）
- 跨链转账中元数据未正确传递（IBC Transfer 中 metadata 缺失或错误）
- 元数据更新机制不符合标准（未能正确处理元数据升级）

**代码示例位置定位**（L1：关键词扫描）：
- 搜索 `ValidateMetadata()` 或 `Validate()` 元数据验证函数
- 检查 `Metadata` 结构的定义：是否包含所有必需字段（Name、Symbol、Decimals、Display）
- 扫描 IBC transfer hook 中的元数据处理代码
- 验证是否存在元数据注册表查询和验证逻辑

**保护机制识别**（L2：跳读）：
- 确认元数据验证是否完整：decimals 范围检查、symbol 格式验证、name 长度限制
- 检查跨链元数据一致性：是否验证了 IBC denom 与本地 denom 的映射关系
- 验证是否存在重复注册保护（防止同一代币多次注册不同元数据）
- 审查元数据存储策略：是否使用了持久化存储并进行了完整性检查
- 检查权限控制：是否只有特定账户可以更新元数据

## Classify

**理论研判标准**：

1. **确认为元数据验证不符合**：
   - 元数据验证函数完全缺失，未进行任何检查
   - 元数据字段完全不符合 IBC 标准（如缺少 decimals）
   - IBC transfer 中完全未处理元数据
   - 元数据存储与实际代币信息严重不一致

2. **分别为代码异味**：
   - 元数据验证存在但某些检查不完整（如缺少 symbol 格式验证）
   - 元数据在某些路径中处理不当但基本逻辑正确
   - 跨链元数据映射关系复杂但能追踪
   - 权限检查不充分但通过其他机制补偿

3. **排除误报**：
   - 项目实现了更严格的元数据验证
   - 使用了第三方库（如 Cosmos SDK 标准库）的验证
   - 元数据由中央注册中心管理，本模块只读取不验证

## Low risk

**低风险评级场景**：

- 元数据验证基本正确但某些字段验证缺失（如缺少 description 检查）
- 跨链元数据处理基本正确但缺少部分优化
- 元数据存储使用简化方案但通过测试证明一致性
- 项目明确说明元数据为只读，由链下系统维护

## 审计专业技巧

### 1. 真实漏洞与误报区分方法

**真实漏洞特征**：
- **无验证边界**：完全无 if/validation 语句，元数据直接从外部输入写入存储
  - 示例：`metadata := ib Metadata{Denom: req.Denom, Decimals: req.Decimals}` 无任何检查
  - 影响：攻击者可注册恶意元数据，导致代币显示错误或重复
- **动态字段未校验**：Decimals 无范围检查（0-18 是标准范围）
  - 真实案例：某链允许 decimals 为负数，导致溢出计算
- **跨链不一致**：本地验证与 IBC 远端不同步
  - 真实漏洞：存储 decimals=18，但 IBC transfer 时使用缺省值 0

**常见误报案例**：
- **假漏洞**：验证存在但写在测试代码中（非生产代码）
  - 审计技巧：grep "// only for test" 后的验证可忽略
- **假漏洞**：元数据由中央注册表通过 gov 提案管理，此模块只读
  - 识别方式：查看权限机制，如果 SetMetadata 权限为 gov 模块，则非本模块漏洞
- **假漏洞**：使用 cosmos-sdk 的 types.Metadata 自带验证
  - 检查方式：追踪 Metadata 结构定义，如有 Validate() 方法则验证已包含

### 2. 深度分析技巧

**溯源关键路径**：
1. 追踪元数据注册入口：找到 RegisterMetadata/SetMetadata 函数
2. 检查权限层：谁可以调用此函数（用户、治理、特定角色）
3. 验证校验链：跟踪每个字段的验证位置
4. 检查持久化：元数据如何存储（KVStore、内存、缓存）
5. 追踪使用点：元数据在何处被读取和使用

**真假判断依据**：
- 若某字段验证缺失但其他地方补偿（如：Decimals 未验证但转账时有防溢出），评级降低
- 若验证是安全检查的补充（深度防御），而非唯一防线，非高风险
- 若元数据为初始化时给定且不可更新，验证不足但风险低

### 3. 代码读取顺序优化

**推荐阅读路线**：
```
Step 1: 定位数据结构 (types.go)
  └─> type Metadata struct 字段列表
      └─> 是否包含 Validate() 方法

Step 2: 查找修改入口 (keeper.go)
  └─> Set/Register/Update Metadata 函数
      └─> 参数来源（用户输入 or 治理提案）

Step 3: 验证逻辑分析 (validate.go or 内联)
  └─> 各字段验证函数调用
  └─> 错误处理方式

Step 4: 权限检查 (auth/permission layer)
  └─> ctx.Sender 或权限验证
  └─> gov 权重检查

Step 5: 使用场景审查 (ibc_handler.go)
  └─> 跨链转账中的元数据同步
  └─> 本地与 IBC 元数据映射
```

### 4. 实战审计检查清单

| 检查项 | 真漏洞表现 | 可接受表现 | 误报迹象 |
|--------|----------|----------|--------|
| Decimals 范围 | 无检查或允许 >18 | if d < 0 \|\| d > 18 | 常量定义为 18 |
| Symbol 格式 | 无验证，允许任意字符串 | regexp.MustCompile 或长度限制 | 注释说明符号格式 |
| Denom 唯一性 | 允许重复注册相同 denom | KVStore 检查存在性后再写 | denom 由系统生成不可重复 |
| 权限检查 | 任何人可调用 SetMetadata | 检查发起者权限或治理权重 | 函数为私有或只在初始化调用 |
| 错误处理 | 验证失败返回 nil 或忽略 | 返回 error 类型且被检查 | panic 在测试代码中 |

### 5. 常见陷阱规避

- **陷阱 1**：看到 validation 包就认为验证完整 → 需要逐一检查各字段是否调用
- **陷阱 2**：跨链代币元数据与本地混淆 → 需区分 ibc/xxx denom 和原生 denom 的不同规则
- **陷阱 3**：注释中有验证说明但代码无实现 → 编译器不会检查注释，仍需代码验证
- **陷阱 4**：测试通过认为逻辑正确 → 需检查测试用例是否覆盖边界情况（decimals=0, symbol="", 超长 denom）
