# C/C++ 动态 SQL 拼接漏洞

## Details

### 漏洞成因
在 C/C++ 代码中，开发者使用 `sprintf`、`snprintf`、`strcat`、`strcpy` 等字符串操作函数动态拼接 SQL 查询语句时，若未对用户输入进行适当的转义或参数化处理，攻击者可通过构造特殊输入注入恶意 SQL 代码，导致数据泄露、篡改或系统权限提升。此外，开发者自定义封装的字符串拼接函数（如包装标准库函数的工具函数、自定义的格式化函数等）若用于构造 SQL 语句，同样存在 SQL 注入风险。

### 代码示例

**易受攻击的代码：**
```c
// 场景：用户登录验证
char query[256];
char username[64];
char password[64];

// 从用户输入获取数据
get_user_input(username, sizeof(username));
get_user_input(password, sizeof(password));

// 不安全的 SQL 拼接
sprintf(query, "SELECT * FROM users WHERE username='%s' AND password='%s'", 
        username, password);

// 执行查询
sqlite3_exec(db, query, callback, 0, &err_msg);
```

**另一个不安全示例（使用 strcat）：**
```c
char query[512] = "SELECT id, name, email FROM users WHERE role='";
strcat(query, user_role);  // user_role 来自用户输入
strcat(query, "'");
mysql_real_query(conn, query, strlen(query));
```

### 快速定位技巧

#### 核心操作定位（审计等级：L1-L2）
**关键词扫描：**
- 字符串拼接函数：`sprintf`、`snprintf`、`strcat`、`strncat`、`strcpy`、`strncpy`
- 字符串流操作：`std::stringstream`、`std::ostringstream`（C++）
- 字符串拼接运算符：`+`、`+=`（C++ std::string）
- 格式化函数：`asprintf`、`vasprintf`

**定位步骤：**
1. 使用全局搜索查找上述函数
2. 过滤出结果字符串中包含 SQL 关键词的调用点：`SELECT`、`INSERT`、`UPDATE`、`DELETE`、`WHERE`、`FROM`
3. 跳读（L2）这些代码段，确认是否在构造 SQL 查询

#### 保护机制定位（审计等级：L2-L3）
**检查是否存在：**
- **预编译语句（Prepared Statements）：**
  - SQLite: `sqlite3_prepare_v2`、`sqlite3_bind_*`
  - MySQL: `mysql_stmt_prepare`、`mysql_stmt_bind_param`
  - PostgreSQL: `PQprepare`、`PQexecParams`
  
- **转义函数调用：**
  - MySQL: `mysql_real_escape_string`
  - PostgreSQL: `PQescapeStringConn`
  - SQLite: `sqlite3_mprintf` 使用 `%q` 占位符
  
- **输入验证：**
  - 白名单验证（如检查输入是否仅包含字母数字）
  - 长度限制
  - 类型检查（如确保输入为整数）

**定位技巧：**
- 在发现不安全拼接点后，向上追踪（L3逐行读）变量来源
- 检查变量赋值前是否经过上述保护函数处理
- 若变量来自外部输入（HTTP 参数、文件读取、网络数据包）且无保护，则为高风险

#### 审计等级标注

| 场景 | 审计等级 | 说明 |
|------|----------|------|
| 完全使用预编译语句 | **L0（快速跳过）** | 代码全部通过参数化查询，无字符串拼接 |
| 拼接但使用了转义函数 | **L2（跳读）** | 快速确认转义函数使用是否正确 |
| 拼接来自外部输入 | **L3（逐行读）** | 需仔细分析数据流，确认是否有漏洞 |
| 拼接且涉及多模块传递 | **L4（跨模块追踪）** | 需追踪变量在多个函数/文件间的传递和处理 |

## Classify

### 研判标准

#### 确认漏洞
满足以下所有条件时，判定为 SQL 注入漏洞：
1. **存在动态 SQL 拼接：** 使用 `sprintf`、`strcat` 等函数构造查询
2. **输入可控：** 拼接的数据直接或间接来源于用户输入（HTTP 请求、命令行参数、文件内容、网络数据包等）
3. **缺乏保护：** 未使用参数化查询、未调用转义函数、无有效输入验证

#### 误报
以下情况可判定为误报：
1. **拼接内容为常量或内部配置：** 变量值为硬编码常量或从配置文件中读取的固定值，非用户可控
2. **已使用有效转义函数：** 在拼接前使用了数据库库函数提供的转义函数（如 `mysql_real_escape_string`、`PQescapeStringConn`）
3. **输入经过严格白名单验证：** 通过严格的白名单检查，确保输入只能是预定义的安全值（如列名、表名的枚举验证）

#### 代码异味
即使暂时不构成漏洞，以下情况也应标记为代码异味（需重构）：
1. **部分转义或验证不完整：** 只对某些字段进行了保护，其他字段仍存在风险
2. **自定义转义函数：** 使用自行编写的转义逻辑而非标准库函数，可能存在绕过风险
3. **混用拼接和参数化：** 同一查询中部分使用参数化、部分使用拼接
4. **依赖客户端过滤：** 假定前端已做输入验证，后端未再次检查

## Low risk

### 低风险评级场景

#### 1. 输入源自受控环境
- **场景：** SQL 拼接的数据来自配置文件、环境变量或管理员后台
- **风险评估：** 虽然攻击面较小，但若配置文件可被篡改或管理员账号被窃取，仍可能被利用

#### 2. 仅拼接数值型参数且进行了类型转换
- **场景：** 使用 `atoi`、`strtol` 等函数将字符串转为整数后再拼接
- **风险评估：** 大幅降低了注入风险，但仍不如参数化查询安全

#### 3. 影响范围受限的查询
- **场景：** 注入点存在，但查询的表仅包含非敏感数据，且数据库用户权限受限（只读、无系统表访问）
- **风险评估：** 潜在危害较小，但仍可能导致数据泄露或 DoS

#### 4. 存在额外的防护层
- **场景：** 虽然代码层面存在拼接，但部署时存在 WAF、IDS 或数据库防火墙等外部防护
- **风险评估：** 外部防护可能被绕过，不应作为长期依赖
- **注意：** 应尽快修复代码层面的问题

### 风险降级条件总结
| 条件 | 降级理由 | 建议优先级 |
|------|----------|------------|
| 输入仅来自管理员/配置 | 攻击面小 | 中 |
| 数值型参数+类型转换 | 注入难度高 | 中 |
| 只读权限+非敏感数据 | 影响范围小 | 低 |
| 存在 WAF 等外部防护 | 有缓解措施 | 高（仍需修复）|
