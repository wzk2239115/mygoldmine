**Vyper**  
常出现在资金回收、合约退役或治理触发的销毁场景中，包括但不限于使用 `selfdestruct` 指令在满足特定条件（如治理投票通过）后移除合约，或在多签金库清空后自毁等方式：  
- 治理触发的销毁：通过治理提案触发 selfdestruct 销毁合约，但未验证投票合法性或资金转移安全性，详见：Vyper_GovernanceTriggeredDestruction.md  
在区块链领域，专注于这一垂直漏洞类型研判任务，从漏洞成因触发，编写该md文件，包含一下三个小标题，【注意语言精炼，表达简洁，可以作为审计小抄，仅专注于审计，不包含攻击与修复】：

## Details

**代码示例**：
```vyper
governance_vote: public(HashMap[bytes32, uint256])
owner: public(address)

@external
def destroy_contract(_proposal_id: bytes32):
    # 缺少投票权重验证
    assert self.governance_vote[_proposal_id] > 0
    selfdestruct(self.owner)
```

**快速定位核心操作** (L3:逐行读)：
- 搜索 `selfdestruct()` 调用点
- 追踪调用路径上的权限检查（`@external`/`@internal` 修饰器）
- 检查是否存在 `assert`/`if` 条件判断投票结果
- 确认资金接收地址来源（`self.owner`/`msg.sender`/硬编码地址）

**快速定位保护机制** (L4:跨模块追踪)：
- 验证投票权重计算逻辑：追踪 `governance_vote` 映射的更新路径
- 检查时间锁机制：搜索 `timestamp`/`block.number` 相关的延迟执行逻辑
- 确认多签要求：查找 `threshold`/`signers`/`approvals` 等变量
- 追踪提案生命周期：验证 `proposal_status`/`executed` 状态管理
- 资金转移审计：检查 `selfdestruct` 前是否有 `send()`/`raw_call()` 清空余额

**专业审计技巧** (实战指南)：

1. **投票合法性三层验证法**：
   - 第一层：检查投票权（voting_power/balance snapshot是否有恢复块高指定）
   - 第二层：检查投票计数（total_votes与quorum阈值是否正确比较）
   - 第三层：检查提案状态机（Pending→Active→Succeeded→Executed，是否有完整状态转移）

2. **地址来源的关键路径追踪**：
   - 若 `selfdestruct()` 传入 `msg.sender`：必须有权限修饰符（通常只有 owner/multisig 可调用）
   - 若 `selfdestruct()` 传入 `self.owner`：需确认 owner 的初始化与更新权限
   - 若 `selfdestruct()` 传入硬编码地址：需验证地址可变性（如在 init 时传入）

3. **易被忽视的重放风险**：
   - 查看是否使用 nonce 机制（`executed_proposals[_id] = True`）防止重复执行
   - 检查块号/时间戳约束是否会导致过期提案被不当执行
   - 对于多签场景：验证签名是否被正确验证且不可复用

4. **资金清算审计要点**：
   - 即使 `selfdestruct()` 可以原子性转移剩余余额，也应检查是否有 ETH/代币清算逻辑
   - 若合约持有 ERC20，确认是否在销毁前调用了 `transfer()` 或 `approve()`
   - 监测是否存在多余资金被永久锁定的风险

## Classify

**漏洞**：
- 缺少投票合法性验证（无投票权重/时间锁/多签门槛检查）
- `selfdestruct` 接收地址可被操纵（如直接使用 `msg.sender`）
- 投票状态可重放（未标记提案为已执行）
- 权限检查缺失或可绕过（如仅检查 `owner` 而非投票结果）

**误报识别清单** (真实场景与虚假告警的区分)：

1. **跨合约治理系统的误报**：
   - 现象：销毁函数缺少内联投票检查，仅信任外部调用者权限
   - 真因：通常是治理合约单独部署，权限检查在调用链前置
   - 识别方法：追踪 `msg.sender` 权限来源，确认是否为已验证的治理合约地址
   - 验证：查看销毁函数是否被 `@external` 修饰但仅允许特定地址调用

2. **测试/演示函数的误报**：
   - 现象：存在 `test_destroy()`/`demo_selfdestruct()` 函数
   - 真因：仅供开发环境使用，生产合约中实际销毁函数被正确保护
   - 识别方法：检查函数名是否含 `test`/`demo`/`debug` 前缀
   - 验证：确认函数是否在主逻辑分支中可达

3. **时间锁的完整性验证**：
   - 现象：销毁函数检查看起来不够严格
   - 真因：时间锁延迟可能在发出提案时实现，而非销毁函数内
   - 识别方法：查看 `propose()` 函数是否存在 `pending_time` 或 `proposal_created_block` 记录
   - 验证：确认执行与提案发起时间的强制间隔

4. **多签恢复地址的合理性**：
   - 现象：`selfdestruct()` 发送至特定地址而非 `msg.sender`
   - 真因：为防止多签被破坏时资金丢失，可能是安全多签钱包地址
   - 识别方法：验证该地址在链上的交互历史，是否为知名多签合约（Gnosis Safe 等）
   - 验证：检查地址是否被多个合约信任或频繁操作

**代码异味** (需进一步调查的场景)：
- 资金接收地址硬编码但经过充分治理讨论（检查 DAO 提案/论坛记录）
- 销毁逻辑与紧急暂停混合（可用但设计不清晰，需检查暂停状态与销毁的交互）
- 存在多个销毁相关函数（`destroy()`/`selfdestruct_now()`）但权限不一致
- 销毁条件涉及外部预言机或 L2 状态（增加了认知复杂度，需验证跨链数据完整性）

## Low risk

- 合约已空置且无任何余额或重要状态
- 销毁仅用于回收部署费用，且受严格多签控制
- 存在链下治理流程（如快照投票）配合链上执行器，且执行器权限明确
- 合约为短期临时合约（如活动奖励），生命周期明确且已公告
- 销毁函数权限等同于暂停权限，已在多个关键操作中验证其准确性
- 投票权重通过已审计的 ERC20 balance snapshot 获取，时间点不可篡改
- 时间锁延迟超过 7 天且在链上记录可验证，过期提案自动作废
- 销毁地址为标准 Gnosis Safe 多签或知名机构冷钱包，链上可验证

**审计确认模板**：
- ✓ 投票权重验证完整（三层检查都通过）
- ✓ 地址来源可追踪且无被篡改风险
- ✓ 重放保护机制完整（nonce/状态标记/时间约束）
- ✓ 资金清算符合预期（余额清空或确认为 0）
- ✓ 跨合约权限链条清晰（可从销毁函数反推到初始权限来源）
