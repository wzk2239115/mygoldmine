**Move - 策略资源销毁漏洞 (Policy Resource Burn)**  

策略或权限资源被 `burn` 销毁时，若未充分验证销毁条件、权限控制或影响范围，可能导致关键系统功能失效、状态不一致或权限混乱。

---

## Details

**典型代码模式：**
```move
public fun revoke_policy<T: store>(account: &signer) {
    let addr = signer::address_of(account);
    let Policy { id } = move_from<Policy<T>>(addr);  // 直接移除并解构
    // 缺失：权限检查、依赖验证、状态清理
}
```

**核心操作定位（L2-跳读）：**  
- 搜索 `move_from<Policy>`、`move_from<Capability>`、资源解构模式 `let Resource { ... } = move_from`
- 关注配合 `destroy`/隐式销毁的资源操作
- 检查资源类型：`store` 能力的策略/凭证/配置类资源

**保护机制定位（L3-逐行读）：**  
- 销毁前权限验证：`assert!(is_admin(account), E_NOT_AUTHORIZED)`
- 依赖检查：是否验证该资源被其他模块/资源引用（如 `assert!(dependency_count == 0)`）
- 状态清理：销毁后是否同步更新全局状态表、事件或关联资源
- 不可逆操作保护：是否有时间锁、多签确认或紧急暂停机制

---

## Classify

**确认为漏洞：**  
- 权限缺失：任意用户可销毁他人或全局策略资源
- 影响未控：销毁导致依赖该策略的合约/功能永久失效，且无恢复机制
- 状态不一致：销毁后全局索引未更新，产生悬挂引用或逻辑错误

**判定为误报：**  
- 资源仅用于用户自身账户，销毁仅影响操作者本人（如个人凭证）
- 设计明确允许销毁，且有完善的降级/迁移方案
- 销毁操作受严格权限控制（多签/治理）且有充分文档说明

**代码异味：**  
- 销毁操作合法但缺少事件日志，影响可审计性
- 权限检查存在但过于宽松（如仅检查签名者非零地址）
- 缺少销毁前的影响范围提示或警告机制

---

## Low risk

**满足以下条件可降级为低风险：**
- 销毁仅影响测试/临时环境的非关键资源
- 策略资源可通过治理流程重新创建，且停机时间可接受
- 存在备用策略或降级机制，系统不会完全停摆
- 销毁操作已集成在清晰的生命周期管理中（如明确的废弃流程）
- 受限于极高权限（如多签治理账户）且有充分监控告警

## 审计专业技巧

### 1. 真实漏洞特征识别

**关键信号（高置信度判定为真实漏洞）：**

- **权限检查失效链**：虽然有 `assert!` 权限检查，但检查逻辑本身存在绕过
  - 例：检查 `signer` 非零，但没有验证其是否为授权账户
  - 例：权限检查在 `move_from` 之前，但资源结构允许通过其他函数路径销毁

- **全局状态孤立**：销毁操作只删除资源，但关联的计数器、索引表未同步清理
  - 扫描 `table::remove()`、`vector::remove()` 的位置，对比 `move_from<>` 位置
  - 若销毁与清理操作不在同一事务原子块内，可能导致资源泄露审计失败

- **恢复路径完全阻断**：销毁后无任何重新初始化路径，且无多签/治理流程
  - 搜索是否存在 `init_policy()` 或类似初始化函数的访问控制
  - 若初始化也受同样严格权限限制，验证这些权限是否真实可执行

### 2. 常见误报模式及排除方法

**模式A：用户私人资源销毁**
- 代码：`let addr = signer::address_of(account); move_from<PersonalKey>(addr)`
- 审计陷阱：看起来像无权限检查，实际上资源存储在用户自己账户下
- 排除方法：确认 `PersonalKey` 是否被其他模块或全局状态引用；查证 `move_from(addr)` 中的 `addr` 是否必然等于 `tx::sender()`

**模式B：已废弃但仍保留的销毁函数**
- 代码注释明确标记为 `#[deprecated]`，但审计者误认为是隐藏的销毁后门
- 排除方法：检查函数是否在 `package.yaml` 中声明为 `deprecated`；验证合约版本升级历史中该函数何时被标记

**模式C：条件性销毁（非无条件）**
- 代码：`if (condition) { move_from<Resource>(...) } else { ... }`
- 审计陷阱：若 `condition` 检查表面上看复杂，审计者可能误判
- 正确做法：逐层反向追溯 `condition` 的所有赋值来源，验证是否真实可被攻击者控制

### 3. 深层审计技巧

**技巧1：跨模块依赖溯源**
```
步骤1：找到目标销毁函数 (e.g., revoke_policy)
步骤2：在整个 sources/ 目录中搜索该资源类型的使用 (e.g., grep -r "Policy<T>" .)
步骤3：统计有多少模块 store 或 borrow 了该资源
步骤4：验证销毁时是否有全局注册表清理这些依赖计数
步骤5：若存在悬挂引用，标记为真实漏洞；若无引用，降级为低风险
```

**技巧2：权限源头验证（Authority Chain Tracing）**
```
当遇到权限检查时 (e.g., assert!(is_admin(account), E_NOT_ADMIN)):
1. 找到 is_admin() 函数定义
2. 回溯其内部调用链：is_admin() -> get_admin_list() -> ???
3. 确认管理员列表的最终来源是否真实受控
4. 常见误区：管理员列表存储在一个可写的全局资源中，看似有权限实则无
```

**技巧3：原子性缝隙检测**
```
检查销毁操作的多步流程是否存在中间状态暴露：
- 步骤A：权限检查通过
- [审计点] 是否存在中断机制？
- 步骤B：资源标记为待销毁
- [审计点] 其他交易是否能在此时介入？
- 步骤C：资源实际删除

若步骤间可被插入恶意事务，标记为真实漏洞（TOCTOU）
```

### 4. 实战案例区分

**案例1：真实漏洞**
```move
// 漏洞代码
public fun burn_token<T>(account: &signer, amount: u64) {
    let addr = signer::address_of(account);
    let balance = borrow_global_mut<Balance<T>>(addr);
    balance.amount = balance.amount - amount;  // 只修改余额
    // 遗漏：没有销毁对应的资源对象，只是改数字
    // 后果：可重复销毁同一资源
}
// 风险：缺少对应 Token 资源的销毁逻辑
// 判定：高风险 - 导致通胀
```

**案例2：误报示例**
```move
// 初看起来危险但实际安全
struct UserKey has key { id: ID }
public fun revoke_user_key(account: &signer) {
    let addr = signer::address_of(account);  // 只能撤销自己的
    let UserKey { id } = move_from<UserKey>(addr);
    // 用户可以撤销自己的密钥，这是正常能力
}
// 排除：确认只有持有者能销毁自己的资源
// 判定：低风险 - 用户自主管理
```

**案例3：边界情况**
```move
// 管理员销毁任意策略 - 需细致判断
public fun admin_revoke_policy<T>(admin: &signer, target_addr: address) {
    assert!(is_admin(admin), E_NOT_ADMIN);  // 权限检查
    let Policy { ... } = move_from<Policy<T>>(target_addr);
    // 问题：是否存在替代政策或恢复机制？
}
// 细致判定：
// - 若目标地址无法重新创建 Policy，且无他人维护，属高风险
// - 若存在治理流程重新初始化，属中风险
// - 若有备用策略池，属低风险
```

### 5. 审计检查清单

- [ ] 销毁函数的所有入口点是否都有权限验证？
- [ ] 权限验证本身是否可绕过（递归检查 `is_admin()` 源头）？
- [ ] 被销毁的资源是否被其他全局结构或模块持有引用？
- [ ] 销毁后的全局状态一致性是否保证？（计数器、索引表、事件）
- [ ] 是否存在原子性缝隙（TOCTOU风险）？
- [ ] 销毁操作是否可逆？若不可逆，权限等级是否足够高？
- [ ] 相关文档是否明确说明销毁的预期行为和权限模型？
- [ ] 是否有审计日志或事件记录所有销毁操作？
