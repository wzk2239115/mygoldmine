# Go 逻辑账户删除漏洞（Logical Account Deletion）

## Details

**典型代码模式：**
```go
// 模块中的账户删除函数
func (k Keeper) DeleteAccount(ctx sdk.Context, addr sdk.AccAddress) error {
    store := ctx.KVStore(k.storeKey)
    store.Delete(types.AccountKey(addr))  // 直接删除账户数据
    return nil
}
```

**核心操作定位技巧（审计等级：L2-跳读）：**
- 关键函数：`Delete()`、`Remove()`、`Clear()`、`Purge()`、`Deactivate()`
- 关注状态存储操作：`store.Delete()`、`keeper.RemoveAccount()`
- 查找账户生命周期终止点：模块注销、账户关闭、vault清理逻辑
- 检索资金转移前置条件：删除前是否调用 `SendCoinsFromAccountToModule()` 或余额检查

**保护机制定位技巧（审计等级：L4-跨模块追踪）：**
- 余额清零校验：`GetBalance() == 0`、`require(balance.IsZero())`
- 依赖关系检查：遍历相关模块状态，确认无外部引用（委托、质押、授权等）
- 资金强制转移：删除前调用 `BurnCoins()`、`SendCoinsToFeeCollector()` 或退款逻辑
- 二次确认机制：删除操作需管理员签名或时间锁延迟
- 事件审计：`EmitEvent()` 记录删除操作及残留状态
- 跨模块依赖追踪：检查 staking、distribution、gov 等模块是否持有该账户引用

## Classify

**确认为漏洞的条件：**
1. 账户删除前未强制清空余额，导致资金被锁定在已删除账户中
2. 删除操作未解除跨模块依赖（如质押记录、授权关系、待领取奖励），造成模块状态不一致
3. 删除逻辑缺乏原子性保障，部分状态清理失败导致孤儿数据

**判定为误报的情形：**
1. 系统明确禁止删除持有余额或依赖关系的账户（通过前置校验拒绝）
2. 账户删除仅为逻辑标记（软删除），实际数据保留且可恢复
3. 删除操作仅作用于临时缓存或视图层，不影响链上状态

**代码异味标识：**
1. 删除逻辑分散在多处，缺乏统一入口和完整性保证
2. 依赖人工触发清理流程，无自动化状态一致性检查
3. 删除前仅检查账户自身状态，忽略关联模块的依赖扫描

## Low risk

**风险可接受的场景：**
1. **隔离沙箱账户**：测试环境或临时账户，删除不影响主网经济模型
2. **强制空账户策略**：链层协议硬编码规则，任何账户创建必须零余额初始化，删除前自动退款至指定地址
3. **只读历史账户**：已归档的历史账户删除仅为存储优化，通过快照或归档节点保留完整历史
4. **权限受限删除**：仅治理提案通过多签审批后可删除，且删除前需完成公示期和状态审计报告
5. **可逆删除机制**：实现软删除或版本控制，允许在宽限期内恢复账户及关联状态
6. **无经济价值账户**：系统内部辅助账户（如手续费池占位符），删除不涉及用户资产

## 审计专业技巧

### 真实漏洞的特征信号

**1. 资金锁定陷阱识别**
- 删除账户时保留余额（未调用 `SendCoins()` 或 `BurnCoins()`）
- 表现：查询已删除账户时返回 `nil` 或 `not found`，但余额数据仍在底层 KVStore
- 审计验证：在删除操作前后分别读取账户状态和 balance store，确认余额一致性转移
- 实战案例：Cosmos SDK 早期版本中，BankKeeper 删除账户仅删除 account store，未同步清理 balance 和 spendable balance 两层数据结构

**2. 跨模块依赖悬空检测**
- 删除后其他模块仍可引用该账户（如 staking keeper 的 validator 对象、distribution 的委托者记录）
- 审计验证：遍历所有引用该账户的模块关键数据结构，构建依赖图谱
- 实战案例：删除委托人账户时，未清理 distribution 模块中的 delegator withdraw address，导致奖励分配时访问已删除账户引起 panic

**3. 原子性破裂症状**
- 多步骤删除流程在中间失败，部分状态被清理，部分保留
- 审计验证：检查是否使用 `defer` 或事务性操作确保全部成功或全部失败
- 实战案例：删除操作分为三步（1.清理余额 2.删除账户 3.更新索引），若第2步失败，余额已被清理但账户仍存在，恢复时数据不一致

### 误报高频场景

**1. 软删除正当性确认**
- 症状：代码调用 `Delete()` 但账户数据通过存档表保留
- 判别方法：查证是否存在 `DeletedAccounts`、`ArchivedAccounts` 等并行存储结构；检查事件日志中是否记录完整状态快照
- 消除误报：若有定时任务将账户迁移到存档库后再删除主表，则为合法的分阶段清理

**2. 隔离账户误判**
- 症状：发现 `DeleteAccount()` 在测试模块或隔离环境中调用
- 判别方法：验证该账户是否被网络级别的协议规则排除（如不参与代币供应计算、不在状态根中）
- 消除误报：检查参数化配置，确认删除仅作用于 `testnet` 或 `staging` 标志下的账户

**3. 临时缓存删除误认**
- 症状：在内存 LRU cache 或会话状态中调用 Delete()
- 判别方法：追踪该删除操作作用的 store 对象，若为 `transient.Store` 或 `memdb.Store`，则不影响链上持久化状态
- 消除误报：查阅 store key 的注册表，确认 `NewTransientStoreKeys()` 与 `NewKVStoreKeys()` 的区别

**4. 权限受限的安全删除**
- 症状：删除前存在 `require(msg.Sender == admin)` 或治理检查
- 判别方法：追踪删除操作的完整调用链，确保所有入口都受权限保护
- 消除误报：若所有可能触发删除的 handler 都需要治理提案或多签，且有审计日志，则风险可控

### 审计检查清单（Pro 级）

**第一阶段：静态扫描（2-3小时）**
- [ ] 全局搜索 `Delete()` 调用，记录行号和上下文
- [ ] 检查删除前的前置条件（余额清空、依赖检查）
- [ ] 统计删除操作涉及的 store key 数量（应 >= 2）
- [ ] 验证是否存在 `EmitEvent()` 记录删除操作

**第二阶段：跨模块追踪（4-6小时）**
- [ ] 绘制账户引用的模块依赖图（至少涵盖 bank、staking、distribution、auth）
- [ ] 在各模块中搜索该账户 address 的所有使用位置
- [ ] 检查是否存在缓存层或二级索引，确认删除时同步更新
- [ ] 审查管理员函数和治理提案，确认是否存在非预期的删除入口

**第三阶段：风险量化（2-3小时）**
- [ ] 估算被锁定资金的上界（分析哪些账户可能被删除）
- [ ] 评估模块状态不一致的可恢复性（是否有日志可重放）
- [ ] 计算触发漏洞需要的最少操作步骤数（1 步最危险，>3 步可接受）
- [ ] 确定是否有时间窗口进行修复（如删除延迟机制）

**第四阶段：POC 验证（1-2小时，可选）**
- [ ] 编写单元测试，删除账户后查询余额
- [ ] 模拟跨模块操作，尝试在依赖账户被删除后访问
- [ ] 使用链上模拟器执行多笔交易，观察状态一致性

### 真实案例对比

| 特征 | 真实漏洞案例（Cosmos SDK v0.39） | 误报案例（正确的软删除） |
|------|--------------------------------|----------------------|
| 删除操作 | `bank.RemoveAccount(addr)` 仅删除 account store | `account.SetDeleted(true)`，数据保留 |
| 余额清理 | 未调用，资金悬空 | 删除前调用 `SendCoins()` 转走全部 |
| 恢复能力 | 无，链状态污染 | 可通过事件日志重放恢复 |
| 权限控制 | 任意模块可调用 | 需治理提案或多签授权 |
| 检测手段 | 查询 bank balance store，发现数据孤儿 | 查询应用存档表，数据完整 |
