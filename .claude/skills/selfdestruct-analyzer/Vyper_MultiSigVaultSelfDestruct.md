# Vyper多签金库自毁漏洞

## Details

**代码示例**：
```vyper
@external
def withdraw_and_destroy():
    assert msg.sender in self.signers
    # 转移所有ETH给指定地址
    send(self.beneficiary, self.balance)
    # 立即自毁
    selfdestruct(self.beneficiary)
```

**快速定位核心操作技巧**（L2:跳读）：
- 搜索 `selfdestruct()` 调用点，确认触发条件是否检查余额为零
- 检查 `self.balance` 是否在自毁前完全归零（不仅是ETH，还包括已接收的其他代币）
- 关注 `send()` / `raw_call()` 与 `selfdestruct()` 之间是否有充分的状态验证
- 查看是否存在待处理的提款请求、时间锁或批准队列未清空

**快速定位保护机制技巧**（L3:逐行读）：
- 确认是否有 `assert self.balance == 0` 或 `assert self.pending_withdrawals == 0` 的前置检查
- 检查多签阈值要求（如 `assert approval_count >= self.required_signatures`）
- 验证是否有紧急暂停或时间延迟机制（如 `assert block.timestamp > self.destroy_unlock_time`）
- 查看合约是否记录所有依赖方地址并要求确认迁移完成
- 检查ERC20/ERC721代币余额归零验证（`assert ERC20(token).balanceOf(self) == 0`）

## Classify

**漏洞**：自毁前未验证所有资产（包括ETH、ERC20、NFT）完全清空；未检查待处理交易队列或时间锁提案；依赖方合约仍持有该金库地址且未更新；自毁后资金发送到错误或不可控地址。

**误报**：金库设计为一次性使用场景，且合约创建时明确标注生命周期；所有资产转移由链下系统全量验证后触发；存在独立的资产追踪合约记录所有转账历史。

**代码异味**：自毁逻辑与资金清空逻辑紧密耦合无法单独审计；缺少事件日志记录自毁原因和剩余资产快照；多签门槛过低（如2/3）导致少数签名者可强制自毁。

## Low risk

时间锁已强制延迟90天以上且广播链下依赖方；合约仅管理测试网资产或已废弃功能模块；自毁需治理投票+多签双重确认且投票期超30天；存在资产白名单且每种资产都有独立归零检查；链下监控系统实时追踪金库地址引用并在自毁前确认无外部依赖。

## 审计专业技巧

### 真实漏洞识别模式

1. **资产完整性验证缺失**
   - 典型案例：合约仅检查 `send()` 是否成功，但未验证接收者真的获得了全部资金
   - 正确做法：使用 `extcall` 进行转账后，立即检查 `self.balance == 0`；对ERC20代币调用 `balanceOf()` 确认转出
   - 审计重点：`selfdestruct()` 前必须有至少3层验证（余额检查、事件日志、外部调用返回值确认）

2. **多签绕过风险**
   - 真实漏洞：存在单签调用路径（如emergency_withdraw）与多签自毁路径混存，导致单签可提光资金后自毁
   - 识别方法：搜索所有能转移资金的函数，检查是否都要求 `approval_count >= self.required_signatures`
   - Vyper特有问题：`raw_call()` 的返回值易被忽略，攻击者可构造失败的调用绕过验证逻辑

3. **状态转换漏洞**
   - 真实案例：合约未设置 `is_destroyed` 标志，在自毁执行到 `selfdestruct()` 之前，其他并发交易仍可操作状态变量
   - 防护方案：在 `selfdestruct()` 前设置 `self.destroyed = True` 并将所有函数入口检查 `assert not self.destroyed`
   - 验证方法：逐行追踪 `selfdestruct()` 前的每个 `@external` 函数是否都设置了守卫条件

4. **接收者地址信任问题**
   - 常见误报原因：审计员发现 `selfdestruct(self.beneficiary)` 后立即警告，但实际上 `beneficiary` 由多签设置且不可变
   - 正确审计：检查 `beneficiary` 是否为常量（`immutable` 关键字）或由受信任的治理过程设置
   - 真实漏洞：`beneficiary` 为可更改变量，近期被修改过（检查历史交易），或设置为钓鱼地址

### 误报排除清单

1. **设计合理性判断**
   - 确认金库生命周期：检查部署日期、初始化参数、文档说明
   - 验证自毁是否为正常功能（如包装器合约升级时销毁旧版本）vs 异常操作
   - 查看是否存在替代方案（如 pausable 合约暂停、权限转移）且自毁明显优于替代方案

2. **资产追踪验证**
   - 误报陷阱：看到 `selfdestruct()` 就认为资金丢失
   - 正确做法：检查链下系统是否已记录所有资产转移，链上验证历史事件日志 `WithdrawalCompleted / AssetMigrated`
   - 查看是否存在独立的 `AssetRegistry` 合约追踪所有转账，或多签成员是否已确认收款

3. **时间锁有效性**
   - 误报：看到时间锁就认为安全
   - 审计要点：验证时间锁不可被跳过（不存在 `skip_timelock()` 后门），且延迟天数是否足以让社区响应（<30天为红旗）
   - 检查历史：查询链上时间锁执行日志，是否曾被人为加速或延迟过

4. **多签阈值评估**
   - 常见误报：3/5 多签看似安全
   - 真实风险：检查5个签名者的身份（是否为核心开发者、是否曾有纠纷）、私钥管理（是否使用硬件钱包）、地理分布（单个国家风险）
   - 正确评估：即使阈值高，如果签名者可被单点攻击（如社工、同一交易所账户），仍为高风险

### 常见审计误区

| 误区 | 错误做法 | 正确做法 |
|------|--------|--------|
| 过度关注自毁本身 | 看到 `selfdestruct()` 就标记为漏洞 | 重点审计自毁前的资产清空逻辑是否完整 |
| 忽视状态变量 | 仅检查转账函数 | 追踪所有可修改 `beneficiary` / `destroy_unlocked` 等关键变量的路径 |
| 轻信事件日志 | 假设事件日志代表实际执行结果 | 验证事件日志对应的链上状态变化（如余额确实为零） |
| 缺少上下文 | 离线评估代码片段 | 查看Git历史、部署交易、链上交互历史，理解合约的实际使用场景 |
| 过度依赖工具 | 用自动化扫描器报告就下结论 | 手工逐行验证扫描器标记的每个位置，确认上下文真的存在风险 |

### 审计检查清单（完整流程）

- [ ] **源代码审计**：`grep -n "selfdestruct\|raw_call\|send" Vyper_MultiSigVaultSelfDestruct.vy`，确认共几处转账点
- [ ] **权限分析**：列出所有能修改 `beneficiary` / `signers` 的函数及其访问控制
- [ ] **状态转换图**：绘制初始化 → 运营 → 销毁阶段的状态变量变化
- [ ] **链上验证**：查询合约历史交易，检查是否有异常的多签提案或自毁调用
- [ ] **依赖方追踪**：搜索所有调用本合约的其他合约或EOA账户，确认它们是否已做迁移准备
- [ ] **灾备验证**：确认是否存在升级合约或备用金库，防止自毁导致资金无处可去
- [ ] **文档交叉验证**：对比代码逻辑与官方文档 / README，确认是否一致（文档落后是高风险信号）
