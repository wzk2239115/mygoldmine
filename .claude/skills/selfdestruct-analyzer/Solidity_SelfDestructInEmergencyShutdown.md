# Solidity - 紧急关停中的自毁

**漏洞类型**：紧急情况下调用 `selfdestruct` 销毁合约，但未考虑依赖方影响或资金转移目标可控性

## Details

**代码示例特征**：
```solidity
function emergencyShutdown() external onlyOwner {
    selfdestruct(payable(owner));
}
```

**快速定位核心操作**（L2-跳读）：
- 搜索 `selfdestruct` 关键字，定位销毁入口
- 检查调用路径：紧急函数（`emergency*/pause/shutdown`）→ `selfdestruct`
- 关注触发条件：单签/多签/时间锁/状态检查

**快速定位保护机制**（L3-逐行读）：
- 资金去向：接收地址是否硬编码、可控或由管理员指定
- 依赖检查：是否验证无外部合约依赖/余额归零/子合约已清理
- 状态同步：是否通知上层合约/注册表/工厂合约
- 时间缓冲：是否存在延迟执行或可撤销机制

## Classify

**漏洞等级研判**：
- **严重**：销毁后资金发送至不受控地址（如 `msg.sender`）、依赖方合约未感知导致逻辑失效、存在残留资金但未转移
- **中危**：单一权限即可触发、无时间锁保护、依赖方合约需手动更新但无事件通知
- **低危**：有完善的预警/多签机制、资金已清空、无外部依赖、已发出停用公告
- **误报**：测试合约、已废弃且明确标注的合约、完全独立的临时任务合约
- **代码异味**：有保护机制但文档/事件不完善、缺少明确的生命周期管理

## Low risk

**以下情况可评为低风险**：
1. 存在多签+时间锁双重保护，且时间窗口充足（≥48h）
2. 合约资金已通过独立函数提前转移完毕，`selfdestruct` 前强制校验余额为零
3. 工厂/注册表合约已实现自动下线机制，销毁时触发事件并同步状态
4. 仅用于临时性任务（众筹/投票/空投）且文档明确生命周期，无外部依赖
5. 存在优雅降级方案，依赖方可无缝切换至新合约地址
6. 已通过链下/链上公告提前警示用户，且观察期内无异常交互

## Audit Pro Tips（审计专业技巧）

### 1. 真实漏洞识别维度

**关键差异点**：
- **真漏洞**：允许`msg.sender`或非预期地址接收销毁前资金、销毁后依赖合约调用失效导致资金冻结、存在前向运行窗口允许攻击者抢先转移资金
- **误报**：仅在完全控制的测试网络中、合约注释明确标注`// To be removed after audit`、销毁函数受完整的访问控制+日志+测试用例覆盖

**实战判断标准**：
```
真漏洞权重分：
- 资金可控性 (40%): msg.sender接收 → 高危
- 依赖方通知 (30%): 无事件/无时间锁 → 中危
- 状态同步 (20%): 存量合约无法切换 → 中危
- 触发权限 (10%): 单签 → 加权
```

### 2. 高频误报场景及快速甄别法

**场景A**：代理合约销毁实现合约
检查方法：
- `selfdestruct` 是否在 proxy fallback 中调用？
- 是否有 `delegatecall` 路由？
- 若是，则为设计预期，非漏洞

**场景B**：紧急暂停合约（Pausable）的过度防御
典型代码：
```solidity
function emergencyPause() external onlyOwner {
    _pause();
    // selfdestruct(owner); // 已注释，仅作备选
}
```
判断：若 `selfdestruct` 被注释或在 TODO 中，检查是否在任何执行路径被真正调用

**场景C**：多重签名钱包的自销毁逻辑
- 检查是否为标准的 gnosis-safe 模式或 OpenZeppelin Ownable2Step
- 若带时间锁+多签+事件，通常为预期行为

### 3. 链上证据收集

**推荐交叉验证**：
1. 合约交互历史：搜索 `selfdestruct` 函数调用是否存在于主网交易中
   - 若有调用：统计时间间隔，查看是否符合紧急情况
   - 若无调用：可能为防御性设计，风险降低
2. 关联合约检索：通过 `Etherscan API` 查询该合约地址是否为以下场景
   - 工厂合约产生的一次性子合约（众筹周期结束后销毁）
   - 测试或已标注为 deprecated 的旧版本
3. 代币跨度分析：若合约销毁前存在大额 approve，判断是否为"资金抽离"前置步骤

### 4. 真假漏洞对比案例

| 特征 | 真实漏洞 | 误报 |
|------|---------|------|
| 接收地址 | `address(msg.sender)` 或动态 `recipient` | `address(owner)` 硬编码或多签钱包 |
| 资金转移 | 销毁前无转移，或转移不完整 | 显式的 `withdraw()` + 余额校验 |
| 事件通知 | 无 `event` 或日志不足 | 有 `Shutdown` 或 `Destroyed` 事件 |
| 依赖方 | 存在外部调用该合约的合约 | 无依赖或已实现 fallback 机制 |
| 时间窗口 | 无时间锁或时间<6h | 有 timelock≥48h 或多签延迟 |
| 测试覆盖 | 无 selfdestruct 的单元测试 | 有明确的销毁场景测试用例 |

### 5. 审计报告红线与绿线

**必要条件（任一满足改为中危+）**：
- [ ] `selfdestruct` 向 `msg.sender` 或用户可控地址转账
- [ ] 合约存储关键状态但销毁前未清理（如用户余额映射）
- [ ] 无任何访问控制（任意调用者可触发）
- [ ] 依赖方合约调用失败后无降级方案

**充分条件（全部满足改为低危）**：
- [x] 多签+时间锁（≥48h）
- [x] 销毁前 `require(address(this).balance == 0)`
- [x] 发出明确的 `Shutdown` 事件
- [x] 工厂合约自动同步或用户可自助迁移
- [x] 公开文档说明生命周期，观察期≥30天无异常

### 6. 常见上钩点与专家判断

**容易遗漏的风险点**：
1. **闪电贷场景**：攻击者在 selfdestruct 同一 tx 调用前借出资金，导致 `require(balance==0)` 通过后资金流入攻击者
   - 防护检查：是否有 `nonReentrant` 或 lock 机制
2. **ERC20/NFT 遗留**：合约销毁但仍持有用户 approve 的资金
   - 防护检查：销毁前是否有 `sweepTokens()` 逻辑
3. **回调陷阱**：接收地址的 `fallback` 或 `receive` 函数异常，导致销毁失败
   - 判断：是否 hardcode 至低风险地址（burn 地址、多签钱包）
