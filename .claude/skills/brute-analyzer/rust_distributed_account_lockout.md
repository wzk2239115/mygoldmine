# 分布式 Rust 账号锁定状态同步失效

## Details

### 核心漏洞原理
分布式 Rust 服务在多实例部署场景下，账号锁定状态仅存储在本地内存（如 HashMap、Mutex、RwLock 等），导致不同实例间无法共享锁定状态。攻击者可通过轮转请求至不同实例，绕过单实例的暴力破解防御。在 Kubernetes、Docker Swarm 或多进程服务器部署中尤为常见。

### 代码定位技巧

**快速定位核心操作** `L1:关键词扫描`
- 搜索关键词：`HashMap`, `Mutex<Map>`, `RwLock<Map>`, `static`, `lazy_static`, `once_cell`
- 追踪账号锁定逻辑的存储声明：查找 `lock`, `account_lock`, `failed_attempts`, `brute_force` 等标志变量
- 定位登录验证函数中的锁定状态检查和修改操作，通常命名为 `check_lock()`, `is_locked()`, `increment_failed()` 等
- 搜索 `static mut` 或 `thread_local!` 声明，这些通常暗示局部状态维护

**快速定位保护机制** `L2:跳读`
- 检查是否使用分布式存储（Redis, Memcached）或共享数据库（PostgreSQL, MySQL）存储锁定状态
- 查阅中间件配置和跨实例通信机制：是否存在消息队列（RabbitMQ, Kafka）同步锁定信息
- 确认是否使用分布式锁（Redis SETNX、etcd 或数据库行级锁）保护状态更新
- 检查配置文件（如 `config.toml`、环境变量）中是否启用了分布式锁或 Redis 连接

**关键代码审计检查清单**
- 查阅 `Cargo.toml` 依赖，是否导入了 Redis、etcd 或分布式锁库（如 `redis`、`redlock-rs`）
- 追踪登录端点的全链路：从 HTTP 处理器到认证逻辑，确认每一步是否都经过分布式状态检查
- 确认失败计数增加和账号解锁的操作是否都在分布式存储中执行，而非本地内存

## Classify

### 漏洞研判逻辑

**确认为漏洞的条件：**
- 服务部署为多实例（2个或以上并发运行）
- 登录密码尝试失败次数限制仅在本地内存维护，无分布式同步
- 不同实例间完全隔离，无共享的锁定状态存储
- 攻击者可通过轮转请求策略绕过单实例防御（如 Round-Robin 负载均衡）
- 使用 `static` 或 `lazy_static` 维护的锁定状态，且无数据库或 Redis 持久化

**识别为代码异味的条件：**
- 服务设计为单实例运行，有明确的架构约束
- 虽使用本地存储但实现了替代防御机制（如 IP 速率限制、验证码强制、请求签名校验）
- 认证系统与业务分离，使用独立认证服务（如 OAuth2、OIDC）集中管理
- 有计划迁移至分布式锁方案但尚未实施（需确认实施时间表）

**判定为误报的条件：**
- 锁定状态通过分布式缓存或数据库集中管理
- 实现了跨实例事件同步机制（如消息队列同步）
- 采用无状态设计，每次认证均向中央系统查询校验
- 使用 Kubernetes StatefulSet 并配置反亲和规则保证单实例，有验证证明

### 审计经验要点

**常见的隐蔽问题：**
- 部分实例使用分布式锁，但并非所有实例都使用（如灰度发布阶段）
- 分布式锁实现存在竞态条件：检查-修改间隙未原子性执行
- Redis 连接故障时的 fallback 逻辑退化为本地锁定
- 账号解锁逻辑只在主实例执行，导致其他实例状态不一致

**测试验证技巧：**
1. 获取有效用户账号，故意输入错误密码 3 次，观察是否锁定
2. 快速切换实例进行测试：使用 HAProxy 或 nginx 代理，通过修改源 IP 或 Cookie 强制路由到不同后端
3. 观察错误计数器：通过本地日志或数据库查询账号的失败次数，判断是否在不同实例间共享
4. 分析负载均衡策略：检查是否为轮转（最容易触发漏洞）或基于连接数的平衡
5. 若服务开放 Redis 管理端口，直接查询 `KEYS failed_attempts:*` 确认是否使用分布式存储

## Low risk

### 低风险评级场景

**架构限制因素：**
- 明确的单实例部署设计约束，且有配置检查强制执行
- 容器编排（K8s）配置确保单副本部署，带重启策略
- 负载均衡器配置为粘性会话（sticky session），同一用户始终路由到同一实例

**防御深度补偿：**
- 实现了全局 IP 限速机制（不依赖账号维度），阈值合理（如 10 次/分钟）
- 集成强制性 CAPTCHA 或 OTP 验证，在多次失败后激活
- 使用 WAF 或网关层的分布式限流规则，统计维度为 IP + 路径，覆盖所有实例

**业务特殊性：**
- 内部系统仅限特定 IP 段访问
- 账号锁定时间极短（秒级），同时具有强制单点登录机制
- 使用硬件令牌或生物识别作为主要认证因子，密码仅为辅助
- 登录页面使用时间戳签名防护，单次有效期极短（30 秒内）

## High risk

### 高风险评级场景

**暴露的指标：**
- 无任何防御机制，轻易可在几秒内绕过登录限制
- 多实例部署且无工作流日志记录，无法审计攻击链路
- 实例数量多（10+ 实例），增加了轮转请求的成功率

**实际危害：**
- 弱密码账号可被快速破解，特别是仅有 4-6 位数字密码的场景
- 重要账号（管理员、核心业务账号）失控风险高
- 可配合其他漏洞（如用户枚举）进行精准攻击

## Remediation

### 修复方案

**推荐方案：使用 Redis 分布式锁**
- 将 `failed_attempts` 和 `locked_until` 迁移到 Redis，使用 `redlock-rs` 或 `redis::Client` 实现原子操作
- 设置 Redis 键过期时间，自动清理过期的锁定记录
- 处理 Redis 连接故障的降级逻辑，故障时采用更严格的 IP 限速

**可选方案：数据库中央化**
- 使用 PostgreSQL 或 MySQL 的行级锁实现 `UPDATE ... FOR UPDATE` 原子性检查-修改
- 添加触发器自动清理过期的锁定记录
- 性能成本高于 Redis，但安全性更强

**快速临时方案（应急）**
- 在负载均衡器层实现粘性会话，确保同一用户始终路由到同一实例
- 在网关层添加 IP 级别的限流规则，阈值设置为 10 次/分钟
- 提前告知用户账号锁定机制，要求强密码策略
