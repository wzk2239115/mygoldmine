# 通用防护缺陷模式（所有项目必审）

拿到任何实现了身份认证、验证或需要防止穷举的项目，无论使用何种编程语言，以下暴力破解防护缺陷都必须进行审计。这些问题源于防护机制的缺失或实施不当，与具体语言实现无关。

## 速率限制缺失或配置不当

### 认证端点缺乏速率限制
登录、密码重置、验证码请求等敏感操作缺少频率限制，允许攻击者无限次尝试：
- 登录接口缺失速率限制或限流规则过于宽松，攻击者可在秒级内尝试数千个密码组合
- 密码重置接口未限制请求频率，可无限发送重置链接或验证码轰炸用户邮箱或手机
- 验证码获取接口无频率限制，可短时间内大量获取验证码进行离线分析或暴力穷举

**审计技巧**：重复发送请求观察响应是否有 `Retry-After` 或 `X-RateLimit-*` 头；检查响应状态码是否存在 429（Too Many Requests）；对批量请求（如10个/秒）进行压力测试；检查是否有服务端日志记录异常频繁的请求。

### 速率限制配置不当或易绕过

虽然实施了速率限制，但配置过于宽松或存在绕过方法：
- 阈值设置过高（如每分钟100次登录尝试），无法有效防止穷举；标准应为3-5次失败后锁定，单位时间内总次数≤5
- 限制仅基于IP，可通过轮换代理IP、使用VPN/代理池或改变 `X-Forwarded-For` 头绕过
- 计数器存储在内存未持久化，分布式环境下跨服务器请求无法同步，每台服务器独立计算限制

**审计技巧**：更换X-Forwarded-For/CF-Connecting-IP/Client-IP等代理相关头尝试绕过；轮换不同IP地址测试是否能重置计数器；对同一账号从多个IP并发请求；查看是否有故障转移时计数器重置的现象。

## 账号锁定机制缺失或可绕过

### 账号锁定机制缺失

多次认证失败后未锁定账号，允许持续暴力破解：
- 登录失败多次后账号未被锁定或临时冻结，用户可无限制重新尝试；标准为5次失败后锁定30分钟
- OTP/2FA 验证失败后未锁定验证流程，用户可持续尝试验证码；应在验证失败3次后临时禁用该认证方式

**审计技巧**：使用Burp Suite Intruder对同一账号进行20-30次连续错误登录，观察是否出现"账号已锁定""稍后重试"等提示；检查前端是否有虚假锁定提示（JS限制）而服务端未实现；查看会话中是否有失败计数器。

### 账号锁定机制可被绕过

实施了锁定机制，但可通过特定方法绕过：
- 锁定状态仅存储在内存或会话中未持久化，应用重启后状态丢失，攻击者可继续暴力破解
- 锁定机制未规范化用户名处理，可通过大小写变化（Admin/admin）、Unicode变体（а=Cyrillic a）、前后空格绕过
- 分布式环境下锁定状态仅存储在单节点缓存，未使用Redis等共享存储，攻击者可针对其他节点请求

**审计技巧**：尝试 `admin`、`Admin`、`ADMIN`、`aDmIn` 等不同大小写组合；用空格、制表符或0x00字节包裹用户名；使用国际化字符相似性（如用Cyrillic字母替换ASCII）；观察负载均衡器路由，测试是否每次请求都到达同一节点。

## 验证码生成或验证缺陷

### 验证码生成算法弱或可预测

验证码使用弱随机源或可预测算法生成，可被提前计算或枚举：
- 使用不安全的随机源（时间戳、固定种子、Math.random），可通过重现随机状态提前计算验证码；必须用 `/dev/urandom`、`SecureRandom` 等加密随机源
- 长度过短（3-4位）或字符集过小（仅0-9），暴力破解成本低；推荐至少6位数字或4位字母+数字
- 顺序递增/固定序列生成，前端拦截多个验证码后识别规律；应使用真正随机源

**审计技巧**：连续请求20个验证码观察序列是否有规律（递增、字符重复）；对时间戳类验证码，尝试修改本地时间后重新生成；查看网络流量是否能识别验证码生成逻辑；测试同一session内多次获取验证码是否返回相同值。

### 验证码验证逻辑缺陷

验证码校验后未失效或可被重复使用：
- 验证成功后未删除或标记，攻击者可在同一验证码上反复请求业务操作；必须验证成功后立即删除或标记已用
- 无过期时间或过期时间过长（24小时），被捕获的验证码可长期重复利用；推荐5-15分钟过期
- 验证失败次数无限制，用户可反复尝试直到穷举所有可能验证码；应在失败3-5次后锁定验证流程

**审计技巧**：验证码验证成功后，用同一验证码再次验证是否通过；观察是否存在验证码预送（预先验证且不消费）；尝试在验证码快过期时反复提交已知的过期验证码；使用Intruder工具遍历所有4位数字（0000-9999）观察是否能穷举。

## OTP/2FA 验证防护不足

### 多因素认证尝试次数无限制

OTP、2FA 等多因素认证码可无限次尝试验证：
- 短信验证码验证次数无限制，6位纯数字仅100万种可能，攻击者可5-10分钟穷举；应在失败3-5次后强制重新发送
- TOTP验证无失败限制，虽然基于时间戳难以预测，但可同时尝试前后若干时间窗口的值
- 邮箱验证码无重试限制，可无限穷举；应在失败3次后冻结验证能力

**审计技巧**：用Intruder对6位验证码进行穷举，测试系统响应速度；尝试同时发送多个OTP验证请求观察计数器是否正确递增；检查时区问题导致的TOTP时间窗口偏差；查看API是否有速率限制与验证码限制相分离的问题。

## 分布式环境状态同步问题

### 限流或锁定状态未正确同步

在分布式或负载均衡环境下，防护状态未在节点间同步：
- 计数器使用本地内存（ConcurrentHashMap等），多节点环境下每个应用服务器独立维护，攻击者可轮询不同服务器绕过；必须用Redis等共享存储
- 锁定状态仅存储在单节点本地，跨节点请求被转发到未更新的节点继续尝试认证；必须存储在共享数据库或分布式缓存
- Redis防护状态虽然共享，但未设置合理的过期时间，过期时间过长或过短都会导致防护失效

**审计技巧**：识别负载均衡方式（观察Cookie中的Server ID、响应头中的Server标识）；在连续请求中刻意轮换服务器（更换User-Agent、IP、Session等），观察限流计数器是否能正确同步；监听网络流量查看后端是否有共享存储的通信。

## 审计检查清单

- [ ] 遍历所有认证相关端点（登录、注册、密码重置、验证码、OTP）并检查速率限制实施
- [ ] 确认速率限制是否基于IP+用户名或其他合理标识符，而非仅IP
- [ ] 对限流规则进行压力测试，观察阈值、锁定时间、解锁机制
- [ ] 检查是否存在状态持久化和分布式环境下的同步问题
- [ ] 测试账号锁定机制的规范化处理（大小写、空格、Unicode）
- [ ] 验证验证码生成的真随机性，尝试识别规律
- [ ] 确认验证码一次一用的机制（验证后自动删除或标记）
- [ ] 对所有验证码进行失败次数限制和过期时间验证
