# C/C++ 弱验证码生成

## Details

### 核心代码示例

验证码生成弱点通常出现在以下场景：

1. **使用时间戳或简单计数作为种子**
```c
// 易被预测的验证码生成
srand(time(NULL));
int captcha = rand() % 10000;  // 4位数字验证码
```

2. **使用线性同余生成器（LCG）**
```c
// 状态空间小，可快速穷举
unsigned long seed = time(NULL);
captcha = ((seed * 1103515245 + 12345) / 65536) % 10000;
```

3. **静态随机数种子初始化不足**
```c
// 种子仅初始化一次，多次调用生成序列可被预测
srand(fixed_seed);
for (int i = 0; i < attempts; i++) {
    int code = rand() % 1000000;
}
```

### 快速定位到核心操作的技巧
**【审计等级：L1 - 关键词扫描】**

- 搜索关键字：`rand()`, `srand()`, `random()`, `srandom()`
- 搜索时间相关：`time()`, `gettimeofday()`, `clock()`
- 搜索验证码相关：`captcha`, `verification`, `otp`, `code`, `pin`, `token`
- 查找模运算：`% 10000`, `% 1000000`, `% 9999`
- 识别数字生成：`snprintf`, `sprintf`, `itoa` 生成验证码的代码段

### 快速定位到保护机制的技巧
**【审计等级：L2 - 跳读】**

- 检查是否使用密码学安全的随机数生成：`/dev/urandom`, `getrandom()`, `CryptGenRandom()` (Windows), `arc4random()` (BSD)
- 搜索加密库调用：`OpenSSL`, `libsodium`, `mbedTLS`
- 查找速率限制/限流机制：`rate_limit`, `throttle`, `attempt_limit`, `cooldown`
- 检查验证码过期机制：`expiry`, `timeout`, `ttl`, `validity`
- 查找验证次数限制：`max_attempts`, `attempt_count`, `failures`
- 检查是否有一次性使用标志：`used`, `consumed`, `valid_once`

## Classify

### 漏洞判定标准

**确认为漏洞的条件：**
- 验证码熵值过低（< 20 bits），可通过穷举在合理时间内破解
- 使用非密码学安全的伪随机数生成器 (PRNG)
- 种子空间限制（如仅基于时间戳，预测空间 < 100000）
- 同一会话内多次生成的验证码存在可预测的数学关系
- 验证码长度过短（数字验证码 < 6位，字母数字 < 4位）
- 缺乏速率限制导致可高频尝试

**误报识别：**
- 使用 `rand()` 但仅作非安全用途（如UI动画、游戏内非关键随机）
- 验证码生成后立即销毁且无存储
- 虽使用弱PRNG但有强有力的外部保护机制（如验证次数严格限制 ≤ 3次、指数退避延迟）

**代码异味：**
- 验证码硬编码或配置不当
- 缺少有效期验证逻辑
- 验证码在日志中明文记录
- 验证时缺少完整性校验（如HMAC）

## Low risk

### 低风险评级情景

以下情况可降低为低风险：

1. **强有力的多层防护**
   - 虽验证码生成弱，但具有有效的限流机制（指数退避、账户锁定）
   - 验证次数严格限制（≤ 3 次），且单次失败后强制等待时间递增
   - 验证码有效期极短（< 2 分钟）且支持一次性使用

2. **高熵辅助机制**
   - 验证码与用户会话绑定（Session ID + HMAC 校验）
   - 使用挑战-响应协议进行二次验证
   - 结合设备指纹、IP 地址验证等额外因素

3. **低价值场景**
   - 验证码仅用于低权限操作（如修改非关键偏好设置）
   - 保护的资源不涉及敏感信息或资金转移
   - 操作需结合其他强认证因素

4. **短期部署**
   - 已确认该代码已在计划内修复，修复周期明确
   - 临时性验证机制，用于功能演示或测试环境
