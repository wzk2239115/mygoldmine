# Rust - 弱验证码生成机制

## Details

**代码示例及风险特征：**

```rust
// 漏洞模式 1：时间戳种子 - 熵源可预测（通常为秒或毫秒级）
use std::time::{SystemTime, UNIX_EPOCH};
use rand::Rng;

fn generate_captcha_weak_time() -> String {
    let seed = SystemTime::now()
        .duration_since(UNIX_EPOCH)
        .unwrap()
        .as_millis() as u64;  // 熵仅 ~40 bits，约1秒内重复概率 > 50%
    let mut rng = rand::rngs::StdRng::seed_from_u64(seed);
    let code: u32 = rng.gen_range(0..1000000);
    format!("{:06}", code)
}

// 漏洞模式 2：非加密安全 RNG - rand::thread_rng 使用 XorShift 后端，可被预测
fn generate_captcha_insecure() -> String {
    let mut rng = rand::thread_rng();  // 底层是 ThreadRng，非 getrandom 支持
    let code: u32 = rng.gen_range(0..1000000);
    format!("{:06}", code)  // 攻击者可通过多次生成推导 RNG 状态
}

// 漏洞模式 3：确定性计数器 - 完全无随机性，可直接枚举
static mut CAPTCHA_COUNTER: u32 = 0;
fn generate_captcha_counter() -> String {
    unsafe {
        CAPTCHA_COUNTER += 1;
        format!("{:06}", CAPTCHA_COUNTER)  // n+1, n+2, n+3... 完全线性，无安全性
    }
}

// 漏洞模式 4：确定性哈希 - DefaultHasher 设计用于 HashDoS 抵抗，非碰撞安全
use std::collections::hash_map::DefaultHasher;
use std::hash::{Hash, Hasher};

fn generate_captcha_from_session(session_id: &str) -> String {
    let mut hasher = DefaultHasher::new();
    session_id.hash(&mut hasher);  // 对于相同 session_id 总是相同结果
    let hash = hasher.finish();
    let code = (hash % 1000000) as u32;
    format!("{:06}", code)  // 验证码可被离线推导，无一次性特性
}

// 漏洞模式 5：低熵组合 - 时间戳粒度太粗，XOR 操作无加密意义
fn generate_captcha_no_entropy(user_id: u64) -> String {
    let timestamp = std::time::SystemTime::now()
        .duration_since(std::time::UNIX_EPOCH)
        .unwrap()
        .as_secs() / 60;  // 粒度 60s，同一分钟内所有用户都有相同时间戳
    let code = ((user_id ^ timestamp) % 1000000) as u32;  // XOR 不增加熵
    format!("{:06}", code)  // 攻击者知道当前分钟时间戳，可暴力枚举 user_id
}
```

### 快速定位核心操作 **L1: 关键词扫描**

| 关键词 | 风险等级 | 说明 |
|--------|---------|------|
| `SystemTime::now()` / `as_millis()` / `as_secs()` | 🔴 高 | 时间戳作为种子，可预测 |
| `seed_from_u64()` / `seed_from_u64_bytes()` | 🔴 高 | 确定性种子化，非加密安全 |
| `rand::thread_rng()` | 🟠 中 | 需检查是否在加密上下文中使用 |
| `StdRng::seed_from_u64()` | 🔴 高 | 标准 RNG 用确定性种子，无随机性 |
| `DefaultHasher` / `std::hash::Hasher` | 🔴 高 | 哈希函数作为验证码生成 |
| 计数器变量（`Counter`, `ATOMIC_SEQ`, `Mutex<u64>`） | 🔴 高 | 线性递增，完全确定性 |
| `gen_range(0..1000000)` | 🟡 中 | 检查 RNG 源是否安全 |

### 快速定位保护机制 **L2: 跳读 + L3: 逐行读**

| 检查项 | 审计等级 | 关键代码特征 |
|--------|---------|-------------|
| **密码学安全源** | **L2** | `use rand::rngs::OsRng`；`OsRng.gen_range()`；`getrandom` crate；`ChaCha20Rng` |
| **种子初始化** | **L2** | `OsRng::new()` + `gen()` 而非 `seed_from_u64()` |
| **样本空间验证** | **L3** | 验证码位数 ≥ 6（数字）或 ≥ 5（字母数字），`1000000` 或更大 |
| **时间限制** | **L3** | 创建时间戳 + 有效期（检查是否 < 10分钟） |
| **一次性验证** | **L3** | 验证成功后 delete/remove/mark_used 操作 |
| **错误限制** | **L3** | 验证失败计数、锁定阈值（通常3-5次） |
| **分布式一致性** | **L4** | Redis TTL、数据库事务、分布式锁（如 `redlock-rs`） |
| **并发竞态** | **L4** | `Mutex` 保护共享验证码存储、`Arc<RwLock>` 的 TOCTOU 检查 |

## Classify

### 真漏洞判定

对以下特征之一的存在表示确定性漏洞，需要立即修复：

1. **熵源不足 - 可预测验证码**
   - 使用 `SystemTime::now()` 作为 RNG 种子（精度通常 ms ~ sec 级，熵 < 40 bits）
   - 时间戳 XOR/加法 + 用户 ID（攻击者知道时间戳后可枚举 user_id）
   - 使用 `hash(session_id)` 等确定性函数（相同输入永远相同输出）

2. **完全确定性生成**
   - 计数器递增（`COUNTER += 1`）：可直接枚举，无安全性可言
   - `seed_from_u64()` 初始化 RNG：种子来自可预测源（时间、计数器等）
   - 基于固定参数的哈希（`user_id * 某常数 % 1000000`）：可完全推导

3. **样本空间过小且无防护**
   - 验证码空间 < 10^6（4位数字 = 10000 种可能）且无错误限制
   - 即使有随机性，6分钟内（360秒）完全枚举的概率 > 99%

4. **缺乏时间限制且无一次性约束**
   - 不检查验证码生成时间，允许无限期有效
   - 验证成功后不删除/失效，相同验证码可多次使用
   - 示例：生成的验证码在数据库中永久存储

5. **防暴破机制缺失**
   - 验证码错误尝试无限制（没有计数逻辑）
   - 无账户锁定、无IP限流、无延时重试
   - 攻击者可在短时间内尝试大量验证码

6. **分布式环境下的竞态条件**
   - 在缓存主从同步中验证码可能跨实例重复
   - 并发验证时先读后写未原子化（TOCTOU）

### 误报排除标准

以下情况视为低风险或误报，不应作为严重漏洞上报：

1. **密码学安全的 RNG + 充分样本空间**
   - 使用 `rand::rngs::OsRng` 或 `getrandom` 生成
   - 验证码长度 ≥ 6 位数字（10^6 种）或 ≥ 5 位字母数字（36^5 ≈ 6.05×10^7 种）
   - 原因：攻击成本 > 用户损失

2. **严格时间限制 + 一次性失效**
   - 有效期 ≤ 10 分钟，验证成功立即删除/标记
   - 在验证表中存储生成时间和验证时间，逻辑中检查两者差值

3. **完整防暴破体系**
   - 错误次数限制（3-5 次后锁定）且有明确延时（指数退避或固定延时）
   - IP 级限流（同一 IP 每分钟最多 N 次请求）
   - 异常登陆检测（检测多个地理位置、设备、IP 的快速切换）

4. **业务上下文的低敏感性**
   - 验证码仅用于非金融操作（如邮箱确认、评论发布）
   - 后续还需额外认证（密码、硬件密钥）
   - 单一验证码泄露不足以完全绕过认证链

### 代码异味（需关注）

以下特征不直接构成漏洞，但指示风险，需进一步审查：

1. **随机源来源不明**
   - 验证码生成函数未注释说明 RNG 类型和初始化方式
   - 开发者可能混淆了 `thread_rng()` 与 `OsRng` 的用途

2. **种子来自外部输入**
   - `seed_from_u64(user_provided_value)` 或从请求参数读取种子
   - 攻击者可控制 RNG 初始值，验证码变为完全确定

3. **验证码与上下文的数学关系**
   - `user_id XOR timestamp`、`hash(user_id + session_id)`
   - 虽然含随机成分，但不是密码学推导，可能存在碰撞或预测

4. **验证逻辑过度简化**
   - 仅比对字符串，未检查生成时间、尝试次数、使用次数
   - 验证码表无 TTL 或清理机制，历史验证码可能被恢复

5. **分布式系统下的不一致性**
   - 不同应用实例有各自的 RNG 种子（不共享，导致同一用户多次生成不同码）
   - 验证码存储在本地内存而非共享存储（Redis、数据库），多实例部署时无法验证

## Low risk

### 低风险评级条件

满足以下 **任意组合** 的场景可以降级为低风险，通常不需要立即修复（但仍需记录和后续跟踪）：

#### 1. 密码学安全 RNG + 充分防护

**条件：** 同时满足以下三点
- 使用 `rand::rngs::OsRng` / `getrandom::getrandom()` / 可信库的加密安全 RNG
- 验证码长度 ≥ 6 位数字（10^6 种）或 ≥ 5 位字母数字（36^5 种）
- 实现了严格的时间限制（有效期 ≤ 10 分钟）和一次性验证（验证成功立即失效）

**风险降级依据：** 即使 RNG 被攻击或边界情况下，样本空间足够大，暴力破解成本 > 用户权限价值

#### 2. 强时间限制 + 业务低敏感性

**条件：** 同时满足以下两点
- 验证码有效期 < 2 分钟，且验证后立即删除
- 使用场景为低风险操作（邮箱确认、评论发布、找回密码第一步）

**风险降级依据：** 小时间窗口限制了攻击时间，业务低敏感性限制了攻击收益

#### 3. 完整防暴破体系

**条件：** 满足以下 **至少 3 项**
- 错误尝试限制明确（3-5 次后账户 30 分钟内锁定 OR 触发 CAPTCHA）
- IP 级速率限制（同一 IP 每分钟最多 1-3 次验证请求）
- 指数延时重试（如第 1 次失败延时 0s，第 2 次 1s，第 3 次 2s，第 4 次 4s）
- 异常登陆检测（多个地理位置 30 分钟内切换时触发风控）
- 验证码与用户上下文绑定（含 user_id / session_id 的 HMAC，离线推导成本高）

**风险降级依据：** 即使验证码可预测，多重防护使得攻击成本极高且易于检测

#### 4. 多因素验证链中的单环

**条件：**
- 验证码仅为登陆流程中的一个环节（如先密码后验证码后硬件密钥）
- 后续仍需通过密码或第二因素验证

**风险降级依据：** 攻击者即使获得验证码，仍无法完全绕过认证链

#### 5. 基于业界标准库的实现

**条件：**
- 使用经过安全审计的 Rust 验证码库（如 `totp-rs`、`sha2` + 密码学框架）
- 库的最新版本无已知 CVE
- 按照官方文档使用，未定制化改造随机源

**风险降级依据：** 库维护者承担安全责任，社区持续监控

#### 6. 可观测性与告警完善

**条件：**
- 短时间内多次验证失败时自动触发告警（如 10 分钟内 10 次失败）
- 验证码生成与验证全过程记录在审计日志，可溯源追踪
- 存在人工审查流程（异常行为自动暂停并通知管理员）

**风险降级依据：** 即使被攻击，能及时发现和阻止，限制损失

| 内部系统验证码 + `thread_rng` | 🟠 中等 | ✅ 完整 | ✅ 2分钟 | 🟠 中 | 低 | 内部系统降低风险权重 |

### 降级判定检查清单

评估时按以下顺序检查，**任一条件不满足则不能降级**：

- [ ] 已确认使用加密安全 RNG 或业界标准库（检查源代码或依赖）
- [ ] 验证码长度/空间充分（计算 log₂(样本空间) ≥ 20 bits）
- [ ] 验证码有效期明确 < 某个上限值（通常 10 分钟）
- [ ] 验证成功后验证码失效逻辑存在（delete/expire/mark 操作）
- [ ] 至少存在一种防暴破机制（错误限制、速率限制、延时重试、检测告警）
- [ ] 业务风险等级与防护体系匹配（高风险需多重防护）

---

**最终规则：** 低风险报告时应明确说明依赖的防护条件，如防护被绕过或配置改变，风险等级应自动升级为中/高
