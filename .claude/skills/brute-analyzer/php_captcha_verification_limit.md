# PHP 验证码校验次数限制缺失

## Details

验证码校验次数限制缺失是指应用在验证用户提交的验证码时，未对同一验证码的校验尝试次数进行限制，攻击者可无限制地进行暴力破解尝试。

**核心操作代码定位 (L1: 关键词扫描)**
- 关键词：`$_SESSION['captcha']`、`$_POST['captcha']` 或 `$_GET['captcha']` 的比对逻辑
- 搜索模式：`if ($_POST['captcha'] == $_SESSION['captcha'])` 或 `if ($_POST['captcha'] === $_SESSION['captcha'])`
- 查找验证码的读取、存储和清除操作，检查是否仅在成功验证后才清除

**保护机制缺失检查 (L3: 逐行读)**
- 检查验证码校验函数/方法是否实现了以下保护机制之一：
  - **计数器限制**：使用 `$_SESSION['captcha_attempts']` 或数据库记录校验尝试次数
  - **锁定机制**：达到失败次数限制后锁定账户/IP，如 `$_SESSION['captcha_locked'] = true`
  - **延时机制**：每次失败后增加延时，如 `sleep()` 或时间戳校验
  - **一次性销毁**：验证码在任何校验尝试（成功或失败）后立即销毁
- 确认是否存在针对同一验证码的失败次数上限检查
- 追踪验证码是否在失败校验后保留，导致可重复利用

## Classify

**误报 vs 漏洞的区分**

1. **确定为漏洞**：
   - 验证码在校验失败后仍保留，允许无限制重试
   - 不存在任何形式的尝试次数限制（计数器、锁定、延时）
   - 未在会话层面检查校验状态，同一验证码可被多次使用

2. **可能的误报/低风险**：
   - 存在全局的IP级别速率限制（独立的中间件或网关防护）
   - 验证码长度足够长（>6位）且使用密码学随机数生成
   - 存在单向哈希存储的验证码（如 `password_hash()` 而非明文比对）
   - 系统实现了联合防护：超时销毁 + 短生命周期 + 其他身份验证因素

3. **代码异味**：
   - 验证码存储在客户端 Cookie（可被篡改）
   - 使用弱随机数生成器（如 `rand()` 而非 `random_bytes()`）
   - 验证码生命周期过长（>10分钟）
   - 校验逻辑使用弱比较（`==` 而非 `===`）

## Low risk

**给予低风险评级的情况**

1. **完整的联合防护措施**：
   - 应用实现了严格的尝试次数限制（3-5次失败后锁定）
   - 同时配置了账户级或IP级的临时锁定机制（锁定时间 ≥ 15分钟）
   - 验证码在任何情况下的生命周期不超过5分钟

2. **强化的验证码设计**：
   - 验证码长度 ≥ 6位且字符集丰富（数字+字母+特殊字符）
   - 使用密码学安全的随机数生成（`random_bytes()` 或等价方案）
   - 验证码仅允许一次性校验（成功或失败后均销毁）

3. **外层防护充分**：
   - 请求端部署了WAF或API网关层的速率限制（如每IP每分钟限制10次请求）
   - 验证码校验端点受到独立的DDoS防护或请求限流机制保护
   - 系统同时部署了账户锁定、日志审计等多层防御

**注**：即使存在上述低风险情况，仍应在审计报告中记录该漏洞点的存在，标注为低风险或建议优化，而不应完全忽略。

## 审计专业技巧

### 1. 动态追踪验证码生命周期

**关键审计流程**：
- 在浏览器开发者工具中监控 Session 变化，记录验证码从生成、验证失败、验证成功的全流程
- 使用 `var_dump($_SESSION)` 在关键节点输出会话状态，对比验证前后的 `$_SESSION['captcha']` 变化
- 测试序列：首次生成验证码 → 5次错误尝试 → 观察验证码值是否仍存在 → 尝试第6次错误输入
- 记录每次验证前后的时间戳，验证延时机制是否真实有效

**代码审查要点**：
```php
// 易出现漏洞的模式：验证码永不销毁
if ($_POST['captcha'] === $_SESSION['captcha']) {
    // 登录成功
} else {
    // 仅记录计数，验证码仍保留在会话中
    $_SESSION['captcha_attempts']++;
}
```

### 2. 计数器机制的有效性验证

**常见误导的防护代码**：
- ❌ 计数器存储在客户端 Cookie（可篡改）：`setcookie('captcha_attempts', $count)`
- ❌ 计数器仅在内存中，会话过期后重置：不持久化到数据库
- ❌ 计数器重置逻辑不清：生成新验证码时是否同时重置计数？

**正确的验证方法**：
```php
// 检查以下条件都需满足才能认定为有效防护：
// 1. 计数器存储在服务端会话或数据库（难以篡改）
// 2. 达到限制后是否真正阻止后续请求（如返回 403 或强制等待）
// 3. 锁定时间是否足够长（至少15分钟）
```

### 3. 区分真实漏洞与误报

#### 真实漏洞的确凿证据

| 表现 | 确认方法 |
|-----|--------|
| **无限制重试** | 连续发送50次不同验证码，均被接受 |
| **验证码复用** | 验证失败后，同一验证码在1小时内仍可重复使用 |
| **并发破解** | 使用多个并发请求，绕过串行计数器 |
| **会话延续** | 关闭浏览器重新打开，旧验证码仍有效 |
| **时间窗口** | 短时间内（<5秒）发送大量请求，无任何延时响应 |

#### 常见的误报场景

**场景1：存在全局速率限制但不明显**
- 特征：单个验证码的失败尝试受限，但限制由网关/WAF实现，不在应用代码中
- 确认方法：检查 Nginx/Apache 配置、WAF 规则、云平台防护策略（AWS WAF、CloudFlare 等）
- 评级：如果整体防护充分，可降级为低风险

**场景2：客户端端点实现了强缓存**
- 特征：前端JavaScript在一定时间内禁用提交按钮，但不是服务端限制
- 确认方法：Burp Suite 绕过前端限制，如果后端无防护则为漏洞
- 结论：**前端限制不算防护**，仍需服务端验证

**场景3：验证码与账户绑定的特殊情况**
- 特征：每个账户有独立的验证码，一个账户失败多次后，其他账户验证码仍可用
- 确认方法：使用不同账户测试，观察是否触发全局限制
- 评级：降低风险但仍可用于针对性破解

### 4. 绕过技巧与复杂场景

**跨会话攻击**：
- PHP `session.gc_maxlifetime` 默认1440秒，部分应用可能更短
- 攻击者可创建多个会话，每个会话重新尝试验证码破解
- 确认：生成新验证码后切换会话重试，观察是否计数独立

**时序攻击与竞态条件**：
```
if (checkAttempts() < 5) {  // T1: 检查
    verifyCode();           // T2: 验证（假如费时操作）
    incrementAttempts();    // T3: 增加计数
}
// 线程安全问题：T1-T3间隙，多个请求可能同时通过检查
```
- 确认：使用多线程工具（如 Apache JMeter）在验证码快要失效时并发请求

**缓存污染**：
- Redis/Memcached 未正确配置过期时间，计数器永不清除
- 确认：查看缓存配置、监控缓存键的实际 TTL

## 审计工具与自动化检测

### Burp Suite 定制测试

1. **重复器（Repeater）**：持续发送相同验证码，监控响应码变化
2. **入侵者（Intruder）**：逐次修改验证码值，统计成功/失败比例
3. **扩展脚本**：编写 Burp 扩展自动检测验证码是否销毁

### 代码扫描清单

- [ ] 检查 `unset($_SESSION['captcha'])` 或 `$_SESSION['captcha'] = null` 的位置
- [ ] 确认计数器存储位置（会话 vs 数据库 vs Cookie）
- [ ] 审计锁定机制的解锁条件（是否可被绕过）
- [ ] 验证随机数生成函数（`random_bytes()` vs `rand()`）
- [ ] 检查验证码有效期的硬编码值或配置值

## 报告撰写建议

**高风险判定依据**：
- 零防护机制：无计数器、无锁定、无延时、无销毁
- 防护可绕过：前端限制、客户端存储、弱加密

**中风险判定依据**：
- 不完整防护：仅有计数器但无锁定、或有锁定但可在新会话中绕过
- 防护配置不当：锁定时间过短（<5分钟）、计数限制过高（>10次）

**低风险判定依据**：
- 多层防护协同：计数器 + 锁定 + 外层WAF + 强验证码设计
- 确认无组合攻击风险（如跨会话、并发、缓存污染）
