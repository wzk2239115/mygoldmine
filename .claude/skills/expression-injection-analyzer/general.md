# 通用表达式注入缺陷模式（所有项目必审）

拿到任何涉及表达式处理或动态代码执行的项目，无论使用何种编程语言，以下表达式注入缺陷模式都必须进行审计。这些问题源于不安全的表达式评估或模板处理方式，与具体语言实现无关。

## 直接在表达式中拼接用户输入

将用户输入直接嵌入表达式字符串中评估，包括：
- 字符串拼接或格式化嵌入用户输入到表达式，如 `eval("obj." + user_input)` 或 `f"${user_input}"`
- 使用模板字符串或字符串插值构造动态表达式，未进行任何验证或转义
- 直接在配置文件解析、模板引擎、规则引擎中使用未过滤的用户输入

## 使用危险的表达式评估函数

使用 eval()、exec() 等危险函数直接执行用户输入的代码：
- JavaScript/Python 中的 `eval(user_input)` 直接解释用户输入
- PHP 中的 `eval()` 或 `assert()` 执行用户提供的代码
- 动态代码执行框架（MVEL、OGNL、SpEL）未正确沙箱化
- 任意代码执行入口（如反序列化、代码生成）

## 模板引擎上下文污染

在模板引擎中错误地暴露危险对象或函数到表达式上下文：
- Jinja2/Django 模板中未过滤用户变量导致 SSTI
- Freemarker 模板中 `?new()` 等危险内置函数可被调用
- Velocity 模板中 ClassTool 等工具类暴露
- Twig 模板中对象方法无限制访问
- EJS、Handlebars 等 Node.js 模板引擎的不安全渲染

## 表达式语言 (EL) 注入

在 Java Web 应用中的 EL 表达式注入：
- JSP 页面中 `${}` 或 `#{}` 表达式直接使用用户输入
- Spring SpEL 表达式中用户输入未正确沙箱化
- 自定义表达式语言实现未对用户输入进行限制

## 规则引擎与条件表达式注入

在规则引擎或条件判断中注入恶意表达式：
- Drools、Easy-Rules 等规则引擎的规则定义包含用户输入
- 动态条件判断（如 `if (eval(condition))` ）接收用户输入
- 配置文件中的表达式字段被用户可控数据污染

## 特殊语法元字符未过滤

未对表达式特殊字符进行过滤、转义或白名单验证，常见注入方式：
- 属性访问运算符 (`.`、`[]`) 用于访问对象属性或数组元素
- 函数调用语法 `()` 用于执行对象方法
- 逻辑运算符 (`&&`、`||`、`?:`) 用于条件执行
- 字符串拼接符号 (`+`、`.concat()`) 用于动态字符串构造
- 类型转换和强制转换 (`(Type)`) 用于绕过安全检查

## 危险内置函数或方法访问

表达式引擎中暴露的危险函数或方法被恶意利用：
- 反射调用（`.getClass()`、`.getDeclaredMethods()`）绕过沙箱
- 文件操作（`Runtime.getRuntime()`、`ProcessBuilder`、`File`）
- 系统命令执行（Java 中通过反射调用 Runtime）
- 类加载和动态编译（`ClassLoader.loadClass()`、`GroovyShell`）

## 配置文件表达式求值

在解析配置文件时动态求值表达式：
- YAML/JSON 配置文件中的表达式被直接执行
- 属性文件中包含 EL 表达式被框架自动求值
- Spring PropertyPlaceholder 中的表达式注入
- 自定义配置解析器未正确处理表达式

## 动态脚本注入

通过动态脚本引擎执行用户提供的脚本代码：
- Groovy、Rhino 等脚本引擎直接执行用户输入的脚本
- 数据库脚本（JavaScript 在 MongoDB、Lua 在 Redis）执行用户代码
- 自定义 DSL（Domain Specific Language）解析器对用户输入求值

## 输入验证不足

对用户输入的验证不充分或使用了不安全的验证方式：
- 仅使用黑名单过滤特殊字符，可通过编码、大小写变化或其他方式绕过
- 白名单验证不严格，允许部分危险字符通过
- 未验证表达式的复杂度和执行时间，导致拒绝服务
- 缺少对表达式访问范围的限制

---

这些缺陷模式是表达式注入类漏洞的根本原因，在进行代码审计时需要重点关注。
