# C/C++ 配置文件表达式注入

**漏洞成因**：在解析配置文件（如 INI、JSON、YAML、自定义格式）时，将其中的表达式字段直接求值或传递给表达式引擎，导致用户可控的配置参数被当作代码执行。常见于配置框架集成、参数化配置解析、条件执行等场景。

---

## Details

**代码示例**：
```c
// 危险：直接求值配置中的表达式
const char* config_expr = config_get("condition");
if (eval(config_expr)) {  // 直接执行用户配置中的表达式
    process_request();
}

// 危险：配置文件中包含表达式被直接解析
// config.ini: filter_rule = "user.id > 1000 || user.role == 'admin'"
char* rule = ini_read("config.ini", "security", "filter_rule");
apply_filter(rule);  // 表达式未经过验证直接使用

// 较安全：白名单验证 + 固定值映射
const char* mode_str = config_get("execution_mode");
if (strcmp(mode_str, "safe") == 0) {
    execution_mode = SAFE_MODE;
} else if (strcmp(mode_str, "strict") == 0) {
    execution_mode = STRICT_MODE;
}
```

**快速定位核心操作**：
- 关键词：`eval(`、`parse_expression(`、`interpret(`、自定义表达式解析函数
- 查看配置读取源（文件读取、环境变量、外部 API）
- 追踪配置值是否直接进入表达式评估函数
- 检查是否存在配置热重载机制（允许运行时修改表达式）
- 关注字符串拼接构造表达式的代码路径

**快速定位保护机制**：
- 是否存在配置值的白名单验证
- 是否限制配置文件的读取权限和来源
- 是否对配置值进行类型检查和格式验证
- 是否使用配置数据绑定而非动态表达式求值
- 是否对表达式的复杂度、长度、执行时间有限制

**审计等级**：**L2-L4**
- **L2**：跳读配置读取和表达式处理的关键路径
- **L3**：逐行分析配置值的流向和验证逻辑
- **L4**：跨模块追踪配置文件来源到表达式执行的完整链路，检查是否支持运行时热加载

---

## Classify

**确认为漏洞**：
- 配置文件中的表达式字段被直接传入 eval() 或自定义表达式求值函数
- 配置来源包括用户可控的渠道（上传配置文件、配置管理界面、环境变量）
- 表达式求值环境未被沙箱化，可访问危险函数或对象
- 配置验证缺失或不完整（仅检查格式，未检查内容安全性）

**误报**：
- 配置表达式完全由应用内部提供，不包含用户输入
- 配置字段为简单的数据类型（字符串、数字、布尔值），不支持表达式
- 存在严格的白名单限制，配置值被完全限制在预定义的安全范围内
- 表达式在沙箱环境执行，无法访问文件系统、网络或执行系统命令

**代码异味**：
- 配置处理逻辑中存在 eval() 调用，即使当前未被用户污染
- 支持热重载配置但缺少变更审计和校验机制
- 配置解析器的实现不规范，处理边界情况不完善

---

## Low Risk

以下情况可评为低风险：
- **受限环境**：配置文件由系统管理员管理，普通用户无上传或修改权限
- **内网隔离**：配置管理界面仅对内部用户暴露，有访问控制和审计日志
- **沙箱隔离**：表达式运行在严格沙箱中，无法访问 File I/O、进程管理、网络等危险 API
- **表达式能力弱**：配置表达式仅支持基础运算（算术、布尔逻辑），不支持函数调用和方法访问
- **长度和复杂度限制**：配置表达式有严格的长度限制和执行时间超时控制

**注意**：低风险≠可忽略，仍应结合实际访问控制、运维流程进行综合评估。
