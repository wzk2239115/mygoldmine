# Go Gin 框架未验证重定向漏洞

Gin 框架的 `c.Redirect()` 方法在处理用户可控的重定向参数时，若未进行严格的URL验证，会导致开放重定向漏洞。攻击者可利用此漏洞将用户重定向至恶意网站。

## Details

### 代码示例

```go
// 漏洞代码：直接使用查询参数进行重定向
func RedirectHandler(c *gin.Context) {
    redirectURL := c.Query("redirect_to")
    // 直接使用用户输入，未进行任何验证
    c.Redirect(http.StatusFound, redirectURL)
}

// 调用示例
// GET /redirect?redirect_to=https://evil.com
```

**快速定位到核心操作的技巧** `(L1:关键词扫描)`
- 搜索关键词：`c.Redirect()`、`c.Header("Location")`、`http.Redirect`
- 重点关注：从 `c.Query()`、`c.PostForm()`、`c.Param()` 等用户输入方法直接进入重定向函数的代码路径
- 表现特征：重定向目标与用户可控输入在同一表达式中，无中间处理环节

**快速定位到保护机制的技巧** `(L2:跳读)`
- 检查 `Redirect()` 调用前是否存在URL验证函数调用
- 识别常见安全函数模式：
  - URL白名单验证（使用 `strings.HasPrefix()` 或正则表达式）
  - 协议检查（仅允许 `http://`、`https://`）
  - 域名白名单（与 `url.URL.Host` 比对）
  - 相对路径检查（确保不包含 `//` 或完整域名）
- 查看是否有中间件或通用的验证函数被调用
- 跳读验证函数逻辑，关注边界情况处理（如 `//`、编码绕过等）

## Classify

从漏洞成因分类标准：

**真实漏洞的判断依据**
- 重定向URL完全来自用户输入（Query、Form、Header、Body等），且无任何验证
- 验证逻辑存在但可被绕过：
  - 仅检查协议前缀，未防止 `http:///evil.com` 等双斜杠绕过
  - 白名单检查不完整，如仅检查 `URL.Host` 但忽视 `//domain.com@evil.com` 的用户信息字段绕过
  - 相对路径验证中未考虑 `.../../../` 的穿越
  - 使用易被绕过的函数，如 `strings.Contains()` 而非 `strings.HasPrefix()`
- 验证函数形同虚设：验证后仍使用原始输入而非验证结果

**误报的特征**
- 重定向URL完全硬编码于代码中，不依赖用户输入
- 仅重定向至相对路径（如 `/login`、`./dashboard`），无法指定外部域名
- 虽接收用户输入但参数名不在白名单内（如 `allowed_redirects` 配置定义了精确允许的值）

**代码异味的表现**
- 存在URL验证逻辑，但与业务代码的关联不清晰
- 有多个重定向点，部分验证完整，部分不完整
- 使用了过时或不推荐的验证方式，虽未构成严重漏洞但规范性不足

## Low risk

低风险情况的评级标准：

**协议和域名的双重约束**
- 代码明确限制只允许 `https://` 协议（不接受 `http://`），且使用 `url.Parse()` 进行解析验证
- 已配置域名白名单，并通过 `url.URL.Host` 字段逐一对比，同时正确处理子域名

**参数空值处理**
- 用户输入为空时默认重定向至安全页面（如首页或来源页），体现了防御性编程
- 使用了显式的条件判断，如 `if redirectURL == "" { redirectURL = "/home" }`

**相对路径限制**
- 强制使用相对路径（如 `c.Redirect(http.StatusFound, "/" + sanitizedPath)`）
- 通过正则表达式 `^/[a-zA-Z0-9/_-]+$` 严格限制路径格式，不允许 `://` 出现

**来源验证与令牌绑定**
- 结合 Referer 头部验证（虽不绝对安全，但增加了攻击成本）
- 使用 CSRF Token 或签名的重定向令牌方式，用户无法伪造

**框架级安全特性**
- 使用业界已验证的 URL 验证库（如 Go 标准库 `url.Parse()` 配合严格检查），避免自行实现
- 在中间件层统一处理，确保所有重定向均经过验证
