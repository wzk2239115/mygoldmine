# Move DeFi MEV 前置交易漏洞

**漏洞概述**  
常出现在涉及资源状态竞争的DeFi协议、治理提案投票或NFT铸造逻辑中，包括但不限于未隔离用户操作的原子性、允许公开读取待处理操作状态、或在模块中暴露可被抢先调用的公开入口函数。验证者可通过调整交易顺序提取 MEV。

---

## Details

**典型代码示例：未保护的 DEX 价格套利场景**

```move
public entry fun swap<X, Y>(
    account: &signer,
    amount_in: u64
) acquires Pool {
    let pool = borrow_global_mut<Pool<X, Y>>(@protocol);
    // 直接按当前池状态计算输出 - 无滑点保护
    let amount_out = (amount_in * pool.reserve_y) / (pool.reserve_x + amount_in);
    // 更新池状态
    pool.reserve_x = pool.reserve_x + amount_in;
    pool.reserve_y = pool.reserve_y - amount_out;
    // 转账操作
    coin::transfer<X>(account, @protocol, amount_in);
    coin::transfer<Y>(@protocol, signer::address_of(account), amount_out);
}
```

**【L2-L3】快速定位核心操作技巧：**
- **L2 跳读**：扫描 `public entry fun` 入口函数，关注参数中是否缺少 `min_amount_out`、`deadline`、`max_price` 等保护参数
- **L3 逐行读**：追踪状态读取点（`borrow_global`）到状态修改点（池储备量更新）的间隔，检查是否存在可被插入的交易窗口
- **关键模式**：`amount_out` 计算仅依赖链上当前状态，未要求用户提供预期值验证

**【L1-L4】快速定位保护机制技巧：**
- **L1 关键词扫描**：搜索 `assert!`、`min_`、`max_`、`deadline`、`slippage` 关键词，检查是否存在滑点保护
- **L2 跳读**：检查函数签名是否包含 `expected_output` 或 `price_limit` 参数
- **L3 逐行读**：验证 `assert!` 条件是否在状态修改后检查（后置检查有效），还是仅检查输入参数合法性（无效保护）
- **L4 跨模块追踪**：检查是否依赖外部 oracle 或时间戳进行交易有效性验证，追踪 `timestamp::now_seconds()` 的使用

## Classify

**漏洞研判标准：**
- **确认为高危漏洞**：入口函数接受金额/价格输入但无最小输出保护，且状态读取到修改之间无原子性保证，允许验证者通过交易重排序获取无风险套利
- **误报判定**：
  - 函数内部通过 `assert!(amount_out >= min_expected, ERR_SLIPPAGE)` 验证输出
  - 操作被包含在批量原子事务中（但 Move 的 entry 函数天然原子，需检查是否有跨交易依赖）
  - 协议设计为"荷兰式拍卖"等明确允许价格竞争的场景
- **代码异味**：存在滑点保护但阈值设置过于宽松（如 50% 滑点），虽不算漏洞但增加 MEV 风险

**关键研判点：**
- 用户预期是否可通过单一交易的重排被违背
- 协议是否在文档中明确告知存在的 MEV 风险
- 损失是否可被验证者无成本提取（区别于用户间的公平竞争）

## Low risk

**低风险场景判定：**
- **协议设计特性**：协议本身为链上订单簿模型（如限价单），用户主动设定价格且长期挂单，前置交易仅影响成交速度而非价格
- **金额门槛限制**：单笔交易对池状态影响 < 0.1%，即使被前置套利损失也在 gas 成本范围内，经济上不可行
- **时间锁机制**：交易需等待 N 个区块确认后才执行状态变更，验证者无法在单一区块内完成前置+受害者交易+套利的组合
- **白名单调用**：`public(friend)` 或 `public(script)` 限定只能通过可信合约调用，防止外部任意构造抢跑交易
- **链下签名验证**：虽然交易可见，但执行需链下授权签名，验证者无法伪造用户意图

**注意**：以上场景需结合实际 gas 成本、池流动性、区块时间综合评估，不可机械套用

## 审计专业技巧

### 一、状态读写间隔分析（State-Read-Write Gap）

**核心原则**：识别用户可感知的数据点（价格、余额、费率）在读取与使用之间的时间窗口。

**实践技巧**：

1. **时间序列追踪**
   - 从 entry 函数入口追踪每一个 `borrow_global`、`borrow_global_mut` 位置
   - 标记状态读取顺序和修改顺序，绘制读写依赖图
   - 检查用户可控参数（amount_in）与状态计算之间是否存在"隐含的中间态依赖"
   - **案例**：Flash Loan 中的价格读取必须在贷款后立即检查，若在转账后检查则窗口存在

2. **参数验证时序**
   - 前置检查（Pre-check）：在任何状态修改前验证用户参数的合法性（如 amount > 0）
   - 后置检查（Post-check）：在状态修改后验证结果是否符合用户预期（如 amount_out >= min_out）
   - **危险模式**：仅做前置检查，状态修改后不再验证，给 MEV 留出空隙
   - **安全模式**：后置检查必须使用用户在交易开始时提供的预期值，而非当前池状态

3. **隐含共享状态识别**
   - 扫描全局资源 `Resource` 结构，检查是否存在多个操作共享的可修改字段
   - 关注 fee_rate、slippage_tolerance 等可能在交易执行过程中被修改的参数
   - **真实案例**：某 DEX 的 Pool 同时存储当前流动性和待结算费用，前置交易修改费用池可改变后续交易费率

### 二、真实漏洞与误报区分

**真实漏洞特征**：

1. **直接可提取价值 (DPV - Directly Profitable Value)**
   ```move
   // 真实漏洞示例：价格完全由前一个交易决定，无保护
   let price = pool.reserve_y / pool.reserve_x;
   let output = amount_in * price;  // 攻击者可通过前置交易操纵 pool 状态
   assert!(output > 0);  // 仅检查非零，无最小值限制
   ```
   - 验证者可无风险地获利：先做套利交易推高价格 → 用户高价成交 → 验证者获利
   - **确认方法**：计算前置+受害+套利三部分交易，验证每一步都盈利

2. **条件竞争 (Race Condition)**
   - 多个用户的交易依赖同一个全局状态，且修改顺序会显著改变结果
   - **示例**：Staking 合约中，第一个用户锁定的额度由下一个用户的存款金额决定
   - **确认方法**：模拟两种交易顺序，计算两个用户最终收益的差异

3. **金额计算漏洞 (Arithmetic MEV)**
   ```move
   // 舍入误差可被提取
   let fee = (amount * fee_rate + 999) / 1000;  // 向上舍入
   let user_gets = amount - fee;
   // 攻击者通过调整交易顺序改变舍入方向
   ```
   - **确认方法**：在多个舍入步骤上检查，累积误差是否显著

**常见误报**：

1. **误报：AMM 自然滑点**
   ```move
   // 常被误认为漏洞，实际为 AMM 特性
   let output = (amount_in * pool.reserve_y) / (pool.reserve_x + amount_in);
   // 大额交易因公式而产生滑点，这是正常的 AMM 行为，不是 MEV
   ```
   - **区分要点**：用户可在提交前预计算输出；协议允许通过 min_out 参数防护
   - **不是漏洞**：因为损失来自 AMM 设计，而非验证者操纵

2. **误报：跨区块时间锁**
   ```move
   // 正确的时间锁设计
   assert!(now_seconds() >= scheduled_time, ERR_TOO_EARLY);
   execute_action();
   ```
   - **确认点**：检查 scheduled_time 是否在交易创建时就已固定（不可变）
   - **如果可修改**（如通过 admin 函数）则不构成保护

3. **误报：已有足够的滑点保护**
   ```move
   // 这不是误报，是真实保护
   let min_out = calculate_minimum(amount_in, pool, max_slippage_5_percent);
   let actual_out = swap_internal(amount_in);
   assert!(actual_out >= min_out, ERR_SLIPPAGE);
   ```
   - **验证方法**：追踪 min_out 的计算来源，确保使用的状态在用户签名时就确定了

### 三、审计工作流

**第一步：快速扫描（5 分钟）**
- 搜索所有 `public entry fun` 和相关转账操作
- 标记是否有 `min_`/`max_` 参数，deadline 检查
- 初步分类：明显安全/明显危险/需要深入分析

**第二步：状态图绘制（15 分钟）**
- 为每个关键函数绘制状态读写序列图
- 标注用户可控的输入点和验证点
- 识别所有全局资源的修改

**第三步：攻击情景演练（10 分钟）**
- 假设攻击者能任意排序交易，尝试构造 3 层嵌套交易：
  - Layer 1（前置）：修改全局状态以有利于攻击者
  - Layer 2（受害者）：用户正常交易，受到 Layer 1 影响
  - Layer 3（套利）：攻击者恢复状态或获利
- 若能构造出无风险获利的序列 → 确认漏洞

**第四步：经济可行性验证**
- 计算前置交易的 gas 成本 + 套利交易的 gas 成本
- 对比可提取的 MEV 价值
- 若 gas 成本 > MEV 价值 × 0.7，该漏洞在实际中不可行

### 四、常见审计陷阱与避坑

| 陷阱 | 错误判断 | 正确做法 |
|------|--------|--------|
| 过度信任 `assert!` | 见到 assert 就认为安全 | 检查 assert 条件是否依赖用户时间点的状态 |
| 忽视跨交易依赖 | 单交易原子不等于无 MEV | 检查多笔交易是否共享可修改资源 |
| 混淆权限与保护 | `public(friend)` 限制权限，等同于 MEV 保护 | 友权限仅防止外部调用，不能阻止验证者排序 |
| 低估舍入误差 | 认为小数点以下的差异可忽略 | 在大规模操作下累积，可达可利用级别 |
| 忽视 oracle 风险 | 使用链上 oracle 就认为价格可信 | Oracle 本身可能被操纵或有延迟，需验证 |

### 五、文档与证据收集

**编写漏洞报告的关键点**：

1. **包含完整攻击链**：不能仅说"存在滑点"，必须展示攻击者如何获利
2. **量化经济影响**：计算典型场景下可提取的 MEV 规模
3. **验证修复方案**：提出修复建议后，需确认修复在理论和实现上都有效
4. **区分严重程度**：
   - 关键(Critical)：不需前置条件，任意验证者都能获利
   - 高(High)：需要特定市场条件（如大额流动性）
   - 中(Medium)：获利成本接近收益，但仍可行
   - 低(Low)：实际经济中不可行（gas > MEV）
