# Java｜Thymeleaf 未转义表达式导致 XSS

## 基本信息

- **难度等级：** ★★★☆☆ (中级)
- **审计时间：** 15-30分钟（单个漏洞点）
- **先决知识：** Thymeleaf 模板引擎、表达式语言、安全标签、Spring Boot 集成
- **复杂度评估：**
  - 简单场景（单个模板）：15-20分钟
  - 复杂场景（多个模板、自定义方言）：30-45分钟

## 🚀 30秒快速清单

- [ ] 模板中是否使用 `th:utext` 或 `[(…)]` 等不转义的表达式？
- [ ] 这些表达式的值是否来自用户输入或不可信数据源？
- [ ] 是否使用了 `th:text` 或 `[(...)]` 等自动转义的标签替代？
- [ ] 是否为自定义的 Thymeleaf 方言和函数添加了转义机制？
- [ ] 是否存在在 Thymeleaf 表达式中嵌入不安全的 Spring EL？

**判断：** 如果第 1-2 个问题打勾且第 3 个未打勾，需要进行 L3+ 深度分析

## Details

### 漏洞成因
Thymeleaf 默认使用 `th:text`、`[[...]]` 输出转义后的文本。但若使用 `th:utext`、`[(...)]` 或 `th:attr="data=${...}"` 等未转义表达式，就会将用户输入直接注入 HTML，导致 XSS。也有开发者为了渲染富文本显式关闭 `th:inline` 以及 `th:utext`，未进行净化。

### 代码示例

**易受攻击的代码：**
```html
<p th:utext="${comment.content}"></p>
```

**安全示例：**
```html
<p th:text="${comment.content}"></p>
<!-- 如需富文本，先在后端使用 Jsoup 白名单净化 -->
```

### 快速定位技巧

#### 核心操作定位（审计等级：L1-L2）
**关键词扫描：** `th:utext`, `th:inline="javascript"`, `[(...)]`, `th:attr`, `th:attrappend`, `th:with`。

**定位步骤：**
1. 搜索未转义表达式；
2. 跳读（L2）确认变量来源是否可控；
3. 检查模板是否设置 `th:inline="javascript"` 并拼接变量到脚本。

#### 保护机制定位（审计等级：L2-L3）
**检查是否存在：**
- 使用 `th:text`、`[[...]]` 默认转义；
- 后端 Jsoup、OWASP Java HTML Sanitizer 白名单过滤；
- 针对脚本上下文使用 `JavaScriptEscape`；
- 统一的输出编码工具类。

**定位技巧：**
- 逐行读（L3）确认富文本字段在后端净化；
- 跨模块追踪（L4）模板包含、布局是否传递未净化数据。

#### 审计等级标注
| 场景 | 审计等级 | 说明 |
|------|----------|------|
| 全部使用转义表达式 | **L0（快速跳过）** | 风险低 |
| 少量使用 `th:utext` 并有净化 | **L2（跳读）** | 核实净化策略 |
| 广泛使用未转义表达式 | **L3（逐行读）** | 高风险 |
| 多模板继承链路复杂 | **L4（跨模块追踪）** | 需完整分析 |

## Classify

### 研判标准

#### 确认漏洞
1. 模板使用未转义表达式输出用户可控数据；
2. 缺乏净化或限制；
3. 能构造 payload 执行脚本。

#### 误报
1. 数据来自受控后台或已白名单过滤；
2. 未转义表达式仅用于常量；
3. 页面仅面向内网并不可被攻击者影响。

#### 代码异味
1. 在脚本、属性中直接插入 `${}` 变量；
2. 使用 `th:inline="javascript"` 拼接 JSON 字符串；
3. 无统一富文本处理策略。

## Low risk

### 低风险评级场景

#### 1. 富文本仅由管理员维护
- 攻击面小，可暂列低风险。

#### 2. 页面部署在隔离环境
- 仍建议净化，但优先级较低。

#### 3. 已规划引入白名单净化服务
- 明确计划，可暂降级并跟踪执行。

### 风险降级条件总结
| 条件 | 降级理由 | 建议优先级 |
|------|----------|------------|
| 受控来源 | 攻击面小 | 中 |
| 隔离环境 | 影响有限 | 低 |
| 改造计划明确 | 可暂缓 | 低 |
