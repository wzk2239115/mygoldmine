# Go - 微服务编排状态不一致

## 成因
分布式事务场景下，多服务状态变更缺乏协调机制，部分服务成功部分失败时未实现补偿或回滚，导致数据不一致。

## Details

**核心场景识别：**
- 编排模式：Saga、两阶段提交、事件驱动
- 关键代码：跨服务调用链路中的状态更新操作
- 失败边界：error 处理分支、超时、网络异常

**代码示例：**

```go
// 典型存在问题的编排代码
func CreateOrder(ctx context.Context, req *OrderRequest) error {
    // 服务A：扣减库存
    if err := inventoryService.Deduct(req.ProductID, req.Qty); err != nil {
        return err  // ✓ 此处失败无副作用
    }
    
    // 服务B：创建订单
    orderID, err := orderService.Create(req)
    if err != nil {
        return err  // ✗ 库存已扣减，但订单未创建，状态不一致
    }
    
    // 服务C：扣减余额
    if err := paymentService.Deduct(req.UserID, req.Amount); err != nil {
        return err  // ✗ 库存已扣、订单已创建，但支付失败
    }
    
    return nil
}
```

**审计定位技巧：**

**[L1] 关键词快速扫描：**
- 函数名：`Orchestrate`, `Saga`, `Compensate`, `Rollback`, `Transaction`
- 多服务调用：连续多个 `xxxService.Xxx()` 调用
- 失败处理：`defer`, `rollback`, `compensate`, `undo`

**[L3] 状态操作逐行审计：**
1. 定位编排入口函数（通常在 handler、service 层）
2. 追踪跨服务调用序列，标记每个状态变更点
3. 检查每个变更点后的 error 分支：
   - 是否有回滚前序操作？
   - 是否记录补偿任务？
   - 是否使用事务上下文？

**[L4] 保护机制跨模块追踪：**
- 查找 Saga 协调器实现：`saga.Coordinator`, `workflow.Engine`
- 检查补偿函数注册：`RegisterCompensation`, `WithRollback`
- 追踪事务上下文传递：`context.WithValue`, `TransactionContext`
- 审计幂等性设计：去重表、版本号、状态机校验

**保护机制识别：**
- ✓ Saga 模式：每步操作注册对应补偿函数
- ✓ 两阶段提交：prepare → commit/rollback
- ✓ 事件溯源：通过事件重建状态，支持回滚
- ✓ 分布式事务框架：DTM、Seata 等
- ✓ 最终一致性：异步补偿队列 + 定时对账

## Classify

**确认为漏洞：**
- 存在多步状态变更，中间步骤失败时直接返回 error 未回滚
- 无补偿机制且无定时对账任务
- 关键业务场景（支付、订单、库存、积分等资产相关）
- 无分布式锁且存在并发修改可能

**判定为误报：**
- 已实现完整的补偿函数并正确调用（通过 defer 或手动回滚）
- 使用成熟分布式事务框架且配置正确
- 采用最终一致性模型，有独立对账补偿服务
- 操作幂等且有定时任务兜底修复
- 非关键路径，数据不一致可人工介入修复

**代码异味：**
- 有补偿机制但实现不完整（如只回滚部分操作）
- 依赖人工运维介入修复，缺乏自动化
- 补偿逻辑与正向逻辑耦合度高，难以维护
- 错误处理路径覆盖不全（未考虑超时、panic 等场景）

## Low risk

**以下场景可降级为低风险：**

1. **非资产类业务**：日志记录、统计分析等最终一致即可的场景
2. **用户可重试**：失败后用户可重新发起操作，系统自动去重
3. **影响范围受控**：
   - 单用户场景，不涉及多方资产转移
   - 数据可通过界面人工修正且修正成本低
4. **已有监控告警**：
   - 实时监控数据不一致
   - 定时对账任务（间隔 < 1小时）
   - 异常自动触发人工审核
5. **业务容错设计**：
   - 超卖场景有冗余库存
   - 金额差异在可接受阈值内（如 < 0.01元）
6. **外部约束保护**：
   - 数据库外键约束防止孤儿数据
   - 上游系统有防重校验
   - 下游系统能处理脏数据

**风险降级条件（需同时满足）：**
- 发生概率低（如仅在极端网络抖动时触发）
- 影响金额/数据量小
- 有自动或半自动修复手段
