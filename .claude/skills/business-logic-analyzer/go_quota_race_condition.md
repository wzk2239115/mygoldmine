# Go 配额竞态条件漏洞（Quota Race Condition）

**漏洞成因**：配额扣减、库存更新、余额操作等资源消耗场景，在并发请求下因缺乏原子性保护，导致"检查-使用"时间窗（TOCTOU）被利用，造成超限消费、负库存、重复扣减等逻辑错误。

---

## Details

**核心代码特征**：
```go
// 典型漏洞模式
quota := getUserQuota(uid)
if quota >= needed {           // 第一步：检查
    doOperation()              // 第二步：使用
    updateQuota(uid, -needed)  // 第三步：扣减
}
```

**审计定位技巧**：

**L1 - 关键词扫描**：
- 快速扫描：`quota`、`stock`、`balance`、`limit`、`remain`、`available`、`count`
- 数据库操作：`UPDATE ... SET count = count - ?`、`SELECT ... FOR UPDATE`
- 并发关键字：`sync.Mutex`、`atomic.Add`、`redis.Incr`、`db.Transaction`

**L3 - 逐行审计（核心操作）**：
1. **定位资源检查点**：找到 `if quota/stock >= needed` 或 `SELECT` 查询
2. **追踪消耗点**：确认实际扣减位置（可能在另一个函数/goroutine）
3. **测量时间窗**：检查-扣减之间的代码行数（>5行高风险）

**L4 - 跨模块追踪（保护机制）**：
- **悲观锁**：`SELECT ... FOR UPDATE` + 事务包裹、`SETNX` 分布式锁
- **乐观锁**：`UPDATE ... WHERE version = old_version`、CAS 操作
- **原子操作**：`atomic.AddInt64`、Redis `INCRBY`、数据库自增字段
- **队列化**：所有请求串行化到 channel 或消息队列

**危险信号**（审计等级提升至 L3）：
- 跨越 HTTP 请求边界的检查-扣减
- 在循环中批量处理配额但无锁
- 异步 goroutine 中更新配额
- 使用 `time.Sleep()` 模拟并发测试时发现问题

---

## Classify

### ✅ 确认漏洞
- **读后写分离**：配额查询与更新不在同一原子操作（如读缓存判断，写数据库扣减）
- **裸写模式**：`UPDATE quota SET value = value - ?` 无 WHERE 条件校验剩余值
- **跨事务边界**：`db.Query()` 查询后，另一个 `db.Exec()` 更新，中间无锁
- **缓存不一致**：先扣 Redis 缓存，稍后异步扣 MySQL，中间窗口可被利用

### ⚠️ 误报/需深入确认
- **已有数据库约束**：字段定义 `UNSIGNED` 或 `CHECK (quota >= 0)` 可拦截负值（但仍可能超卖）
- **单线程模型**：整个服务是单 goroutine 处理（罕见，需确认无 `go func()` 调用）
- **幂等 token**：虽然有竞态，但业务层用 `request_id` 去重（需确认去重实现本身无竞态）

### 🔍 代码异味
- **注释标记 TODO**：代码中有 `// TODO: add lock here` 但未实施
- **测试覆盖不足**：无并发压测用例（`go test -race` 未启用）
- **混合保护**：部分路径有锁，部分无锁（说明开发者意识到问题但未完全修复）

---

## Low Risk

以下场景可评为低风险（但仍需标注并建议修复）：

1. **低价值资源**：操作的是积分、经验值等容错资源，超限对业务影响小
2. **低并发场景**：内部管理后台、定时任务触发，实际 QPS < 1
3. **自动修正机制**：系统每日对账并自动回滚异常消费（需确认对账逻辑可靠）
4. **金额上限兜底**：单笔扣减 <= $1，账户余额有硬上限（但需关注累积效应）
5. **已知短期下线**：该功能计划 2 周内重构/下线

**风险升级条件**（低风险→高风险）：
- 资源涉及金钱、付费配额、限量商品
- 日活 > 1000 或历史出现过用户投诉
- 可通过自动化工具（并发脚本）稳定复现
