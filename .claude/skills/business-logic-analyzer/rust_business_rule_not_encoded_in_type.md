# Rust - 业务规则未在类型系统中编码

**漏洞类型**：业务规则未在类型系统中编码（如 newtype、trait bound），依赖运行时检查

---

## Details

**审计等级**：L3-L4（逐行读+跨模块追踪）

### 典型代码模式

```rust
// 反例：纯粹依赖运行时检查
fn process_payment(amount: f64, user_id: u64) -> Result<()> {
    if amount <= 0.0 {  // 运行时检查
        return Err("invalid amount");
    }
    if amount > 10000.0 {  // 业务规则散落各处
        return Err("exceeds limit");
    }
    charge_user(user_id, amount)
}

// 反例：状态转换未类型化
struct Order {
    status: String,  // "pending" | "paid" | "shipped"
    total: f64
}

impl Order {
    fn ship(&mut self) -> Result<()> {
        if self.status != "paid" {  // 手动检查状态
            return Err("not paid");
        }
        self.status = "shipped".to_string();
        Ok(())
    }
}
```

### 快速定位技巧

**核心操作定位**：
- 搜索 `impl` 块中的 `pub fn`，重点关注涉及状态变更、金额计算、权限判断的方法
- 查找 `String`、`u64`、`f64` 等原始类型直接用于业务概念（如状态、金额、ID）
- 跟踪跨函数的参数传递，观察是否缺少类型约束

**保护机制定位**：
- 搜索 `if`、`match`、`assert!`、`debug_assert!` 等运行时检查
- 查找验证逻辑散落位置：构造函数、setter、业务方法开头
- 检查是否使用 newtype 模式（`struct Wrapper(InnerType)`）或 trait bound
- 观察是否利用类型状态模式（typestate pattern）编码状态机

### 审计重点

1. **原始类型滥用** (L3)：业务概念用 `String`、`i32` 等表示，无类型级约束
2. **状态机未类型化** (L4)：状态用字符串/枚举表示，转换规则靠手动检查
3. **不变量散落** (L4)：同一业务规则在多处重复验证，易遗漏
4. **跨边界传递** (L3)：从外部接收原始类型，仅在使用点做临时检查

---

## Classify

### 确认为漏洞

1. **绕过验证路径**：存在多个入口函数，仅部分路径包含业务规则检查
   - 例：`new` 做了验证，但 `from_raw` 直接构造绕过
2. **状态转换逻辑错误**：缺少类型保护的状态机允许非法转换
   - 例：订单可从 "shipped" 跳回 "pending"
3. **跨模块不一致**：不同模块对同一业务规则的运行时检查逻辑不同
   - 例：模块A限额 10000，模块B限额 50000
4. **序列化/反序列化漏洞**：通过 serde 绕过构造函数的验证逻辑

### 误报

1. **内部辅助函数**：仅在模块内部调用，外部已有类型保护
2. **已有 trait bound 约束**：虽用原始类型，但通过泛型约束限制了输入范围
3. **性能敏感热路径**：有明确注释说明为性能优化故意降低类型安全

### 代码异味

1. **过度工程化边界**：非关键路径使用过于复杂的类型编码
2. **验证冗余**：类型已保证不变量，仍进行运行时检查（浪费但无害）

---

## Low Risk

1. **单一调用点**：业务规则仅在唯一入口使用，运行时检查覆盖全面
2. **只读数据结构**：对象构造后不可变，构造时已完成验证
3. **内部工具/测试代码**：非生产代码路径
4. **明确的文档约定**：有清晰注释说明调用方责任，且调用方可控（非公开API）
5. **数值上下界宽松**：业务规则非强制性（如建议性限额），违反不造成实质损失
6. **已有上层防护**：虽然该函数未类型化，但调用链上层已用 newtype 封装
7. **Audit/Logging场景**：日志或监控代码，不影响关键业务逻辑
