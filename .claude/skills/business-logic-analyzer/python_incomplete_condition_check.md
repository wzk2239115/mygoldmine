# Python 条件分支判断逻辑覆盖不完整

**漏洞成因**：条件分支判断缺少对边界值、空值、异常类型的处理，导致预期的校验逻辑被绕过；或多条件组合时使用错误的逻辑运算符（`and`/`or`）、判断顺序不当、提前返回，使某些路径跳过关键校验，引发越权、数据泄露、状态异常等业务逻辑漏洞。

---

## Details

**核心代码特征**：
```python
# 典型漏洞模式 1：未处理 None 边界情况
def check_permission(user_role):
    if user_role == 'admin':
        return True
    # 缺失 else/elif：user_role 为 None 或空字符串时返回 None，某些框架视为 True
    
# 典型漏洞模式 2：逻辑运算符误用
def validate_payment(amount, user_verified):
    if amount > 0 or user_verified:  # 应为 and，导致未认证用户也可通过
        process_payment(amount)

# 典型漏洞模式 3：错误的提前返回
def authorize_action(user):
    if user.is_active:
        return True
    if user.role == 'admin':  # 永远无法到达：管理员未激活时被拦截
        return True
    return False

# 典型漏洞模式 4：类型混淆绕过
def check_age(age):
    if age >= 18:  # age='18' 字符串比较时绕过整数校验
        grant_access()
```

```python
# 典型漏洞模式 5：异常路径缺失 finally 或补偿
def update_balance(user_id, amount):
    lock = acquire_lock(user_id)
    try:
        balance = get_balance(user_id)
        if balance >= amount:
            deduct_balance(user_id, amount)
    except DBError:
        return  # 缺失 finally：异常时锁未释放，导致死锁
```

```python
# 典型漏洞模式 6：空集合绕过校验
def validate_permissions(required_permissions):
    if required_permissions:  # 空列表 [] 时为 False，跳过校验直接放行
        if not user.has_permissions(required_permissions):
            raise Unauthorized
    grant_access()
```

**快速定位核心操作**：

**L1 - 关键词扫描**：
- **判断关键字**：`if`、`elif`、`else`、`and`、`or`、`not`、`is None`、`== None`
- **校验函数**：`validate`、`check`、`verify`、`authorize`、`is_allowed`、`has_permission`
- **边界值处理**：`if not`、`if ... is None`、`if len()`, `bool()`
- **异常处理**：`try/except` 块中缺少 `else` 或 `finally`

**L2 - 跳读（高危结构）**：
- **无 else 分支**：关键校验函数中 `if` 后无明确返回/抛出异常
- **复杂逻辑运算**：三个及以上条件组合的 `and/or`，检查括号和优先级
- **提前返回模式**：多个 `if ... return` 顺序排列，检查后置条件是否可达
- **类型转换前校验**：`int()`、`float()` 前是否检查类型和格式

**L3 - 逐行审计（追踪路径）**：
- **绘制决策树**：列出所有输入组合，检查是否存在"预期拒绝但实际放行"的路径
- **None 与 False 等价性**：确认 `if variable` 与 `if variable is not None` 的差异影响
- **短路求值陷阱**：`A and B` 中 A 为 False 时 B 不执行，检查副作用
- **异常传播链**：上游抛出异常，下游是否正确捕获或传播

**L4 - 跨模块追踪（保护机制）**：
- **框架级拦截器**：Decorator（`@login_required`、`@permission_required`）是否覆盖所有路径
- **全局异常处理**：`try/except Exception` 是否掩盖了校验失败异常
- **中间件链路**：Flask/Django middleware 中的权限检查是否可被绕过
- **多层校验一致性**：前置校验通过但后续流程是否有重复校验或不一致逻辑

**快速定位保护机制**：
- **显式返回值**：所有分支明确返回 `True/False` 或抛出异常
- **类型提示+运行时检查**：`isinstance()`、`type()` 结合类型注解
- **断言验证**：关键分支后 `assert` 确认预期状态
- **Pydantic/Marshmallow**：使用数据验证库强制类型和范围
- **白名单机制**：使用 `in [允许值列表]` 而非黑名单排除

**危险信号（审计等级提升至 L3-L4）**：
- 权限校验函数中存在 `pass` 或仅打印日志但不中断执行
- 多个 `if` 无 `else`，最后无兜底 `raise` 或 `return False`
- 使用 `eval()`、`exec()` 处理用户输入前的条件判断
- 嵌套 3 层以上的条件判断，逻辑复杂度高
- 异常捕获后 `continue` 或 `pass`，未记录或告警

### 审计等级判定

| 等级 | 场景 | 审计策略 |
|------|------|----------|
| **L0** | 纯数据展示、日志记录、无业务决策影响的条件 | 跳过 |
| **L1** | 使用成熟验证库（Pydantic）且有单元测试覆盖边界 | 关键词确认是否覆盖 None/空/异常类型 |
| **L2** | 简单二分支判断，有明确 `else` 和异常处理 | 跳读确认逻辑运算符正确性 |
| **L3** | 权限/金额/状态判断，多条件组合或提前返回模式 | 逐行绘制决策树，验证所有路径 |
| **L4** | 跨函数/跨模块的条件依赖，或涉及并发/异步状态 | 追踪调用链，检查状态一致性和竞态 |

## Classify

### ✅ 确认漏洞

**条件覆盖不完整**：
- 关键校验函数缺少 `else` 分支，部分输入路径返回 `None`（被框架视为放行）
- 未处理 `None`、空字符串、空列表等边界值，导致校验被跳过
- 多条件判断使用错误的运算符（如应用 `and` 却使用 `or`）

**类型混淆**：
- 字符串与数字比较（`'18' >= 18` 在 Python 2 通过）
- `bool()` 转换未考虑 `0`、`''`、`[]`、`{}` 为 `False` 的影响
- 使用 `==` 比较可能为 `None` 的对象，应使用 `is None`

**逻辑顺序错误**：
- 宽松条件在前，严格条件在后，导致后者永不可达
- `return` 或 `raise` 提前终止流程，后续安全检查被跳过

**异常处理缺陷**：
- `try/except` 捕获过宽（`Exception`），掩盖校验失败
- 异常处理中缺少资源释放（锁、文件句柄、数据库连接）
- 仅记录日志但未中断执行，继续处理非法数据

**实际可利用特征**：
- 通过传入 `None` 或空值绕过付费校验
- 构造边界值（如负数、超长字符串）触发未处理分支
- 并发请求命中时序窗口，利用状态检查与状态应用分离

### ⚠️ 误报排除

- ✗ 函数仅用于内部日志/监控，不影响业务决策流程
- ✗ 上游中间件已完成校验，当前函数仅处理已授权数据（需确认中间件覆盖所有路径）
- ✗ 类型提示 + MyPy 静态检查，且有完善的单元测试覆盖边界（需确认 CI 强制执行）
- ✗ 使用 Pydantic 等验证库，边界情况已由库处理（需确认模型定义完整）
- ✗ 故意的宽松逻辑（如试用期允许部分功能无限制），有明确业务需求文档

### 🔍 代码异味

- △ 注释说明"待补充异常处理"但未实施
- △ 复杂的嵌套条件，圈复杂度 >10，难以穷举所有路径
- △ 使用 `if not variable` 但未区分 `None`、`False`、`0`、`''` 的语义差异
- △ 异常捕获后仅 `print()` 或 `logging.warning()`，未阻断流程
- △ 不同代码路径对相同输入的处理逻辑不一致（说明缺少统一校验层）
- △ Git blame 显示条件判断频繁修改（说明业务逻辑不清晰或补丁式修复）

## Low Risk

### 给予低风险评级的场景

1. **仅影响用户体验**
   - 条件判断错误导致错误提示不准确，但不影响实际权限
   - UI 展示逻辑错误（如推荐算法分支），无金额/权限影响

2. **下游有兜底校验**
   - 数据库层有唯一约束或 CHECK 约束
   - 下游支付网关/第三方系统会二次验证
   - 审批工作流中有人工复核环节

3. **攻击条件苛刻**
   - 需同时满足多个低概率条件（如特定时间+特定用户等级+特定商品组合）
   - 需要内部知识（如隐藏的状态码、特殊字段名）

4. **影响范围受限**
   - 测试环境或沙箱环境（需明确确认）
   - 仅影响已停用功能或即将下线的旧版本接口
   - 只能绕过非关键限制（如验证码次数限制，但有 IP 级别风控）

5. **监控与恢复机制**
   - 异常路径触发实时告警，SOC 团队快速响应
   - 有数据对账机制，异常操作可追溯和回滚
   - 业务规则引擎有全局规则二次验证

6. **已计划修复**
   - 技术债已记录在 issue tracker，排期在下个迭代
   - 新版本采用状态机模式重构，旧版本流量 <5%

**评级建议**：即使低风险，应在报告中详细说明可能的绕过路径，并提供修复示例（如添加 `else` 分支、类型检查、单元测试用例），避免在业务扩展时风险升级。
