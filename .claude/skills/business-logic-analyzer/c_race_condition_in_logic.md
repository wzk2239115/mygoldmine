# C/C++ 并发竞态条件业务逻辑漏洞

## Details

### 漏洞成因
多线程/多进程环境下，共享资源的检查(TOCTOU)与使用存在时间窗口，业务状态更新非原子性，导致重复处理、超额扣减、状态不一致。

### 代码示例

```c
// 典型竞态：余额检查与扣减分离
if (user->balance >= amount) {        // T1: 检查通过
    sleep(1);                          // 时间窗口
    user->balance -= amount;           // T2: 扣减（可能被多次执行）
    db_commit(user);
}
```

```cpp
// 状态机竞态：订单状态转换未加锁
if (order.status == PENDING) {
    order.status = PROCESSING;         // 多线程可能同时执行
    allocate_inventory(order);
}
```

```c
// 文件操作TOCTOU
if (access(file, W_OK) == 0) {        // 检查权限
    // 时间窗口：文件可能被替换为符号链接
    fd = open(file, O_WRONLY);         // 使用时已是不同文件
    write(fd, data, len);
}
```

### 快速定位核心操作
- **关键词扫描**：`pthread_`, `std::thread`, `fork()`, `shared_ptr`, `static` 全局变量
- **TOCTOU模式**：`if (check()) { use(); }` 结构，中间无锁保护
- **资源检查点**：余额/库存/配额检查 → 搜索 `balance`, `stock`, `quota`, `limit`, `available`
- **状态转换**：`status =`, `state =` 后跟业务逻辑 → 检查是否原子操作
- **文件操作序列**：`access/stat` → `open/unlink` 组合

### 快速定位保护机制
- **互斥锁**：`pthread_mutex_lock`, `std::mutex`, `std::lock_guard`
- **原子操作**：`std::atomic`, `__sync_*`, `__atomic_*`, `compare_and_swap`
- **数据库锁**：`SELECT ... FOR UPDATE`, `BEGIN TRANSACTION`
- **无锁**：检查是否使用 CAS 循环或乐观锁版本号
- **进程锁**：`flock()`, `fcntl()` 文件锁，`semaphore`

### 审计等级判定

| 等级 | 场景 | 审计策略 |
|------|------|----------|
| **L0** | 单线程程序、无共享状态 | 跳过 |
| **L1** | 使用了完整互斥保护的代码 | 关键词扫描确认锁范围覆盖 |
| **L2** | 简单多线程但无业务关键操作 | 跳读检查是否有隐藏共享资源 |
| **L3** | 存在资源检查与使用分离 | 逐行追踪锁粒度是否覆盖完整事务 |
| **L4** | 分布式状态、跨服务调用、数据库+内存双状态 | 跨模块追踪一致性保证机制 |

## Classify

### 确认漏洞（需满足三要素）
1. **共享资源**：多线程/进程可访问同一变量/文件/数据库记录
2. **检查-使用分离**：验证与操作之间存在时间窗口
3. **业务影响**：可导致超额扣款、重复下单、权限绕过、数据损坏

**典型漏洞特征**：
- 余额/积分/库存检查后无锁直接扣减
- 订单状态判断与更新非原子，可重复提交
- 文件权限检查与实际操作分离（TOCTOU）
- `static`/全局计数器无原子保护
- 回调/异步任务中状态已变化但未重新验证

### 误报排除
- ✗ 只读操作的竞态（脏读但不影响数据一致性）
- ✗ 本地栈变量（非共享）
- ✗ 已有完整锁保护且锁粒度覆盖整个业务事务
- ✗ 使用原子操作且正确处理 CAS 失败重试
- ✗ 数据库事务隔离级别（Serializable）已保证

### 代码异味（需进一步验证）
- △ 锁粒度过大（性能问题非安全问题）
- △ 锁粒度过小但业务逻辑不完整（需验证时间窗口是否可利用）
- △ 双重检查锁模式（DCL）实现不正确但实际竞态概率极低
- △ 使用 `volatile` 而非原子操作（可见性不等于原子性）

## Low Risk

### 给予低风险评级的场景

1. **竞态窗口极短且无法稳定触发**
   - 单机内存操作，时间窗口 < 1μs
   - 需要极高频并发（实际业务流量达不到）

2. **业务自带幂等性**
   - 操作本身可重复执行无副作用（如设置状态为同一值）
   - 最终一致性模型且有异步校验补偿机制

3. **影响范围有限**
   - 仅影响单用户自身数据（如重复发送通知）
   - 非金额/权限/核心业务数据
   - 状态不一致但不影响业务决策

4. **已有部分保护**
   - 数据库唯一索引约束（虽然业务层有竞态但数据库会拒绝）
   - 业务流程有人工审核环节
   - 金额差异监控告警能及时发现

5. **遗留代码且将被废弃**
   - 已计划重构/下线的模块
   - Beta功能且用户量极少

**评级建议**：即使为低风险，也应在报告中注明竞态条件存在，建议加固保护机制。
