# Move_ForgeableAccessToken - 可伪造的访问令牌

**Move**  
常出现在资源操作、能力（Capability）管理、模块初始化等业务逻辑实现中。权限凭证对象（如 AdminCap、OwnerCap）设计不当，未正确使用 `key` ability 或缺少 `store` ability 限制，导致权限对象可被复制、转移或伪造，从而使权限控制机制完全失效。

## Details

对应代码示例：
```move
// 脆弱示例：AdminCap 具有 copy 能力，可被任意复制
struct AdminCap has copy, drop {}

public fun privileged_operation(cap: &AdminCap) { /* ... */ }
```

**快速定位到核心操作的技巧（L2: 跳读）：**
- 搜索 `struct` + `Cap`、`struct` + `Authority`、`struct` + `Witness` 等权限凭证结构体定义
- 关注接受权限参数的函数签名，如 `fun admin_action(cap: &AdminCap)` 或 `fun mint(cap: &MintCap)`
- 定位 `public entry fun` 中需要权限验证的敏感操作（铸币、销毁、配置变更等）
- 检查模块初始化函数 `init` 或 `init_module` 中权限对象的创建和分发逻辑

**快速定位到保护机制的技巧（L3: 逐行读）：**
- 检查权限结构体的 abilities 声明：正确模式应仅具有 `key` 或 `key + store`，禁止 `copy` 和 `drop`
- 验证权限对象的创建点：应仅在 `init` 函数中创建一次，或通过严格的授权函数创建
- 追踪权限对象的转移路径：使用 `transfer::transfer` 转移到特定地址，而非 `transfer::public_transfer` 允许任意转移
- 确认无公开函数可返回或构造权限对象：搜索 `public fun` 返回权限类型的情况
- 检查是否使用了 Hot Potato 模式（仅有 `drop` 的结构体）或 Witness 模式（无 abilities 的类型）作为一次性验证凭证

## 审计专业技巧与真实案例区分

**实战审计清单（优先级排序）：**

1. **权限对象的 Ability 组合分析**
   - 最危险模式：`copy + drop` → 可任意复制和丢弃，权限控制完全失效
   - 高风险模式：`store + key` 但缺乏访问控制 → 可被存储在任意对象字段中，权限泄露
   - 安全模式：仅 `key` 或 `key + store` + 严格转移逻辑 → 权限受控转移
   - 正确模式：Witness（无 abilities）+ 一次性验证 → 本质上无法伪造

2. **初始化链路溯源**
   - 追踪权限对象的唯一创建点（通常在 `init` 或 `init_module`）
   - 验证创建后是否立即转移到受信地址或存储在 `0x1` 系统地址
   - 检查是否存在循环创建权限的隐藏路径（如升级函数、管理员权限可创建新权限）
   - 留意共享对象（`Shared` ability）中存储权限导致的并发漏洞

3. **函数签名与访问控制验证**
   - 对每个接受权限参数的 `entry` 函数，验证参数是否为 `&Cap` 引用（安全）vs `Cap` 值转移（风险）
   - 检查权限验证函数是否在每个关键操作前被调用，抗拒绝服务检查（如递归权限验证）
   - 搜索所有 `public` 和 `public(friend)` 函数，确认无法返回权限对象本身或其包含对象

4. **权限转移路径审计**
   - 区分 `transfer::transfer`（私有转移）vs `transfer::public_transfer`（公开转移）
   - 对公开转移场景，验证是否由业务逻辑函数（如 `grant_admin_to_address`）进行白名单验证
   - 检查权限对象是否可能被存储在共享对象后再被并发竞速提取

**真实漏洞 vs 误报的区分经验：**

| 代码特征 | 真实漏洞信号 | 误报风险 | 审计建议 |
|---------|----------|--------|--------|
| `struct AdminCap has copy, drop {}` | 权限可任意复制，100% 漏洞 | 无误报风险 | 立即标记严重漏洞 |
| `struct AdminCap has store, key {}` + `public fun new_admin()` | 权限可公开创建，确定漏洞 | 可能是初始化函数被误读 | 验证函数可访问性和入口点 |
| `struct AdminCap has key, store {}` + 仅内部转移函数 | 检查转移函数是否真的被限制，以及是否可通过升级绕过 | 设计正确但代码异味 | 审查所有导出的转移API，检查升级能力 |
| Witness 模式结构体 `struct Witness {}` 无 abilities | 需验证是否配合泛型参数正确使用 | 误报风险高：若未正确检查泛型约束，仍可伪造 | 追踪该证人在使用处的上下文，验证一次性消费逻辑 |
| Hot Potato `struct Request has drop {}` + 内部链式调用 | 需确认结构体确实无法逃逸到存储或外部上下文 | 高误报风险：若存储在 Table/Bag 中，Hot Potato 模式失效 | 搜索所有涉及该结构体的存储操作，确认仅在栈内传递 |
| 权限对象用作 Map Key | 需检查 Map 本身的访问权限和读取函数 | 常见误报：Map 只读不代表权限对象不可被提取 | 验证 Map 的读写权限是否与原权限一致 |

**常见误报场景与修正：**

1. **权限对象具有 `store` ability 就判定为漏洞** → 误报
   - 正确做法：验证所有接受该权限的函数是否都由模块内部严格管理，且转移目标经过验证
   - 案例：Sui 框架中很多正确的权限对象都具有 `store` ability，用于 CapHolder 模式

2. **发现公开函数返回权限类型的 Bag/Table 就判定为漏洞** → 可能误报
   - 正确做法：检查 Bag/Table 的写入权限是否受限，以及读取函数的访问控制
   - 案例：只读 Table 中存储权限摘要，实际权限对象仅在授权后通过受限函数转移

3. **权限未被 `0x1::package::claim_publish_rights` 风格的机制保护** → 不一定是漏洞
   - 正确做法：验证权限的创建和分发是否通过其他等价机制（如多签、时间锁、治理投票）保护
   - 案例：DeFi 项目的 AdminCap 可能被治理代币持有者集体控制，无需发布者权限

**审计工作流程推荐：**

```
1. 快速扫描：列出所有 Cap/Authority/Witness 结构体及其 ability 组合
   ↓
2. 风险分类：按 ability 组合分为高、中、低风险，跳过明显安全的（如纯 Witness）
   ↓
3. 链路溯源：对高风险权限追踪创建、初始化、转移、使用全链路
   ↓
4. 对标检查：与 Sui 标准库（token::Mint、coin::Mint）进行对比
   ↓
5. 升级风险：检查 package upgrade 是否可能绕过或重置权限
   ↓
6. 记录结论：区分真实漏洞、设计异味、误报，分别给出修复/优化建议
```

## Classify

**漏洞判定：**
- 权限结构体具有 `copy` ability，允许克隆权限凭证
- 权限结构体具有 `drop` ability 且缺少其他保护，导致权限可随意丢弃后重新获取
- 公开函数可构造或返回权限对象，任何人都能获取特权
- 权限对象使用 `public_transfer` 且未在业务逻辑层限制转移目标

**误报识别：**
- 权限对象虽有 `store` ability，但所有转移函数均由模块内部严格控制，且验证接收者身份
- 使用 Witness 模式（无 abilities）配合泛型参数进行一次性验证，虽无 `key` 但设计正确
- Hot Potato 模式结构体仅在函数调用链内传递，无法逃逸到外部上下文

**代码异味：**
- 权限对象具有 `store` ability 但未使用该特性（可优化为仅 `key`）
- 多层权限封装但内层权限可通过公开字段访问
- 权限验证分散在多个函数中，缺乏统一的权限检查抽象

## Low risk

- 权限对象虽可转移，但受到链外治理或多签机制约束，且合约本身不执行关键资产操作
- 权限仅控制非敏感配置参数（如 UI 展示字段、元数据），不影响资金安全或核心业务逻辑
- 权限对象在测试网或开发环境中设计宽松，但主网版本已修复（需明确标注环境差异）
- 项目明确文档说明权限分发机制为故意设计（如 DAO 治理代币类权限凭证），且符合业务需求
- 权限控制的功能已通过其他机制（如时间锁、金额限制、白名单）进行了充分的二次防护
