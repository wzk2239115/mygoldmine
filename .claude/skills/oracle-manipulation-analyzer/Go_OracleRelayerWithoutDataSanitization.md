**Go - 预言机中继器无数据清洗 (Oracle Relayer Without Data Sanitization)**  

常出现在 Cosmos SDK 或自定义区块链的链上验证逻辑、IBC 数据包中继、跨链预言机中继器等组件中。中继器转发链下数据到链上但未进行数据格式验证、边界检查或异常值过滤，导致恶意/异常数据污染链上状态。

## Details

**代码示例特征**：
```go
// 中继器接收链下数据并直接写入链上
func (k Keeper) RelayPriceData(ctx sdk.Context, msg *MsgRelayPrice) error {
    // ⚠️ 危险：直接使用外部数据，无验证
    k.SetPrice(ctx, msg.Symbol, msg.Price)
    return nil
}
```

**快速定位核心操作（L3:逐行读）**：
- 关注 `Keeper.RelayXXX`、`HandleOracleData`、`ProcessExternalMsg` 等中继处理函数
- 搜索 `ctx.SetXXX` 或状态写入操作前是否存在验证逻辑
- 检查 IBC `OnRecvPacket` 回调中数据包解析后的直接存储操作
- 追踪 `msg.Signer` 是否仅验证签名有效性而不验证数据合理性

**快速定位保护机制（L2:跳读）**：
- 查找 `ValidateBasic()`、`Validate()`、`SanitizeInput()` 等数据验证方法
- 扫描 `if price <= 0`、`if len(data) > MAX_SIZE`、`IsValidRange()` 等边界检查
- 寻找 `math.SafeXXX`、溢出保护、类型断言失败处理
- 检查是否有多签验证、时间戳新鲜度检查、数据源白名单校验

## Classify

**判定为高危漏洞**：
- 中继器直接将外部数据写入关键状态（价格、汇率、抵押率）且无任何验证
- 缺少数值范围校验导致极端值破坏经济模型（如价格为0或MAX_UINT64）
- 无时间戳或序列号检查，允许重放攻击或陈旧数据覆盖

**判定为误报**：
- 数据在链上模块的 `ValidateBasic` 或 `AnteHandler` 中已完成完整校验
- 中继器仅转发已通过链下共识且带多签证明的数据
- 链上存在独立的数据聚合模块对多源预言机数据进行中位数/加权平均处理

**判定为代码异味**：
- 仅缺少非关键字段验证（如描述文本长度未限制）
- 验证逻辑分散在多个模块导致审计难度大但实质完整
- 使用软性限制（警告日志）而非硬性拒绝，但不影响状态安全

## Audit Professional Techniques（审计专业技巧）

**数据流追踪技巧**：
1. **源头污染追踪**：从 `msg.Price` 或 `packet.Data` 的入口点开始，使用数据流图追踪每一步转换：
   - 标记哪些字段在哪个函数进行了验证
   - 记录所有涉及数据的存储操作（SetPrice、SetExchangeRate等）
   - 验证关键操作前是否完成了全量验证（不是分段验证）

2. **验证链完整性检查**：
   ```go
   // 检查点：验证链中是否存在逻辑断裂
   RelayPriceData()
     ↓ 是否调用 ValidatePrice()?
   SetPrice()
     ↓ 是否有溢出保护?
   更新余额/抵押率
     ↓ 是否存在范围检查?

   // 任何一步缺失都可能是真实漏洞
   ```

3. **边界条件组合测试**：
   - 单点测试：`price = 0`、`price = MaxUint64`、`price = -1`
   - 组合边界：`price = MaxUint64 + 1`（溢出）、`array.length = 0`（数组越界）
   - 时间边界：`timestamp = 0`、`timestamp = future + 1000 years`

**真实漏洞与误报区分的实战经验**：

**真实漏洞的8个标志**：
1. **直接状态污染**：数据不经验证直接写入影响共识的状态变量（确定性标志）
2. **经济学破坏**：价格可被设为0导致除法陷阱或清算级联失效（量化验证）
3. **无源头白名单**：任何钱包都能作为中继器发送价格数据且无事前许可检查
4. **无序列号防护**：缺少递增的 `nonce` 或 `sequence` 字段，允许重放旧数据覆盖新数据
5. **无时间戳新鲜度**：接受任意时间的数据，包括过时的历史数据
6. **批量操作无原子性**：多个字段更新之间存在间隙，中间状态可被外部观察利用
7. **单点依赖**：系统完全依赖单个中继器或预言机源，无冗余性
8. **无聚合或中位数**：直接使用原始数据而非多源聚合结果

**常见误报案例分析**：

| 初步发现 | 深度分析 | 判定结果 | 理由 |
|--------|--------|--------|------|
| RelayPrice无入参验证 | 但在Keeper.SetPrice内有ValidateBasic | 误报 | 验证只是位置不同，逻辑完整即可 |
| Price参数来自untrusted msg | 但msg.Signer经过Cosmos SDK AnteHandler多签验证 | 取决于签名者权限 | 如签名者是治理合约，则安全；如是任意地址，则真漏洞 |
| 没有MAX_PRICE检查 | 但聚合模块用中位数过滤极端值 | 误报 | 聚合层已隔离污染，单点污染风险可接受 |
| IBC packet未验证长度 | 但IBC协议本身限制了包大小为4KB | 误报 | 协议层已约束，应用层验证冗余但无害 |
| 允许负数价格 | 但后续操作全用 uint64 会panic | 取决于panic处理 | 若panic导致拜占庭行为，则为真漏洞；若只是tx失败，较低风险 |

**审计工作流优化**：

1. **快速分类法（30秒内）**：
   - 问题1：这个值写入的是否是共识关键状态？（非，则低风险）
   - 问题2：这个值是否经过至少一层验证？（是，则继续深入）
   - 问题3：验证是否可被用户参数绕过？（否，则很可能误报）

2. **深度验证核对表**：
   ```
   □ 追踪msg构造处：是否在合约调用前进行了签名验证？
   □ 追踪Keeper.Set处：参数类型是否强类型（避免隐式转换漏洞）？
   □ 追踪读取处：所有读操作是否检查了nil/未初始化状态？
   □ 追踪使用处：后续除法/乘法操作是否有溢出防护？
   □ 追踪相关状态：该值修改是否影响其他计算（如抵押率）？
   ```

3. **漏洞严重性量化评估**：
   - **TVL影响度**：污染数据最多能直接影响多少价值锁定额？
   - **利用难度**：攻击者需要什么权限（任意地址/白名单/多签）？
   - **响应时间**：从发现攻击到治理修复需要多久（小时/天/周）？
   - **复合风险**：是否需要与其他漏洞组合才能造成破坏？

## Low risk

**低风险场景评判**：
- 中继数据仅用于链下查询索引或事件日志，不影响共识状态
- 数据污染影响范围隔离在测试网或沙箱环境
- 存在链上治理机制可及时撤销/修正异常数据（需评估治理响应时间是否足够快）
- 经济激励设计使攻击者作恶成本远超潜在收益（需量化分析）
- 多预言机源配置且使用拜占庭容错聚合算法（如舍弃前后10%极端值）
