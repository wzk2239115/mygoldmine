# Move 预言机更新者访问控制缺失

**漏洞类型**: Oracle Manipulation  
**影响范围**: Aptos/Sui 生态的资产定价、流动性挖矿奖励计算、杠杆交易保证金评估等依赖外部价格数据的场景

## Details

**代码示例特征**：
```move
public entry fun update_price(oracle: &mut Oracle, new_price: u64, timestamp: u64) {
    oracle.price = new_price;
    oracle.last_update = timestamp;
}
```

**快速定位核心操作**（L2: 跳读）：
- 扫描 `public entry` 或 `public` 函数中包含 `update`、`set`、`feed`、`push` 等关键词
- 定位修改 `Oracle`、`PriceFeed`、`DataSource` 等资源字段的赋值操作
- 关注直接修改 `price`、`rate`、`value`、`data` 等敏感字段的语句

**快速定位保护机制**（L3: 逐行读）：
- 检查函数签名是否使用 `&signer` 参数并验证身份
- 查找 `assert!(signer::address_of(account) == @admin, E_NOT_AUTHORIZED)` 类权限断言
- 搜索 `has_role`、`is_authorized`、`only_updater` 等权限验证函数调用
- 确认是否使用 `Capability` 资源进行基于能力的访问控制
- 验证是否有 `friend` 模块限制或仅允许特定模块调用

## Classify

**判定为漏洞**：
- 更新函数为 `public entry` 且无 `&signer` 参数验证调用者身份
- 存在 `&signer` 但未对地址进行白名单或角色检查
- 依赖 `acquires` 资源但未验证资源所有者权限

**判定为误报**：
- 函数使用 `public(friend)` 限制仅友元模块调用，且友元模块已实施权限控制
- 通过 `Capability` 模式实现访问控制，更新需持有特定能力资源
- 函数签名为 `public entry fun update(admin: &signer, ...)`，且内部严格验证 `admin` 地址

**代码异味**：
- 权限验证逻辑分散在多个辅助函数中，审计难以追踪完整验证链
- 使用自定义权限系统但缺乏标准化实现
- 权限检查依赖外部合约调用，存在跨模块信任风险

## Low risk

**以下场景可降级为低风险**：
- 预言机数据仅用于展示或统计，不影响资金流转或权限判定
- 存在多签或时间锁机制，恶意更新需经过延迟期和社区审查
- 实施价格偏离度检查，单次更新幅度受限且有异常回滚机制
- 采用多源预言机聚合，单一数据源作恶无法操控最终价格
- 预言机更新频率受限且有冷却期，攻击窗口极小且成本极高
- 合约处于测试网或沙箱环境，不涉及真实资产

## 审计专业技巧

### 1. 权限验证链路追踪（关键步骤）

**深度审计方法**：
不要仅检查函数入口的权限断言，需要完整追踪：
- `update_price()` 调用了哪些内部函数
- 内部函数是否再次进行权限检查或可被任意模块调用
- 是否存在"权限检查绕过"：如函数A有权限控制，但调用未受保护的函数B实现相同功能

**实战案例**：
```move
// ❌ 漏洞案例：权限检查被绕过
public entry fun update_price_checked(admin: &signer, new_price: u64) {
    assert!(signer::address_of(admin) == @oracle_admin, E_NOT_AUTHORIZED);
    update_price_impl(new_price);  // 调用未受保护的内部函数
}

public fun update_price_impl(new_price: u64) {
    // 没有权限检查！任何模块都可以调用
    let oracle = borrow_global_mut<Oracle>(@oracle_addr);
    oracle.price = new_price;
}
```

### 2. 真实漏洞 vs 误报的五大区分经验

**经验1：`public(friend)` 模块隔离的陷阱**
- **常见误报**：看到 `public(friend)` 就认为安全，但忽略了友元模块本身可能有漏洞
- **真实漏洞指标**：需要检查友元模块是否真的实施了权限控制。如果友元模块的所有调用者都是 `public entry`，那么权限控制形同虚设
- **审计建议**：追踪 `friend` 声明的所有模块，验证这些模块内部是否有完整的权限检查链

**经验2：`Capability` 模式的验证深度**
- **常见误报**：看到使用了 Capability 资源就认为是能力控制
- **真实漏洞指标**：Capability 资源可能在初始化时就被广泛分配。需要验证：
  - Capability 在何时、何处、给谁创建
  - 是否有机制防止权限下放（如直接转账 Capability）
- **审计建议**：搜索 `new_capability` 或类似创建函数，确认创建时的访问控制

**经验3：时间锁 / 多签看似完整但实际可绕过**
- **常见误报**：检查到存在时间锁，就认为足够安全
- **真实漏洞指标**：
  - 时间锁是否可被管理员提前取消（如有 `cancel_pending_update` 且无权限控制）
  - 是否存在"紧急更新"路径绕过时间锁
  - 多签需要多少个签名者？是否只有1/N 的签名者？
- **审计建议**：搜索所有能修改预言机状态的函数，验证它们都遵守同样的时间锁

**经验4：价格偏离度检查的实现缺陷**
- **常见误报**：看到有 price sanity check，认为可以防止极端价格
- **真实漏洞指标**：
  - 偏离度检查的基线是什么？如果基线本身就是被污染的价格，检查无效
  - 是否允许第一次更新时跳过检查？
  - 单次更新上限是否可被升级合约或管理员修改？
- **审计建议**：检查 `assert!(price_delta <= MAX_DELTA, E_PRICE_TOO_HIGH)` 中的 MAX_DELTA 值和修改权限

**经验5：数据来源的真实性验证**
- **常见误报**：使用了外部预言机（Pyth/Chainlink），就认为数据可信
- **真实漏洞指标**：
  - 本地是否还有其他 `update_price` 函数可以更新价格？
  - 预言机中的哪些字段是可以被本地合约修改的？
  - 是否存在两套定价系统（如官方价格 + 社区价格）存在冲突？
- **审计建议**：全局搜索所有修改价格的操作，不要假设只有外部预言机可以更新

### 3. 常见审计陷阱

**陷阱1：忽略模块初始化阶段**
初始化时的权限设置可能存在漏洞。检查：
- `init_module` 或构造函数中是否正确设置了管理员地址
- 是否有默认管理员地址被硬编码（可能是测试地址）
- 初始化权限资源时是否有正确的所有权限制

**陷阱2：跨版本兼容性问题**
- 新版本可能添加了新的价格更新函数，且权限控制不一致
- 已弃用的函数仍然可用，导致权限检查被绕过

**陷阱3：事件日志与实际操作不同步**
- 函数可能记录了权限检查的事件，但实际未执行检查
- 审计时需要验证事件发出的位置，不要只看事件名称

### 4. 完整审计检查清单

```
□ 定位所有修改预言机状态的函数（update*/set*/feed*）
□ 验证这些函数的可见性（public/public(friend)/entry）
□ 检查每个函数的权限验证逻辑（&signer/Capability/Role）
□ 追踪权限验证的完整链路（包括调用的其他函数）
□ 验证权限资源/能力的创建和分配机制
□ 检查是否存在时间锁或多签，以及是否可被绕过
□ 搜索价格检查逻辑，验证基线数据的真实性
□ 检查初始化函数中的权限设置
□ 验证模块间的信任关系是否合理
□ 确认没有已弃用但仍可用的风险函数
```
