# Rust 账户枚举 DoS

**漏洞类型**：拒绝服务 (DoS)  
**影响链**：Solana、基于 Anchor 框架的程序  
**核心成因**：指令处理中对传入账户数量无上限约束，攻击者通过传入大量账户触发超时或计算单元耗尽

## Details

**典型代码模式**：
```rust
pub fn process_batch(ctx: Context<ProcessBatch>) -> Result<()> {
    for account in ctx.remaining_accounts.iter() {  // 未限制账户数量
        // 状态更新、计算或存储操作
        perform_heavy_operation(account)?;
    }
    Ok(())
}
```

**定位核心操作**（L2：跳读）：
- 搜索 `remaining_accounts.iter()`、`accounts.iter()`、`for account in`
- 关注批量处理指令：如 `batch_*`、`process_all`、`update_multiple` 等函数名
- 检查账户数组参数：`Vec<AccountInfo>`、`&[AccountInfo]` 类型入参

**定位保护机制**（L1：关键词扫描）：
- 账户数量检查：`require!(accounts.len() <=`、`assert!(ctx.remaining_accounts.len() <`
- 分页参数：`limit`、`offset`、`page_size` 变量
- 计算单元限制：`compute_budget::set_compute_unit_limit()`
- 批次拆分：`chunks()`、`split_at()` 调用

## Classify

**确认为漏洞**：
- 循环处理账户数量完全由用户输入控制，无上限验证
- 单次指令可传入账户数超过合理业务需求（如 >128 个）
- 循环内有非常量时间操作（PDA 派生、CPI 调用、状态写入）

**判定为误报**：
- 账户数量已在指令约束层限制（如 `#[account]` 宏的固定数量）
- 仅读取操作且有明确超时保护
- 循环内操作为 O(1) 常量时间且总计算量可预测

**代码异味**：
- 有数量限制但阈值过高（>50）
- 缺少分页但业务场景实际不会触发大量账户

## Low risk

**降级为低风险的情况**：
- 指令调用权限受限（仅管理员/白名单地址）
- 链下已有速率限制或调用成本极高（需消耗大量代币）
- 账户数量限制充足但未达最佳实践（如限制 100 但建议 50）
- 业务逻辑确保账户集合规模始终可控（如固定 IDO 参与者列表）

## 审计专业技巧

### 1. 动态分析与成本估算

**实战审计方法**：
- **计算单元追踪**：对循环内每个操作估算 CU 消耗（PDA 派生约 100-200 CU，CPI 调用约 1000+ CU）
  ```rust
  // 示例：128 个账户 × 每个账户 1500 CU = 192,000 CU（可能超过 200,000 默认限制）
  for account in remaining_accounts.iter() {
      let (pda, _) = Pubkey::find_program_address(...);  // ~150 CU
      invoke_signed(...)?;  // ~2000 CU
  }
  ```
- **设计测试用例**：在本地 validator 环境构造极限输入（如 1000 账户）观察实际表现
- **观察点**：交易是否失败、返回错误信息是否暴露内部逻辑

### 2. 真实漏洞与误报的区分经验

**真实漏洞的关键标志**：
1. **可不消耗用户代币地无限消耗计算资源**：无需支付手续费即可触发 DoS
   - 例如：免费查询端点中处理所有账户
   - 对比：需支付代币费用的操作已自带经济制约

2. **重复触发成本极低但链上成本极高**：
   - 攻击成本：发送一个交易（微量 SOL）
   - 链成本：处理 128 个账户的 300,000 CU（浪费）
   - **风险度**：成本比 > 1000 倍时为高风险

3. **链下聚合器无法防护**：
   - 即使 RPC 层有限流，验证器仍需处理 MEV 抢先交易
   - 若攻击涉及 MEV bot，链上防护必须存在

**常见误报场景**（需要排除）：
- 循环处理的是 **固定集合**：如 `&ctx.accounts.winners[..]`（PDAs 派生时确定）
  - 虽然迭代大量元素，但集合大小在链上有保证
  - 示例：解散 10,000 个已创建的托管账户（一次性清理）

- **隐性数量限制已存在**：如通过 Anchor 宏约束
  ```rust
  #[derive(Accounts)]
  pub struct Batch {
      #[account(len = winners.len())]
      pub accounts_data: AccountLoader<'info, Vec<User>>,  // 大小受 account loader 约束
  }
  ```

- **操作为对数或常数时间**：
  ```rust
  // 即使 100 个账户，仍为 O(n) 但单个操作极轻
  for account in remaining_accounts.iter() {
      let flag = account.data.borrow()[0];  // 仅读单个字节，O(1)
      if flag == 1 { votes += 1; }
  }
  // 总成本：100 × 50 CU ≈ 5,000 CU（安全）
  ```

### 3. 审计检查清单

**第一步：量化分析**
- [ ] 单个循环迭代的 CU 成本（通过代码检查或运行测试估算）
- [ ] 账户数量限制值 VS 默认计算预算（200,000 CU）
- [ ] 预期最大业务量（如分布式应用同时处理的账户数）

**第二步：权限与成本约束分析**
- [ ] 检查调用者权限：`signer` 约束、签名要求、费用消耗
- [ ] 是否存在链下预验证：RPC 节点限制、钱包应用层检查
- [ ] MEV 风险：此类交易是否容易被抢先，是否可被夹击

**第三步：修复方案的可行性评估**
- [ ] 添加 `require!(accounts.len() <= 32)` 的业务合理性
- [ ] 分页实现是否可行（如 offset-limit 模式 vs 状态机）
- [ ] 是否需要权限降级（使用 ProgramData 存储已验证的账户列表）

### 4. 报告差异化建议

**High 级漏洞的陈述示例**：
> 账户枚举 DoS：函数 `batch_update()` 处理的账户数量完全由用户控制，无上限约束。在传入 256 个空账户时，循环内 CPI 调用（每个 ~2000 CU）会导致消耗 512,000+ CU，超过默认 200,000 CU 限制。攻击者可通过重复发送此类交易使验证器资源耗尽，影响网络可用性。**建议**：添加 `require!(remaining_accounts.len() <= 32)` 强制限制。

**低风险或排除的表述**：
> 账户批量迭代已检查：`process_winners()` 处理的账户来自链上已验证的 IDO 参与者列表（最多 1000 人）。虽然循环迭代数量多，但每次迭代仅读取 8 字节状态（O(1) 常数时间），总成本约 8,000 CU，未超过默认预算。**判定**：低风险。

### 5. 实战案例对比

**案例 A：高风险漏洞（Phantom Wallet 历史漏洞）**
- **症状**：`approve_multiple_tokens()` 无上限处理代币转账授权
- **关键特征**：每个代币转账需 SPL 指令调用（~1500 CU/次），256 个代币 = 384,000 CU
- **攻击方式**：免费构造、无经济成本、易被 MEV 抢先交易复制
- **区分点**：虽然应用层有签名验证，但区块链层面无保护

**案例 B：误报（Marinade Liquid Staking）**
- **症状**：`claim_stake_accounts()` 迭代最多 1000 个托管账户
- **关键特征**：每个账户仅查询 owner 字段和余额（~200 CU/次），总计 200,000 CU
- **为何不是漏洞**：
  1. 账户数上限由链上合约逻辑保证（托管池固定大小）
  2. 这是一次性批量声明操作，非重复触发漏洞
  3. 调用者必须是池创建者（权限受限）

**案例 C：边界情况（需权衡）**
- **症状**：`finalize_batch()` 限制 100 个账户，但业务最多需 80 个
- **判定**：不报告为漏洞，而是在建议部分提及"最佳实践"
- **理由**：已有有效保护，提升上限不影响安全边界
