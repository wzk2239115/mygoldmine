# Vyper 无界 for 循环 DoS

## Details

**典型代码模式：**
```vyper
participants: public(DynArray[address, 1000])

@external
def distribute_rewards():
    for participant in self.participants:
        send(participant, reward_amount)
```

**快速定位核心操作技巧（L2-跳读）：**
- 扫描 `for` 循环遍历 `DynArray` 或动态长度结构
- 关注批量操作函数：distribute、batch、mass、withdraw_all、refund_all 等命名
- 检查循环内是否存在外部调用（`send`、`raw_call`）或状态写入
- 优先审计公开函数中的循环，特别是涉及资金分配的函数

**快速定位保护机制技巧（L1-关键词扫描）：**
- 搜索长度限制：`len()` 配合 `assert` 或 `require` 进行上限检查
- 查找分页参数：`start_index`、`end_index`、`limit`、`offset` 等
- 检查是否使用固定长度数组替代 `DynArray`
- 确认是否存在紧急暂停机制：`paused`、`emergency_stop`

## 审计专业技巧

**1. 单迭代成本评估**
- 外部调用：`send()` = 9000+ Gas，`raw_call()` = 变动，`staticcall()` = 约 2600 Gas
- 存储读写：SSTORE = 20000 Gas（冷）/ 5000 Gas（热），SLOAD = 2100/100 Gas
- 实际案例：如果循环 100 次且每次调用 send()，基础 Gas = 900000+，加上额外操作易超块限制
- 建议：对有外部调用的循环限制在 50 次以内；纯计算循环可允许 200+ 次

**2. 函数入口点权限分析**
- 验证是否为 `@external` 还是 `@internal`：仅 internal 函数可认为风险大幅降低
- 检查修饰符：`@onlyOwner`、`@nonReentrant` 等能否限制调用者
- 追踪数组更新者：谁能调用 `append()`、`pop()` 等修改数组长度的方法？
- 典型误报：管理员限定的内部分页分发函数被错误标记为 DoS

**3. 动态数组创建路径追踪**
- 追踪所有修改数组长度的代码路径（append、extend、pop）
- 区分受限增长 vs 无限增长：
  - 受限：需要 token 质押、限额制、审核流程等成本机制
  - 无限：用户可低成本自由添加（真实 DoS 风险）
- 实际案例：某项目允许任意地址 `addParticipant()`，无任何成本或上限 → 严重漏洞

**4. Gas 成本精确化估算**
```vyper
# 低成本场景（通常为误报）
for addr in self.recipients:
    balance[addr] += reward  # 热存储写入 ~5000 gas
# 总成本：5000 * len，1000 地址 = 5M gas（可接受）

# 高成本场景（真实漏洞）
for addr in self.recipients:
    send(addr, amount)  # ~9000+ gas per call + 内存开销
# 总成本：9000 * len，100 地址 = 900k gas + overhead（容易超限）
```

**5. 误报陷阱识别**
- **陷阱 1**：固定大小数组被审计员误认为动态 → 检查 `DynArray[T, MAX]` 中的 MAX 值
- **陷阱 2**：链上长度固定化 → 项目初期可能设置为空，但部署后不再增长，检查历史交易验证
- **陷阱 3**：分页实现隐蔽 → 部分项目在前端实现分页，链上无约束，需查看 Web3 调用模式
- **陷阱 4**：测试网与主网差异 → 某些保护机制可能仅在主网启用，需核实部署参数

## 真实漏洞与误报区分经验

**真实漏洞的确认清单：**
1. **可控性验证**：追踪调用链，确认无权限限制或限制无效
   - `@external` 无 `@onlyOwner` 修饰 ✓ 高风险
   - 有权限但权限可被绕过（如过期检查失效） ✓ 高风险

2. **增长机制验证**：
   - 数组长度与用户输入直接相关
   - 无成本或极低成本的添加机制
   - 没有预设的硬上限

3. **成本-效益验证**：
   - 攻击成本 < 网络收益：如花 0.01 ETH Gas 实现网络瘫痪
   - 重复性触发：是否可多次触发累积成本

4. **实际可行性验证**：通过 foundry/brownie 模拟：
   ```vyper
   # 模拟攻击：构造最坏场景
   for i in range(100):
       contract.addParticipant(attacker_address)
   # 估算最终 distribute_all() 的 Gas 消耗
   ```

**误报的高频原因和修复建议：**
1. **遗漏显式上限**（30% 误报率）
   - 问题：代码中 `DynArray[address, MAX_SIZE]` 的 MAX_SIZE 被忽视
   - 修复：必须查看 Vyper 类型定义，`DynArray[T, N]` 中 N 是硬限制
   - 验证方法：编译合约后查看 ABI 或字节码中的数组大小约束

2. **遗漏业务逻辑限制**（25% 误报率）
   - 问题：虽然接口开放，但业务规则隐式限制增长
   - 示例：投票系统仅允许注册用户投票，注册需要完成 KYC（成本高）
   - 修复：追踪完整业务流程，评估现实中能否大规模触发

3. **遗漏分页机制**（20% 误报率）
   - 问题：链上合约虽无分页，但有 `start:end` 参数的分片处理
   - 示例：`distributeRewards(uint256 start, uint256 end)` 限制了单次迭代范围
   - 修复：检查所有公开函数的参数，特别是 `limit`、`offset`、`batch` 相关

4. **遗漏管理员操作限制**（15% 误报率）
   - 问题：函数标记为 `@onlyOwner` 但审计员未注意
   - 修复：自动化检查所有 `for` 循环是否都在权限保护下

5. **遗漏冷却期/速率限制**（10% 误报率）
   - 问题：存在 `last_call[user]` 时间戳检查，限制了调用频率
   - 修复：不仅检查循环本身，还需检查外层调用的频率限制

## Classify

**判定为漏洞：**
- 循环长度由外部输入控制且无上限约束，可被攻击者恶意扩充至 Gas 上限
- 循环内包含状态修改或外部调用，单次迭代成本高，叠加循环次数导致不可执行
- 数组修改入口对所有用户开放，无成本或极低成本触发
- 已通过实际测试验证可在预算内执行攻击

**判定为误报：**
- 循环长度由固定常量限制（如 `MAX_PARTICIPANTS: constant(uint256) = 50`）
- 循环仅读取数据且总 Gas 消耗在合理范围内（需实际测算）
- 存在有效的分页机制或迭代器模式
- 数组修改入口受权限保护或高成本机制保护
- 已在链上历史记录中验证，数组长度稳定在安全范围

**判定为代码异味：**
- 循环长度虽有限制但阈值过高（如 >500），接近 Gas 边界
- 缺少显式的长度检查但业务逻辑隐式限制了增长
- 权限检查存在但存在潜在的权限提升漏洞

**评估建议（分级矩阵）：**
```
风险等级      数组增长可控    单次成本    循环上限    权限限制
高（漏洞）     无             高          无         否
中（异味）     弱             高或中      有但过高    部分
低（接受）     强             低          有且合理    是
```

## Low risk

**以下情况可评为低风险：**
- 循环长度有明确上限（<100）且经 Gas 测试验证可执行
- 仅限管理员调用且数组长度由治理控制
- 循环内操作为纯计算，无外部调用或存储写入
- 已部署合约中数组长度实际维持在安全范围内，且无公开接口可添加元素

**审计检查清单总结：**
```
□ 确认数组类型（DynArray 或固定数组？）
□ 追踪数组增长的所有代码路径
□ 验证数组修改函数的权限控制
□ 估算单次循环迭代的精确 Gas 成本
□ 查看是否存在长度上限检查或分页参数
□ 检查部署后链上实际长度和增长历史
□ 评估攻击成本与实际威胁程度
□ 模拟最坏场景进行 Gas 预估测试
```
