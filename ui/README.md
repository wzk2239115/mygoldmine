# VUL/AI Findings Board

漏洞审计看板读取 `runs/<project>/<timestamp>/audit-report.json`，把二次审计结论、CVE 候选和运行日志放在同一个工作台里。

## 启动

```bash
# 生产模式：构建前端并启动本地接口和静态文件服务
bash scripts/ui/start.sh
# 打开 http://127.0.0.1:8787
```

## 导入项目并启动审计

左侧“漏洞审计”标题旁的加号用于导入新目标：

- **GitHub 仓库**：输入 `https://github.com/所有者/仓库` 后自动读取分支下拉列表，首次显示 10 条，点击“加载更多”追加第 11–20 条，依次类推；分别标记默认分支和“本页最新”分支，也可手动刷新。服务只读取当前页分支的提交对象，不下载目录树和源码，分支列表与页面结果短时缓存；导入时以浅克隆方式保存到 `targets/<项目标识>`，只支持公开仓库，不收集访问令牌。已有目录不会被强制更新或切换分支。
- **本地目录**：点击“选择目录”浏览服务器上的可见子目录，可进入子目录、返回上一级、回到主目录并选择当前目录；也可以直接输入绝对路径。导入后直接审计该目录的当前内容，不复制源码或切换分支。

项目标识用于隔离运行报告和仓库专属经验，默认取目录或仓库名称。导入成功后，接口登记 `ui/data/projects.json` 和 `targets/manifest.json`，再调用现有 `run.sh` 启动完整流程，包括环境构建、挖掘、蓝队验证、红队验证和挖掘修复学习；不会使用仅静态挖掘的快捷流程。已有实时审计的项目不能重复启动。

首次运行会自动执行 `npm install` 和 `npm run build`。也可以手动执行：

```bash
cd ui
npm install
npm run build
npm start
```

开发模式使用 Vite 热更新和接口服务：

```bash
cd ui
node server/index.mjs
# 另一个终端
npm run dev
# http://127.0.0.1:5173
```

环境变量：

```bash
PORT=8787 HOST=127.0.0.1 bash scripts/ui/start.sh
```

`HOST=0.0.0.0` 会把接口暴露到网络；默认只监听回环地址，因为报告里可能包含未修复漏洞细节。

## 验证

```bash
# 服务启动后
cd ui
npm run smoke
```

`smoke` 命令会检查 `/api/board` 结构、统计一致性、至少 25 条人工复核、至少 8 个 CVE 候选，以及 `/api/live` 和日志与轨迹接口。

## 数据来源

- `ui/data/finding-ledger.json` 扫描所有完整有效的审计报告，为每次发现的候选问题保留单独编号，并归并多轮审计中的同一问题；历史报告中独有的问题也会保留，运行中、失败或不完整草稿不会替代最新完整报告。没有发现记录表时，界面改用旧版最新报告路径。
- 默认排除 `smoke`、`smoke-real`、`smoke-target`；报告里的 `findings` 或 `vulnerabilities` 字段统一转换为候选问题列表。
- 优先读取 `run.sh` 生成的 `.meta/status.json`；没有状态文件的运行按日志更新时间识别为实时运行。
- `ui/data/curated.json` 保存人工复核种子；旧 `project:finding-id` 只有语义唯一时才继承，歧义状态不会套到不同候选问题。
- `ui/data/auto-state.json` 合并发现记录表、验证结果和 CVE 产物，生成自动路由及待人工验收条件；红队验收会重算确定性的随机标记证据来源链。
- `ui/data/state.json` 保存手工改动，优先使用单次观测编号（`occurrence_id`），旧接口仍可使用 `project:id`。
- `scripts/workflow/refine_worker.py` 按来源内容哈希重算未处理候选，新证据可触发已归档项重新评估；轨迹写入 `rsi/trajectories/refine.jsonl`。
- `scripts/workflow/flow_worker.py` 处理分诊和待验证候选：调用第四阶段验证智能体、补图文报告、触发第五阶段红队验证；状态写入 `flow-state.json`，队列和心跳写入 `flow-queue.json`，轨迹写入 `rsi/trajectories/flow.jsonl`。
- 优先级：`state.json` > `curated.json` > `flow-state.json` > `refine-state.json` > `auto-state.json` > 默认未处理候选。手工变更不修改原始报告。
- `scripts/ui/start.sh` 默认启动自动分类后台任务；`REFINE_WORKER=0` 可关闭。自动流转默认不随看板启动，设置 `FLOW_WORKER=1` 或运行 `flow_worker.sh start` 开启；缺少环境时设置 `FLOW_BUILD_ENV=1` 先构建环境。自动流转只处理已分类候选，不会创建 CVE 编号或跳过验证和独立审核的通过条件。

## 列与判定

| 列 | 含义 |
|---|---|
| 未处理候选 | 未进入流程 |
| 分诊 | 严重和高危候选自动入队；自动流转后台任务调用验证智能体，人工仍可优先处理 |
| 待验证 | CVE 等级候选或已有确认的验证结论；自动流转后台任务补图文报告并触发红队，尚未证明可利用 |
| CVE 跟踪 | 先查 NVD、GHSA 和项目公告去重，再披露或联系 CNA |
| 已关闭 | 误报、重复、已知 CVE、设计限制 |

自动分诊只代表“值得先看”，不等于漏洞成立；`AUTO` 和 `FLOW` 徽标表示该状态来自自动分类或自动流转产物，而不是人工。未处理候选（`inbox`）是自动评分后未达到进入下一阶段条件的候选问题，默认隐藏，不是待办。

候选判定（`verdict`）：`TP` 表示代码级成立，`FP` 表示误报，`DUP` 表示重复，`UNCLEAR` 表示待定。

## 视图

- **看板**：顶部“正式执行链”固定展示环境构建、安全审计编排、攻击场景设计、蓝队验证、红队场景构建、红队执行、独立审核和经验学习八个节点，分别读取最新一次运行的真实产物；项目筛选可切换目标。点击节点可打开对应的只读轨迹，多次调用可按轮次、候选或红队运行选择；Claude 原生流式日志复用第三方 Claude Code 会话界面，旧文本日志与红队独立模型循环保留各自轨迹形式。下方六阶段流程继续统计候选处理状态，卡片显示严重度、判定、CVE 等级和证据数，点击卡片或按键盘打开详情后可修改状态。
- **阶段技能学习**：经验学习节点读取八阶段反馈、覆盖记录、复审计划和验证结果，选择目标后由宿主机调用本地 SkillOpt 核心重写入口生成候选；候选继续使用现有评估、发布和回退，未配置可信套件时只保留候选。SkillOpt 请求和重写结果作为文本轨迹显示，不冒充原生 Claude 会话。
- **实时审计**：运行中的审计任务在看板顶部显示实时状态条，包括状态、耗时和最后一行日志；点开进入实时日志抽屉，可查看同一八节点执行链、节点级会话、对话、内部智能体拓扑、结构化轨迹和原始日志。运行状态每 4 秒轮询，执行链在实时运行时按 5 秒轮询，报告生成后看板自动重新加载。
- **持久沙箱**：每次审计运行都可用 `scripts/env/sandbox.sh` 复用同一工作副本，继续交互式探索和离线验证；架构页“隔离工作副本”详情提供对应命令。
- **表格**：按严重度或目标排序，适合批量分诊。
- **系统架构**：左侧轨道书图标先展示最新项目的八节点执行链，再进入三级架构浏览器。第一级以漫画系统地图展示 5 个区域；点击区域进入中层阶段和组件图，再点击节点查看输入输出、执行规则、对应脚本与输出文件、失败时如何处理和优化检查点。安全审计编排节点说明原生工具 `Grep`、`Glob` 和 `Skill`、第 1 波 6 个 `infra-analyst`、第 2、3 波最多各 6 个 `audit-skill-worker`、按 `recommended_skills` 和覆盖缺口选择技能，以及最多 3 波、18 个分析任务的上限。“RSI 学习流程”区分验证资源只读建议、红队验证程序候选和挖掘修复：挖掘修复按共享或仓库专属作用域生成，经真实前后运行评估后发布，由下一轮挖掘加载并可回滚。页面明确可信样本支持数为 0（`trusted_support=0`）时验证动作继续仅静态证据的只读建议，回放不证明因果，验证程序不会自动修改，未评估挖掘候选不会发布。漫画由 360 平台的 Seedream 生成，只承担叙事，准确结构以可点击节点为准。同步维护要求见根目录 `AGENTS.md`。
- **详情抽屉**：摘要、证据和智能体流。
  - 摘要：修改状态、判定、CVE 等级、CVE 状态、关联 CVE 和审计备注。
  - 证据：复制证据路径、打开 `audit-report.md` 或 `audit-report.json`、查看原始候选问题 JSON。
  - 智能体流：读取 `claude.rendered.log` 尾部，可自动刷新、复制 `run.sh --verify-only` 命令。
- **筛选**：目标、严重度、判定、仅 CVE、待验收和搜索；默认隐藏未处理候选，只显示已进入自动分类流程的候选。
- **待验收**：只显示通过红队随机标记验证、独立审核且图文报告齐全的候选；人工在这里做最终验收。
- **流程说明**：悬停或聚焦“未处理候选/分诊/待验证/CVE 跟踪/待验收/已关闭”会显示该环节的定义、当前下一步和是否由自动流转推进；底部显示自动流转后台任务心跳和待处理数。
- 深色和浅色主题；状态与筛选保存在浏览器本地存储中。

## 设计说明

- 交互参考 `siteboon/claudecodeui` 的工作区外层布局、侧栏、详情面板和智能体会话组织方式；没有复制其代码，其许可证为 AGPL-3.0-or-later。
- 视觉采用中性浅色工作区：白色内容面、浅灰侧栏、细边框和柔和圆角；颜色主要用于严重度、判定、错误和运行状态，深色主题使用中性炭灰。左侧品牌图标为混元三维生成的黄金铲子；首页自动分类流程保留三维工厂主视觉，进入具体流程后切换为轻量计数面板。
- 报告是静态分析结果，界面会明确标注“未运行时验证”。CVE 结论以人工复核和 `docs/cve-handoff.json` 为准。

## 重置

```bash
printf '{}\n' > ui/data/state.json
python3 scripts/workflow/build_state.py
```

只重置某条记录：

```bash
jq 'del(."vllm:F-02")' ui/data/state.json > /tmp/state.json && mv /tmp/state.json ui/data/state.json
```

### 看板首页布局

首页顶部以紧凑状态带展示八个执行阶段，点击阶段仍可查看执行轨迹。下方全宽工厂场景展示处理进度；场景底部的阶段计数和严重度、判定筛选保留原有操作。窄屏下状态带和计数面板自动换行。

### 项目导入进度

导入弹窗通过 `POST /api/targets/import-stream` 接收逐行 JSON 状态事件，在提交按钮下方显示排队、源码准备、版本登记、审计启动和命令输出，以及等待时间。失败信息保留在弹窗内。原有 `POST /api/targets/import` 接口保持可用；点击取消或关闭导入连接会停止排队、下载或启动过程；本次新建源码目录会清理，已有目录和本地源码保留。已登记的项目恢复导入前记录，已启动的审计调用停止命令，运行产物保留供排查。取消后可重试，新请求会等待清理完成。此状态仅表示导入与启动过程，不表示完整审计已完成。

### 按提交版本导入

公开仓库导入使用 `POST /api/targets/github-commits` 直接读取提交历史，每页 10 条，显示短提交编号、时间与说明，默认选最新提交，支持加载更多。读取列表不下载源码，相同页短暂缓存并合并并发请求。导入按完整提交编号浅下载、检出并核对版本。

已有有效提交只有与所选版本相同才复用；不同版本须换项目标识。仅含 `.git`、来源匹配且没有有效提交的未完成目录，以及空目录，会移动到 `backups/incomplete-imports` 后重试。其他已有内容不会自动移动。下载失败、超时或取消会清理本次新建且尚未登记的目录。

下载耗时显示为实际已用时间，不是倒计时。仓库下载不设固定总时长上限；每次收到下载命令标准输出或错误输出都重置空闲计时，连续 3 分钟无输出才停止并允许重试。列表请求和启动审计仍保留各自超时。

### 本地目录选择

切换到本地目录会打开服务器目录浏览器，仓库地址和本地路径分别记忆。点击目录进入，点击路径层级、上一级或主目录返回；名称筛选仅作用于当前已加载的子目录。列表限制高度并独立滚动，点击“使用此目录”将当前路径填入导入表单。本地导入需要服务器绝对路径，不接受仓库网址。

导入弹窗直接挂载到页面最外层，覆盖导航层级；最大高度限制为视口高度的 88% 且不超过 760 像素，标题和底部操作区固定，超出的表单在内部滚动。

看板扫描同时识别主运行目录和带有 `status.json` 的相邻 `.meta` 状态目录。启动早期只有状态目录时，项目也会显示在侧栏；两种目录同时存在时只统计一次，不把 `.meta` 当作独立运行。

节点轨迹转换为 Claude 会话后，使用 `scripts/ccui/index_trace.mjs` 同步登记到会话数据库，再返回对应会话地址。转换缓存与数据库登记分开处理，登记失败显示错误，不进入项目选择空页。环境构建的交付状态与能力范围分开展示：智能体正常交付可用沙箱时显示已完成；部分可用环境同时注明能力受限，轨迹面板可展开具体限制。使用备用方案、必要验收未通过或交付未确认时仍显示降级，无可用环境时显示受阻。底层环境状态与下游能力约束保留。轨迹面板提供消息数量、同步和新窗口入口。

安全审计节点在没有主会话或主会话为空时，展示本次运行的启动日志（相邻状态目录中的 wrapper.log）。复制源码失败会标明审计智能体未启动；生成主会话后优先展示真实会话。历史运行日志保持原始结果，不因代码修复改成成功。

### 删除项目

侧栏项目右侧提供删除按钮。确认后删除项目登记、发现记录与对应运行目录，不提供撤销或恢复接口；源码目录保留。项目仍在运行时禁止删除。删除使用 `DELETE /api/targets/:project`，后续重新导入是新建审计，不恢复旧记录。

### 串行阶段状态

监督脚本按实际调用顺序记录 `pipeline-stage.json`：环境准备、安全审计、攻击场景、蓝队验证、红队处理、经验学习。红队批处理在调用场景构建、执行、独立审核前更新当前节点与候选编号；不同候选会依次重复这些步骤。看板只将当前节点显示为运行中，尚未到达的节点显示等待，不使用整次任务存活状态推断每个节点运行，也不将初始占位值当成已跳过。旧运行缺少阶段文件时按已有阶段日志和产物兼容推断。完成、降级等最终结果仍以真实产物为准。

中断记录按最后执行阶段展示：该阶段保留已有结果，未完成时标注已中断；后续没有执行记录的阶段标注未执行。旧记录结合环境日志识别中断位置，不把启动前中断误报为安全审计失败。

项目侧边栏提供“重新审计”：通过 `POST /api/targets/:project/restart` 读取已登记的源码目录，调用完整审计主流程并创建新的运行目录，保留历史记录。源码不重新下载，项目正在运行时拒绝重复启动；重新审计与导入共用串行启动队列。启动后自动选择该项目并刷新看板。

项目没有显式图标配置时，优先使用本地同名项目图片 `ui/public/logos/<项目标识>.png`；没有图片时才显示默认图标。删除后重新导入也会恢复已有图片。

打开执行轨迹时，看板先检查轨迹服务；默认本机回环服务未运行时自动启动，并合并并发启动请求。启动日志写入 `runs/ccui-home/service.log`，只恢复查看服务，不重新启动审计智能体。自定义远程服务不由看板启动。

“设置 → 配置模型”可分别设置安全审计、蓝队验证、红队验证、环境构建、攻击场景设计与独立审核模型。配置经校验后保存至 `config/stage-models.json`；可选阶段留空时跟随审计模型。候选列表只读取已有模型名称，不返回服务密钥。新导入和重新审计在启动时将配置传入主脚本并固定为本次任务的模型参数；已有任务不受影响。运行状态通过 `stage_models` 保存本次各阶段模型。命令行的场景与审核模型在参数解析完成后计算，避免选项未生效。模型名称必须在对应的既有服务中可用，此入口不配置服务地址或密钥。

新启动任务的默认安全审计时限为 24 小时（86400 秒），各启动入口保持一致；看板从本次运行记录读取实际时限，不使用固定的显示值。已启动任务保留启动时传入的时限，配置修改不伪装为已延长历史任务。环境构建和验证阶段仍使用各自时限。

红队模型默认跟随安全审计模型，设置中留空即可跟随；不再默认使用 flint。红队按模型的服务前缀读取已有服务地址与鉴权配置，并去除服务前缀后发送请求；缺少配置时明确失败，不回退到旧模型服务。密钥不会写入看板配置或运行结果。


### 环境构建指令约束

环境构建技能与智能体定义以本次验收目标决定依赖范围，默认先满足轻量审计需要；导入、CPU 测试与 GPU 训练分别验收，不默认安装全部开发或训练依赖。指令要求先做平台和下载源预检、按实际日志检查进展、修正原因后重试，并保留失败方案及真实限制。

这轮调整仅更新 Markdown 指令，不改变现有智能体超时、Docker 构建超时、备用流程、缓存实现或页面进度展示。已有 Dockerfile 仍可能被备用流程复用；指令要求智能体在预算内明确处理并如实报告，不表示脚本已经提供自动降级或独立构建管理。新启动的环境构建智能体加载新指令，正在执行的会话不会自动重新加载。

环境构建指令进一步区分预检与安装：预检只读取必要元数据，安装验证必须进入正式 Docker 构建；禁止在临时容器内安装依赖。先验证最小方案，再按指定验收路径补齐依赖；持续版本回溯须先诊断约束。检查保留原命令退出码，避免管道筛选掩盖超时。这些是智能体指令要求，未新增脚本级强制检查。

环境构建指令默认优先交付满足当前审计需要的沙箱，达到明确的最小要求后停止扩建；允许带真实限制的部分可用结果，不以完整部署、全部测试通过或就绪标签作为默认目标。必要能力及既有隔离边界仍须验证，不因追求快速交付而放宽。该要求属于技能指令，不改变脚本的状态判定。

环境构建技能选择性参考 Docker 的构建分层与缓存指导、Repo2Run 的具体验收标准和 SetupX 的有证据修复经验。指令要求按平台与版本核对历史经验，在本次输出目录保留构建说明，并保留已验证方案；未接入外部框架、数据库或自动快照回退，仍以够用的审计沙箱为默认目标。来源链接记录在技能文件中。

执行轨迹的会话索引缓存统一写入相邻的 `<运行目录>.meta/ccui-session.json` 或 `.meta/ccui-sessions/`，包括批量导入入口；查看环境轨迹不会创建或占用尚未启动的审计输出目录。旧缓存可由原始轨迹重新生成，历史审计结果不改写。输出目录非空时拒绝覆盖的检查保持不变。

环境构建指令要求优先核对已有镜像的源码对应关系、平台与实际镜像编号，通过必要断网验收后直接复用。仅修正清单、补充验收记录或修复辅助脚本不触发重建；保留原始构建时间并另记本次验收时间。只有构建输入不匹配、镜像不可用或指定验收被具体缺失项阻塞时才构建。此项属于智能体指令，未新增脚本级自动复用机制，新启动的环境构建会话生效。

攻击场景设计仍由智能体按技能执行。启动器在调用 Claude 命令行前去除模型的服务前缀，配置兼容服务地址、鉴权和子智能体模型；显式连接配置优先，未设置时沿用环境构建阶段的 360 服务及已有凭据。启动时仅加载项目及本地项目设置，排除用户级设置中的其他模型服务。凭据只传入子进程环境，不写入任务或轨迹。

审计编排退出前对实际运行目录的报告执行既有质量检查，反馈缺失字段供智能体修正；原有退出检查次数上限和最终报告质量门槛保留。恢复报告标记为 `coverage.analysis_mode=assembly-only` 时，轨迹入口明确显示恢复汇总；约定的同项目 `-recovery` 运行还关联原始完整审计，两个会话分别缓存。恢复成功只代表汇总流程完成，不代表重新扫描或漏洞验证通过。

节点轨迹抽屉提供“重新运行此节点”。当前支持攻击场景设计、蓝队验证、红队场景构建、红队执行、独立审核和经验学习：复用选定运行的报告，使用设置中的当前阶段模型，将报告快照、新日志与产物保存到 `<run>.meta/node-retries/<node>/<id>/`。前置产物缺失或项目仍在运行时拒绝启动；同项目节点重跑互斥，项目重跑也检查该锁。界面显示最新节点状态及历史轨迹；仅更新该节点展示，不自动执行后续阶段，也不覆盖原始报告、验证结论或历史成功状态。其他节点尚不支持独立重跑，显示不可用说明与项目重新审计入口提示，不显示看似可用的重跑按钮。


### 结构化阶段交付

新增 `scripts/stages/submission.py`，通过 MCP 函数 `submit_stage_result` 接收实际产物路径、简短说明和限制。审计、环境构建、场景设计、蓝队验证、红队场景构建、独立审核及经验学习的 Claude 启动入口加载此工具；红队独立模型循环提供同名结构化动作。智能体可多次提交，返回 `needs_revision` 和具体缺失项，修正后再次提交；通过后返回 `accepted`、产物 SHA-256 和检查范围，每次记录独立保存于指定输出目录的 `.stage-submissions/<stage>/`。

当前检查范围明确为 `artifact_contract`：复用报告质量检查、场景格式检查、审核结论格式检查；环境额外核对实际 Docker 镜像编号和已声明验收记录，场景设计检查设计文件与同名图片。其余交付检查文件结构及状态。提交成功不等于漏洞验证通过，不以模型自述替代执行证据；原有动态验收、来源绑定、随机标记核验、阶段脚本检查和人工验收仍须通过。这一轮不把收据自动升级为整条流程成功，历史任务没有收据时也不伪造补写。工具使用受限输出目录，拒绝越界路径和符号链接越界。已接入输出位置的交付记录可在节点轨迹选择器查看。

恢复汇总中没有重新执行环境构建时，环境节点关联同项目原始运行中的环境构建会话，并标为“原始运行”，不再误报暂无轨迹；若恢复运行确实启动过新构建，则展示本次记录。


阶段技能改进现支持八阶段分别提炼通用与仓库专属规则，按版本加载并记录本轮快照；安全审计阶段新增覆盖记录、假设追踪和复审计划，作为阶段反馈证据进入候选队列。第 08 阶段默认通过请求让宿主机调用本地 SkillOpt 核心重写入口，结果转换为现有候选；候选经现有前后对照评估后才发布，支持回退。终态与单节点重跑采集各阶段反馈，保留缺失、受阻和不确定状态。连续迭代使用有轮数和无改善停止条件的命令行控制器，默认不自动启动；没有可信评估套件时只积累候选。详见 [阶段技能改进说明](../docs/stage-skill-evolution.md)。


### 验证阶段的模型连接与报告传递

蓝队、攻击场景、红队场景构建和独立审核共用 `scripts/stages/claude_connection.py`，统一模型前缀、服务地址和鉴权；Claude 命令只读取项目及本地项目设置，避免个人设置将模型切换到其他服务。红队批处理通过 `--report` 校验本轮报告、绑定项目与运行编号并记录内容摘要，不依赖仅包含已结束运行的发现记录表；未指定报告的离线入口仍按指定历史发现解析。蓝队与红队的全部受阻、部分受阻分别记录为 `blocked`、`partial`，主流程汇总为降级，看板依据实际结果展示，不能仅凭汇总文件存在就显示完成。历史运行产物保持原样。


环境构建阶段将平台、验收记录和能力限制保存到本次 `env-phase.json` 的 `final.capabilities`，历史展示优先读取该快照。旧记录仅在共享清单仍绑定同一项目、源码路径和镜像，且验收时间不晚于本次阶段结束时读取其说明；条件不符时只显示已有阶段记录的能力范围，不套用后来的环境说明。


轨迹面板按项目、运行、节点及具体调用缓存最近会话信息（最多 24 条、30 秒），鼠标移入或键盘聚焦节点时提前准备，并合并同一次准备请求。源日志版本变化、缓存过期或点击“同步会话”时重新读取；运行中的会话仍按原周期检查更新，更新日志时保留已有会话页面。首次准备期间可直接选择“查看原始记录”，并可返回会话视图。后台并行进行轨迹导入与服务准备，复用短期健康检查；新转换结果按源文件路径、大小和纳秒修改时间判断缓存是否有效，不依赖导入时间与源日志时间比较。


蓝队验证在阶段内部按候选并行执行，默认并发上限为 10；命令行 `phase4_verify_agent.sh --jobs N` 可设置 1–10，`--max` 仍控制选取总数。主流程等待全部候选结束后再进入红队阶段。每条候选使用独立进程组、隔离执行目录、报告和日志；调度器原子写入 `verify/agent/tasks/<候选编号>.json`，各任务分别写 `verify/agent/<候选编号>/result.json`，父进程按原报告顺序生成总汇，多个任务不同时追加同一结果文件。取消时终止活动任务进程组，未启动任务记录已中断。

蓝队轨迹面板显示各候选的排队、运行、确认、排除或受阻状态，点击候选只打开其对应轨迹，“查看报告”读取该候选的独立报告。节点重跑使用稳定的候选编号关联轨迹，不因新增其他日志改变编号；报告接口校验运行、候选与重跑批次，不读取模型提供的任意路径。旧串行批次单独标注，不把正在执行的旧任务强行改为并发。

蓝队包装器启动后执行脚本快照，后续发布不改变运行中批次的汇总代码。汇总异常的历史批次可在校验逐候选报告后恢复汇总；保留原退出码与恢复凭据，界面明确标注仅恢复汇总，候选没有重新执行。

蓝队节点显示本批次候选数量和确认、排除、待定、受阻计数，部分候选受阻时显示“部分受阻”，保留底层降级状态。执行记录数量单独放在“日志与历史记录”中，包含智能体会话、执行器日志和批次日志，不作为候选数量。抽屉显示本批次选中数、原审计报告候选总数及逐条受阻原因；单节点重跑的结果统计读取最新重跑产物，不混用原流程旧汇总。

红队场景构建的独立重跑由 `ui/server/node-retries.mjs` 和 `ui/server/redteam-lab-retry.mjs` 调度，读取本轮审计报告快照与原红队候选清单；清单缺失时从严重和高危中选择蓝队已确认且产物完整的候选，最多 5 条。候选必须属于当前项目和运行，源码目录必须可用；调用现有场景构建智能体及其技能，使用当前红队模型。每条候选的输入、场景、构建日志和交付检查写入本次重跑的 `output/redteam/inputs/` 与 `output/redteam/labs/<id>/`，实时汇总写入 `output/redteam/summary.json`。不覆盖共享场景目录；场景构建完成后由无人值守调度另建06任务，按证据继续审核和学习；场景仍按原有源码与候选哈希、支持的攻击面和隔离条件校验，受阻不会冒充可用。关闭轨迹后刷新节点状态，独立重跑期间继续自动轮询，完成后采集对应阶段技能反馈。

红队执行的独立重跑由 `ui/server/redteam-agent-retry.mjs` 调度，从最新场景构建重跑、主流程红队汇总或共享场景目录解析候选，只执行同时具备候选文件和可用场景的条目。每个候选使用当前红队模型和独立运行根目录，输出写入本次重跑的 `output/redteam/agent-runs/`，逐候选状态与汇总写入 `output/redteam/tasks/` 和 `output/redteam/summary.json`；默认最多 10 条并行。节点重跑不自动启动独立审核，也不覆盖原始红队结果。

完整项目流程与红队构建重跑共用 `scripts/redteam/blue_handoff.py`：只接收同一项目、同一轮报告的最新已结束蓝队批次，最新批次运行中或失败时不回退旧结果。候选须有真实运行确认、匹配当前镜像编号的报告、与本轮候选内容一致的输入、验证脚本和全部引用证据。未确认、静态确认、产物缺失或版本不符的候选不启动构建，原因写入 `redteam/selection.json` 的 `excluded` 并在队员列表展示；全部不满足时记录受阻，不标为已完成。

每次构建将通过检查的文件及内容摘要保存到本批次 `redteam/blue-handoff/<id>/`；构建者再复制到自身场景目录 `blue-verification/`，通过 `lab-task.json` 的 `blue_handoff` 读取。交付快照绑定报告、候选和源码版本，构建前复核摘要，防止误用其他批次或改动后的文件。蓝队材料仅供场景构建者核对真实入口与对照，不传给红队攻击执行者；后者仍只读取原始候选与必要场景信息，独立获取新随机标记。未指定 `--report` 的离线历史发现入口保留原行为，不表示已通过本轮蓝队检查。

红队场景构建在候选之间并发，独立重跑和完整项目流程均默认最多 10 条同时构建；并发上限与候选选取总数分开，继续使用本轮选定候选。完整流程的 `batch.py --build-jobs 1..10` 可调整构建并发，全部构建结束后按候选并行执行红队；`--agent-jobs 1..10` 和 `--judge-jobs 1..10` 分别控制红队执行与独立审核并发，默认均为 10。新场景和日志写入本批次的 `redteam/batch/construction/labs/<project>/<id>/`，任务进度原子保存到 `construction/tasks/`，不会并发覆盖共享场景；已有场景仍按原规则校验后复用。独立重跑使用各自的 `output/redteam/labs/<id>/` 和 `output/redteam/tasks/`。界面显示每条候选的排队、构建中、可用、受阻和独立轨迹入口，交付接口绑定当前运行与重跑批次，只读取约定目录下的场景、报告和受阻说明。旧串行批次保持原执行方式并单独标注，新批次使用并发。

### 长节点与构建任务的持久等待

原生工作流中的节点调用只登记或查询任务；任务文件保存进程身份、心跳、截止时间、输出和退出码。节点返回运行中后，当前协调会话可以结束，宿主机继续持有项目锁并等待磁盘任务终态，再通过保存的原生工作流协调剩余节点。相同计划重复请求只接管原任务，不在十分钟后重新启动01。模型文字与会话退出码不能代替任务交付回执。

01的正式构建同样使用持久任务；模型会话结束不会终止构建。环境启动器先等待已登记构建实际结束，再在需要时启动仅做验收的有界会话；验收会话不能扩装依赖或重建。只有本次清单对应的有效交付回执才能算智能体验收完成，否则保留失败并交由既有备用流程处理。环境智能体具备 Monitor 和 TaskStop，读取任务状态和输出，不使用 Task 充当后台输出查询；专用钩子拒绝直接依附于模型会话的 Docker 构建命令。默认01只验收源码可读、Python可运行及隔离边界，额外导入、训练、GPU和服务能力未经验证时明确保留限制；后续验证仍需各自的真实证据。

执行链用 I—VIII 标示固定阶段；已完成轮数按同一项目原生工作流的完整八阶段交付计算，包括有明确降级或跳过结论的轮次，不代表八阶段全部成功，也不等于技能发布次数。节点重跑、失败及只执行后半段的流程不计完整轮数。
网页“启动连续循环”显式请求持续模式：每轮由原生工作流工具执行，结束后间隔五分钟进入下一轮；没有发布改善时保持当前技能，不绕过评估。调度失败停止并显示原因，停止按钮等待当前轮结束。原有命令行和未指定持续模式的接口仍保留最多三轮、连续两轮无发布改善停止的默认值。普通重新审计只运行一轮，返回箭头不代表已经启动持续任务。
左侧邮件图标进入“验证报告”；接口 `/api/verified-reports` 按候选单独整理影响、根因、触发条件、验证方法、审核结论、修复和证据路径。只有当前批次蓝队动态确认、红队证据核验、独立审核通过，并有匹配文生图插图和图文总报告才展示。新插图核验生成记录和内容哈希，历史插图仅兼容具有同路径模型响应缓存且文件未晚于缓存修改的记录；程序绘制的结构图不能满足条件。读取后续重跑尚未完成时不展示旧批次结果。


执行链标题下显示实际运行编号。候选问题来自最近有效报告，而最新任务可能是失败且没有正式报告的恢复尝试，两者不互相覆盖。编号不一致时明确提示来源差异，并提供“查看候选对应执行链”和“返回最新运行”切换；轨迹、产物和重跑始终绑定当前展示的运行。历史失败保留可见，不用候选数量推断最新任务已成功。

验证报告页默认展示全部项目，项目筛选由报告页独立管理，不继承看板的左侧筛选；标题显示当前数量与全部数量，选择器标明每个项目的报告数。


漏洞插图统一采用 technical-explainer-v1，模板位于 .claude/skills/project-cartographer/references/technical-explainer-prompt.md。场景设计智能体与备用文生图脚本都应用该模板：默认请求 1536×864，浅色背景、3–5 个真实技术实体、深灰组件、蓝色正常数据流、连续红色利用路径和具体检查缺口；允许必要的短技术标签，禁止故事人物、纸纹、安全或工业隐喻。矢量仅指视觉风格，仍完全由文生图模型生成位图。新任务不将旧故事插画缓存当成本样式完成项；历史产物保留。这里只验证提示词、请求与缓存选择，新风格的实际模型输出仍需生成后检查，不能把风格约束当作生成质量保证。

顶部实时审计任务卡片区已移除。左侧看板图标使用数字角标展示正在运行的项目数，按项目去重，不受当前筛选影响；无项目运行时隐藏角标，悬浮说明提供运行数量。既有实时状态轮询继续更新角标，具体运行状态和轨迹通过项目执行链查看。

项目缺少本地图标时，界面服务后台下载 GitHub 或 GitLab 仓库所有者头像，不阻塞审计和页面；并发请求合并，失败后十分钟内不重复请求。仅接受受限大小的位图，完成后原子写入 ui/public/logos；图标从该目录直接提供，无需重新构建页面。下载失败时继续使用默认图标，不影响项目运行。


报告下载统一提供 ZIP 包，原始模型 Markdown 保持不变。通用导出器解析 Markdown 的图片、附件链接和引用式链接，递归收集同一产物范围内的资源与被链接章节，并在包内报告副本中重写相对路径；外部网页链接保留，外部图片、缺失附件、越界或符号链接明确报错。节点产物页的 Markdown 下载复用该导出器，不依赖模型措辞、固定文件名或某个项目。
邮箱报告包另按该候选的阶段结果收集 AI 插图、蓝队验证报告与落盘证据、验证程序、红队场景和工具轨迹、独立审核结果，生成来源及 SHA-256 清单，不包含整个运行目录或其他候选的文件。每文件上限 10 MiB，总文件内容上限 32 MiB；必需证据缺失则停止导出。下载前重新检查当前报告是否满足展示条件，客户端不能指定服务器文件路径。


交付清单按文件类型校验：普通文件记录 SHA-256；同一交付目录内的相对文件符号链接记录链接文本、解析目标和目标内容哈希，下游继续使用前重新核对。绝对路径、越界、悬空、循环和目录链接均阻断，不使用仓库名称或库名例外，也不跟随未知链接。所有文件仍进入清单，没有静默跳过依赖文件。
交付检查失败按 artifact_contract 分类，责任为 workflow-delivery；阶段执行失败另行分类。已完成批次的指针在交付成功前保留。恢复流程只在项目、运行、工作流所有者、阶段、输入总报告哈希及全部上游产物快照完全匹配时复用最新完成批次；已有成功回执再次校验，失败任务归档。条件不符则不复用旧结果，不通过反复调用模型掩盖交付问题。

左侧验证报告邮件图标使用数字角标展示实际可阅读报告总数，与报告列表共享同一接口数据，每三十秒更新，也可在报告页手动刷新。数量不使用待人工验收候选数，不受看板或报告页项目筛选影响；读取失败时保留上次成功数据并在报告页提示错误。

报告项目身份采用交付前与消费前双重校验：统一报告检查器从受控运行目录确定项目编号，也支持启动器显式传入；模型显示名称只能写入 project_name。旧版 metadata.project_id 由统一解析器兼容，顶层与旧版编号冲突时拒绝。原生工作流在 II 阶段冻结报告前及后续节点读取报告时核对启动任务的项目编号，两种编号均缺失、字段冲突、品牌名或其他项目均拒绝，错误分类为 artifact_project_identity。校验不使用人工别名表，也不自动改写已冻结报告及哈希；生产者收到修改意见后应重新提交正确产物。

项目列表不再在每个项目右侧重复显示人工整理数量；候选总数仍在项目名称下方显示。

导入已有 GitHub 仓库时，按主机、所有者和仓库名称比较身份，兼容 HTTPS、SSH 及 Git 地址重写；仍拒绝不同主机、所有者或仓库，保留已有源码和提交版本。

阶段二使用固定版本 agentcov 解析工具实际返回的读取范围；派发前登记审计意图、覆盖编号、假设与范围，并关联各子会话。每波可刷新读取汇总用于后续规划，退出时汇总到 task-artifacts/read-coverage/summary.json 与 summary.md，随现有阶段二交付清单冻结，经验学习沿用现有证据入口读取。仅阶段二启动器启用采集；其他阶段不增加采集。搜索命中、未知范围、未关联意图与采集异常分开保留，不改变验证状态，不计算全仓库覆盖率。历史运行不回填，工作副本遗留读取记录不会计入新一轮。


交付契约更新：报告身份由 scripts/workflow/delivery_contract.py 统一解析，兼容顶层 project 和旧版 metadata.project_id；两者同时存在必须一致，并与任务编号精确匹配，不使用品牌别名，也不改写已冻结报告。新报告模板写顶层 project 与 project_name。工作流所有阶段共用版本化交付清单：普通文件与安全的相对文件链接继续校验内容摘要；带有效 pyvenv.cfg 的 Python 虚拟环境形成 runtime_only 快照，记录配置、每个文件摘要及链接文本，不跟随容器解释器链接，不作为可移植证据。蓝队交付额外校验报告明确引用的脚本、候选和证据附件，缺失、越界或仅存在于临时环境的引用仍阻止交付；红队交接与报告下载复用相同分类，环境只导出配置和快照。此分类不按 venv 等目录名跳过，也不放宽普通产物的链接校验。计算已完成而交付失败时，沿用同一工作流、项目、上游摘要和完成批次重新校验，不重复调用模型。

验证报告的有效性检查与阶段交付工具统一校验附件，不能仅凭 verdict 接受报告。附件不完整但有验证脚本时，由执行器在干净输出目录重跑受控验证，保留原始暂存产物及脚本依赖；不让模型手动复制部分结果。旧运行可使用交付恢复命令从报告 SHA-256 完全相同且附件完整的执行目录补齐缺失文件，拒绝内容冲突，不生成或伪造日志。环境生成器对 Java 使用无图形界面的 JDK，并使用 BuildKit 的软件包缓存和有界下载重试；仍保留构建总时限，网络持续不可用时如实受阻。

阶段八优先修订方法规则，使用真实执行文档并绑定摘要；基线变化后拒绝发布旧候选。项目知识与程序故障单独归因，缺少真实评估时不声称有效进化。详见 [Markdown 优化边界](../docs/rsi-markdown-optimization.md)。

全局项目并发上限由 config/system.json 的 projectConcurrency 配置，当前为 5。完整原生工作流及独立节点重跑在调用模型前统一申请项目名额，其内部节点沿用同一名额，不重复占用。超出上限的任务持久化排队，按排队顺序取得名额，完成、失败或停止后释放；连续循环每轮重新排队。部署前已有活动工作流计入占用，不强制终止。项目内成员并发保持原配置，此上限不是 API 请求数限制。


反馈引导探索已接入阶段二与阶段八。阶段二读取 task-artifacts/exploration-plan.json，以区域、视角、假设和证据组织任务，energy 为 0—3 建议档位，并保留探索份额；智能体可基于新证据调整，不改变总时限或验收条件。读取新区域提供弱信号，证据变化提供封顶过程信号；强奖励只复用 /api/verified-reports 的严格验收并按独立根因去重，接口不可用时不产生强奖励。报告奖励仅记录关联，不能证明 skill 的因果收益。

阶段八默认直接提出 Markdown 补充，SkillOpt 改为 RSI_SKILLOPT_ENABLED=1 时可选。新生成、provenance.change_kind=method 的阶段二候选可进入项目限定短期试用；通用候选也只在来源项目试用。试用记录位于 rsi/exploration/<project>/，不修改稳定 active.json。工作流启动时固定试用版本；执行文档摘要变化则不加载。试用观察三轮后，有持续过程收益可保留为项目限定规则；连续两轮无收益或循环运行失败会收回，保留历史记录。保留不等于全局稳定发布。其他阶段仍使用原评估发布机制。

阶段二允许使用文档检索工具按项目需要查询同类 CVE、维护者公告和修复提交；检索不可用时保留限制。外部资料仅作为假设来源，必须回到当前源码核实。临时方法笔记位于 .workspace/findings/skill-experiments/，通过补充上下文读取，不冒称动态注册原生 Skill；长期方法通过现有候选机制试用。

蓝队正式报告只按批次 summary.json 中候选编号选择，诊断与历史报告保留归档但不作为当前候选验收。红队正常执行但未捕获标记记为 degraded，不提升证据等级；真实执行错误仍 failed，并单独记录目标触发次数与未触发原因。操作日志存放于独立会话目录，正式交付冻结其只读快照；旧日志恢复必须核对原长度及原 SHA-256，仅保存匹配前缀，归档迁移记录，不修改原证据。环境构建智能体在下载前检查发行版、架构和候选包；缺索引明确为 unknown，不猜测可用。
